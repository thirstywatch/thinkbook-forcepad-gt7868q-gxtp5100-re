# 追加三十三 — GT7868Q 架构定案：Turbo51（8051 兼容核）

> 2026-09-30 · 纯软件离线（联网检索 + 本地源码/固件分析）· 零设备操作
> 承接 `追加三十二`。本文回答"GT7868Q 是什么架构"，并给出由此产生的结论修正。

---

## 〇 一句话现状

**架构定案：GT7868Q 属于 Goodix GT 系列，内核是 `Turbo 51`（8051 二进制兼容的增强核，双核架构）。**

**但由此得到一个重要的负面结论：**
**GT7868Q 主体（已解密）不是 8051 代码** —— 它的 8051 特征甚至**低于随机基线**。
⇒ `追加三十二` 的"主体可能是非 ARM 自研 CPU 代码"这一假设（假设 3）**被排除**，
**剩下两个假设（数据 / 内层编码）**，且"代码在芯片 ROM"的可能性上升。

---

## 一 ★★★ 架构证据链（四路独立，互相印证）

### 1.1 Goodix GT 系列数据手册的**芯片框图** —— 直接写出内核名

从 Goodix **GT911 / GT928 / GT968 / GT9110** 的数据手册 PDF 中提取的框图（多处一致）：

```
Driving channels → Driver → Digital State Machine → DSP → 【Turbo 51(M)】 → ADC → AFE → Sensing channels
                                                              ↑
                                        OSC(60MHz) ----→ AHB → Memory → 【Turbo 51(S)】 → I²C → INT/RSTB
```

**框图里明确写着 `Turbo 51(M)` 与 `Turbo 51(S)`** —— Goodix 自研的**双核 Turbo51**（M=Master，S=Slave）。

**GT7868Q 属于同一 GT 系列**（QFN88 / I²C / Windows+Chrome 规范）。

### 1.2 IEEE 论文：TURBO51 **严格兼容 8051 指令集**

> 「TURBO51 是一款旨在提高 8051 微处理器性能的嵌入式处理器，**它在保持与 8051 指令集兼容的同时**，
> 通过引入 32 位系统架构元素（乱序执行、分支预测、一级指令缓存）提升性能。」

> 「Under the premise of **strictly ensuring compatibility with 8051 instruction set**」

> 「This core **retains full binary compatibility with the legacy 8051 instruction set**」

> 「支持标准 8051 内存空间：Internal RAM (lower 128 bytes)、**SFRs**、**External Data Memory (XDATA)**」

**⇒ Turbo51 = 8051 二进制兼容。这是关键推论的前提。**

### 1.3 官方更新工具源码里的 8051 痕迹

本地已克隆的 `goodix/gdix_hid_firmware_update`（`E:\...\poc\gdix-hid-fw\`）：

| 证据 | 出处 |
|---|---|
| `gdix_err("Failed write cfg to **xdata**, ret=%d\n", ret)` | `gt7868q_gt7868q_update.cpp:516` · `gtx8_gtx8_update.cpp:511` · `gtx3_gtx3_update.cpp:469` |
| `#define FLASH_BUFFER_ADDR **0xc000** // X8=0XDE24` | `gt_update.h` |
| `#define CFG_START_ADDR **0x96F8**`（GT7868Q）/ `0x60DC`（GTX8）/ `CMD_ADDR 0x60CC` | 各 update.cpp |
| `class GTx8Device : public **GTx3Device**` | `gtx8_gtx8.h` |
| `class GT7868QFirmwareImage : public **GTX3FirmwareImage**` | `gt7868q_gt7868q_firmware_image.h` |

**"xdata" 是 8051 专有术语**；`0xc000` / `0x96F8` / `0x60CC` 全是 **16 位地址**（8051 xdata 上限 64 KB）。

### 1.4 原厂固件的自我标识

`GT7868Q` 容器头部描述符：`xx xx xx xx 59 45 4c 53 54 4f(YELSTO) 00 00 06 37 38 36 38 51(7868Q)`
—— 与 GT9896（`9896`）结构同源，同属 GTX 系列。

## 二 ★★ 但主体不是 8051 代码（决定性否证）

既然 Turbo51 与 8051 二进制兼容，**若主体是代码，标准 8051 反汇编必须成立**。

### 2.1 自建 8051 反汇编器后的实测统计

（加扰区 `0x1200-0x19A00`，排除 0 起始后 45,426 条"指令"）

| 操作码 | 实测占比 | 真 C51 输出应有 |
|---|---|---|
| `0x22` RET | **0.407%** | 1–3% |
| `0x12` LCALL | **0.451%** | 1–3% |
| `0x74` MOV A,#imm | **0.117%** | 3–8% |
| `0x75` MOV direct,#imm | **0.075%** | 2–6% |
| `0xE5` MOV A,direct | **0.216%** | 3–10% |
| PUSH(0xC0)/POP(0xD0) 比值 | **3.81** | ≈1.0 |

### 2.2 综合指标 sig（比单项更有力）

```
sig = RET% + LCALL% + MOV A,#imm% + MOV direct,#imm%

  真 C51 输出      sig ≈ 7 – 20
  随机字节基线      sig ≈ 1.56        （每项 100/256 = 0.39%，四项合计）
  GT7868Q 全段均值  sig = 0.90        ← 低于随机！
  GT7868Q 最强 4KiB 区（0x0C200） sig = 1.56  ← 恰好等于随机
```

**⇒ 不仅"不像代码"，那几个关键操作码的**出现率甚至低于随机** —— 被系统性抑制。**

### 2.3 函数量反推

RET 仅 185 条。按每函数 40–80 字节估算，对应代码量 **7.4–14.8 KB**，
而主体实际有 **99,840 B**（差 7–13 倍）。

### 2.4 反汇编直验（最强候选区 0x0C200，人眼可判）

```
0C202  f541           MOV dir,A      0x41
0C207  c020           PUSH dir       0x20
0C20A  d55d8e         ?D5            0x5D8E      ← DJNZ 但形态可疑
0C218  9084fd         MOV DPTR,#     0x84FD
0C233  32             RETI                        ← 孤立 RETI
0C238  900000         MOV DPTR,#     0x0000
```

**孤立 PUSH/RETI、大量无上下文的 16 位装载 —— 不是编译器输出。**

### 2.5 已排除的其他架构

| 假设 | 判据 | 结果 |
|---|---|---|
| ARM/Thumb | BL 14.8/KB ≈ 随机 15.7；32 位指令 48.2 ≈ 随机 46.7；MOVW 0.1/KB | ❌ |
| 字节重排的 Thumb | 16 位交换 / 32 位反转 / 去交织 k=2,4 | ❌（比均值 0.30–0.84，全 <1） |
| 标准压缩 | 无魔数；zlib / lzma 解压全失败 | ❌ |
| **8051 / Turbo51** | **sig 0.90 < 随机 1.56** | ❌（本文） |

## 三 修正 `追加三十二` 的三种假设

| # | 假设 | 本轮更新 |
|---|---|---|
| 1 | 主体是数据/配置表，**代码在芯片 ROM** | ⬆️ **可能性上升** —— 框架图显示 Turbo51 双核 + Memory + DSP，ROM 代码是标准做法 |
| 2 | 有内层加密/编码，K 只解外层 | ⬆️ **上升** —— 关键操作码"被抑制到低于随机"不像纯数据，更像**经过字节级映射** |
| 3 | ~~非 ARM 的自研 CPU 代码~~ | ❌ **已排除** —— 已确认是 8051 兼容核，且主体不符合 8051 代码特征 |

**⚠️ 关键约束（来自 `追加三十一` C2）仍然成立**：
0 填充区解出**真 0**，且其密文严格 1024 周期（1.000000）—— 这对"假设 2 的整段加密"不利，
**更支持"主体是分块的：明文数据块 + 另一种处理的代码块"**。

## 四 由此产生的新线索：官方固件包结构

从 `gtx8_gtx8_update.cpp` 的 `fw_update()` 完整读出**固件镜像格式**：

```
镜像头（0 - 255 B）
  [15..22]  PID（8 B）          ← "7868Q"
  [23]      CID
  [24..26]  VID（主/次版本）
  [27]      子固件数量
  [32..]    子固件信息表（每项 8 B）
              type(1) + len(4, 大端) + flash_addr(2, 再 <<8)
  [256..]   子固件数据（依次紧排，长度见信息表）

子固件类型：按位选（firmware_flag & (1 << sub_fw_type)）
配置子固件：每项 3 B（id + len(2)），数据紧随其后
```

**⇒ 固件是"多子固件拼装"，每个子固件写到各自 flash 地址。**

**这解释了主体为什么"结构分层"**（0 填充、128 字节尺度、地址成簇），
**也给出了下一步的抓手**：如果能拿到各子固件的 `type` 与 `flash_addr`，
就能知道"哪一段是代码、哪一段是配置"。

**另外：`CFG_FLASH_ADDR = 0x19000`（GT7868Q）** —— 配置的 flash 地址。
实测文件偏移 `0x19000` 处（解密后）是高熵内容；而 `0x19800-0x19A00` 解出的是**纯 K 重复**
（说明加扰区实际延伸到 **0x19A00**，比原来记的 0x19800 多 512 B）。
