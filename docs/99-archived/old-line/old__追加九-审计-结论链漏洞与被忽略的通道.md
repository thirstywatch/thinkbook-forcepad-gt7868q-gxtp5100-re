## §1 ★★ 自我更正：09-14 是两次实验，其中一次用的是**表内合法**子命令

我在 追加八 §8 断言"那次真机测试用的是表外子命令 ⇒ 该测试无效"。**复查原始日志后，这个断言过严了。**

### 1.1 原始日志事实（`probe-logs/col04-A1-realmachine-20260914.txt`）

| 时间 | 帧 | 子命令（按工具写法 `pkt[2]/pkt[3]`） | 是否在 `0xA1` 的 22 条表内 |
|---|---|---|---|
| **11:15:50** | `0E A1 0F 00 05 01 18 00 00 1B` | `0x000F` | ❌ **表外** |
| **23:40:29** | `0E A1 00 0B 05 01 18 00 00 1B` | **`0x0B00`** | ✅ **表内合法！** |

日志抬头原文：
```
# 帧: 0E A1 00 0B 05 01 18 00 00 1B   (sub=0x0B00, H1 写法)
# 结论: send=True err=0; 之后纯读 6 种长度全 err=122; 无 0xA2 应答 -> H1 否
...
对照: 历史 11:15:50 发的是 0E A1 0F 00 05 01 18 00 00 1B (sub=0x000F => pkt[2]=0F pkt[3]=00)
```
⇒ **那次决定性的 H1 实验，确实把子命令改成了表内合法的 `0x0B00` 重发了一遍**（这正是项目当年"更正字节序"的产物）。
而 `PREFLIGHT-STATE §6.9` 引用的也是这一条（`0B 00` 版）。

**⇒ 所以不能说"该测试无效"。** 它是否有效，取决于**子命令在 Col04 报文里的偏移**，而这一点有两种自洽的可能。

### 1.2 两种封装假设，交叉后结论如何

| 假设 | 子命令位置 | 23:40 那条帧的判定 | 推出的结论 |
|---|---|---|---|
| **H-b：结构化重组**（GT7868Q 把 `pkt[2]/pkt[3]` 当子命令转发） | `pkt[2]/pkt[3]` | 子命令 = **`0x0B00`（表内合法）** | 23:40 是**有效实测**，结果为否 ⇒ **实测封死** |
| **H-a：原样转发**（`wire = pkt[1..]`） | `pkt[4]/pkt[5]` | 子命令 = `pkt[4]\|pkt[5]<<8 = 0x0105`（表外） | 该帧无效；**但**：TF100A 的 38 条子命令里 **37 条低字节恒为 `0x00`**（`0xNN00` 形式），而这位置在 Col04 协议里是**长度字段** ⇒ 主机**极难构造出合法子命令** ⇒ 结构上接近封死 |

**⇒ 无论 H-a 还是 H-b，结论都是"主机侧封死"，但支撑方式完全不同：**
- H-b ⇒ **实测封死**（有一条有效的真机实验）；
- H-a ⇒ **结构性封死**（子命令编码与 Col04 帧布局冲突），但需要额外确认 `pkt[4]=0` 会不会被 GT7868Q 直接拒掉。

**⇒ 结论方向不变，而且这是"两条独立论证"，比 追加八 里"只有一条推断"要好。**
**⇒ 但我在 追加八 §8 与总表 §2.2 里的措辞必须更正**（已在本文 §1.3 给出替换文本）。

### 1.3 建议替换的措辞

> 原（追加八 §8 / 总表 §2.2）：「那次真机测试用的是表外子命令 ⇒ 该测试无效 ⇒ 结论靠推断」
> **改为**：「09-14 做了两次实验：11:15 那次用 `0x000F`（表外，无效）；**23:40 那次用 `0x0B00`（表内合法）**，结果 send=True 但 6 种长度读取全 `err=122`、无 `A2`。
> ⇒ 若子命令在 `pkt[2]/pkt[3]`（H-b），这就是**一次有效的实测封死**；
> 若子命令在 `pkt[4]/pkt[5]`（H-a），则该帧仍表外，但**TF100A 的 37/38 条子命令低字节恒为 0，与 Col04 的长度字段位置冲突** ⇒ 主机在结构上难以构造合法帧。
> ⇒ **两种封装假设下结论一致（封死），性质不同（实测 vs 结构）。**」

## §2 ★★ 「收口测试」的论证前提被日志推翻

### 2.1 原始数据（`opcode-sweep-log.txt` + `sweep-ops.ps1`）

```powershell
# sweep-ops.ps1
# 跳过: 0x10/0x11(切patch/开始更新) 0x12(load flash) 0x13(软复位,会重启IC) 0x20(内存读写)
$skip = @(0x10,0x11,0x12,0x13,0x20)
```
```powershell
$p = New-Object byte[] 65
$p[0] = 0x0E; $p[1] = [byte]$op; $p[4] = 0x01; $p[5] = 0x01     # ← 探测帧
```

日志实测覆盖：

| class | 结果 | 说明 |
|---|---|---|
| `0x00`–`0x0D` | **OK**（返回 24 字节） | **已实现** |
| `0x0E` / `0x0F` | FAIL `err=122` | 未处理 |
| `0x10`–`0x13` | **未测**（脚本有意跳过） | 已知是"切 patch / 开始更新 / load flash / 软复位" ⇒ **已实现** |
| `0x14`–`0x1F` | FAIL | 未处理 |
| `0x20` | **未测**（脚本有意跳过） | **liveness 就在用它**（`readMem`，能稳定返回 12~16 字节）⇒ **已实现、且能应答** |
| `0x21`–`0x2F` | FAIL | 未处理 |
| `0x30` 起 | **未测** —— liveness 探针在 0x30 **之前**就已失败，脚本 ABORT | |
| `0x30`–`0x7F`、`0x80`、`0xA0`、`0xA1` | **从未测过** | |

### 2.2 ⇒ 推理链的问题

**「收口测试」的原论证**（总表 §2.1）：
> GT7868Q 已实现 `0x00`–`0x0D` 这 **14 个连续 class**，而触觉在 `0xA0`/`0xA1` 分区 …
> ⇒ 中间件要么是**纯 TARGET 路由器**，要么是 **PARSE_ONLY 白名单** ⇒ **扩展命令从进线起就不认**。

**问题**：日志证明已实现的 class **是分段的**：`0x00–0x0D` **+** `0x10–0x13` **+** `0x20`（≥ **19** 个，不是 14 个，而且**不连续**）。
⇒ "已实现跨度 ≥ 16 个**连续**单位"这个前提**不成立** ⇒ 由连续性推出的"纯路由器 / 白名单"**失去依据**。
⇒ **正确表述**：`0x30–0x7F`、`0x80`、`0xA0`/`0xA1` 的状态是「**未测**」，不是「结构上试不到」。

### 2.3 但"不能扫描"这一条**仍然成立**（论证要换）

日志的关键事实不是"0x30 把我打断"，而是：
```
[  23.72s] LIVENESS before 0x30: readMem(0x0000,16)  send=True/err0  recvFAIL/err122
ABORT at 0x30
```
**在 0x30 还没被发送之前，连"已知有效"的 `readMem` 都已经不应答了。**
⇒ 真正的教训是：**设备的应答能力会被累积流量拖垮**（26 个无效 class × 400 ms 间隔 ≈ 23 秒之后通道就废了）。
⇒ **「大规模扫描不可行」成立；「结构上不存在」不成立。** 两者必须分开说。

### 2.4 顺带：sweep 的帧结构本身可疑（见 §5）

`pkt[4]=0x01, pkt[5]=0x01` 与 `Gx.cs` 的合法帧（读 = `pkt[4]=5, pkt[5]=1`）不一致 ⇒
**对"需要子命令"的 class（`0xA0`/`0xA1`），扫 class 这种方法天然不可能成功** —— 它们要的是子命令，不是 class 探测。

## §3 ★★ 被忽略的通道：Col04 class `0x20` = host→device **内存读**

### 3.1 事实（`Gx.cs` + `scan-mem.ps1` + `mem-now.txt`）

```csharp
// Gx.cs —— 注释原文："Goodix 厂商命令通道（已实测可用）"
读:  0E 20 00 00 05 01 <addr16BE> <size16BE>
写:  0E 20 00 00 <len+7> 00 <addr16BE> <len16BE> <data...>
/// 32 位地址帧读取（BRLB 家族帧；地址可为 0x08000000 等 MCU 空间）
public static byte[] Read32(uint addr, int size, out string log)
```
```powershell
# scan-mem.ps1：把 16 位地址空间整块读下来（纯读，非破坏性）
for ($a = 0; $a -lt 0x10000; $a += 60) { $d = [Gx]::Read($a, 60, [ref]$log) ... }
```

**实测后果**：`mem-scan-16bit.txt`（205 KB）= **整个 64 KB 窗口的转储**；`mem-now.txt` 是抽样。
其中 `0x4000` 处能看到明文标识：`59 45 4C 53 54 4F` = **`YELSTO`**、`37 38 36 39` = **`7869`**
—— 与项目 `fw_identity_audit.py` 在固件容器里找到的 `YELSTO`@0x1142 / `7868Q`@0x114B **同源**。

⇒ **class `0x20` 是一条已经跑通的、主机侧可达的"设备内存读"通道。**

### 3.2 ★ 但"32 位地址路线"**从未走过**

- `Gx.Read32()` 存在，注释明说"地址可为 `0x08000000` 等 MCU 空间"（= TF100A 的 flash 空间）
- 但**没有任何日志、脚本或报告记录过一次 `Read32(0x08000000, …)` 的成功或失败**
- 项目当时只用 `Gx.Read()`（16 位地址）扫了 64 KB，然后得出"读窗口不是 TF100A 的 RAM"（`PREFLIGHT-STATE §0.1 四`）

### 3.3 ⇒ 这直接命中一个悬置很久的证据等级问题

`PREFLIGHT-STATE.md §1` 原文（项目自己写的警告）：

> ⚠️ `【反推固件】` 这一级**最容易腐坏** —— 那份镜像**自称 `Test_FW` 且被截断**，
> **"它就是设备在跑的固件"从来没有被验证过。**

**⇒ 而现在有一条现成的通道可以去验证它**：
用 `Gx.Read32(0x08000000, 16)` 起步（纯读、16 字节），与本地 `touchpad_FW` 明文镜像的**头部若干字节**比对。

| 若能读出并匹配 | 意义 |
|---|---|
| **成功** | ① 把 20,314 行反汇编的全部结论从【反推固件】提升为【实测同源】；② 可以尝试 dump 100 KB 加密区；③ 可以读设备上**实际在跑**的 RAM 值（若 32 位读能到 RAM） |
| **失败** | 明确记录一条负结果（"32 位地址不可读"），把这条路关掉，不再有人重复 |

**先小步**：16 字节 → 若通再 256 字节 → 再谈 56 KB / 100 KB。
**风险**：纯读；但 `Read32` 的参数组合（`pkt[4]=7`）与已实测的读（`pkt[4]=5`）**不同**，属"未实测形态"，故按项目红线"单发、先小后大、前后体检"执行。

### 3.4 另一条从未做过的比对

`mem-scan-16bit.txt`（设备实际 64 KB 窗口）**从未与 GT7868Q 的固件容器做过比对**。
而 `YELSTO`/`7869` 已经在窗口里出现 ⇒ **两边确实有可比内容**。
这条比对（纯离线）能回答：容器里**哪一段与设备当前状态一致**、哪一段是加密的 ⇒ 也间接回答"加密区到底是什么"。

## §4 ★ Col04 IN 通道：180 秒 **0 报文**（监听实现正确）

### 4.1 监听实现经审计**没有问题**

`VendorListen.cs`：
- `CreateFileW(path, GENERIC_READ, FILE_SHARE_READ|WRITE, …, FILE_FLAG_OVERLAPPED)`
- 循环里 **`ReadFile` 异步 + `WaitForSingleObject`（1 s 超时）+ `CancelIo`**
- **不是** `HidD_GetInputReport` / `IOCTL_HID_GET_INPUT_REPORT` 轮询 ⇒ **没有踩项目红线**

⇒ `reports=0`、`idleTimeouts=179` 是**可信的**。

### 4.2 与本次新发现对照

`vendor-listen-log.txt`：`caps: inLen=65 outLen=65`；180 秒内 `reports=0`；
**同期用户持续触摸**（`[TOUCH] contacts=1/2` 反复变化，来自 Col02）。

而本次（追加八）新解出：**TF100A 主循环里有一个任务在持续上报**：
```
0x0800767C（mode==2 任务，main 在 0x0800FE20 调用）
  ├ 门控：[0x20004094]==2，且 [0x20005FF4+0x32]==1（数据就绪）
  ├ bl 0x0800CE94            ; 读 TIM3 计数
  ├ 取一个 u16 索引 → 取一个 u16 值
  ├ bl 0x0800BDE0            ; ★ 发 I2C 帧（[0x80][04][02][lo][hi] + 拉 PA3）
  └ 继续往 [[0x2000EC8]] 指向的缓冲区填 u16（偏移 0x578 / 0xaf0 …）
```

### 4.3 ⇒ 净结论

> **TF100A 会主动向 GT7868Q 上报数据；而主机在 Col04 IN 通道 180 秒收到 0 条。**
> **⇒ GT7868Q 不把 TF100A 的上报转出主机。**

**这条独立地加固了「不转发」的推断**（虽然严格说"上行不转发"≠"下行不转发"，但两者共用同一扇门）。
⚠️ **保留**：上报可能只在特定条件（模式==2 + 数据就绪）触发；那 180 秒里模式字节是否为 2 无从得知。

## §5 帧映射的新证据：`pkt[0]` 是 **HID report ID**，不是载荷

### 5.1 证据（`Gx.cs`）

```csharp
static bool Send(byte[] pkt) { var b = new byte[65]; Array.Copy(pkt,b,...); b[0] = 0x0E; ... }   // ★ 强制 b[0]=0x0E
static byte[] Recv() { var r = new byte[65]; r[0] = 0x0E; ... }                                    // ★ 强制 r[0]=0x0E
// 注释："经 Col04 自己的 OUT 报表 (rid=14, 65B) 发送"
```
而响应解析用的是 `r[2]`(cont) / `r[3]`(seq) / `r[4]`(len) / 数据从 `r[5]` 起 —— **`r[0]` 从头到尾没被当过数据**。

⇒ **`0x0E` = Col04 的 report ID（rid=14）。**

### 5.2 ⇒ 报文布局与 wire 的对应

```
Col04 报文（65 B）        TF100A 的 wire
  pkt[0] = 0x0E  ← report ID（HID 栈层面剥离，不进 wire）
  pkt[1] = class      →   wire[0]  → ctx+0x104   （分派器读这里）
  pkt[2] = b1         →   wire[1]  → ctx+0
  pkt[3] = b2         →   wire[2]  → ctx+1
  pkt[4] = len/dir?   →   wire[3]  → ctx+2       （子命令低字节）
  pkt[5] = dir?       →   wire[4]  → ctx+3       （子命令高字节）
  pkt[6..]            →   wire[5..]→ ctx+4..
```
⇒ 在 **H-a（原样转发）** 假设下，**子命令 = `pkt[4] | pkt[5]<<8`**，
而工具当年写的是 `pkt[2]=sub&0xFF; pkt[3]=sub>>8` ⇒ **不是"字节序"问题，而是"偏移差了 2"**。

### 5.3 这条映射的一个耐人寻味的推论

TF100A 的 38 条子命令里 **37 条低字节恒为 `0x00`**（形式是 `0xNN00`；唯一例外是 `0xA1/0x0203`）。
⇒ 在 H-a 下，主机必须让 `pkt[4]=0x00`；而 `pkt[4]` 在 Col04 协议里是**长度字段**（读=5，写=len+7）。
⇒ **两个语义在同一字节上冲突** —— 这是 H-a 下"主机难以构造合法命令"的根源（**可能**被 GT7868Q 直接判为畸形帧）。

## §8 红线（不变，并新增两条）

**原有全部不变**：不轮询 `Col04`；不枚举厂商命令空间；只发单发已知安全命令；异常先杀后台任务；触控板是唯一指点设备需备退路；恢复靠"关机+拔电+长按电源 30 秒"；刷机三连 `00 10 / 00 11 / 0E 12` 绝对不碰。

**新增**：
1. **`class 0x20` 的读通道虽已实测安全，但 `Read32`（32 位地址）是未实测形态** —— 必须**从 16 字节起步**、单发、前后用 `readMem` 体检；一旦出现 `err=122` 立即停手。
2. **禁止在真机上测试 §1 的"表内合法帧"** —— 要测只允许在**料板**上，或用**逻辑分析仪**改动观察（不改动）。
