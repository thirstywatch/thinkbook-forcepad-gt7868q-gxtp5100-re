## 一、★ 唯一剩下的软路径：Col04 `0xA0 / 0x0B00`（写波形缓冲）

### 为什么是它
项目 `COL04-BOUNDARY.md §2.2` 早就把 `0xA0` 的 16 个子命令列了出来，其中：

| 子命令 | 项目早已解出的含义 |
|---|---|
| **`0x0B00`** | **★ 触觉：写波形缓冲**（`0x080088C0(ctx)`） |
| `0xA2` | **回复类**（固件自己发，主机**禁发**） |

也就是说：**"往设备里写波形"这条命令，项目早就定位到了**，但一直没发成功。

### 卡在哪：**子命令的字节序**（项目 `§4` 原话）
> 固件侧的判定值形如 `0xNN00`，低字节必须是 `0x00`。而现有工具 `poc/VibLink.cs` 是 `pkt[2]=sub&0xFF; pkt[3]=sub>>8` ⇒ 内部读到的 u16 = `0x000B`，而固件在等 `0x0B00`。**永远不相等。**

项目当时设计了"零风险定案实验"（发帧后读回 `0x4134` 看映射），但**该实验的前提被真机实测证伪**（读窗口不是 TF100A 的 RAM 空间）⇒ 字节序问题**悬置至今**。

### ★ 今天的新证据（纯静态，来自反汇编）

1. **分派器怎么读子命令**（`0x0800E1C0`）：
   ```asm
   str  r1, [r0]        ; [0x20004940] = 传入的 ctx（实为 I2C 句柄 0x20004134）
   ldr  r0, [r0]
   ldrh r0, [r0, #2]    ; ★ 小端半分字：ctx[2] = 低字节, ctx[3] = 高字节
   cmp.w r0, #0x100 / #0x500 / #0xB00 / …   ; 期望 0xNN00
   ```
   ⇒ **要命中 `0x0B00`，必须 `ctx[2]=0x00, ctx[3]=0x0B`**

2. **TF→TP 发包编码器怎么写**（`0x0800BDE0`，5 字节帧头）：
   ```asm
   0800BDF0  movs r0,#0x80;  strb r0,[r1,#0x8c]   ; 命名空间 0x80
   0800BDF6  movs r0,#4;     strb r0,[r1,#0x8d]   ; 长度 4
   0800BDFC  movs r0,#2;     strb r0,[r1,#0x8e]   ; 子类型 2
   0800BE02  ldrh r0,[sp,#6]; strb r0,[r1,#0x8f]  ; ★ 参数**低字节先**
   0800BE0A  ldrb r0,[sp,#7]; strb r0,[r1,#0x90]  ; 参数**高字节后**
   ```
   ⇒ **该固件在报文里用的是"低字节先"**（与 §1 的小端读法一致）

3. **合起来的推论**：
   - 如果收/发使用同一套字节序（同一固件的自然写法），那么**主机应发 `pkt[2]=0x00, pkt[3]=0x0B`**
   - 而项目工具 `pkt[2]=sub&0xFF`（0x00）、`pkt[3]=sub>>8`（0x0B）**恰好就是这样** ⇒ **工具字节序其实是对的**
   - ⇒ 项目文档里那句"内部读到 0x000B"**很可能是读错了偏移/读错了窗口**（那次读窗口 `0x4134` 已被证伪）

### ⇒ 下一步（离线，1 轮就能定案）
**找到 I2C RX 路径把收到的报文写进 `[句柄 + 0..3]` 的代码**，与上面的发包编码器对照：
- 若也按"低字节先"存 ⇒ **字节序确认，可直接发 `0xA0/0x0B00`**
- 若做了交换 ⇒ 主机要按相反顺序发

**发帧纪律**（沿用项目红线）：**单发、≤2 往返/秒、前后体检、绝不发 `0xA2`**；先发**长度 0 或极短载荷**的 `0x0B00` 试探（`§2.5`：未列出的子命令是**静默 no-op，不会崩**；但 `0x0B00` 是**边界内**的写入类，需谨慎）。

# 追加四：★ 字节序定案（2026-09-28）—— 报文**不做任何字节交换**

> ⚠️ **2026-09-28 18:2x 更正**：本节 §3/§4 的**字节落位偏移是错的**（把 Col04 报文偏移直接当成 TF100A 内部偏移），
> 且"下一步很便宜"的判断**已被项目真机实测否掉**。**请直接看下面的「追加五」**；本节保留原文仅作推理轨迹。

## 1. 收包路径（反汇编实测，`0x08008A70` 起）

```asm
; 状态 0（收第一个字节）
08008A98  movw r1,#0x5410 ; movt r1,#0x4000      ; ★ I2C1_DR = 0x40005410
08008AA0  ldr  r2,[r1]      ; 读 DR（第 1 字节）
08008AA2  uxtb r2,r2
08008AA4  strh.w r2,[r0,#0x104]                  ; ★★ 第 1 字节 → [handle+0x104]（= 分派器读"命名空间"的地方）
08008AA8  ldr  r1,[r1]      ; 读 DR（下一个字节）
08008AAA  ldrh.w r2,[r0,#0x102]                  ; 收包计数器
08008AAE  adds r3,r2,#1
08008AB0  strh.w r3,[r0,#0x102]
08008AB4  strb r1,[r0,r2]                        ; ★★ 字节存入 [handle + 计数器] —— 从 handle+0 起顺序存放

; 状态 2（继续收）
08008AB8  ldrh.w r1,[r0,#0x102]  ; 计数器
08008ABC  cmp  r1,#0x7f ; bhi   ; 超 0x7F 报错
08008AC8  ldr  r2,[0x40005410]   ; 读 DR
08008ACA  adds r3,r1,#1
08008ACC  strh.w r3,[r0,#0x102]
08008AD0  strb r2,[r0,r1]        ; ★ 继续存到 handle+计数器
```

**两条硬结论**：
1. **收到的字节是连续存进 `handle+0`、`handle+1`、`handle+2`…**（`strb r1,[r0,r2]`，计数器在 `[handle+0x102]`）
2. **全程没有任何字节交换**（纯 `strb` 直存）⇒ **项目的 H2 假设（链路层做字节交换）被排除**

## 2. 与分派器的读法对上 ⇒ 字节序定案

分派器：`ldrh r0,[handle+2]`（**小端**：`+2` 低、`+3` 高）再与 `0xNN00` 比较。
收包：字节按序落在 `handle+0 / +1 / +2 / +3`。

**⇒ 报文第 2 字节 = 子命令低字节、第 3 字节 = 子命令高字节（小端）。要命中 `0x0B00`，主机必须发 `pkt[2]=0x00, pkt[3]=0x0B`。**

## 3. ★ 于是项目那条"永远不相等"要重新看

项目记录的历史帧是 **`0E A1 0F 00 05 01 18 00 00 1B`**：

| 字节 | 值 | 含义 |
|---|---|---|
| `[2]` | `0x0F` | 若按**小端**读 ⇒ u16 = `0x000F` |
| `[3]` | `0x00` | **`0x000F` 不在 `0xA1` 的 22 个合法值里** ⇒ 落到**静默 no-op 兜底**（`COL04-BOUNDARY §2.5` 已确认 no-op 不崩、不回）|

⇒ **那条帧拿不到 `0xA2` 应答，不是因为"字节序对不上"，而是因为它是"手搓的、子命令不在表内"的帧** ⇒ 必然 no-op、必然无应答。
而项目工具 `pkt[2]=sub&0xFF; pkt[3]=sub>>8`（低字节先）**恰好就是固件期望的顺序** —— 也就是说 **H1 成立（报文原样拷贝到 ctx），H2 不成立**。

**⇒ 结论：不是字节序的问题，是"发了一个不存在的子命令"。**

## 4. 因此下一步变得很便宜

按**正确字节序**发一条 **`0xA1` 类、子命令在表内**的帧（例如 `0x0400` / `0x0F00` / `0x0203`），**应当能拿到 `0xA2` 应答**；拿到应答即证明 **Col04 命令空间首次打通**，随后才谈得上试 `0xA0/0x0B00`（★ 写波形缓冲）。

**发帧纪律（沿用项目红线）**：单发、≤2 往返/秒、发前后体检、**绝不发 `0xA2`**；先从"查询类 `0xA1`"开始（`§3` 明确 `0xA1` 是只读族）。

# 追加五：★★ 收包路径完整解出 + 对「追加四」的更正（2026-09-28 18:2x）

## 0. 一句话

**TF100A 的收包路径已完整解出（调用链 + 结构体 + 逐字节落位）。结论：第 1 个字节被单独取走，其余字节整体前移一位 ⇒ 子命令落在 `wire[3]/wire[4]`（不是 `wire[2]/wire[3]`）。**
**因此"永远不相等"那条要整体作废 —— 但理由不是"字节序反了"，而是它把 Col04 报文的字段偏移当成了 TF100A 内部缓冲的偏移。**
**⚠️ 但这不构成新的可试路径：项目已真机实测过，结果是否（见 §7）。**

## 1. 完整调用链（反汇编实测）

```
I2C1_EV_IRQHandler = 0x08008978     ← 全镜像无任何代码引用它（grep 零命中）⇒ 向量表入口
  │  依次检查 5 组事件条件（evt_check(I2C1, code)）：
  ├─ 0x05010109 → 0x08008B30   ADDR：清计数器（= 一次事务的起点）
  ├─ 0x05060109 → 0x08008A70 ★ RXNE：收字节  ← 唯一的收包路径
  ├─ 0x05040109 → 0x08008A4C   PE-toggle 总线复位（读 SR1 → 回写 CR1）
  ├─ 0x05070109 → 0x08008AE4   TXE：发字节
  └─ 0x050?010A → 0x08008A1C   （另一事件）
```

**条件求值器 `0x0800FC80(base, code)` 的解码**（这条以前没解出，是本次的关键工具）：

| code 位域 | 含义 |
|---|---|
| `code[15:6]` | 寄存器**字节偏移** |
| `code[4:0]` | 该寄存器内的 **bit 号** |
| `code[31:22]` | 第二个寄存器的字节偏移 |
| `code[20:16]` | 第二个寄存器内的 bit 号 |

对 `0x0506_0109`：`0x0109>>6 = 4 → CR2`、`0x0109&0x1F = 9 → bit9 = DMAEN`；
高 16 位 `0x0506>>6 = 0x14 → SR1`、`(0x0506>>0)&0x1F = 6 → bit6 = RxNE`。
特殊分支（`0x0506/0x0507`）还要求 `I2C1->CR2 & 0x400`（LAST）。

**置位版本 `0x0800FC20(base, code)` 用同一套编码** —— 于是能读懂初始化：
`0x08008BAA bl 0x800fc20` 传 `r1 = 0x109` ⇒ **`CR2 |= (1<<9)` = DMAEN**；
`0x08008BB4 bl 0x800fc0c` ⇒ **`CR1 |= PE`**（启动 I2C）。
⇒ **收包函数的触发条件由固件自己置上 ⇒ 它在执行通路上，不是死代码**（区别于 TIM3 那个零调用者的例子）。

## 2. ctx 结构体（由访问偏移反推）

```c
struct tf100a_ctx {          // 句柄 = 0x20004134 = [0x20004128] + 0xC
  uint8_t  rx_buf[0x80];     // +0x000  接收缓冲（128 B）
  uint8_t  tx_buf[0x80];     // +0x080  发送缓冲（128 B）
  uint16_t tx_idx;           // +0x100  发送计数
  uint16_t rx_idx;           // +0x102  接收计数
  uint8_t  ns;               // +0x104  命名空间 ← 分派器读这里
  uint8_t  _pad;             // +0x105
  uint8_t  ctrl;             // +0x106
  uint8_t  state;            // +0x107
  uint8_t  addr;             // +0x108
  uint32_t speed;            // +0x110
  void (*cb_done)(void);     // +0x114
  void (*cb_err)(void);      // +0x118
};
```

依据：收包 `strb r1,[r0,r1(rx_idx)]`；发送 `ldrb r1,[r4+0x80+tx_idx]`；两边溢出阈值都是 `cmp ..., #0x7f`
⇒ **两个 0x80 长的缓冲正好并列**，结构自洽。

08008AA2  uxtb  r2,r2

## 4. ★★ 字节落位定案

| wire 索引 | 落点 |
|---|---|
| **wire[0]** | **`ctx+0x104`**（被单独取走作命名空间） |
| wire[1] | `ctx+0` |
| wire[2] | `ctx+1` |
| **wire[3]** | **`ctx+2`** ← 子命令低字节 |
| **wire[4]** | **`ctx+3`** ← 子命令高字节 |
| wire[5..] | `ctx+4..`（载荷） |

分派器 `ldrh r0,[ctx+2]`（小端）⇒ **子命令 = `wire[3] | wire[4]<<8`**

## 5. 与发送侧独立对照（自洽）

发送编码器 `0x0800BDE0` 的基址寄存器是 **`0x20004128`（不是 ctx）**：

```asm
0800BDE8  movw r1,#0x4128 ; movt r1,#0x2000   ; r1 = 0x20004128
0800BDF2  strb.w r0,[r1,#0x8c]                ; = ctx+0x80（发送缓冲偏移 0）★
0800BDF8  strb.w r0,[r1,#0x8d]                ; = ctx+0x81  长度 = 4
0800BDFE  strb.w r0,[r1,#0x8e]                ; = ctx+0x82  类型 = 2
0800BE06  strb.w r0,[r1,#0x8f]                ; = ctx+0x83  ★ 参数低字节
0800BE0E  strb.w r0,[r1,#0x90]                ; = ctx+0x84  ★ 参数高字节
```

（`0x20004128 + 0x8C = 0x200041B4 = ctx + 0x80` ✓）

⇒ 发送帧 = `[0x80][len=4][type=2][lo][hi]` = **`[命名空间][长度][类型][低][高]`**
⇒ 该协议带**独立的长度/类型字段** ⇒ 接收帧对称 ⇒ 子命令落在 `wire[3]/wire[4]`
⇒ **与 §4 从收包代码独立算出的结果完全一致**（两条独立证据链交叉验证 ✔）

## 6. ★★★ 因此：项目那条「永远不相等」要整体作废

**项目 `COL04-BOUNDARY.md:166` 原话**：

> 工具 `pkt[2]=sub&0xFF; pkt[3]=sub>>8` ⇒ 内部读到的 u16 = `0x000B`，而固件在等 `0x0B00`。**永远不相等。**

**这条推导的隐含前提是「`ctx[i] = pkt[i]`，子命令位于 `pkt[2]/pkt[3]`」。按现在解出的落位重算**：

| 假设的转发方式 | `ctx[2]` | `ctx[3]` | 子命令 u16 |
|---|---|---|---|
| Col04 报文**原样**进 wire | `pkt[3]` = 0x0B | `pkt[4]` = 0x05 | **0x050B** ✗ |
| 剥掉 `pkt[0]=0x0E` 后进 wire | `pkt[4]` = 0x05 | `pkt[5]` = 0x01 | **0x0105** ✗ |

⇒ **两种都不是 `0x000B`。** 那句"内部读到的 u16 = `0x000B`"**本身就不成立** —— 它是从"工具代码 + 一个未验证的偏移映射"推出来的，不是从固件读出来的。

**⇒ 正确说法：这条要作废，但原因不是"字节序反了"，而是它把「Col04 报文的字段偏移」直接当成了「TF100A 内部缓冲的偏移」。两者之间隔着一个未知封装层（`0x0E` 前缀 + `len` + `dir`），字段位置根本不重合。**

顺带：项目工具的 `pkt[2]=sub&0xFF; pkt[3]=sub>>8` 是**低字节在前**，而固件 `ldrh` 也是**低字节在前** ⇒ **字节序这件事，工具本来就是对的**。

## 7. ⚠️ 但**不要**据此宣布"改成 `pkt[3]/pkt[4]` 就成了"

**因为项目已经真机实测过，结果是否。** —— 这是我上一轮漏掉的关键证据。

`PREFLIGHT-STATE.md §6.9`（2026-09-14 23:40，用户授权真机执行）：

| 观察 | 结果 |
|---|---|
| 发 `0E A1 00 0B 05 01 18 00 00 1B` | `send=True err=0`（写通道接受） |
| 之后纯读 6 种长度（65/67/129/257/737/4096） | **全部 `err=122`**，持续 ≥3 分钟 |
| 决定性对照 | 发帧**前**读 `ok=True` → 发帧**后** `err=122` → **再发一条 class `0x20` 读帧后又回到 `ok=True`** ⇒ 通道没坏，122 只是"当前没有可交付的应答" |
| **class 全扫**（`poc/opcode-sweep-log.txt`） | `pkt[1]` = `0x00`–`0x0D` **正常应答**；**`0x0E`、`0x0F`、`0x14`–`0x2F` 连续 28 个 class 全部 `err=122`** |

⇒ **门在 GT7868Q 侧：它只实现了 `class 0x00–0x0D`，从 `0x0E` 起一律不处理。**
⇒ `0xA1` 不在它的实现范围 ⇒ **不会转发到 TF100A** ⇒ 主机侧 Col04 扩展路径**确实作废**（项目原结论正确）。

**⇒ 我在「追加四」里写的"下一步很便宜、发一条合法 `0xA1` 帧应能拿到 `0xA2` 应答"是错的。该实验项目已经做过且结果为否。正式撤回。**

3. **对硬件路径（方案③ HDP/HDN）无影响**：仍是唯一确定可行路径。

# 追加六 —— ★ 触觉「播放/波形」通路完整解出（2026-09-28 晚）

> 这是 00-总表 §六 ①「TF100A 播放/波形通路回溯」的执行结果。
> 方法：静态调用图（新工具 `fw-touchpad/callgraph.py`）+ 反汇编逐段读。
> **纯离线、零风险、不碰硬件。**

## 0. 一句话

**「播放」不是一个函数，是 `main()` 里无条件初始化的两个定时器（TIM2=200 Hz / TIM3=400 Hz），
外加一个零调用者的手动入口 `0x0800D628`。波形（手感）不在这个镜像里。**

## 1. 起点：21 处 CCER 集中在 3 个簇，不是散落全镜像

上一轮说「TIM1/TIM8 CCER 读-改-写 ×21 处」，本轮定位后修正为：

| 簇 | 地址 | 次数 | 身份 |
|---|---|---|---|
| A | `0x08010604`/`08010614` | TIM1×1 + TIM8×3 | 同一个**通道配置函数** `0x080105AC` 内部的不同 case |
| B | `0x080106BA`/`080106CA` | TIM1×1 + TIM8×3 | 同上，另一个 case |
| C | `0x08010778`/`08010788` | TIM1×1 + TIM8×3 | 同上，第三个 case |

**全部 21 处 = 一个函数 `0x080105AC` 的 3 个 case 分支**（每 case 各处理 TIM1 + TIM8）。
⚠️ 所以「21 处运行时调制」这个说法要更正为「**1 个通道配置函数，3 个 case，各覆盖 TIM1/TIM8**」。

### 1.1 `0x080105AC` 的真身：定时器通道配置器（教科书级）

```asm
080105AC  sub sp,#0x10
080105B0  strh r1,[sp,#0xa]     ; 参数1 = 通道号 (u16)
080105B4  str  r2,[sp,#4]       ; 参数2 = 配置结构体指针
080105BE  cmp  r0,#3 / bhi → 0x8010876   ; 通道号 0..3
080105C6  tbh  [pc,r1,lsl#1]    ; ★ 跳转表，4 个 case
; --- case 0（0x080105D2）---
080105D4  ldr  r0,[r1,#0x20]    ; CCER
080105D6  bic  r0,r0,#1         ; 清 CC1E
080105DA  str  r0,[r1,#0x20]
080105DC  ldrh r2,[r0]          ; 取结构体[0]
080105E4  orrs r0,r2
080105E6  str  r0,[r1,#0x20]    ; 置 CC1E
; ... 再处理 CC2E（bit1）...
08010600  movw r1,#0x2c00 / movt #0x4001  ; TIM1 = 0x40012C00
0801060A  beq  → 额外比特
0801060E  movw r1,#0x3400 / movt #0x4001  ; TIM8 = 0x40013400
; case 0 额外：CC3E(bit2)/CC4E(bit3) + CR2 的 CCUS(bit2)/CCDS(bit3)
; case 1（0x08010684）：CC1E/CC2E 左移 4 → ★ CC1NE/CC1NP（互补输出！）
; case 2（0x08010742）：CC1E/CC2E 左移 8 → CC1NE/CC1NP 的 N 位
; case 3（0x08010800）：CC1E/CC2E 左移 12 → CC3NE/CC3NP
```

**⇒ 「单端 PWM、无互补输出」这个既有结论要修正**：
case 1/2/3 明确在写 **CCxNE/CCxNP**（互补通道使能 + 极性）—— 这叫**互补输出配置**，
只是**没写 BDTR**（死区寄存器）。STM32F1 高级定时器**允许开互补输出而不设死区**（DTG=0）。
⇒ 准确说法：**支持互补输出，但未启用死区。**（对方案③ 的含义见 §5）

## 2. ★ 「播放器」函数 `0x0800D704` —— 全链中枢

### 2.1 调用者只有 2 个，且都硬编码

| 调用点 | 所在函数 | 传入的定时器 | PSC | ARR | 频率 |
|---|---|---|---|---|---|
| `0x0800E03E` | `0x0800DFE8` | **TIM2** `0x40000000` | `0x77`=119 | `0x7CF`=**1999** | **200 Hz** |
| `0x0800E784` | `0x0800E750` | **TIM3** `0x40000400` | `0x77`=119 | `0x3E7`=**999** | **400 Hz** |

两个包装函数**结构几乎相同**，参数全硬编码，**没有任何 `cmp`/`cbz` 分支** ⇒ 不是"从主机接收波形再播"，是**两段固定波形**。

```asm
; 0x0800DFE8（TIM2 版）
0800E008  movw r0,#0x4070 / movt #0x2000   ; ctx = 0x20004070
0800E010  movw r1,#0x5de1 / movt #0x800   ; ★ 回调 = 0x08005DE1（TIM2 用）
0800E018  str  r1,[r0,#0xc]                ; 存回调
0800E022  bl   0x8006b98                   ; 注册
0800E026  movw r0,#0x40b8 / movt #0x2000   ; ctx = 0x200040B8
0800E02E  mov.w r1,#0x40000000             ; ★ TIM2
0800E032  str  r1,[r0,#4]
0800E034  movs r1,#0x77;  str r1,[r0,#8]   ; PSC = 119
0800E038  movw r1,#0x7cf; str r1,[r0,#0xc] ; ARR = 1999  ⇒ 200 Hz
0800E03E  bl   0x800d704                   ; ★ 播放器

; 0x0800E750（TIM3 版）
0800E75E  movw r1,#0x400 / movt #0x4000    ; ★ TIM3
0800E766  str  r1,[r0,#4]
0800E768  movs r1,#0x77;  str r1,[r0,#8]   ; PSC = 119
0800E76C  movw r1,#0x3e7; str r1,[r0,#0xc] ; ARR = 999   ⇒ 400 Hz
0800E77A  movw r1,#0xd6f5 / movt #0x800   ; ★ 回调 = 0x0800D6F5
0800E782  str  r1,[r0,#0x14]               ; 存回调
0800E784  bl   0x800d704
```

### 2.2 `0x0800D704` 内部：真正启动 PWM

```asm
0800D704  push {r7,lr}; sub sp,#0x38
0800D71A  ldr r0,[sp,#0x34]; ldr r0,[r0,#4]
0800D71E  cmp.w r0,#0x40000000             ; if (tim == TIM2)
0800D722  bne  0x800d7aa
; --- TIM2 分支 ---
0800D748  mov.w r0,#0x40000000; str r0,[sp,#0x14]
0800D74E  add  r1,sp,#0x18
0800D750  bl   0x8010bf0                   ; ★ 时基/预分频配置
0800D75C  movs r1,#1; strh r1,[sp,#0x28]   ; ★ 通道位掩码 = 1（通道1）
0800D764  add  r2,sp,#0x28
0800D766  bl   0x80105ac                   ; ★★ 调 CCER 配置器（§1.1）
0800D76E  mov.w r2,#0x2bc                  ; ★ 0x2BC = 700
0800D772  bl   0x8010908                   ; ★★ 设 CCR（占空比）
0800D77A  movs r2,#0x60
0800D77C  bl   0x801087c
0800D786  bl   0x8010950
0800D78E  bl   0x8010d80
0800D794  bl   0x8010598                   ; 使能输出
0800D79A  bl   0x8010bc8
0800D7A2  orr  r0,r0,#1; strb r0,[r1]      ; ★ 置"已启动"标志
; --- TIM3 分支（0x0800D7AA 起）对称 ---
0800D7EC  movt r0,#0x4000                  ; TIM3
0800D7F2  bl   0x80109dc
0800D826  movs r1,#1; bl 0x8010d1c         ; 使能
```

**⇒ 关键常量 `0x2BC` = 700 得到实锤**（总表 §3.2 的 "CCR≈700" 由猜测 → 确认）。

## 3. ★★ 「触觉定时器在 `main()` 里被无条件初始化」

`0x0800E1C0`（命令分派器）的调用者是 `0x0800FDFA` —— 在**函数 `0x0800FA20` 内**，
而该函数体包含 `0x0800FD64` 起的**一行到底的初始化接力 + 一个无限主循环**：

```asm
0800FD64  bl 0x80064b4     ; ① 基础初始化
0800FD68  bl 0x800bd7c     ; ② 疑似发包编码器
0800FD6C  bl 0x800df14
0800FD70  bl 0x800df48
0800FD74  bl 0x800cf10
0800FD78  bl 0x800da4c
0800FD7C  bl 0x800dfe8     ; ★★★ TIM2 = 200 Hz（触觉 A）
0800FD80  bl 0x800e750     ; ★★★ TIM3 = 400 Hz（触觉 B）
0800FD84  bl 0x800e798
0800FD88  bl 0x800e7fc
0800FD8C  bl 0x800e074
0800FD90  bl 0x800a430
0800FD94  bl 0x800e7d4
0800FD98..0800FDC0         ; 搬 4 个 u16 到某结构
0800FDF4  bl 0x8008c64     ; ┐
0800FDFA  bl 0x800e1c0     ; │ ★ 命令分派器（主循环体）
0800FE06  bl 0x8009780     ; │
0800FE10  bl 0x800a050     ; │
0800FE18  bl 0x8007470     ; │ 共 8 个调用
0800FE20  bl 0x800767c     ; │
0800FE26  bl 0x8006230     ; │
0800FE2E  bl 0x8005bb8     ; │
0800FE34  bl 0x8007f7c     ; ┘
0800FE38  b  #0x800fdf4    ; ★ 无条件回跳 = 无限主循环
```

**⇒ 两个触觉定时器在主循环开始前就被初始化完毕。没有任何条件、没有任何参数。**

## 4. ★★★ 因此：总表 §二 第 4 条的定性要修正

总表原文：
> **4** | 固件内部（TF100A 明文段）| 播放函数零调用者 | `0x0800D628`（启动 TIM3）在本镜像**无任何调用者** + 镜像自报 `TF100A_Test_FW` ⇒ **测试固件**

本轮实测：
- `0x0800D628` **确实**零调用者（`callgraph.py --indeg` = 0/0）—— **这点原文正确**
- 但 `0x0800D628` **不是"播放函数"**。它是：

```asm
0800D628  push {r7,lr}
0800D62A  movw r0,#0x400 / movt #0x4000    ; TIM3
0800D632  movs r1,#1
0800D634  bl   0x8010d44                  ; ★ 查"就绪"标志
0800D638  cbz  r0,#0x800d658               ; 未就绪 → 直接返回
0800D63C  movw r0,#0x400 / movt #0x4000
0800D644  movs r1,#1
0800D646  bl   0x8010d30                  ; ★ 清标志
0800D64A  movw r0,#0x40d0 / movt #0x2000   ; TIM3 控制块
0800D652  bl   0x800d858                  ; ★ 间接调用槽 [ctx+0x14]
0800D658  pop  {r7,pc}
```

`0x0800D858` 是**间接调用跳板**：
```asm
0800D858  push {r7,lr}; sub sp,#8
0800D85E  ldr r0,[sp,#4]
0800D860  ldr r0,[r0,#0x14]                ; ★ 取函数指针
0800D862  blx r0                           ; ★★ 间接调用
```

而 **`0x0800E782` 正好写 `str r1,[r0,#0x14]`**（把 `0x0800D6F5` 存进 TIM3 控制块）。
⇒ `[ctx+0x14]` = **"定时器回调槽"**，由 `0x0800E750` 填充。

### 4.1 修正后的准确结论

| 项 | 原文 | 修正后 |
|---|---|---|
| `0x0800D628` | "启动 TIM3 的播放函数" | **一个零调用者的"就绪后手动触发一次回调"入口** |
| 真正播放器 | —— | **`0x0800D704`，2 个调用者，在 main 里被无条件调两次** |
| "测试固件"证据强度 | 强 | **减弱**：零调用者 ≠ 死代码，它可能是**中断/向量触发点**（本镜像已有先例：`0x08008978` ISR 也零调用者） |

⚠️ **不能因为 `0x0800D628` 零调用者就断定它是死的。** 本镜像 13 个零调用者入口里，
至少有 1 个已确认是 ISR（`0x08008978` 事件分派器）。零调用者只能说明**不由普通代码调用**。

### 4.2 可达性统计（`callgraph.py`）

| 指标 | 值 |
|---|---|
| 函数入口总数（`push {...,lr}`） | **136** |
| 从 main 可达 | **110** |
| 不可达 | **26**（含 ISR 向量 + 间接调用目标 + 真死代码） |
| 关键链可达性 | TIM2包装 ✅ / TIM3包装 ✅ / **播放器 `0x0800D704` ✅** / 分派器 ✅ |

⚠️ `0x080105AC`（CCER 配置器）在直接图上显示"不可达"——**假阴性**，
它是经 `[ctx+0x14]` 类函数指针**间接调用**的。静态图必须配合函数指针分析才完整。

## 5. 对方案③（HDP/HDN）的净影响

### 5.1 新增可用的规格（可以照做）

| 项 | 值 | 来源（本轮实锤） |
|---|---|---|
| 触觉 A 频率 | **200 Hz** | `0x0800E038` ARR=1999, PSC=119 |
| 触觉 B 频率 | **400 Hz** | `0x0800E76C` ARR=999, PSC=119 |
| 占空比 | **700/2000 = 35%** | `0x0800D76E` `mov.w r2,#0x2bc` |
| 通道 | **通道 1（CC1E）**，位掩码 `1` | `0x0800D760` `strh r1,[sp,#0x28]` |
| 互补输出 | **支持（CCxNE/CCxNP 可配），但未设死区** | `0x080105AC` case 1/2/3 |
| 定时器 | TIM2（200 Hz）/ TIM3（400 Hz），**同型号不同角色** | §2.1 |

### 5.2 ★ 关键：波形不在固件里

- 两个包装函数**参数全硬编码**，没有"从主机取波形"的路径
- 定时器回调（`0x0800D6F5`）**只是计数器**（`ldr; adds #1; str`），不产生调制
- ⇒ **包络/手感确实不在 TF100A 明文段** ⇒ 支持项目 09-28 的倾向判断

⚠️ **但注意**：这不等于"包络由加密 TP 侧下发"。还有一种可能：
**包络由 TF100A 加密段（100 KB 那块）产生**，或**由 GT7868Q 侧产生**。
本镜像（56 KB 明文）只是"定时器驱动层"。

### 5.3 结论：本项**降级但不作废**

- **降级**：确认了"手感不在明文段"，符合项目预判
- **不作废**：本轮产出了 **6 条可直接使用的驱动规格**（§5.1），
  其中 **"通道 1 + CC1E + 35% + 200/400 Hz"** 是方案③ 可以直接照抄的初始化序列
- **剩余缺口仍是 2 个**（不变）：**振幅** 与 **LRA 型号/谐振频率**

## 6. 新工具：`fw-touchpad/callgraph.py`

静态调用图分析器（本轮的副产品，将来直接复用）：

```
callgraph.py --indeg  <addr>...   查某地址的调用者（含所在函数入口）
callgraph.py --callees <addr>     列某函数的直接调用（带调用点）
callgraph.py --reach  <addr>      从该地址做可达闭包
callgraph.py --zero               列出所有零调用者入口
callgraph.py --funcs              列出所有函数入口 + 被调次数
callgraph.py --top                被调用最多的目标
```

**已知局限（必须记住）**：只扫**直接** `bl`/`b`，**不解析函数指针间接调用** ⇒
会把间接调用目标误判为"不可达"（实例：`0x080105AC`）。
判"死代码"需同时满足：① 直接图零入度；② 无函数指针写入；③ 不在向量表位置。

## 7. 教训（本轮新增）

1. **"21 处散落"要先定位再解读**。我一开始说"21 处运行时调制、散落全镜像"，
   实测是**1 个函数的 3 个 case**。**数量 ≠ 分布**，先定位再下结论。
2. **零调用者 ≠ 死代码**。本镜像已有 ISR 先例。凡以"零调用者"作结论，
   必须补一句"但需排除向量表/函数指针触发"。
3. **静态调用图必须标注局限**。`--reach` 把间接调用目标判成不可达，
   如果直接采信就会得出"CCER 配置器是死代码"的荒谬结论。

## 1. 先更正一个地址（旧文档误记）

| 项 | 旧记载 | **实测（本轮）** |
|---|---|---|
| `0xA0/0x0B00` 处理函数 | `0x080088C0` | **★ `0x0800D8C0`** |
| `0xA1/0x0B00` 读回函数 | `0x08008868` | **★ `0x0800D868`** |

`0x080088C0` 与 `0x0800D8C0` 在镜像里**都存在**（是不同函数），项目 09-14 那批文档把地址写岔了一位。
本工区 09-28《TF100A命令分派器与I2C链路.md》记的 **`0x0800D8C0` 是对的**。

## 2. `0xA0/0x0B00` 处理器 `0x0800D8C0` —— 逐条实读

```asm
0800D8C0  sub  sp, #0xc
0800D8C6  ldrb r0, [r0, #1]      ; N = msg[1]（长度）
0800D8C8  strb.w r0, [sp, #7]
0800D8CC  movs r0, #0             ; i = 0
0800D8D2  循环顶:
0800D8D4  ldrb r1, [sp, #7]
0800D8D8  cmp  r0, r1  ; bge 退出
0800D8DE  ldr  r0, [sp, #8]       ; msg
0800D8E2  add  r0, r2
0800D8E4  ldrb r0, [r0, #4]       ; ★ 源 = msg[4 + i]
0800D8E6  movw r1, #0x40e8
0800D8EA  movt r1, #0x2000        ; r1 = 0x200040E8
0800D8EE  strb r0, [r1, r2]       ; ★ 0x200040E8[i] = msg[4+i]
0800D8F8  b    0x800D8D2
0800D8FA  add  sp, #0xc ; bx lr
```
⇒ **纯逐字节拷贝 `msg[4..]` → `0x200040E8`**，无其它副作用。

## 3. `0xA1/0x0B00` 处理器 `0x0800D868` —— 逐条实读

```asm
0800D868  push {r7, lr} ; sub sp, #0x10
0800D874  movs r0, #0xa2
0800D876  strb r0, [r1]           ; buf[0] = 0xA2（回复标签）
0800D878  ldrb r0, [sp, #0xb]
0800D87E  strb r0, [r1, #1]       ; buf[1] = n
0800D886  循环顶: cmp r0, r1 ; bge 退出
0800D894  movw r0, #0x40e8
0800D898  movt r0, #0x2000        ; 0x200040E8
0800D89C  ldrb r0, [r0, r1]       ; ★ 读 0x200040E8[i]
0800D8A2  strb r0, [r1, #2]       ; ★ buf[2+i] = 表内容
0800D8AE  movw r0, #0x800
0800D8B2  movt r0, #0x4001        ; GPIOA 基址
0800D8B6  movs r1, #8             ; bit3 = PA3
0800D8B8  bl   0x800F7FC          ; ★ GPIOA->BRR = 1<<3（拉低 PA3 握手线）
```
（`0x0800F7FC(GPIOx, val)` 实测 = `str rN, [rM, #0x14]` = **写 BRR**）

⇒ 与项目 `VIB-REOPENED.md` §194 记载**逐条吻合**：`A2 <n> <n 字节表内容>`，并拉低 PA3。

## 4. ★★★ 判定：`0x200040E8` **全镜像只有这两处引用**

用 `grep "movw rN, #0x40e8"` 全镜像扫描（20,314 行），命中**恰好 2 处**：

| 地址 | 操作 | 所属函数 | 调用者 |
|---|---|---|---|
| `0x0800D8EE` | **写**（`strb`） | `0x0800D8C0` = `0xA0/0x0B00` | `0x0800E372`（分派器 `0x0800E1C0` 内） |
| `0x0800D894` | **读**（`ldrb`） | `0x0800D868` = `0xA1/0x0B00` | `0x0800E68A`（分派器内） |

**⇒ 这张表的完整生命周期 = 「主机写进来」+「主机读回去」。**
**⇒ 全镜像没有任何第三处代码消费它 —— 没有代码把它接到 TIM2/TIM3、没有接到 LRA 驱动、没有接到播放回调 `ctx+0x14`。**

## 5. ⇒ 对 §一 的结论修正（重要）

| 项 | §一 原判断 | **修正后** |
|---|---|---|
| `0x200040E8` 性质 | "触觉波形缓冲"、"最像触觉参数/波形的内部表" | **是一只纯收发寄存器组**：只被主机写、只被主机读回，**无人消费** |
| `0xA0/0x0B00` 的价值 | "唯一剩下的软路径"，字节序解决后或可触发振动 | ★ **即使字节序问题解决、写入成功，也不会产生任何振动**（无消费者） |
| "字节序卡点"这条研究线 | 值得离线定案 | **结论先行：定案也无用** ⇒ **降级为"仅记录"，不投入** |

**这与项目旧文档 `HANDOVER.md` 的判定一致**（原话："39 条 handler 无一读写 `ctx+0x14`，无一碰 TIM2/TIM3 ⇒ 主机命令能到触觉区间，**到不了马达**"）。
本追加**为该判定提供了正面证据**：不是"没找到"，是**引用完整性检查证明不存在**。

## 6. ⇒ 净影响

- §一 那条"唯一剩下的软路径"**实质关闭**（不是因为字节序，是因为没有消费者）
- 触控板的**软路径归零**
- **方案③（HDP/HDN 焊盘外挂）仍是唯一确定可行路线**，且不受此影响
- 副作用：这解释了为什么项目当年"写 `rid=9` 力度变但不震" —— 参数确实被收下了（进了 `0x200040E8` 之类），但**没有任何东西把它变成驱动**

## 7. 顺带确认的一条（`0xA0/0x0D00` 是唯一"有动作"的分支）

分派器 `0x0800E1C0` 的 `0xA0` 组内，`0x0800D6B4`（`0x0D00`）是**唯一**做"设模式=4 + 调 `0x080051C2(0x2000495E, 0x1694)` 大块传输 + 置标志"的分支
（`0x0800E378` 直接 `bl`，不传参数）。其余分支多为纯读写或转发。⇒ **若将来要找"主机能触发的最强动作"，应看 `0x0D00` 而非 `0x0B00`。**（本项目未验证其是否触达马达）
