## 〇、一句话

> ## **`HW_REG_SCRAMBLE = 0x2218` 能读到、稳定、值就是 `00 00 00 00`；但官方驱动对它【只写不读】、唯一写入值也是 `0x00`，且写在"把 ISP 载入 SRAM"之前 ⇒ 它更像【升级数据通路的期望态开关】，不是"flash 静态存储是否加扰"。**
> ## **⇒ A②「试写 0」= 写当前值（零信息量）；「写 1」验证的是另一个命题。这一支不值得再投入。**
> ## **⇒ 同时确认：厂商 16 位窗口里【没有固件镜像】，拿固件只能走离线密码分析或物理路线。**

## 二、★ 官方 HW 寄存器定义表 × 本机实测

来源：`gtx8_driver_linux/goodix_gtx8_update.c:27-48`（该驱动明确支持 `IC_TYPE_YELLOWSTONE = 3`）。全部为**一次性 4 字节读**，间隔 600 ms。

| 地址 | 实测值 | 官方宏 | 官方语义 / 备注 |
|---|---|---|---|
| 0x2010 | `66 05 12 00` | HW_REG_DSP_MCU_POWER | 升级流程写 `0x00` 使能 |
| 0x2014 | `08 07 00 00` | HW_REG_GIO_YS | GIO |
| 0x2048 | `01 00 00 01` | HW_REG_BANK_SELECT | bank 选择 |

| 0x204D | `00 00 00 28` | HW_REG_ACCESS_PATCH0 | 升级流程写 `0x00` 禁 bank0 访问 |
| 0x204F | `00 28 40 FE` | HW_REG_EC_SRM_START | |

| 0x4000 | `A7 E0 E5 B1` | HW_REG_CPU_RUN_FROM_YS | ⚠️ 见下 |
| 0x4506 | `92 25 8B 8E` | HW_REG_CPU_RUN_FROM | ⚠️ 见下 |
| 0x6006 | `77 A8 C3 47` | HW_REG_ISP_RUN_FLAG | ⚠️ 见下 |
| 0x6020 | `EF 96 AA 25` | HW_REG_SUBSYS_TYPE | |
| 0x6022 | `AA 25 30 11` | HW_REG_FLASH_FLAG | |

**★ 一个重要的分区证据：`0x2xxx` 是活的，`0x4xxx/0x6xxx` 在应用模式下不是那回事。**

官方 `update_finish()` 结束时会把 `HW_REG_CPU_RUN_FROM_YS (0x4000)` 写 **8 个字节的 `0x00`**（注释："set CPU run from normal firmware"）。
若"应用模式 == 正常固件"成立，0x4000 应读出 `00 00 00 00 00 00 00 00`；**实测是 `A7 E0 E5 B1 …`（高熵）**。

| 结论 | 强度 |
|---|---|
| `0x2xxx` 寄存器块在应用模式下**读得到真值**（`0x2180` 的 `0x00` = "CPU 放行" 与芯片在干活自洽） | 中—高 |
| `0x4xxx / 0x6xxx` 在应用模式下**不是 ISP 寄存器空间**（很可能是数据/传感区，见 §七） | 中 |

## 三、★ 关键判定：读得到 ≠ 打开门

三条来自官方源码的事实（`goodix_gtx8_update.c`）：

```
① HW_REG_SCRAMBLE 全代码库【只写不读】—— 没有任何读回校验。
② 唯一写入值就是 0x00（第 612-614 行，注释 /* set scramble */）。
③ 写入位置在 goodix_load_isp() 之前 —— 那一步是把 ISP 代码载入芯片 SRAM，
   不是往 flash 写；而往上送数据的 goodix_format_fw_packet() 对数据【零变换】
      pkt = [len_be16][flash_addr][memcpy(data)][checksum]   ← 无任何加解密
```

⇒ 更自然的解释：**`0x2218` 描述的是"主机↔芯片这条升级数据通路上，期望什么样的数据"**
（`0x00` = 主机按**明文**送），**而不是"flash 里已存的内容是否被加扰"这个静态属性**。

**这直接给出 A② 的判断：**

| 动作 | 信息量 | 风险 | 判定 |
|---|---|---|---|
| 写 `0x00` | **零** —— 当前值就是 `0x00` | 未知寄存器写入可能挂起（重启可恢复） | ❌ 不做 |
| 写 `0x01` | 验证的是"把升级通路期望改成加扰"，**几乎不可能改变已存 flash 的读回结果** | 同上 | ⚠️ 性价比极低，不建议 |

## 四、对 `追加二十八` 的修订

| 既有说法 | 出处 | 本次判定 |
|---|---|---|
| 「加扰是芯片行为 ⇒ 只要写入路径通，芯片会自己加扰 ⇒ **回刷的可能性重新打开**」 | `追加二十八` §四① | ⚠️ **依据不足，下调**。该推理把"升级通路开关"当成了"存储加扰属性"。两条推论（"可以解密" / "可以回刷"）**都不再由这条支撑** |
| 「加扰由芯片做、主机侧零变换」 | `追加二十八` §一 | ✅ **保持成立**（源码属实）。但"芯片做加扰"现在看更可能指**升级数据通路** |
| 「弱变换（1 KiB 周期）」 | `追加二十八` §二/§三 | ✅ **保持成立**（统计证据独立于本寄存器） |

> **一句话**：`追加二十八` 的**统计部分没问题**，**"由此推出回刷门重开"这部分不成立**。

## 五、顺带纠正两处

### 5.1 容器段划分应写"约"

容器 `touchpad_GT7868Q_fw.bin`（161,628 B）的熵剖面（窗口 0x400 / 步长 0x200）：

| 区间 | 熵 | 性质 |
|---|---|---|
| 0x000000 – 0x0011FF | ≈ 5.1（首 4 KiB 5.089） | **明文**（含 `0x1143` 处的 ASCII **`YELSTO`**） |
| ≈0x001200 – ≈0x0197FF | **7.78 – 7.96** | **加扰段**（≈96 KB） |
| 0x019800 – 0x0199FF | 6.121 | 过渡 |
| 0x019A00 – 0x02775C | 5.3 – 6.5 | 明文（TF100A 等） |

⇒ 此前文档写的 `0x1400–0x19A00` 与实测的 `≈0x1200–0x19800` **差 0x200，两端都是渐变的**。属合理范围，但应记为"**约**"。
⇒ ★ **新线索：`0x1143` 有明文 ASCII `YELSTO`，紧贴加扰段边界** ⇒ 这是一个**已知明文锚点候选**，对 A③ 有用。

### 5.2 两份"设备 dump"不是设备读的

`fw-touchpad/device_fw_1E1175.bin`（99,179 B）与 `device_fw_1E3000.bin`（91,360 B）：

| 检查 | 结果 |
|---|---|
| 前 32 B 在 `cap_payload.bin` 中的位置 | **0x1E1175 / 0x1E3000** —— 文件名就是偏移，**它们是从 UEFI capsule 载荷里切出来的** |
| 开头 | `42 54 46 57` = **ASCII `BTFW`**（结构化的子镜像头） |
| 熵 | 7.69 / 7.80（主体高熵） |
| 与容器加扰段的关系 | 逐字节相等率 **1.0/256**，异或分布均匀 ⇒ **毫无关系** |

⇒ **它们不能当"明文参照"用**。这条排除了一个看来诱人的假路。

## 六、★★ 新结论：厂商 16 位窗口里没有固件

抽样 64 个地址（步长 `0x400`、每次 32 字节、间隔 600 ms），把每个 32 字节样本在容器里做**精确子串搜索**：

> ### **命中 0 个。**
> ⇒ **厂商内存窗口不是容器镜像的映射；靠它拿不到固件（明文或密文都拿不到）。**

顺带发现了这个窗口的**真实性质**（见 §七）——它是触控芯片的**数据 / 参数 / 状态空间**，不是代码空间。

**红线的实测更新：** 本轮 64 次读 + 每 16 次一次健康门，设备**全程 YELSTO、收尾一致**。
⇒ 以 **≥600 ms 间隔、单次遍历（不循环）** 的方式读这个窗口是**安全**的，此前对"总线操作"的紧张可以适度放宽（但**写入**仍未验证）。
