## 0. 一句话结论

> 这 5 个文件里**没有触觉配置/波形/触发定义/力度阈值**，也没有任何厂商寄存器内容。
> `rid2_full` 是 **RID 2（设备能力）** 的 2 字节应答 + 未使用的 0 填充；
> `rid9_full` / `256B` 是 **RID 6（0xFF00/0xC5 设备认证状态）** 的 257 字节应答（= 微软公开的 PTPHQA **默认样例 blob**）；

> **RID 9（0x0E/0x23 触觉强度）和 RID 11/12/13 的内容根本没被读出来**——GET_FEATURE 对它们返回的是同一份 RID 6 缓存 blob。

### 1.1 十六进制摘要（前 64 字节 + 关键区段）

`col02_feature_rid2_full.bin`（全部 737 字节里只有 3 个不同字节值：`00`×735、`15`×1、`02`×1）
```

0010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0020  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0030  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
...   （0x40 … 0x2E0 全部为 00）
```
关键字节：**offset 0x00 = `0x02`（RID=2），offset 0x01 = `0x15`**。
`0x15` 拆成两个 4-bit 字段（微软 PTP 样例描述符里 0x55 在前、0x59 在后，HID 按低位先装）：

* 低 4 位 = `0x5` = **Contact Count Maximum = 5**（0x0D/0x55）
* 高 4 位 = `0x1` = **Button Type = 1 = Non-Depressible（Pressure-pad，压感/触觉板）**（0x0D/0x59）
  （反过来的解释会让 Button Type = 5，规范只允许 0/1/2，故该方向被排除 → 这个位序**不是猜测而是被规范唯一确定的**）
  依据：微软 "Windows Precision Touchpad Collection" + "Sample Report Descriptors"（页面 Usage 表里 1 = Non-Depressible/Pressure-pad）。

### 1.2 关键事实：这个 256 字节 blob 是**微软公开的常量**

微软 PTP 规范给出设备"尚未拿到签名认证 blob"时应实现的**默认样例 blob**，其开头正是
`0xfc, 0x28, 0xfe, 0x84, 0x40, 0xcb, 0x9a, 0x87, 0x0d, 0xbe, 0x57, 0x3c, 0xb6, 0x70, 0x09, 0x88, 0x07, 0x97, 0x2d …`
本机数据与之**逐字节 256/256 完全相同**（见 `_verify_ptphqa.py` 输出：`256B file == MS blob : True`）。
这解释了它"高熵、像随机数、却跨会话完全一致"的全部现象——它是**固定常量**，不是随机数也不是未初始化内存。

### 1.3 那 2 个 8 字节文件为什么相同（事实 + 推测）

* 观察到的事实：两者字节完全相同；内容恰好等于 RID 2 的规范应答 `02 15` + 0 填充；
  而 RID 9 在描述符里是"1 字节 payload（0x0E/0x23，8-bit）"，其应答应为 `09 xx`。
* 推测（理由充分但无法 100% 证明）：`col02_feat_rid9.bin` 是**采集假象**——RID 9 的那次读要么复用了 RID 2 的缓冲/句柄，要么脚本把 RID 参数写错（目录里**没有**留下产生这批 `.bin` 的脚本，我 grep 过整个目录，只有我本次写的分析脚本提到这些文件名）。
* 反证：稍后那次受控的整轮扫描（`col02-precise/`，禁用设备后逐 RID 读）里，RID 9 从来没有返回过 `02 15`，而是返回 257 字节的 `06 FC 28 …`。

## 3. `col02_feature_256B.bin` 是否是那两个 737 B 文件的子串

| 比较对象 | 是否连续子串 | 出现位置 | 同偏移处一致字节数 |
|---|---|---|---|
| `rid9_full` | **是** | **offset 1**（唯一一处） | 0 / 256（因为整体右移 1 字节） |
| `rid2_full` | 否 | 无任何出现 | 0 / 256 |

* 精确关系：`col02_feature_256B.bin == col02_feature_rid9_full.bin[1:257]`
* 也等于受控扫描的 `col02-precise/rid06_len257.bin[1:257]`（同样是剥掉 RID 字节）。
* 所以：**同偏移处不一致**，它是"错位 1 字节"的子串——那 1 个字节就是 Report ID 本身。
* 注意 `256B` 文件里 **没有任何 0x00 字节**，而两个 737 文件的尾部填充是 0x00，因此它不是"截断的 737 文件"，而是"256 字节 payload 本体"。

## 4. 737 = 1 + 736 ？首字节是不是 `0x0C`？这些文件到底属于哪个 RID？

### 4.1 声明层面的算术（事实）
* `HidP_GetCaps` 的 `FeatureReportByteLength` 语义是"**最大** feature 报表长度"，所以 `Feat=737` 指的是**最长的那一份**，不是所有 feature 之和（各字段相加是 1064）。
* 737 = 1 字节 Report ID + **736 字节**，正好对应 `RID=12 / page=0xFF00 / usage=0xC6（736 字节）`。**这一条算术成立。**

### 4.2 但首字节不是 `0x0C`（事实）
| 文件 | 首字节 | 含义 |
|---|---|---|
| `col02_feature_rid2_full.bin` | `0x02` | RID 2 报表 |
| `col02_feature_rid9_full.bin` | `0x06` | **RID 6** 报表 |
| `col02_feature_256B.bin` | `0xFC` | payload 本体（无 ID 字节） |

所以：
* **`rid9_full` 不是 RID 12/0xC6 的内容**（若真是 RID 12，首字节应为 `0x0C`）；
* 它是 **RID 6** 的内容：`0x06` + 256 字节 `0xFF00/0xC5` 认证 blob，第 258 字节起是未被写入的缓冲区填充；
* **RID 12（0xC6, 736 B）的真实寄存器内容在这批文件里完全不可见。**

### 4.3 为什么用 rid=6/7/9/11/12/13 去读会读出**同一段**字节（事实 + 推测）

事实（来自同目录**已存在**的受控扫描 `col02-precise/summary.json` 与对应 `.bin`，我只读文件未重跑设备）：

* RID 2 → 只写回 2 字节 `02 15`，其余保持缓冲初值（旧脚本填 `00`，受控脚本填 `EE`，两次对比证明真数据长度=2）。
* RID 6 / 7 / 9 / 11 / 12 / 13 → **六者的 257 字节应答 md5 完全相同**（`1e11b3f2a0e1`），都是 `06 FC 28 FE 84 40 CB 9A …`；737 缓冲版本 md5 也全是 `7c5e4ea95f57`；第 258 字节起保持缓冲初值。
* 未在描述符中声明为 feature 的 RID（0,1,3,4,5,8,10,…）→ `HidD_GetFeature` 直接失败；即**驱动确实按描述符校验了 RID**，然后对这 6 个 RID 都回同一份 257 字节缓存。

推测（标注理由）：
1. **最可能**：这些 vendor/haptics feature 报表的 GET_FEATURE 并没有被路由到设备对应寄存器，而是被 HID 类驱动/厂商过滤驱动用**一份缓存缓冲**（枚举阶段读到的认证状态报表）应答；因此内容与请求的 RID 无关，且写入也**无法用读回来验证**。
2. 旁证（外部、独立）：Linux 内核邮件列表某 RFC 作者在**他自己的压感触控板**上报告同一现象——"*getting the feature report returns garbage data (probably from the last input report in the buffer), which makes some sense as the implementation guide only requires SET_FEATURE support*"，并说明该 knob 只能通过 SET_FEATURE 下发、设备掉电前保持。
3. 备选解释（较弱）：固件对未知 RID 统一回一份固定缓冲。无法与 (1) 区分，因为两者都要求改硬件/驱动侧才能区分。
4. 结论上二者等价：**这 5 个文件不能证明也不能否证 RID 9/11/12/13 寄存器的内容；它们只是读不到。**

### 4.4 对"顺手验证写入"的直接影响（很重要）
`col02-writeprobe/writeprobe_log.txt` 里"写 RID 9 = 0x0A 成功，但读回 md5 全部不变"这条证据**不成立**：
在 §4.3 的读路径下，读回**必然**与写入无关。**要确认 RID 9 写入是否生效，只能靠手感/示波器/驱动侧抓 IRP，不能靠 GET_FEATURE 回读。**

## 5. 数据结构扫描（逐项，全部基于 257 字节真实数据）

| 检查项 | 结果 |
|---|---|
| ASCII 字符串 | 无有意义串。≥4 字符的仅有偶然片段：`(K|-S`(0x2A)、`YotC`(0x34)、`m9%)\|`(0x5C)、`+S\iR`(0xA9)；无 `hap/vib/wave/motor/lra/trigger/force/press/thres/effect/pid/gt/gx` 任何关键词 |
| UTF-16LE 字符串 | 无（0 条） |
| 定长表（记录） | 无。记录长 2/4/6/8/10/12/16/20/24/32/64 全部无"常量字节列 / 低值域列 / 等差列" |
| 4 字节地址 | 无合理地址窗口值（64 个 u32LE 里只有 ~6 个随机落在 0x13xxxxxx 附近的巧合） |
| IEEE754 浮点 | 无真实浮点语义：float32 LE 63/64 有限但量级乱（含 -7.18e33）；**不含任何常见常量位型**（0.0f/1.0f/2.0f/0.5f/0.1f/100.0f/1000.0f/10000.0f 一个都没有）；float64 无小整数 |
| 递增/递减序列 | 无。最长"严格 +1（mod 256）"连跑长度 = **1**；最长单调连跑 4–5 字节（随机数据的典型值） |
| 校验和 / CRC | 无。CRC32(payload[0:252]) LE、CRC16-Modbus(payload[0:254]) LE/BE、CRC8、sum8、xor8 与尾部字节**全部不匹配** |
| 全 0 / 全 FF 区段 | payload 内：**0 个 0x00**、2 个 0xFF（偏移 113、183）、1 个 0xEE（偏移 210）、0 个零 dword / FF dword；无 ≥4 连续相同字节 |
| 香农熵 | 整体 7.22 bit/byte；16 字节块 ≈4.00（= 每块 16 个互异值的期望值）；χ²=244（df=255）→ 与均匀分布一致；lag1..8 自相关和 0.476 ≈ 0 → **不像波形/采样序列** |
| 可重复性 | 17:50 与 18:04 两次独立采集，前 257 字节 md5 一致 → 会话内确定性 |
| 值得注意的小事实 | payload 里最小 u16LE = 2099，128 个 u16LE 里只有 1 个 ≤4095（随机期望 ≈8）——这只是微软那个公开常量的固有性质，**不构成任何语义** |

## 6. 最关键：有没有触觉配置 / 波形 / 触发定义 / 力度阈值 / 手势-触觉映射？

### 6.1 在这 5 个文件的**数据内容**里：**没有找到。**
逐项排查都为空（§5）：没有波形表、没有定长触觉参数记录、没有力度阈值常量、没有手势→效果映射、没有字符串/关键词、没有校验结构、也没有任何厂商寄存器内容（因为根本读不到）。
数据部分唯二的"结构性"事实是：RID 2 的两个 4-bit 字段（Contact Count Max=5、Button Type=1）和 RID 6 的公开认证常量 blob。

### 6.2 但在**描述符（caps）层面**，触觉相关信息是明确存在的（这是本次分析真正的收获）
把 `caps-all.txt` 的 col02 字段表与微软公开规范对齐，语义完全确定：

| RID | Usage | 长度 | 规范定义 | 对本次目标的意义 |
|---|---|---|---|---|
| 2 | 0x0D/0x55 + 0x0D/0x59 | 1 B | PTP **Device Capabilities**（Contact Count Max / Button Type） | 实测 `0x15` → **Button Type = 1 = 非按压式压感板（pressure-pad）**，与"设备自决触觉"前提一致；CCM=5 |
| 6 | 0xFF00/0xC5 | 256 B | PTP **Device Certification Status**（PTPHQA blob） | 读到的是微软**默认样例常量**（未签名），与触觉无关 |
| **9** | **0x0E/0x23** | 1 B（0..100） | **Haptics Intensity**（微软 Input Device Haptics Guide：设备自决触觉的"强度"旋钮，**只需 SET_FEATURE**） | ✅ **这是本机唯一一个规范定义的触觉软件旋钮**：它改变"按压/释放时设备自己震动"的强度 |
| 11 / 12 / 13 | 0xFF00/0xC7 / 0xC6 / 0xC4 | 66 / 736 / 4 B | 无公开规范（含 0xC6 = 分段认证状态段号/数据 的厂商用法） | 内容不可读（§4.3），格式未知 |

**没有**发现 `0x0D/0xB0 Button Press Threshold`（第二个规范定义的设备自决触觉旋钮）→ 本机不支持。

### 6.3 关于"让主机主动触发震动"（回答背景里的真实目标）
* 按微软 Haptics 规范，**主机主动触发（host-initiated）** 必须同时具备：一个 `0x0E/0x10`(Waveform List) + `0x0E/0x11`(Duration List) 的 **GET_FEATURE** 报表，和一个含 `0x0E/0x21`(Manual Trigger) 的 **OUTPUT** 报表。
* 本机 Col02：`In=40 Out=0`，且描述符里**没有** 0x0E/0x10、0x0E/0x11、0x0E/0x21 任何一个 → **标准协议下本机不支持主机触发震动**，没有"立即震一下"的标准命令。
* 因此纯软件可用的只有：**SET_FEATURE RID 9 = 触觉强度（0..100）**，影响"设备自决"的按压/释放震动强弱。
* 唯一可能藏"厂商触发命令"的通道（**推测**，需另行取证）：`gxtp5100&col04` 是 `UsagePage=0xFF00 Usage=0x0001`、**65 字节 Input + 65 字节 Output、RID 14** 的厂商双向管道（Col02 本身没有 output 报表）。若厂商固件支持"手动播放波形"，格式只可能在这种厂商管道里，而要拿到格式需要**驱动侧抓包**（对 Goodix 驱动/IOCTL 或 HID 层做 ETW/USB 或 I2C 层跟踪），**无法靠读 feature 得到**。

## 7. 事实 / 推测 分界（严格版）

**观察到的事实**
1. md5/长度/差分/子串关系如 §1–§3；两 737 文件有 257 字节不同、480 字节相同（尾部 0 填充）。
2. `256B` 与微软公开 PTPHQA 默认样例 blob **逐字节 256/256 相同**；`256B == rid9_full[1:257]`。
3. `rid2_full` 的真实数据只有 2 字节 `02 15`；`rid9_full` 的真实数据是 257 字节 `06 + 上述 blob`（由 0/0xEE 两种填充的差分确定）。
4. 两个 8 字节文件字节完全相同，内容为 RID 2 应答。
5. 受控扫描中 RID 6/7/9/11/12/13 的应答 md5 两两相同；未声明的 RID 读取失败。
6. payload 无字符串/表/地址/浮点/序列/校验；熵 7.22，自相关≈0。
7. `0x15` 的两个 4-bit 字段按规范只能解释为 CCM=5 与 Button Type=1。

**推测（已注明理由）**
1. RID 9/11/12/13 的寄存器内容**读不到**（GET_FEATURE 被缓存 blob 顶替）；理由是六 RID 应答逐字节相同 + 尾部保持缓冲初值 + LKML 独立旁证。
2. `col02_feat_rid9.bin` 是采集假象（内容=RID 2、且无保留脚本）。
3. 写入 RID 9 是否生效**无法用回读验证**（同 1）。
4. Col04 的 65 字节 OUTPUT（RID 14）可能是厂商命令通道（无证据，仅因它是唯一的主机→设备数据通道）。
5. 256 字节 blob 是固件里那份"未签名默认认证数据"被驱动缓存后回显；具体是驱动层还是固件层行为，**无法从这些文件区分**。

## 8. 建议的下一步（不涉及硬件改动）
1. **验证 RID 9 触觉强度**：写 `SET_FEATURE RID 9`（例：`00 → 100`），**不要用 GET_FEATURE 回读判断**，改为人工感受"按压/释放震动强度是否变化"（或用手机录震动声/加速度计比对）。这是纯软件、可逆、零风险的一步。
