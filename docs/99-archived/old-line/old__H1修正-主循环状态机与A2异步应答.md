# H1 修正 —— `0xA2` 回复是**主循环状态机的异步产物**，不是命令的同步应答

- 时间：2026-09-27 · 输入：TF100A 明文固件 · 脚本：`armed_consumers.py`
- 这条**推翻**了项目里 H1 判否的**验收方式**，并修正了两处对固件结构的基本理解
- **本条已取代** `触控板-三项离线分析结果.md` §1.4/§1.5 的初步推测

## 一、先把主循环看清（这是全部结论的地基）

```
0800AA20  ← 主循环（项目已定位）。它的 BL 调用者只有一个：0x8003B98（复位后入口）
   ...
0800ADF4  bl   #0x8003C64             ; 每轮开头
0800ADF8  mov  r0, r4
0800ADFA  bl   #0x80091C0             ; ★ 调用命令分发器（处理主机发来的帧）
0800ADFE  mov  r7, sl                 ; sl = 0x20004090
0800AE00  ldrb r0, [r7, #4]!          ; ★ r7 ← 0x20004094；r0 = [0x20004094] = 模式字节
0800AE04  mov  r1, r5                 ; r5 = 0x2000495E（上下文基址）
0800AE06  bl   #0x8004780             ;   模式 1 处理器
0800AE0A  ldrb r0, [r7]               ;   重读 [0x20004094]
0800AE0C  mov  r1, r6                 ;   r6 = 0x20005FF4
0800AE0E  mov  r2, r5
0800AE10  bl   #0x8005050             ;   模式 3 处理器  ← ★ 0xA2 回复就在这里产生
0800AE14  ldrb r0, [r7]               ;   重读
0800AE16  mov  r1, r5
0800AE18  bl   #0x8002470             ;   模式 4 处理器
0800AE1C  mov  r0, r7
0800AE1E  mov  r1, r6
0800AE20  bl   #0x800267C
0800AE24  mov  r0, r8                 ;   r8 = 0x200061B4
0800AE26  bl   #0x8001230
0800AE2A  mov  r0, r5
0800AE2C  mov  r1, sb                 ;   sb = 0x2000403C
0800AE2E  bl   #0x8000BB8
0800AE32  ldrb r0, [r7]               ;   重读
0800AE34  bl   #0x8002F7C
0800AE38  b    #0x800ADF4             ; ★ 回到循环头
```

**要点**：
1. 主循环每轮**先跑分发器**（处理主机命令），**再把三个模式处理器各调一遍**
2. 三个模式处理器收到的 `arg0` **是同一个字节 `0x20004094`** —— 它们**各自内部**用 `cmp #1 / #3 / #4` 判断"是不是轮到我"
3. 所以主循环是**轮询式状态机**：谁的模式号对上了，谁就在这一轮干活

## 二、修正理解 1：那三个 `cmp #N` **不是子命令**

| 之前（我在上一份文件里的推测） | 实际 |
|---|---|
| `cmp #1 / #3 / #4` 是"子命令编号"，受 arm 门控的是子命令 1/3/4 | **`cmp #N` 比较的是 `0x20004094` 这个"模式字节"的值**。三个处理器分别是**模式 1 / 模式 3 / 模式 4 的处理器**，主循环把它们都调一遍，各凭模式号自证身份 |

**证据**（三个函数的入口形态完全一致）：

```asm
08004780  push  {r7, lr}
08004782  sub   sp, #0x20
08004784  strb.w r0, [sp, #0x1f]     ; arg0 = 模式字节
08004788  str   r1, [sp, #0x18]      ; arg1 = 上下文
0800478A  ldrb.w r0, [sp, #0x1f]
0800478E  cmp   r0, #1               ; ★ 我是模式 1 吗？
08004790  bne.w #0x800499C           ;   不是→直接返回
08004796  ldr   r0, [sp, #0x18]
08004798  movw  r1, #0x1690
0800479C  ldrb  r0, [r0, r1]         ; ★ 再看 armed 标志
0800479E  cmp   r0, #1
080047A0  bne.w #0x800499A           ;   没 arm→返回
```

## 三、修正理解 2：`0x20004090` 是一块 **16 字节控制块**，`+4` 是模式选择器

| 偏移 | 含义 | 证据 |
|---|---|---|
| **`0x20004094`（+4）** | **模式选择器**（1 / 2 / 3 / 4 …） | 主循环读它；三个处理器按它自证；多处写入 |
| `+6 / +7 / +8` | 参数（由某个输入结构的 `+0xC/+0xD/+0xE` 拷入） | `0x80014CE / 0x80014D4 / 0x80014DA` |
| `+0xD / +0xE / +0xF` | 参数（被读入应答帧的 `+2/+3/...`） | `0x80015C6 / 0x80015CC / 0x80015D2` |

**已确认的模式写入点**：

| 写入值 | 地址 | 所在 |
|---|---|---|
| `= 1` | `0x8006E56` | `0x8006E4C` 分支（前置 `cmp r0,#1`） |
| `= 2` | `0x8006E78` | `0x8006E6E` 分支（前置 `cmp r0,#2`） |
| **`= 4`** | **`0x80086C2`** | **handler `A0-0x0D`（`0x080086B4`）** |
| （`= 3`） | 未在本次截断输出中确认 | 待补 |

> ★ **`0x8006DE0` 正是 `0x80` 类处理器调用的那个函数** —— 所以 **`0x80` 类很可能就是"设置模式 N"的命令**。这解释了 `0x80` 类存在的意义。

## 四、修正理解 3（核心）：`0xA2` 是**异步**产物

**消费 `armed` 并紧接着构造 `0xA2` 帧的代码，在模式 3 处理器 `0x8005050` 里：**

```asm
080052B6  movw  r1, #0x495E
080052BA  movt  r1, #0x2000          ; 上下文基址
080052BE  movw  r2, #0x1690
080052C2  strb  r0, [r1, r2]         ; ★ 清掉 armed
080052C6  movs  r0, #0xA2            ; ★ 紧接着：开始构造 0xA2 回复帧
```

**而 `A0-0x0D` 设的是模式 4，不是模式 3：**

```asm
080086B8  movw  r1, #0x4090
080086BC  movt  r1, #0x2000
080086C0  movs  r0, #4
080086C2  strb  r0, [r1, #4]         ; 0x20004094 = 4   ← 模式 4
080086C4  ...                         ; r0 = 0x2000495E
080086CE  ...                         ; 0x20005FEE = 1   ← arm
080086E0  movw  r0, #0x426C           ; memset(0x2000426C, 0x2C=44)
```

**模式 4 处理器 `0x8002470` 做的事**：

```asm
0800248C  ldrb  r0, [r0, r1]         ; armed
0800248E  cmp   r0, #1
08002490  bne.w ...                  ; 没 arm → 返回
08002496  ldr   r0, [sp, #8]
08002498  ldrb  r0, [r0]             ; 上下文 byte0
0800249A  cbnz  r0, ...              ; 非 0 → 跳走
0800249E  movw  r0, #0x403C          ; 读 0x2000403C
080024A8  lsls  r0, r0, #0x1F
080024AA  cbz   r0, ...              ; bit0 为 0 → 跳走
080024B8  and   r0, r0, #0xFE
080024BC  strb  r0, [r1]             ; 0x2000403C bit0 清零
080024C0  movw  r1, #0x168E          ; ★ ctx+0x168E（= 0x20005FEC）是个**计数器**
080024C4  ldrb  r0, [r2, r1]
080024C6  adds  r0, #1
080024C8  strb  r0, [r2, r1]         ; 计数 +1
080024CE  cmp   r0, #5
080024D0  blt   ...                  ; < 5 → 返回
080024D4  ...                        ; >= 5 → 推进（回绕 / 改模式）
```

### ⇒ 完整机制（一句话）

```
主机帧 → 分发器（主循环里）→ handler A0-0x0D：
            置 模式 = 4  · 置 armed = 1  · 清 44B 结构
                    ↓
主循环下一轮起，每轮调用三个模式处理器：
    模式4(0x8002470)：armed==1 → 清某个位 → 计数器 ctx+0x168E 累加，到 5 推进
    模式3(0x8005050)：mode==3 且 armed==1 → ... → 清 armed → 发 0xA2 帧
    模式1(0x8004780)：mode==1 且 armed==1 → ...
                    ↓
        计数器到 5 后推进 → 终会走到 模式 3 → 才产生 0xA2 回复
```

**⇒ `0xA2` 的产出依赖：① 模式推进到 3 ② 主循环转过足够多圈 ③ armed 仍为 1。**
**它不是"收到命令就立刻回"，而是"状态机走到那一步才回"。**

## 五、这解释了当年的假阴性

| 当年做法 | 为什么读不到 |
|---|---|
| 发一条 `A1` 帧 → **立刻读** → 无 `0xA2` | **回复是主循环异步产生的**。主循环要转几圈、计数器要累到 5、模式要推进到 3 —— **"立刻读"必然读不到** |
| 由此判定 H1 = 否（GT7868Q 不转发） | **验收方式错**，不是结论对 |

**另一个已知事实现在也说得通了**：项目发现"**纯读 `Col04 IN` 不被消耗、可重复读**" —— 那正是**"上一条应答的寄存器镜像"**。既然应答是异步来的，**正确的读法是反复读、等它出现**。

### ⇒ 正确的实验姿态（供将来在料板/样机上用）

```
1. 发帧（已知安全的那类）
2. 不要"立刻读"——改为【按固定间隔重复纯读】，持续 1–3 秒
3. 记录第一次出现非空 / 变化的那一刻
4. 若出现 0xA2 帧头 → H1 = 是（GT7868Q 会转发）
```

**⚠️ 红线不动**：**不要在真机上做这个**（`A0/A1` 帧正是会把通道打断的那类）。要验走**料板**，或用**厂商工具插桩**先拿到合法序列再回放。

## 七、净结论

| 项 | 状态 |
|---|---|
| **H1 的"否"** | ⚠️ **验收方式被推翻**。`0xA2` 是异步的，当年"立刻读"必然读不到 |
| 主循环结构 | ✅ 看清：**先跑分发器 → 再轮询三个模式处理器** |
| 那三个 `cmp #N` | ✅ 修正为**模式号 1/3/4**，不是子命令编号 |
| `0x20004090` | ✅ 新认识：**16 字节控制块**，`+4` = 模式选择器 |

| `0x80` 类的用途 | ✅ 基本确认是 **"设置模式 N"**（它调的 `0x8006DE0` 是模式写入器） |
| A0 子命令表 | ✅ 完整 16 条 + 地址 |
| **仍未定** | 模式如何从 4 推进到 3（计数器到 5 之后那步）；模式 3 的写入者 |

## 八、补完：状态机三件套（本节已把上面 1–3 项做完）

### 8.1 状态变量就挤在三个连续字节里

| 地址 | 相对 ctx | 含义 | 证据 |
|---|---|---|---|
| `0x20005FEC` | `+0x168E` | **计数器 0–5** | 模式 4 处理器 `+1`，到 5 清零 |
| `0x20005FED` | `+0x168F` | **"阶段推进"一次性标志** | 计数器到 5 时置 1，随后被消费清零 |
| `0x20005FEE` | `+0x1690` | **`armed`** | 命令写 1，模式 3 处理器消费后清 0 |

### 8.2 ★ 模式 3 的写入点找到了：`0x8006E9A`

模式写入器（函数含 `0x8006E28`）逻辑：

```asm
08006E2A  strb.w r0, [sp, #0xb]     ; arg0
08006E2E  str    r1, [sp, #4]       ; arg1 = 结构指针
08006E32  ldrb   r0, [r0]           ; arg1[0]  ← 特征字节
08006E34  strb.w r0, [sp, #3]

08006E3C  cmp r0(arg0), #1 ; bne 0x8006E5A
08006E46  cmp r0(特征), #1 ; bne 0x8006E5A
08006E56  → 0x20004094 = 1          ; 模式 1

08006E80  cmp r0(arg0), #2 ; bne 0x8006E9E
08006E8A  cmp r0(特征), #1 ; bne 0x8006E9E
08006E9A  → 0x20004094 = 3          ; ★★ 模式 3

08006EA8  → 0x20004094 = 0          ; 否则回空闲
```

**⇒ 模式写入器签名：`set_mode(arg0, struct)`**
| arg0 | struct[0] | 结果 |
|---|---|---|
| 1 | 1 | 模式 **1** |
| 1 | 其它 | 模式 **2** |
| **2** | **1** | **模式 3** ← **产生 `0xA2` 的那一档** |
| 其它 | — | 模式 0（空闲） |

### 8.3 ★ `0x8006DE0` 其实是**帧构造器**，不是模式写入器

```asm
08006DE0  push {r7, lr} ; sub sp, #8
08006DE4  strh.w r0, [sp, #6]        ; 参数（16 位）
08006DE8  r1 = 0x20004128
08006DF0  movs r0, #0x80 ; strb.w r0, [r1, #0x8C]   ; 帧头 = 0x80
08006DFC  movs r0, #2    ; strb.w r0, [r1, #0x8E]   ;     = 2
08006DF8  movs r0, #4    ; strb.w r0, [r1, #0x8D]   ;     = 4
08006E02  ldrh.w r0, [sp, #6] ; strb.w r0, [r1, #0x8F]  ; 参数低字节
08006E0A  ldrb.w r0, [sp, #7] ; strb.w r0, [r1, #0x90]  ; 参数高字节
08006E12  movw r0, #0x800 ; movt r0, #0x4001        ; ★ = 0x40010800 = GPIOA
08006E1A  movs r1, #8
08006E1C  bl   #0x800A7FC                            ; GPIO 写 → 发帧
```

**⇒ 这是"设备 → 主机"的一个帧构造器**：帧头 `0x80`，随后 `4, 2, <16 位参数>`，最后**操作 GPIOA 发出** —— 与项目记录的"帧构造器：填数据 → 操作 GPIOA"形态完全一致。

**⇒ 连带修正：`0x80` 类处理器 `0x08001628` 的真实作用** = **"取一个值（来自 `0x20005FF4+0x34`，上限钳到 1000）并构造 `0x80` 帧上报"**，不是"设置模式"。
（我上一节把 `0x8006DE0` 猜成"模式写入器"，**这里更正**：模式写入器是 `0x8006E28` 那个函数。）

### 8.4 模式 4 的"推进"逻辑

```asm
080024D4  r2 = 0x168E ; r0 = 0
080024DC  strb r0, [ctx, 0x168E]        ; 计数器清零
080024E0  r2 = 0x168F ; r0 = 1
080024E6  strb r0, [ctx, 0x168F]        ; ★ 置"阶段推进"标志 = 1
...
080024F4  ldrb r0, [ctx, 0x168F]
080024F6  cmp  r0, #1
080024F8  bne  → 返回
080024FC  ...                            ; 消费这个标志
```

**⇒ 模式 4 的完整行为**：`armed==1` → 清 `0x2000403C` 的 bit0 → 计数器 `+0x168E` 自增 → 到 5 则**清零并置阶段推进标志**。

### 8.5 现在这张图是闭合的

```
主机帧 ──→ 分发器（在主循环里跑）
             ├─ 类 0x80 → 0x08001628：取值(≤1000) → 构造 0x80 帧 → GPIOA 发出
             ├─ 类 0xA0 → 16 条子命令表
             │     0x0D → 0x080086B4：模式=4 · armed=1 · memset(0x2000426C,44)
             └─ 类 0xA1 → 0x080093D2 起的第二段
                          ↓
主循环每轮： 三个模式处理器各调一遍（按 0x20004094 自证身份）
             模式4 0x8002470：armed==1 → 计数 0x20005FEC++ → 到 5 置阶段标志
             模式3 0x8005050：mode==3 且 armed==1 → … → 清 armed → ★ 构造 0xA2 帧
             模式1 0x8004780：mode==1 且 armed==1 → …
                          ↓
              模式推进（由 set_mode(arg0,struct) 决定：1 / 2 / 3 / 0）
                          ↓
                   走到模式 3 才吐 0xA2
```

**⇒ 完全解释了"立刻读读不到"**：`0xA2` 出现在**主循环转到模式 3 那一轮**，而不是命令被处理的那一轮。
