## 〇、一句话结论

> **不是马达大小的问题，也不是芯片不同的问题 ——**
> **是「震动的扳机在谁手里」的问题：X9-15 由**主机**握扳机，我们这台由**固件**握扳机，且未给主机留入口。**
> **⇒ 而"滑动震动"本质要求主机能在任意时刻触发。**

## 二、硬件对照（实物照片 + 官方规格，均已核实）

### 2.1 两块板的结构（用户实拍，已互相确认标识）

```
[左] GT7868Q（触控主控） ──I2C1── [右] TF100A（压力+触觉 MCU） ──HDP/HDN── 马达
                                  （银色矩形件 = 马达，HDP/HDN 为其两根驱动线）
```

### 2.2 两块板的关键差异

| | **本机（ThinkBook 14 G6+ IMH）** | **ThinkPad X9-15 Gen 1** |
|---|---|---|
| ACPI 名 | `GXTP5100:00` | `GXTP5100:00` |
| **PID** | **`27C6:01E9`** | **`27C6:01EA`**（另一台 X9-15 报 `01EB`，ThinkBook 14+ 2025 报 `01E0`） |
| **执行器** | **小型 LRA**（FRU `5T60S94326`，批次 `240725 03`） | **Nidec TapSense**（丝印 `NIDEC 55F0410`，批次 `250809 02`） |
| 批次/FRU | `FRU: 5T60S94326` · `WKH53K` · 条码 `7906959400007` | QR `B57101538547` · `51B10A9110` |
| 排线丝印 | `ILVM AND R0C3PAD JRC` / `NBX00019000 Rev1.0` / `CV 2023.12.25` | — |
| 触觉形态 | 设备自决（按下沿/抬起沿各一次） | **主机可触发** |

### 2.3 Nidec TapSense 官方规格（`nidec.com/en/nidec-precision/product/tapsense/`）

```

★ 谐振频率      200 Hz          ← ★★★ 与 TF100A 的 TIM2 配置完全相同
过驱(OD)电压     7.0 Vrms        ← 远高于 3.3V ⇒ 必须升压/驱动电路
OD 波形         3-pulse sine wave

官方描述        「creates a variety of haptic feedbacks, such as tapping, ★swiping, scrolling, or flicking」
```

## 三、换模块实测与 Code 10 的 ACPI 机理

### 3.1 社区实测（B站视频 `BV1eSorBJE85` 评论区，@草坪上要种草）

> 「这俩互换的概率很大…**都属于 GXTP5100 系列的 haptic touchpad**，很可能**唯一的差距就在马达尺寸**…**我已经买了一块 X9-15 的触摸板**」
> 「**坠机了**，装上去 **windows 能看到有这么一个触摸板但是显示代码 10 无法启动**」
> 「goodix 系列的触控板貌似都是**免驱**的，现在问题是 **windows 读不到他的 HID descriptor** 导致设备 id 读不出来，也没有办法初始化设备」
> 「我解锁了 bios 的隐藏选项发现里面**并没有配置项**，触摸板的**初始化设置应该是写在 acpi 表里面的**」

**⇒ 症状组合（设备被枚举但描述符读不出来）精确指向 I2C-HID 初始化阶段的失败。**

### 3.2 本机 DSDT 里 `TPAD` 节点的机制（项目已有成果，本轮接合）

**`TPID` 五厂商表（`Name(TPID, Package(5))`，每条 5 字段：索引/从机地址/描述符寄存器/HID/CID）：**

| # | 索引 | I2C 从机地址 | 描述符寄存器 | HID | CID | 厂商 |
|---|---|---|---|---|---|---|
| 1 | 1 | 0x2C | 0x20 | `SYNA2BA6` | PNP0C50 | Synaptics |
| 2 | 2 | 0x15 | 0x01 | `ELAN06FA` | PNP0C50 | Elan |
| 3 | 3 | 0x2C | 0x20 | `CIRQ1080` | PNP0C50 | Cirque |
| **4** | **4** | **0x2C** | **0x20** | **`GXTP5100`** | PNP0C50 | **Goodix（本机命中）** |
| 5 | 255 | **0xFF** | **0xFF** | `XXXX0001` | — | **占位（无效）** |

**`TPDS(列, 值A, 值B, 默认)`** = 按「硬件上报的厂商索引」查表取值的查表函数（本 DSDT 内**无调用者** ⇒ 逻辑分散在 SSDT）。

### 3.3 ★ 本轮新解出的关键机制：`IICBADR0` 的真身

**实测（新增脚本 `re/acpi-iicb-scan.py`，扫 30 张 ACPI 表）：**

```
IICBADR0  ->  DSDT(3)  ← 只有 3 处【引用】，全表 0 处【定义】
              其余 29 张表全部 0
IICB      ->  DSDT 101 处，其中 98 处【独立】   ← 不是神秘跨表符号，是高频使用的名字
ADR0      ->  DSDT  15 处
I2C0      ->  DSDT 44 处 · SSDO 2 处（SSDO 里只是 External 声明）
```

**反编译（新增脚本 `re/dsdt-crs-dump.py`）解出真实形态：**

```
0x011707: Name(BUF0, Buffer(...))              ← ★ ACPI 资源模板缓冲
0x01171E: Name(IBUF, Buffer(...))              ← 中断缓冲
0x011732: ★ CreateDWordField(BUF0, 4, ADR0)    ← ★★★ 在模板偏移 4 处开 DWord 字段 = 【I2C 从机地址】
0x01173D: ★ CreateWordField (IBUF, 5, IRQN)    ← 中断号字段
0x011748: Store(..., ADR0)  0x011759: Store  0x01175F: Store
```

> ## **⇒ `ADR0` 不是变量，是「资源模板偏移 4 处的地址字段视图」；往它写就等于改写 I2C 从机地址。**
> ## **⇒ 所以"这台机该用哪个 I2C 地址"是**运行时拼出来的**，取决于 BIOS 探测到的厂商索引。**

### 3.4 Code 10 的因果链（本轮定案）

```
上电
  ↓ BIOS/EC 探测触控板模组 → 得到【厂商索引】
  ↓ 用 TPDS 查 TPID 五厂商表
  ↓ 命中第 4 条 → 地址 0x2C · 描述符寄存器 0x20 · HID "GXTP5100"
    未命中 → 落到第 5 条占位项（地址 0xFF · 寄存器 0xFF）
  ↓ 地址经 ADR0 写入资源模板，_DSM 用 IICB+ADR0 拼出最终资源
  ↓ Windows 用该地址 + 描述符寄存器发起 I2C-HID 读描述符
  ↓ ★ 地址/寄存器不对 ⇒ 读不到描述符 ⇒ 【代码 10】
```

**★ 这解释了那位网友看到的**精确症状组合**（设备在、但描述符读不出来），也解释了为什么他"解锁 BIOS 隐藏选项里没有配置项" —— 因为这一层是 **ASL 逻辑**，不是 BIOS setup 项。**

**★★ 两种可能成因（未分辨）：**
- **(a) 模组上报的厂商索引 BIOS 不认** ⇒ 落到占位项
- **(b) 本机 ACPI 未提供复位 GPIO / 上电延时**（项目记录里 TPAD 只有 `GpioInt` 中断引脚 182，**未提及任何 ResetGpio**），而 X9-15 模组需要复位才能吐描述符

## 四、★★★ 马达归属定案：在 GT7868Q 侧，不在 TF100A

### 4.1 本轮用**两种独立方法**验证「TF100A 的 PWM 占空比运行期恒定」

| 方法 | 结果 |
|---|---|
| **字面量搜索**（`0x40000034` = TIM2_CCR1 等） | **0 处** |
| **结构体间接搜索**（新增 `re/tf100a-tim-write-scan.py`：搜 `str rX, [rY, #0x34/0x38/0x3C/0x40]`，覆盖 `ldr rBase,[struct,#4]` 后间接写的全部代码形态） | **只有 SetCompare HAL（`0x08010908`）内部那 4 条**，而该 HAL **全固件仅 1 个调用者（初始化）** |

**⇒ 硬结论：TF100A 的 PWM 占空比**运行期不变**。**

### 4.2 由此推出的定案

```
若 TIM2 驱动马达 ⇒ 马达会【一直震】。实际不是。
⇒ 马达不由 TF100A 的 PWM 驱动。
⇒ "点击时震一下"只能由 GT7868Q 完成。
```

**★ 旁证：项目结论「无外部驱动 IC、MCU 直驱」中的那个"MCU"，此前被当成 TF100A，更可能是 **GT7868Q**。`HDP`/`HDN` 焊盘在版图上挨着 TF100A，但走线可以接到 GT7868Q 的引脚。**

### 4.3 另一条被本轮否掉的线索（诚实标注）

**此前曾怀疑「派发函数 `0x080110BC` 会分派到触觉播放」。本轮反汇编证明：**

```
0x080110BC 是尾调用蹦床 → 真正目标是 0x08011304
0x08011304 是 vsnprintf/printf 家族实现：
   cmp r0,#0x25('%') · cmp r0,#0x2a('*') · sub r2,r0,#0x30('0'..'9')
   ldr r2,[sb],#4 (va_arg) · cmp r0,#0x2e('.') · cmp r0,#0x6c('l') · cmp r0,#0x4c('L')
```

**⇒ `0x080059E0`（含 `0x28`=40 判据）→ 采集 19 点 → 打包 → `0x080110BC` → `0x08011304`(printf) —— 整条链终点是**调试打印**。**
**⇒ 那个 `|Δ|>40` 是**调试日志触发阈值**，不是震动阈值；改 `0x28` 只刷日志。**（补全了追加二十五里那条更正的证据链）**

## 五、纯软件四条路的最终裁定

| 路 | 裁定 | 依据 |
|---|---|---|
| **标准 HID 触发** | ❌ | 描述符无 `0x0E/0x21`；`Col02 Out=0`（PTP 集合**没有输出端点**） |
| **伪造描述符骗 Windows** | ❌ | 描述符只是声明；即便声明了，**发给设备的报文格式未知**（固件加密） |
| **改 TF100A**（`0x28` / 灵敏度） | ❌ | ① `0x28` 链终点是 printf；② TF100A 的 PWM 恒定 ⇒ **它不驱动马达** |
| **改 GT7868Q** | ❌ | 分组密码 **ECB**（13.42% 的 16 字节块重复 + 周期 8/16/32/64 类内熵显著低）；官方刷机工具**主机侧零变换**（原样 `memcpy`）⇒ 加扰算法在厂商内部工具里 ⇒ **解开也回刷不了** |
| **注入压力振荡** | ❌ | 实测震动=点击同阈值（按下 **140** / 抬起 **98**）⇒ 会造假点击 |
| **换 X9-15 模块** | ⚠️ **卡 ACPI** | 社区实测 Code 10；卡点已定位到 ACPI 初始化（见 §三） |
| **厂商命令触发** | ⚠️ **唯一未证否** | 读通道**已验证可用且稳定**（见 §六.3）；但项目当年那轮扫描**地址窗口根本没到 TF100A**（它自己的日志：读 `0x40D0` 得 24 个 `0x00`、`0x4134` 得 32 个 `0xFF`，**预期真值一个都没有**）⇒ **"39 条命令无马达入口"这个结论不成立** |

**★ 平台事实（Layer 1，确定）**：芯片相同、**固件不同** ⇒ 能力不同；固件与执行器（驱动链路）**绑定成一套**，换不了其中一半。
**★ 唯一悬念（Layer 2，未验）**：我们这份固件**有没有**一条**未声明**的厂商触发通道。

## 七、方法学（本轮新增）

1. **字面量搜索会漏掉结构体间接访问** —— 判"某寄存器运行期是否被改"时，必须**同时**搜字面量地址与 `str rX,[rY,#off]` 形态（基址来自结构体字段）。本轮对 TF100A 两者都做，才敢下"CCR 恒定"的结论。
2. **社区评论是有效的一手证据** —— "换模块 → Code 10 → 读不到描述符"这条信息，比任何推测都直接；且与 DSDT 静态分析**互相印证**。
3. **"派发函数"要打开看，不能靠名字猜** —— `0x080110BC` 被一路当成"上报派发器"，实际是 `printf` 蹦床；一个词的假设连带毁掉了一整条推论。
4. **厂商规格表能纠正"巧合"判断** —— Nidec TapSense 谐振 200 Hz 的官方数据，把"200 Hz 是采样时基巧合"这个判断推翻了。
5. **`support.lenovo.com` 会 403，但 `download.lenovo.com` 可直连**；取下载链接应走真实浏览器（`web-access`）。
6. **★ 在 x86 代码段里做 2 字节模式匹配会大量假阳性** —— `E9`(jmp)、`0F 84 xx`(jz) 等指令字节极易凑出 `01E9`/`01EA` 这类"厂商常量"。**任何"常量命中"都必须逐处回看上下文指令才能采信。**（本轮据此误报过"BIOS 里有 0x01EA"，见 §11.3。）
7. **"看到常量"不等于"它在比较"** —— 即使命中真实常量，也要继续读下去确认它出现在 `cmp`/白名单里，而不是打包进某个无关缓冲区。本轮的正面例子是：`cmp eax, 0x27c6` + `cmp eax, 0x1e8/0x1e9`，**这才是可采信的白名单证据**。

```asm

00005DC1  test  eax, eax
00005DC3  je    0x5ed0            ; ★ 前面那条 (PID & 0xFFF0)==0x1E0 的分支是【死代码】，永远被跳过

00005ED0  xor   eax, eax
00005ED2  cmp   eax, 1
00005ED5  je    0x5f0e
00005ED7  movzx eax, word ptr [rsp+0x40]   ; eax = VID
00005EDC  cmp   eax, 0x27c6                ; ★ VID == 0x27C6（汇顶）?

00005EE3  movzx eax, word ptr [rsp+0x34]   ; eax = PID
00005EE8  cmp   eax, 0x1e8                 ; ★ PID == 0x01E8 ?

00005EEF  movzx eax, word ptr [rsp+0x34]

00005EFB  lea   rcx, [rip + 0x3c56]
00005F02  call  0x97c                      ; 打印成功消息
```

### 11.3 ⚠ 本轮自身的一处误报（已更正）

**我曾据"字节模式匹配"报告「`I2cTouchPanelDxe.bin` 里有 `0x01EA` × 9 处、`0x01E9` × 2 处，说明本机 BIOS 认识 01EA」，并据此说要更正结论。**
**经逐处核对字节后，**该推断不成立**：**

```
0x01EA 的 9 处全部是 x86 指令编码：
  @0x0BB9 / @0x1F6A : 0F 84 EA 01 00 00   ← jz rel32（位移 0x1EA）
  @0x2311           : 48 83 EA 01         ← sub rdx, 1
  @0x23D4 / 0x24FC / 0x25F6 / 0x29F7 / 0x2E91 / 0x2E96 : 同类指令流

0x01E9 的 2 处同样是误报：
  @0x3186 : 41 01 49 06 / E9 B6 01 00 00   ← add + jmp rel32
  @0x31F4 : E9 DB 00 00 00                 ← jmp rel32
```

**更彻底的反证：`I2cTouchPanelDxe.bin` 里 `0x27C6 / 0x04F3 / 0x06CB / 0x0488` 的**小端出现次数全是 0** —— 该模块根本不含任何 VID/PID 常量。**

**⇒ 教训（已并入 §七 方法学）：**在 x86 代码段里做 2 字节模式匹配，`E9`(jmp) / `0F 84 xx`(jz) 会大量制造 `01E9`/`01EA` 假阳性；**任何"常量"命中都必须逐处看上下文指令才能采信。**（本轮在 TF100A 的 ARM 反汇编里犯的是同一类错的对称版：漏看结构体间接。）

> ## **⇒ 最终一句话：**
> ## **硬件同构 ⇒ 差异在固件；而正因为差异在固件，换模块也带不过来 —— 白名单只认 `0x01E8/0x01E9`，X9-15 那颗是 `0x01EA`。**
> ## **⇒ 两头堵死：自己的固件不给扳机；别人的固件过不了白名单。**

## 十二、★★★ 厂商命令通道：地址纠错 + 一个真 bug + 一次事故（2026-09-29 三补）

> **本节是本轮技术含量最高的部分**，也是必须留给后来者的操作教训。

### 12.1 ★ 地址纠错：项目一直用的是 **GTX8** 的地址，而本机是 **GT7868Q**

**官方源码里两代地址不同：**

| 常量 | `gtx8_gtx8.cpp`（GTX8） | **`gt7868q_gt7868q.cpp`（GT7868Q = 本机）** |
|---|---|---|
| `VER_ADDR` | `0x452C` | **`0x4014`** |
| `CMD_ADDR` | `0x60CC` | **`0x4160`**（`gt7868q_gt7868q.h:23`） |
| `CFG_START_ADDR` | `0x60DC` | **`0x96F8`** |

**实测对照（本机）：**
```
0x4014 = 00 87 00 00 | "YELSTO" @0x4018 | 06 00 | "7869" @0x4022   ← ★ 官方 VER_ADDR，返回真值
0x4160 = FF FF FF FF                                              ← 官方 CMD_ADDR，空闲态
──────────────────────────────────────
0x4000 = A7 E0 ED B1   ← GTX8 语境的旧读点，乱码
0x452C = AE EB 22 90   ← GTX8 的 VER_ADDR，本机乱码
0x60CC = 99 F5 FB 01   ← GTX8 的 CMD_ADDR，本机乱码
```

**★ 附带更正：设备**实时自报**的是 `YELSTO` + **`7869`**（不是固件容器上的 `7868Q`）—— 芯片与固件容器的型号串**不同**。**

### 12.2 ★★★ 找到并修复一个真 bug：`Gx::Write` 的帧长度字段

```csharp
// 修前（Gx.cs）：
pkt[4] = (byte)(data.Length + 7);        // ❌ 16 位地址帧误用 +7
// 修后：
pkt[4] = (byte)(data.Length + 5);        // ✅ 官方是 +5
```

**★ 这个坑项目**自己早就发现过** —— 就写在 `WriteHelper.cs:54` 的注释里：**
> `p[4] = (byte)(data.Length + 5);   // ★★ 官方是 +5（16 位地址），不是 +7 ★★`

**⇒ 但 `GTX8.BuildWrite` 修了，`Gx::Write` 没同步修 —— 而项目所有探针脚本用的是 `Gx::Write`。**

**修前/修后的**实测差异**（同地址 `0x4160`、同命令 `0x34 00 00 00 34`）：**

| 帧 | 写入后 `0x4160` 的变化 |
|---|---|
| **`+7`（旧）** | `FF FF FF FF` → **`FF FF FF FF`（毫无变化）** ⇒ 整帧被设备**丢弃** |
| **`+5`（新）** | `FF FF FF FF` → **`FF 00 00 00`（确实被改动）** ⇒ **写入落地** |

> ## **⇒ 项目当年那轮「39 条命令全表覆盖、无马达入口」的扫描，**每一条命令都被设备丢弃了**。**
> ## **⇒ 该结论**作废**：厂商命令通道**从来没有被真正打开过** —— 不是设备拒绝，而是**帧是坏的**。**

### 12.3 命令协议（官方源码，已实测）

**命令格式**：5 字节 `{ cmd, param, 0x00, 0x00, checksum }`（由 `cmd_init(buf, cmd, param)` 构造；`0x32/0x33/0x34` 的 checksum = cmd 本身）

**完整命令表：**

| 命令 | 字节 | 语义 |
|---|---|---|
| `0x32` | `32 00 00 00 32` | 切 PTP 模式 |
| `0x33` | `33 00 00 00 33` | 禁用坐标上报 |
| `0x34` | `34 00 00 00 34` | 启用坐标上报 |
| **`0x80`** | `cmd_init(buf,0x80,0)` | "我要发配置" ← ★ **唯一有 `0x82` 应答的命令** |
| `0x83` | `cmd_init(buf,0x83,0)` | （配置流程） |
| `0x7D` | `cmd_init(buf,0x7D,0)` | `END_SEND_CFG` |
| `0x00 0x10` | `00 10 00 00 01 01` | 切到 patch/bootloader ☠ |
| `0x00 0x11` | `00 11 00 00 01 01` | 开始更新 ☠ |
| `0x0E 0x13` | `0E 13 00 00 01 01` | 重启 ☠ |
| `0x03 0x03` | `03 03 00 00 01 01` | 切 PTP 模式（gtx8 版） |

**状态判据（实测校正）：**
```
0x4160 字节 0 = 命令码
写完任一 5 字节命令后，字节 0 都回到 0xFF（空闲）—— 这【不是】"接受"信号，是常态
0x82 只出现在命令 0x80 之后，且需等约 250 ms（官方先 usleep(250000) 再轮询）
6 字节写入走不同路径：写 {0E 13 00 00 01 01} 后字节 0 保持 0E（未被清除）
```

**⇒ 因此：对任意操作码**不存在通用的"接受/拒绝"信号** —— "扫操作码找命令"缺少判据。**

### 12.4 ⚠️ 一次挂起事故（可复现，已完全恢复）

**经过：**
```
[0x30] 写前 FF 00 00 00 | 回读 FF×6 | health OK
[0x31] 写前 FF 00 00 00 | 回读（空） | ★ HEALTH FAIL    ← 立即停止（健康门生效）
此后所有读取：send-fail err=121 (ERROR_SEM_TIMEOUT)
等待 10s / 30s 后重试：仍 err=121
但 Windows 侧：ACPI\GXTP5100  Status=OK · CM_PROB_NONE · "working properly"
触控板：完全无响应（光标不动、点击无效）
```

**恢复：重启电脑 ⇒ 完全恢复**
```
0x4014 = 00 87 00 00 | 0x4018 = "YELS" | 0x401C = "TO" | 0x4160 = FF FF FF FF
ACPI\GXTP5100 Status=OK
```

**★ 由此得到的硬结论：**
1. **命令寄存器是**易失**的 ⇒ 挂起**只是状态问题，不损伤固件/flash** ⇒ **重启即恢复（已实测）**
2. **`0x30` / `0x31` **不是"无害的无效命令"** —— 固件对它们**真的有反应**（停止响应输出报告）**
3. **`0x50`（未知码）无任何异常** ⇒ 固件对无关码宽容 ⇒ **`0x30/0x31` 的特殊性本身是一条线索**
4. **我们的写入**只碰了命令寄存器**，未碰 flash / 配置区 / 固件区，也未发那三条 ☠ 命令**

### 12.5 ⚠️ 健康门的有效与无效（方法学）

| | 有效 | 无效 |
|---|---|---|
| 健康门（`0x4014` 必须为 `YELSTO`） | ✅ **挡住了"继续往下发"** —— `0x31` 一失败立刻停手 | ❌ **挡不住"已经发出去的那一条"把固件卡住** |

**⇒ 正确做法（下次必须遵守）：**
```
① 先用已知安全命令（0x34）验证握手 → 确认"写 → 设备响应"链路
② 只在官方命令表内验证（0x32/0x33/0x34）
③ 未知区改成【一次只试一条】，两条之间必须有可复位手段
④ ⚠️ 当前会话非管理员 ⇒ pnputil /restart-device 与 Disable/Enable-PnpDevice 都不可用
   ⇒ 唯一复位手段是【重启电脑】⇒ 未知区扫描的频率上限 = 每次重启一条
⑤ 官方 RESTART 命令 {0E 13 00 00 01 01} 【未】被接受（字节 0 保持 0E，未被清除）
   ⇒ 不能当软件复位用
```

## 十四、点击阈值的搜索进展（2026-09-29 五补，部分为进行中的工作）

> **目标**：找到那个值为 **140**（按下）/ **98**（抬起）的寄存器 ⇒ 写小它 ⇒ 滑动时压力自然波动反复跨阈值 ⇒ **反复震动**。

### 14.6 扫描中的意外发现：`0x2D64` 是**运行时变动**位置

## 十五、★★★ 两代白名单精确对比 · 厂商刻意锁定 · 与"改 BIOS"的可行性调研（2026-09-29 六补）

### 15.1 ★★★ 两代白名单的差异，精确到一条指令

**方法**：从 X9-15 的 BIOS 里挖出**同一份汇顶 DXE 驱动**（`x9bios\out_sc1\N4C_SC1_blob03_dec.bin`，含 `InitGoodix`×6 / `GTPHIDRead`×4 / `Found Goodix device guid`）并反汇编，与本机 `bios\out\GoodixTpDxe.bin` 逐条对比。

**X9-15 的驱动：**
```asm
BAA14A:  3D C6 27 00 00     cmp   eax, 0x27C6           ; VID == 汇顶?
BAA150:  0F 85 F5 00 00 00  jne   <失败>
BAA15B:  25 F0 FF 00 00     and   eax, 0xFFF0           ; ★ 掩掉 PID 低 4 位
BAA160:  3D E0 01 00 00     cmp   eax, 0x1E0            ; ★ 等于 0x1E0 即可
```

**本机的驱动：**
```asm
00005DCE: cmp eax, 0x27c6      ; VID == 汇顶
00005DE3: cmp eax, 0x1e0       ; ★ 宽松检查（掩低 4 位）—— 见下行
00005DBF: xor eax, eax
00005DC1: test eax, eax
00005DC3: je    0x5ed0         ; ★★★ 恒跳 ⇒ 宽松检查是【死代码】，被跳过
──────────────────────────────────────────
00005EE8: cmp eax, 0x1e8       ; 实际生效：精确匹配 {0x01E8, 0x01E9}
00005EF4: cmp eax, 0x1e9
```

| | **X9-15** | **本机** |
|---|---|---|
| 白名单 | `VID 0x27C6` 且 **`(PID & 0xFFF0) == 0x1E0`** ⇒ **整个 `0x01E0–0x01EF` 家族** | `VID 0x27C6` 且 **PID ∈ {`0x01E8`, `0x01E9`}**（精确） |
| 对 X9-15 模块（`0x01EA`） | ✅ 接受 | ❌ **拒绝 ⇒ Code 10** |

> ## **⇒ ★★★ 关键发现：**本机 BIOS 里**本来就有** X9-15 那条宽松检查（`cmp eax,0x1e0`），但被**故意禁用成死代码**（`xor eax,eax; je` 恒跳）。**
> ## **⇒ 说明"只认两个 PID"是**厂商刻意的锁定**，不是代码疏忽或版本落后。**

### 15.2 ★ 白名单检查是**引导期**行为（重要推论）

```
GoodixTpDxe 是 DXE 驱动 ⇒ 在【开机过程中】读触控板 VID/PID 并比对白名单
操作系统在那【之后】才启动
⇒ ★ 操作系统侧【无法影响】该判定
⇒ 排除"从系统侧想办法绕过白名单"的一整类思路
```

### 15.3 ⚠️ 本轮自身第二处误报（`_BG`，已更正）

**我曾报告"BIOS 里发现 `BootGuard _BG` 标记 × 3，说明启用了 Boot Guard"。**
**逐处回看上下文后推翻：**
```
013CD9A6: 5F 42 47 4D 41 00 00   →  "_BGMA"   ← ACPI 命名空间路径 \._SB_BGMA 的一段
000321C6: 5F 42 47 4D 41 00 00   ← 同上（X9-15 侧）
⇒ 那些 "_BG" 字节属于 ACPI 字符串，【不是】Boot Guard 标记
```
**★ 结论：**我**没能**证实 Boot Guard 是否启用。**
**★ 教训（与 §11.3 同源，已是本会话第二次）：**二进制短字节模式匹配的命中，**必须**回看上下文指令/字符串才能采信。**

### 15.4 "改 BIOS 白名单"的可行性调研（含社区方法）

**社区脉络（已检索）：**

| 来源 | 内容 | 对本机的适用性 |
|---|---|---|
| `deguard`（Coreboot 项目，`review.coreboot.org/deguard`） | 专门击败 Intel Boot Guard 的工具链 | 用于**移植 Coreboot**，非"改白名单" |
| Win-Raid：`Lenovo ThinkBook 16p G5 IRX: SPI Image Creation` | ★ **现代 ThinkBook 的 SPI 镜像自制讨论** | ★ 最接近：**证明现代 ThinkBook 的 BIOS 确实可改** |
| `1vyrain`（n4ru） | xx30 ThinkPad 的 LiveUSB 漏洞链（白名单/高级菜单） | ❌ 仅老机型 |
| `Lenovo-whitelist-tool`（GitHub） | 联想白名单工具 | ❓ 需细看，多半也是老机型 |
| 3mdeb Dasharo《Introduction to deguard》 | Boot Guard 原理 | 参考资料 |

**★ 那条 Win-Raid 帖同时是一份**警告**：**
> 发帖人「解锁了 BIOS 高级设置，手动关掉 JEDEC write leveling 与内存训练选项」⇒ **重启后不再 POST（变砖）**，且无恢复手段。

**关键技术分析（对本机有利的一点）：**
```
Intel Boot Guard 只验签【IBB】= Initial Boot Block
   （BIOS 区域最前、内存初始化【之前】就运行的那段：SEC / 早期 PEI）
而 DXE 驱动（含 GoodixTpDxe）在【内存初始化之后】加载
   ⇒ ★ 不在 IBB 内 ⇒ 不在 Boot Guard 的验签范围内
⇒ 理论上：用【硬件 SPI 编程器】离线改写 GoodixTpDxe 的那一个字节，
          Boot Guard 管不到；离线刷写也绕过 PCH 的区域写保护（那是运行时保护）
```
**★★ 但有三道未知关卡：**
| # | 关卡 | 状态 |
|---|---|---|
| 1 | 联想是否对 BIOS 区域整体做**自签名**校验 | ❓ 未知 |
| 2 | `GoodixTpDxe` 所在 FV 是否带签名/校验标志 | ❓ 未查 |
| 3 | 改后需重算 FFS/FV 校验和 | ✅ 技术已知 |

**★★★ 而完整代价是：**买编程器 → 拆机接 SPI（flash 常在主板背面）→ 完整备份 → 改 1 字节 → 重算校验 → 刷回（失败即变砖，救回靠同一编程器）→ 再拆机换模块。**

### 15.5 结论：为什么**不建议**走这条路

| 理由 | 说明 |
|---|---|
| **与本项目的约束直接冲突** | 用户明确要求「**完全以程序的方式**，让所有 tb14+ 的压感触控板都能用」；刷 BIOS + 拆机换模块**既非程序方式，也只对这一台有效** |
| **风险与收益不成比例** | 为一块 ¥179 的模块，押上整机变砖风险（Win-Raid 那位就是前车之鉴） |
| **仍是硬件路线** | 即便成功，得到的是"这一台能用"，而非"所有 tb14+ 都能用" |
| **软件侧已无路** | §五 的裁定表 + §12/§13/§14 的硬负结果 |

**★ 净结论：把 X9-15 的硬件 ID 加入白名单，**技术上理论可行（DXE 不受 IBB 验签约束），实际上不可行（成本/风险/性质三重不匹配）。**

## 十七、★★★★★ 马达归属**翻转**：驱动者是 **TF100A**，不是 GT7868Q（2026-09-29 七补）

> **本节推翻本文 §四 与 §〇 的核心结论（「马达归属：在 GT7868Q 侧，不在 TF100A」）。**
> **触发原因是一条**外部专家确认**；而回看证据，项目当年的"排除 TF100A"论证本身就有漏洞。**

### 17.1 外部专家确认（独立来源）

**对象**：QQ 群「AL-1S Bot 非官方技术群」群主 **UMP45** —— 有**实际逆向消费级触觉触控板**（Surface 系列）的经验；
本轮他给的方法论（先看芯片 → GitHub 找资料 → **逆向驱动包** → 顺着执行器往上找上游）已被验证有效。

**他的原话（针对本文分析）：**
> ## **「是的宝宝，**goodix 不控制振动本身**」**

**⇒ 即：汇顶 GT7868Q **不驱动**马达。★ 这与本文 §四 的结论**直接冲突**。**

### 17.2 回看 §四 的论证：它有一个未闭合的漏洞

**§四 的推理：**
```
TF100A 的 TIM2 的 CCR（比较值）运行期恒定
  ⇒「若 TIM2 驱动马达，就会一直震」⇒ 矛盾
  ⇒ 判定 TF100A 不驱动 ⇒ 因此在 GT7868Q 侧
```

> ## **★ 漏洞：`CCR 恒定 ⇒ 不驱动` 只在【输出已使能】时成立。**
> ## **· 驱动 LRA 的**标准做法**恰恰是「固定振幅（CCR 恒定）+ 仅在事件时打开输出使能」**
> ## **⇒ 所以 CCR 恒定**不但不排除** TF100A 驱动，反而**符合**脉冲式触觉驱动的典型特征。**
> ## **★ 而 §四 是**用排除法**得出「在 GT7868Q 侧」的 —— 排除不成立，结论自然不成立。**

### 17.3 支持「TF100A 驱动」的四条证据

| # | 证据 | 说明 |
|---|---|---|
| **1** | ★ **外部专家确认** | UMP45：「goodix 不控制振动本身」—— 他逆向过同类设备的振动链路 |
| **2** | ★★★ **TF100A 的 TIM2 精确配在 200 Hz**（PSC=119 / ARR=1999） | **而 LRA 的谐振频率就是 200 Hz**（Nidec TapSense 官方规格）。把定时器精确配在执行器谐振点上，是**触觉驱动**的标配，不是巧合 |
| **3** | **§四 的排除论证有漏洞**（见 17.2） | 该论证不成立 |
| **4** | **TF100A 固件为明文，且自带 `TF100A_Test_FW`** | 一颗**只做压力采集**的 MCU 不需要把 PWM 配到执行器谐振频率，也不需要这么完整的测试固件 |

### 17.4 更正后的架构

```
Windows 主机
   │ I2C0（PCH I2C，从机 0x2C）
   ▼
GT7868Q（汇顶）—— 触控主控 / 主机接口 / 【决策】
   · 4 个 HID 集合（Col01–04）· PTP 坐标 · 压力上报（0x0D/0x30, 0–2000）
   · 厂商命令通道 0x4160 · 寄存器 0x4014
   · ★ 判定"点击"（阈值 140/98）⇒ 决定"该震了"
   · 固件：加密
   │ I2C1（内部总线，主机够不到）
   ▼
TF100A（钛方，ARM MCU）—— 力传感前端 + 【马达驱动】
   · 4 通道压感采集
   · ★ TIM2 @ 200 Hz = LRA 谐振频率 ⇒ LRA 驱动
   · 固件：★ 明文（官方 BIN 0x19A00+，含 TF100A_Test_FW / ARM 地址表 / 构建时间）
   │ HDP / HDN
   ▼
LRA（马达）
```

|---|---|---|

## 十八、★★★ 硬件实证：`CA4F` 是 LRA 驱动；以及**两次自我推翻**（2026-09-29 八补）

> **本节先记**已由实物确认的硬事实**，再**如实记录本轮两次错误的推断**，最后在 §18.5 给出当前证据指向。**
> **⚠️ 读本节请注意：§18.3 与 §18.4 是**被推翻的推断**，不是结论。**

### 18.1 ★★★ 硬事实 ①：`CA4F` = LRA 驱动 IC（实物确认）

**来源：用户对触控板模组的实物拍摄与人工确认。**

```
模块上 HDP/HDN 焊盘旁有一颗小 IC，丝印：
    CA4F
    ABF3
用户实测：封装 = 长边 6 脚 + 短边 4 脚 ⇒ 6×2 + 4×2 = 【20 脚 QFN】
用户实测：★ 其中【4 路】焊盘直接连到马达的 FPC（HDP/HDN 所在那张金色 FPC）
周边元件：★ 一颗【升压电感】+ 多颗电容
```

**⇒ 推论（强）：`CA4F` 是一颗**带升压的专用触觉（LRA）驱动 IC**：**
- **LRA 需高压驱动（Nidec TapSense 规格 OD 7.0 Vrms），板载只有 3.3V/5V ⇒ 必须升压 ⇒ 电感即其升压元件**
- **4 路到马达而非 2 路 ⇒ 除 H 桥外很可能含**反电动势检测 / F0 谐振跟踪**（智能驱动的标配）**

**同类公开器件（形态一致，供类比）：AW8697FCR（艾为）· DRV2625 / DRV2667（TI）·「11V Fast Startup With F0 Detect And Tracking LRA Haptic Driver」**

### 18.2 ★★★ 硬事实 ②：TF100A = 压力采集前端（本次读码确认，硬件级）

```
0x08005CD4  压力采集模拟前端初始化（GPIOA/GPIOB 模拟输入 + ADC1 配置链）
0x08006B98  ★ ADC1 + DMA1 连续采样：
              写 0x4001244C = ADC1_BASE + 0x4C = 【ADC1->DR 数据寄存器】
              ⇒ 硬件自动搬运采样值，非软件轮询
0x0800F81C  GPIO 引脚配置辅助函数（本次解出参数语义：(cfg & 0xF) | mode）
```

**★ GPIO 配置表（按 `(cfg&0xF)|mode` 解码，共 8 个调用）：**

| 调用点 | 端口 | 4 位配置 | 引脚 | 含义 |
|---|---|---|---|---|
| `0x0800A440` | GPIOA | **0xB** | `0x001` | **PA0 复用推挽 50MHz** |
| `0x0800DA62` | GPIOA | `0x3` | `0x008` | PA3 普通推挽（"门铃"） |
| `0x0800DF6E` | GPIOA | **0xB** | `0x200` | **PA9 复用推挽** |
| `0x0800DF7C` | GPIOA | **0xB** | `0x400` | **PA10 复用推挽** |
| `0x08005CF6` / `0x08005D0A` | GPIOA/GPIOB | `r2==4` 分支 | — | 模拟输入（压力采集） |

**★ `0xB` = CNF=10（复用推挽）+ MODE=11（输出 50MHz）。而 `0x0800DF7C` 之后**紧接着**加载 `0x40013800`（**USART1**）⇒ PA9/PA10 更可能是 **USART1**（与项目原判断一致）。**

### 18.3 ❌ 被推翻的推断 ①：「TF100A 用 TIM1/TIM8 互补输出驱动 LRA」

**当时理由：** 外设枚举显示 `0x40012C00`(TIM1) 与 `0x40013400`(TIM8) 各 7 处引用，
而 TIM1/TIM8 是**高级定时器**（互补输出 CHxN + BDTR/MOE），正合差分驱动 LRA。

**推翻依据：**
```
· 定时器 HAL（0x080105AC CCER 配置器 · 0x08010908 SetCompare · 0x08010D80 MOE_Set …）
  的【每一个】调用者都只有 1 个：那个"播放器" 0x0800D704
· 而播放器内部只做两件事：cmp 0x40000000(TIM2) 与 cmp 0x40000400(TIM3)
  ⇒ 它【从不】以 TIM1/TIM8 为参数被调用
· ⇒ 0x080105AC 里那段"若为 TIM1/TIM8 则额外配置互补通道"的代码 = 【死代码】
```

### 18.4 ❌ 被推翻的推断 ②：「TF100A 运行期门控 PWM ⇒ 路是活的」

**当时理由：** 找到 `TIM_MOE_Set`（`0x08010D80`，置/清 BDTR 的 MOE 位），以为运行期会开合它。

**推翻依据：**
```
0x08010D80 = TIM_MOE_Set(timer, enable)：
   enable==1 → [tim+0x44] |= 0x8000    （置 MOE）
   else      → [tim+0x44] &= ~0x8000   （清 MOE）
其【唯一】调用者 = 0x0800D78E（播放器的 TIM2 分支），参数 enable=1，
★ 且该调用发生在【初始化】路径中（播放器由 TIM2 初始化链调用）
⇒ MOE 开机即置位，运行期从不被改
⇒ 若该 PWM 真驱动 LRA，LRA 应【一直震】—— 实际不是
⇒ 结论：LRA 不接在 TF100A 的 PWM 上
```

### 18.5 ⇒ 当前证据指向的架构（**谨慎表述，非定论**）

```
GT7868Q（汇顶，固件加密）── 触控 / HID / 判定"该震了" / 【很可能直接下发触发】
   │ I2C1（内部总线，主机够不到）
TF100A（钛方，固件明文）── 压力采集（ADC1+DMA 已证实）+ 通用 I²C 驱动（中断驱动）
   │
CA4F（20 脚 QFN，升压 + 桥，4 路直连马达 FPC）── ★ 波形发生器 + 驱动器
   │
LRA
```

**★ 与 UMP45 的话自洽：「goodix 不控制振动**本身**」= 汇顶不产生波形、不驱动；但**可以下发"播放哪段波形"的触发**。**

### 18.6 ⚠️ 仍未定的一点（下一轮要做的判定）

**问题：`CA4F` 的 I²C 主机是谁？**

**本轮新观察（尚未得出结论）：**
```
TF100A 里存在一套【完整的、中断驱动的通用 I²C 驱动】：
   · 读 I2C1_SR1(0x40005414) / SR2(+4) 后按事件分派
   · 读写 I2C1_DR(0x40005410)
   · 带事件回调指针（结构体 +0x114 / +0x118）
   ⇒ 属厂商 SDK 风格，【主/从两种模式都支持】
★ 因此"驱动库存在"不能回答"TF100A 是否发起主机传输"
⇒ 必须查：谁调用了该驱动的【主机发送入口】
```

**★ 决定性判据（明确、不需硬件）：**
> **若 TF100A 从不发起 I²C 主机传输 ⇒ 它不可能命令 `CA4F` ⇒ 主机只能是 GT7868Q ⇒ 扳机仍在加密固件里。**

### 18.7 ★ 方法学：本轮两次自我推翻的教训

| # | 我提出的推断 | 推翻它的判据 | 教训 |
|---|---|---|---|
| **1** | TF100A 用 TIM1/TIM8 互补输出驱动 LRA | **HAL 调用者唯一性分析**：所有定时器 HAL 的唯一调用者只处理 TIM2/TIM3 ⇒ TIM1/TIM8 分支是死代码 | **"外设被引用"≠"外设被使用"** —— 必须追到**调用者**，再追到**参数的实际取值** |
| **2** | TF100A 运行期门控 PWM（路是活的） | **`TIM_MOE_Set` 的唯一调用点 + 参数 enable=1 + 位于初始化路径** | **"找到开关函数"≠"开关会被拨动"** —— 必须同时证明**存在运行期调用点** |

**★★ 两条教训的共同点：**我只证明了"代码存在"，就当成"行为发生"** —— 与 §16.4 记的三次错误（把推断当结论）**同源**。**

**⇒ 补充纪律（写给后来者）：**
```
凡"某功能在运行期发生"的断言，必须给出【运行期调用点】的证据：
  · 该函数的调用者是谁
  · 调用发生在初始化路径还是运行期路径
  · 传入的参数是什么
三者缺一，只能写"存在该代码"，不能写"该功能生效"。
```
