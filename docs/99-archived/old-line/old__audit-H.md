# 对抗性审计报告 — 假设 H 的可推翻性

**假设 H**：TF100A（触控板模组内，STM32F1 类，明文固件）在 I²C1 上只做从机，从不发起任何 I²C 主机传输；它也没有其它可用总线去命令第三方芯片。

**审计目录**：`fw-touchpad\verify-B\`（全部脚本与输出，未修改任何已有文件）
**审计方式**：不复用 `touchpad_TF100A_thumb.asm.txt`，直接从 `touchpad_GT7868Q_fw.bin` 用 capstone 5.0.7 重新线性解码（20,314 条指令），自建常量传播 / 物化点配对 / 有界反向切片 / 可达性分析。

## 1. 裁决

# **部分推翻**

- **H 的后半句（"没有任何其它可用总线去命令第三方芯片"）—— 被推翻。**
  镜像中存在完整、可达、且**实际写数据寄存器**的 USART（串口）驱动。
- **H 的前半句（I²C1 只做从机、从不发起主机传输）—— 未被推翻。**
  全镜像对 I²C1 寄存器块（0x40005400–0x40005440）只证得 **3 条访存**，其中对 CR1 只有 **1 次写**，且不置位 START/STOP/SWRST，也没有任何 CCR/TRISE/CR2 写入。

## 2. 逐条裁决表

### 第 1 条 — 软件模拟（bit-bang）I²C

**结论：未找到。不能推翻 H。**

| 命令 | 作用 |
|---|---|
| `python gpiobang.py` | 枚举所有 GPIO 端口基址物化点 + BSRR/BRR/ODR/CRL/CRH 写 |
| `python final_q.py` | 同上（修正 `movt` 隐式物化：`movs r0,#0` + `movt r0,#0x4001` 时低半为 0 的 bug） |
| `python bitbang_final.py` | 对每个 GPIO 常量做有界反向切片求 (r0,r1)，穷举 GPIO 库函数调用点 |

关键证据：

1. 全镜像 **零** 处 GPIO 端口基址后的 `+0x0C(ODR)` / `+0x10(BSRR)` / `+0x14(BRR)` 直写。
   `final_q.py [1]` 列出的全部候选，经复核**都在 GPIO 库函数的函数体内部**（参数化基址），不是调用点。
2. GPIO 位操作库函数已定位并按函数体精确区分（`callsites.py` / `pin.py`）：
   - `0x08010D1C` = `GPIO_SetBits`：`ldr r0,[r1,#0xc]; orrs r0,r2; str r0,[r1,#0xc]`
   - `0x08010D30` = `GPIO_ResetBits`：`ldr r0,[r1,#0x10]; bics r0,r2; str r0,[r1,#0x10]`
   - `0x08010D44` = `GPIO_ReadOutputDataBit`：**同时**读 `+0xc`(ODR) **和** `+0x10`(BSRR) —— 这解释了 `final_q.py` 在 `0x08010D16/0x08010D2A/0x08010D3E` 的"BSRR/BRR/ODR 三连击"命中，**是库函数体，不是 bit-bang 时序**。
   - 全镜像 `bl` 到这些库函数的站点只有 4 处，其 (r0,r1) 为：`0x40000400 mask=0x1` ×2（TIM3，非 GPIO）、`0x1D`/`0` ×2 ⟹ **无一处针对真实 GPIO 端口**。
3. 反向切片证明：GPIOC 常量在 `0x08010CAA` 处作为 r0 传入 `0x0800F81C`（= `GPIO_Init`），随后 `0x08010CD4 ldrh r0,[r0,#0xc]` 是读 ODR，无写。

> 无成对、无规律的引脚拉高/拉低序列（任何 bit-bang I²C 都必然在 ODR/BSRR/BRR 上留下成百上千次写）。**结论：镜像内不存在软件模拟 I²C。**

### 第 3 条 — 其它可能承载"命令第三方芯片"的总线

命令：`python q2_q3.py`、`python funcs.py 0x800DF4C 0x800DFE0`、`python reach.py ...`

| 事实 | 地址 |

| 引脚配置：`GPIO_Init` on `0x40010800`(GPIOA) pin 0x18/0x48 mode 3 = **PA11/PA12 AF 推挽 50MHz** | `0x0800DF64`–`0x0800DF7C` |
| 引脚配置：`GPIO_Init` on `0x40010800` pin 0x28/0x38 mode 3 = **PA9/PA10（USART1 TX/RX）** | `0x0800DF64`–`0x0800DF7C` 邻近序列 |
| USART 基址分派覆盖 `0x40004400 / 0x40004800 / 0x40004C00 / 0x40005000 / 0x40013800` | `0x08010E0E`–`0x08010E58`（裸机多 UART 驱动表） |

⚠️ 但注意：`0x40004400 / 0x40004800 / 0x40004C00 / 0x40005000` **不是 STM32F1 标准 USART 基址**（标准为 `0x40013800`/`0x40004400`/`0x40004800`）。这说明该驱动是**跨芯片移植来的通用裸机 UART 库**，实际只有 `0x40013800`(USART1) 与 `0x40004400`(USART2) 是真实地址。这不影响"存在数据寄存器的真实写"这一反证，但影响"实际用的是哪一路"的判定。

### 第 4 条 — 间接写 I²C 寄存器（绕开直接 `str`）

**结论：未找到绕开路径。不能推翻 H。**

命令：`python masterhunt.py`（含 `mov` 传递 / `orr`·`bic` 常量推导 / `bl` 后保守清空）、`python halmap.py`（形参寄存器偏移映射）、`python i2cmap2.py`、`python reach.py`

| 检查路径 | 结果 |
|---|---|
| **辅助函数传基址** | `0x0800FA14`（`0x0800F9F8` 体）与 `0x08008B98` 确实把 `0x40005400` 当参数传入，且**函数体内确实写了 I²C 寄存器**：`halmap.py` 显示 `0x0800FA20` 对**形参 r0** 写 `+0x04`(CR2)、`+0x20`(TRISE ×3)、`+0x1C`(CCR 读改写)；`0x0800FC44` 读 `+0x14`(SR1)、`+0x18`(SR2)。**但这些都是从机模式必需的寄存器**：CR2 只用于 FREQ/ITERREN/ITBUFEN，CCR/TRISE 是从机模式下硬件要求的时序配置，SR1+SR2 连读是**唯一**的清 ADDR 手段。**START/STOP/SWRST 位在整个镜像中没有被置位。** |
| **DMA 写外设寄存器（CPAR→0x40005400）** | 0（见第 3c 条） |
| **函数指针 / 跳转表间接调用** | `reach.py` 列出全部 `blx rN` 站点（33 处）。与 I²C1 相关的只有 3 处，且目标都是**本函数的 RAM 结构体回调**（`ldr.w r2,[r0,#0x11c]` / `[r0,#0x118]` / `[r0,#0x114]`），不是 I²C 寄存器写：`0x08008A32`、`0x08008A5E`、`0x08008B56`。无任何函数指针指向"主机发送"例程。 |
| **基址 + 运行期偏移（`str rX,[rBase,rOff]`）** | 对 I²C1 块**零命中**。`i2cmap2.py` 里 `+0x106`/`+0x107`/`+0x100`/`+0x114`/`+0x11A`/`+0x273`/`+0x2CD`/`+0x2D5` 等命中是**我的传播把 RAM 结构指针误当作仍在 r0**（那些偏移越过 I²C1 的 0x40 字节窗口，非真实寄存器访问）；按寄存器窗口过滤后全部消失。 |

**净结果**：全镜像对 I²C1 寄存器块只有 4 类偏移被访问：

| 偏移 | 寄存器 | 次数 | 站点 |
|---|---|---|---|
| `+0x00` | CR1 | **1 读 + 1 写** | `0x08008A6A` / `0x08008A6C` |
| `+0x10` | DR | 3 读 | `0x08008AA0`、`0x08008AA8`、`0x08008AC8` |
| `+0x14` | SR1 | 2 读 | `0x08008A68`、`0x08008B60` |
| `+0x18` | SR2 | 1 读 | `0x08008B62` |

**唯一 CR1 写**（`finalverify.py [C]`，逐字反汇编）：

```
08008A4C  push      {r7, lr}
08008A4E  ldrb.w    r1, [r0, #0x106]      ; RAM 结构（基址 0x20004128）
08008A52  ldr.w     r2, [r0, #0x118]      ; 回调指针
08008A56  orr       r1, r1, #0x20
08008A5A  strb.w    r1, [r0, #0x106]
08008A5E  blx       r2
08008A60  movw      r0, #0x5400
08008A64  movt      r0, #0x4000           ; r0 = 0x40005400 = I2C1
08008A68  ldr       r1, [r0, #0x14]       ; 读 I2C1_SR1
08008A6A  ldr       r1, [r0]              ; 读 I2C1_CR1  <-- r1 被覆盖
08008A6C  str       r1, [r0]              ; 写回 I2C1_CR1（原值不变）
08008A6E  pop       {r7, pc}
```

⟹ 这是一段 **"读 SR1 然后读 CR1 再写回"** 的固定序列；`0x08008A6C` 写回的是刚从 `0x08008A6A` 读出的同一个值（**位不变**），因此**不可能置位或清除 START(0x100) / STOP(0x200) / SWRST(0x2000)**。全镜像 `orr/bic` 立即数扫描（`masterhunt.py [2]`）中，对 `0x2000` 的置位只出现在 `0x08010F98`（USART CR1 = UE）和 `0x0801136A`，**没有一处落到 I²C1_CR1**。

### 第 5 条 — 主机模式的状态标志（SB / BTF / MSL / BUSY / TRA）

**结论：未找到任何"等 SB"或"判 MSL"的代码。不能推翻 H。**

命令：`python hunt.py`、`python masterhunt.py`

STM32F1 主机专属位：`SR1.SB`(bit0)、`SR1.BTF`(bit2)、`SR2.MSL`(bit0)、`SR2.BUSY`(bit1)、`SR2.TRA`(bit2)。

| 检查 | 结果 |
|---|---|
| `SR1` 读出后的消费点 | **只有两处**：`0x08008A68`（`0x08008A6A` 立刻覆盖 r1 ⟹ **哑读**，不判断任何位）与 `0x08008B60`（`ldr r1,[r0]`；`ldr r0,[r0,#4]` —— 即 **读 SR1 后紧跟读 SR2**）。 |

| `SB` 判定（`cmp/ands/tst #1` 作用在 SR1 值上） | **0**。全镜像 `ands/ands #1` 只有 3 处（`0x08006C70`、`0x0800DB0E`、`0x0800F702`），均非 SR1 消费者。 |
| `MSL` / `BUSY` / `TRA` 判定 | **0**（无任何 SR2 值的位测试；`0x08008B62` 读出的 SR2 只被 `pop {r7,pc}` 直接丢弃）。 |
| CCR / TRISE 配置 | 有（`0x0800FA6C` 写 `+0x20`(TRISE) ×3，`0x0800FAE0/0x0800FAE4` 对 `+0x1C`(CCR) 读改写）——**但从机模式也必须配 CCR/TRISE**，且这些操作**不含 START**，不构成主机证据。 |

## 3. 我找到的最强反证

### 反证 A（推翻 H 后半句）—— 存在真实可用的"命令第三方芯片"总线：USART

**地址与指令序列**

`0x08010EC4`（`USART_SendData`，标准库函数，被 `0x0800DFBC` 等调用）：

```
08010EC4  sub       sp, #8
08010EC6  str       r0, [sp, #4]          ; USARTx 基址
08010EC8  str       r1, [sp]              ; 待发数据
08010ECA  ldr       r0, [sp]
08010ECC  bfc       r0, #9, #0x17         ; 截断为 9 位（DR 宽度）
08010ED0  ldr       r1, [sp, #4]
08010ED2  str       r0, [r1, #4]          ; ★ 写 USARTx_DR —— 真实发送
08010ED4  add       sp, #8
08010ED6  bx        lr
```

调用点 `0x0800DFBA`–`0x0800DFC0`（同一函数内，紧跟 `0x0800DF84 movt r0,#0x4001` 得到的 USART1 = `0x40013800`）：

```
0800DFBA  ldr       r0, [sp, #8]          ; r0 = 0x40013800 (USART1)
0800DFBC  movw      r1, #0x305            ; 待发数据/命令
0800DFC0  bl        #0x8010fe0            ; USART_SendData
```

同一函数还把 GPIOA 的 PA9/PA10（`0x0800DF64`–`0x0800DF7C`，pin 0x28/0x38、mode 3）配为 USART1 TX/RX，并调用 `USART_Init`（写 BRR）、`USART_Cmd`（置 CR1.UE=`0x2000`）。**路径可达**（`reach.py`：`0x08010E40` reachable=True，最近可达点 `0x08010E3C`）。

⟹ 即使把 I²C1 认成纯从机，H 的"没有其它可用总线"一句也**不成立**：该固件具备 UART 发送能力，且发送例程被真实调用。

### 反证 B（对 H 前半句的**最强但最终失败**的挑战）—— I²C1 事件中断里确实写 CR1

`0x08008A4C` 里 `0x08008A6C str r1,[r0]` 是**全镜像唯一**的 `I2C1_CR1` 写。若它是 `CR1 |= START`（`0x80`）或 `CR1 |= STOP`（`0x100`），H 立刻被推翻。
**但经逐指令核对，它写回的是 `0x08008A6A ldr r1,[r0]` 刚读出的原值**（`movw/movt` 之后没有任何 `orr`/`bic` 修改 `r1`），位不变 ⟹ **不是 START，不是 STOP**。此外 `0x08008A68` 读出的 SR1 在 `0x08008A6A` 即被覆盖，是哑读。
**故这条反证不成立，H 前半句保留。**

### 反证 C（部分成立，削弱 H 的措辞严格性）

H 声明的形式是"**CR1 从未被写入 START(0x0100)/STOP(0x0200)**"。事实上 **CR1 确实被写过一次**（`0x08008A6C`），只是写的值与读回值相同、不涉及这两位。若原假设被理解为"CR1 从未被写入"，则**措辞被推翻**；若理解为"从未被写入 START/STOP"，则**成立**。
另注：`0x0800FA6C` 对 `+0x20` 的写（在 `0x0800FA20` 内部、形参 r0 = I2C1）说明 `TRISE` **有**被写入，`0x0800FAE4` 说明 `CCR` **有**被读改写 —— 这些是原假设未列出的 I²C 寄存器写。

## 4. 我未能覆盖的盲区

1. **明文段不是全部固件。** 明文段仅 `0x08005000–0x08012C9F`（文件 `0x19ABC`–`0x2765A`，约 55 KB）。容器 `touchpad_GT7868Q_fw.bin` 长 161,628 (0x2775C) 字节，**文件尾部约 `0x2765A`–`0x2775C`（约 258 字节）以及文件开头 `0x0`–`0x19ABB`（105 KB）未解密/未分析**。若主机 I²C 例程位于尾部残余或加密区，本审计看不见。**这是最大的盲区。**
2. **`0x40006C00` / `0x40007000` / `0x40001400` 身份未定。** 这些地址在 STM32F1 标准外设图上无对应（`0x40006C00` 接近 USB/CAN，`0x40007000` 常见于 STM32F2/F4 的 TIM 或 I2C2）。我核对了它们的访存形状（`0x0800F0CA`、`0x0800FF7C`、`0x0800FFD4`）**不像 I²C**（无 CCR/TRISE/CR2 的偏移模式），但**能"不像"不等于"是别的"**——若该芯片是 STM32F1 的定制/衍生型号把 I²C2 放在非标准地址，我需要厂商数据手册才能定论。
3. **形参传播的不完备。** 对"基址经多层函数传递后再写"的情形，我只做了单层（`halmap.py` 直接看形参寄存器）。若存在 `f(base) → g(base) → write(base+0x1C)` 这种**两层以上**的传递且中间做了寄存器重排，我的扫描会漏。我用 `census.py` / `finalverify.py` 的窗口扫描做了交叉覆盖，两者一致，但两者都不是形式化数据流。
4. **`0x08010E0E`–`0x08010E58` 的 USART 分派表中 `0x40004400/0x40004800/0x40004C00/0x40005000` 与实际 STM32F1 标准基址不符**，说明这是移植来的通用库；我**无法确定被真实驱动的到底是哪一路 USART**，也无法确定 `0x0800DFC0` 处的 `0x305` 是否是稳定常量（在运行期可能被改写）。
5. **未做动态验证。** 全部结论来自静态反汇编。若有运行期自修改代码、或在加密区解出的第二级 loader 重写 I²C1_CR1，静态分析无法发现。
6. **反汇编歧义。** 线性解码在 `0x08005000–0x0800517F`（向量表/字面量池）会产生垃圾指令；我已在结论中排除该区域，但不能 100% 排除全文中另有**少量**错位解码（我抽查了 `0x08010AB6` 与 `0x08008A6A` 两处歧义点，均已查清）。

## 5. 置信度

| 子结论 | 置信度 | 理由 |
|---|---|---|
| **I²C1 上永不发起主机传输（H 前半句成立）** | **中高** | 三重独立证据互相印证：① 全镜像对 I²C1 寄存器块仅 3 条访存、CR1 仅 1 次写且为"读回写回"值不变，无任何 `orr/bic #0x100/#0x200/#0x2000` 落到 CR1；② 无 CCR/TRISE 的**主机初始化链**（`0x0800FA14` 的参数 `r2=0`，且整个镜像无 START）；③ 全镜像**零**处 `SR1.SB`(bit0)/`SR2.MSL`/`SR2.TRA` 位测试，从机专属的 SR1+SR2 连读清 ADDR 反而存在。扣分项：明文段只覆盖固件的 ~1/3；结论依赖"主机代码必须至少留一个 START 或 SB 轮询"这一 STM32 硬件事实（该事实本身是确定的，但"另一段加密代码里可能有"无法排除）。 |
| **不存在 bit-bang 软件 I²C（第 1 条）** | **高** | 全镜像 GPIO 端口常量的所有出现点之后，**零**处对 `ODR/BSRR/BRR` 的写；仅有的 4 处 GPIO 位操作库函数调用点，参数分别是 TIM3 地址与 `0x1D`，**无一指向真实 GPIO 端口**。bit-bang 必然留下大量 ODR/BSRR 写，此处一条都没有。 |
| **不存在第二个 I²C 外设（第 2 条）** | **高** | 三路穷举（直接立即数 / PC 相对池 / `movw`+`movt` 配对）对 `0x40005800`、`0x40005C00`、`0x40006000`、`0x40006400`、`0x40006800` 全部 0 命中。 |
| **不存在 SPI / DMA 对外自动发送（第 3 条前半）** | **中高** | SPI1/2/3 基址物化 0 处；DMA 通道寄存器（CCR/CNDTR/CPAR/CMAR）写 0 处；无 `CPAR` 指向 I²C1。扣分项：DMA 的部分字段访问（如 `DMA_CPARx` 之外的 `+0x90`）我归因于 RAM 结构，未逐一确认。 |
| **存在真实可用的 USART 发送路径（第 3 条后半，推翻 H 后半句）** | **中高** | `USART_SendData` 的 `str r0,[r1,#4]`（DR 写）+ 真实调用点 + GPIOA PA9/PA10 AF 配置 + `USART_Init`/`USART_Cmd` + 从复位可达，链条完整。扣分项：驱动基址表与实际 STM32F1 图不符，无法确定哪一路被真正驱动，也无法确认发送的数据是稳定的"命令"常量。 |
| **其它总线不可用（第 3 条总体）** | **中** | 我证明了 SPI/DMA 不可用，但**推翻了**"无其它总线"的整体断言。所以对 H 的整体裁决只能是"部分推翻"。 |

**综合置信度：中高。**
- "唯一 I²C 主机"这半边，我用了三条互相独立的证据链（寄存器写位分析、主机位测试缺失、从机专属序列存在）都指向同一结论，且与"触控板固件必然是从机"的领域常识一致；
- 但整个结论建立在只占容器 ~34% 的明文段上（55 KB / 161 KB），且 `0x40006C00`/`0x40007000` 两个可疑外设块的身份未定——这两点使我不能给"高"。
