> ### 更正 2：★ **§1.5 的推论作废** —— 那三个"armed 消费者"不是命令处理器
> 实测：`0x08007470` / `0x08009780` / `0x0800A050` **只在 `main()` 的主循环里被调用**
>（`0x0800FE06` / `0x0800FE10` / `0x0800FE18`），它们比较的 `1 / 3 / 4`
> **不是子命令号，而是主循环每次读的"模式字节" `[0x20004094]`**。
> ⇒ **「先 arm（`A0-0x0D`）→ 再发子命令 1/3/4 → 得 `0xA2`」这个假设不成立。**
> ⇒ 正确语义：**主机命令设置"模式字节" → 主循环按模式分派三个任务；`armed` 只决定任务是否真有活干。**
> ⇒ 但 §1.4 那条"`armed` 有一条消费者清标志后立即产出 `A2`"**是对的**，只是它的身份是
> **`0xA1/0x0A00` 与 `0xA1/0x1300`** 共同调用的回复函数 `0x0800A2A8`。
>

### 1.2 里程碑的调用者（BL）

| 里程碑 | BL 调用者 | 说明 |
|---|---|---|

| `lra_cfg 0x08009750`（TIM3/LRA 配置） | **1 → `0x800AD80`** | **在主循环区**（项目已定位主循环 `0x0800AA20` 附近）⇒ **LRA 由主循环配置，不是命令配置** |

### 1.3 handler 可达性

```

lra_cfg_TIM3        <- 0 handler
pwm_cfg             <- 0 handler
```

### 1.4 ★ 关键新发现：`armed` 标志**有 6 个访问点，且消费者就在 0xA2 回复旁边**

标志地址 = 上下文基址 `0x2000495E` + 偏移 `0x1690` = **`0x20005FEE`**

| 类型 | 地址 | 所在 |
|---|---|---|
| **写 1** | `0x80086D8` | handler **`A0-0x0D`**（`clear_arm 0x86B4`）内 |
| **写 1** | `0x8004CEC` | handler **`A0-0x12 / 0x24`**（`0x8004CD4`）内 |
| **读，要求 == 1** | `0x800248C` | 前置判断 `cmp r0, #4` |
| **读，要求 == 1** | `0x800479C` | 前置判断 `cmp r0, #1` |
| **读，要求 == 1** | `0x800506E` | 前置判断 `cmp r0, #3` |
| **写 0** | `0x80052BE` | **紧接着下一条就是 `movs r0, #0xA2`** ← ★★★ |

三段读取的形态完全一致：

```asm
ldr   r0, [sp, #0x18]      ; 上下文
movw  r1, #0x1690
ldrb  r0, [r0, r1]         ; 读 armed 标志
cmp   r0, #1
bne.w ...                  ; 不是 1 就跳过
```

而 `0x80052BE`：

```asm
80052B6  movw  r1, #0x495e
80052BA  movt  r1, #0x2000       ; r1 = 上下文基址
80052BE  movw  r2, #0x1690       ; 偏移
80052C2  strb  r0, [r1, r2]      ; armed = 0   ← 消费掉
80052C6  movs  r0, #0xa2         ; ★ 紧接下一句：开始构造 0xA2 回复帧
```

### 1.5 ⇒ 对 H1 判定的影响

| 原判定 | 修正 |
|---|---|
| 「`A0-0x0D`（清/arm）只是清标志，无后续」 | ❌ **标志有 3 条消费者，其中一条消费者清标志后立即产出 `0xA2` 回复帧** |
| 「整条主机侧 Col04 扩展路径作废（因为没收到 A2）」 | ⚠️ **验收方式可能错在顺序**：真机那次发的是 **A1 子命令 `0x0B`**，而受 arm 门控的是**子命令 1 / 3 / 4** |

**⇒ 更合理的假设**：设备要求 **先 arm（`A0-0x0D`）→ 再发子命令 1 或 3 或 4**，才会走到"消费标志 → 出 0xA2 回复"那条路。
**H1 不是"不转发"，而是"没按顺序敲"。**

> **诚实标注**：`cmp r0,#N` 里的 N 我按"子命令"理解（与分发器"子命令取自 `frame+2`、形如 `0xNN00`"一致），但**未逐条核实这三个 N 的确是子命令编号**；也**未确认**哪一条才是真正产出 0xA2 的那条。这两点都可纯离线继续查。
> **红线不变**：**不要在真机上试这个顺序**（两次打挂的教训）。要验，在料板上验，或用厂商工具插桩后回放。

## 二、`0x80` 类 —— 整类空白已填

### 2.1 分发器结构（首次看清）

```asm
80091EE  ldrb.w r0, [r0, #0x104]     ; ★ 类字节取自 frame + 0x104
80091F2  strb.w r0, [sp, #0xb]
80091FA  cmp   r0, #0x80
80091FC  bne   0x8009208
8009200  ldr   r0, [sp, #0xc]
8009202  bl    #0x8001628            ; ★ 0x80 类 → 单一函数，不查子命令表
8009206  b     0x8009748
8009208  cmp   r0, #0xa0             ; 0xA0 类 → 表驱动
800920E  bne.w 0x80093d2
...
8009222  ldrh  r0, [r0, #2]          ; ★ 子命令 = frame + 2 处的 16 位
8009228  cmp.w r0, #0x100   → 0x800937e   ; 子命令 0x01
8009234  cmp.w r0, #0x500   → 0x800932a   ; 0x05
800923E  cmp.w r0, #0xb00   → 0x8009368   ; 0x0B
800924A  cmp.w r0, #0xd00   → 0x8009378   ; 0x0D
8009256  cmp.w r0, #0xe00   → 0x80092f4   ; 0x0E
...
80093D2  cmp   r0, #0xa1             ; 0xA1 类是第三段
```

**三点确认**：
1. 类字节在 **`frame + 0x104`**（说明帧被拷进 0x100 起的缓冲）
2. **子命令是 `frame+2` 的 16 位，取值形如 `0xNN00`** —— 与项目原记录一致
3. **`0x80` 类不是表驱动，而是单一函数** `0x08001628`

### 2.2 `0x80` 类处理器 `0x08001628`

```asm
8001630  movw/movt → 0x20006170 ; str 帧指针
800163C  bl   #0x8008900        ; ← 推测：位于 0x8886–0x8900 波形容器操作簇内
8001642  movs r1, #0x80
8001644  bl   #0x80001c2        ; memset/memcpy，长度 128 字节
8001648  movw/movt → 0x20004090 ; ldrb r0, [r0, #4] → 读 0x20004094
8001652  cbnz r0, 0x8001690     ; ★ 非 0 就直接返回
8001656  movw/movt → 0x20005FF4 ; str 到栈
8001660  bl   #0x8003094
8001666  ldrh r0, [r0, #0x34]   ; 读一个 16 位值
8001668  cmp.w r0, #0x3e8       ; 与 1000 比较
800166C  ble  ...               ; >1000 → 钳到 1000
800168A  bl   #0x8006de0
```

### 2.3 ★ 与 `A0-0x0D` 存在真实耦合

| 事实 | 出处 |
|---|---|
| `A0-0x0D`（`clear_arm 0x86B4`）**写 `0x20004094 = 4`** | `movw r1,#0x4090; movt r1,#0x2000; movs r0,#4; strb r0,[r1,#4]` |
| `0x80` 类**读 `0x20004094`，非 0 就跳过参数设置** | `movw r0,#0x4090; movt r0,#0x2000; ldrb r0,[r0,#4]; cbnz` |

**⇒ 命令类之间不是彼此独立的**：`0x80` 类的行为受 `A0-0x0D` 先前的写入影响。
**⇒ 也意味着：项目的"类 3 个互不相干"这个隐含假设需要修正**（至少 0x80 与 0xA0-0x0D 之间有状态耦合）。

**`0x80` 类的语义（推测）**：取波形缓冲 → 清 128 字节 → 若"已配置"则跳过 → 否则设置一个**上限 1000** 的参数。

## 三、`goodix_ts_tools.c` —— 读完了，是**负面结果 + 两条新线索**

### 3.1 它是什么

| 项 | 内容 |
|---|---|
| 机制 | **miscdevice 字符设备**（**不是** debugfs/sysfs） |
| 节点 | **`/dev/gtp_tools`** |
| 定位 | **通用 I2C 寄存器/命令/配置调试通道** |
| ioctl | **10 个**：`GTP_IRQ_ENABLE`(0) · `GTP_DEV_RESET`(1) · `GTP_SEND_COMMAND`(2) · `GTP_SEND_CONFIG`(3) · `GTP_ASYNC_READ`(4) · `GTP_SYNC_READ`(5) · `GTP_ASYNC_WRITE`(6) · `GTP_READ_CONFIG`(7) · `GTP_ESD_ENABLE`(8) · `GTP_DRV_VERSION`(9) |

### 3.2 明确没有的

| 功能 | 结论 |
|---|---|
| **自检 / self-test** | ❌ **没有** |
| **马达 / 振动 / 触觉命令** | ❌ **没有** |
| 固件升级 | ❌ 没有 |

⇒ **"汇顶官方驱动里藏着马达测试命令"这个假设，否掉了。** 省掉继续追的力气。

### 3.3 但它给出三条**新**线索

| # | 线索 | 价值 |
|---|---|---|
| **a** | **`GTP_SEND_COMMAND`（ioctl 2）= 主机下发任意命令字** | ⇒ **"主机发命令"在 Goodix 体系里是设计内的接口**，不是我们要硬闯的后门。命令字的集合才是瓶颈 |
| **b** | 结构体里有 **`rawdiffcmd`（进入 rawdata 模式）/ `normalcmd`（回 normal 模式）** 字段，**代码未使用** | ⇒ **Goodix 命令集里存在 "rawdata 模式 / normal 模式" 切换命令**。可拿去与 TF100A 的 `0xA0` 子命令表逐条对照 —— **这是目前最有希望对上号的一条** |
| **c** | `TS_REG_COORDS_BASE = 0x4100` | 一个具体的寄存器基址，可用于核对项目读到的 64 KB 窗口里的内容布局 |

### 3.4 一个值得注意的机制差异

`GTP_SYNC_READ` 的语义是"**挂进等待队列 → 等中断唤醒**"（超时 3 s）。而项目观测到 Windows 侧"**纯读不被消耗、可重复读**"。
两者是**两种不同的读模型**（事件驱动 vs 寄存镜像）。**如果 Windows 侧那个"可重复读"的寄存器确实存在，那 Linux 侧的 `GTP_ASYNC_READ` 语义更接近它。**
