# 追加二十八 —— GT7868Q「加密」的定性复核：**不是强密码，是 1 KiB 周期的弱加扰**

> 日期：2026-09-29 · 触发：用户问「有没有办法解密？或者搞到密钥？」
> 方法：读汇顶**官方开源驱动** + 对容器做统计标定（全部纯离线）
> ⚠️ 本文**修订** `追加十二` / `追加二十五` §4 的定性结论。

---

## 〇、一句话

> ## **官方驱动里根本没有"密钥"这回事 —— 加扰是芯片内部的一个开关寄存器。**
> ## **而且统计证据表明它不是强分组密码，是【周期 1024 字节】的弱加扰。**
> ## **⇒ 「解密」的门比想象的大得多；「写回」的门也很可能没锁（因为加扰由芯片做，不由你做）。**

---

## 一、★★★ 官方源码：`HW_REG_SCRAMBLE` 是个**可以关掉的开关**

`goodix/gtx8_driver_linux/goodix_gtx8_update.c`（**这个驱动明确支持 `IC_TYPE_YELLOWSTONE = 3`，就是本机芯片**）：

```c
#define HW_REG_SCRAMBLE                0x2218        // 第 33 行

/* set scramble */
reg_val[0] = 0x00;
r = goodix_reg_write(ts_dev, HW_REG_SCRAMBLE, reg_val, 1);   // 第 612-614 行
if (r < 0) { ts_err("Failed to set scramble"); return r; }

/* load ISP code and run form isp */
r = goodix_load_isp(ts_dev, &fwu_ctrl->fw_data);
```

旧一代 `goodix/gt9xx_driver_android/gt9xx_update.c` 里是同一语义、不同寄存器：
```c
/* step2:set scramble */
ret = gup_set_ic_msg(client, _rRW_MISCTL__BOOT_OPT_B0_, 0x00);   // 第 739-740 行
```

**两个关键事实：**
1. **加扰是芯片的一个硬件特性（`0x2218` / `BOOT_OPT`），官方流程在加载明文 ISP 之前把它写成 0（关掉）。**
2. **主机侧全程明文、零变换**（`goodix_format_fw_packet`：`len + flash_addr + memcpy(data) + checksum`，
   checksum 规则是"一包数据和为 0"）—— **没有任何加解密代码**。

> ### ⇒ **不存在"主机侧可以偷到的密钥"。加扰是芯片自己做的。**
> ### ⇒ 这条同时**动摇**了 `追加二十五` §5 的结论「断在无法重新加扰」：
> ### **如果加扰由芯片做，那么"你只要能让芯片写，它自己会加扰"** —— 需要重新验证。

## 二、★★★ 统计标定：它不是强分组密码（复核 `追加二十五` §4）

**判据**：按位置 `mod L` 分组后，看"各类字节直方图的众数占比"。
强密码的输出在类内应被"很多个不同平移"混合 ⇒ 众数占比 ≈ 均匀值；弱加扰 / 未加扰则保留明文分布的不均匀。

| 样本 | L=16 | L=32 | L=64 |
|---|---|---|---|
| **真数据（容器 0x1400–0x19A00）** | **0.00914** | **0.01308** | **0.02060** |
| 强流密码代理（SHA256-KS 异或同段数据） | 0.00637 | 0.00756 | 0.00918 |
| 纯随机 | 0.00645 | 0.00770 | 0.00912 |

**真数据是随机基线的 1.4× / 1.7× / 2.3×；强密码代理精确落在基线上。**
**⇒ 密文保留了明文的逐位置分布结构 ⇒ 不是 AES 之类的强分组密码。**
（`追加二十五` §4 用"16 字节块重复 13.42%"推出"分组密码 ECB"—— 但**块重复对弱加扰同样成立**，
该判据不足以区分，**结论需下调**。）

## 三、★★★★ 新发现：**1 KiB（1024 B）周期**

### 3.1 字节级自相关（`C[i]` vs `C[i+L]` 的相等率）

| L | 真数据 | 打乱对照 | 偏离 |
|---|---|---|---|
| 32 | 0.00598 | 0.00439 | +36% |
| 256 | 0.00485 | 0.00392 | +24% |
| 512 | 0.00484 | 0.00399 | +22% |
| **1024** | ## **0.07162** | 0.00379 | ## **+1787%** |
| **2048** | ## **0.05636** | 0.00381 | ## **+1378%** |
| 768 | 0.00574 | 0.00361 | +59% |

**强密码下，任何 L 的相等率都必然 ≈ 1/256 = 0.39%。实测 1024 处 7.16%（18 倍）**
⇒ **变换是周期为 1024（或其因子）的周期性加扰。**

### 3.2 重复 16 字节块的位置间隔

出现 14 次的那些高频块，位置间隔全部是 **1024 的倍数**：
```
8192, 8192, 3072, 1024, 1024, 1024, 1024, 1024, 8192, 16384, 12288, 4096, 8192
```
⇒ 明文的结构本身就是**按 1 KiB 页对齐**的。

### 3.3 每个偏移（0..1023）的众数占比

```
min 7.2% · 中位 14.4% · 90 分位 20.4% · max 28.9%      （随机基线 0.39%，每个偏移仅 ~98 个样本）
```
**强密码（哪怕弱-XOR）都不可能在 98 个样本里出现 14% 的众数占比** —— 这是"1 KiB 块之间高度相似"的铁证。

> ### ⇒ 结论：**变换 = 以 1 KiB 为周期的弱加扰**，与官方命名的 `scramble` 完全吻合。
> ### ⇒ **攻击面只有 1024 字节**，而且**可逆**。

## 四、这对项目意味着什么（三条，按重要性）

**① 「无法重新加扰」这条结论很可能不成立（→ 可回刷）。**
加扰由芯片做、主机侧零变换 ⇒ **只要写入路径通，芯片会自己加扰**。
`追加二十五` §5 推出"断在无法重新加扰"的前提是"加扰算法在厂商内部工具里"，
但官方驱动源码显示：**主机侧根本不参与加扰**。**⇒ 需要重新验证。**

**② 解密的门变大了：弱加扰 + 1 KiB 周期 ⇒ 只差一个「已知明文锚点」。**
有了锚点即可恢复这 1024 字节的变换；而变换是**固定的**（见 ③），一旦恢复就对全镜像通用。

**③ 密钥是固定的、不是每芯片独有的。**
`追加二十三` §7 记录：本机与 X9-15 两份 GT7868Q 镜像**有 32,877 字节完全相同**。
若密钥是每芯片独有，相同明文的密文也会不同 ⇒ **⇒ 密钥是全局固定密钥。**
（★ 注意：`fw-touchpad` 下的 `gt7868q.bin` 与 `touchpad_GT7868Q_fw.bin` md5 相同，
是**同一份副本**；X9-15 那份容器需另找。）

## 六、修订声明

| 既有说法 | 出处 | 本次修订 |
|---|---|---|
| 「加密区 = 分组密码 + ECB 模式」 | `追加二十五` §4 | ⚠️ **证据不足，下调为"周期 1024 的弱加扰"**（块重复不能区分两者；类内分布与强密码标定强烈不符） |
| 「断在无法重新加扰 ⇒ 解密也不能震」 | `追加二十五` §5 | ⚠️ **前提存疑**：主机侧本来就零变换，加扰是芯片行为（`HW_REG_SCRAMBLE = 0x2218`） |
| 「密钥在芯片 OTP/eFuse」 | 总表 §二 第 3 条 | ⚠️ **需修正**：至少存在一个**可被软件访问的加扰开关寄存器**；"密钥"可能只是这个开关的状态 |
