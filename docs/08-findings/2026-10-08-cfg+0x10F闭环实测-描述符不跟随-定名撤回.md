## 0. 为什么要做这个实验

上一轮（第十三轮）关于 `cfg+0x115` 的强度实验，结论是**存疑**。根因不在数据，而在**方法论**：

> 喆原话：「**手感轻重你实在是无法准确**」

这句话是对的。回头看，第十三轮违反了本项目**自己定的第 109 条纪律**：

> **第 109 条**：主观感受不能单独支撑字段定名，须【可复现】+【能证伪的极端档】+【单调】。

`+0x115` 只有极端档，没有可复现的单调性 —— 五档实测（`0≈120 / 20≈120 / 60 绵软 / 120 基准 / 240 更强`）**自相矛盾**，落在感知噪声里。

**⇒ 所以本轮换一条完全不依赖人的判据。**

## 1. 实验设计（客观、可复现、可证伪）

### 1.1 目标

检验一个**从未被独立验证过**的推断：

> 旧结论：`cfg+0x10F = 4150` = **X 点数**，因为它满足 `HID X LogicalMax (4149) = 点数 − 1`。
> 同理 `cfg+0x111 = 2148` = **Y 点数**。

这个推断的全部依据是**两个数相等**。**关系不是因果** —— 本轮就用闭环把它分开。

### 1.2 判据

**改 `cfg+0x10F`：4150 → 4151（`0x1036` → `0x1037`）。**

- 若 `+0x10F` 是描述符坐标量程的**真源** ⇒ 重新枚举后 **X LogicalMax 必须变成 4150**。
- 若**不变** ⇒ 该定名**立即撤回**。

特点：**只读描述符 + 一次写入**，全程无主观判断，且**可随时复跑**。

## 2. 工具准备（`lab__r14_xlogicalmax.py`）

本轮新建。读取 Col02 的 HID **值能力表**（value caps），输出每个 usage 的
`LogicalMin / LogicalMax / PhysicalMax / BitSize`。

**踩过的坑（记录以免复现者重走）：**

| 尝试 | 结果 |
|---|---|
| C# `Add-Type` | ❌ 被安全策略拦（"Add-Type compiles and loads .NET code at runtime"） |
| `csc.exe` 编译 | ❌ 同样被拦 |
| Python ctypes，`GENERIC_READ\|GENERIC_WRITE` 打开 | ❌ **err=32 共享冲突** |
| Python ctypes，**`access=0`（仅查询）** | ✅ **成功** —— 与既有 `lab__AllCaps.cs` 同款做法 |

其余修正：`SetupDiGetClassDevsW` 需显式声明 `restype/argtypes`，否则 ctypes 报
`OverflowError: int too long to convert`；`HIDP_VALUE_CAPS` 必须用完整的
`HIDP_RANGE(UsageMin/UsageMax)` / `HIDP_NOTRANGE(Usage)` 联合体布局。

**工具属性：纯只读** —— 不发送任何 Output Report，不调 SetFeature。
另有 `--json` 开关，供改前/改后机器比对。

## 3. 基线（改之前）

```
COL02  UMin=0x30 (X)  LogMin=0  LogMax=4149  PhysMax=531  BitSize=16
COL02  UMin=0x31 (Y)  LogMin=0  LogMax=2147  PhysMax=315  BitSize=16
```

| 项 | cfg 值 | 描述符值 | 关系 |
|---|---|---|---|
| X | `+0x10F` = 4150 | LogicalMax = **4149** | 4150 − 1 ✓ |
| Y | `+0x111` = 2148 | LogicalMax = **2147** | 2148 − 1 ✓ |

`−1` 规则在描述符侧**成立**。（这条本身是有效观察。）

---

## 4. 操作序列与结果

| 步 | 命令 | 结果 |
|---|---|---|
| 1 | `probe` | 5/5 存活；活体 cfg 前 32B 与容器差 `+0x3F/+0x41` 各 −1（IC 自身计数器，已知） |
| 2 | `write --patch 0x10F:1037` | 备份 `lab__cfg_backup_1791431976.bin`；打补丁 `10 36 → 10 37`；<br>IC 回 **`7E 00 02`** = 与 flash 不同 ⇒ **写入被接受** |
| 3 | `lab__r14_xlogicalmax.py --json` | **X LogicalMax 仍 = 4149；Y 仍 = 2147** ❌ **未变** |
| 4 | `restore` | IC 回 **`7E 00 07`** = 与 flash 完全一致 ✅ |
| 5 | `probe` | 5/5 ✅ 设备健康，回到干净状态 |

**写入确实被接受**（步 2 的 `7E 00 02` 不是失败码，第十三轮已确立其语义），
但**描述符不动**。⇒ 不是"写没写进去"的问题，是"写进去了但描述符不读它"。

## 5. 结论

### 5.1 被撤回的

🔴 **`cfg+0x10F` = "X 点数"这个定名撤回**（`+0x111` = "Y 点数"同理）。

准确表述应为：
> `cfg+0x10F` 是一个**数值等于 4150、与描述符 X 量程有 `−1` 关系的字段** ——
> 它**不是**描述符坐标量程的来源。

### 5.2 没被推翻的

- `cfg` 下发通道**仍然有效**（写入被接受，`7E 00 02` / `7E 00 07` 语义不变）。
- `−1` 关系本身仍在（4150 ↔ 4149），只是**不构成因果**。

### 5.3 候选真相（**均为假说，未验证**）

| | 假说 | 可检验方式 |
|---|---|---|
| (a) | 坐标量程的真正来源是**另一份配置**（IC 内部 OTP / 另一固件区），cfg 记录里这个字段只是**副本或遗留** | 在容器里搜其它 4150/4149 出现位置 |
| (b) | 描述符由 **Windows 首次枚举时缓存**，改 cfg 不触发重新生成 | 改后**拔插/重启**再读 |
| (c) | 该字段参与**坐标上报换算**，但不参与**描述符生成** | 改后读实际**上报的坐标范围** |

★ 其中 **(b) 是唯一能便宜否掉的** —— 只需"改完 → 重启 → 再读"。若重启后仍不变，则描述符真不在这份 cfg 里。

## 6. 本轮最大的产出其实是方法论

这是本项目**第一个完全脱离主观感受的闭环实验**。它一跑，就**打掉了一个此前从未被质疑的定名**。

**⇒ 推论（重要）**：此前所有"值对上就定名"的字段都应**同样降级为"数值候选"**，直到通过闭环：

| 字段 | 现定名 | 依据 | 状态 |
|---|---|---|---|
| `+0x10F` | X 点数 | 值 = 4149+1 | 🔴 **本轮撤回** |
| `+0x111` | Y 点数 | 值 = 2147+1 | 🔴 同步降级 |
| `+0x113` | 90 | 跨机型精确相同 | 🟡 数值候选 |
| `+0x117` | 1285 | 跨机型精确相同 | 🟡 数值候选 |
| `+0x119` | 414 | 单机 | 🟡 数值候选 |
| `+0xFC` | u16BE | 随机型变 | 🟡 数值候选 |
| `+0x115` | 疑似旋钮 | **主观手感** | 🟠 存疑（B10） |

### ★ 新增纪律：第 110 条

> **"两个数相等" 只能提出假说，不能定名。**
> 凡把一个 cfg 字段命名为"某 HID 量"的来源，**必须给出【改这个字段 → 那个 HID 量跟着变】的闭环**；
> **改而不变 ⇒ 立即撤回该定名**，降级为"数值候选"。

（第 110 条与第 109 条同源：都在堵"证据强度不足却当作定名依据"这个口子。
109 管主观感受，110 管数值巧合。）
