## 一、已确证的硬件与 HID 事实（全部本机实测）

### 1.1 四个 HID 集合

| 集合 | 顶层 usage | 报文长度 | 内容 | Windows 驱动 |
|---|---|---|---|---|
| Col01 | `0x01/0x02` 鼠标 | — | 鼠标兼容口 | `mouhid` |
| **Col02** | `0x0D/0x05` 精确式触控板 | **in=40, out=0, feat=737** | 见下 | HID 类 + 输入栈 |
| Col03 | `0x0D/0x0E` 配置集合 | in=0, out=0, feat=3 | 仅 1 条 feature：`rid=3`（`0x0D/0x52` Input Mode，0–10） | `MTConfig` |
| **Col04** | `0xFF00/0x01` 厂商自定义 | **in=65, out=65, feat=0** | **report ID = 14** | **无任何驱动绑定** |

**Col02 输入报文**（`rid=4`，40 字节）：5 个触点 link collection；每触点 `ContactID(0x0D/0x51,4bit)`、`X(0x01/0x30,0-4149)`、`Y(0x01/0x31,0-2147)`、**`压力(0x0D/0x30,0-2000)`**；另有 `接触数(0x0D/0x54)`、`扫描时间(0x0D/0x56)`。

**Col02 feature 报文**：`rid=2`（`0x0D/0x55` 触点上限 + `0x0D/0x59`）、**`rid=9`（`0x0E/0x23` 触觉强度，0–100，注册表 `FeedbackIntensity=100` 与之对应）**、以及**厂商报文 `rid=13(4B) / rid=11(66B) / rid=6(256B) / rid=12(736B)`（usage page `0xFF00`）**。

### 1.2 触觉能力（关键结论）

- ✅ **设备自主触觉**：力度越过点击阈值 → 固件驱动马达（按下/抬起各一次）。系统里可调"强度"（rid=9）。
- ❌ **无主机发起触觉**：没有 `Manual Trigger(0x0E/0x21)` 输出报文、没有 `Auto Trigger/Waveform List/Duration List` feature 报文 → **任何应用都无法请求它震动**（三重证据：本机描述符实测 + 微软规范 + Google ChromeOS 团队提交 Linux 上游的实现文档）。

### 1.3 写入通道的存在性（重要）

- `CreateFile` 打开 **Col02 = ERROR_SHARING_VIOLATION(32)**（被系统独占，用户态无法读写其 feature 报文）。
- `CreateFile` 打开 **Col04 = 可读写**；Windows 侧发送必须用 **`HidD_SetOutputReport(65)`**（`WriteFile` → err 87；`HidD_SetFeature` → err 1，因 `featLen=0`）；**报文必须自带 report ID**（去掉即 err 87）。
- **经 Col03 句柄调用 `HidD_SetFeature` 可以投递任意 report ID 的 feature 报文，且确实到达设备**（见 §三 事故记录）。

## 三、事故记录（写入确实生效）

| 操作 | 观察到的后果 | 恢复 |
|---|---|---|
| 向 **Col03 / `rid=3` 写 Input Mode = 100** | 按微软规范"非 0/3 的值设备应解释为 0 → 切**鼠标模式**"→ 出现"**光标可用、双指滚动失效**" | Fn+F8（Windows 重新下发 Input Mode=3） |
| 向 **Col02 厂商报文 `rid=11`(66B) / `rid=13`(5B) 盲写** | 出现"**滑动失效、但点按仍有震动**"（说明固件的力度检测+马达路径正常，坏的是坐标上报环节） | Fn+F8 |

**两条结论：**
1. **写入真实生效** → 这条通道是活的，能控制触控板。
2. **盲写会改坏状态**（虽然 F8 可回滚）→ **后续只发"读"命令；固件写入命令（`{00,10}`/`{00,11}`/`{0E,12}`）绝对禁区。**

## 四、Goodix 官方协议（从 fwupd 开源代码取得）

```c
#define PACKAGE_LEN    65        // 与 Col04 完全一致
#define REPORT_ID      0x0E      // = 14，与 Col04 完全一致
#define I2C_DIRECT_RW  0x20
#define I2C_READ_FLAG  1
#define I2C_WRITE_FLAG 0
```

**传输层**：Linux 用 `HIDIOCSFEATURE/HIDIOCGFEATURE`（feature 报文）；发送时 `buf[0]=0x0E`。

**GTX8 家族命令（16 位地址）**
| 命令 | 报文 |
|---|---|
| 读内存 | `[0E,20,00,00,05,01, addr16(BE), size16(BE)]` |
| 写内存 | `[0E,20,00,(块号),size+5,00, addr16, size16, data...]`（≤55B/包） |
| 复位 IC | `{0E,13,00,00,01,01}` |
| 切 PTP 模式 | `{03,03,00,00,01,01}` |
| 固件信息地址 | `0x452C`(72B，含 patch PID/校验和)、`0x60DC`(cfg 版本) |
| **刷机（禁区）** | `{00,10,...}` 切 patch、`{00,11,...}` 开始更新、`{0E,12,...}` 写 flash；BL 状态 `0x5095`、flash 结果 `0x5096`、缓冲 `0xC000` |

**BRLB 家族（32 位地址）**：读包为 `[0E,20,00,00,07,01, addr32(BE), size16(BE)]`，版本信息在 `0x1001E`/`0x10076`，DRAM `0x14000`。

**PID→家族映射**：GTX8 = `0x01E0~0x01E7`；BRLB = `0x012B~0x0132` 等 → **本机 `0x01E9` 两者都不在**。

## 六、核心矛盾与线索

**矛盾**：Col04 的常量（report ID 14、65 字节）与 Goodix 官方协议**完全吻合**，但发命令**无响应**；与此同时**写入确实生效**（Input Mode 被改）。

| # | 候选解释 | 对应线索 / 下一步 |
|---|---|---|
| **L1** | **响应不是走 Col04 输入，而是走 feature 报文**（Goodix 用 GET_FEATURE 收响应）。Col04 无 feature 报文 → Windows 侧读不到 | 需要能对 Col02/Col04 发 **GET_FEATURE** 的通道：用户态被 hidclass 挡住 → **内核 HID 过滤驱动** |
| **L2** | **帧格式不对**（芯片属第三家族） | 取 **Dell 的 Windows 官方工具**，读其帧格式（零风险） |
| **L3** | 命令需先解锁/切模式 | 可能性较低（fwupd 流程里读版本在 `disable_report` 之前） |
| **L4** | **Col04 的 OUT 报文根本没到达固件**；真正生效的只有 feature 路径 | 只用 feature 通道做实验，并观察副作用 |
| **L5** | **Col02 的厂商 feature 报文才是本 SKU 的命令通道**（注意 `rid=11` = **66 字节 ≈ 65+1**，与协议包几乎同尺寸） | 写入可经 Col03 句柄投递（已验证生效）；**读取被堵** → 仍需驱动或响应改走输入报文 |

# 九、本轮重大更新：**厂商通道打通（并修正历史错误）**

## 9.1 必须修正的历史错误：EnumPaths 子串匹配 bug
`ColProbe.EnumPaths('Col02')` 是**子串匹配**，而系统里另有一个 Intel HID 设备 `intc816&col02`
（caps 为 `up=0x0001 u=0x000D in=2 feat=2`）——**此前所有"Col02 feature 写失败 err=87/1"的结论，
全是打在这块 Intel 设备上的假象** ✗。
→ 正确做法：`FindPath('&col02')` 取 **GXTP5100** 的完整路径后再 `OpenPath()`。
真实的 Goodix Col02 caps：`up=0x000D u=0x0005 in=40 out=0 feat=737 featVals=7` ✓

## 9.2 已打通的通道（可用）
| 通道 | 能力 | 证据 |
|---|---|---|
| **Col02 只写句柄的 feature 写** | `rid=9`(振动强度,2B)、`rid=2`、`rid=13`、**`rid=11`(67B 厂商包)** 全部 `SetFeature → True err=0` | **用户体感验证**：写 50 → 震动变轻；写 100 → 震动消失；写 10 → 恢复如初。**写入确实改变硬件行为** ✓✓✓ |
| **Col04 OUT(rid=14) → IN(rid=14)** | 传感器 **16 位地址空间读**：真数据、稳定、随地址变化 | 读 0x1000 → 配置表；0x4100 → 0x00；0x452C → 高熵块 |
| **Col03 (mtconfig) feature 写** | `rid=3`(Input Mode, 3B) 可写、值域 0–10 | 写 4..10 均 True，**无可观测效果**；已恢复为 3 |

**帧格式（16 位 / GTX8 家族，实测有效）**
- 读：`0E 20 00 00 05 01 <addr16BE> <size16BE>`
- 写：`0E 20 00 00 <len+7> 00 <addr16BE> <len16BE> <data…>`
- 响应（仅 Col04 通道可读）：`0E 20 <cont> <seq> <len> <data…>`

## 9.3 已排除的可能（省得再走一遍）
- **Col02 读**：始终 `err=32`（写可以、读不行）。**禁用 Col03(MTConfig) 后依旧 err=32** ⇒ 持有者**不是** MTConfig。
- Col04 输入报表 = **上一条命令的镜像 + 静态块**（4096B 缓冲下两条不同命令只差地址字节）⇒ 不是响应通道。
- Col03/Col02 的 `GET_FEATURE`（小缓冲一律 err=122，4096B 才成功）返回的是**同一块共享缓冲**（命令回声）⇒ 读不到各自报表。
- **那 64KB 空间属于传感器芯片**：不含 MCU 侧 TIM 基址/LRA 结构（无 119/1999/TIM3 base）⇒ 摸不到马达寄存器。
- 传感器内存**写不生效**（0xC100 写 `A5 5A …` 回读全 0）⇒ 与 Dell 工具流程一致：**必须先进 raw 模式**（`0x60CC ← {33 00 CD}`）才可写。
- HID 层**只暴露"强度"**（`0x0E/0x23`），无 Manual Trigger / Waveform ⇒ **无标准触发接口**。
- Input Mode 4–10 **无任何可观测效果**。

## 9.4 LRA 驱动链（56KB 明文段内，实测反汇编）

## 9.5 结论与剩余路径
- "滑动震动"仍缺**唯一生死点**：主机可用的**震动触发命令**（固件未公开）。
- 剩余可选：① 联网找 Goodix 触觉/工厂测试工具或协议（最快，可能一步到位）；② 进 raw 模式后探测传感器寄存器（收益不明、状态会暂时异常）；③ 内核 HID 过滤驱动（**需用户二次确认**，且要测试签名）；④ 手势 MVP 兜底。
- **恢复手段（已验证）**：`pnputil /restart-device "ACPI\GXTP5100\1"` ＞ Fn+F8 ＞ 重启。
  ⚠️ **Col03 被禁用时 F8 会失效并把触控板切进"降级模式"**（能点按震动、滑动手势全废）。
- **新纪律**：命令必须稀疏；每条命令的响应必须排空 —— 否则传感器忙于服务主机命令，触控上报会"抽帧"。

# 十、联网调查（一手来源）结论

## 10.1 微软官方《Input Device Haptics Implementation Guide》
> 主机触发震动（Host-Initiated Haptic Feedback）**必须**具备：
> - **OUTPUT 报表**：`Manual Trigger (0x0E/0x21)` + `Intensity (0x0E/0x23)`
> - **GET_FEATURE 报表**：`Waveform List (0x0E/0x10)` + `Duration List (0x0E/0x11)`
> - 且必须是 PTP 顶层集合下 SimpleHapticsController 子集合
>
> **设备自触发**只需 `Haptic Intensity (0x0E/0x23)` 一个 SET_FEATURE 报表；
> 规范原文："**zero indicating that no feedback should be triggered**"（0 = 不震）

**对照实测**：Col02 `out=0`（**无任何输出报表**）、page 0x0E 下**只有 Intensity (rid=9)**、无 Waveform/Duration ✗
⇒ **本机固件在文档协议层面不存在"主机触发震动"接口**（Windows 自己也无法命令它震动）。

**强度语义实测映射**（与规范的"越大越强"相反，本机固件按反比/阈值映射）：
| 写入 rid=9 | 用户体感 |
|---|---|
| 10 | ≈ 默认（强） |
| 50 | 明显变轻 |
| 100 | 震动消失 |
⇒ 可用：**1–10 = 强，100 = 关**。

## 10.2 GT7868Q 的公开资料
- 微软/内核邮件确认：**GT7868Q 是 haptic touchpad**（Lenovo ThinkBook 13x Gen 4、16+ 2024 IMH 等机型）。
- 官方内核补丁 `c8000deb68365b461b324d68c7ea89d730f0bb85`（HID: multitouch: Add support for GT7868Q）+ 社区驱动
  `github.com/ty2/goodix-gt7868q-linux-driver`：**只修描述符**（第 605/607 字节重复描述），**不含触觉协议** ✗。
- 内核 HID 树存在 `for-6.18/haptic` 分支（触觉子系统开发中），不改变本设备的接口缺失。

## 10.3 Col02 读封锁的归因（新增证据）
用自写工具 `poc/WhoHolds.cs`（NtQuerySystemInformation 全系统句柄枚举 + File 类型索引筛选 + 句柄名解析）
扫描：**在所有用户态可访问进程中都找不到持有 GXTP5100 设备句柄的进程**（可访问的 File 句柄仅 89 个，命中 0）。
⇒ 持有者是**系统/受保护进程或内核组件**，用户态无法定位或干预
⇒ **要读厂商命令的响应，只能靠内核过滤驱动**。

## 10.4 最终剩余路径
1. **手势 MVP**（可立即交付；震动用原生点按反馈 + 已可控制的强度）；
2. **内核 HID 过滤驱动**（唯一能拿响应 → 系统性探测厂商命令空间的手段；需测试签名，有蓝屏/失效风险，须二次确认）；

# 十一、阈值测定与"写封锁"（本轮最终结论）

## 11.1 罗塞塔石碑：明文配置 ↔ 传感器内存
- BIN 的记录 0–4（明文配置）**逐字节映射**进传感器的 16 位地址空间（例：记录 +0x2A4 ↔ 传感器 0x5B8E，映射常数随每次重新初始化而**变化**）。
- 因此**配置的每个字段都能被逆向**，不再需要盲扫 ✓。

## 11.2 点击阈值：**实测 = 压力 141（HID）/ 70（原始）**，松开 = 97/48
- 方法：`press-capture.ps1` 采集 2241 条报文 → 报文布局 = `[ID][按键/触点ID][X][Y][压力]`（压力@offset6，0–2000）
- 按键位 = **报文最后一字节 bit0（byte39.bit0）**；其上升沿压力：140/141/142/141/141/149/146 ✓ 高度一致
- 与配置字段 `+0x2AC = 70 / +0x2AA = 48` 完全吻合（Linux 社区确认原始域上限 1000、HID 上报 2000，即 ×2）✓✓

## 11.3 写封锁（本轮卡点）
| 尝试 | 结果 |
|---|---|
| Col04 OUT 写 0xC100 / 0x5B96（16 位帧） | 返回 True，**回读无变化** ✗ |
| Col02 feature rid=11 写（16 位帧 + 32 位 Dell 帧） | 返回 True，**回读无变化** ✗ |
| 进 raw 模式 `0x60CC ← {33 00 CD}` | 无效果（0x4100 仍为 0x00）✗ |
| **用户实测**（阈值 70→25 后手感是否变敏感） | **完全没变化** ✗ → 写入确实被丢弃 |
| 对照：Col02 **rid=9（HID 声明的振动强度）** | **写生效**（用户体感验证 ✓✓） |

**推论**：设备只接受 **HID 已声明报表**的写入；厂商命令通道对我们是**只读**的。
Dell 工具能写，说明它掌握了我们尚缺的东西——很可能是：**只接受写 FLASH_BUFFER(0xC000)** + 用 `0E 12`（load flash）提交，或存在写使能/校验握手。

## 11.4 剩余路径（按性价比）
1. **离线：把 Dell 工具 11 个 `hid_write` 调用点全部解码**，找出"写缓冲区 + 提交"的完整时序（零风险）；
2. **内核 HID 过滤驱动**：读厂商命令的**响应**（含错误码），从而知道写为何被拒 —— 前置条件不足：**WDK 未安装、Secure Boot 处于开启**（需先关 Secure Boot 才能测试签名）；
3. **手势 MVP**（立即交付，震动用原生点按反馈）。

# 十三、事故记录：Col04 高频轮询把 IC 打挂（2026-09-13）

## 13.1 事件经过
- 后台任务 `sniff-col04.ps1 -Seconds 300 -PollMs 30` 在**无人留意的情况下持续跑满 5 分钟**，
  以约 **33 Hz** 对 Col04 反复调用 `HidD_GetInputReport`（只读，但极高频）。
- 同一时段主会话又对**同一集合**发厂商读命令 ⇒ 响应被嗅探器抢走，主机侧表现为连续 `err=122`。
- 5 分钟后嗅探器结束，但**触控板已完全无响应**（光标不动、点按无震动、Fn+F8 无效）。

## 13.2 故障态现场证据
| 检查项 | 结果 | 含义 |
|---|---|---|
| `pnputil /enum-devices` | ACPI\GXTP5100\1 与 Col01–04 全部 Started | 故障初期设备树仍完好，**不是驱动/枚举问题** |
| `HKCU\...\PrecisionTouchPad\Status\Enabled` | 1 | OS 认为触控板是开的（排除"F8 关掉"） |
| 连发只读命令 ×3（65B 与 4096B 缓冲都试） | 发送 True/err0，回读**全部 err=122** | IC 应答通道已乱 |
| 软复位 `0E 13 00 00 01 01` | 发送成功、**无任何应答** | IC 连复位命令都已不处理 |
| 切 PTP 模式 `03 03 00 00 01 01` | 同上 | — |
| 管理员 `disable-device` + `enable-device` | 设备转为 **Problem 10 / 0xC000009E (STATUS_IO_TIMEOUT)** | 重新初始化时 IC 不应答 I2C |
| 管理员 `restart-device`（触控板 + 父级 `PCI\VEN_8086&DEV_7E78`） | 依旧 0xC000009E | 软件层已无手段恢复 |
| **WHEA 硬件错误日志（近 3 小时）** | **完全为空** | ★ 无过流/过压/总线硬件错误 ⇒ 可排除"芯片烧毁" |
| I2C 控制器 `PCI\VEN_8086&DEV_7E78` 自身 | Status: **Started** | 主机侧总线硬件完好，只是从设备不应答 |
| 同款嗅探 `-Seconds 22`（早前验证跑） | 触控板**安然无恙** | 22 秒可承受、300 秒才挂 ⇒ **累积型固件崩溃**，非瞬间电气损坏 |

## 13.3 机制判断
- hidi2c 的 `err=122` = GET_REPORT 拿到的**长度字段非法**（**不是**主机缓冲不够：4096B 缓冲同样报 122）
  ⇒ IC 的 HID 寄存器接口状态机被高频 GET_REPORT 冲垮。
- IC 挂死后三件事同时发生：**HID 输入报表停发**（触控全废）＋**厂商应答停摆**（err=122）＋
  **连 I2C 描述符读都不应答**（0xC000009E）。
- **Fn+F8 必然无效**：它是靠给 IC 发"输入模式"报表实现的，IC 不应答时无从生效。

## 13.4 恢复路径（唯一 = 整机断电）
固件与硬件**从未被写入**（刷机命令 `00 10 / 00 11 / 0E 12` 一次都没发过），IC 仍会从 flash 正常启动，
因此**重启（或休眠→再开机）后必恢复**：
1. 重启电脑（休眠→再开机的断电效果等同）；
2. 开机后核对 `pnputil /enum-devices /instanceid "ACPI\GXTP5100\1"` 是否回到 `Started`；
3. 若仍未 Started，再重启一次（PnP 会自动重试启动）。

## 13.5 新增硬规则（永久生效，优先级高于"推进进度"）
1. **禁止对 Col04 做任何后台轮询**：`GetInputReport` 循环一律不得常驻；嗅探必须**前台、限时（≤30 秒）、低频（≥200ms）**。
2. 嗅探进行期间**不得同时发厂商命令**（互相抢响应，且可能共同把 IC 打挂）。
3. 后台任务启动时登记 job id，用完**立即** `job_kill`；出现任何异常，第一步是**杀掉所有后台任务**。
4. 判断"IC 是否还活着"只用**单次**只读命令；需要连发就已经是故障征兆。
5. 触控板是本机唯一的指点设备：**凡是可能让它停摆的操作，先确认有一条不依赖它的退路**。

## 13.6 顺带排除的一条线索
事故前的最后一次读取还否掉了一个"识别芯片"的捷径：
- `0x452C` 读到的 72 字节**不是** fwupd HID 协议里的固件信息块（`sum8 = 0xD9 ≠ 0`，所谓「PID」位置是 `2E 77 42 77 3C 77`），
  而是 `77 xx / 76 xx` 形式的 **16 位小端实时传感器原始值**；
- `0x60DC` 读到 `BB 39 0A E8`，也不是配置版本号。
⇒ **fwupd 那套 HID 协议的内存映射（fw info @0x452C、cfg @0x60DC）不适用于本芯片**，
   这两条"官方地址"不能再当作获知型号/版本的途径。芯片识别仍只能靠丝印与丝印 QR。

4. 松手，**等 1 分钟**

| 全系统 Problem 设备 | **0 个**（连事故前 `ACPI\MSFT0001` 的资源冲突也消失）✓ |

## 14.3 已证伪 / 无效的手段（别再浪费一次重启）
| 手段 | 实测结果 |
|---|---|
| 软复位命令 `0E 13` / 切 PTP 模式 `03 03` | IC 已不应答，发得进去但无回音 ✗ |

| Novo 按钮孔（底视图第 3 项） | 只进 Novo 菜单（固件设置 / 引导菜单 / 高级启动），**不断电、不清数据** ✗ |

## 14.4 机制结论（本次事故证明）
1. **热重启 ≠ 断电**：S0→重启不会放掉触控板供电轨 ⇒ IC 的挂死状态**跨重启存活**。
2. **BIOS 在 POST 探测触控板**：探测失败就把设备从 ACPI 命名空间隐藏（`_STA=0`）⇒ 表现为 `Disconnected`，
   连它的 ESRT 固件资源也一起消失。**"设备消失"≠"驱动掉了"**（驱动名一直挂在设备上）。
3. **IC 挂死是状态、不是损坏**：WHEA 硬件错误日志全程为空；EC 复位后完全恢复，配置与阈值无任何残留变化。
4. **Novo 孔不是复位孔**：官方手册底视图只有 `1 进风口 / 2 扬声器 / 3 Novo 按钮孔`（本机无紧急复位孔）。

## 14.5 恢复阶梯（最终版，严格按序）
1. **先杀掉所有后台任务**（第一优先，异常时第一动作）
2. **单次**只读命令确认 IC 是否应答
3. 设备仍在（`Started`/`Problem`）→ `Fn+F8`（**仅 IC 尚能应答时有效**）
4. **已挂死 / 已消失 → 关机 → 拔充电器 → 长按电源键 20～30 秒 → 等 1 分钟 → 开机** ← **唯一有效**
5. **不要做**：`disable/enable`、`restart-device`、`scan-devices`、反复热重启（只会让状态更差或白费时间）

# 十五、厂商命令空间：**不可枚举**（2026-09-13 实测，扫描被迫中止）

## 15.1 扫描协议（按安全约束执行）
- 前台单线程，逐条 `0E <op> 00 00 01 01`，间隔 400ms，每条都排空响应
- 跳过 `0x10/0x11/0x12`（刷机三连）+ `0x13`（软复位，会重启 IC）+ `0x20`（内存读写）
- **每 16 个 opcode 做一次只读活性体检**（`0E 20` 读 0x0000），失败立即中止
- 实际发出约 35 条命令后中止

## 15.2 结果
| opcode | 响应 | 判读 |
|---|---|---|
| `0x00`–`0x0D` | 全部返回**同一个空 ACK** `00 00 01 01 00…` | 通用 ACK、无信息量；**未引发任何震动** |
| **`0x0E`** | **自这一条起应答通道死亡**，其后全部 `err=122` | ★ 元凶 |
| `0x0F`–`0x2F` | 全部 `err=122` | — |
| `0x30` 前的活性体检 | 失败 → 中止 | 保护协议生效 ✓ |

## 15.3 结论
1. **厂商命令空间不可安全枚举**：`0x0E`/`0x0F`/`0x99` 都会打断应答通道 ⇒ "扫完 256 个 opcode"在物理上做不到。
2. **没有找到任何"测试马达"命令**：能应答的 13 个 opcode 全是同一个空 ACK。
3. 已知可用的厂商命令**只有 `0x20`（内存读写）**；除此之外这个命令空间对我们没有价值。
4. **对路线 B（内核 HID 过滤驱动）是决定性的负面证据**：B 的价值前提是"探测命令空间以验证固件是否藏了震动触发"，
   而命令空间既不能安全探测、也没有震动触发 ⇒ **B 成功率趋近 0，不值得再付"装 WDK + 关 Secure Boot"的代价**。
5. 副作用：本次留下 `err=122` 卡态（设备树仍 `Started`，但厂商应答通道死）。
   **且该卡态会继续恶化**：扫描后触控板**彻底失效**（与第十三章事故同一路径）⇒
   **恢复 = EC 复位**（关机 → 拔充电器 → 长按电源键 20–30 秒 → 等 1 分钟 → 开机），已验证 ✓
6. **代价**：这是同一天内第二次把触控板打挂，两次根因都是"用户态厂商通道操作"（第一次=后台高频 GET_REPORT，第二次=批量试 opcode）。
   ⇒ 结论：**用户态碰厂商通道 = 迟早打挂触控板**，不是"小心一点就行"的问题。

## 15.4 新增硬规则（累加到 13.5 之后）
6. **禁止枚举/批量试探厂商命令空间**（禁止批量试 opcode）。厂商通道只允许**单发、已知安全**的命令（当前仅 `0x20` 读）。
7. **厂商通道整体降级为"只读诊断、且非必要不用"**：攻坚震动不再依赖它（`0x20` 之外没有可用命令）。
8. **路线 B（内核 HID 过滤驱动）判定为不值得做**（依据见 15.3 第 4 条）⇒ 除非出现全新证据，不再讨论。

# 十六、外部情报研究：**内置马达无法由主机触发**（2026-09-13，权威证据汇总）

## 16.1 结论
本机触控板属于 **device-initiated（设备自主触发）触觉压感板**：主机**只能设置强度**
（Col02 feature `rid=9` = 0x0E/0x23），**没有任何接口能让主机"命令它震一下"**。
这不是"我们没找对方法"，而是接口在设计上不存在。

## 16.2 三条独立证据
| # | 证据 | 内容 |
|---|---|---|
| 1 | 本机实测描述符 | `Col02 out=0`（**零个输出报表**）；usage page 0x0E 下只有 `Intensity` |
| 2 | 微软《Input Device Haptics Implementation Guide》 | 主机触发**必须**有 `Manual Trigger (0x0E/0x21)` **OUTPUT** 报表 + `Waveform List`/`Duration List` feature 报表 —— 本机一个都没有 |
| 3 | **Linux 上游 RFC（2026-06-16）** | Rong Zhang 发起，Dmitry Torokhov（input 维护者）、Peter Hutterer（libinput 维护者）参与：<br>「haptic feedback may be either **device-initiated** or host-initiated... **device-initiated ones are currently not configurable at all**」<br>「...since **there's no way to initiate a force feedback from the host**, the device is not a true FF device」<br><https://lore.kernel.org/all/bbee6e61a243a0ae4db6ea155909607326a80dac.camel@rong.moe/> |

## 16.3 解开的三个谜团
| 谜团 | 答案 |
|---|---|
| Linux 驱动为什么必须改描述符**第 607 字节**（`0x15`→`0x25`）？ | 该字节正是 **Haptics Intensity（`rid=9`）的 Logical Maximum**。原厂固件把它写成 `0x15`（Logical Minimum），使强度字段没有合法量程 ⇒ **原厂描述符 bug 恰好落在触觉报表上**（对应 libinput quirk 的 `AttrPressureRange=2:0`） |

# 十七、固件深度逆向（2026-09-13，纯离线，零风险）

## 17.1 镜像画像
| 项 | 值 |
|---|---|
| 明文段 | `BIN[0x19ABC:]` = **56,480 字节**，加载地址 **0x08000000** |
| MCU 内核 | **STM32F1 类**（`GPIOA=0x40010800` · `GPIOB=0x40010C00` · `RCC=0x40021000` · `FLASH=0x40022000` · `TIM2=0x40000000` · `TIM3=0x40000400` · `I2C1=0x40005400` · `USART1=0x40013800`） |
| 初始 MSP | `0x200076C8` ⇒ SRAM ≈ 29.7 KB |
| 编译时间 | **`Nov 28 2023` `19:10:59`**（镜像内字符串 `0x08000430/0x08000450`） |
| 内部版本 | **`5.21.01.23007`**（`0x0800CA32`） |
| 工程标记 | **`TF100A_Test_FW`**（`0x08000410`） |
| 向量表 | I2C1_EV=`0x08008978` · I2C1_ER=`0x0800894C` · **TIM3=`0x0800D628`** · DMA1_CH1=`0x08006B3C`；其余 IRQ 全是默认空转 `0x0800517F`<br>🔴 **依据已作废**：`0x08900 ∈ [0x08800,0x08C00)` = **K 交织表副本内部**（`udf` 0.0548 vs 真代码 0.0020）。**结论保留**，**新依据** = `I2C_Init@0x0800FA20` 逐指令 |
| 调用图 | 字节级 BL 扫描：**250 个目标 / 600 条边**（注意：BL 的 25 位立即数须减 `0x2000000`，减成 `0x1000000` 会得到 `0x09xxxxxx` 的伪目标） |

## 17.2 触觉子系统（`0x08008600–0x08009800`）
| 地址 | 作用 |
|---|---|
| `0x08009750` | LRA 配置：**振幅 119、周期 999**，并把波形回调 **`0x0800D6F4`** 写进结构体 `+0x14` |
| `0x08008FE8` | TIM2 初始化：振幅 119、周期 **1999**（结构体 `0x200040B8`） |
| `0x08008704` | PWM 硬件配置（ARR=700/CCR=96 与 ARR=1999/CCR=119） |
| `0x08008858` | "调用结构体 `+0x14` 里的回调"（通用间接调用器） |
| `0x08008628` | 守卫 TIM3 → 调 `0x08008858(0x200040D0)`（"播放"包装）**但在 600 条边的调用图里无任何调用者** |
| `0x200040D0` | 上下文结构；`+0x10` 是**计数器**（取值器 `0x08007E94`、自增器 `0x080086F4`） |

## 17.3 关键结论
1. **LRA 驱动参数是编译期常量**：`119 / 999 / 1999` 全镜像**只出现在两处配置点** ⇒ 波形**写死在固件里**，主机侧无从配置（与"改点击阈值无效"的实测互相印证）。
2. **`0x08008628`（播放包装）不可达**：无 `bl` 调用者、无 `movw #0x8628` 立即数、无数据指针 ⇒ 死代码，或仅能经异常路径进入。
3. **没有文本命令接口**：全镜像无 `vib`/`motor`/`haptic`/`cmd`/`AT+` 之类字符串；唯一的"人话"字符串是 `TF100A_Test_FW`、编译时间、版本号，以及 printf 用的十六进制表（`0x0800C704/C718`）。
4. **设备→主机上报路径已定位**：存在一族（约 20 个）**"帧构造器"函数**，模式统一为
   *写入 `0xA2` 头 → 填数据 → 操作 `GPIOA` 第 3 位（掩码 `0x8`）* ⇒ 极可能是**"组好报文 + 拉中断线通知主机"**。
   其中 `0x08008868` 的构造过程：`buf[0]=0xA2`，`buf[1]=参数`，`buf[2..]=从 0x200040E8 拷贝`。
5. **主循环 = `0x0800AA20`**（此前误判为"初始化"）：内含一长串顺序调用（`0x0800AD64–0x0800AD94`）与 `0x0800ADFA` 处的分发调用
   `0x080091C0`（多分支分发器，各 case 落在 `0x080093xx–0x080097xx`，其中 `0x0800968A` 会调用 `0x08008868` 把**收到报文的 `byte[1]`** 回填进 0xA2 帧）。

## 17.4 尚未解决 / 诚实结论
- **仍未找到任何"主机命令 → 触发 LRA"的路径**；结合 17.3(1)(2)，震动是**固件内部行为**，主机侧没有入口。
- 之前"第二颗芯片 TF100A 驱动马达"的推测**被削弱**：`0xA2` 帧遍布全固件、是**统一的报文头**，更像"设备 → 主机"的上报通道，而不是芯片间私有协议。LRA 由主 MCU 的 TIM2/TIM3 PWM 直接驱动。
- ⇒ **要在这块板子上实现"滑动震动"，已确认只剩"改固件"一条软件路**；而改固件的**前置条件**是：先验证存在一条可靠的**刷回官方固件**的通道（ESRT/BIOS 的 `Goodix Update UEFI`，或厂商刷机通道），否则一次失败即永久变砖。

# 十八、"刷回通道"验证结论（2026-09-13，只读，未做任何修改）

## 18.1 官方刷机机制 = **BIOS/UEFI 侧执行**（不是 Windows 厂商通道）
`goodixtouchpad.inf`（`oem87.inf`，**Class = Firmware**，Goodix，`DriverVer 02/02/2024,0.0.2.8`）全文关键段：
```ini
[Firmware.NTamd64]
%FirmwareDesc% = Firmware_Install,UEFI\RES_{b6ae105a-ba93-4fc8-aa28-e63903ffedde}
[Firmware_CopyFiles]
TB14P_GT7868Q_14030522_20240202.BIN
[Firmware_AddReg]
HKR,,FirmwareId,,{b6ae105a-ba93-4fc8-aa28-e63903ffedde}
HKR,,FirmwareVersion,%REG_DWORD%,0x14030522
HKR,,FirmwareFilename,,TB14P_GT7868Q_14030522_20240202.BIN
[DestinationDirs]  DefaultDestDir = %DIRID_WINDOWS%,Firmware   ; → C:\Windows\Firmware
```
设备键 `HKLM\SYSTEM\CurrentControlSet\Enum\UEFI\RES_{b6ae105a-…}\0\Device Parameters`：
`FirmwareId={b6ae105a-…}` · `FirmwareVersion=335742242 (=0x14030522)` · `FirmwareFilename=TB14P_GT7868Q_14030522_20240202.BIN` · **`FirmwareStatus=0`**
ESRT 设备：`HardwareID=UEFI\RES_{b6ae105a-…}&REV_14030522` · `CompatibleIDs=UEFI\CC_00010002 GenFirmwareResource` · 描述 **"Goodix Update UEFI"**

⇒ 这是微软标准的 **"固件资源（Firmware Resource）+ ESRT"** 模型：Windows 只负责把 `.BIN` 放进 `C:\Windows\Firmware`，
**真正的刷写由平台固件（BIOS）在启动时执行**（所以描述里写的是 "Update **UEFI**"）。
**好消息**：刷机不走那条脆弱的 Windows 用户态厂商通道。

## 18.2 但**我们无法按需触发它** ✗
| 触发条件 | 现状 |
|---|---|
| Windows 只在"有**更新的、已签名**的固件包"时才安排刷写 | 已安装包的版本 `0x14030522` **等于**设备当前版本 ⇒ **无待刷更新** |
| 自己造一个"更新版"包 | 不可行：`GoodixTouchpad.cat` 是签名目录，改 INF/换 BIN 会破坏签名，Windows 拒绝安装 |
| 让 BIOS 接受我们改过的镜像 | 几乎不可能：厂商容器本身是加密/签名的（见 17.5 的 97 个子镜像） |

## 18.3 ★ 结论：**改固件是一条"单程门"，没有自助救援**
- 官方刷机机制存在，但**只掌握在 OEM（联想/汇顶）手里** —— 他们能推一个新版本；**我们不能**。
- 因此：**一旦用厂商裸刷通道写入魔改固件失败，我们没有任何办法把官方固件刷回去**（既造不出可接受的包，也强制不了 BIOS 更新）。
- ⇒ **路线 C（改固件）判定为不可接受**：失败代价是永久变砖 + 送修，收益（滑动震动）可以用零风险的路线 A 达成。

# 十九、测试 A：主机写入"强度"本身会不会引发震动（2026-09-13，已执行，**阴性**）

## 19.1 为什么要测
此前"主机无法让触控板震动"的论证建立在三条上：① 描述符无 `Manual Trigger`；② 39 条命令 handler 无一碰 TIM2/TIM3；③ 35 个 opcode 硬件实测。
**这三条都不排除一种情况**：固件对某个**标准 HID 可写字段**产生**副作用式的震动**（不是 Manual Trigger，而是"改设置 → 预览震一下"这种常见 UX）。
而且 `rid=9` 走的是**标准 HID feature 路径**，不是厂商通道 ⇒ ② 对它不适用。**这是论证链上最后一条未测的缝。**

## 19.2 方法
`poc/haptic-preview-test2.ps1` —— **只碰 Col02 `rid=9`**；不碰 Col04，不碰厂商报表（`rid=6/11/12/13`）。
- 只写句柄打开 Col02 ✓（只读句柄被 PTP 驱动独占，符合预期 ⇒ **无法备份原值**）
- 空转 20 秒（用户把手指**轻放**在板上）→ 连写 6 个不同值 `5 / 40 / 75 / 15 / 60 / 90`，间隔 4 秒，每次先"嘀"一声
- 结束回写 10（项目历史记录的"恢复正常"值）

## 19.3 结果
| 观测 | 结果 |
|---|---|
| 6 次 `SetFeature(rid=9)` | 全部 `True` |
| **阳性对照：点击反馈力度** | **确实随之改变**（用户体感）⇒ **命令真的到达了设备**，不是空跑 |
| **关键问题：写入瞬间有无额外震动** | **无。6 次全无** ✗ |
| 回写 | `rid=9 <- 10`，`True err=0` |

## 19.4 结论
⇒ **"主机写入强度会顺带触发一次震动"——实测阴性。最后一条缝已焊死。**
与固件侧结论一致：LRA 驱动参数是**编译期常量**，波形写死在固件里；主机侧除了 `rid=9` 这个**参数**之外，没有任何能引起震动的写入。

> 本次实测同时再次确认：`rid=9` 是**参数**，不是**动作**。（`WHY-NOT-VIBRATE.md` §3/§6 已同步。）

**① 那段镜像指向但未包含的代码 ★★★**

`0x0800DFE5`（**+837 B** ← 真实越界最大值）、`0x0800DEE9`（+585 B）、`0x0800F0B5`（~~+5,141 B~~ **此数已推翻**）。
⚠ 这**不是"文件缺字节"**——两个声明长度与在场字节**精确相等**（见 `VIBRATION-FORENSICS-2.md` §5.9）。

> **★ 2026-09-14 修正（重要，避免后人被这个数带偏）**
> **「缺 5,141 字节」是误判。** 它来自 `0x08008FF6` 处 `movw r1,#0xf0b5` + `movt r1,#0x800` 构造的常量 `0x0800F0B5`，
> 减去基址与镜像长度得 5,141 —— **算术没错，但推论错了**：该常量**无法证明是"镜像应有的长度"**，更可能只是个数据指针，
> 且它**在镜像里从未被当字面量使用**；同一张表外还有一个越界更大的 slot（`+8,389`）。
> **⇒ 准确的量级是「缺失下界 837 字节（约 0.8 KB）」，不是 5,141。**
> **对行动的影响**：想补齐只需找另一份同族容器比对末尾，**不必为这个数字去拆机**。
> 依据：`COL04-BOUNDARY.md` 之前的独立验证报告 + `PREFLIGHT-STATE.md` §10。
落在该区段内的：

| 找什么 | 地址 | 意义 |

| **播放例程调用者** | `0x08008628` | 启动 TIM3 → LRA 的唯一入口，引用数 0 |

⇒ **要找的是"扣扳机的那根手指"。** 但它在**哪条通路**上，取决于上面的前提是否成立。

**② "震"的触发帧 → 直接重放 ★★★**

- 按下时震是**设备自主**的，但**判定在哪颗芯片？** —— **这是本节的核心未知，不是已知前提**

**③ 两颗芯片的真实分工** —— 公开资料空白，可产出第一手资料

## 二十一、差分探针：结果阴性 —— 「写假压力值触发反射」这条路已关闭 · 2026-09-13

> 本节关闭 §20.5 待办 1。**纯读，零写入，未触碰红线 7/8/10。**

### 21.1 做了什么

用厂商通道 `0x20` 读（唯一已知安全的命令）对三个窗口做**差分读取**。
三轮共 39 次读，**无一次失败**。每次读取前有存活门（`0x5B8E`）。

| 窗口 | 大小 | 选择理由 |
|---|---|---|
| `0x5B80` | 128 B | `0x5B96` 写入测试成功过 ⇒ **已知可写的对照** |
| `0x4000` | 256 B | 空白对照 |
| `0x9000` | 256 B | 疑似二维网格（§7 结构分析）|

三次读数（时间戳取自 `poc/diff-probe-log.txt`）：

| 读数 | 时刻 | 手指 |
|---|---|---|
| **B** | 16:46:44 | **按下** |
| **A1** | 16:47:21 | 抬起（距 B **37 秒**）|
| **A2** | 16:49:15 | 抬起（距 A1 **114 秒**）|

### 21.2 第一眼：一个假的阳性

A1 vs B：`0x9000` 变化 **120/128** 字，而 `0x4000`/`0x5B80` 各变化 **0**。
看上去就是压力响应。

### 21.3 对照推翻了它

| 比较 | 手指状态 | 时间间隔 | `0x9000` 变化 |
|---|---|---|---|
| **A1 vs A2** | **都是抬起** | **114 秒** | **121 / 128** |
| A1 vs B | 抬起 vs 按下 | 37 秒 | 120 / 128 |

**两次「没碰」的读数，差异和「碰了 vs 没碰」一样大——而且时间间隔还长 3 倍。**
⇒ `0x9000` 是**持续刷新的活缓冲区**，A/B 差异是时间噪声，不是压力响应。

（数值分布上 B 确有小幅偏离：正号格子 61 个 vs 对照的 17/4 个；但 n=1，
且 `mean|Δ|` 的信噪比只有 1.47，不足以立论。**不采信。**）

### 21.4 直接测出刷新周期（决定性）

`poc/refresh-test.ps1`：同一地址 `0x9000` 连读两次，控制间隔。纯读，12 次读。

| 间隔 | 变化的字节 |
|---|---|
| **0 ms（背靠背）** | **49 / 60** |
| 5 ms | 24 / 60 |
| 20 ms | 26 / 60 |
| 50 ms | 28 / 60 |
| 200 ms | 28 / 60 |
| 1000 ms | 28 / 60 |

**零间隔的两次读就已经差 49/60。** 一次厂商读往返约 10 ms
⇒ **刷新周期 ≲ 10 ms**（触控板扫描率 ~100 Hz，正好一帧）。

⇒ **写进 `0x9000` 的任何值，在一帧（~10 ms）内就被固件覆盖。**

### 21.5 结构性结论：一把虎钳

| 区域 | 三次读数间的变化 | 对手指敏感 | 写得住吗 |
|---|---|---|---|
| `0x5B80` | **0 / 64** | ✗ | **✓**（§13 `0x5B96←25` 读回成功）|
| `0x4000` | **0 / 128** | ✗ | 未测 |
| `0x9000` | 121 / 128（**同为抬起时也是**）| ✓ | **✗——≤10 ms 被覆盖** |

**能写住的区域跟手指无关；跟手指有关的区域写不住。**

这不是「没找到那个格子」，是**那个格子不持有状态**——
它是一次扫描的**实时读数**，不是控制寄存器。

> **传感器不可写。你不能靠对着温度计喊来让它读高。**

### 21.6 这同时判定了 `0x20` 空间的性质（关闭 §20.5 待办 1）

§7 曾推测 `0x20` 是「任意 16 位地址读写原语」（⇒ 可直通 SRAM）。
§20.5 待办 1：若是 **SRAM 窗口**，则 LRA 上下文 `0x200040D0` 在可达范围内 ⇒ 不拆机捷径存在。

**现判定：不是。** `0x20` 空间是**触摸传感器数据域**：

- **可写区** = 静态配置/标定（稳定、与触碰无关）
- **活体区** = 扫描读数（刷新 ≲10 ms、写不住）

⇒ **「不拆机捷径到固件内部」不存在。** 这是**测量**出来的，不是推断。

### 21.7 方法教训（记下来）

我在跑对照之前，就对用户说了「★ 信号出来了」。
是 **A2 对照**把它按回去的。

**差分探针的全部价值在对照上。** 没有「同一状态的两次读数」作基线，
`changed cells: 120` 和 `changed cells: 0` 一样没有意义。
同批次里 `0x4000`/`0x5B80` 的 `0/128`、`0/64` 是让结论站得住的那另一半。

### 21.8 现状：对原始问题的完整回答

| 路径 | 状态 | 依据 |
|---|---|---|
| 1. 主机触发内置马达 | ✗ 不可行 | 描述符 `Col02 out=0`；测试 A 实测阴性 |
| **1b. 写传感器域伪造压力** | **✗ 不可行（本节新关闭）** | 刷新 ≲10 ms，写必被覆盖 |
| 2. 改固件 | ✗ 不该走 | 三道刷写锁 + 无退路 |
| 3. **外置马达 + 手势软件** | **✓ 推荐** | ¥40–65，零风险 |
| 4. 拆机嗅探 USART1 | ⚠️ 能**确认**，不能改变 | §20.2 / §20.3 |

**主机侧现在是真的没有门了**——不是「找不到」，是三处**独立成立**的结论：

1. **描述符没有入口**（`Col02 out=0`，page `0x0E` 下只有 Intensity）
2. **固件没有出口**（39 条命令无一碰 TIM2/TIM3）
3. **数据域不可写入**（活体区 ≤10 ms 刷新；可写区与触碰无关）

剩下的唯一未知仍在 **USART1**（片间链路），而那需要拆机。

## 二十二、容器结构定案 + 三处文档错误回滚（2026-09-13 晚）

### 22.1 为什么重查

用户三连问把架构故事顶回来了：「你给出来的结果是 TF100A 的固件吗？你搞明白 TF100A 是什么了吗？
还有 gt7868q 和 TF100A 是什么关系？」——查的过程中发现**文档之间互相矛盾**，
于是回到字节重新量。**本节全部结论可复现**：`re/container_layout.py`、`re/image_bounds.py`（均为只读）。

### 22.2 容器结构（精确到字节，实测）

```
0x00000    1,084   容器头（含 VID 27C6 / PID 01E9、步长 0x43C、两个声明长度）
0x0043C    3,252   块 1/2/3：3 份字节级相同的明文块
0x010F0       76   尾部
0x0113C  100,608   载荷 A   声明 100,608 / 在场 100,608   ✅ 精确相等
0x019A3C     128   载荷 B 自己的头（04 14 00 00 + 124 个 0x00）
0x019ABC  56,480   明文 ARM 镜像（向量表在此，SP=0x200076C8 / Reset=0x08005165）
--------- 161,628  = 文件大小，精确
头部 0x0048 声明 56,608 = 128 + 56,480                      ✅ 精确相等
```

**两种分解不是竞争假设。** `97×1084 + 56,480 = 161,628` 与
`1084 + 3252 + 76 + 100608 + 128 + 56480 = 161,628` **恒等**——
`97×1084 = 105,148 = 0x19ABC` 正是镜像起点，块 4 跨越该边界（= 76 B 尾部 + 载荷 A 的 1008 B）。
**差 128 字节只是把线画在哪里的问题，不是缺口。**

### 22.3 回滚的三处文档错误

| # | 位置 | 错误 | 实测 |
|---|---|---|---|
| 1 | `VIBRATION-FORENSICS-2.md` §5.9 | 称旧文档"1×1084 + 96×1084 + 56,480 的划分是**错的**" | **两种划分都对且恒等**（§22.2）|
| 2 | 同上 §5.9 / §5.9.1 / `§8.8` | 明文起点 `0x19A3C`，「旧文档差了 128 字节」；并据此称 payload"本身就短"、"是增量" | 镜像在 **`0x19ABC`**；`0x19A3C` 是**载荷 B 自己的 128 B 头**。**声明值 = 在场值，无缺口** ⇒ 增量说**无证据**，已退回未定 |
| 3 | `VIBRATION-FORENSICS-2.md` §5.9 判据二 | 块 **0**/1/2 逐字节相同；块内含 ASCII 表 `0123456789abcdef` | 块 **1**/2/3 相同；块 0 与其仅 1014/1084 相同（70 B 头不同）。`0123456789abcdef` **全文件仅 1 处且不在这些块内**；块内实为 **HID 键盘用法码表 + 键映射** |

**外加一处伪造引用**：§5.9.1 写「`STATUS.md` §2 记录其丝印 `TF100A`」——
`STATUS.md` **从未记录任何丝印读数**。它记的是**镜像内字符串** `TF100A_Test_FW`（`:539`），
而 `:346` 恰好说反：「芯片识别**仍只能靠丝印**」= **丝印是我们没有的东西**。字符串 ≠ 丝印。

### 22.4 我自己这一轮的错误（按发生顺序，全部已改）

1. **对用户说「TF100A 是反馈控制器、驱动 LRA」** —— 无证据。项目文档当时已记「双芯片归属仍未有定论」。
2. **对用户说容器是「1084 头 + 3328 + 100608 + 56608」四段** —— 那是文档里的说法，我没核就转述。
3. **随后又反向过度纠正**，说「97×1084+56480 才对、四段式是错的」 —— **两个都对**，我第二次也错了。
4. **线性反汇编失步**：`md.disasm(img[o:o+4], …)` 却按 `o += 2` 前进，4 字节指令被当 2 字节推进 ⇒
   凭空造出约 40 个"越界分支目标"（`0x08CFCEA2` 之类）。**改用递归下降后**才拿到真实集合。
   *教训：反汇编器前进必须用 `ins.size`；线性扫描在 Thumb 上一定会失步。*

### 22.5 站得住的结论（重新逐条实测）

- **镜像引用越界**：向量表 84 项（16 系统 + 68 外设 IRQ），73 项非空，**其中 2 项在镜像外**——
  slot 6 → `0x0800DFE5`（**+837 B** ← 真实越界最大值）、slot 53 = **IRQ37 USART1** → `0x0800DEE9`（+585 B）。
  代码 `0x08008FF6` 的 `movw r1,#0xf0b5` + `movt r1,#0x800` → `0x0800F0B5`（~~+5,141 B~~ **已推翻，见 §20 前的修正块**）。
  ⇒ **镜像是地址空间的不完整视图**（与"文件缺字节"是两件事），**缺失量级是下界 837 字节**。
- **门铃三函数零引用**：`0x08008AF0` / `0x08008B38` / `0x08008B5C` 在全容器无 `bl`/`blx`/字面量。（不变）
- **载荷 A 开头是明文头**：`00 01 88 FA | 5F 37 | YELSTO | 00 00 06 | 7868Q`，其后熵恒 7.97–7.99。
- **两条载荷的自称不同**：A 自报 `7868Q`，B 自报 `TF100A_Test_FW`。
  **这是支持"两个目标"的一个证据**，但**自称字符串 ≠ 读自芯片的丝印**，不构成定论。

### 22.6 新增悬空项

- **容器头携带的是 HID 键盘描述符 + 键映射**（块 1/2/3 内：
  `FF×8, 2D 2E 2F 30…3F, FF×N` 与 `FF×8, 27 26 25 23 24 22 20 21…`）。

### 22.7 方法论教训（本条比结论更值钱）

| # | 教训 |
|---|---|
| 1 | **两个"各自精确闭合"的分解，不一定是竞争假设**——可能只是同一份数据、边界画在不同处。先验恒等，再谈对错。 |
| 2 | **"引用越界" ≠ "文件缺字节"**。前者说地址空间，后者说封装。混起来会推出"增量固件"这种无证据结论。 |

| 4 | **反汇编前进用 `ins.size`**。线性扫描失步会静默造出大量假引用，且**看起来很像真结论**。 |
| 5 | **引用必须回原文核**。本轮三处错误里，有两处是"文档说 X"被我直接转述。 |
