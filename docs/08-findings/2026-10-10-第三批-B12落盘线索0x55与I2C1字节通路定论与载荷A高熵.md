## 1. ★★★★★ B12 重大线索：那三个官方更新器是怎么"真正落盘"的

> **B12 是项目最大的未解决问题**：HID 写入后数据**只留 RAM、重启即失**；已试 `0x80`+写+`0x83`、额外 `0x34`、`0x7D` 收尾 —— 全部只到 RAM；因只有一台机器，**不敢试红线 `0E 12`**。

### 1.1 三个仓库的落盘套路（逐条附原文）

**① `anarsoul/pbtp_fw_writer`（Pinebook 触控板）**
```c
/* Erase pages 0-6 */
memset(report_data, 0x45, request_size); report_data[0] = 0x05;
...
do_write_fw(...)                        /* 写：0x05 0x57 设地址+长度 → 0x06 0x77 + 2048B/块 */
do_read_fw(...) + memcmp(...)           /* ★ 读回全量比对（最多 5 次重试） */
...
/* Send end programming command */
memset(report_data, 0x55, request_size); report_data[0] = 0x05;   /* ★★ 0x55 全填充 */
```
**★ 提交步 = `0x05 0x55 0x55 0x55 0x55 0x55`，源码注释直接写 "Send end programming command"。**

**② `ayufan-rock64/pinebook-pro-keyboard-updater`**
- 键盘路径：`{0x05,0x55,0x55,0x55,0x55,0x55}` + **`libusb_reset_device()`**（注释 `"Reseting device?"`）
- **触控板路径（状态机握手，最值得看）**：
```c
#define ENTERBOOTLOADER 0xF1
#define ICERASE         0xF2
#define PROGRAM         0xF3
#define VERIFY1KDATA    0xF4
#define VERIFY_CHECKSUM 0xF5
#define PROGRAMPASS     0xF6
#define ENDPROGRAM      0xF7      /* ★ 提交 */
#define ENDPROGRAM_PASS 0xE7      /* ★ 期望回值 */
```
流程：`逐 1024B 块写 → 每块 VERIFY1KDATA → ENDPROGRAM → VERIFY_CHECKSUM → PROGRAMPASS`

**③ `cirque-corp/chromeos_cirque_fw_update`（**Cirque 官方**，ChromeOS 触控板）**
```cpp
static const int BL_CMD_FLUSH    = 1;
static const int BL_CMD_VALIDATE = 2;
static const int BL_CMD_RESET    = 3;
...
bl.WriteData(...);  bl.Flush();  // ★ 提交 1
bl.Validate(EntireImage);        // ★ 校验（失败返 NV_err_chksum_mismatch）
bl.Reset();                      // ★ 提交 2：让新镜像生效
```
**★ 提交被拆成三步：`Flush → Validate → Reset`。** 且每区携带 **Fletcher_32**。

### 1.2 ★ 抽出的通用 5 步套路

```
1. 进入编程/引导模式
2. 擦除目标区
3. 按固定块大小顺序写入
   （注意：两个 Pinebook 实现在数据循环后【再发一次"起始/长度"命令并重写第 0 块】，
     还有"首字节清零"的 hack —— 注释 FIXME: why?）
4. ★ 读回 / 校验和验证
5. ★ 发一条【独立的提交/落盘命令】（0x55 全填充 / ENDPROGRAM / Flush+Validate），
   再【复位器件】使其生效
```

### 1.3 ★★★ 对照我们的 B12：**哪一步做漏了**

| 我们的做法 | 三个仓库的做法 | 差异 |
|---|---|---|
| `0x80` + 写 + `0x83` → 收尾 `0x7D` / `0x34` | 收尾是 **`0x55` 全填充** 或 **ENDPROGRAM `0xF7`** 或 **Flush(1)** | 🔴 **收尾码字可能整个用错了** |
| 写完**没有"读回校验通过"这个门槛** | ★ **三个仓库都在提交前强制校验** | 🔴 **顺序缺一环** |
| 写完直接收尾 | 两个 Pinebook **在数据循环后重发长度命令 + 重写第 0 块** | 🔴 **可能漏了"触发认账"的动作** |
| —— | 擦除用 `0x45` | 🟡 我们没走过擦除 |

**⇒ 最值得先试的是 `0x55` 全填充提交。**

### 1.4 ⚠️ 安全说明（与我方红线的对比）

- 三个仓库里**都没有 `0E 12` 这一对字节**，也**没有任何一条命令被标注为"会砖/红线"**。
- 它们唯一的防呆是：`LastError` 状态检查（Cirque）、写前 `SanityCheck`、失败重试、`"You have 5 seconds to press CTRL+C"`。
- ⇒ **"持久化"本身不需要危险命令**；真正高风险的是**擦除/写地址越界**，而非提交动作。
- ⇒ **但**：`0x55` 是**别的厂商（SinoWealth/ELAN 系）的协议码**，**不能假定** GT7868Q 通用。**必须设计成"失败可表征"**：

> **建议的最小风险试验设计（不现在执行）**
> 1. **先建恢复路径**：记录当前 `cfg+0x10F/+0x111/+0x113/+0x115/+0x117/+0x119` 与 `0x96F8` 前 32 B 基线；
> 2. **只动一个已知无害字段**（如 `+0x10F`），**单发一次** `0x55` 全填充报文（长度取与本通道一致）；
> 3. **立刻重读该字段** → 若"改后仍为改值且关会话后仍在" ⇒ **落盘成立！**；若字段回原值或通道无响应 ⇒ **记阴性并停止**；
> 4. 全程**前置/后置健康三连**（`probe` 5/5）；
> 5. **不做任何擦除类动作**。
> ⇒ **判据客观（读回），不需要手感**，符合项目纪律。

**⇒ 真正碰 `0x40005400` 的只有 `0x0800894E–0x08008B88` 这 12 处（全在 I2C1 的 ISR/回调/初始化簇内）。**

### 2.2 分派器 `0x0800E1C0` 周边 120 条指令：**零个 I2C1 寄存器访问**

### 2.3 ⇒ 定论

```
ITBUFEN = 0  ⇒ RXNE / TXE 中断【不产生】
   ↓
唯一读 I2C1_DR 的代码 = RXNE 回调 0x08008A70（被 ITBUFEN 门控）  ⇒ 运行时不执行
   ↓
全镜像【没有】其他地方轮询 SR1.RXNE，也【没有】别的 DR 读点
   ↓
分派器 0x0800E1C0 不碰 I2C1
   ↓
★★★ 结论：128 B 收包环在本镜像里【永远填不满】
```

**⇒ 两种解释中，第 (b) 种成立**：**本镜像的 I2C 字节接收通路没有接完。**
而本镜像**自称 `TF100A_Test_FW`**（`file 0x19ECC`）⇒ **完全一致：它是测试固件。**

**★ 重要推论（防止过度外推）**：
- 项目文档说"39 条命令跑在 I2C1 上" —— **命令表本身完整、39 个 handler 齐全**（子代理逐条比对确认）；
- 但**在本镜像里收不到能触发它们的数据**。
- ⇒ **"`ITBUFEN` 从不置位"是【这个 Test_FW 的】特性，不是器件特性。** 量产固件很可能设了它。

## 3. ★★★★ 载荷 A 是高熵的 —— 不是"明文数值表"

### 3.1 分区熵与 GR4 式加法校验

| 区段 | 长度 | **熵** | 零字节占比 | GR4 字和 mod 2³² |
|---|---|---|---|---|
| 外层清单（4×1084 B） | 4,412 | 5.154 | —— | `0x61E77FEF` |
| **载荷 A（Goodix 容器）** | **100,608** | **7.997** | **0.3–0.6%** | `0xE961C045` |
| 分隔 128 B | 128 | **0.132** | 极高 | `0x00001404` |
| TF100A ARM 固件 | 56,480 | 6.645 | —— | `0xF2F80077` |
| 整文件 | 161,628 | 7.743 | —— | `0x3E4154AF` |

**② 校验模型检验：文件末尾 4 B = `0x00000000`，与任何区段字和都不匹配 ⇒ GR4 式加法校验【不适用】。**
（⇒ "容器校验和通过"用的是**别的算法**，不是 LE32 字和。**这是一个干净的负结果。**）

### 3.2 ★ 载荷 A 的头部（明文）—— `YELSTO` 就在这里

```
载荷A +0x0000  00 01 88 fa | 5f 37 59 45 4c 53 54 4f | 00 00 06 37 38 36 38 51 | 00 00 00 1c ...
                 ↑未明      "_7 Y E L S T O"           len=6  "7 8 6 8 Q"
载荷A +0x0020  01 00 00 08 00 00 ff 00 03 00 00 20 00 01 60 00
载荷A +0x0030  03 00 00 20 00 00 60 00 03 00 00 20 00 00 80 00   ← ★ 明显的 [类型][长度][值] 三元组
```

**★★★ 两个新事实：**
1. **`YELSTO` 魔数就在载荷 A 的开头**（载荷 A `+0x06`；= 容器 `file 0x1142`）—— 它**属于载荷 A**，不是外层清单。
2. **载荷 A `+0x20` 起出现规律的 `03 00 00 20 00 01 60 00` / `03 00 00 20 00 00 60 00` / `03 00 00 20 00 00 80 00`** —— 看起来是**`[类型=3][?=0x20][长度/计数]` 的 TLV 结构**，与前 16 B 的魔数/名称是同一层。

### 3.3 ★ 这对既有表述的影响

| 既有表述 | 本次实测 | 影响 |
|---|---|---|
| "载荷 A = 官方 Goodix 容器，**13 块全是数据**" | 熵 **7.997**、零字节 0.3% ⇒ **不是明文数值表**（明文表会有低熵区/大量零） | ⚠️ **"是数据"成立，但"是明文数据"不成立** —— 它**加密或压缩**了 |
| "容器校验和通过" | LE32 字和模型不匹配 | 校验算法**待定**，但不影响"通过"这一事实 |
| `GT7868Q_plain.bin` 解密后该区仍是 ~7.4（本日更早实测） | 7.997 → 7.4，**只降了一点，远未到明文水平** | ★ **与 C4（该解密作废）方向一致** |

**⇒ 推测（标为未验证）**：载荷 A 是 **Goodix 自己的加密/压缩容器**，**头部明文 + 主体加密**是常见结构。项目手上的 `K`（1024 B）**可能**是其中一层，但**实测解密没能把熵降下来** ⇒ **K 不是（或不只是）这一层的密钥**。

## 5. 新增纪律

> **第 121 条**：**"别人的协议码"不能假定通用，但"别人的协议*结构*"可以借用。**
> 三个官方更新器的**码字完全不同**（`0x55` / `0xF7` / `Flush(1)`），但**五步结构完全一致**（进入→擦除→写→**校验**→**提交+复位**）。
> ⇒ **借用结构去检查自己漏了哪一步，比照抄码字安全得多。**

> **第 122 条**：**"高熵"必须与"数据/代码"分开表述。** 熵 7.997 只能证明"不可压缩/近随机"，
> **不能**据此断言"是加密"或"是压缩"（两者都可能），**更不能**据此断言"里面有内容"。**须另有证据**（如已知明文头、或解密后熵下降）。
