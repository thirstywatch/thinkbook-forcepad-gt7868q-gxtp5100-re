### 🔴 而且我必须给 `+0x115` 的定名**打问号**

既有 Q54 说「**震动阈值 = 点击阈值 = 140**」。而喆的反馈是：
`120→60`「**变绵软**」、`120→240`「**明显更强**」。

**这两种反馈同样可以用"触发点（阈值）移动"解释，而不只是振幅：**
- 阈值**提前**触发 ⇒ 手指还没压到底就"点击"了 ⇒ 手感**软塌/绵软**；
- 阈值**靠后**触发 ⇒ 压到位才点击 ⇒ 手感**扎实/更强**。

**⇒ 当时推断：`+0x115` 更可能是"点击/触觉触发阈值"，不是"振幅"。**
**⇒ 若如此，把它压到很低（如 20）就应该让轻滑也触发。**

> 🔴 **2026-10-05 补测后本段推断已作废** —— 压到 20 与压到 **0** 都既没让滑动震动、
> 也没产生任何误触发，**"阈值"与"振幅"两个假说同时被否**。详见 [§七 裁决](#七--首个行为改变实证cfg-0115--触觉强度)。

## 一 打通过程：六次失败 → 一次命中（失败全部可归因，且**每一次都留下了确定性事实**）

| 轮 | 分块方式 | IC 回复 | 活体 `0x96F8` 窗口 | 从中得到的事实 |
|---|---|---|---|---|
| 1 | 19 块**同一地址** `0x96F8`，`cont=1…1,0` | `7E 00 00` | 变为 **`body[990:1024]`**（= 尾块 34 B） | **每块都写在给定地址 → 互相覆盖**；`cont` 在"主机→设备"方向**没有**换锚保护作用 |
| 2 | 地址递增，仍带 `cont=1` | `7E 00 02` | 纹丝不动 | `cont=1` 带上反而被判序列错 |
| 3 | 地址递增，全 `cont=0` | `7E 00 02` | 纹丝不动 | （当时误判为"没写进"——见第四轮纠正） |
| 5 | 地址恒定 + `[8..9]=总长1024` + `cont=1` | `7E 00 02` | 被清成全 `00` | **进 cfg 模式时 IC 会清暂存区** |
| 4′ | 非 cfg 模式**预装** 1024 B 再进模式 | `7E 00 02` | 进模式瞬间被清零 | 预装法**不可行** |
| 5′ | **cfg 模式内**单块写 + **写后立刻读窗口** | `7E 00 02` | **= `cfg[0:32]` 逐字节相同 ✓✓✓** | **单块写在 cfg 模式内是有效的！数据完整进了暂存区** |
| **6** | **同 5′，但长度改成 1084** | **`7E 00 07`** | 一致 | **★ 命中：真正的 `sub_cfg_len` = 1084** |

> **方法论**：这轮唯一的"神来一笔"是**把 IC 当成判等预言机**——官方只把 `7E 00 07` 定义为"与 flash 完全一致"，
> 于是"写回原样应得 07"就成了一条**自带真值的验收判据**。用扫长度（1024 / 1084 / 2048 / 4096 / 512 / 256 / 128）
> 一秒定位了真实长度。**这正是本项目"必须先有一个答案已知的样本"纪律的直接应用。**

## 三 ★★★ 传输层语义定案（这是本轮最硬的技术增量）

`0E 20` 就是"**I²C 直通读写**"，因此官方 `goodix_i2c_write_trans()` 就是 IC 侧语义的权威定义：

```c
while (pos != len) {
    transfer_length = min(len - pos, I2C_MAX_TRANSFER_SIZE - TS_ADDR_LENGTH);
    msg.buf[0] = address >> 8;  msg.buf[1] = address & 0xFF;   // 2 字节 BE 地址前缀
    msg.len = transfer_length + 2;
    memcpy(&msg.buf[2], &data[pos], transfer_length);
    ...
    pos += transfer_length;
    address += transfer_length;      // ★★ 地址由【主机】自己递增
}
```

**⇒ 一条 `0E 20` 写包 = 一次 `i2c_transfer`**，报文结构实测为：

```
0E 20 <cont> <seq> <本块数据长度+5> 00 <addr16BE> <本块数据长度16BE> <data…>
```

| 字段 | 结论（实测） |
|---|---|
| `[2] cont` | 主机→设备方向**保持 0**（单块自成一次完整写）。带 `1` 反而被判序列错 |
| `[3] seq` | 实测 0..n 都可以（未发现约束） |
| `[4]` | **本块数据长度 + 5**（与官方 `hidbuf[4] = data_sz + 5` 一致） |
| `[5]` | `0x00`=写；`0x01`=读 |
| `[6..7]` | 16 位地址（BE） |
| `[8..9]` | **本块**数据长度（不是总长！填总长会让 IC 清暂存区） |
| `[10..]` | 数据，单包最多 **55 B**（65 B 报告 − 10 B 头） |

**⇒ 正确下发 1084 B = 20 个单块包，地址从 `0x96F8` 起每块 +55。**

**读包**（同族）：`0E 20 00 00 05 01 <addr16BE> <size16BE>`；响应 `0E 20 <cont> <seq> <len> <data…>`，单包最多 60 B 数据。

## 四 ★★★ `0x96F8` 的可读窗口 = **32 字节**（本轮实测）

把 `0x00..0xFF` 用 5 个单块写进 `0x96F8..0x96F8+255`，再整段读回：

| 区段 | 结果 |
|---|---|
| `+0x00..+0x1F` | **逐字节正确** ✓ |
| `+0x20` 之后 | 变成另一批寄存器内容（`77 31 77 2A 77 15 …`），**不是我们写的数据** |

**⇒ 项目既有的"`0x96F8` 只有前 32 B 可可靠读出"由此得到机制层解释**：
**它是"32 字节窗口 + 后接别的寄存器"，而不是"读通道不稳"。**
**⇒ 推论（重要）：只要目标字节落在 `+0x00..+0x1F`，就能做到"读回自证"；本轮的 `+0x115` 不在此窗口内，故只能靠人类感官验收。**

## 五 ★★★ cfg 真实长度 = **1084**（不是 1024）

| 写入长度 | IC 回复 | 含义 |
|---:|---|---|
| 1024 | `7E 00 00` | 与 flash 不同 |
| **1084** | **`7E 00 07`** | **与 flash 完全一致 ✓** |
| 2048 / 4096 / 512 / 256 / 128 | （未继续跑，已被 1084 命中） | — |

**⇒ 容器里那条"1024 B 主体 + 60 B 尾 = 1084"的**记录**整体才是 cfg**：
尾部那 60 B **不是冗余/对齐填充，而是 cfg 的一部分**（很可能承载跨芯片参数，见 §七）。
**⇒ 本项目此前"cfg body = 1024 B"的用法要修正为"cfg = 1084 B 记录"。**

## 六 结果码语义（实测修正官方注释）

| 回复（`0x4160` 5 字节） | 官方注释 | 实测语义 |
|---|---|---|
| `7F …` | cfg 已接受并写入 | 未观测到（本机 IC 似乎从不回 7F） |
| `7E 00 07 00 85` | **与 flash 完全一致** | ✓ 写回原样时得到 |
| `7E 00 02 00 80` | 官方视为"失败" | 🔴 **实测 = "与 flash 不同，已采纳并生效"** —— 因为 `+0x115` 的改写正是带着这个回复**真实改变了手感** |
| `7E 00 00 00 7E` | — | 长度不对（写 1024 时） |

> ⚠️ **不要把 `7E 00 02` 当失败。** 官方那份代码只判 `7F` 和 `7E 00 07` 两种成功，
> 而本机 CID `0x1C` / 固件 2.3.5 用 `00 02` 表示"有差异、已应用"。
> **本项目的验收判据应改为：`0x7E 00 07` = 无改动；`0x7E 00 02` = 有改动且已应用。**

## 七 ★★★★★ 首个行为改变实证：`cfg +0x115` = 触觉强度

**实验设计**：每次下发都以【容器原始 1084 B】为基准做绝对补丁（不是增量），
写完立刻读 `0x96F8` 窗口 + 读 IC 健康寄存器，然后**由喆在键盘前用感官判断**。

| 试验 | `+0x115` 值 | 喆的原始反馈（逐字） | 判读 |
|---|---:|---|---|
| A | **60**（0x003C） | 「**变绵软了震动反馈**」 | 更弱 |
| B | **240**（0x00F0） | 「**明显更强了**」（对比最初手感） | 更强 |
| C | 120（原始，作为对照） | 「**轻一点**」（对比 B） | 回到原始 |

| D | **0**（0x0000） | 点按「**跟之前差不多**」；滑动「**还是不震**」；**没有任何误触发** | 🔴 **同时否掉两个假说**（见下） |
| E | 20（0x0014） | 点按「正常」；滑动「没变化」 | 与 120 无差别 |

**🔴 裁决（2026-10-05 第十三轮 补测）：`+0x115` 的“强度旋钮”定评【不成立，已降级为存疑】**

| 数据 | 读法 |
|---|---|
| `0` 与 `20` **都 ≈ 120**（点按照旧震、无误触发） | ⇒ **不是振幅**（振幅=0 应当静音）<br>⇒ **也不是触发阈值**（阈值=0 应当疯狂误触发） |
| `60` = 变绵软 | **唯一一个"偏低值变软"的点**，与 0/20 的行为**自相矛盾** |
| `240` = 明显更强 | 唯一支持"强度"的点，**尚未复现第二次** |

**⇒ 5 个取值里只有 2 个显示出差异，且二者互相矛盾 ⇒ 当前最可能的解释是【感知噪声 / 单次测量的对比效应】，不是参数效应。**
**⇒ 想立住"`+0x115` 是强度旋钮"，必须补一个【盲测 A/B 复现】：同一档位写两次、中间夹一次另一档位，看反馈是否随值翻转。**
**⚠️ 在此之前，`+0x115 = 240` 只能算"无实测支持但无害"的设置，不能当结论引用。**

**★ 仍然成立的只有一条**（这才是本轮真正的增量）：
**cfg 下发通道本身可用，且写入进 flash、跨重启保持**（§十二.二，重启实测）。

**⚠️ 上面这张"两个候选语义"的表已作废**（它是在只有 60/240 两点时写的）：

| 语义 | 对 60 / 240 的解释 | 若成立，怎么让滑动也震 |
|---|---|---|
| ~~A 触发阈值~~ | ~~60 = 提前触发 ⇒ 手感软塌；240 = 靠后触发 ⇒ 手感扎实~~ | ~~压到 20 ⇒ 轻滑也越过阈值~~ **已实测，无效** |
| ~~B 振幅/强度~~ | ~~60 = 弱震；240 = 强震~~ | 无效 —— 需另找触发字段（很可能在 TF100A） |

**⇒ 两者都已被 `0` / `20` 两档否掉**（见上裁决）。想立住任何一条，必须先做**盲测 A/B 复现**。

## 十二.一 🔴 重要裁决：**TF100A 固件补丁【不可执行】**（主机侧没有写它的路）

> 我曾提出"真正的路是 TF100A 固件补丁（`|Δ|>40 → >8`）"。**回查后必须撤回这个提议** —— 它有两个硬阻塞：

| # | 阻塞 | 证据 |
|---|---|---|
| **1** | **官方 HID 更新工具只写 GT7868Q，不写 TF100A** | `gt7868q_gt7868q_update.cpp::RunTo()` 全文只有两段：`fw_update()`（载荷 A 的 13 个子固件 → GT7868Q flash）与 `cfg_update()`。**没有任何针对"第二载荷 / 56,608 B / TF100A"的写入阶段** |

**★ 而且这条路就算走得通，方向也可能不对** —— 项目 2026-10-01 已定案（`lab__2026-10-01-TF100A输出端反向追溯.md` §八）：

## 十二.二 ★★★★★ 持久性实测：**cfg 写入进 flash，跨重启保持**

**实验设计（用一个"落在 32 B 可读窗口内"的标记字节，把持久性变成可客观读回的量）：**

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | 下发 `记录+0x115 = 0x00F0`（强度 240）+ `记录+0x01E = 0xAA`（标记） | IC 回 `7E 00 02`；窗口读回 `… 05 AA 00` ⇒ 标记在位 ✓ |
| 2 | **整机重启** | — |
| 3 | 重启后读 `0x96F8` 32 B | **`… 05 AA 00`** ⇒ **`+0x1E` 仍 = `AA`** ✓✓✓ |
| 4 | 清理：只下发 `+0x115 = 240`（不补标记） | 窗口回 `… 05 00 00`，标记已抹，**强度 240 仍在** |

**⇒ 结论**：
1. **cfg 下发通道是"写 flash"的** —— 不是只改运行时 RAM。**这是本项目第一条"主机侧写入、且能跨重启保持"的配置通路。**
2. 于是 `cfg+0x115 = 240` 是一个**永久生效的触觉强度设置**，可以直接当"调好的参数"留着。
3. **也顺带给出"可回滚"的实证**：本轮的 `restore` 之所以能让 IC 回 `7E 00 07`，是因为它把 flash 里的记录写回了原样 —— **回滚是真的落盘回滚，不是假动作**。
4. ⚠️ **风险提示要同步升级**：既然写的是 flash，**每一次实验都会消耗 flash 擦写次数**，且**改错了不会随重启恢复**（必须靠 `restore`）。
   ⇒ **纪律第 108 条：对 cfg 的每次写入都当作"改固件"来对待 —— 先备份、单变量、写完立刻验收、结束必 `restore`（除了刻意要保留的参数）。**
