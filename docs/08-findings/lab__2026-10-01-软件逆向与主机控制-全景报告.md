# 第一部分 · 目标与硬件基线

## 1.1 目标

**在 ThinkBook 14 G6+ IMH（21LD）上，让压感触控板在滑动时产生震动反馈。**

约束（原始需求）：
- 纯软件，不改造硬件
- 不拆机、不换模块
- 与外接马达方案互斥（那属于降级）

## 1.2 硬件构成

| 器件 | 标识 | 角色 | 状态 |
|---|---|---|---|
| 触控主控 | Goodix **GXTP5100 / GT7868Q** | 触控 + HID 主控 | ✅ 实物 + HID 枚举 |
| 压力前端 | 钛方 **TF100A** | 压力采集（自己 ADC 采 4 路）并打包 | ✅ 明文固件已完整反汇编 |
| 触觉驱动 IC | 艾为 **AW86927FCR**（丝印 `CA4F`） | 高压 H 桥 LRA 驱动器，8 KB SRAM 波形库，3 个 TRIG 脚 | ✅ 在线鉴定（厂商手册 Marking 列 + 实物引脚名 `HDP`/`HDN` 双向吻合） |
| 执行器 | 线性马达 LRA（Nidec） | 谐振 200 Hz | ✅ 已实证 |

# 第二部分 · 主机控制通路：三层结构

主机要让触控板做任何事，**只有一条物理通路**：通过 I²C 跟触控 IC 说话。
但这条路上叠了**三层关卡**：

```
第 1 层 · HID 描述符层   设备声明自己支持什么（决定主机有没有"合法手段"）
第 2 层 · 驱动层          hidi2c.sys 决定放行什么（决定主机能不能"越界"）
第 3 层 · 设备固件层     触控 IC 固件决定响应什么（决定设备"愿不愿意"）
```

**三层必须全部打开，主机才能触发震动。** 下面逐层汇报。

---

## 2.1 第 1 层：HID 描述符 —— ❌ 设备没有声明触觉能力

### 实测数据（Col02 描述符解析）

| 检查项 | 结果 |
|---|---|
| 是否存在 Manual Trigger（Usage Page `0x0E` / Usage `0x21`） | ❌ **不存在** |
| 是否存在 Haptics Intensity（`0x0E` / `0x23`） | ✅ 存在（FEATURE，只读参数） |
| Col02 的 Output 报表数量 | ❌ **0 个** |
| `0x0D` / `0xB0` Button Press Threshold | ❌ 不存在 |

### 含义

- **设备的 HID 描述符里只有"读"的参数接口，没有"命令"接口。**
- 按 HID 规范：**触觉要由主机触发，设备必须在描述符里声明 `0x0E/0x21` 作为 OUTPUT 报表。本机没有。**
- ⇒ **主机在规范层面"没有合法手段"要求震动。**

### Col04（厂商定义通道）的情况

```
Usage Page 0xFF00，Report ID 0x0E
  64 字节 Output + 64 字节 Input
```

⚠️ 这个通道**看上去**像"厂商私有命令口"，也是本项目早期寄予厚望的地方。

🔴 **2026-10-02 更正**：本条原写「**`Col04 Out = 0`**（实测无输出路径能力）」—— **这是错的**。
`Out = 0` 说的是**PTP 主体集合 `Col02`**，不是 Col04。**`Col04 Out = 65`（实测），且已验证可用**
（`HidD_SetOutputReport` 成功、`0x96F8` 读回与离线配置体逐字节一致，见《全书》§19.17.2）。

**那 Col04 为什么仍不可用？** 真正的原因不是"没有输出能力"，而是**没有任何主机组件会向它发报文**：
```
① 描述符层：Col01/Col02/Col03 的 Out 全为 0，只有 Col04（厂商 0xFF00）有 Out=65
   ⇒ Windows PTP 驱动栈（唯一消费者）面对的是 Out=0 的 Col02，物理上发不出去
② 设备栈层：四集合 UpperFilters/LowerFilters 全空，Col02/Col04 无专属 Service
   ⇒ 链上只有 inbox hidclass + spi_hid/hidi2c，无第三方 filter 或服务
③ 进程层：全系统无任何 Goodix / 联想触控板服务在跑
```
⇒ **Col04 上能观测到的一切 OUT 流量，都只是本项目自己的实验流量，永不代表"主机行为"。**

⇒ **所以「它是在 HID 层之上的封装口，不是绕过 HID 的通道」这条原判依然成立**，
但**理由必须是"主机侧没有组件去用它"，而不是"它没有输出能力"**。

**详见《全书》§19.27（2026-10-02 下午，三条独立硬事实闭合）。**

### ★ 交叉印证（外部一手资料）

蓝莓（barryblueice）的 `ESP32-Precision-TouchPad` 项目 Wiki 记录了汇顶鼠标/触控板的 HID 描述符，其中：

> **Report ID `0x0E`：`06 00 FF`（Vendor-defined）→ 64 字节 Output + 64 字节 Input**

**与本机 Col04 的结构逐字对应** ⇒ 印证了"`0x0E` = 厂商扩展通道"这个判断是对的。

同时该 Wiki 给出另一条有用信息：
> 汇顶 **HID 描述符寄存器地址有两种：`0x01` 或 `0x20`**（依据 coreboot 源码）

## 2.2 第 2 层：驱动层 —— 🔒 `hidi2c.sys` 硬阻断

### 2.2.1 驱动栈现状（实测）

```
ACPI\GXTP5100\1    → hidi2c.inf      （Microsoft 10.0.26100.8972）   ← 拦截点
HID\GXTP5100&COL01 → msmouse.inf     （Microsoft 10.0.26100.1150）
HID\GXTP5100&COL02 → input.inf       （Microsoft 10.0.26100.9444）
HID\GXTP5100&COL03 → mtconfig.inf    （Microsoft 10.0.26100.1150）
HID\GXTP5100&COL04 → input.inf       （Microsoft 10.0.26100.9444）

运行中: hidi2c  Running  C:\Windows\system32\drivers\hidi2c.sys
UpperFilters: mshidkmdf
```

**注意**：DriverStore 里有 Lenovo/Goodix 自己的包 `goodixtouchpad.inf_amd64_…`，
但它**只提供 Firmware 类设备**（UEFI 胶囊），**不服务任何 HID 接口**。
5 个 HID 接口全部绑 Microsoft 驱动 —— **这是设计，不是配置错误。**

### 2.2.2 阻断机理（两层）

**第一层 · 协议层**：I²C-HID 是**寄存器寻址协议**，设备固件只认 ACPI 声明的这几个寄存器：

| 寄存器 | 默认地址 | 用途 |
|---|---|---|
| `wReportDescriptorRegister` | 0x21 | Report Descriptor |
| `wCommandRegister` | 0x22 | SetPower(`08 00`) / RESET(`01 00`) |
| `wDataRegister` | 0x23 | 数据传输 |
| `wInputRegister` | 0x24 | 输入报告 |
| `wOutputRegister` | 0x25 | 输出报告 |

我们需要的 Goodix 私有封装（`_I2C_DIRECT_RW`）**超出声明范围 → 被拒**。

**第二层 · 驱动层**：`hidi2c.sys` 作为 KMDF HID 迷你端口，**按 ACPI 声明范围严格转发，超出即拒**。

### 2.2.3 实测证据（用户态尝试，全部失败）

```python
COL04: VID=27C6 PID=01E9 UP=FF00  bus_type=3 (I²C)
open_path()                    → 成功 ✅
GET_FEATURE(0x0e, 65/64/10/8)  → OSError: read error   (全部失败) ❌
SET_FEATURE([0e 20 00 00 05 01 96 F8 00 03])
                               → 返回 -1                ❌
```

**⇒ 用户态无论怎么试，私有命令都到不了设备。**

### 2.2.4 ❌ 已排除：上层 HID 过滤器驱动

在 `hidi2c` **之上**挂过滤驱动只能看到 HID 层。
**而我们的私有命令正是在 HID 层被拒的** —— 请求根本不会下传到过滤层。**逻辑死路。**

### 2.2.5 ❌ 已排除：再挂一个"并列 SPB 客户端驱动"

这个想法看似可行（I²C 控制器物理上可以有多个客户端），但被**微软官方文档明确否定**：

> **"Only one driver can hold an open logical connection to an SPB-connected peripheral device at a time. An attempt by another driver to open a second connection to the same device fails."**
> —— *Connection IDs for SPB-Connected Peripheral Devices*

**技术细节（本次查证）**：

| 项 | 事实 |
|---|---|
| 连接 ID 是什么 | 一个 **64 位整数**，由 PnP 分配，**随硬件资源下发**（驱动在 `EvtDevicePrepareHardware` 的 `ResourcesTranslated` 里取） |
| `{F0E20F09-…}` 是什么 | ⚠️ 那是 **SPB 连接参数属性**（`DEVPKEY_Device_SpbConnectionParameters`），**不是连接 ID** |
| 客户端正确做法 | `RESOURCE_HUB_CREATE_PATH_FROM_ID`（`Reshub.h`）→ `WdfIoTargetOpen` |
| `SpbTargetGetConnectionParameters` | ❌ **只有控制器驱动能用**（在 `EvtSpbTargetConnect` 回调里）；独立第三方客户端用不了 |
| `SpbTargetConnect` | ❌ 同上，需要只有控制器驱动能拿到的 `SPBTARGET` 句柄 |

**⇒ 结论：`hidi2c` 已经占用了那个外设的"唯一连接名额"。第二家打开必然失败。**

**★ 概念澄清**：
> "I²C 控制器不是 `hidi2c` 独占的" —— **这句本身没错**（控制器可以有并列客户端，不同外设各占一个连接）；
> **错的是推论** —— **同一个外设的连接，只能一家持有。**

## 2.3 第 3 层：设备固件 —— ❌ 主机侧根本没有"触发"这条命令

### 2.3.1 实测

> 🔴 **2026-10-03 撤销本小节依据**（见[登记表 §B4](00-矛盾与推翻登记表.md)）
> 当时环境是 **shell 版 Linux live USB（U 盘启动）**，**触控板驱动从未接管**。
> 这种环境下"指针动不动""震不震"**无法区分**「无驱动 ⇒ 固件走自治默认路径」与「驱动已接管但只是没上报」，
> 因此**无论观测到什么都不构成证据**。下表仅作现场留档。
>
> **本节结论改由 Windows 侧四条结构性证据支撑**（`Col02` `OutputReportByteLength=0` / Haptics 页无 `Manual Trigger (0x0E/0x21)` / `GET·SET_FEATURE` 全失败 / 设备栈无固件对象）—— 见《全书》§6.2。

~~**在 Linux live USB 里（触控板完全无驱动）：**~~

| 观察 | 含义 |
|---|---|
| ~~触控板**指针完全不能用**~~ | ~~主机**没有在跟触控板通信**~~ |
| ~~但**点按照样震动**~~ | ~~★ **震动完全不依赖主机**~~ |

⇒ **震动是模组内部自治产生的**（按压 → TF100A 测压力 → 阈值判定 → 驱动 LRA）。

⇒ **主机侧在描述符层就"发不出"触觉输出，这条不依赖任何 Linux 侧观察。**

⇒ **就算主机拿到 I²C 话语权，也还得有"让触控板震"的那条命令 —— 而原厂设计里没有。**

### 2.3.2 佐证：老线对厂商命令通道的穷举

- **`GoodixTpDxe`（BIOS 侧官方驱动）反汇编**：全部命令按字符串分类只有四类
  - 使能/禁止上报（`7863/7868Q enable|disable report`）
  - 读取基本信息（`pid` / `vid` / `sensorID` / `cfgVer` / `IC version` / `TF version`）
  - 固件更新（`update mode` / `erase` / `write flash` / `reload subFW`）
  - FMP/capsule 解析
  **没有任何"振动 / 触觉 / 力反馈"命令。**
- **整个 30.88 MB BIOS 固件里 `Haptic` / `haptic` 命中 0 次。**
- **TF100A 的 39 条命令全表覆盖，无马达入口。**

### 2.3.3 佐证：蓝莓项目的结论（外部一手）

蓝莓故意逆向了主机侧协议，结论：
> **他 869 字节的 HID 描述符里，`0x0E`（Haptics）usage page 出现 0 次。**
> **主机能做的只有"调参数"（强度、力度阈值、手势映射）；"何时震"完全由他的设备固件决定。**
> **主机没有"发送震动"的指令 —— 一条都没有。**

⇒ **与本机情况完全同构。**

# 第三部分 · 固件逆向线与 EC/ACPI 线

## 3.1 固件逆向线（`goodix-tool` 方向）

### 3.1.1 ❌ 已终结：「固件加密 / 找密钥」整条路线作废

| 曾经的结论 | 现状 |
|---|---|
| `TB14P_GT7868Q_*.BIN` 是加密固件、高熵区需密钥 | ❌ **它是 UEFI 胶囊**（`Class=Firmware`，`ClassGuid={f2e7dd72-...}`），Windows 交给 UEFI ESRT，**BIN 不解析它** |
| `K`（1024 B）是加扰密钥 | ❌ **是 Goodix 通用填充表**（`tpfw.bin` 里 10 个"完美均衡块"，`tpfw[0x1C00:0x2000] == rot_left(K,316)` 逐字节 0 误差，K 的 256 个旋转变体在 tpfw 命中 4619 处） |
| 固件区是密文 | ❌ **三重独立量结案**：真压缩器可压比 0.8797（随机 1.0004 / 真 Thumb 码 0.4719）· 条件熵低于随机 0.36 bit · lag1 自相关 2.94× ⇒ 弱相关的**结构化数据** |
| 「两个 agent 都说有加密」 | ❌ 根因 = **零阶熵 H0≈8.0 是非特异判据**（白化/压缩/加扰/密文/真随机**全都**给 ~8.0） |

⇒ **"别再找密钥了" —— 这是本项目最贵的教训之一。**

### 3.1.2 已确认的官方协议与数据

**官方 HID 协议（Goodix `gdix_hid_firmware_update`）**

| 命令 | 字节 | 含义 |
|---|---|---|
| `_I2C_DIRECT_RW` | `0x20` | 直接读写 |
| `_I2C_INDIRECT_READ` | `0x21` | 间接读 |
| Write 封装 | `[0E 20 00 00 05 00 addrH addrL lenH lenL]` | 写 |
| Read 封装 | `[0E 20 00 00 05 01 addrH addrL lenH lenL]` | 读 |
| 取回 | `GetReport(0x0e)` → `[.. .. .. pkgidx datalen data…]` | |

**地址常量**
```c
#define CFG_FLASH_ADDR    0x19000    // 与静态推的 0x08019000 一致
#define CFG_START_ADDR    0x96F8     // 明文 cfg 写入点
#define CMD_ADDR          0x4160
#define VER_ADDR          0x4014     // 读 32B，末 2B 校验和
#define BL_STATE_ADDR     0x5095     // 等 0xDD
#define FLASH_RESULT_ADDR 0x5096     // 等 0xAA
#define FLASH_BUFFER_ADDR 0xC000
#define RAM_BUFFER_SIZE   4096
```

**参数区布局**
| 偏移 | 长度 | 含义 |
|---|---|---|
| `0x0444` / `0x2444` / `0x3044` | 1 B | 标定/属性字节 |
| **`0x1800`** | **27 B** | ★ **触觉参数区** |
| **`0x3800`** | **8 B** | ★ **触觉参数区** |
| `0x2000` / `0x2C00` | 1092 B | 配置块 A / B |

**官方 cfg 握手（明文本通路）**
```
读 0x96F8 拿旧版本 → 写 cmd 0x80 → 等 CMD_ADDR == 0x82
→ 明文写 cfg 到 0x96F8 → 写 cmd 0x83 → 等 CMD_ADDR == 0x7F(或 0x7E 00 07)
→ 写 cmd 0x7D 结束 → 读 0x96F8 复核
```

**update flag 枚举**

### 3.2.3 曾被怀疑的名字已归因（本项目一次错误推断的完整纠正）

**`MLR1` / `MLR2` / `MOFD` / `MMCM` / `MBGS`** 一度被误读为 "LRA #1/#2 + 震动开关"。反编译源码给出真身：

```asl
OperationRegion (LA3M, SystemMemory, 0xFE0B0F00, 0xFF)
Field (LA3M, ByteAcc, Lock, Preserve)
{
    Offset (0xBD),
    MLR0, 8, MLR1, 8, MLR2, 8, MLR3, 8,      // 0xBD..0xC0
    Offset (0xD0),
    PL1V, 8, PL2V, 16, CTAU, 8, GTGP, 8, GPAB, 8,
    Offset (0xDE),
    MPL1, 1, MPL2, 1, MTAU, 1, MTGP, 1, MPAB, 1, , 10, MOFD, 1
}

Method (_Q47, 0) {
    Debug = "Q47 trigger"
    If (WMI5.DSIF == One) {
        If ((MLR1 > 0) && (MLR1 != WMI5.LPWR)) {
            WMI5.SDRF = ...
            If (MLR1 >= 0x82) { ... }        // 阈值 0x82
            WMI5.LPWR = MLR1
            Notify (WMI5, 0xD0)
        }
        If ((MLR2 > 0) && (MLR2 != WMI5.LSCN)) { WMI5.LSCN = MLR2; Notify(WMI5, 0xD1) }
    }
}
Method (_Q48, 0) { ... If (MMCM == Zero) { CPL1 = PL1V * 8; CPL2 = PL2V * 8 } ... }
```

**归因**：
- `MLR1`/`MLR2` **不是方法，是 EC RAM 的 8 位硬件寄存器**（`0xFE0B0F00 + 0xBD/0xBE`）
- `PL1V`/`PL2V`（**Intel PL1/PL2 功耗限制**）**紧邻** `MLR1`，且 `_Q48` 做 `PL1V * 8`
- `LPWR`/`LSCN`/`SDRF`/`DSIF`/`OVTP` 全是电源与散热语汇
- `MOFD` 是 `Offset(0xDE)` 的**单个 bit**，与 `MPL1/MPL2/MTAU/MTGP/MPAB` 同组
- `0x82` 阈值 = 经典电源/电池状态握手

⇒ **这是 EC → WMI 的功耗/热管理通知机制。与触觉无关。**

### 3.2.4 EC RAM 实测读取（本次新增能力）

**方法**：PawnIO **签名**模块 `LpcACPIEC.bin`（`ioctl_pio_read`/`ioctl_pio_write`，端口**仅允许 `0x62`/`0x66`**）
**协议**：ACPI 规范 `RD_EC` 握手（`WaitFlag(IBF,false)` → 写 `0x66=0x80` → 写 `0x62=offset` → `WaitFlag(OBF,true)` → 读 `0x62`）

**结果**：
```
读完 256 字节，失败 40 个（84% 可读，244/256 有效）
非 0xFF 偏移：214 / 256
0x12–0x17 : 温度块（70 00 34 29 .. 26 32 2F D0）
0x6D–0x70 : ASCII "2023"
0xBD/0xBE : 0x7A / 0x02
```

### 3.2.5 ❌ EC 差分实验：无触觉证据

**方法**：读基线 → 用户操作触控板 30 秒 → 连读 3 次快照 → 静置 10 秒再读（噪声对照）

**结果**：
```
[3] 交互期 25 个偏移"变化"
[4] 静置 10 秒后与基线相比: 93 个偏移不同   ← ★ 读数噪声大，方法学受限
[5] 关键偏移：
    EC[0xBD] base=0x7A  snapshots=0x7A 0x7A 0x7A   ← 静止
    EC[0xBE] base=0x02  snapshots=0x02 0x02 0x02   ← 静止
    EC[0xD0] base=0x00  snapshots=0x00 0x00 0x00   ← 静止
    EC[0xD1] base=0x00  snapshots=0x00 0x00 0x00   ← 静止
```

**唯一可信的变化**：`0x12–0x17` 温度块**单调下降**（`0x34→0x30`、`0x29→0x28`、`0x2F→0x2D`…）⇒ **时间漂移，不是触控引起。**

⇒ **没有证据支持"EC 管理触觉"。**

⚠️ **方法学说明**：静置后仍有 93 个偏移不一致，说明**读噪声大**（`--` 与实际值反复跳）。
⇒ 本次差分**只能作为"阴性旁证"，不足以作为强结论**。改进方向：与 Windows 自身的 ACPI EC 驱动协调、或用更严格的多数表决。

### 3.2.6 EC 访问能力的边界（工具层事实）

| 事实 | 说明 |
|---|---|
| Windows **没有** `IOCTL_ACPI_READ_EC` | 查本机 WDK `acpiioct.h` 确认：ACPI 只暴露 `EVAL_METHOD` / `ENUM_CHILDREN` / `GET_DEVICE_INFORMATION` / `GLOBAL_LOCK` 等（`IOCTL_ACPI_READ_EC` 是 **Linux** 的） |
| 固件未提供 EC 读取 ACPI 方法 | 全 ASL 扫描无此类方法 |
| ⇒ **Windows 上读 EC 内存必须有内核驱动** | 本机选择 PawnIO（**签名**，不受吊销名单影响） |

## 4.1 AW86927 的业界标准用法（一手资料）

**Fairphone 5 设备树 + Linux 主线驱动**（[补丁组](https://patchew.org/linux/20250806-aw86927-v1-0-23d8a6d0f2b2@fairphone.com/)）：

```dts
vibrator@5a {
    compatible = "awinic,aw86927";
    reg = <0x5a>;                                              /* 从地址 0x5A */
    interrupts-extended = <&tlmm 101 IRQ_TYPE_EDGE_FALLING>;
    reset-gpios = <&tlmm 100 GPIO_ACTIVE_LOW>;
};
```

**⇒ 标准形态：挂在 SoC 普通 I²C 上的从设备 + reset GPIO + 中断 GPIO。**

**★ 身份标识（一手）**
```c
#define AW86927_CHIPIDH (0x57)
#define AW86927_CHIPIDL (0x58)
#define AW86927_CHIPID  (0x9270)
```
⇒ **读 `0x57`(高)/`0x58`(低) == `0x92 0x70` ⇒ 确认是 AW86927。**

**★ 完整播放流程（`aw86927.c` 摘要）**
```
硬复位(reset 拉高1ms→释放→等8ms) → 软复位(0x00=0xAA,3ms) → 验身份(0x57/0x58)
→ 初始化(TMCFG 0x5B=0x7D 解锁 → ANACFG11/12/13/15/16, CONTCFG1/5/10/13,
          PWMCFG1/3/4, DETCFG2, PLAYCFG1 BST=8500mV → 锁定)
→ SRAM 初始化 + 下波形(BASEADDR 0x2D/0x2E=0x0800；RAMDATA 0x42 连写 头+数据)
→ ▶ 播放: 写 0x09 PLAYCFG4 = 0x01 (GO)
→ ■ 停止: 写 0x09 PLAYCFG4 = 0x02 (STOP)
```

**★ 参考波形**：驱动内置 106 字节 sine（`round(84*sin(x/16.25))`，双补码）

## 4.2 ❌ 与主机命令体系的不匹配（重要发现）

| AW86927 协议 | 本机主机命令体系 | 是否同源 |
|---|---|---|
| 寄存器空间 `0x00–0x80` | 触控板命令：私有封装 `[0E 20 ...]` + 地址 `0x1800/0x3800/0x96F8/0x4014/0x4160` | ❌ **完全不同** |
| 从地址 `0x5A` | 触控板从地址 `1` | ❌ |
| 播放 = 写 `0x09` = GO | 触觉参数 = `0x1800`(27B) / `0x3800`(8B) | ❌ **地址空间无交集** |

⇒ **"主机→触控 IC"和"触控 IC→AW86927"是两条完全独立的链路，协议毫无关系。**

⇒ **且没有任何证据表明触控 IC 会把主机写入的 `0x1800/0x3800` 转发给 AW86927。**

## 4.3 ❌ AW86927 不在 PCH SMBus 上（**强结论**）

**方法**：PawnIO 签名模块 `SmbusI801.bin`（`ioctl_smbus_xfer`，`in=[addr, rw, cmd, protocol]`）

**实测**：
```
[3] 控制器身份: type = "i801", IO base = 0xEFA0, PCI IDs = 0x382717AA7E228086
    → 0x8086:0x7E22 = Intel SMBus，确认是本机 PCH SMBus ✓
[4] 三种协议（Quick / Byte / ByteData）交叉扫描 0x03..0x77
    → 仅 1 个地址应答: 0x44
[5] 0x44 dump (reg 00-0F):
      00 00 00 03 00 00 00 00 00 24 49 00 04 01 10 26   其余全 00
[6] 0x5A / 0x5B: 无应答 (STATUS_NO_SUCH_DEVICE = 0x800701B1)
```

**为什么可信（关键）**：
1. ✅ **有阳性对照** —— `0x44` 应答，证明控制器工作、扫描方法有效
2. ✅ **用对了协议** —— `BYTE_DATA`（AW86927 读寄存器所需），不是 `BYTE`
3. ✅ 控制器身份经 `ioctl_identity` 确认为 `0x7E22`

⇒ **AW86927 不在这条 SMBus 上。**

## 4.4 ⚠️ 触控板那条 I²C 总线：无法安全探测

**触控板挂在 Intel Serial IO I²C（内核 `i2c-designware`）上。**

```
i2c-4  → i2c_designware.4: i2c_dw_handle_tx_abort: lost arbitration ×4
       → i2cdetect exited with irqs disabled → 内核崩溃
i2c-15 → 用户报告卡死
```

⇒ **对 `i2c-designware` 用 `i2cdetect -r` 快速探测会卡死/崩溃内核。**
⇒ **Linux 这条路也无法安全走完。**

## 4.5 ⚠️ Linux 实测观察汇总

```
i2c-0 … i2c-5     基本全空
i2c-5             0x44 出现（与 Windows 侧 PCH SMBus 的 0x44 一致）
i2c-0             0x28 / 0x51 显示 UU（驱动已占用，非空闲设备）
i2c-16 及以后      显卡相关（DDC/EDID）总线
⚠️ 有表格出现整片 50 51 52 … 5f 连续"应答" —— 属可疑回显，不作为证据
```

## 5.4 方法学问题（本项目反复踩的坑）

| # | 坑 | 教训 |
|---|---|---|
| 1 | **"二进制里看到一个像缩写的名字"当成证据** | `MLR1` 被误读成 "LRA #1"。**必须反编译到 `OperationRegion`/`Field`/调用点，看清邻居和值域** |
| 2 | **零阶熵 H0≈8.0 当作"加密"判据** | H0 是**非特异判据**（白化/压缩/加扰/密文/随机全给 ~8.0）。否定"密文"需 **≥3 个独立量 + 随机基线** |
| 3 | **用字节搜索验证 ARM imm32 常量** | `0x45670123` 从不以连续 4 字节出现（`movw`+`movt`）⇒ **会得出"不存在"的假否定**。必须 MOVW/MOVT 配对解码 |
| 4 | **只走 `DSDT`/`SSDT` 表键** | `SSD1`..`SSDS` 是**平级键** ⇒ 漏掉 30 张表 |
| 5 | **PowerShell 脚本给 v5.1 不带 BOM** | 中文按 GBK 解码、全角标点吃掉引号 ⇒ 语法崩。**脚本输出用纯 ASCII 最稳** |
| 6 | **没做阳性对照就下"读不到"的结论** | 第一次 SMBus 扫描无阳性对照 ⇒ 结论无效；第二次有 `0x44` 才可信 |
