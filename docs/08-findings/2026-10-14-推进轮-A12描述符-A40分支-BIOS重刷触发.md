## §1 A#12：HID 描述符里**没有** `cmd_register` / `data_register` 类字段（本项关闭）

### 1.1 问题

GATP（`goodix_advance_touch_platform`）的 `struct gatp_hid_desc` 含 `cmd_register` / `data_register`
⇒ 若本机描述符里也有同类字段，主机侧就能**自动取得寄存器地址**，不必依赖 cfg bin / DLL。

### 1.2 证据（全部来自本仓库既有归档）

| 集合 | 报表构成（`docs/07-hid/lab__GXTP5100-HID-usage-report.md`，基于 `HidP_GetValueCaps`） |
|---|---|
| Col01 / Col02 / Col03 | `Out = 0`（**没有任何 OUTPUT 报表**） |
| **Col04**（厂商集合 `0xFF00/0x0001`） | **唯一的 OUTPUT**：usage `0xFF00/0x0000..0x003E` + `0xFF00/0x0001`，**纯字节数组**，无地址/宽度字段 |
| 全体 feature 值字段 | `{0x0D/0x59, 0x0D/0x55, 0x0E/0x23, 0xFF00/0xC5(256B), 0xFF00/0xC4(4B), 0xFF00/0xC6(736B), 0xFF00/0xC7(66B)}` —— 全是 **blob**，没有"寄存器选择器"命名 |

### 1.3 结论

> **描述符层不存在 `cmd_register`/`data_register`。** 本机的"寄存器地址信封"是**报表载荷**：
> `0E 20 00 00 <len> 01 <addr16BE> <len16BE> <data>`（v1）/ `<addr32BE>`（v2）——
> 见 `docs/07-hid/lab__COL04-BOUNDARY.md` §11.1 / §11.2。
> **地址表本身**只存在于两处：(a) 驱动 DLL 的 `.text`（家族级共享表，§19.62/§19.64）；(b) 官方 cfg bin 的 `reg_info`（§19.59）。

**⇒ A#12 关闭（无剩余价值）**。

### 1.4 ★ 附带的一个可执行线索

`0xFF00/0xC4`（**Report ID 13，Count = 4 字节**）**从未被写过**（§20.11 #38 清单里已有它）。
4 字节正好可以装一个 **32 位地址或操作码**，且 DLL 命令表的表项正是 `{地址, 宽度, 期望值}` ⇒
建议在 A#38 的 feature 写探里**优先试 RID 13**（判据：写后是否出现寄存器读回/行为变化）。

## §2 A#40：`ICSelect` ↔ 分支键 ↔ 家族（本项**闭合**）

### 2.1 ① `ICSelect` 就是分支编号（三个 CAB 独立佐证）

三份厂商 CAB 的 INF（UTF-16LE）原文：

| CAB | `DriverVer` | `HKR,"tpupdate_7868q_driver","ICSelect",0x00010001,`**N** |
|---|---|---|
| `x_driver_e` | 11/28/2022, 0.5.4.0 | **3** |
| `x_ee49202f` | 02/17/2023, 0.7.4.1 | **1** |
| `x_108e1f62` | 03/13/2024, 11.7.0.2 | **5** |

而 DLL `x_108e1f62` 的分派键（字节级确认）是：
```
0x101F  83 F8 01   cmp eax, 1      0x1262  83 F8 02   cmp eax, 2  ← 本机 Yellowstone
0x14BA  83 F8 03   cmp eax, 3      0x1732  83 F8 04   cmp eax, 4
0x1A2E  83 F8 05   cmp eax, 5
```
`ICSelect` 的取值域 **1/3/5** 与分支键 **1..5** 完全同域 ⇒ **`ICSelect` = 分支编号**。

> ★ **推论（对项目有实际意义）**：本机 = **Yellowstone = 分支 2** ⇒ 它对应的 CAB 应当是 **`ICSelect=2`**。
> 而手上三份 CAB 是 **1 / 3 / 5** —— **没有一份是给本机的**。
> ⇒ 这就解释了"**为什么官方命令表只能靠反汇编拿**"：我们从未拿到本机家族的官方更新工具。

### 2.2 `ICSelect` 的读取路径（字符串级证据）

| 项 | 值 |
|---|---|
| `ICSelect` 字符串 | UTF-16 @ RVA **`0xE428`** |
| 引用它的代码 | **RVA `0x7FF8`–`0x8148`**（`lea rdx,[0xe428]` / `lea rcx,[0xe43c]`…）⇒ 注册表读取函数 |
| 消费点 | **RVA `0x1010`**：`mov ecx,[rip+d] → 0x18B00`（@`0x1019`）后 `cmp eax,1..5` |
| `[0x18B00]` 所在段 | `.data` 尾部（`vsize 0xCC0 > rawSize 0x400`）⇒ **BSS，静态全零** |
| ⚠️ 未闭合 | **`.text` 内没有任何直接写 `0x18B00` 的指令**（含 REX 前缀 / imm32 / byte 全形式扫描）⇒ 写入走间接寻址，需真正的反汇编器（capstone）才能定位 |

### 2.3 ② 分支 3/4/5 的家族归属（用官方源码常量做字节匹配）

| 分支 | 区间（RVA） | 命中的常量 | 判定 |
|---|---|---|---|
| **3** | `0x14C3-0x1732` | `0x10010` `0x10011` `0x14000`(flash) `0x10174`(cmd) `0x13B74` `0x1001E` | ★ **GTX9** —— 与官方 `gtx9_gtx9_update.cpp` 的地址集**逐项对上** |
| **4** | `0x1746-0x1A2E` | `0x10180`(cmd) `0x10016` `0x15EB4` `0x29400`(flash) | **未定** —— 手上 6 份官方源码里**没有任何一份含 `0x29400`/`0x15EB4`/`0x10016`** ⇒ 需 `berlin_a` 或其它新家族源码 |
| **5** | `0x1A42-0x1D87` | `0x10184` `0x10174`(cmd) `0x13D08` `0x49800`(flash) `0x1001E` | ★ **Marseille/Marsei** —— `0x10184` 与官方 `marsei_marsei_update.cpp` 命中；且 `x_108e1f62`（`ICSelect=5`）的 CAB 里正是 Marseille 的 cfg bin（B34） |

⇒ **「2024 版新增的三族」= GTX9 / 未定（Berlin 系？） / Marseille**；
⇒ 与主线 LKML「Register addresses are 16-bit on GTX8, **32-bit on Berlin**」一致（分支 3/4/5 全是 32 位空间）。

### 2.4 方法（免 capstone，任何人可复核）

1. 最小 PE 解析（DOS→PE→节表），取 `.text` 的 RVA/raw 映射；
2. 在**已知分支区间**内按 4 字节小端搜官方源码里的常量；
3. 对 `mov [rip+disp32], reg/imm` 全形式（含 REX 前缀）反解目标 RVA，定位对 `0x18B00`/`0x18B04` 的访问（§2.2 表）。
> 装了 `capstone` 后可直接用 `tools/analysis/lab__dll-family-tables.py` / `lab__dll-who-touches.py` 交叉复核。

## §3 B 部「前置」：BIOS 自动重刷触发条件（**阶段一：例程已定位，门控未定案**）

### 3.1 ★★★★ 重大发现一：`GoodixTpDxe` 里就是**官方刷写实现**，且**帧与项目红线逐字节一致**

函数 **RVA `0x45E0`**（内部循环 `0x4600`–`0x496E`，`ret` 在 `0x497A`；被 `0x4CD7` / `0x4D8B` 调用）：

```asm
0x4624  mov byte [rsp+0x40], 0x0E      ; ┐
0x4629  mov byte [rsp+0x41], 0x12      ; │ 帧 = 0E 12 00 00 06 …
0x462E  mov byte [rsp+0x42], 0         ; │ （与 RED-LINES 引的官方源 buf_load_flash[15] 一致）
0x4633  mov byte [rsp+0x43], 0         ; │
0x4638  mov byte [rsp+0x44], 6         ; ┘ ← 长度字段 = 6
0x4662  cmp dword [rsp+0x38], 3        ; 重试/页计数 ≤ 3
0x4667  jge 0x496E                    ; └ 退出
0x4674  cmp [rsp+0x28], eax            ; offset vs 总长 ⇒ 写完退出
0x468D  cmp eax, 0x1000                ; ★★★ 单块钳位 = 4096 B
0x4694  mov dword [rsp+0x50], 0x1000   ;     （= 项目 2026-10-12 实测的 unitlen 必须 4096）
```

> ★ **这是 `unitlen = 4096` 的【官方实现侧独立确认】** —— 项目是靠真机单变量对照（B30/§19.51）得出的，
> 现在在 BIOS 侧看到同一个 4096 钳位。

三帧同族（`0x49A1`–`0x49FE`）：

| 帧 | 字节（DXE 现场） | 与项目文档 |
|---|---|---|
| `0E 10 00 00 01 01` | `[+0x38]=0x0e [+0x39]=0x10 [+0x3c]=1 [+0x3d]=1` | 红线写作 `00 10` ⇒ ⚠️ **首字节不同** |
| `0E 11 00 00 01 01` | `[+0x40]=0x0e [+0x41]=0x11 [+0x44]=1 [+0x45]=1` | 同上 |
| `0E 13 00 00 01 01` | `[+0x48]=0x0e [+0x49]=0x13 [+0x4c]=1 [+0x4d]=1` | 一致 |

> ⚠️ **红线措辞需要精确化**：四条刷机命令的**命令码**是 `0x10/0x11/0x12/0x13`；**首字节随通道不同** ——
> UEFI DXE 用 **`0E`**（= Col04 的 Report ID），厂商 Windows/Linux 源码用 **`00`**。
> 复刻序列时若照抄首字节会打错通道。（建议作为红线 3 的补充注记。）

### 3.2 ★★★★ 重大发现二：DXE 里**同时存在 `0x1E000` 与 `0x19000`**（直接关联 B31）

调用者（`0x4D20`–`0x4DA0`）现场：

```asm
0x4D2B  call qword [rsp+0xe0]                     ; 某 Boot Service / 回调（ecx=0x4B）
0x4D60  call 0x44E0                                ; 预检查（返回 0 = 通过）
0x4D6E  xor eax, eax / cmp eax, 1 / je 0x4D7D      ; ← 本 build 里恒不跳
0x4D74  mov dword [rsp+0x34], 0x1E000             ; ★ 地址 A（此 build 不可达）
0x4D4D  mov dword [rsp+0x34], 0x19000             ; ★ 地址 B（本 build 实际走这条）
0x4D8B  call 0x45E0                                ; → 用该地址去刷
```

> **解释力**：`0x19000` 不是项目瞎猜的 —— 它是**从官方 UEFI 驱动里读到的字面量**；
> 而同一函数里另有 `0x1E000`（fwupd/gtx8 侧的值）。**两个常量并存**正是 B31「地址之争」的源头。
> ⇒ **B31 的纪律要补一句**：**同一驱动里可能同时存在多个候选地址，且由分支选择** —— 不能"看到一个就当成全部"。

### 3.3 门控线索（阶段一）

| 线索 | 位置 | 含义 |
|---|---|---|
| `cmp eax, 0xdd` / `jne` | `0x4Bxx` | 与 B38 的 `BL_STATE_ADDR` 轮询值 **`0xDD`** 完全一致 ⇒ **DXE 也在等 bootloader 状态** |
| `call 0x44E0` → `cmp eax,0` | `0x4D60` | 刷写前的一次**预检查**（返回 0 = 通过） |
| `call 0x45E0` 的两处调用 | `0x4CD7` / `0x4D8B` | 两条不同的刷写路径（块/整片？） |
| `mov ecx, 0x4B` + `call [rsp+0xe0]` | `0x4D2B` | 疑似 Boot Services 调用（**未定名**） |

### 3.4 ⚠️ 未闭合与后续（**必须诚实记录**）

1. **"要不要刷"的版本比较不在本 dump 可判**：`GoodixTpDxe` 与 `FmpDxe` 的 `*.asm.txt` 都是
   **无符号名、无字符串**的精简反汇编 ⇒ 无法定位 FMP 协议的 `GetImageInfo` / `CheckImage` 版本比较。
2. 需要的材料（**均不在仓库，需从本机固件卷取**）：
   · `GoodixTpDxe` 的 `.data` / `.rdata`（协议 GUID、版本结构体）；
   · `FmpDxe` 的 ESRT/`EFI_FIRMWARE_MANAGEMENT_PROTOCOL` 实现与版本比较代码；
   · 或带符号的复现环境（Ghidra + 完整 FFS 卷，GUID 可解）。
3. **可零风险先做的替代路径**（建议排进下一轮）：**从 LIVE 系统读 ESRT**（`Get-FirmwareInformation` / 注册表 `HKLM\SYSTEM\CurrentControlSet\Control\Firmware`）
   ⇒ 直接看 BIOS 为触控板声明的**当前版本 / 最低版本**，与 `0x96F8` 版本字段对照 ⇒ **这比反汇编更快给出触发判据**。
