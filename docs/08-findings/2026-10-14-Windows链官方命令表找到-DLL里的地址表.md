## §0 一句话

> **项目找了很久的「Windows 链官方命令表」，就在 `tpupdate_driver.dll` 的 `.text` 里 —— 它不是数据表，而是一串
> `mov dword ptr [全局], imm32` 初始化指令**（形如 `C7 05 <disp32> <imm32>`）。
> **解码出的值与「官方 cfg bin 的 `reg_info`」+「本机实测」三方一致**，
> **而且比 cfg bin 样本更全**：多出 `0x60CC`（gtx8 `CMD_ADDR`）、`0x5095`、`0x5096`、`0xC000`、三个 `0x8000` 段地址，以及一个哨兵 `0xAAAAFFE0`。

## §1 怎么找到的（可复现的三步）

1. **字符串定位**：`tpupdate_driver.dll` 含 `[Info] CHIP = 7868Q.`（RVA `0xE4BB`）、`[Info] 7868Q disable report` 等 ⇒ **DLL 实现了 7868Q 专属路径**
2. **没有直接 `lea/mov` 引用，也没有指针表** ⇒ 排除"字符串表"路线
3. **改用「值聚类」**：把已知的 `reg_info` 地址当 **u16 LE** 搜，看是否**聚在一起**
   ⇒ 三个 DLL 都在 **文件偏移 `0x748–0x754` 起**出现同一簇（`x_108e1f62` 是 `0x754`）
   ⇒ **256 B 窗口内落 5–6 个不同地址**（随机预期只有 ~1.8 次/地址）⇒ **判定为真表**

> ★ **方法要点**：`u16` 单点命中**没有意义**（116 KB 文件的随机期望 ≈ 1.8 次）。
> **必须做"聚类检验"** —— 真表会让多个地址彼此靠近。本脚本第一步的朴素搜索给了"命中"，
> 但如果就此宣称"找到表了"就是**过度解读**（`0x96F8` 只命中 1 次 = 噪声级）。

## §5b ★★★★★ 深入一层：**分派树 + 两张平行表**（本轮第二次推进）

## §5g ★★★★★★★ **厂商侧的帧组装代码** —— 完整帧格式 + v1/v2 之谜彻底解开

继续追 `+0x10C`（=`0x4160`）的**读取者**（用 `lab__dll-who-touches.py` 跑全，共 **351** 条命中），
找到调用链：**`DisableReport` 循环 → 分派器 `0x56F0` → 按 `icType` 跳两支发送函数**。

### ① `DisableReport` 的调用循环（`RVA 0x1E51`）

```asm
001E51: mov   edi, 3                       ; ★ 重发 3 次
001E60: movzx r9d, byte ptr [0x18C1E]      ; r9d = 长度
001E68: lea   r8,  [0x18C14]               ; r8  = 命令缓冲区指针
001E6F: mov   edx, dword ptr [0x18C10]     ; edx = ★ 命令寄存器地址（0x4160）
001E75: mov   rcx, r14                     ; rcx = connection 对象
001E7D: call  0x56F0                       ; 发送
001E82: mov   ecx, 0xa
001E89: call  [Sleep]                      ; 睡 10
001EA9: sub   rdi, 1 / jne 0x1E60          ; 循环 3 次
```
**⇒ 与官方 `DisableReport()` 的「连写 3 次」结构一致；延迟 10（ms）。**
**⇒ 顺带定了两个字段：`+0x10C` = 要写入的寄存器地址、`+0x114` 起的缓冲区 = 命令字节、`+0x11A` = 长度。**

### ② 分派器 `RVA 0x56F0`

```asm
mov edi, edx            ; edi = addr
mov ebx, r9d            ; ebx = len
mov edx, [rcx+0x18]     ; edx = icType（在 connection 对象 +0x18）
mov rsi, r8             ; rsi = 命令缓冲区指针
cmp edx, 1 / jne 0x574E ; icType==1 → 记日志后 jmp 0x52D0
cmp edx, 2 / jne 0x5793 ; icType==2 → 记日志后 jmp 0x54B0（★ 本机）
                        ; 否则返回 -1（0xFFFFFFFF）并记错
```

### ③ ★★★★ 两支发送函数 —— **帧格式完整解出**

#### `icType==1` → `RVA 0x52D0`（**proto v1**）

```asm
005343: mov word ptr [rsp+0x30], 0x200e      ; +0x30=0x0E  +0x31=0x20
005332: mov ecx, 0x37                        ; ★ 单块上限 = 0x37 = 55
005312: movzx esi, dx                        ; ★★ 地址只取 16 位
005353: mov byte ptr [rsp+0x37], sil         ; 地址低字节
00535B: seta  byte ptr [rsp+0x32]            ; cont 标志
005337: mov byte ptr [rsp+0x33], r15b        ; seq
00534C: mov byte ptr [rsp+0x35], bpl         ; 0x00
```

#### ★★★★★ `icType==2` → `RVA 0x54B0`（**proto v2 —— 本机族**）

```asm
005532: mov word ptr [rsp+0x30], 0x200e      ; +0x30=0x0E  +0x31=0x20
005521: mov ecx, 0x35                        ; ★ 单块上限 = 0x35 = 53
00554A: seta  byte ptr [rsp+0x32]            ; +0x32 = cont（还有后续块 ? 1 : 0）
005526: mov byte ptr [rsp+0x33], r15b        ; +0x33 = seq
005564: mov byte ptr [rsp+0x34], al          ; +0x34 = (len + 7) & 0xFF
00553B: mov byte ptr [rsp+0x35], bpl         ; +0x35 = 0x00
00556D: shr eax,0x18 / 005576: shr eax,0x10 / 00557F: shr eax,8 / 005542: sil
                                             ; +0x36..+0x39 = ★★ 地址【4 字节大端】
005588: shr eax,8 / 00555A: bl               ; +0x3a..+0x3b = 长度【2 字节大端】
005552: lea rcx, [rsp+0x3c]                  ; +0x3c 起 = data
005557: add rdx, r13                         ; 源 = 命令缓冲区 + 已发送偏移
```

### ★★★★★★ 结论：**两族的帧格式**

| 族 | 发送函数 | 完整帧 | 地址宽度 | 头部 | 单块上限 | 校验 |
|---|---|---|---|---|---|---|
| `icType==1`（表 A / `0x60CC`） | `0x52D0` | `0E 20 <cont> <seq> <len+5> 00 <addr16BE> <len16BE> <data>` | **16 位** | 10 B | **55** | 10+55 = **65** ✅ |
| **`icType==2`（★本机 / `0x4160`）** | **`0x54B0`** | `0E 20 <cont> <seq> <len+7> 00 <addr32BE> <len16BE> <data>` | **32 位** | 12 B | **53** | 12+53 = **65** ✅ |

**⇒ ⇒ 两个上限都恰好填满一个 65 字节 HID 报告 —— 自洽性极强。**

### ★★★★★ 「v1 / v2」之谜彻底解开（与项目既有结论逐值吻合）

| 来源 | 描述 | 对照 |
|---|---|---|
| **厂商 DLL `0x52D0`** | `len+5` + **16 位地址** + 单块 **55** | = 项目的 **proto v1** ✅ |
| **厂商 DLL `0x54B0`** | `len+7` + **32 位地址** + 单块 **53** | = 项目的 **proto v2** ✅ |
| 项目 §6.2 | 「v1：`0E 20 00 00 05 01 <addr16BE> <size16BE>`（10 B）；<br>v2：`0E 20 00 00 07 01 <addr32BE> <len16BE>`（12 B）」 | **逐字段吻合** ✅ |

### ★★★ 顺带：`0x0E 20` 的 `<cont>` 语义得到厂商侧确认

⇒ 项目 r13 第 1 轮的观察（`cont=1` 会互相覆盖）与 §19.40.2「每块自成一次完整写、`cont=0`」**方向不同**，

⚠️ **两者不矛盾的前提是"地址逐块递增"**：续传语义 + 递增地址 = 正确拼接；续传语义 + 同一地址 = 互相覆盖。
**⇒ 项目第 1 轮的失败正是"同一地址 + cont=1"，与厂商语义一致。**（这一条把 §19.40.2 的解释补全了）

### ② ★★★ 本轮从 DLL 得到的**关键负面结论**

**这份 DLL 从头到尾【只发一种 HID 帧】：`0E 20 …`（内存读写）。**

### ③ ★★★★ 为什么 A 面**不得盲扫**（结构性理由，不是谨慎）

| 理由 | 说明 |
|---|---|
| **类比事实** | A 面**已知有语义的 class 全在低位**：`0x10–0x13` = **切 patch / 启动更新 / 写 flash / 复位**（官方源码）⇒ **`0x1x` 段就是"危险区"** |
| **未知区的危险不可排除** | `0x38–0xFF` 里的任何值**都可能**落在同一族（如 `0x3x`/`0x4x` 是否是另一组 flash/bootloader 命令？**无从得知**） |
| **每次猜错的代价 = 一次掉电重启** | 2026-10-14 事故（`0x4160` 盲扫）已实测：未知命令会让 IC 进入**掉电才清的持久态**，`0E 13` + HID 启停都不够 |
| **规模不可接受** | A 面未测 ≈ **228** 个 class ⇒ 若平均每 N 个就要重启一次，**物理上不可行**（更别提这是用户日常在用的机器） |

**⇒ ⇒ 结论：「A 面盲扫」这条路**不是因为谨慎而被搁置，而是**因为代价结构不可接受而被结构性否决**。**
**⇒ 除非拿到"该 IC 的完整 HID 命令表"**（来源只有两处：① IC 自身固件 —— **不可反汇编**；② 官方工具 —— **已查，不含**），**否则 A 面不应再扫。**

| **E 面：cfg 触觉区（TAG `0x50`–`0x7A`）** | **低** | ✅ **唯一语义明确、可回滚（会话 RAM）的暴力面**。判据须客观（`vib_probe.py` 已就绪，待校准） |
| **D 面：只读** | 零 | ✅ **只读扫描没有风险** —— 可以先做一次**全域只读 dump**（把 32 KB 读个遍），看有没有"看起来像触觉控制寄存器"的字段；**只读不写** |
| **A 面：只读** | 零 | ⚠️ `0x0E <cls>` 的**读**形式（`0E 20` 的读）已覆盖；**其它 cls 的读形式未知** ⇒ 不宜假设"读安全" |
| ~~C 面~~ | — | 🔴 **作废** |

**⇒ 即：「暴力软件逆向控制」的现实上限 = `只读全景 dump` + `cfg 会话写入`（E 面）。**

### ⑤ 对目标的最终判定（诚实）

**「滑动震动」需要【设备自主触发的条件】被改写。** 而：

| 必要条件 | 状态 |
|---|---|
| 触发条件在 **cfg** 里 | ⚠️ **未证**（cfg 目前看是"参数层"，不是"事件层"）⇒ **E 面扫描是唯一还能验的可能** |
| 触发条件在 **触控 IC 固件** 里 | ❌ 不可反汇编 ⇒ 改不动 |
| 触发条件在 **TF100A 固件** 里 | ❌ TF100A **不驱动 LRA**（逐指令定案） |
| 主机**强制触发** | ❌ 缺 `0x0E/0x21 Manual Trigger`（规格层 + 实现层双重关闭） |

**⇒ 若 E 面扫完仍无"事件层"字段，则本机硬件上做不到「滑动震动」——而那时的结论是【穷尽后的】。**

### 方法论沉淀

| 教训 | 内容 |
|---|---|
| **① 找厂商地址表，要扫【指令立即数】，不是数据段** | 本表的形态是 `mov dword [global], imm32`，**数据段里一个都搜不到** |
| **② `u16` 单点命中 ≠ 证据** | 116 KB 文件里任一 u16 的随机期望 ≈ **1.8 次**；`0x96F8` 只命中 1 次 = **噪声级** ⇒ **必须做聚类检验**（256 B 窗口内 ≥3 个不同地址） |
| **③ 负结果也有用** | "字符串无 `lea/mov` 引用、无指针表"这个负结果，**直接把我从字符串表路线推到值聚类路线** |
| **④ 三版 diff 才是"分派机制"的证据** | 单看一份 DLL 会得出"表里有 `0x60CC`"这种**会误导**的结论（那其实是另一个型号的条目） |
