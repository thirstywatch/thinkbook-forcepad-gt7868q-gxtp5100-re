## §1 🔴 对上一轮（§19.55 / §19.56）的**两处更正**（先自我纠错）

### 1.1 更正一：「`sid0.bin` 是 5 个包的容器」→ **错**

| 我上轮写的 | 实情 |
|---|---|
| 「本机容器（`sid0.bin`，魔数 `PCB\0`）的 **5 个包**，读出各自 `reg_info.cfg_addr`/`command`」 | 🔴 **错。** `sid0.bin`（1302 B）的 `0x10` 处 `05 00 00 00` 是 **`rev`（u32LE）**，**不是 `pkg_num`**。<br>它是一份 **55 条 TLV 容器**，**格式早已在全书 §19.21.2 完整测绘过**（64 B 文件头 + TLV 区，`0x3B`=TLV 区长 1238、`0x3D`=条目数 55、`0x40` 起为 TLV）。 |
| 「读出各包 `cfg_addr`/`command`」 | 🔴 **该文件里没有任何地址表。** 实测：`0x4160` / `0x5095` / `0x5096` / `0x96F8` / `0x1E000` 以 LE16/BE16/LE32/BE32 在容器中**全部 0 命中**；55 条 TLV 的 TAG 是 `01…7A` 的**配置字段 ID**，不是寄存器地址。 |
| 「1084 B cfg 与容器同源」 | 🔴 **1084 B cfg 的首 32 B 在容器中【零命中】** ⇒ **两者不是同一个对象**（容器 = 文件侧 TLV，cfg = 芯片侧 27 袋序列化）。 |

**⇒ 我上轮把「`05 00 00 00` = 5」直接读成了 `pkg_num`，没有先查 §19.21.2 —— 这正是纪律 116「下结论前先读既有文档」的违例。**

### 1.2 更正二：「官方 7 步 cfg 会话流程本项目没做过」→ **错，第十三轮就做过**

| 我上轮暗示的 | 实情 |
|---|---|
| 「本项目从未执行官方 cfg 会话写入（`0x80→0x82→写→0x83→读→0x7D`）」 | 🔴 **错。** 全书 **§19.40**（第十三轮，2026-10-05）标题就是「**cfg 下发通道打通 —— 全项目首个"主机写入改变设备行为"**」。<br>脚本 `tools/hid/lab__r13_cfgupdate.py` / `lab__r13_2_stream.py`，第 46 行注释原文：`"""0x80 握手 → 写 → 0x83 → 读结果 → 0x7D"""`。<br>**而且连错误码都对上了**：`lab__r13_2_stream.py:78` 已经写了 `res[:3] == b'\x7e\x00\x07'` = 「与 flash 完全一致」。 |

### 1.3 更正三：`0x5095/0x5096` 的「待核」**作废**（已定案）

上一轮把它列为"待核"。**本轮查项目自己的脚本就知道答案了**（`lab__r32_official_seq.py:52-55`）：

| 地址 | 项目定名 | 用途 | 与官方对应 |
|---|---|---|---|
| `0x4160` | `CMD_ADDR` | 写 5 字节命令 / 读命令应答 | ✅ **就是官方 `dev->reg.command`（`command_reg`）** |
| `0x5095` | `BL_STATE_ADDR` | 轮询 `== 0xDD` 等 bootloader | 官方 `HW_REG_ISP_RUN_FLAG (0x6006)` 的同类（**地址不同**） |
| `0x5096` | `FLASH_RESULT_ADDR` | 轮询 `== 0xAA` 等 flash 块写入结果 | 官方 flash 层结果寄存器 |
| `0xC000` | `FLASH_BUFFER_ADDR` | flash 写缓冲 | ✅ 官方 `HW_REG_ISP_ADDR = 0xC000`（**精确对应**） |
| `0x96F8` | cfg 读窗口 | cfg 落点 | ✅ **官方 `cfg_addr` 角色**（YS 头 27/27 校验通过已证） |

**⇒ 所以"与官方 `{0x7E,0x7F}` 不符"这个疑问本身就是【伪命题】：**
- 官方 `{0x7E,0x7F}` 是 **cfg 会话流程** 在 **`command_reg`（= `0x4160`）** 上、**读 3 B** 的结果；
- 而 `0x5095/0x5096` 服务的是 **flash/ISP 流程**（`0E 10 / 0E 11 / 0E 12 / 0E 13`）；
- **两条流程、两个寄存器、两种宽度。** 拿它们互比是"苹果比橘子"。
- 并且 —— **项目确实在 `0x4160` 上读到了 `0x7E`/`0x7F`**（`lab__r13_2_stream.py:74`：`if d and d[0] in (0x7E, 0x7F)`）**⇒ 根本不存在矛盾。**

## §2 ★★★★★ 真正的收获：官方 cfg 回复码**全表**（首次拿到）

`gtx8drv_goodix_ts_i2c.c:83-88`：

```c
enum TS_SEND_CFG_REPLY {
	TS_CFG_REPLY_PKGS_ERR   = 0x01,
	TS_CFG_REPLY_CHKSUM_ERR = 0x02,
	TS_CFG_REPLY_DATA_ERR   = 0x03,
	TS_CFG_REPLY_DATA_EQU   = 0x07,
};
```

`gtx8drv_goodix_ts_i2c.c:930-937`（读 3 B 之后的判读逻辑）：

```c
if (buf[0] == TS_CMD_CFG_ERR) {               /* 0x7E */
	if (buf[2] != TS_CFG_REPLY_DATA_EQU)   /* 0x07 */
		ts_err("failed send cfg");
	else
		ts_info("config data equal with flash");
	r = -EINVAL;                          /* ★ 无论哪个子码，0x7E 一律判失败 */
	goto exit;
}
```

### 2.1 完整语义表（**buf[0] = 主码，buf[2] = 子码**）

| `buf[0]` | `buf[2]` | 官方符号 | 含义 | 官方判读 |
|---:|---:|---|---|---|
| `0x7F` | — | **`TS_CMD_CFG_OK`** | 配置被接受 | ✅ **成功** |
| `0x7E` | `0x01` | `TS_CFG_REPLY_PKGS_ERR` | **袋/包错误** | 🔴 失败 |
| `0x7E` | `0x02` | **`TS_CFG_REPLY_CHKSUM_ERR`** | **校验和错误** | 🔴 **失败** |
| `0x7E` | `0x03` | `TS_CFG_REPLY_DATA_ERR` | 数据错误 | 🔴 失败 |
| `0x7E` | `0x07` | `TS_CFG_REPLY_DATA_EQU` | 与 flash 完全一致 | 🔴 失败（但日志特判为"一致"） |

> ★ 同类还有 §19.40 已用的 `TS_CMD_REG_READY = 0xFF`、`COMMAND_SEND_CFG_PREPARE_OK = 0x82`。

### 2.2 🔴 由此更正一个**既有结论**

全书 **§19.40.4** 的表把 `7E 00 02` 读作「✅ **有差异且已应用** —— **不是失败**」。

**官方口径：`0x02` = `TS_CFG_REPLY_CHKSUM_ERR`（校验和错误），且 `buf[0]=0x7E` 一律 `-EINVAL` ⇒ 是【失败】。**

⇒ **§19.40.4 里 `7E 00 07` 那一行是对的（DATA_EQU，与项目理解一致）；`7E 00 02` 那一行是错的。**
⇒ 连带 **纪律 108 的前提**（"写入被接受（`7E 00 02`）只证明固件在会话期内接收并暂存了这份配置"）**必须更正** —— 见 §3。

## §3 ★★★★★ 机械确证：`+0x115` 落在 **`bag_id=6`** 袋内

### 3.1 定位（纯离线）

用 `tools/hid/gdix_cfg_tool.py bags` 建的 27 袋表：

```
+0x115 = 277  落在 bag_id=6   袋范围 0x10D..0x11B   袋内偏移 +0x8
袋内容 = 06 0A 10 36 08 64 00 5A 00 78 05 05 01 9E
                                        ↑↑↑↑↑↑↑↑
        [bag_id=6][len=10][── data ──][校验尾 01 9E]
原始袋校验 ys_ck = 0x0   ✅ 合法
```

### 3.2 复现 r13 的实验（只改 `+0x115..0x116` = u16BE 120 → 240，**不重算袋尾**）

```
改后袋内容 = 06 0A 10 36 08 64 00 5A 00 F0 05 05 01 9E
                                                    ↑↑↑↑↑ 尾字节未动
改后袋校验 ys_ck = 0x78  ❌ 非 0 ⇒ 校验和错误
头校验      = 0x0       ✅（改的是袋内数据，头部不受影响）
```

**⇒ r13 当时拿到的 `7E 00 02` = `TS_CFG_REPLY_CHKSUM_ERR` —— 完全解释了。**

### 3.3 用合法改法重来（重算袋尾）

```
用 gdix_cfg_tool.py setbyte <cfg> 116 F0 out.bin
  → 重算 bag_id=6 校验尾：01 9E → 02 16   （0x19E − 0x78 + 0xF0 = 0x216 ✓）
  → 27/27 袋全部 ck = 0   ✅ 结构合法
```

## §6 ★★ 正面确认：项目用的命令帧**与官方逐字段相同**

`gtx8drv_goodix_ts_i2c.c:629-652`（`goodix_cmd_init`，YS 分支）：

```c
if (dev->ic_type == IC_TYPE_YELLOWSTONE) {
	ts_cmd->length = 5;
	ts_cmd->cmds[0] = cmds;                              /* 命令 */
	ts_cmd->cmds[1] = (cmd_data >> 8) & 0xFF;            /* 数据高 */
	ts_cmd->cmds[2] = cmd_data & 0xFF;                   /* 数据低 */
	checksum = ts_cmd->cmds[0] + ts_cmd->cmds[1] + ts_cmd->cmds[2];
	ts_cmd->cmds[3] = (checksum >> 8) & 0xFF;
	ts_cmd->cmds[4] = checksum & 0xFF;
}
```

| | 命令 | 数据高 | 数据低 | 校验高 | 校验低 |
|---|---|---|---|---|---|
| 官方 | `cmds[0]` | `cmds[1]` | `cmds[2]` | `cmds[3]` | `cmds[4]` |
| 项目（`lab__r13_2_stream.py:55`） | `0x33` | `0` | `0` | `0` | `0x33` |

**⇒ 5 字节、`{cmd, dataHi, dataLo, sumHi, sumLo}`、校验 = 前三字节之和 —— 完全一致。**
**⇒ 侧面证实：本机 IC 属 `IC_TYPE_YELLOWSTONE`（`0x60CC`/`0x60DC` 那套不是本机的 `command`/`cfg`）。**

## §7 「两套地址集」的最终裁决

| 角色 | 本机实测值 | 证据 |
|---|---|---|
| **`command_reg`** | **`0x4160`** | ① 5 字节帧与官方 YS **逐字段相同**；② 常态读回 `0xFF` = `TS_CMD_REG_READY`；③ `0x80` 后回 `0x82` = `SEND_CFG_PREPARE_OK`；④ `0x83` 后回 `7E/7F` |
| **`cfg_addr`** | **`0x96F8`** | 读回内容 = 合法 YS cfg 头（`22 01 1B 00 3E`，27/27 袋校验通过，末端 = 1084） |
| **flash cfg 地址** | **`0x1E000`** | 4 个独立来源（fwupd / gtx8 源码 / 实机 / 容器 idx6）+ 实机验证 |
| **`0x60CC` / `0x60DC`** | **不适用本机** | 官方 gtx8 驱动里有此宏，但本机读 `0x60DC` 得到 `BB 39 0A E8`（**不是版本号**）⇒ 本机虽然命令帧是 YS 格式，但**地址按本机映射** |

**⇒ 结论：「两套地址集」不是矛盾，是【同一家族在不同实例上的不同映射】。本机映射已由行为证据锁定。**

## §8 纪律

| 条 | 内容 |
|---|---|
| **108（前提更正）** | 旧前提「写入被接受（`7E 00 02`）」**作废**。`0x02` = `TS_CFG_REPLY_CHKSUM_ERR` = **失败**。<br>**新第 108 条**：「通道有效」≠「参数有效」。且**只有 `buf[0] == 0x7F`（`TS_CMD_CFG_OK`）才算成功**；`0x7E + 任何子码` 都是失败。 |

| **150（新增）** | **在把任何「失败」写进结论之前，先问一句：「这个失败有没有【厂商定义的名字】？」**<br>本项目把 `7E 00 02` 当成"已应用"、把 `PKGS_ERR` 当成"不可知黑箱"，各错了 8 天和 1 天 —— 而官方源码里两个码都有名字。<br>**⇒ 遇到任何错误码/状态码，先去官方源码里搜它的枚举定义，再下结论。** |
