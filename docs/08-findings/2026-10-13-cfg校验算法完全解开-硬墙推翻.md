## §1 决定性证据：官方校验算法

### 1.1 原始代码（`goodix_ts_core.h:568-587`）

```c
/* cal u8 data checksum */
static inline u8 checksum_u8(u8 *data, u32 size)
{
	u8 checksum = 0;
	u32 i;
	for (i = 0; i < size; i++)
		checksum += data[i];
	return checksum;
}

/* cal u8 data checksum for yellowston */
static inline u16 checksum_u8_ys(u8 *data, u32 size)
{
	u16 checksum = 0;
	u32 i;
	for (i = 0; i < size - 2; i++)
		checksum += data[i];
	return checksum - (data[size - 2] << 8 | data[size - 1]);
}
```

### 1.2 官方原文注释（两处，互相印证）

| 位置 | 原文 |
|---|---|
| `goodix_gtx8_update.c:645` | `* checksum rule: sum of data in one format is equal to zero` |
| `goodix_ts_i2c.c:970-990`（`goodix_check_cfg_valid`，驱动内被注释掉但保留） | `checksum = 0; for (i = 0; i < TS_CFG_HEAD_LEN; i++) checksum += cfg[i]; if (checksum != 0) { ts_err("cfg head checksum ERROR..."); }` |

### 1.3 规则总结

| 家族 | 规则 | 合法条件 |
|---|---|---|
| **NOR** | `checksum_u8(data, n)` | `sum(data[0..n-1]) & 0xFF == 0` |
| **YS（Yellowstone）** | `checksum_u8_ys(data, n)` | `sum(data[0..n-3]) == BE16(data[n-2..n-1])` |

> ⚠️ **注意 YS 是 16 位大端校验尾，占 2 字节** —— 这是本机家族的格式。
> 本项目此前把 `cfg[+0x4]` 当成"1 字节校验和"（`+0x4 = sum(前 3 B) & 0xFF`）**是巧合成立的**（因为 `cfg[0x3] == 0x00`，16 位 BE 的高字节恰为 0）。

## §2 本机 cfg 的完整结构（实测，1084 B）

### 2.1 头部（5 字节）—— 官方 `TS_CFG_HEAD_LEN_YS = 5`

| 偏移 | 字段 | 本机实测 | 官方依据 |
|---|---|---|---|
| `+0x0` | **`cfg_version`** | `0x22` | `goodix_ts_i2c.c:1085` `ts_info("config_version:%u, vub_bags:%u", buf[0], sub_bags)` |
| `+0x1` | 固定/保留 | `0x01` | 实测恒为 `0x01` |
| `+0x2` | **`bag_num`（袋数量）** | `0x1B` = **27** | `TS_CFG_BAG_NUM_INDEX = 2`（`goodix_ts_i2c.c:70`） |
| `+0x3..0x4` | **u16 BE 校验和** = `sum(head[0..2])` | `00 3E` = `0x3E` | `checksum_u8_ys(buf, 5) == 0` |

**验算**：`sum(0x22, 0x01, 0x1B) = 0x3E`; `BE16(0x00,0x3E) = 0x3E`; 差 = **0** ✅

🔴 **结论：`cfg[+0x2]` 是 `bag_num`，不是「版本字节」。真正的版本字节是 `cfg[+0x0]`。**

### 2.2 袋链（自 `off = 5` 起）—— 官方 `TS_CFG_HEAD_LEN_YS = 5` 即袋起始

每袋结构：`{ u8 bag_id, u8 data_len, data[data_len], u16 BE checksum }`，**总长 = `data_len + 4`**

官方走法（`goodix_read_config_ys`，`goodix_ts_i2c.c:1074-1105`）：
```c
offset = TS_CFG_HEAD_LEN_YS;              // = 5
sub_bags = buf[TS_CFG_BAG_NUM_INDEX];      // = buf[2]
for (i = 0; i < sub_bags; i++) {
    goodix_i2c_read(dev, cfg_addr + offset,      buf + offset,     2);           // 袋头 2 B
    subbag_len = buf[offset + 1];                                                 // data_len
    goodix_i2c_read(dev, cfg_addr + offset + 2,  buf + offset + 2, subbag_len + 2); // 数据 + 校验尾
    checksum = checksum_u8_ys(buf + offset, subbag_len + 4);
    if (checksum) { /* 出错 */ }
    offset += subbag_len + 4;
}
ret = offset;                              // ★ 返回配置总长
```

## §4 「硬墙」的机械复现（不需要设备）

### 4.1 当年到底改了什么

对比 `2026-10-12-12-34-02/_cfg_ver1C.bin` 与 `lab__cfg_backup_1791782094.bin`：

```
文件长度均 = 1084 B
不同字节位置：仅 ['0x2', '0x4']
  +0x2: 0x1B -> 0x1C     ← 被误当作「版本字节」
  +0x4: 0x3E -> 0x3F     ← 配套修的头校验（这一步是对的）
```

### 4.2 仿真结果

| 版本 | `bag_num` | 头校验 | 袋走过 | 结果 |
|---|---:|---:|---:|---|
| 原样 | 27 | 0 ✅ | 27/27 | `ALL_OK` → **IC 接受** |
| `_cfg_ver1C.bin` | **28** | 0 ✅ | 27，**第 28 袋 `off=0x43C` 越界** | `OVERFLOW_HEAD` → **IC 拒绝** |

**失败点精确定位**：`cfg` 只有 1084 B（27 袋刚好用尽），`bag_num` 改成 28 后，IC 去读第 28 袋的袋头时 `off = 0x43C` **已越界**（文件长也是 `0x43C`）。

### 4.3 官方错误码（`goodix_ts_i2c.c:77-82`）

```c
enum TS_SEND_CFG_REPLY {
	TS_CFG_REPLY_PKGS_ERR   = 0x01,   // ← 本次命中的就是这个
	TS_CFG_REPLY_CHKSUM_ERR = 0x02,
	TS_CFG_REPLY_DATA_ERR   = 0x03,
	TS_CFG_REPLY_DATA_EQU   = 0x07,
};
```

⇒ **IC 的拒绝是【完全有据可查的袋链长度校验】**，不是不可知的黑箱。

### 6.2 实测结果

| 操作 | 输出头 | 判定 |
|---|---|---|
| 原文件 | `22 01 1B 00 3E` | ✅ 头 ck=0 · 27/27 袋 ck=0 |

### 6.3 合法改写四原则（新）

1. **不动 `cfg[+0x2]`**（`bag_num`）；要改版本就改 `cfg[+0x0]`
2. 改完头部，重算 `cfg[+0x3..+0x4] = BE16(sum(cfg[0..2]))`
3. 改任意数据字节，重算**该字节所在袋**末尾 2 字节，使 `sum(bag[:-2]) == BE16(bag[-2:])`
4. **总长必须仍是 1084 B**（27 袋恰好用尽；不增减袋）

## §8 ★★ 官方 cfg 写入【完整 7 步】流程（本项目应逐条对照）

来源 `goodix_ts_i2c.c:847-935`（`_do_goodix_send_config`）：

```
1. 轮询 command_reg 直到 == 0xFF (TS_CMD_REG_READY)
2. 发命令 COMMAND_START_SEND_CFG = 0x80
3. 轮询 command_reg 直到 == 0x82 (COMMAND_SEND_CFG_PREPARE_OK)
4. goodix_i2c_write(cfg_reg, config->data, config->length)   ← 整块一次写
5. 发命令 COMMAND_END_SEND_CFG = 0x83
6. (仅 YELLOWSTONE) 读 command_reg 3 B，等 buf[0] ∈ {0x7E ERR, 0x7F OK}
7. (仅 YELLOWSTONE) 发命令 COMMAND_END_SEND_CFG_YS = 0x7D  ← 收尾
```

**命令表（`goodix_ts_i2c.c:56-66`）**：

| 命令 | 值 |
|---|---|
| `COMMAND_SLEEP` | `0x05` |
| `COMMAND_START_SEND_CFG` | `0x80` |
| `COMMAND_SEND_SMALL_CFG` | `0x81` |
| `COMMAND_SEND_CFG_PREPARE_OK` | `0x82` |
| `COMMAND_END_SEND_CFG` | `0x83` |
| `COMMAND_READ_CFG_PREPARE_OK` | `0x85` |
| `COMMAND_START_READ_CFG` | `0x86` |
| `COMMAND_END_SEND_CFG_YS` | `0x7D` |
| `COMMAND_CLOSE_HID` | `0xAA` |
| `TS_CMD_REG_READY` | `0xFF` |
| `TS_CMD_CFG_OK` | `0x7F` |
| `TS_CMD_CFG_ERR` | `0x7E` |

> ★ 注意 `COMMAND_CLOSE_HID = 0xAA` —— 本项目长期把 `0xAA` 当"成功"码，
> 而官方语境里 **`0xAA` 是一条【关 HID】命令值**，不是成功码。这与 B34 记录的「跨家族借用」一致。

## §9 官方 `goodix_cfg_pkg_reg_info`：那张「官方命令表」的真身

`goodix_cfg_bin.h` —— **cfg bin 文件里【内嵌】着一张"寄存器地址表"**，每个器件实例的地址在此给出：

```c
struct goodix_cfg_pkg_reg { u16 addr; u8 reserved1; u8 reserved2; };  // 4 B

struct goodix_cfg_pkg_reg_info {
	struct goodix_cfg_pkg_reg cfg_send_flag;
	struct goodix_cfg_pkg_reg version_base;
	struct goodix_cfg_pkg_reg pid;
	struct goodix_cfg_pkg_reg vid;
	struct goodix_cfg_pkg_reg sensor_id;
	struct goodix_cfg_pkg_reg fw_mask;
	struct goodix_cfg_pkg_reg fw_status;
	struct goodix_cfg_pkg_reg cfg_addr;     // ★ dev->reg.cfg_addr 的来源
	struct goodix_cfg_pkg_reg esd;
	struct goodix_cfg_pkg_reg command;      // ★ command_reg
	struct goodix_cfg_pkg_reg coor;
	struct goodix_cfg_pkg_reg gesture;
	struct goodix_cfg_pkg_reg fw_request;
	struct goodix_cfg_pkg_reg proximity;
	u8 reserved[9];
};
```

`goodix_cfg_bin.c:257`：`ts_dev->reg.cfg_addr = cfg_pkg->reg_info.cfg_addr.addr;`

⇒ **★ `cfg_addr` 与 `command_reg` 不是硬编码常量，是【从 cfg bin 文件里读出来的】**。
⇒ 这解释了为什么本机实测的地址集是"混合集"：**它取决于用哪份 cfg bin**。
⇒ **【待办】** 解析本机容器（`sid0.bin` 魔数 `PCB\0`）的 5 个包，读出各自的 `reg_info.cfg_addr/command`，即可**直接得到本机应该用的地址**（= §20.11 A-6 第 ④ 项的可执行化）。

### 9.1 官方 cfg bin 容器头（Linux 驱动侧）

```c
struct goodix_cfg_bin_head {
	u32 bin_len;                    // LE
	u8  checksum;                   // = sum(bin_data[5..bin_len-1]) & 0xFF
	u8  bin_version[4];
	u8  pkg_num;
	/* + TS_CFG_BIN_HEAD_RESERVED_LEN = 6 字节保留 */
};   // 共 11 B
```
校验（`goodix_cfg_bin.c:44-52`）：`checksum = sum(bin_data[5..end]) & 0xFF`，须 `== head.checksum`。

### 9.2 ⚠️ 但官方 CAB 里的 `.cfg` 是【十六进制文本】

`x_108e1f62/tpcfgsid0.cfg` 开头是 `307835302C307834332C...` = 字面文本 `"0x50,0x43,0x42,0x00,..."`。
