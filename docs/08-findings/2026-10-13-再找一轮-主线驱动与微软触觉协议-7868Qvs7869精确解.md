## §1 ★★★★★ 主线 `goodix_gtx8` 驱动（已归档 6 文件）

来源：lore-kernel `phone-devel/20260228-gtx8-v2-*@mainlining.org`（**v2，2026-02-28**；作者 Aelin Reidel）。
**未合入主线**（`torvalds/linux` master 上 `goodix_gtx8.c` 仍 404；`linux-next` 同样 404）。

### 1.1 ★★★★★ 它独立确认了 **YS 校验算法**

```c
static bool goodix_gtx8_checksum_valid_normandy(const u8 *data, int size) {
	u8 cal_checksum = 0;
	for (i = 0; i < size; i++) cal_checksum += data[i];
	return cal_checksum == 0;                                   /* NOR: sum == 0 */
}
static bool goodix_gtx8_checksum_valid_yellowstone(const u8 *data, int size) {
	u16 cal_checksum = 0;
	for (i = 0; i < size - GOODIX_GTX8_CHECKSUM_SIZE; i++) cal_checksum += data[i];
	r_checksum = get_unaligned_be16(&data[i]);
	return cal_checksum == r_checksum;                          /* YS: sum(前 n-2) == BE16(末 2) */
}
```
**⇒ 与本项目从官方 vendor 驱动反推出的算法【逐字一致】**（§19.56）。**这是第二条独立实现。**

### 1.2 ★★★★ Yellowstone 地址：**三方一致**

```c
#define GOODIX_GTX8_FW_VERSION_ADDR_YELLOWSTONE   0x4022
#define GOODIX_GTX8_TOUCH_DATA_ADDR_YELLOWSTONE   0x4180
#define GOODIX_GTX8_FW_VERSION_ADDR_NORMANDY      0x4535
#define GOODIX_GTX8_TOUCH_DATA_ADDR_NORMANDY      0x4100
```
| 地址 | 官方 cfg bin `reg_info` | 主线驱动 | **本机实测** |
|---|---|---|---|
| `0x4022` | `pid` | YS fw-version/product-id | ✅ `"7869"` |
| `0x4180` | `coor`/`gesture`/`fw_request` | YS touch-data | ✅ `40 01 01 00` |

### 1.3 ★★★★ `product_id` 结构 —— 解释了本机读到的 `"7869"`

```c
struct goodix_gtx8_fw_version {
	char product_id[4];   /* "4 digits IC number" */
	u8 __unknown[4];
	u8 fw_version[4];
};
```
**本机 `0x4022` 起 12 B = `37 38 36 39 | 00 00 00 00 | 1C 02 03 05`** ⇒ 与结构体**逐字段吻合**：
`product_id="7869"` · `__unknown=00×4` · **`fw_version = 1C.02.03.05`**

### 1.4 ★★ 其它独立印证
- `struct goodix_gtx8_header_yellowstone` = **8 字节** ⇒ 与官方 vendor 驱动的 **`IRQ_HEAD_LEN_YS = 8`** 一致。
- LKML 原文（外部独立陈述）：**「checksum method differs yet again」**·**「Normandy → Yellowstone → Berlin」**·**「Register addresses are 16-bit on GTX8 and 32-bit on Berlin」**。
- ⚠️ **该驱动无 cfg/config 写入、无触觉、无 force** ⇒ **不能用于本项目的目标**，只作交叉验证。

## §2 ★★★★★ 微软官方《Input Device Haptics Implementation Guide》（已归档）

### 2.1 ★★★★ 它**直接解释了**本项目的一个长期困惑

微软原文（Haptic Intensity Feature Report 段）：

> 「…must define a SimpleHapticsController logical child collection (Page `0x0E`, Usage `0x01`) … containing the **Haptic Intensity** usage (**Page `0x0E`, Usage `0x23`**) as a feature report …
> **This child collection must NOT contain the Auto Trigger (Page `0x0E`, Usage `0x20`) or Manual Trigger (Page `0x0E`, Usage `0x21`) usages.**
> **It must be separate from the SimpleHapticsController child collection used for host-initiated haptic feedback (if supported).**」

**⇒ 本机 Col04 只暴露 `0x0E/0x23`，而没有 `0x0E/0x21` —— 这不是"漏做"，而是【微软规范允许且明确定义的一种配置】：**
**厂商选择了「仅设备自主触发（device-initiated only）」+「主机可调强度」的合规组合。**
⇒ **本项目的判决（§19.30 / B7「设备侧无接收分支」）得到官方规格层面的解释；不是缺陷、不是我们没找到。**

### 2.2 ★★★★★ **主机侧触觉**的完整官方要求（= 若要"主机发起滑动震"必须有的东西）

| 组件 | Page/Usage | 说明 |
|---|---|---|
| SimpleHapticsController 集合 | **`0x0E` / `0x01`** | 必须是 PTP 顶层集合的**子集合** |
| **Waveform Information Feature Report** | 两个子集合：**Waveform List** + **Duration List**，用 **Ordinal page `0x0A` 的 usage range** | 主机用它**查询支持的波形与时长（毫秒）**；逻辑下限必须 0 |
| **Manual Trigger Output Report** | **`Manual Trigger` = `0x0E` / `0x21`（Mandatory）** + `Intensity 0x0E/0x22` + Repeat Count + Retrigger Period + Waveform Cutoff Time | 主机用它**主动触发波形** |

**⇒ 本机缺的正是【这两个 report 及其所属的第二个子集合】。**

### 2.3 ★★★★★ 官方波形表（含**与"边缘滑动"直接对应**的条目）

| 波形 ID | 名称 | 官方描述 | 触控板 |
|---|---|---|---|
| `0x1001` | None | 空操作 | 必需 |
| `0x1002` | Stop | 停止正在播放的波形 | 必需 |
| `0x1008` | Hover | 「**悬停状态的轻脉冲，预示即将发生的动作**」 | 必需 |
| **`0x1012`** | **Collide** | 「**表示到达【边界或极限】的软脉冲**」 | 必需 |
| **`0x1013`** | **Align** | 「**对象吸附到对齐参考线时的锐脉冲**」 | 必需 |
| **`0x1014`** | **Step** | 「**离散变化的实感脉冲（如逐级步进）**」 | 必需 |
| **`0x1015`** | **Grow** | 「**传达运动/过渡/系统活动的动态脉冲**」 | 必需 |
| `0x1003` | Click | 内容点击 | **触控板【禁止】支持**（会与按键触觉混淆） |
| `0x1006` / `0x1007` | Press / Release | 按下 / 抬起 | 可选（应与设备自主触觉一致） |
| `0x1009` / `0x100A` | Success / Error | 成功 / 失败 | 触控板可选 |
| `0x1004 0x1005 0x100B–0x1011` | Buzz/Rumble/Ink/… | **连续波形一律不得支持**（部分仅限笔） | 禁止 |

**⇒ ★★★★★ `Collide 0x1012`（到达边界/极限）就是「边缘滑动震」在官方协议里的对应波形**，`Align`/`Step`/`Grow` 同理。
⇒ 但这些**都是【主机发起】的** —— 而本机**没有 Manual Trigger** ⇒ **官方协议这条路在本机是关的**（除非改设备描述符，而 §19.30 已定案设备侧无接收分支）。
**⇒ 因此「滑动震」只能从【设备/固件侧】求 —— 这反而**强化了 cfg / TF100A 固件这条线的必要性**。**

### 2.4 ★★ 其它可用的官方事实
- **Button Press Threshold** = Page **`0x0D` / Usage `0xB0`**，且**必须不在** SimpleHapticsController 集合内；物理量程**建议覆盖 110g–190g**（默认 150g）；逻辑三档 = 低/中/高。
  ⇒ 证实 §19.53 关掉的「直发 `0x0D/0xB0`」是对的（本机描述符里没有）。
- **Haptic Intensity 逻辑范围**：下限必须 0，上限 **≥ 4**；0 = 不触发按键触觉。
  ⇒ 本机 `0x0E/0x23` 的 8 bit 实现与之兼容。
- **Win32 侧对应旋钮**：`TOUCHPAD_PARAMETERS_V1` 里有 **`feedbackSupported` / `clickForceSupported` / `feedbackEnabled` / `feedbackIntensity`（0–100）**，经 **`SystemParametersInfo` + `SPI_SETTOUCHPADPARAMETERS`** 读写。
  ⇒ ★ **这是比裸 HID 写更"官方"的路径**，可作为本项目强度控制的**规范入口**（新增待办）。

## §4 ★★★★★ `7868Q` vs `7869` —— **精确解开**（以容器为对照）

### 4.1 容器（联想固件包）里也有完整的版本块

`orig_TB14P.bin`（= `TB14P_GT7868Q_14030522_20240202.BIN`，161,628 B）：
- **4 份 cfg 副本 @ `0x4C` / `0x488` / `0x8C4` / `0xD00`**（间距 `0x43C` = 1084 ✓），**四份 sha256 全同**，且**与活体读出的 cfg 相同**（`22 01 1B 00 3E`）。
- 版本块在 `0x1142` 附近，含 **ASCII `"YELSTO"`**。

### 4.2 以 `YELSTO` 为锚，逐字节对齐（决定性）

```
容器:  ... 00 06 | 37 38 36 38 51 | 00 00 00    | 1C 02 03 05 | 0D 95 02 03 ...
活体:  ... 00 06 | 00 | 37 38 36 39 | 00 00 00 00 | 1C 02 03 05 | 00 04 00 00 ...
                        └─ "7869" ─┘                └─ 完全相同 ─┘
容器在同一位置是  "7868Q"
```

| 字段 | 容器 | 活体 IC |
|---|---|---|
| 家族标签 | `YELSTO` | `YELSTO` ✅ **相同** |
| product-id 串 | **`"7868Q"`**（5 字符） | **`"7869"`**（4 字符，正好 = 主线 `char product_id[4]`） |
| **`fw_version`** | **`1C 02 03 05`** | **`1C 02 03 05`** ✅ **相同** |

### 4.3 ⇒ 结论（谨慎、精确）

1. **不是版本矛盾**：`fw_version` 两边**完全一致**（`1C.02.03.05`）⇒ **容器里的固件就是 IC 里跑的固件**。
2. **只是 product-id 字符串不同**：容器写 **`7868Q`**（= 联想包名 / 丝印 / INF 的标称），IC 的 `product_id` 字段报 **`7869`**。
3. **最合理的读法**：**「7868Q」是【产品/模组的标称代号】，「7869」是【IC 的 4 位编号字段】** ——
   与主线结构体注释 `char product_id[4]; /* 4 digits IC number */` 完全吻合（**4 位，装不下 "7868Q"**）。
4. ⚠️ **仍保留的可能**：活体读数的**字段起点可能偏移 1 字节**（容器 `06` 后直接是串，活体 `06` 后多一个 `00`）。
   ⇒ **判据（零成本）**：以 `YELSTO` 为锚重读活体 `0x4016..0x4032`，**确认 `product_id` 字段究竟从哪一字节起**（本轮已做一次，结论见 §4.2；如需可再复核一次）。

**⇒ 措辞收敛：**「本机 IC 自报 `product_id = "7869"`，固件版本 `1C.02.03.05`，家族 `YELSTO`；联想侧标称 `GT7868Q`。」**不再使用"型号是 GT7869"这类表述。**

## §5 ★★★ 持久化路径：官方原文（= §20.11 第 5 项的前置）

`gtx8_gtx8_update.cpp::flash_cfg_with_isp()`：
```c
for (i = 0; i < sub_cfg_num; i++) {
	sub_cfg_id  = fw_data[sub_cfg_info_pos];
	sub_cfg_len = (fw_data[sub_cfg_info_pos + 1] << 8) | fw_data[sub_cfg_info_pos + 2];
	if (dev->GetSensorID() == sub_cfg_id) {
		cfg = &fw_data[cfg_offset];
		cfg_ver_infile = cfg[0];
		break;
	}
	cfg_offset += sub_cfg_len;  sub_cfg_info_pos += 3;
}
...
ret = load_sub_firmware(CFG_FLASH_ADDR, cfg, sub_cfg_len);   /* ★ CFG_FLASH_ADDR = 0x1E000 */
```
**⇒ 确认三点**：① 持久化 = `load_sub_firmware(0x1E000, …)`（即 `0E 12` 那条路）；② 选包判据 = **`GetSensorID() == sub_cfg_id`**（本机 SID = **4**）；③ 索引表格式 = `{u8 id, u16 BE len}`，**步长 3**。

**⇒ 由此修正上一轮的一个待办表述**：第 4 项「找本机的 `goodix_cfg_group.bin` 按 SID=4 挑包」
**其实已经满足** —— 手上的 `orig_TB14P.bin` 里就是本机的 cfg（4 份副本、与活体一致）。

**⇒ 另发现**：`firmware_image.h` 给出更新标志枚举
`NEED_UPDATE_FW=1` · **`NEED_UPDATE_CONFIG=2`** · **`NEED_UPDATE_CONFIG_WITH_ISP=0x10`** · `NEED_UPDATE_HID_SUBSYSTEM=0x80`
⇒ 解释了官方两条 cfg 路径的标志位差异（§19.54）。
