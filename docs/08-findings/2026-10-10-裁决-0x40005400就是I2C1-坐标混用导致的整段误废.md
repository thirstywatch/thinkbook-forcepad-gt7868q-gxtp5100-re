## 1. 先厘清坐标：这是整条矛盾的根因

`method/METHOD.md:138-152` 给出的映射：

```
加载基址：addr 0x08005000  ↔  file 0x19ABC      （已明确标注"不是 0x08000000"）
换算： file = addr - 0x08005000 + 0x19ABC
```

**两组【不同层级】的东西，数值长相极像，这是矛盾的根源：**

| | 文件偏移 | 地址 | 内容 |
|---|---|---|---|
| **① K 表** | **`file 0x08800`**（连 4 份：`0x08800 / 0x08C00 / 0x09000 / 0x09400`） | —— | **`K_gt7868q.bin` 逐字节相同（1024/1024，已实测）** |
| **② 争议代码** | `file 0x1D408 / 0x1D40A …` | **addr `0x0800894C / 0x0800894E …`** | **真 Thumb-2 代码（见 §2）** |

**⇒ `file 0x08800` 与 `addr 0x08008800` 相差 0x19ABC/0x08005000 两级映射，是【完全不同的地方】。**

**实测复核**：
- `d.find(K)` = **`0x08800`** ✓（且 K 在该文件中**恰好出现 4 次**，位于 `0x08800 / 0x08C00 / 0x09000 / 0x09400`）
- `file 0x08800–0x08C00` 与 K 逐字节 **1024/1024 相同** ⇒ 那里**确实是 K 表** ✓
- `addr 0x08008800`（= `file 0x1D2BC`）与 K 逐字节 **9/1024** ⇒ **完全不是 K 表** ❌
- 若把 `file 0x08800` 误当向量表起点，其 entry 47 = `0x880C0A22`（垃圾）⇒ **排除"向量表读错位置"这一解释**，项目读到的 `0x08008978/0x0800894C` **确实来自真向量表**（`file 0x19ABC`）

## 2. ★★★★★ 十项证据（全部来自项目自己的反汇编）

### 证据 1–2：IRQ31 / IRQ32 是真 ISR 入口

`data/reference/lab__TF100A_thumb.asm.txt`：

```
0800894C  push      {r7, lr}          ← IRQ32 = I2C1_ER 入口
08008978  push      {r7, lr}          ← IRQ31 = I2C1_EV 入口
```

真向量表（`file 0x19ABC`）实测：`IRQ31 = 0x08008979`、`IRQ32 = 0x0800894D`（带 Thumb 位）⇒ entry `0x08008978 / 0x0800894C` ✓ **与项目所报完全一致**。

> **STM32F1 的 IRQ 编号核对**：IRQ31 = **I2C1_EV**、IRQ32 = **I2C1_ER**、IRQ33 = I2C2_EV。项目对 IRQ31/32 的命名**正确**。

### 证据 3：`0x0800FC80` 是"读寄存器位"通用 helper

```
0800FC8C  ldr  r0, [sp, #0x10]      ; r0 = arg0 = 外设基址
0800FC8E  ldr  r0, [r0, #4]         ; ★ 读 [base + 4]
0800FC90  and  r0, r0, #0x400       ; ★ 掩 bit10
0800FC98  ldrh.w r1, [sp, #0xc]     ; r1 = arg1 低16位 = desc
0800FC9C  lsrs r1, r1, #6           ; ★ desc >> 6 = 字节偏移
0800FC9E  ldr  r0, [r0, r1]         ; ★ 读 [base + (desc>>6)]
0800FCA2  and  r2, r1, #0x1f        ; ★ desc & 0x1F = 位号 0..31
0800FCA8  lsl.w r2, r1, r2          ; 1 << 位号
0800FCAC  ands r0, r2               ; 测该位
```

**⇒ 语义 = `read_bit(base, desc)`，其中 `desc>>6` 是字偏移、`desc&0x1F` 是位号。**
**⇒ 它不是"GPIO 引脚助手"——arg0 是【外设基址】，arg1 是【寄存器/位描述符】。**

### 证据 4：★★★★ 两个 ISR 各自检查**自己那条**中断使能位（完全自洽）

把两处 desc 代入 helper：

| ISR | desc（`r1`） | `desc>>6` | 实际读到的寄存器 | `desc&0x1F` | 位名 |
|---|---|---|---|---|---|
| **IRQ32 = I2C1_ER** | `0x050A`**`0108`** | 4 | `[0x40005400+4]` = **I2C1_CR2** | **8** | **`ITERREN`** ✅ |
| **IRQ31 = I2C1_EV** | `0x0501`**`0109`** | 4 | `[0x40005400+4]` = **I2C1_CR2** | **9** | **`ITEVTEN`** ✅ |

出处：`08008956 / 08008982 / 080089AA / 080089D2`。

**⇒ 错误中断查 `ITERREN`、事件中断查 `ITEVTEN` —— 这是教科书级自洽，不可能是巧合。**

> ★★ **这同时给出了项目悬案的机制答案**：项目长期困惑"`CR2.ITBUFEN`/`ITERREN` 为何从不置位"。
> 真相是：**这段代码是在【读并测试】这些使能位（用作门控条件），不是在置位它们。**
> 而且 EV 路径实际门控的是 **`ITEVTEN`(bit9)** —— 项目此前只查了 `ITBUFEN`/`ITERREN`，**可能查漏了这一位**。

### 证据 5：★★★ `0x40005410` 是**真解引用**，且构成 I²C 从机收包环

```
08008A98  movw      r1, #0x5410
08008A9C  movt      r1, #0x4000      ; r1 = 0x40005410 = I2C1_DR
08008AA0  ldr       r2, [r1]         ; ★★ 解引用（不是传参！）
08008AA2  uxtb      r2, r2           ; 取收到的 1 字节
08008AA4  strh.w    r2, [r0, #0x104]
08008AA8  ldr       r1, [r1]
08008AAA  ldrh.w    r2, [r0, #0x102] ; 环形缓冲计数
08008AAE  adds      r3, r2, #1
08008AB0  strh.w    r3, [r0, #0x102]
08008AB4  strb      r1, [r0, r2]     ; ★★★ 存入 ctx + 计数 = 环形缓冲
```

同型：`08008AC0–08008AD2`（且有 `cmp r1,#0x7f` ⇒ **容量 128 B**，与项目记录一致）。

**⇒ 这是 I²C 从机 RX 路径：从 `I2C1_DR` 逐字节读入 128 B 环形缓冲。**
（项目把同一段解读为"UART DR"—— 但 `0x40005410` = `0x40005400 + 0x10`，**在 STM32F1 存储映射里 `0x40005400` = I2C1、`+0x10` = DR**，而 USART1 的 DR 在 `0x40013800 + 0x04`。）

0800FA6C  str       r0, [r1, #4]     ; ★★★ 写 I2C1_CR2 (+0x04)！

0800FAE0  ldr       r0, [r1, #0x1c]

## 3. ★ 裁决结论

### 3.1 `0x40005400` = **I2C1**，且本镜像含**真实的 I²C 从机驱动**

**证据链闭合**：
```
I2C1_EV 中断(IRQ31)
  → 检查 CR2.ITEVTEN (证据4)
  → 调 0x08008A70
  → 从 I2C1_DR (0x40005410) 读字节 (证据5)
  → 存入 ctx 环形缓冲 (证据5)
```
外加：`I2C1_ER`(IRQ32) 有独立入口（证据1–2）、`SR1/SR2` 读取（证据6）、`I2C_Init` 配 CR2/CCR/TRISE（证据8–10）。

**⇒ 口径 A（`追加三十七 §23.4/§23.13/§23.10`）被推翻：**
- ❌ "`0x40005400` 是 GPIO/寄存器结构体助手" —— 它是被**解引用**的外设基址（证据5/6/7/8–10）
- ❌ "`0x40005410` 是 UART 数据寄存器" —— 它是 **I2C1_DR**（证据5）
- ❌ "本镜像里没有 I²C 主机驱动" —— 至少**从机驱动**确凿存在（证据4/5/6）

### 3.2 登记表 **B1** 的"整段作废"依据在坐标层不成立

B1 的判否理由原文（要点）：**"`0x08900 ∈ [0x08800, 0x08C00)` = K 交织表副本内部 ⇒ 把数据表字节误读成了指令。且 `0x40005400` 全文件只有 9 处、全在 `0x1D40A–0x1D644`，`0x08008xxx` 区一处都没有。"**

**实测**：
- `[0x08800, 0x08C00)` 作为**文件偏移**：**确实是 K 表**（1024/1024，连 4 份）✓ —— B1 这句本身没错
- 但向量表条目 `0x0800894C` 是**地址**，换算到 `file 0x1D408`，**是带 `push {r7,lr}` 的真代码**
- **B1 自己的两句话互相矛盾**：`file 0x1D40A` 换算成地址**正是** `0x0800894E`，即**就在它说的"`0x08008xxx` 区"里**
- ⇒ **B1 把"文件偏移"与"地址"当成同一坐标系了。**

**⚠️ 诚实声明（未能复现项）**：B1 引用的"该区非法指令率 `udf` 0.0548 vs 真代码 0.0020"，我用 Thumb 永久未定义指令 `0xDE00` 在
`file 0x1D2BC–0x1D6BC`、`file 0x08800–0x08C00`、`file 0x1E000–0x1E400` 三段**均测得 0.0000**，**无法复现该数字**。
因此我**不主张**"项目误读了指令"——我只主张**坐标混用**这一点（该点有字节级实测支撑）。B1 的 udf 判据**需项目自行复核其定义与取样区**。

### 3.3 对"TF100A 只做从机"这一结论的影响

**→ 不受影响，且反而获得一条比原依据更硬的新证据链**（证据 4/5/6）：从机 RX 路径 + 两个中断各自的门控位自洽。
（原新依据是 `I2C_Init@0x0800FA20` 的 `OAR1=0x58`；本文档另补了 ISR + DR + SR1/SR2 + CR2 门控，**比单点更强**。）

## 4. 对"片间链路：I2C1 还是 USART1 未定"的回答

**结论：强烈倾向 I2C1，但【未完全闭合】。**

|---|---|---|

## 5. 新增纪律

> **第 117 条**：**同一份材料里，"文件偏移"与"运行时地址"是两个坐标系，禁止在同一判据里混用。**
> 判定任何"某地址处的字节是不是代码"时，必须**先把它折算成文件偏移并打印该偏移处的实际字节**；
> 禁止拿地址的**数值形态**（如 `0x08008800`）去和文件偏移**区间**（如 `[0x08800,0x08C00)`）做包含判断。
> **本条的直接代价**：本项目 B1 因混用坐标系，把 TF100A 的真实 ISR 代码判成了 K 数据表，并据此**整段作废**了 `追加二十七 §五`。

> **第 118 条**：**"某位从未被置位"这类结论，必须先确认【代码是在读它还是写它】。**
> 本项目 `ITBUFEN/ITERREN` 悬案：代码实际是在**读并测试**这些使能位（门控），不是在写。且实际门控的是 `ITEVTEN`(bit9)，此前只查了 bit8/bit10。
