# 「代码 10」归因复核 —— 主机侧还是固件侧？

> 日期：2026-10-03 · 触发：喆「做吧」
> 背景：项目记录「换 X9-15 模块 → 装上去 Windows 能看到设备但**代码 10**，读不到 HID descriptor」，
> 并把原因归为「本机 BIOS 白名单 PID ∈ {0x01E8, 0x01E9}」。
> 本次复核这条归因**成立到什么程度、卡点到底在哪一环**。
> 全部证据都来自本机既有材料（DSDT/SSDT 反编译、BIOS 明文镜像、`GoodixTpDxe` 反汇编），**可复核**。

---

## 〇、结论（先看这个）

| 问题 | 答案 |
|---|---|
| 代码 10 是**主机侧**拒绝吗？ | ❌ **不是**。主机侧**没有任何按 PID 的白名单** |
| 是**固件侧**（BIOS）拒绝吗？ | ⚠️ **部分是**，但不是"禁止使用" |
| **直接原因** | ★ **Windows 在 ACPI 指定的 I²C 地址 + 描述符寄存器上，从模组读不到 HID 描述符** ⇒ 设备枚举成功但不能启动 |
| **根因链** | `BIOS 开机写 TPDF（物理内存配置字节）` → `ACPI 用 TPDF 在 TPID 表里选一项` → **这一项给出【I²C 从地址】和【描述符寄存器地址】** → Windows 按这两个值去模组读描述符 |
| **⇒ 项目原记录的修正** | 「白名单卡死」只是**表症**。真正的机制是 **`TPDF` → `TPID` 选择链**；而这条链**在 DSDT 里，可补** |

---

## 一、证据链（逐条带出处）

### 1.1 ★★★ DSDT 的 `TPAD` 子树：主机侧的设备身份**完全由一张表决定**

`dsdt-asl/DSDT_本机_21LD.dsl` L87377 起：

```asl
Device (TPAD) {
    Name (_ADR, One)          // I²C 从地址 1
    Name (_UID, One)
    Name (ADR0, Zero)         // ← 运行时写入的 I²C 从地址
    Name (HID2, Zero)         // ← 运行时写入的"HID 描述符寄存器地址"
    Name (TPID, Package (0x05) {        // ★ 5 项 {index, I²C地址, 描述符寄存器, HID串, CID}
        { One,  0x2C, 0x20, "SYNA2BA6", "PNP0C50" },   // 1 Synaptics
        { 0x02, 0x15, One,  "ELAN06FA", "PNP0C50" },   // 2 ELAN
        { 0x03, 0x2C, 0x20, "CIRQ1080", "PNP0C50" },   // 3 Cirque
        { 0x04, 0x2C, 0x20, "GXTP5100", "PNP0C50" },   // 4 ★ 汇顶（本机）
        { 0xFF, 0xFF, 0xFF, "XXXX0001", 0x030FD041 },  // 5 占位项
    })
```

### 1.2 `_HID` / `_CID` 是**方法**，选表逻辑写死在 `TPDS`

```asl
Method (_HID, 0, Serialized) {
    If (~CondRefOf (TPDF)) { Name (TPDF, 0xFE) }
    Switch (One) { Case (Zero) { TPDF = 0xFE }  Case (One) { }  Default { TPDF = 0xFE } }
    Return (TPDS (0x03, 0xFE, TPDF, "MSFT0001"))     // ← 默认串 = MSFT0001
}
Method (_CID, 0, Serialized) { … Return (TPDS (0x04, 0xFE, TPDF, "PNP0C50")) }

Method (TPDS, 4, NotSerialized) {
    Local0 = 0
    Local1 = TPID[0][0]
    While ((Local1 != Arg1) && (Local1 != Arg2)) {      // Arg1 = 0xFE, Arg2 = TPDF
        Local0++
        If (Local0 >= SizeOf(TPID)) { Return (Arg3) }   // 找不到 ⇒ 返回默认串
        Local1 = TPID[Local0][0]
    }
    Return (TPID[Local0][Arg0])                          // 命中 ⇒ 返回该字段
}
```

★ **命中哪一项，完全取决于 `TPDF` 这一个字节。**

### 1.3 ★★★ `_CRS` 与 `_DSM`：把【I²C 地址】和【描述符寄存器】交给 Windows

```asl
Method (_CRS, 0, Serialized) {
    ……用 TPDF 在 TPID 里找到同一项……
    ADR0 = TPID[Local0][1]      // ← I²C 从地址（Goodix 项 = 0x2C）
    HID2 = TPID[Local0][2]      // ← HID 描述符寄存器（Goodix 项 = 0x20）
    Return (ConcatenateResTemplate (IICB (ADR0, "\_SB.PC00.I2C0"), SBFI))   // 组装 I²C 资源
}

Method (_DSM, 4, NotSerialized) {
    If ((Arg0 == ToUUID ("3cdff6f7-4267-4555-ad05-b30a3d8938de") /* HID I2C Device */)) {
        If ((Arg2 == One)) { Return (HID2) }        // ★ Function 1 = 「HID 寄存器地址」
    }
    ……
}
```

★★★ **关键判断**：HID-over-I²C 的 `_DSM` **Function 1 返回的是"描述符放在哪个寄存器"（一个 DWORD），不是描述符本身**。
⇒ **Windows 拿到 `0x2C` + `0x20` 之后，是【自己去模组的寄存器 `0x20` 读描述符】。**
⇒ **所以"读不到 HID descriptor"＝模组侧（或地址/寄存器给错），不是 Windows 按 PID 拒绝。**

### 1.4 ★★★ `TPDF` 不是 AML 常量，是**物理内存里的一个配置字节**

`dsdt-asl/SSDA_本机_21LD.dsl`（SSDT，262 B）全文只有一段 OperationRegion：

```asl
OperationRegion (COMP, SystemMemory, 0x6DEBEB18, 0x0300)
Field (COMP, AnyAcc, Lock, Preserve) {
    RSR0, 32, BDDD, 8, CPFB, 8, PBTI, 8, BRLV, 8, CAVR, 8, TJMA, 16, CORE, 8,
    TPDF, 8,            // ★ 触控板型号选择字节
    TPLF, 8, TPDD, 8,   // ← TPDD 被 _STA 使用
    TMUD, 8, CTUR, 8, CUCB, 32, CG21, 16, CSID, 8, …
    BFDT, 1024, ESMS, 8, ESMB, 256, E3EN, 8, IDFD, 1024, IDF2, 1024, …
    CPP0, 8, CPP1, 8, CPP2, 8, CPP3, 8, RSR3, 992
}
```

⇒ **`TPDF` 由 BIOS/DXE 在开机早期写进这块 OEM 配置内存**，AML 只负责读。
⇒ 全库检索：`TPDF` 只出现在 **DSDT（14 处）+ SSDA（1 处）**，**没有任何其它表给它赋值** ⇒ 赋值者是**固件代码**。

### 1.5 ★★ `GoodixTpDxe` 的真身：**触控板固件的 UEFI FMP 刷写器**

`bios-re/GoodixTpDxe.bin` 的字符串给出了它的全部职责：

```
<TpupdateEntryPoint> Function begins.        ← 模块入口就叫 "Tpupdate"
<tffwUpdateProcess> Download firmware …      ← 下载固件
<writeBinFile> Enter update mode / Erase flash / Write flash / CRC error
<getTFVersion> TF version: %02X %02X         ← "TF" = 钛方 TF100A
<InitGoodixHidDescriptor> Read HID descriptor failed. ret = %d
<InitGoodixDevice> InitGoodixHidDescriptor failed
7863 disable report / 7868Q enable report
Allocate goodix touch pad FMP private data failed.   ← ★ FMP = Firmware Management Protocol
SetBasicProperties7868Q failed
```

⇒ 它就是**把 `TB14P_GT7868Q_*.BIN` 那个 UEFI 胶囊写进触控板**的那个 DXE 驱动。
⇒ **它的 `VID==0x27C6 && PID∈{0x01E8,0x01E9}` 判据，决定的是"要不要给这块模组做初始化 / 刷固件"，
而不是"这台机器允不允许用这块模组"。**

（★ 顺带：本轮曾怀疑该判据旁还有一条更宽的 `and eax,0xfff0; cmp eax,0x1e0`（覆盖 `0x01EA/0x01EB`）。
读完控制流后**该怀疑作废** —— 它的入口被 `xor eax,eax / test / je` 恒跳转跳过，是不可达分支。
真正生效的仍是 `{0x01E8, 0x01E9}`。项目旧结论站得住。）

### 1.6 ★★★★★ 实锤：项目当年那份 DSDT 补丁，动的**正是这张表**

`dsdt-asl/verify/DSDT_patched_方案A.aml` 与原表逐字节比对：**只差 9 个字节**。

```
0x000009           95 → A9                      ← ACPI 表校验和（必然要重算）
0x0704B0           04 → FE                      ← ★ TPID 第 4 项的 index 字段：4 → 0xFE
0x0704B6..0x704BB  "GXTP5100" → "MSFT0001"      ← ★ 该项的 HID 串
0x0704BD           30 → 31                      ← 末位 '0'→'1'
```

原始字节（`0x704A0` 起）：
```
… 12 1b 05  0a 04  0a 2c  0a 20  0d "GXTP5100" 00  0d "PNP0C50" 00   ← 就是 TPID 第 4 项
```

**⇒ 两件事同时被证实：**
1. **`_HID` 确实由 `TPDF` 决定，且开机时 `TPDF` 命中 `TPID` 第 4 项（Goodix）** —— 否则不需要改它；
2. **`TPID` 表可以直接在 DSDT 里补，且项目已经补过一次并做过 orig/patched 两套读数对比（`verify/`）**。

## 二、三条假说的判决

| 假说 | 判据 | 判决 |
|---|---|---|
| **H-A 主机侧按 PID 白名单拒绝** | ① DSDT 里无任何 PID 常量；② `_HID` 是方法且默认串为 `MSFT0001`；③ §19.27.3 已证设备栈上**没有任何第三方驱动**（只有 inbox `hidi2c` + `hidclass`） | ❌ **否证** |
| **H-B 主机侧按型号表拒绝（`TPDF`→`TPID`）** | `TPDF` 是**内存配置字节**，由 BIOS 写；`_HID`/`_CRS`/`_DSM` 全依赖它 | ✅ **成立，但它是"选表"，不是"拒绝"** |
| **H-C 设备侧根本没起来（无有效固件/未初始化）** | `GoodixTpDxe` 的 PID 判据决定**要不要刷固件 + `SetBasicProperties7868Q`**；症状"能枚举、启动失败、读不到描述符"与"模组未初始化"一致 | ✅ **最贴合症状** |

**⇒ 合并解释（自洽的一条链）：**
```
X9-15 模组 PID = 0x01EA ∉ {0x01E8, 0x01E9}
   ↓
BIOS 的 GoodixTpDxe 跳过它的初始化 / 固件下载（tffwUpdateProcess 不跑）
   ↓
模组以未初始化状态挂在 I²C 上；同时 ACPI 侧 TPDF 若未被写成让 TPID 命中该项，
   _CRS 给出的 I²C 地址 / _DSM 给出的描述符寄存器就可能不是模组实际的那一组
   ↓
Windows 枚举成功（_STA 仍返回 0x0F），但按 ACPI 给的地址/寄存器**读不到描述符**
   ↓
CM_PROB_FAILED_START = 代码 10
```
⇒ ★ **归因结论：这不是"主机侧拒绝"，而是"模组没被初始化 + ACPI 选表链没对上"。
其中【选表链】在 DSDT 里，是 9 个字节级别的可补项。**

## 三、对「换 X9-15」这条路的可执行含义

### 3.1 ★ 正确的工程形态是**补 DSDT**，不是改签名 BIOS

| 方案 | 改动量 | 门禁 |
|---|---|---|
| 改 `GoodixTpDxe` 的 PID 判据 | 编译器常量 | ❌ 模块在 FV 里是 **LZMA 压缩**（明文 19.2 MB 里搜 `cmp eax,0x27c6` 命中 **0**）⇒ 要解压→改→重压→重建 FV→过 Insyde secure flash（`H2OFFT.cat` 是签名目录） |
| **补 DSDT（改 `TPID` 第 4 项 / 让 `_CRS`+`_DSM` 恒命中 Goodix 项）** | **9 字节 + 校验和** | ⚠️ 需要能替换 ACPI 表（项目已做过一次：`verify/DSDT_orig.aml` ↔ `DSDT_patched_方案A.aml`） |

**具体补法（两条，任选）**
1. **改表**：把 `TPID` 第 4 项变成"必然被选中"——例如把它的 index 字段从 `0x04` 改成 `0xFE`
   （但这会让 `_HID` 走默认分支返回 `MSFT0001`，即**主动降级到微软兜底 PTP**，也正是方案A 干的事）；
   或者直接在 `_CRS`/`_DSM`/`_HID` 里**跳过 `TPDF` 匹配，硬编码 `0x2C + 0x20 + "GXTP5100"`**。
2. **改逻辑**：把 `TPDS`/`_CRS` 里的 `While` 条件改成"恒真"或把默认分支的 `Arg3` 直接换成 Goodix 项。

> ★ 第 1 条的第 2 种形态（硬编码 `0x2C + 0x20 + GXTP5100`）**不依赖 BIOS 写什么 `TPDF`，最稳**。

### 3.2 ⚠️ 但必须诚实：补 DSDT 只解决**枚举**，不解决**模组固件**

- `GoodixTpDxe` 因 PID 不在名单而**不刷 X9-15 的固件** ⇒ 模组可能仍停在**未初始化/ROM 态**。
  本项目已证：模组在 ROM 态**能自己跑**（Windows 下点按自震，2,760 条报文实测）⇒ **至少"能用"是可能的**，但手感/参数不可控。<br>🔴 原文写的"Linux 下点按照样震"作废（shell 版 live USB 未建立有效测试，见[登记表 §B4](../08-findings/00-矛盾与推翻登记表.md)）。
- ★ **X9-15 的 LRA 是 Nidec TapSense（25×25×1.4 mm, 200 Hz），与本机小型 LRA 不是同一等级**
  ⇒ 即便全部打通，**手感也不等于本机原来的手感**。

### 3.3 因此这一步的**正确验收标准**

> **不是"能不能触发触觉"，而是"装上之后普通滑动/点击能不能用"。**
> 能 ⇒ 补 DSDT 这条路值一票；不能 ⇒ 说明卡在模组初始化（固件）而非选表链，回头再判。

## 四、本轮方法论沉淀

36. ★★★ **"设备能枚举" ≠ "设备能用"**：`_STA` 返回 `0x0F` 只说明 ACPI 认这个设备，
    真正决定能不能启动的是 **描述符能不能被读到**。两者是**两条独立的链**。
37. ★★★ **HID-over-I²C 的 `_DSM` Function 1 返回的是【描述符寄存器地址】，不是描述符本身。**
    ⇒ 任何"读不到 HID descriptor"的症状，**第一时间应该去看 ACPI 给出的地址/寄存器对不对**，
    而不是去猜"Windows 拒绝了什么"。
38. ★★ **"一个配置字节 + 一张表"是 OEM 常见的机型适配手法**（本机 = `TPDF` + `TPID`）。
    ⇒ 遇到"同系列模块换装失败"，先找**这张表**，它通常在 DSDT 里、且**可补**。
39. ★ **先复核自己已有的产物**：本轮最有价值的证据不是新挖的，而是**翻出项目自己那份 `DSDT_patched_方案A.aml`
    逐字节 diff**——9 个字节直接锁定了整条机制。（同 §19.30.1 "某工具不做 X ≠ 该工具没用" 同源。）
