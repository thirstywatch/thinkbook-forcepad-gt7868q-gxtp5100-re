## §1 汇顶的触觉芯片（问题①）

### 1.1 汇顶确实有——两条产品线（一手来源）

| 产品 | 是什么 | 与本机的关系 |
|---|---|---|
| ★ **Newton Touchpad®** | 官方称「**触控 + 高精度力感应集成到单芯片**」，中文页明确写：**「加入了压力检测以及全新的振感反馈功能」「提供触控、压力检测、振动反馈的整合方案及模组」** ⇒ **它就是汇顶的"带触觉"压力触控板方案** | ❌ **本机不是它**。本机是「GT7868Q（触控）+ TF100A（独立力/触觉 IC）」的**分离式**架构（`docs/02-hardware/00-GT7868Q外部资料汇总-公开可得边界.md` §26–28） |
| ★ **TFA9894D** | 汇顶**智能触觉驱动器**：10 V 升压 D 类，5.6 W@8 Ω LRA，**自适应谐振/温度/振幅**，支持"音频转触觉" | ❌ **本机不是它**。本机的执行器驱动是**艾为 AW86927FCR** |

**⇒ 结论：汇顶的"支持触觉的芯片"存在，而且就是 Newton Touchpad®；但它是【单芯片集成力感应】，而本机是【分离式】。**
**⇒ 换句话说：本机的"触觉缺失"不是"汇顶没这个能力"，而是【联想选了另一个模组架构】——力感应交给了钛方 TF100A，触觉决策也就跟着落在了 TF100A 的固件里。**

### 1.2 ⚠️ 但这里有一个必须点破的事实

> **"汇顶有支持 Manual Trigger 的芯片" ≠ "本机这颗 GT7868Q 支持 Manual Trigger"。**

Manual Trigger 不是芯片能力，而是**HID 描述符里的一条 usage 声明**（`0x0E/0x21`，Output）。同一颗芯片，**OEM 可以在描述符里声明它，也可以不声明**。
- 本机描述符：`0x0E` 页下**只有 `Intensity`（`0x0E/0x23`，还是 FEATURE）**，`0x0E/0x21` **不存在**（实测 + Linux 上游 RFC 双向确认）。
- ⇒ **就算给本机换上 Newton Touchpad 模组，也是"换了硬件"**，不是"暴力软件"。

## §2 「人家是怎么做到的」——官方机制的完整拆解（问题②）

### 2.1 三条路线，同一个前提

| 平台 | 主机触发机制 | 前提 |
|---|---|---|
| **Linux 6.18 主线** | `hid-haptic.c` + Force Feedback 协议（新 `FF_HAPTIC` effect） | 设备暴露 simple haptic controller 集合 + 波形 usage + **`auto trigger waveform`** + **`manual trigger`**；`ABS_MT_PRESSURE` 以**牛顿/克**报告 |
| **Windows 11** | `Windows.Devices.Haptics.InputHapticsManager.TrySendHapticWaveform()` | 设备须进**官方支持列表**（目前仅 **Surface Laptop 8 / 8 for Business** + 部分鼠标/笔） |
| **macOS** | 私有 `MTActuatorActuate` | Apple 全系 Force Touch |

**⇒ 三条路线没有一条在"设备未声明"的情况下工作**（`追加十六` §4 原话：*"厂商的做法都是「在设备侧定义接口，在主机侧提供 API」，从未试图绕过设备侧"*）。

### 2.2 ★★★★★ 关键机制：「交出控制权」这一步是怎么做的

这是本轮**最有价值的新知识点**（原文档只写了"需要声明"，没写**怎么切换**）：

> **模式切换 = 写 `auto trigger waveform`（`0x0E/0x20`）这一个【FIELD】**
> - **设备自主模式**（device-controlled）= 把 `auto trigger waveform` 置为 **`WAVEFORM_PRESS`**（默认）
> - **主机控制模式**（host-controlled）= 把 `auto trigger waveform` 置为 **`WAVEFORM_STOP`** ← ★ **就是这一步让设备"闭嘴、听主机的"**

**内核原文**（`[PATCH 00/11] HID: Implement haptic forcepad support`，`hid-haptic.c`）：

> *"Device-controlled mode can be enabled by setting the "auto trigger waveform" to WAVEFORM_PRESS.*
> **Host-controlled mode can be enabled by setting the "auto trigger waveform" to WAVEFORM_STOP.**"*
> *"The device must also support manual triggering. If intensity modification for waveforms is supported by the device, the intensity control should be included in the manual trigger output report."*

**内核实现**（`hid_haptic_switch_mode()`，`hid-haptic.c`）：
```c
if (mode == HID_HAPTIC_MODE_KERNEL)  value = HID_HAPTIC_ORDINAL_WAVEFORM_STOP;
else                                 value = haptic->default_auto_trigger;
/* 找到 HID_HP_AUTOTRIGGER 那个 field，改值，然后 */
hid_hw_request(hdev, rep, HID_REQ_SET_REPORT);     /* ← 注意：走 SET_REPORT */
```

### 2.3 ★★★ 由此浮出三条**对本机有实际指向**的推论

| # | 推论 | 对本机的意义 |
|---|---|---|
| **1** | **"交出控制权"靠一条 FEATURE/SET_REPORT 字段，不是 OUTPUT 报** | ⚠️ 本机 Col02 **有 4 组 feature 报**（RID 2/6/9/11/12/13）⇒ **"能不能靠写某个 feature 字段逼它开口"** 从"不可能"变成了"**值得逐个探一次**"（见 §5 战场 N2） |
| **2** | 内核支持**厂商自定义波形**（`struct ff_hid_effect` 里带 `vendor_id` / `vendor_waveform_page`） | ⚠️ 本机 **Col02 的 RID 13 就是 vendor page `0xFF00`（4 B feature）**、**Col04 是 vendor page `0xFF00`（65 B output）** ⇒ **厂商私有波形空间本机是有的**，只是没人告诉我们格式（而厂商 DLL 正好给了地址表，见 §5 战场 N4） |
| **3** | **本机缺的不是"驱动"，而是"描述符声明"** | ⇒ 纯软件提升"能力探测"是唯一**通用且可发布**的形态；**提升"这台机器的能力"必然要动设备侧** |

### 2.4 ★ 本机与"人家"的逐条差距（沿用 §19.27 / `追加十六` §3 的对照，此处补 mode-switch 一行）

| # | 上游要求 | 本机 | 证据 |
|---|---|---|---|
| 1 | simple haptic controller 集合 | ✅ 有（`0x0E/0x01` 的"壳"） | caps / rdesc |
| 2 | 波形 usage（PRESS/RELEASE/STOP） | ❌ 无 | `0x0E` 页下**只有 `0x23`** |
| 3 | **`auto trigger waveform`（`0x0E/0x20`）** | ❌ **无** | 描述符无此 usage（★ 同时 PTP 对触控板是**禁止项**，缺席=合规） |
| 4 | **`manual trigger`（`0x0E/0x21`）OUTPUT** | ❌ **无**（且 `Out=0`） | 实测 |
| 5 | `ABS_MT_PRESSURE` 以 N/g 报告 | ❌ 无物理单位（`0x0D/0x30`，0..2000） | 实测 |

**⇒ 五条缺四条，且缺的正好是"主机侧能开口"和"设备侧肯交权"这两根最关键的门闩。**

## §3 Col02 核查（问题③）—— 到底做过什么，没做什么

### 3.1 ★ 项目在 Col02 上做过的**全部**实验（穷举，逐个复核源码/结果）

| 实验 | 工具 / 产物 | 用的什么 API | 对哪些 RID | 结果 |
|---|---|---|---|---|
| 写语义对照 | `tools/hid/old__col02_write_probe.py` · `hid-probe/col02-writeprobe/` | **`HidD_SetFeature`**（SET_FEATURE） | **2 / 6 / 9**（**全部是已声明的 FEATURE**） | RID 2 同值回写 OK、**改值写入 `effective: false`**；RID 9 写入 `ok:true` 但读回 `0xEE` |
| 特征报表精读 | `col02-precise/` | **`HidD_GetFeature`**（GET_FEATURE） | **2 / 6 / 7 / 9 / 11 / 12 / 13** | 全部返回**垃圾数据**（RID 6 的内容或 `0xEE`）⇒ **GET_FEATURE 在本机无意义** |
| 描述符/caps | `poc/hid-dump.txt` · `lab__GXTP5100-HID-usage-report.md` | `HidP_GetCaps` + 原始报告描述符 | — | **`Out = 0`**（一个输出报都没有）；`0x0E` 页下**只有 `0x23`** |

### 3.2 ★★★ 明确：**从未做过的**

| 未做的 | 为什么没做 | 现在还有没有意义 |
|---|---|---|
| **往 Col02 发 OUTPUT 报告** | `OutputReportByteLength = 0` ⇒ **Windows 的 `HIDCLASS` 会在参数校验阶段直接拒绝**（`HidD_SetOutputReport` 返回 `FALSE`，`GetLastError = 87 ERROR_INVALID_PARAMETER`） | ★ **在 Windows 上确实没意义**（这条结论是对的）。**但在 Linux 上有意义**——见 3.3 |
| **往 Col02 发【未声明】RID** | 同上（Windows 校验 RID 是否属于该集合） | ★ **同上** |
| **往 Col04（`0x0E`）发【未声明】RID** | Col04 只声明了 `0x0E` 一个 output，其余 RID 在 Windows 上也发不出去 | ★ **Linux 上可发** |

> ⚠️ **必须纠正一个曾经的表述**：`docs/07-hid/lab__GXTP5100-HID-usage-report.md` §5.4 写"厂商私有通道（本机 Col04 有 vendor `0xFF00` 的 Output 报 RID 14）…… 该 usage 在官方表里未找到，没有可依据的语义"。
> **这半句现在过时了**：厂商 DLL 已给出该通道的**地址表与期望值**（`command = 0x4160`、`cmd 0x33/0x34`、`I2C_DIRECT_RW = 0x20`），⇒ **"没有语义"→"语义已有一份厂商侧权威来源"**。

### 3.3 ★★★★★ 关键的不对称：**Windows 拒绝，Linux 不拒绝**

| | Windows `HIDCLASS.SYS` | Linux `i2c-hid` |
|---|---|---|
| 发 OUTPUT 报前是否校验 RID 属于该集合 | ✅ **校验**（不通过 → `err=87`，报文根本不出网卡… 不出总线） | ❌ **不校验** |
| 依据 | 实测（`Out=0` ⇒ `SetOutputReport` 失败） | `i2c_hid_output_raw_report()` → `i2c_hid_set_or_send_report(client, 0x02, report_id, buf, count, use_data)`，**直接把 `report_id` 塞进 SET_REPORT 包**发出去 |
| 后果 | **主机侧"发不出"** | **主机侧"发得出"** ⇒ **报文会真的到达 IC** |

**⇒ ⇒ 这就是本项目唯一真正没试过的注入面：**
> **在 Linux 下，用 `hidraw` 的 `write()`（或 `HIDIOCSREPORT`）往触控板发【描述符里未声明】的 OUTPUT 报告。**

`hidraw` 的 `write()` 走 `hid_hw_raw_request(..., HID_OUTPUT_REPORT, HID_REQ_SET_REPORT)`，**全程没有描述符校验**。
⇒ **可以逐 RID 试**：`write(fd, [RID, 64 bytes...])`。

⚠️ **但必须先想清楚风险**（下一节 §5 给分级与停止条件）：本机 Col04 的 RID `0x0E` **就是命令通道**，而命令空间里 `0x10/0x11/0x12/0x13` = patch/update/**写 flash**/reset ⇒ **"RID 空间"里可能藏着会写 flash 的处理器**。这正是纪律 154 要防的事。

## §4 「不行就直接写固件」—— 三条路，逐条给真实卡点（问题④）

### 4.1 路线 W1：写 **GT7868Q** 固件（官方工具链在手 ⇒ 但加不了功能）

| 项 | 事实 | 出处 |
|---|---|---|
| 工具链 | ✅ **有**：汇顶官方 `gdixupdate` **v1.8.0 源码**（`poc/gdix-hid-fw/`，Apache-2.0），镜像格式/子固件循环/命令序列**全部可读** | 载荷A第四轮 |
| 镜像结构 | 256 B 头（`size`/`chksum`/`YELSTO`/`7868Q`/**13 个子固件**）+ 子固件表 + 数据 | 同上 |
| ★ **致命点** | **13 个块【全部是数据/表】，没有一块是程序**（程序在芯片 ROM / 未随包分发） | 载荷A第四轮 §七（带正对照） |
| 官方写入掩码 | `firmware_flag = 0x0C` ⇒ **只写 type `0x02`/`0x03`** 的子固件 | `main.cpp` / `gtx3_gtx3_update.cpp` |
| 写入通道 | `00 10`（切 patch）/`00 11`（启动更新）/`0E 12`（**写 flash**）—— **四条红线之一** | §19.51 |
| 验证 | 刷写由 **BIOS/UEFI** 执行（ESRT 名 = *Goodix Update **UEFI***）；容器加密 + **eFuse 验签**；且**无自助刷回通道** | §18.3 |

**⇒ W1 判定：❌ "改包加功能"不可行。**
**理由不是"技术难"，而是【包里根本没有代码】**：能在主机侧追加的只有 **数据/表 + cfg**；命令处理分支、触觉决策逻辑都在 **ROM**，改不了。
**⇒ 而且它是单程门**（eFuse + 无刷回）。

### 4.2 路线 W2：写 **TF100A** 固件（明文！但够不着）

| 项 | 事实 | 出处 |
|---|---|---|
| 镜像形态 | ✅ **明文 ARM**（STM32F1 类 / Cortex-M3），56,480 B @ `0x19ABC`，有完整反汇编 | TF100A 反汇编 |
| 是否加密 | ❌ **不加密**（"三重定量结案"） | 同上 |
| 是否被 BIOS 验签 | ⚠️ **待证**：它在 Goodix 容器**之外**（Goodix `size+6` 区止于 `0x19A3C`，TF100A 从 `0x19ABC` 起）⇒ **理论上不归 Goodix 验签覆盖** | `early__TF100A_完整性验证报告.md` |
| ★ 致命点 1 | **镜像本身是截断的**（`UsageFault` 向量越界 ≥837 B；末尾是代码不是 `0xFF`） | 同上 |
| ★ 致命点 2 | **主机没有写它的通路** —— TF100A 是**纯 I2C 从机**（`OAR1=0x58` ⇒ 从机 `0x2C`），I2C1 从机通路**未接完**；且它**没有 PWM 输出路径**，`0x08008628`（"播放"包装）**调用图中 0 个调用者** | VIBRATION-CONCLUSION §五 |
| ★ 致命点 3 | 39 条命令的落点（I2C1 vs USART1）**未定** | §6.3 |

**⇒ W2 判定：⚠️ 理论上是**唯一**"可改固件"的目标，但需要**物理接入**。**
唯一确定的入口 = **SWD**（ST-Link / OpenOCD）：
```bash
openocd -f interface/stlink-v2.cfg -f target/stm32f1x.cfg
# 读：dump_image tf100a_full.bin 0x08000000 0x10000    ← 顺手补齐那 837 B
# 写：需先确认 RDP（read protection）等级
```
**⇒ 这已经不是"软件暴力"，是"上编程器"。** 且改完还要回答"改哪儿"——而 **TF100A 的触觉决策在 0x08008600–0x08009800，且"播放"函数不可达** ⇒ 改了也未必能被触发。

### 4.3 路线 W3：写 **BIOS/UEFI**（否决）

ESRT/UEFI 更新 + BIOS 白名单 + SPI 刷写风险 ⇒ `§20.11 C 部` 早已判为"不值得做"。

### 4.4 三条路横向对比（给喆做决策用）

| | W1 GT7868Q | **W2 TF100A** | W3 BIOS |
|---|---|---|---|
| 有没有代码可改 | ❌ 包里无代码 | ✅ **明文有代码** | — |
| 主机够不够得着 | ✅ 够得着（但改不出功能） | ❌ **够不着**（要 SWD） | ❌ |
| 能不能刷回 | ❌ 单程门 | ⚠️ 有 SWD 就能刷回 | ❌ |
| 违反"不插入"约束 | ❌ 不违反 | ✅ **违反** | ❌ 违反 |
| **结论** | ❌ 不可行 | **⚠️ 唯一形态，但代价最大** | ❌ |

**⇒ 一句话：所谓"直接写固件"，在**不改硬件**的前提下是**做不到加功能**的；能做到加功能的唯一目标（TF100A）又必须**上编程器**。**

## §5 ★ 暴力战场重排（带风险等级）—— "全方位暴力"到底还剩哪些面

> 纪律 154 落地后，任何"写设备"的暴力扫描**必须先划【语义已知区】并绕开它**。下面按**风险从低到高**重排。

### 5.1 战场清单（重排后）

| 代号 | 面 | 空间 | 需要什么 | 风险 | 是否新 | 期望 |
|---|---|---|---|---|---|---|
| **N0** | **只读全景 dump**（Col04 地址空间） | ≥32 KB | 设备 | **零**（只读） | 旧（§20.11 #36） | 中低 |
| **N1** | ★★ **Col02/Col04 的【未声明 RID】OUTPUT 报告**（**Linux hidraw**） | RID 0x00–0xFF | 设备 + **Linux live** | **中**（可能撞上 flash 处理器） | ✅ **全新** | **中低—中** |
| **N2** | ★★★ **Col02 的 6 组 feature 报逐个写探**（RID 2/6/9/11/12/13，**单变量、每次一个**） | 6 组 | 设备 | **低**（feature 写，已实测过 RID 2/9 无害） | ✅ **新角度**（受 §2.3 推论 1 启发） | 中低 |

### 5.2 ★ 本轮**新增**的两块战场，展开说

#### N2：Col02 的 feature 报逐个写探（**新角度**）

**为什么要重做**：§2.3 推论 1 说明 —— 业界"交出控制权"靠的是**写一个 feature 字段**（`auto trigger waveform`）。本机**有 6 组 feature 报**，但：
- 历史只测过 **RID 2**（改值 `effective:false`）与 **RID 9**（写 ok，读回 `0xEE`）；
- **RID 6（256 B）/ 11（66 B）/ 12（736 B）/ 13（4 B vendor `0xFF00`）从未被写过**。

**做法**：一次只写一个 RID，**写前先读基线、写后立刻用"点击震动"做人肉判据 + 用 `vib_probe.py` 做客观判据**；RID 13 是 vendor 页，**优先试**。
⚠️ **RID 6 那 256 B 页历史判定为"内容像签名/密钥，乱写风险不可控"** ⇒ **仍不写**（保留旧判定）。

#### N1：Linux hidraw 未声明 RID（**全新**）

**做法（分级）**：
1. **存活基线**：先发已知良好的只读帧 `0E 20 00 00 05 01 40 00 00 08`（读 `0x4000` 存活位），确认 `A7 E0 E5 B1`；
2. **只发"空载荷"**：`write(fd, [RID] + [0x00] * 64)` —— **不携带任何命令语义**；
3. **顺序**：先 `0x0E`（已知通道）→ 再 `0x02/0x06/0x09/0x0B/0x0C/0x0D`（已声明 feature RID）→ 再 `0x01/0x03..0x0F` → 最后 `0x10..0xFF`；
4. **每发一条立刻复查存活位**；**一旦存活位变化或读失败 ⇒ 立即停**（= 撞上了危险处理器）；
5. **判据**：`vib_probe.py`（Windows 侧麦克风）同步记录 → 客观判定"是否震了"。

### 5.3 ★ 必须写明的停止条件（纪律 154 的落地）

| 条件 | 动作 |
|---|---|
| RID 命中已知危险语义（`0x10`/`0x11`/`0x12`/`0x13` 出现在**载荷**里） | **不发** |
| 存活位 `0x4000` 读数变化 / 读失败 | **立即停**，跑 `lab__touchpad_rescue.py` |
| 任何一次出现"通道死亡"（`err=122`） | **立即停**（这是 2026-10-14 事故的前兆信号） |
| 累计发送 > 64 条仍无任何反应 | **停**，判定"IC 固件对该面完全无响应" |

## §6 判决（把话说到底）

| 问 | 答 |

| 那最终怎么办？ | **★ 路线 A 仍然是唯一确定可行解**（外置执行器 + 手势软件，¥40–65）。**若喆坚持要"从这块板子上抠出震动"，剩下的顺序是：N1 → N2 → N3 →（可选）N7。** |
