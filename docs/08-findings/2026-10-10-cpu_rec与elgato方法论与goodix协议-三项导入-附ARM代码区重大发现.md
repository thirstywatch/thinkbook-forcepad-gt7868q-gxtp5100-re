### 2.2 结论（严格区分三个层次）

| 层次 | 结论 | 置信度 |
|---|---|---|
| **事实** | 官方容器 `TB14P_GT7868Q_14030522_20240202.BIN` 在 **≈0x19F3C – ≈0x264xx（约 27–51 KB）** 含一段**未加扰的 ARM Thumb-2 机器码**，其前紧邻 ASCII 构建时间戳 `19:10:59` | ★★★★★ **四重证据，反汇编级 witness** |

### 2.3 ⚠️ 明确**不能**得出的结论

- ❌ **不能**说"GT7868Q 是 ARM 核" —— 缺少归属证据。
- ❌ **不能**说 C3（GT7868Q = 8051/Turbo51）被推翻 —— cpu_rec 未在**任何**区段识别出 8051，但那属工具不适用；而 ARM 段也可能属于**另一颗芯片**。

## 4. ★★★★ 任务③：`goodix-fp-dump` 协议层 —— 同厂商，可迁移

### 4.1 ★★★ 最刺眼的数值重合

`goodix.py` 的 host command 表（**Goodix 自家、指纹产品线**）：

```python
COMMAND_WRITE_SENSOR_REGISTER = 0x80    # ← 写寄存器
COMMAND_READ_SENSOR_REGISTER  = 0x82    # ← 读寄存器
COMMAND_UPLOAD_CONFIG_MCU     = 0x90
COMMAND_RESET                 = 0xa2
COMMAND_MCU_ERASE_APP         = 0xa4
COMMAND_READ_OTP              = 0xa6
COMMAND_FIRMWARE_VERSION      = 0xa8
COMMAND_ACK                   = 0xb0
COMMAND_WRITE_FIRMWARE        = 0xf0
COMMAND_READ_FIRMWARE         = 0xf2
COMMAND_CHECK_FIRMWARE        = 0xf4
```

**本案 cfg 下发通道的字节序是：`0x80` → IC 回 `0x82` → 写 `0x96F8` → `0x83` → 读结果 → `0x7D`。**

⇒ ★★★ **`0x80` = 写、`0x82` = 读，两处数值完全一致。**
⇒ **假说（🟡 未验证，跨产品线推测）**：`0x80`/`0x82` 可能是 **Goodix 全家族通用的"寄存器读写"操作码**，而非本项目私有。

> ⚠️ **必须标注的作用域**：goodix-fp 的 0x80/0x82 是 `cmd0<<4|cmd1<<1` **编码后**的值，且走 **USB bulk / SPI**（非 I²C-HID）；本案的 0x80/0x82 是 HID/IC 层的相位字节。**数值巧合 ≠ 同一编码**（纪律 110）。**须另立实验证伪**：若本案 `0x80` 写不同地址时 IC 的 `0x82` 应答行为与 goodix-fp 的 ACK 语义一致，则假说升级。

### 4.2 两层封装结构（可直接对照本案）

```python
# 外层 transport pack
[flags:1][length:2 LE][checksum:1 = sum(前3字节) & 0xff][payload]

# 内层 message protocol
[command:1][length+1:2 LE][payload][checksum = (0xaa - sum) & 0xff]
#                             ↑ checksum=True 时；否则填 0x88 = "无校验"哨兵
```

★ **`0x88` = "本条无校验"哨兵** —— 与本案 `7E 00 07`（与 flash 一致）/ `7E 00 02`（有差异）**是同一设计思想：用一个 magic 字节承载状态**。

### 4.3 ★★★ 可直接照搬的 4 条工程做法

| # | goodix-fp 做法 | 对本案的价值 |
|---|---|---|
| 1 | **`empty_buffer()`**：每次开设备先循环读到**超时**为止，把残留应答清空 | ★★★ **直接解决本案"复用缓冲区残留"**（第 18 轮的 `0E 20 00 00` 假回读）。**建议加进 `gxmem`/`lab__r2x` 的会话初始化** |
| 2 | **`ACK` 独立命令 `0xB0`**，bit0=有效 bit1=成功；**每条命令都强制校验 ACK** | 与本案结果码 `7E 00 xx` 同构；可对照其"ACK 后才是真应答"的两读模式 |
| 3 | **`write_firmware(offset, payload, number)`** = `[I offset][I len][I 序号][payload]`；`read_firmware(offset,length)`；`check_firmware(offset,length,checksum,hmac)` | ★ **"带偏移+长度+序号的固件写"三件套** —— 本案若要设计落盘序列，这是现成模板 |
| 4 | **双 transport 抽象**（`USBProtocol` / `SPIProtocol` 同一接口） | ★ 本案若要同时支持"HID 通道 / I²C 直通 / RW 脚本"，值得照此分层 |

### 4.4 一条风险对照

```python
class SPIProtocol:
    READ_SIZE = 256  # higher values could lock up the device until full power reset
```

⇒ **"读长度过大 ⇒ 设备锁死到必须完全断电重启"** —— 与本案 `0x0E` 类"**打挂板子两次**"**同型**。
⇒ **佐证本案的谨慎是对的**，也提示：**"单次事务长度上限"是这类 IC 的共性约束**。
