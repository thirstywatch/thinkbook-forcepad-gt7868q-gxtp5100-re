## 〇 摘要：整链一句话 + 结论总表

> **主机在环外。**
> 主机只能**读**：坐标与压力经 `Col02`（PTP）上报，压力量程 **0–2000**（libinput 侧标定）。
> 主机**发不出**触觉命令：`Col02` 的 `OutputReportByteLength = 0`，厂商通道只有 `Col04`。
> **"按下 → 震动"的判决与执行整体发生在模组内部**：GT7868Q 读 TF100A 的 **128 字节寄存器文件**取压力 →
> 按自己的判据决定"点击" → 经内部 I²C 让 **AW86927** 播放波形 → 驱动 **LRA**。
> 判决所依据的参数（时长阶梯、强度包络、阈值）**随 `tpcfgsid<sid>.cfg` 下发给 GT7868Q**。
> **⇒ 想改"什么时候震"，只有两个实体可下手：GT7868Q 的 cfg（参数）与 TF100A 的固件（判据）。**

| # | 环节 | 载体 | 级别 |
|---|---|---|---|
| 1 | 主机 ↔ GT7868Q | I²C 从地址 **`0x2C`**（HID over I²C） | ✅ |
| 2 | GT7868Q → 主机 | `Col01` 鼠标 / `Col02` PTP（坐标 + `ABS_PRESSURE` 0–2000）/ `Col04` 厂商 | ✅ |
| 3 | 主机 → GT7868Q | 只有 `Col04`（`0E 20` 等厂商报文） | ✅ |
| 4 | GT7868Q → TF100A | 模组内部 I²C1，TF100A 从机 `0x2C`，**128 B 寄存器文件** | ⚠️ 强（本轮拿到从机端全部代码，见 §5.3） |
| 5 | TF100A 内部 | **ADC1** 采力 + TIM3 节拍 + 判据 `\|基线−当前\| > 40` | ✅ |
| 6 | GT7868Q → AW86927 | 内部 I²C，`0x5A`/`0x5B`，**平时断电** | ⚠️ |
| 7 | AW86927 → LRA | `HDP`/`HDN`（pin 7 / pin 5） | ⚠️ |
| 8 | 判决"何时震" | **GT7868Q 片上 ROM**，参数来自 cfg | 🔶 |
| 9 | 参数下发 | `tpcfgsid<sid>.cfg`（TLV），写 GT7868Q 的 cfg 区 | ✅ |

## 一 器件与总线（物理层）

| 器件 | 角色 | 标识 / 关键量 |
|---|---|---|
| **汇顶 GT7868Q**（Windows 实例名 `GXTP5100`） | 触控主控 · HID 主机接口 | `ACPI\GXTP5100\1` · `VID_27C6/PID_01E9` · 主机 I²C 从地址 **`0x2C`** · 家族名 `YELSTO`(=YELLOWSTONE) |
| **钛方 TF100A** | 压力采集 MCU | 片内 I²C1 从机 **`0x2C`** · **STM32F1 / Cortex-M3**（本轮定案，见 §5.1） |
| **艾为 AW86927FCR** | 触觉驱动 IC | 丝印 `CA4F` · I²C `0x5A`/`0x5B` · `HDP`/`HDN` = pin 7 / pin 5 |
| **LRA 线性马达** | 执行器 | FRU `5T60S94326`，7.5 × 14 mm |

**★ 一个容易看错的地方**：`0x2C` 出现两次，但**不是同一个东西** ——
① 主机总线上 **GT7868Q** 的地址；② 模组内部 I²C1 上 **TF100A** 的地址。
（项目 `method/09-memory-map.md` §①/①已记，本轮复核无误。）

## 二 主机侧：为什么"永远碰不到震动"（四条独立理由）

| # | 理由 | 一级依据 |
|---|---|---|
| **1** | **描述符层**：PTP 主体集合 `Col02` 的 `OutputReportByteLength = 0` ⇒ 主机**物理上发不出**输出报表；Haptics 页 `0x0E` 下只有 `Intensity`，**没有**微软规范要求的 `Manual Trigger (0x0E/0x21)`。全设备只有 `Col04` 有 `Out=65` | 描述符 |
| **2** | **固件层**：TF100A 的 39 条命令表里**没有任何马达/触觉命令**；`0x0B00`/`0x0D00` 两条写的是 TF100A 自己的缓冲，不是马达 | 反汇编 |
| **3** | **拓扑层**：`0x5A` 不在五条主机 I²C 的任何一条上；**UEFI 刷写器 `GoodixTpDxe` 里的 `0x5A/0x5B` 全是跳转目标、不是立即数**（本轮新增） | DSDT 全扫 + 刷写器反汇编 |
| **4** | **参数层**：触觉参数只随 `tpcfgsid<sid>.cfg` 下发，在固件包里 **0 命中** | cfg TLV + 固件搜索 |

### 2.1 ★ 压力标度：libinput quirk 给出的官方可用数字

`ca4f-hunt/gt7868q-driver/local-overrides.quirks`（社区针对**本机 `MatchProduct=0x01E9`** 的调优文件）：

```
[Lenovo Thinkbook G6+ IMH - Goodix GT7868Q]
MatchVendor=0x27C6
MatchProduct=0x01E9
AttrPressureRange=2:0
AttrPalmPressureThreshold=600
AttrThumbPressureThreshold=1000
```
注释原文（重要）：
> 「默认按下阈值**高于**掌压检测阈值，导致光标无法移动」
> 「最大压力检测被限制在 **1000**，尽管设备声称支持到 **2000**」

**⇒ 得到三条可用数值（✅ 半确认，来自社区实测配置）**：
**① `ABS_PRESSURE` 的名义量程 = 0…2000；② 掌压门限 600；③ 拇指/点击门限 1000。**

★ 同一文件里还有一条**同芯片另一机型**的条目，它对"触觉"这件事很关键：
```
[Lenovo ThinkBook 16 G7+ IAH ForcePad]
MatchName=*GXTP5100*
MatchUdevType=touchpad
ModelPressurePad=1
```
**⇒ 同款主控在 libinput 里被登记为 `ModelPressurePad`** ⇒ 上游把这类设备当"压力板（自带触觉反馈）"建模 ——
**即"震动由设备自己产生"是上游的既定认知**，与本项目"主机在环外"的结论一致。

### 3.2 子固件表：`type` 的真语义 = **update-flag 的位号**

```c
/* gtx3_gtx3_update.cpp :: fw_update() —— 官方原文 */
for (i = 0; i < sub_fw_num; i++) {
    sub_fw_type = fw_data[sub_fw_info_pos];
    sub_fw_len  = (fw_data[sub_fw_info_pos+1] << 24) | (fw_data[sub_fw_info_pos+2] << 16)
                | (fw_data[sub_fw_info_pos+3] << 8)  |  fw_data[sub_fw_info_pos+4];
    sub_fw_flash_addr = (fw_data[sub_fw_info_pos+5] << 8) | fw_data[sub_fw_info_pos+6];
    sub_fw_flash_addr = sub_fw_flash_addr << 8;          /* ← 低字节必为 0 ⇒ 地址恒 256 对齐 */
    if (!(firmware_flag & (0x01 << sub_fw_type))) {      /* ← type 就是位号 */
        fw_image_offset += sub_fw_len;  sub_fw_info_pos += 8;  continue;   /* 跳过 */
    }
    load_sub_firmware(sub_fw_flash_addr, &fw_data[fw_image_offset], sub_fw_len);
    fw_image_offset += sub_fw_len;  sub_fw_info_pos += 8;
}
```

### 3.5 ★★★ 命令寄存器与刷写报文（官方原文）

```c
/* gtx2_update.cpp :: load_sub_firmware() —— 一直缺的那块，第四轮补到 */
unsigned char buf_load_flash[15] = {0x0e, 0x12, 0x00, 0x00, 0x06};
#define RAM_BUFFER_SIZE     4096
#define BL_STATE_ADDR       0x5095      /* 期望 0xDD */
#define FLASH_RESULT_ADDR   0x5096      /* 期望 0xAA */
#define FLASH_BUFFER_ADDR   0xc000      /* RAM 中转缓冲 */

while (retry_load < GDIX_RETRY_TIMES && load_data_len != len) {
    unitlen = min(len - load_data_len, RAM_BUFFER_SIZE);
    dev->Write(FLASH_BUFFER_ADDR, &fw_data[load_data_len], unitlen);      // ① 数据进 RAM
    for (check_sum = 0, i = 0; i < unitlen; i += 2)                       // ② 16 位大端按字求和
        check_sum += (fw_data[load_data_len+i] << 8) + fw_data[load_data_len+i+1];
    buf_load_flash[5] = unitlen >> 8;  buf_load_flash[6] = unitlen & 0xFF;    // ③ 发 0E 12
    buf_load_flash[7] = flash_addr >> 16; buf_load_flash[8] = (flash_addr >> 8) & 0xFF;
    buf_load_flash[9] = check_sum >> 8;  buf_load_flash[10] = check_sum & 0xFF;
    dev->Write(buf_load_flash, 11);
    usleep(80000);
    retry = 100;                                                          // ④ 轮询 0x5096==0xAA
    do { dev->Read(FLASH_RESULT_ADDR, temp_buf, 1);
         if (temp_buf[0] == 0xAA) break; usleep(2000); } while (--retry);
    if (!retry) { retry_load++; ret = -1; }                               //    失败只重传这一块
    else { load_data_len += unitlen;  flash_addr += unitlen;
           dev->Write(0x5096, &dummy, 1);  ret = 0; }                     //    清状态
}
```

### 3.6 ★★★ 第三源交叉：UEFI 刷写器 `GoodixTpDxe`

`GoodixTpDxe`（48,590 B，**本机 BIOS 里真正运行的那份**）反汇编（`data/reference/lab__GoodixTpDxe.asm.txt`）：

```
0x10D6   mov cx, 0x96f8                    ← CFG_START_ADDR
0x145B   mov cx, 0x4160   ; 0x15A3 mov cx, 0x4160   ← CMD_ADDR
0x4B18   mov cx, 0x5095   ; 0x4B3B mov edx, 0x5095  ← BL_STATE
0x486E/0x4887/0x48E2/0x4958  mov cx/edx, 0x5096    ← FLASH_RESULT
0x46D3   mov cx, 0xc000                    ← FLASH_BUFFER
0x4D75   mov dword ptr [rsp+0x34], 0x19000 ← CFG_FLASH_ADDR
```
**⇒ 这六个地址现在有【三个独立来源】**：官方 Linux 工具 `gdixupdate`、官方 GTX8 驱动、**本机 BIOS 的 UEFI 驱动**。
**⇒ 从"项目自测"升级为"厂商三方交叉"。**

**★ 同一份反汇编里一条否证**：`0x5A`（4 次）与 `0x5B`（7 次）**全部是跳转目标**（`je 0x5a2e`、`jge 0x5b81`…），
**没有一处是立即数操作数** ⇒ **连最有理由碰触觉 IC 的那条路径也不碰 `0x5A`**。

### 4.1 解扰：**逐块独立确证**，相位是常量 572

| `0x40000400` | 7 | **TIM3** | ✅ 精确 |
| `0x40004400` | 2 | **USART2** | ✅ 存在（引用极少） |
| `0x40007000` `+004` | 3 | **PWR** | ✅ 精确 |
| `0xE000E010` / `E100` / `E400` | 各 1 | SysTick / NVIC ISER / IPR | ✅ 精确 |
| （`load_sub_firmware` 常量）`0x40010C00` | — | **GPIOB**（`0x40005400 + 0xB800`） | ✅ 精确 |

**★★★ 两条定案：**
1. **MCU 家族 = STM32F1（Cortex-M3）** —— RCC / FLASH / I2C1 / TIM3 / ADC1 / PWR 的**寄存器偏移逐项吻合**，
   不再是"F1 类"的模糊说法。
2. **力的采集 = ADC 模拟量**（`ADC1`），不是数字传感器；对外**只做从机**。

### 5.2 压力判据（项目既有结论 + 本轮定位）

- **判据**：`|基线 − 当前| > 40`，`40` 是两处 Thumb 指令的立即数 `0x28`
  → 载体 file `0x1A54C`（`28 31`→`08 31`）与 `0x1A578`（`28 39`→`08 39`），**仅 2 字节**；
  补丁镜像由 `tools/firmware/make_tf100a_sens_patch.py` 生成（**已验证与手工件逐字节相同**）。
- **★ 本轮新增数值旁证**：cfg 里出现过 `18 1e 28`（=24/30/**40**）**连续重复 4 次**（`sid0.bin +0x349`）。
  ⚠️ **数值相同 ≠ 同一字段**，只记为**线索**，不得当结论。

### 5.3 ★★★ I²C1 从机：双 128 B 寄存器窗口 + ctx + 三个回调（本轮核心新增）

**ctx 基址 = `0x20004128 + 0xC = 0x20004134`**（`movw r0,#0x4128 / movt r0,#0x2000 / adds r0,#0xc`，代码里被全局引用 20+ 处）。

**从机事件处理（`0x08008A70` 起，原样）**：
```asm
08008A70  ldrb.w  r1,[r0,#0x107]      ; ctx->state
08008A74  and     r2, r1, #3
08008A78  cmp     r2, #2
08008A7A  beq     #0x8008AB8          ; → 数据阶段
08008A7C  cmp     r2, #0
08008A80  bxne    lr
; ---- 状态 0：收到寄存器地址 ----
08008A82  and     r1, r1, #0xfc
08008A86  ldrb.w  r2,[r0,#0x106]
08008A8A  adds    r1, #2
08008A8C  strb.w  r1,[r0,#0x107]      ; state = 2
08008A90  orr     r1, r2, #0x80
08008A98  movw    r1, #0x5410 / movt r1, #0x4000   ; 0x40005410 = I2C1_DR
08008AA0  ldr     r2,[r1]
08008AA4  strh.w  r2,[r0,#0x104]      ; ctx+0x104 = 收到的“寄存器号”
08008AAA  ldrh.w  r2,[r0,#0x102]      ; ctx+0x102 = rx_index
08008AAE  adds    r3, r2, #1
08008AB0  strh.w  r3,[r0,#0x102]
08008AB4  strb    r1,[r0, r2]         ; ★ 写入 ctx->rxbuf[rx_index++]
; ---- 状态 2：数据阶段 ----
08008AB8  ldrh.w  r1,[r0,#0x102]
08008ABC  cmp     r1, #0x7f           ; ★ 窗口上限 127
08008ABE  bhi     #0x8008AD4
08008AC0  movw    r2, #0x5410 / movt r2, #0x4000
08008AC8  ldr     r2,[r2]
08008ACA  adds    r3, r1, #1
08008ACC  strh.w  r3,[r0,#0x102]
08008AD0  strb    r2,[r0, r1]         ; ★ ctx->rxbuf[127] 收满即停
08008AD4  ldrb.w  r1,[r0,#0x106]      ; 缓冲满 ⇒ 改状态位
08008AD8  and     r1, r1, #0xf1
08008ADC  adds    r1, #8
08008ADE  strb.w  r1,[r0,#0x106]
; ---- 发送（读）侧 ----
08008AE4  push    {r4, lr}
08008AE6  ldrh.w  r1,[r0,#0x100]      ; ctx+0x100 = tx_index
08008AEA  mov     r4, r0
08008AEC  movw    r0, #0x5400 / movt r0, #0x4000
08008AF0  cmp     r1, #0x7f
08008AF2  bhi     #0x8008B18
08008AF8  ldrb.w  r2,[r4,#0x106]
08008AFC  orr     r2, r2, #0x40
08008B00  strb.w  r2,[r4,#0x106]
08008B04  adds    r2, r1, #1
08008B06  strh.w  r2,[r4,#0x100]
08008B0A  add     r1, r4
08008B0C  ldrb.w  r1,[r1,#0x80]       ; ★ 从 ctx+0x80 + tx_index 取字节
08008B14  b.w     #0x800FBF8          ; → 写入 I2C1_DR
08008B18  movs    r1, #0x55           ; 越界 ⇒ 返回 0x55
```
**★★★ 由此得到 TF100A 的对外接口（这是"联动"的接口层）：**

```
ctx (0x20004134) 布局
  +0x000 : 128 B  接收缓冲 rxbuf[0..127]      ← GT7868Q 写进来的寄存器值
  +0x080 : 128 B  发送缓冲 txbuf[0..127]      ← GT7868Q 读走的寄存器值
  +0x100 : u16    tx_index (0..127)
  +0x102 : u16    rx_index (0..127)
  +0x104 : u16    收到的“寄存器号”/末字节
  +0x106 : u8     flags (bit7/6/5/2/1 都被读写)
  +0x107 : u8     state (0=收寄存器号, 2=收数据)
  +0x108..0x10B : 4 B  → 传给 #0x800FE3C(0x1F/0x20, …) 的引脚配置参数
  +0x10C : u8     → 传给 I2C 相关调用
  +0x110 : 参数   → 传给 I2C_Init@0x0800FA20
  +0x114 : 函数指针 → 初始化尾部 blx
  +0x118 : 函数指针 → I2C 事件里 blx（置 flags bit5 后调用）
  +0x11C : 函数指针 → I2C 事件里 blx（以 flags bit6 为参数调用！）
```
**★ 三个回调都由 I²C 事件触发** ⇒ **"主机（GT7868Q）写了某个寄存器 ⇒ TF100A 内部回调被调用"** 是既成的机制。
**★★ 一个绝对吻合的旁证**：项目 `method/10-semantics.md` 独立认定
「**响应缓冲 `0x200041B4`**」；而 `ctx + 0x80 = 0x20004134 + 0x80 = 0x200041B4` ✅✅ **逐位相同**。
⇒ **两条独立路径给出同一地址**，从机窗口布局成立。

**★ I²C1 初始化序列（`0x08008B88` 起，原样）**：
```asm
08008B88  movw r5,#0x5400 / movt r5,#0x4000     ; r5 = 0x40005400 = I2C1
08008B94  mov r0,r5 ; movs r2,#0 ; bl #0x800FA20   ; I2C_Init(I2C1, [ctx+0x110], 0)
08008BA0  mov r0,r5 ; movs r1,#0 ; movs r2,#0 ; bl #0x800FD24
08008BAA  mov r0,r5 ; movw r1,#0x109 ; bl #0x800FC20
08008BB4  mov r0,r5 ; bl #0x800FC0C
08008BBA  mov r0,r5 ; movs r1,#1 ; bl #0x800F9CC
08008BC2  mov r0,r5 ; movs r1,#1 ; bl #0x800F9F8
08008BCA  ldrb.w r1,[r4,#0x108] ; ldrb.w r2,[r4,#0x109] ; movs r0,#0x1f ; bl #0x800FE3C
08008BD8  ldrb.w r1,[r4,#0x10A] ; ldrb.w r2,[r4,#0x10B] ; movs r0,#0x20 ; bl #0x800FE3C
08008BE6  add.w r5,r5,#0xb800                    ; ★ 0x40005400 + 0xB800 = 0x40010C00 = GPIOB
08008BEA  mov r0,r5 ; movs r1,#0x1c ; movs r2,#3 ; movs r3,#0x40 ; bl #0x800F81C
08008BF6  mov r0,r5 ; movs r1,#0x1c ; movs r2,#3 ; movs r3,#0x80 ; bl #0x800F81C
```
**★ 项目当初那条"B1 更正"是对的**：真正的证据是 **`I2C_Init@0x0800FA20`**（本行 08008B98），
不是 `0x0800894C`。**本轮从从机端把整条初始化链补全了。**

### 5.4 TF100A ↔ GT7868Q 的接口（级别：⚠️ 半确认，本轮大幅加强）

**已确认**：TF100A 是 **I²C1 从机**，对外是 **128 字节寄存器文件**（读窗口 / 写窗口各一）
，并用 `ctx+0x104` 存"收到的寄存器号"。**⇒ 需要一个主机来读写它。**
**未确认**：那个主机是 GT7868Q（🔶 强推断：模组内只有它能当主机；主机侧 I²C 已被四条理由封死）。
**⇒ 描述协议应为**：`[从地址 0x2C][寄存器号 0x00–0x7F][数据…]`（从机端逻辑已看到 `state=0 → 收寄存器号 → state=2 → 收数据`）。
**⚠️ 待证**：寄存器窗口里每个号对应什么（**这是"路径 C"，见 §4.9**）。

## 七 `tpcfgsid<sid>.cfg` 协议（含官方 cfg_bin 与 TLV 双向）

### 7.1 64 B 文件头（5 个字段跨样本成立）

| 偏移 | 字段 | `sid0.bin` | `sid3.bin` |
|---|---|---|---|
| `0x00` | 厂商名 | `PCB\0…` | **`LaiBao\0\0`** |
| `0x08` | **`ic_type`** | **`7867`** | **`7986P`** |

| `0x3B` | `u16LE` = TLV 区长度 | 1238 | 1802 |
| `0x3D` | `u8` = **条目数** | 55 | 53 |
| `0x40` | TLV 区起点 | ✓ | ✓ |

**闭合自校验**：`0x40 + [0x3B] == 文件长度`（1302 / 1866，**两份都精确相等**）。
**⇒ 拿任何 `sid*.bin` 可直接读身份，不必猜、不必靠文件名。**

### 7.2 帧序：**`[LEN:u8][TAG:u8][payload LEN-2]`，起点 `0x40`**

| 文件 | 帧数 | 覆盖 | TAG 严格递增 | `[0x3D]` 声明 |
|---|---|---|---|---|
| `sid0.bin` | **55** | **1234/1238 = 99.7%** | **54/54** | **55** ✅ |
| `sid3.bin` | **53** | **1798/1802 = 99.8%** | **52/52** | **53** ✅ |
| `sid2.bin` | ✗ 不同格式 | — | — | `0x40+5139 ≫ 文件长` |

> ### ⚠️ 一处自我更正（本轮真实踩到）
> 我先按 `[TAG][LEN]`、**从偏移 0** 起解析，报出"98.4% 覆盖" —— **错的**：
> 覆盖率被"解析失败就跳 1 字节"的兜底逻辑抬高了（37 条里只有约 20 条真有 LEN）。
> **判帧序最硬的判据不是覆盖率，而是「`[0x3D]` 声明的条目数是否与实解帧数严格相等」**（55=55、53=53）。
> `method/10-semantics.md` §5.2 本来就是对的，其结论**保持**。

### 7.3 ★★ 触觉区 = `TAG 0x50 – 0x7A`（本轮独立复核通过）

```
0x60 0x61 0x62 0x63 0x65 0x66 0x68 0x6a 0x73 0x74 0x75 0x76 0x77 0x78 0x79 0x7a
```

### 7.4 ★ 强度/时间表的实测形态

| 项 | 实测 | 位置 |
|---|---|---|
| ~~u16 强度斜坡~~ | 🔴 **本轮撤回（虚警）**：`256, 770, 1284, 1798 …` 的"步长恒定 514"**不是结构** —— 它是"**连续整数/连续字节按 2 字节分组**"的必然产物（`n,n+1` 读作 u16BE = 257n+1，相邻项差 514）。实测该段字节真身是 `01 02 03 04 05 06 0c 0d 0e 0f 10 11 …` = **一张"排序的索引列表 + ff 填充"**，不是什么强度斜坡 | `sid0 +0x3E` 起；本机 cfg 也有同类表 |

| 逐项常量数组 | `112(0x70)×N`（`+0x1A0..`）、`70(0x46)×N`（`+0x260..`）、`14(0x0E)×N`（`+0x2B0..`）—— 每个条目一个值，长度随机型 | 与旧结论"112×N / 70×25 / 14×32"一致 |

```
+0x0080（= file 0x19ABC = 加载基址 0x08005000）:
```

```
                        fe 06 0a 0c ac 07 e0 00 5a 00 82 05 05 02 95 07 02 01 00 00
```

| 相对偏移 | 本机 | capA / capB（机型 B） | 判读 |
|---|---|---:|---|
| `+0xFC` u16BE | `0xFFFF` | `0xFFFF` | 🔴 **不是字段**（长 `ff` 填充段）；第十一轮原文误把 `+0xFE` 读成 `+0xFC`，见登记表 **B8** |
| **`+0xFE`** u16BE | **`0x3563` = 13667** | **`0x3D6F` = 15727** | 🆕 **随机型变的 u16**，此前**从未登记**（两块板都只有这一处）；候选：电极数/物理尺寸/校验和 —— **未定** |
| `+0x100`..`+0x10B` | `05 09 01 02 01 05 18 34 13 88 00 00` | **逐字节相同** | 共享常量块（跨机型不变 ⇒ 与"分辨率/机型"无关） |
| `+0x10C` | `fe 06` | `fe 06` | 共享 |
| `+0x10E` | `0a` | `0a` | 共享（**但见 §三十二：它不是"帧标签"**） |
| **`+0x10F`** u16BE | **4150** | **3244** | = X 点数（描述符 4149 / 预测 3243）★ |
| **`+0x111`** u16BE | **2148** | **2016** | = Y 点数（描述符 2147 / 预测 2015）★ |
| `+0x113` | 90 | 90 | 三份全等 ⇒ **不是按板调的量** |
| `+0x115` | **120** | **130 / 130** | 随机型变 |
| `+0x117` | 1285 | 1285 | 三份全等 |

**★ 新增结论（结构层）**：`+0x113` = 90 与 `+0x117` = 1285 **在"另一台机器"上也精确相同** ⇒
这两个值**不是机型参数**（它们才是"家族常量"）；**只有 `+0x10F / +0x111 / +0x115 / +0xFC` 四处随机型变**。
⇒ "按板子调的参数"候选**收敛到 4 个位置**，其中 2 个已被 X/Y 占用，**剩下 `+0x115` 与 `+0xFC`**。
（这也**削弱**了 `+0x113` 作为 `trigger_offset` 的可能：它跨机型不变。）

## 三十 ★★★★★ 跨代「已知答案」：手机 cfgs 里的 X/Y = 该机真实面板分辨率

3 份真实 Berlin/GT9916 cfg 包（`ic_type='Berlin'`, `hw_pid='9916'/'9916K'/'9916R'`）：

| 样本 | 设备 | 真实面板 | cfg 数据里查到的 u16LE 相邻对 | 出现次数 |
|---|---|---|---|---:|
| `lfs-moto-cybert.dat` | moto cybert | **1220 × 2712** | `c4 04 98 0a` = **1220, 2712** | 1（@cfg+`0xB8`） |
| `lfs-moto-dubai-csot.dat` | moto dubai（CSOT 屏） | **1080 × 2400** | `38 04 60 09` = **1080, 2400** | **2**（`0xA0` 与 `0xB8`） |
| `lfs-xiaomi-manet.dat` | xiaomi manet | **1440 × 3200** | `a0 05 80 0c` = **1440, 3200** | **2**（`0xA0` 与 `0xB8`） |

**★ 关键：`0xA0` 处那一段在 dubai 与 manet 上逐字段对齐，且"常量位"完全相同：**

```
dubai  @cfg+0xA0  1080, 2400,  105, 140, 30, 40, 60, 80,  70, 70, 2570, 0
manet  @cfg+0xA0  1440, 3200,   90, 140, 30, 40, 60, 80,   5, 35,  261, 0
                  └── 随板变 ──┘  └── 变 ┘ └─── 5 个跨板全等 ───┘  └─ 随板变 ─┘
```

**⇒ 结论（诚实定级）**：

| 断言 | 证据 | 定级 |
|---|---|---|
| Goodix **cfg 里确实承载"X/Y 坐标量程"，且是相邻一对 u16** | 3 块**已知面板**各自命中自己的真实分辨率 | **★★★ 强（跨代、独立、已知答案）** |
| 该量程的语义是**"坐标点数"**（= 输入设备 `LogicalMax` **+ 1**） | 本机 4150/2148 ↔ 描述符 4149/2147（X、Y 同时 +1）；手机 1080 对 1080 px 宽的面板（设备 max 应为 1079） | **★★ 中强**（手机侧仍依赖"面板像素数 = max+1"这一常识，未读到其描述符） |
| 本机那对就在 **`+0x10F`/`+0x111`** | 本机内部证据（4 副本 / 跨机型变化 / 偏移闭合） | **★★★ 强（我族内部）** |

> **⇒ `+1` 规则现在从"半确认"升到【已确认（语义层）】**：缺的不再是"这个字段是什么"，而是"**另一台 GT7868Q 上同一个偏移是不是同一个字段**"（只有对外要一个数能补）。

**⚠️ 同一批数据给出的一个重要警告**：手机的字段是 **u16LE**，本机是 **u16BE**；
且 cybert 那一段比 dubai/manet **多插入 3 字节** ⇒ **跨代/跨机型"按偏移逐字节比"依旧不可靠**（§十五 的教训在此复现）。

## 三十二 🔴 本轮我自己枪毙的一条假设（分辨力检验当场判死）

**假设**：cfg body 里有一段是 `[TAG:u8][LEN:u8][payload LEN-2]` 的**帧链**。触发点：从 `+0x132` 起能连出 **6 帧**、且最后一帧结束位置**精确闭合**，看起来非常像结构。

**分辨力检验（`lab__r12_3_frame.py`）**：

| 数据 | 最长"闭链"帧数 |
|---|---:|
| 本机 cfg body（真实） | **8** |
| 真随机 1024 B（3 次） | 4 / 4 / 5 |
| 本机字节**打乱**后（保留直方图） | **5** |

**⇒ 判死**：随机数据就能连出 **4–5 帧**，真实数据只多 3 帧；而最长的那条链内容是 `00 0e 00 0e …`（LEN 值分布里 `0x0e` 独占 141 次）——
**它是"重复的 u16=0x0e00"这一数据形态的产物，不是格式**。
**⇒ 6 帧"精确闭合"落在偶然能达到的区间内，不构成证据。已撤回。**
（这正是项目 §5.2 / §二十七 那条纪律的又一次生效：**"能对上"不算证据，先证明它能把已知答案捞出来、且在对照上失败。**）
