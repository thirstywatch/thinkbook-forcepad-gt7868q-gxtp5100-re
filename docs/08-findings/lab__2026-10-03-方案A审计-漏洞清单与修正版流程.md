| | |

## 一、🔴🔴 漏洞 1（致命）：RWE 的「I²C/SMBus」不是我们要的那条总线

### 证据（四条，互相独立）

| # | 证据 | 出处 |
|---|---|---|
| 1 | 官方支持列表把能力写作 **"SMBus Controller: Intel ICH4/5/6/7/8/9/10 · SCH · PCH · SiS · VIA · ULi · ATI · nVidia"** —— **全是 SMBus 主机控制器，没有任何 Serial IO / DesignWare I²C** | `rweverything.com/?p=11` |
| 2 | 帮助文件里的能力页标题就是 **"SMBus Chipset Support List"**，且注明 **"Note1: SMBus function will not available if the chipset cannot be detected"** | 解包出的 `smbuschipsetsupportlist.htm` |
| 3 | 设备页原文：**"This function allow users to access any address on SMBus"** | `smbusdevice.htm` |
| 4 | 实物日志：`Log.txt` 里 RWE 自己打印 **`SMBUS detected: Intel PCH`** | `rwe\Win64\Portable\Log.txt` |

### ⇒ 后果

本项目**已经**用 PawnIO 的签名模块 `SmbusI801.bin`（`ioctl_smbus_xfer`）扫过 PCH SMBus，
结论是「**有阳性对照 `0x44`，但没有 `0x5A`**」（《全书》§8.2）。
⇒ **照《方案A》去做，等于把已经做过、已知是负面的那次实验再做一遍**，
而且会误以为是"关掉安全机制后 RWE 扫过了，所以设备不在主机总线上"。

> ### ⚠️ 这是本次审计最要紧的一条：**《方案A》第 3 节的判读表全部作废。**

## 二、★★ 漏洞 2~4：即使换了正确的总线，判读仍然不成立

### 漏洞 2：`hidi2c` 正占着 I2C0

`ACPI\GXTP5100\1` 由 inbox `hidi2c` 驱动，**它一直在对 `0x2C` 收发触摸数据**。
DesignWare 控制器**只有一个 master FSM** ⇒ 我们从 RWE 发起的传输会与 `hidi2c` **交错**：
- 我们的事务可能被 abort ⇒ **假阴性**
- 或 `hidi2c` 的传输被打断 ⇒ 触控板短时失灵

《方案A》只写了"读的时候手别碰触控板"——**这不够**。

### 漏洞 3：★ 没有**阳性对照** ⇒ "无应答"无法判读

本项目自己的纪律（第 32、48 条）就是"**扫描没找到时先怀疑扫描本身**"。
原方案里没有任何"这条总线是对的"的独立证据。

> ### ★★★ 修正（本次审计新增，值最高的一条）：**划手指做阳性对照**
>
> DesignWare 的 `IC_STATUS`（BAR + `0x70`）里有：
> `bit0 ACTIVITY`、`bit1 TFNF`、`bit3 RFNE`、**`bit5 MST_ACTIVITY`**。
>
> **在 RWE 的 Memory 窗口打开 `BAR + 0x70` 并开自动刷新（`MemoryInterval`），
> 同时用手指快速划过触控板 —— 如果 bit0/bit5 在跳，就证明了"我们读的确实是触控板那条总线"。**
>
> **全程只读、零风险、不依赖任何工具能力。**

### 漏洞 4：读不到 CHIPID ≠ 设备不在

三种假阴性来源必须分开：
| 现象 | 含义 |
|---|---|
| `IC_TX_ABRT_SOURCE`(BAR+`0x80`) **≠ 0**（bit0 = 7 位地址 NAK） | 才是"这个地址没有设备应答" |
| 轮询超时 / 一直不 STOP_DET | 总线被占 / 时序问题，**不是** NAK |
| 读到却不是 `0x92/0x70` | 可能是 `0x5B`（`AD` 脚决定）；或芯片被 RESET 脚拉住 |

## 三、🟠 漏洞 5~9

| # | 漏洞 | 后果 | 修正 |
|---|---|---|---|
| **5** | 《方案A》自己承认"黑名单**可能由 UEFI 变量下发**，只改注册表无效"；本项目实测 `RequireMicrosoftSignedBootChain = 1` | 白重启一次 | 重启后**先验证三个值**；不生效才考虑进 BIOS 关 Secure Boot（这一步要单独决策） |
| **6** | **CONT 模式会持续震动到 STOP**（`0x09←0x01` 之后不会自己停） | 芯片可能一直震；**RWE 崩了不会自动停** | 写完 GO **立刻**读 `0x3F` 并写 `0x09←0x02`；知道"**断电/拔电池可复位**" |
| **7** | 操作卡（`poc\aw86927-操作卡.txt`）的"还原"一节**是空的** —— dryrun 后端不知道原值 | 不知道要还原成什么 | 用下面 §五 的**手工原值记录表** |
| **8** | `W32` 是**物理内存写**，写错地址会碰别的 MMIO | 可能改到不相关设备 | 只允许在 `[BAR, BAR+0x1000)` 内；**每次写前先 `R32` 读回确认地址** |
| **9** | RWE **v1.7 是 2017 年**的，且 SMBus 功能"识别不到芯片组就不可用" | 对 MTL（2023）的 SMBus 页面可能直接不可用 | **但 MMIO 路线与版本无关**（只是物理内存读写）⇒ **这反而成为选 MMIO 路线的又一个理由** |

## 四、★ 审计的正面产出：RWE 可以做**脚本化 MMIO**

从解包出的 `command.htm` / `command_line.htm` 实测确认（**全部是原文，不是我猜的**）：

| 能力 | 语法（原文） |
|---|---|
| **物理内存读** | `R <address>` / `R16` / **`R32 <address>`** |
| **物理内存写** | `W <address> <value>` / `W16` / **`W32 <address> <value>`** |
| PCI 配置读 | `RPCI32 <bus#> <dev#> <fun#> <offset>`（函数式：`Local0 = Rpci32(0,0x15,0,0x10)`） |
| 找 PCI 设备 | `FPCI <DeviceID+VendorID> [Index]` |
| **循环** | **`LOOP{count, cmds...}`**（`count=0` 无限） |
| **带超时的等待** | **`WAIT{result, timeout, cmds...}`** |
| 条件跳出 | `BKIF0(cmds...)` / `BKIF1(cmds...)`（在 `CMDS/LOOP/WAIT` 组内跳出） |
| 延时 | `DELAY <ms>` |
| 打印 | `COUT <msg>` / `CERR <msg>`，格式符 `%[0]L<d/h/b>`（如 `%L0h`） |
| 赋值与算术 | `SETENV` / `ADD` `SUB` `AND` `OR` `SHL` `SHR` `CMZ` `BSWP` …（函数式：`Local0=And(Local1,0xfffffff0)`） |
| **命令行自动化** | **`Rw /Command=<file> /LogFile=<file> /LogDate /LogTime`**，或 `Rw /Command="cmd1;cmd2..."` |

> ⇒ **这解决了"没有 PawnIO 模块就无法脚本化访问 I2C0"的问题。**
> RWE 不需要认识这块芯片组，它只是读/写物理地址。

## 五、✅ 修正版流程（W1-R2）

> 全程需要**管理员**。**第 0 步到第 2 步是只读的**，只有第 3 步会写寄存器。

### 第 0 步：关两层安全机制 → 重启 → 验证

照《方案A》第 1、2 节（**这部分没问题，保留**）：

```powershell
reg add "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled /t REG_DWORD /d 0 /f
reg add "HKLM\SYSTEM\CurrentControlSet\Control\CI\Config" /v VulnerableDriverBlocklistEnable /t REG_DWORD /d 0 /f
shutdown /r /t 0
```
重启后验证（**必须三个都对才往下走**）：
```powershell
(Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity' -EA SilentlyContinue).Enabled      # 期望 0
(Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CI\Config' -EA SilentlyContinue).VulnerableDriverBlocklistEnable                          # 期望 0
(Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard).VirtualizationBasedSecurityStatus                     # 期望 0 或 1
```
**然后**管理员运行 `Rw.exe`，确认**不再报 `Driver cannot be loaded`**。
（RwDrv 若仍被吊销 ⇒ 是固件强制 ⇒ 才需要进 BIOS 关 Secure Boot。**这是漏洞 5 的判据。**）

### 第 1 步：拿到 I2C0 的 BAR（只读）

| 方法 | 操作 |
|---|---|
| GUI | `Access → PCI`，选 **bus 0 / dev 0x15 / fun 0**（即 `8086:7E78`），看 **BAR0** |
| 命令窗 | `RPCI32 0 0x15 0 0x10` → **BAR0 低 32 位**；再 `RPCI32 0 0x15 0 0x14` 看是否 64 位 BAR |
| 交叉核对 | `Access → PCI` 里位置应显示 **"(0,21,0)"**（21 = 0x15） |

记下 `BAR`（低 4 位清零）。

### 第 2 步：★★ 阳性对照（只读，本次审计新增）

1. `Access → Memory`，基址填 **`BAR + 0x70`**（= `IC_STATUS`），**开自动刷新**。
2. **用手指快速划过触控板**，同时看这个 dword。
3. 判据：
   - **bit0（ACTIVITY）或 bit5（MST_ACTIVITY）在跳** ⇒ **确认这就是触控板那条总线** ⇒ 继续。
   - **完全不动** ⇒ 要么基址算错、要么这不是触控板的总线 ⇒ **停下来复核 BAR**（不要往下走）。
4. 顺手确认 DesignWare 指纹：读 **`BAR + 0xFC`(每个候选偏移 +0xFC)**，应为 **`0x44570140`**。
   （DW 块可能在 `BAR+0x000/0x100/0x200/0x400/0x800/0x1000`；**这一步能确定它的真实偏移**。）

### 第 3 步：读 `0x5A` 的 CHIPID（会写 `IC_TAR`/`IC_DATA_CMD`）

> DesignerWare master 读一个 8 位寄存器设备的时序（本模块/脚本就按这个做）：
> ```
> ① 读 IC_STATUS(+0x70)，等 MST_ACTIVITY(bit5)=0
> ② 写 IC_TAR(+0x04) = 0x5A
> ③ 等 IC_STATUS.TFNF(bit1)=1；写 IC_DATA_CMD(+0x10) = 0x57        (待读的寄存器号，不带 STOP)
> ④ 等 TFNF=1；写 IC_DATA_CMD = 0x0700  (READ(0x100)|RESTART(0x400)|STOP(0x200))
> ⑤ 等 IC_STATUS.RFNE(bit3)=1；读 IC_DATA_CMD(+0x10) → 低字节 = 0x57 的值
> ⑥ 读 IC_TX_ABRT_SOURCE(+0x80)：≠0 ⇒ 无应答（bit0 = 地址 NAK）；=0 ⇒ 成功
> ⑦ 重复 ③~⑥ 取 0x58
> ```
> **前提**：`IC_CON`(+0x00) 必须有 `RESTART_EN(0x20)`（400 kHz 主模式下通常有）。
> **不要改 `IC_CON` / timing / RX-TX 阈值。**

| 结果 | 判读 | 下一步 |
|---|---|---|
| `0x57=0x92` 且 `0x58=0x70` | ★★★ **AW86927 就在主机 I2C0 上** | 进第 4 步 |
| `ABRT≠0`（地址 NAK） | 这个地址没有设备 | 试 **`0x5B`**；再不行 ⇒ 见 §六 |
| 但 `IC_STATUS` 对照又是跳的 | 总线对了、地址没有 ⇒ **设备真在私有总线上** | 这就是**有效**的负结论（因为有了阳性对照） |
| 轮询超时 / 一直不 STOP | 与 `hidi2c` 冲突 | 先禁用触控板设备（`ACPI\GXTP5100\1`）释放总线，再重做第 2/3 步 |

### 第 3.5 步：**手工原值记录表**（补漏洞 7）

写任何寄存器之前，**先读并抄下来**：

| 寄存器 | 名称 | 原值（抄这里） |
|---|---|---|
| `0x08` | PLAYCFG3 | `0x____` |
| `0x09` | PLAYCFG4 | `0x____` |
| `0x3F` | GLB_STATE（只读） | `0x____` |
| `0x07` | PLAYCFG2 (GAIN) | `0x____` |
| `0x0A` | WAVCFG1 | `0x____` |
| `0x12` | WAVCFG9 | `0x____` |

### 第 4 步：震一下（照 `poc\aw86927-操作卡.txt` 的"模式 A"）

```
写 0x08 ← 0x02      (PLAY_MODE = CONT)
写 0x09 ← 0x01      (GO)   ← ★ 立刻观察，别走开
读 0x3F  (GLB_STATE，期望 6 = CONT)
写 0x09 ← 0x02      (STOP) ← 数秒内必须做
```
最后按第 3.5 步的表**把原值写回去**。

### 第 5 步：恢复安全设置（别忘了）

```powershell
reg add "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity" /v Enabled /t REG_DWORD /d 1 /f
reg add "HKLM\SYSTEM\CurrentControlSet\Control\CI\Config" /v VulnerableDriverBlocklistEnable /t REG_DWORD /d 1 /f
shutdown /r /t 0
```
（若第 0 步碰过 BIOS 的 Secure Boot，记得开回来。）

## 八、纪律（第 70–72 条）

70. ★★★ **"工具能做这件事"必须落到"工具的哪一个页面/命令能做"。**
    《方案A》写的是"**Access → I²C**"，而 RWE 的这个页面**名字里就有 I²C**，
    于是它看起来完全对 —— **但它的 I²C 是 SMBus 主机控制器，不是我们要的 DesignWare 控制器。**
    ⇒ **工具的"功能名"和"实际总线"是两件事，必须查它的支持列表与日志。**
    （读 5 分钟 `rw.chm` + `Log.txt`，避免一次注定假阴性的实验。）
71. ★★★ **任何"扫不到 → 所以不存在"的结论，都必须配一条同场景的阳性对照。**
    本次新增的对照极便宜：**划手指看 `IC_STATUS` 的 bit0/bit5** ——
    只读、零风险、不依赖任何工具能力，却能把"总线选错了"和"设备真不在"彻底分开。
72. ★★ **审计别人（和自己）的流程时，要按"每一步的判读表是否成立"逐格检查**，
    而不是只检查"步骤是否可执行"。
    《方案A》每一步都能执行，**只有判读表全是错的** —— 这种错最难发现。
