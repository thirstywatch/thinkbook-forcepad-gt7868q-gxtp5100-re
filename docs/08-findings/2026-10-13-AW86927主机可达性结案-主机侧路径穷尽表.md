## 2. ★★★ 硬结论一：AW86927 主机可达性 = **否**（结案）

### 2.1 本次的干净证据链

| 步 | 操作 | 结果 |
|---|---|---|
| 1 | `i2cdetect -l` | 列出 **`i2c-0`–`i2c-19`**；`i2c-0`=触控板 · `i2c-1`=**`LTCN0001`（TCON / eDP DDC）** · `i2c-5`=SMBus |
| 2 | **正确解绑** `i2c_hid_acpi`（客户端 `i2c-GXTP5100:00`） | 成功 ⇒ **总线上不再有驱动占用** |
| 3 | 解绑后探 `i2c-0` 的 `0x5A`/`0x5B` | **全部 NACK**（`Remote I/O error`） |
| 4 | 探 `i2c-1` 的 `0x5A`/`0x5B` | **全部 NACK** |
| 5 | 立即回绑，触控板恢复正常 | ✅ |

### 2.2 ★ 一条**新知识**：`aw86927` 内核驱动**在 x86 ACPI 上无法 probe**

```
# 模块能加载，但
modinfo aw86927-haptics  →  只有设备树别名： of:N*T*Cawinic,aw86927
                             无 ACPI ID 表、无 I2C ID 表

# 强行把 i2c-0..5 的 0x5A/0x5B 绑到该驱动
→  No such device
```

**⇒ 关键区分**：不是"硬件上够不到"，而是 **`aw86927` 驱动是按嵌入式（设备树）平台写的**，服务手机/平板，**不给 x86 ACPI 用**。
（Linux 主线 `CONFIG_INPUT_AW86927` 的唯一实例就是 **Fairphone 5** 的 `vibrator@5a` 挂 SoC `i2c2` —— 与本机形态不同。）

⇒ **即便它真在主机总线上，也必须手动 `new_device` 才能绑**；而本次 **NACK 已排除"它在总线上"**。

### 2.3 ⇒ 裁定

> **「直接接管 AW86927」这条路：关闭。**
> 结合本文件 §3 的穷尽表 ⇒ **主机侧不存在任何能命令 LRA 的通道。**

## 3. ★★★ 硬结论二：**"Linux 下触觉正常" ≠ 目标达成**

### 3.1 现场事实

用户实测：**Linux 下触控板移动 / 点击 / 滚动 / 触觉（点按振动）全部正常**，无需额外驱动。

### 3.2 但这**不是**目标达成 —— 两件事必须分开

| | 内容 |
|---|---|
| **项目目标** | **手指沿边缘滑动 → 音量/亮度步进 + 触控板本体【连贯震动】**（华为式） |
| **本次观察到的"震"** | **点按触发**的、**设备自主**的振动（device-initiated） |
| ⇒ 关系 | **本次结果恰好是 §16.2「主机无法主动触发」的又一次正面确认**，不是"发现可行" |

> ★ **并且这是对 §16.2 第 3 项旧证据的【有效重做】**：
> 该条（"Linux Live 下点按照样震"）曾于 2026-10-03 **整体撤销**，理由是"该 Linux 环境中触控板**从未被有效测试**"。
> **本次是有效环境下的重做，结论与撤销前相同** ⇒ **§16.2 的证据链补上一环，且方向是加强否证。**

### 3.3 表述纪律（**新增纪律 146**）

> **纪律 146**：**"某功能在 Linux 下正常" ≠ "项目的某个目标达成"。**
> 判"目标达成"必须回到**目标的原始表述**逐字比对（本例目标是"**滑动**震"，而观察到的是"**点按**震"）。
> 同理："**之前底层探测失败均属正常现象**" 里的 "正常" **≠ "问题解决"** —— 它只说明"设计与探测结果自洽"。

## 5. 剩下的路，都必须**打破至少一个约束**

| 路 | 必须放弃的约束 | 备注 |
|---|---|---|
| **方案③ 变体**（`HDP`/`HDN`） | ❌ **"不插入"** | ⚠️ `HDP`/`HDN` 是 **AW86927 的差分输出脚**，**外部驱动会与它内部驱动器打架** ⇒ **必须先断开 AW86927 的输出**（割线/去焊）才能安全接管 |
| **改固件** | ❌ "不改原装" | **单程门**；§19.45 已实证 BIOS 会自动重刷救援，**但触发条件未研究** |
| **等 OEM 新固件** | 无需放弃任何约束 | 只能等；若哪版 Goodix 固件支持 Haptics（`0x0E/0x01` + Manual Trigger），**本机自动解锁**主机触发 |

## 6. ★★ 唯一**符合全部约束**、且**从未试过**的实验：**输入模式穷举**

### 6.1 为什么它是"没动过的维度"

**本项目此前所有实验都是「写数据 → 看效果」。从未做过「输入动作模式 → 看效果」。**

### 6.2 实验设计

```
变量： 压力幅值 · 压力变化速率 · 手指数（1–5）· 接触位置（中心/四角/四边）· 边缘区 · 停留时长
因变量：是否出现【设备自主】的震动
客观判据：同一动作在 0x09 写 0（静音）vs 写 100（满档）两档下对比
         —— 两档表现不同 ⇒ 该动作确实引出了自主震动（排除了主观误判）
```

**为什么它符合约束**：原装 · 不插入 · 纯手指 · 零风险 · Windows 端即可完成。

### 6.3 ⚠️ 诚实边界（必须写清）

| 项 | 说明 |
|---|---|
| **触发判据在 GT7868Q 侧** | 该代码**不在手上**（载荷 A 无代码；ISP 是给芯片 ROM 的密文）⇒ **成功率未知** |
| §11.12 那条 `\|Δ压力\| > 40` 检测引擎 | 它在 **TF100A**，且需先由 `0xA0/0x0D00` **设模式 4** —— 而**主机发不到 TF100A 分发器（H1 已否）** ⇒ **那条链不会跑** |
| ⇒ 反推 | **"点按震"走的是 GT7868Q 侧的另一条链** ⇒ 印证 §11.12 的推论 |
| **成本** | **≈ 0**（这是它值得做的唯一理由） |

## 8. 需要修正的两处既有表述

### 8.1 「5/5 闭合」的**分母错了**

原文（`method/06-i2c-spb.md` §三）写「逐条总线实测（**5/5** 闭合）」，但那 5 条是：
**Windows 侧的 `I2C0/2/3/4/5` + PCH SMBus**。

而 Linux 侧 `i2cdetect -l` 见到 **`i2c-0`–`i2c-19`（20 条）**。

> ✅ **建议改为**：**"Windows 侧可见的 5 条 + Linux 侧已排除的 `i2c-0`/`i2c-1`"**，
> 并注明 **实际控制器至少 20 条**（其中 `i2c-1` = TCON/eDP DDC，其余多为显示相关 DDC/AUX）。
> **结论不变**（`i2c-0` 这条唯一的候选已用"解绑后 NACK"排除），但**分母必须说准**，否则会误导后人以为"全部查完了"。

### 8.2 §16.2 第 3 项的证据状态

§16.2 的"三条独立证据"里第 3 条（Linux Live 相关）**曾被撤销**。本次为其**有效重做**，
**结论相同** ⇒ 该条可以**恢复并升级为"已有效验证"**（附本次环境与操作）。
