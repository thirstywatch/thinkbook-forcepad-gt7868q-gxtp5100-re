## 0. 一句话

> ## **官方两个家族（`gtx8` 与 `gt7868q`）的寄存器地址集【完全不同】。**
> ## **而本机实测"有效"的地址是一个【混合集】** —— 本文件把这个混合集与两套官方集逐条对出来。
> ## **并且找到了 `cfg` 的【两条刷写路径】** —— 它**统一解释了本项目 B12（"只在会话期有效"）与后来的"落盘"实验**。

## 1. ★★★★★ 决定性对照：两个家族的地址集**完全不同**

| 宏 | **`gtx8`**（官方仓库，本次新得） | **`gt7868q`**（官方仓库，本项目已有） | 本机实测 |
|---|---|---|---|
| `CMD_ADDR` | **`0x60CC`** | **`0x4160`** | ✅ **`0x4160`** 有效（§6.3："`0x4160 == 0xFF` = IC 空闲"） |
| `CFG_START_ADDR` | **`0x60DC`** | **`0x96F8`** | ✅ **`0x96F8`**（本项目全程用这个） |
| `CFG_FLASH_ADDR` | **`0x1E000`** | **`0x19000`** | ✅ **`0x1E000`** 无害 / 🔴 **`0x19000` 致退化**（B31） |
| `FLASH_BUFFER_ADDR` | `0xC000`（`gt_update.h`） | 同 | ✅ `0xC000`（B30 的 4096 单元） |

**⇒ 三个结论**

1. ✅ **`CFG_FLASH_ADDR = 0x1E000` 现在有【四个独立来源】，其中两个是 `gtx8`**：
   - ① fwupd `plugins/goodix-tp`（汇顶员工所写，Rust/C）
   - ② **本次新得：`goodix/gdix_hid_firmware_update` 的 `gtx8/gtx8_update.cpp`**
   - ③ 本项目实机验证（`0x1E000` 无害）
   - ④ 本机容器 `idx6` 的 `flash_addr` 恰为 `0x1E000`
   ⇒ **B31 的结论更硬了**（但注意：`gtx2`/`gtx3` 源码里是 `0x3E000`，见 §19.51.7 —— **四个值互不相同**，只有 `gtx8` 这一支是 `0x1E000`）

2. 🔴 **本机实测的"有效地址集"是混合的**：
   - `0x4160` + `0x96F8` ← 来自 **`gt7868q`** 家族
   - `0x1E000` ← 来自 **`gtx8`** 家族
   ⇒ **⇒ 两个家族的源码【都不完全适用】本机。** 本机很可能是**新型号/过渡型号**，
     或 `ICSelect` 所选的"家族"与之均不完全吻合。

3. ★★★ **一条必须修正的旧记法**：本项目把 **`0x60CC ← {33 00 CD}`** 记为"**进 raw 模式**的入口"（§9.3）。
   而 **`gtx8` 官方源码里 `0x60CC` 是【通用 `CMD_ADDR`】**，`{0x33,0x00,0xCD}` 只是**"关闭报文（DisableReport）"这一条命令**。
   ⇒ **`0x60CC` 不是"raw 模式专用入口"，而是 gtx8 族的通用命令寄存器。**（本机若也有 `0x60CC`，它可能承担与 `0x4160` **相同的角色**。）

## 2. ★★★★★ `cfg` 的**两条刷写路径** —— 统一解释 B12 与落盘实验

`gtx8/gtx8_update.cpp` 给出两条**互斥**的路径：

```c
/* 路径 ① 交互式：写 xdata（易失） */
if (this->is_cfg_flashed_with_isp == false && flag & NEED_UPDATE_CONFIG) {
    cfg_update();                 /* ← 写 CFG_START_ADDR（xdata），会话期生效 */
}
/* 路径 ② with-ISP：写 flash（持久） */
if (image->GetUpdateFlag() & NEED_UPDATE_CONFIG_WITH_ISP) {
    this->is_cfg_flashed_with_isp = true;
    flash_cfg_with_isp();         /* ← 写 CFG_FLASH_ADDR(0x1E000)，落盘 */
}
```

| | 路径 ① `cfg_update()` | 路径 ② `flash_cfg_with_isp()` |
|---|---|---|
| 目标地址 | **`CFG_START_ADDR`**（本机 = `0x96F8`；gtx8 = `0x60DC`） | **`CFG_FLASH_ADDR`**（`0x1E000`） |
| 性质 | **xdata / RAM —— 掉电即失** | **flash —— 持久** |
| 源码里显式说 | `"Failed write cfg to **xdata**"` | `"flash config with **isp**"` |
| 本项目对应 | ★★★ **B12「cfg 写入只在会话期内有效」** | ★★★ **2026-10-12 的"落盘"实验（`0x0E12 @0x1E000`）** |

> ### ⇒ ★★★★★ **本项目整条 cfg 研究史被这一对函数统一解释了：**
> **早期（B12）走的是路径 ①（写 xdata）⇒ 观察到的现象必然是"只在会话期有效"。**
> **后期改用 `0x0E12`（= 路径 ②，写 flash）⇒ 才谈得上"落盘"。**
> **这不是"设备两个矛盾的行为"，而是【两条不同的官方路径】。**

### 2.1 路径 ① 的官方完整时序（`cfg_update()`）

```
① dev->Read(CFG_START_ADDR, cfg_ver_before, 3)          // 读当前 cfg 版本（3 字节）
② 等 CMD_ADDR == 0xFF（IC 空闲），10 次 × 10 ms          // ← 本机用 0x4160
③ 写 {0x80, 0x00, 0x80} → CMD_ADDR                      // "tell ic i want to send cfg"
④ usleep(250 ms)
⑤ 等 CMD_ADDR == 0x82，GDIX_RETRY_TIMES × 30 ms          // IC 确认
⑥ 写 cfg 数据 → CFG_START_ADDR（sub_cfg_len 字节）        // 写进 xdata
⑦ usleep(100 ms)
⑧ 写 {0x83} → CMD_ADDR                                  // "tell ic cfg is ready in xdata"
⑨ usleep(80 ms)
⑩ 等 CMD_ADDR == 0xFF，GDIX_RETRY_TIMES × 30 ms          // 等 IC 处理完
⑪ dev->Read(CFG_START_ADDR, cfg_ver_after, 3)           // 读新版本
```

⇒ **与本项目解出的 `0x80 → 0x82 → 写 → 0x83 → 读结果 → 0x7D` 精确对应** ✅
⇒ ★ 新增细节：**⑤ 的"确认"值是 `0x82`**；**⑩ 的"完成"值是 `0xFF`**；版本读的是**前后各 3 字节**

### 2.2 路径 ② 的官方实现（`flash_cfg_with_isp()`）

```c
① 按 sub_cfg_id == dev->GetSensorID() 从 bin 里挑出匹配的 cfg
② load_sub_firmware(CFG_FLASH_ADDR /*0x1E000*/, cfg, sub_cfg_len)
```

⇒ ★★★ **cfg 是【按 sensorID 索引】的**：
```c
sub_cfg_id  = fw_data[pos];                       /* 1 字节 sensorID */
sub_cfg_len = (fw_data[pos+1] << 8) | fw_data[pos+2];   /* 2 字节 BE */
pos += 3;                                          /* 表项步长 3 */
if (dev->GetSensorID() == sub_cfg_id) { ... 选中 ... }
```
⇒ ★★★★ **这解释了 `tpcfgsid0/2/3.cfg` 的命名**：**`sid0` = sensorID 0**！
⇒ **而本项目实测 `SID = 0`**（§19.0：照抄官方 `SetBasicProperties()` 成功 ⇒ `SID=0` / PID 7869 / 版本 1.4.3.5.22）
⇒ ⇒ **所以本机该用的就是"`sensorID = 0` 的那份 cfg"** ——
  ⚠️ 但**名字含 `sid0` ≠ 内容匹配本机**（手上那份 `tpcfgsid0.cfg` 来自 `x_108e1f62` 包 = GX5300/Marseille 系）。
  **正确做法是：按 `dev->GetSensorID()`（=0）去**本机的 bin 文件里**挑**（`Gtx8Image` 那套索引），而不是靠文件名。

## 3. ★★★★ `DisableReport()` —— "关闭报文"的官方命令对（本项目此前只知道一半）

```c
cmdDisable[] = {0x33, 0x00, 0xCD};    /* 连写 3 次到 CMD_ADDR，间隔 10 ms */
cmdConfirm[] = {0x35, 0x00, 0xCB};    /* 写 1 次 */
usleep(30000);
dev->Read(CMD_ADDR, buf, 3);
if (buf[1] != 1) → "close report failed"      /* ★★ 成功判据是 buf[1] == 1，不是 0xAA/0xBB！ */
```

⇒ ★★★ **本项目 §9.3 只记了 `{33 00 CD}`**（"必须先进 raw 模式才可写"），
**没说还有 `{35 00 CB}` 这条确认命令，也没说成功判据是 `buf[1] == 1`。**

⇒ **★ 待核对（3 项）**：
1. `{0x35, 0x00, 0xCB}` 在本机是否有效？读回的 `buf[1]` 是否 == 1？
2. `{0x33,0x00,0xCD}` **连写 3 次 × 10 ms**，本项目是否只写了 1 次？（剂量差异可能影响状态）
3. 本机的 `CMD_ADDR`（`0x4160`）上，这套命令是否与 gtx8 的 `0x60CC` 语义相同？

## 4. ★★★★★ `fw_update()` 的官方完整序列（本机 `gt7868q` 版同构，gtx8 版更完整）

```
① DisableReport()                                  // 关报文（3+1 条命令）
② 写 {0x00,0x10,0x00,0x00,0x01,0x01}                // 切 patch
③ usleep(250 ms)
④ 轮询读 BL_STATE_ADDR，等 == 0xDD（GDIX_RETRY_TIMES × 30 ms）
⑤ DisableReport()（★ 第二次！本项目记录里没有这一条）
⑥ 写 {0x00,0x11,0x00,0x00,0x01,0x01}                // 启动更新
⑦ usleep(100 ms)
⑧ for each sub_fw:
     if (!(firmware_flag & (0x01 << sub_fw_type))) { 跳过并前进; continue; }
     load_sub_firmware(sub_fw_flash_addr, data, sub_fw_len)
⑨ if (NEED_UPDATE_CONFIG_WITH_ISP) → flash_cfg_with_isp()
⑩ 写 {0x0E,0x13,0x00,0x00,0x01,0x01}（×3 重试）      // 复位 IC
⑪ usleep(300 ms)
⑫ 写 {0x03,0x03,0x00,0x00,0x01,0x01}（WriteSpeCmd）  // 切回 PTP 模式
失败路径 update_err：同样做 ⑩⑪⑫（复位 + 切 PTP）
```

**★ 相对本项目记录（§19.49.7）的三处新增**：
1. **`DisableReport()` 在"切 patch 前"和"启动更新前"各调用一次（两次）**
2. **`BL_STATE_ADDR == 0xDD` 是 `usleep(250 ms)` 之后才开始轮询的**
3. **失败路径也要复位 IC + 切回 PTP**（本项目是否在失败时切回 PTP？）

**子固件表项解析（逐字节，官方原文）**：
```c
sub_fw_type  = fw_data[pos];                                         /* u8 */
sub_fw_len   = fw_data[pos+1]<<24 | ...<<16 | ...<<8 | fw_data[pos+4]; /* u32 BE @+1 */
sub_fw_flash_addr = ((fw_data[pos+5] << 8) | fw_data[pos+6]) << 8;   /* u16 BE @+5，再 <<8 */
pos += 8;                                                             /* 步长 8 */
```
⇒ ✅ **与本项目 `decrypt.py` 的解析完全一致**（`0x03 / size u32be / addr u16be<<8 / +1`）

## 5. ★★★★ 判据核对结果：本项目的 `0xAA`/`0xBB` 属于**跨家族借用**

| 家族 | 有没有 `0xAA`/`0xBB`/`0xCC` **单字节结果码**判据 |
|---|---|
| **`gtx8_update.cpp`**（本机家族之一） | 🔴 **完全没有** —— 全部是**位标志**（`NEED_UPDATE_FW` / `NEED_UPDATE_CONFIG` / `NEED_UPDATE_CONFIG_WITH_ISP`） |
| **`gt7868q_update.cpp`** / **`gtx3_update.cpp`** | 🔴 同上，**没有** |
| `gtx9_update.cpp` / `marsei_update.cpp`（**GTX9/Marseille**，HID 版） | ✅ 有：**`} else if (ret == 1 && flag == 0xBB) { //checksum error`** ← **官方原文注释** |
| `gtx9_i2c_update.cpp`（GTX9，**I²C 版**） | ✅ 有但语义不同：`FLASH_CMD_TYPE_READ=0xAA` / `FLASH_CMD_TYPE_WRITE=0xBB` = **命令类型** |

**⇒ 裁定**
- ✅ **本项目"`0xBB` = 校验和错误"的方向正确**，有官方注释支撑
- ⚠️ **但那条注释出自 GTX9/Marseille 家族，本机家族里根本没有这些宏** ⇒
  **登记时应标注为「借用 GTX9/Marseille 家族定义，未经本机家族源码确认」**（同登记表 **B13**「需按项分辨」情形）
- ★ **同时新增一个事实**：**同一颗 GTX9 的两条通道（HID vs I²C）状态语义不同** ——
  HID 里 `0xBB` = checksum error；I²C 里 `0xBB` = WRITE 命令类型

## 6. ⚠️ 一处**新矛盾**（必须核对）

| | 值 |
|---|---|
| 官方 `gtx8` 说 | **`CFG_START_ADDR = 0x60DC`**，且 `cfg_update()` 用它**读 cfg 版本（3 字节）**、**写 cfg 数据** |

⇒ **不作为结论，作为"待核对项"登记。**

## 7. 本轮新增纪律

| 条 | 内容 |
|---|---|
| **148** | **同一颗芯片可能有【多套并存的寄存器地址集】。**<br>在"某地址实测有效"之后，**不得据此推断"该家族的另一地址也有效/无效"** —— 必须先**逐条对照两套源码的宏**（本例 `CMD_ADDR`：`0x4160` vs `0x60CC`；`CFG_START_ADDR`：`0x96F8` vs `0x60DC`）。<br>推论：**"混合使用两个家族的地址"是允许的，但必须逐条实机验证，不能跨条外推。** |

**总结**：

> **官方 `gtx8` 源码到手后，本项目两处长期悬案被解释：**
> **① B12「cfg 只在会话期有效」与后来的"落盘"实验 = 官方的两条不同刷写路径（xdata vs flash）。**
