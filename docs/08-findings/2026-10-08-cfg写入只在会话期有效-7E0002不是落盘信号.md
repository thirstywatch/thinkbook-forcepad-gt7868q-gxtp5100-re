## 1. 分层实测（`lab__r21_persistence_test.py`）

测试字段 `+0x10F`：`4150 (10 36)` → `4151 (10 37)`。

| 层 | 动作 | `+0x10F` 读回 | 结果码 | 判读 |
|---|---|---|---|---|
| **层 0** | 基线 | `10 36` (4150) | `7E 00 07` | 与 flash 一致 |
| **层 1** | 同会话内写入改动 → T2 读回 | **`10 37` ✅** | `7E 00 02` | **RAM 暂存区确实被改写** |
| **层 2** | **关闭会话** → 重新开会话 → 读 | **`10 36` 🔴** | `7E 00 07` | **已回原值，未保留** |
| **层 3** | 写改动 → `0x83` → **额外发 `0x34`** → `0x7D` → 新会话读 | **`10 36` 🔴** | `7E 00 02` → 回原值 | **`0x34` 不是"提交"** |
| — | **重启设备**（`pnputil /restart-device` Col02+Col04） | **`10 36`** | — | **flash 从头到尾就是 4150** |
| 收尾 | `restore` | — | `7E 00 07` | 干净 |

---

## 2. ★ 核心结论

> ### `7E 00 02` 只代表「**RAM 暂存区被改写**」，**不是**"已写入 flash"的信号。
> ### `0x7D` 结束后暂存区被丢弃，IC 从 flash 重新载入原值。
> ### ⇒ **cfg 写入的作用域 = RAM 暂存区，仅会话期内有效。**

### 与既有认知的对照

| 结果码 | 旧解读 | **新解读（本轮定案）** |
|---|---|---|
| `7E 00 07` | 与 flash 一致 | ✅ 仍成立 |
| `7E 00 02` | ~~"与 flash 不同 ⇒ 会真正生效"~~ | 🔴 **"与前次会话不同 ⇒ RAM 已被改写"**，与 flash 无关 |

## 3. 连带推翻与更正

### 3.1 🔴 第十三轮的"写入进 flash、跨重启保持"是错的

原文（`2026-10-05-cfg下发通道打通-首个主机写入改变行为的实证.md`）与登记表 **B7** 都写：

> 「cfg 下发通道可用 + **写入进 flash 跨重启保持**」

**当时的依据只有 `restore` 后的 `7E 00 07`，从未做过重启验证。**
本次重启实测直接推翻。**登记表新增 B12 记录此事。**

### 3.2 🔴 第十三轮全部「手感实验」的前提失效

第十三轮用 `+0x115` 做了五档手感实验（60 绵软 / 120 基准 / 240 更强 …），
**前提是"写入已生效"**。但既然 cfg 在会话结束时就回原值：

> **那些手感差异不可能来自 cfg。**

⇒ **B10 的"感知噪声"解释更被支持** —— 那些差异连"被写入的配置"这个物质基础都没有。

### 3.3 ✅ B11 结案（根因不是我原先猜的任何候选）

| 原候选 | 裁决 |
|---|---|
| (a) 真源在别处（OTP 等） | ❌ **不必要** |
| (b') Windows 枚举缓存 | ❌ **不是缓存**（重启也不变，因为 flash 没变） |
| (c) 字段不参与描述符生成 | ❌ 不必要 |
| **新** | ✅ **改动在会话结束时消失；描述符读的是 flash，而 flash 从未被改** |

**⇒ 描述符不变完全正常，它不构成对"`+0x10F` = X 点数"的否证。**
**⚠️ 但定名仍未恢复** —— 因为**从未有过一次"改了 flash 且描述符跟着变"的正例**。
该定名维持 **🟡 数值候选**，直到能真正写入 flash 后再验。

### 3.4 本轮开头那个"活体 vs 容器不一致"之谜也解开了

```
活体 : 22 00 1B 00 3D 01 …     ← 这是 flash 里的值
容器 : 22 01 1B 00 3E 01 …
```

差 `+0x1` / `+0x3` 各 −1 —— **一直是这个值，与我的实验无关。**

## 4. ★ 顺带确立的两个正面成果（仍然有效）

### 4.1 T2 会话态全段可读 —— 偏移体系验证通过

空闲态"不可读/自相矛盾"的 `+0x100~0x11F`，在 T2 会话态**完全可读**（10 点全部前缀一致）。
读回内容与容器 cfg **逐字段命中**（`+0x111`=`0864`/2148、`+0x113`=`005a`/90、
`+0x115`=`0078`/120、`+0x117`=`0505`/1285、`+0x119`=`019e`/414）。
⇒ **容器偏移体系在会话态是正确的**；空闲态读不到纯是相位问题（第 111 条）。

### 4.2 ★ 首次「直接看见写入」+ 全量 dump 零差异

- 写入 `10 37` → T2 读回 `10 37`；写入 `10 36` → 读回 `10 36`。**字节级闭环成立。**
- T2 全量 dump 1084 B：**sha256 与所发 cfg 完全相同，1084/1084 一致，0 差异**。
- ⇒ **IC 对 cfg 是纯透传**，无加工/校验注入/填充。"字段被 IC 改写"类猜测全部不成立。

## 5. ★ 新的核心问题：**如何真正写入 flash？**

| 已试 | 结果 |
|---|---|
| `0x80` 握手 + 写 + `0x83` | 仅 RAM |
| 额外发 `0x34` | 仅 RAM |
| `0x7D` 结束 | 仅 RAM（丢弃） |

**缺的那一步，很可能是红线中的 `0E 12`（真正写 flash）。**

> 🔴 **但这是红线。** `00 10`(switch to patch) / `00 11`(start update) / **`0E 12`(写 flash)** / **`0E 13`(restart)**
> 是**唯一会真正损坏硬件**的动作序列（登记表 A3 明确记录"三连实为四条，旧文档漏了 `0E 13`"）。
> **绝不能在真机上试。**

**⇒ 这条线的下一步应当另辟方向**（例如：`fwupd/goodix-tp` 源码里是否有官方落盘序列、或样机实验）。

## 6. 新增纪律

> **第 112 条：凡是声称"已写入持久存储"的结论，必须经过【至少一次掉电/重启】验证；
> 结果码只能证明"传输被接受"，不能证明"已落盘"。**

**补充到既有方法学上**：
- 第 110 条管"数值巧合"
- 第 111 条管"相位（地址映射）"
- **第 112 条管"持久性（作用域）"** —— 三条同源：都在堵"证据强度不足却当作结论"的口子。
