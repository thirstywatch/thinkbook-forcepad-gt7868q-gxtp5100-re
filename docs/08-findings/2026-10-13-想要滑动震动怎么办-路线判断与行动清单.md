## §0 一句话

> **只有一条路：让【设备自己】在滑动/到边缘时震。**
> **"主机发起震"在本机是【被规格和实现双重关闭】的。**
> **而这条路能不能走通，取决于一个还没定案的问题：【谁在"决定震"？】**

> 🔴 **2026-10-13 追加更正（用户追问引出）**：
> 上一版这里把「本机是纯设备自主触发」与「业界只有 Surface Laptop 8 做到滑动震」并排放在一起，
> **极易被读成「微软在同样的约束下也做到了滑动震」。这个推论【不成立】。**
> **事实相反：Surface Laptop 8 恰恰是【唯一支持主机发起触觉】的那一类设备** ——
> 它靠 **`Manual Trigger`（`0x0E/0x21`）** + **`Windows.Devices.Haptics.InputHapticsManager`** 由**应用/系统**在滑动事件上发波形。
> **⇒ 它和本机是【相反】的两类，不是同类中的特例。** 详见 §1b。

## §1b ★★★★★ Surface Laptop 8 的「滑动震」是怎么实现的（官方文档原话）

### (1) 它是**主机/应用发起**，不是设备自主

微软 Learn《Implement haptic feedback in Windows apps》给的正是**滑块滑动**的官方示例：

```csharp
// Sliders：滑块的 thumb 跨过每个刻度时，发 Step 波形
void OnSliderValueChanged(double newValue) {
    int previousTick = (int)(_previousValue / TickInterval);
    int currentTick  = (int)(newValue / TickInterval);
    if (currentTick != previousTick && supported)
        InputHapticsManager.GetForCurrentThread()
            .TrySendHapticWaveform(KnownSimpleHapticsControllerWaveforms.Step, 0);
    _previousValue = newValue;
}
```
- 同页另有**对齐（`Align`）**、**到达边界（`Collide`）** 的示例；
- `Align / Collide / Step / Grow` 四个波形需 **SDK 10.0.28000.1839（2026-04）**；
- 命名空间 `Windows.Devices.Haptics`，**最低 OS = Windows 11 SDK 10.0.28000.1721（2026-03）**。

微软 Surface 官方博客原文（同一天的另一篇）：

> 「Windows supports haptic touchpads and mice through its input-device architecture, with **compatible firmware exposing device capabilities so the operating system and applications can trigger tactile responses**.」
> 「**applications determine when an interaction should trigger a response**, and Surface hardware and firmware translate the signal into a physical sensation.」

**⇒ 触发时机由【应用/系统】决定 ⇒ 这是【主机发起触觉】。**
**⇒ 所以 SL8 的"滑动震"= 主机在滑动事件上发 `Step`/`Collide` —— 与本机"缺 `Manual Trigger`"正好是反面。**

### (2) 它需要本机缺的那两件 + 一个白名单

| 需要什么 | 本机 |
|---|---|
| **Manual Trigger Output Report（`0x0E/0x21`）** | ❌ 未声明 |
| **Waveform Information Feature Report**（Waveform List + Duration List，Ordinal page `0x0A`） | ❌ 未声明 |
| 进入 Windows 的 **Supported Device Database**（`InputHapticsManager` 的白名单；项目已记：目前**只有 Surface Laptop 8 / 8 for Business**，另加鼠标与笔） | ❌ 不在 |

### (3) ★★ 一个对我们有用的推论（重要）

**`InputHapticsManager` 的白名单只是【微软通用 API】这一层的限制。**
而 **`Manual Trigger` 是标准 HID OUTPUT 报告** —— 任何拿到该 HID 设备句柄的程序都能直接发（本项目的 `gxmem` 已经在这么对 Col04 发 output report 了）。
**⇒ 只要一台 forcepad 的描述符里有 `Manual Trigger`，我们就能【自己写工具】驱动它，不需要通过微软白名单。**

⚠️ 这是**推论**（HID 层可写是已证事实；"Windows 的 HID 栈不会额外过滤该集合"未经实测）。
**判据（零成本）**：拿到任何候选设备后，直接读它的 Col/描述符看有没有 `0x0E/0x21` + Waveform 两个 report。

## §1 为什么"主机发起"这条路在本机是关的（三层证据，互相独立）

| 层 | 事实 | 依据 |
|---|---|---|
| **规格层** | 微软官方明定：**Haptic Intensity 子集合（`0x0E/0x23`）不得包含 Auto Trigger（`0x0E/0x20`）或 Manual Trigger（`0x0E/0x21`）** | 微软《Input Device Haptics Implementation Guide》（本轮已归档） |
| **实现层** | 本机 Col04 **只声明 `0x0E/0x23`**；`0x0E/0x20`、`0x0E/0x22`、`0x0E/0x21` **均未声明** | §19.34.7 第 3 项 / 全书 §19.30 |
| **协议层** | Chromium OS 的 forcepad 补丁说明：**模式切换靠写 `Auto Trigger Waveform`**（`WAVEFORM_PRESS` = 设备控制 / `WAVEFORM_STOP` = 主机控制）<br>⇒ 本机**连 Auto Trigger 都没声明** ⇒ **连"切模式"的入口都不存在** | Linux `[PATCH 00/11] HID: Implement haptic forcepad support`（2025-07-14） |

**⇒ 厂商选择的是「仅设备自主触发 + 主机可调强度」—— 这是规范允许且明确命名的合法配置。不是缺陷，也不是我们没找到。**

## §2 ★★★★★ 关键卡点：**「谁在"决定震"」尚未定案**

把已定案的拼图摆出来：

| 候选驱动者 | 状态 | 能否改 |
|---|---|---|
| **主机** | ❌ 够不到 AW86927（`0x5A`/`0x5B` 全 NACK，**B33 结案**）；且**主机不是 AW86927 的初始化者**（ACPI 无设备、无驱动、无上电下载路径） | — |
| **TF100A（钛方）** | ❌ **不驱动 LRA、也不是 AW86927 的 I²C 主机**（逐指令 20,314 条定案：0 条马达外设、0 条 `0x5A/0xB4/0x9270`；唯一引脚动作 = `PA3` 门铃）<br>⚠️ 且其**"播放"不是函数** —— 只有两个无条件初始化的定时器（TIM2 200 Hz / TIM3 400 Hz）+ 一个**零调用者**的手动入口；**波形不在这个镜像里** | ✅ 固件**明文**、可读可改，但**它不是驱动者** |
| **触控 IC（GT7868Q / YS）固件** | ✅ **最可能是决策者**（它是模块内 I²C 主机，既可与 TF100A 通讯、又可命令 AW86927）<br>❌ 但**解密后主体经检验不是可反汇编的代码** ⇒ 改不动 | ❌ |
| **触控 IC 的 cfg** | ✅ **今天刚打通合法写入**（拿到 `0x7F`）<br>⚠️ 但 cfg 里是**参数**（波形/时长/幅度，TAG `0x50`–`0x7A`），**不是触发条件** | ✅（唯一主机可写通道） |
| **AW86927 自己** | ⚠️ **唯一没被查透的一颗**：它有 **`TRIG1/2/3` 硬件触发脚（≥1 µs 脉冲即播放）**，数据手册注明 *"Must connect to GND when not used"* | ❌ 主机够不到 |

### ★ 我本轮的一个小推断（已排除一个候选）

我原以为 **TF100A 的 `PA3` 门铃 = AW86927 的 `TRIG`**（因为两者都是"拉一个脉冲"）。
**查反汇编后排除**：`PA3` 是在**构造 `A2` 回复帧之后**拉低的（`0x0800F868` 打包器 → `0x0800F806` 写 `GPIOA_BRR`）
⇒ **它是"回复帧就绪"的数据门铃，不是震动触发脉冲。**

**⇒ 卡点收敛为两处**：① **触控 IC 固件**（改不动）② **某条 `TRIG` 硬件线**（未测）。

## §3 立刻能做的三件（都不碰设备，或只读）

| # | 动作 | 成本 | 判据 / 产出 |
|---|---|---|---|
| **1** | **量 `TRIG1/2/3` 是接 GND 还是有线驱动**（模组 pin 2/3/4） | 低（需拆底盖 + 万用表通断） | ★ **唯一的硬件判据**：<br>**接 GND** ⇒ 模组没走硬件触发 ⇒ 触发只能走 I²C ⇒ 决策者只能是触控 IC（⇒ 大概率做不到）<br>**有线驱动** ⇒ **存在一条非 I²C 的播放通道** ⇒ 沿这条线找驱动者 |
| **2** | **在 TF100A 明文固件里穷尽"对外输出"路径**（确认除 `A2` 回复帧与 `PA3` 门铃外没有第三条） | 零（离线；资产已有 `lab__TF100A_thumb.asm` + `callgraph.py`） | 若确实只有这两条 ⇒ **TF100A 整条线可从"震动触发"里排除** |
| **3** | **cfg 侧：逐字段测 haptics 区（TAG `0x50`–`0x7A`）+ gesture 相关字段** | 低（会话 RAM，不落盘） | ⚠️ **判据必须客观可视**（纪律 108/109）。<br>★ 唯一可能翻盘的地方：**若某个字段是"手势 → 触发"的门控**（未证，但值得穷举） |

## §4 诚实判断（不粉饰）

**从现有证据看，「滑动震」在这台硬件上能实现的概率不高。** 能做到的前提是三选一：

| 前提 | 可能性 | 说明 |
|---|---|---|
| **a) cfg 里存在"手势 → 触发"的门控位** | 🟡 **中低** | 可测（今天刚具备能力）；但 cfg 目前看是**参数**层，不是**事件**层 |
| **b) `TRIG` 有线驱动，且驱动者可被我们控制** | 🟡 **中低** | 需硬件测量；即使有线，驱动者很可能是触控 IC（改不动） |
| **c) 换模块 / 换 MCU / 插入外部板** | — | ❌ **已被排除**：X9-15 模块被 BIOS 白名单拦（`0x01EA` vs `0x01E8/0x01E9` ⇒ Code 10）；插入硬件违反你的约束 |

**⇒ 若 a、b 都不成立，则本机硬件上做不到 "滑动震"。**

## §5 如果最后确认做不到 —— 还剩什么

| 选项 | 说明 |
|---|---|
| **① 换一台机器**（唯一能真正得到"滑动震"的路，且**不需要逆向**） | ★ **已确认的样板 = Surface Laptop 8** —— 它的滑动震是**主机/应用发起**的（`InputHapticsManager.TrySendHapticWaveform(Step/Collide/Align/Grow)`，见 §1b），**不是**设备自主实现。<br>**目标特征（买前可直接读描述符验证，本项目方法已成熟）**：<br>· `0x0E/0x01` SimpleHapticsController 集合（PTP 顶层集合的子集合）<br>· **Waveform Information Feature Report**（Waveform List + Duration List，Ordinal page `0x0A`）<br>· **`Manual Trigger` Output Report（`0x0E/0x21`）**<br>★ **不必非要 SL8**：`InputHapticsManager` 的白名单只约束微软那条通用 API；**`Manual Trigger` 是标准 HID OUTPUT 报告，自己写工具就能发**（§1b(3)，属推论，需实测）<br>⇒ **所以验收判据 = 描述符里有那两份 report**，而不是"是否在微软白名单里" |
| **② 接受"设备自主触觉"的现状** | 你手上已经有的：按下/抬起触觉 + **主机可调强度**（`0x0E/0x23`，0–100）。这是本机能力的上限 |
| **③ 破例改约束**（换 MCU / 插入外部板 / 外部驱动 `HDP`/`HDN`） | ❌ 违反你的三条约束；且 `HDP`/`HDN` 是 AW86927 的**输出脚**，外部驱动会与内部驱动器打架（§1.4 工程提醒） |

## §6 这一天真正拿到了什么（值得记住）

即使"滑动震"最终做不成，今天拿下的是**七周以来最大的三件**：

1. **cfg 校验算法完全解开 + 真机拿到项目史上首个 `0x7F`** ⇒ **「改 cfg」从"封死"变成"可写"**
2. **官方 `reg_info` 地址表到手 + 本机 12 地址全表核验** ⇒ 终结「两套地址集」
3. **`"YELSTO"`（IC 自报）+ 三条独立链收敛** ⇒ **本机家族结案 = Yellowstone**；且**微软规格解释了"设备侧无接收分支"是合法配置**（不是缺陷）

⇒ **也就是说：「做不成」这个结论本身，第一次是【有据可依】的，而不是"我们没找到"。**
