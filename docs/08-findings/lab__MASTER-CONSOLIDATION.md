## §0 一句话结论

**点按震动是触控板模块内部（芯片固件）自主行为**：主机在点按时**一个厂商报文都不发**，也**读不到任何"震动开关"**。
因此"随滑随震"**无法由现有主机接口实现**。

## §1 目标与硬约束

| 项 | 内容 |
|---|---|
| 目标 | 单指边缘滑动（亮度/音量）**时手随滑动感到震动** —— 用户原话"**震动才是灵魂**" |
| 硬约束 | 触控板是**唯一指针设备**；冻结=用户没法用电脑；**禁止整段快照**（683 连发读已两次致冻） |
| 剂量红线 | 类 0x20 读：**单轮 ≤80 次、≤3 次/秒、轮间 ≥3 分钟**、前后各一次体检（实测 90 次@≤10/s 安全；683 次@9–13/s 两次致冻，1–2 分钟自愈） |
| **新增红线** | **禁止枚举 class `0x00` / `0x03` / `0x0E`** —— 它们是**固件更新/复位命令族**（会把芯片踢进 Bootloader），这正是历史"IC 挂死"的真因 |
| 冻结处置 | 先等 1–2 分钟（两次都自愈）→ 无效再 EC 复位（关机→拔电源→长按电源 20–30 s→等 1 分钟→开机） |

## §3 固件与容器（两份容器）

### 3.1 本机主容器 `C:\Windows\Firmware\TB14P_GT7868Q_14030522_20240202.BIN`（161,628 B）

- **身份：UEFI 固件更新载荷**（`GoodixTouchpad.inf`：`Firmware_Install,UEFI\RES_{b6ae105a-ba93-4fc8-aa28-e63903ffedde}`、`FirmwareVersion=0x14030522`）。
- **头是【大端】**：`+0x00` magic `0x73C01104`、`+0x04` 元数据偏移 `0x43C`、**`+0x44` payload A 长度 `100,608`**、**`+0x48` payload B 长度 `56,608`**。
  （此前按小端搜长度才会 0 命中。）
- **payload A**（0x11BC..0x19ABC，100,608 B）＝**加密**；**payload B**（0x19ABC..，**56,480 B**）＝**明文固件镜像**，映射 `0x08000000`，内含字符串 `TF100A_Test_FW` + `Nov 28 2023`。
- 元数据尾部标签：`… _7  YELSTO  00 00  06  "7868Q"`（容器 0x1142）。
- **镜像被截断**：向量表/代码引用到 `0x0800DFE5`(slot6)、`0x0800DEE9`(**IRQ37 USART1**)、`0x0800F0B5`(+5,141 B)，而镜像结束于 `0x0800DCA0`
  ⇒ **缺 ~5,141 B 尾部**，内含 **USART1 接收 ISR（= 命令帧装配/校验）** 与 **播放入口 `0x08008628` 的调用者**。

### 3.3 BIOS 侧结论（D2，**死路**）

- `NJCN67WW_FWUpdate.bin`（4,343,352 B）是 **Intel FPT 结构整片镜像**，20 个分区（`RBEP`/`EPP1`/`TBTP`/`MFS`/`NFTP`/…）。

  ⇒ **该 BIOS 里没有 Goodix 专用代码**，容器解析器不在 BIOS 里（D2 关闭）。

## §4 协议（权威定义，三方互相印证）

### 4.1 原厂开源实现（决定性来源）

`fwupd/plugins/goodix-tp/`（`Copyright 2023 **Goodix.inc**`，LGPL-2.1+），关键文件：
`fu-goodixtp-common.h`、`fu-goodixtp-hid-device.c`、`fu-goodixtp-gtx8-device.c`、`fu-goodixtp-brlb-device.c`。

### 4.2 常量（原文）
```c
#define PACKAGE_LEN 65      #define REPORT_ID 0x0E      #define I2C_DIRECT_RW 0x20
#define I2C_READ_FLAG 1     #define I2C_WRITE_FLAG 0    #define RAM_BUFFER_SIZE 4096
```

### 4.3 帧格式（fwupd 源码 + 我们反汇编 Dell 工具 + 项目历史实测，**三者一致**）

```
内存读: 0E 20 00 00 05 01 | addr16BE | len16BE        (10 B)
内存写: 0E 20 <more> <seq> <len+5> 00 | addr16BE | len16BE | data…   (单块 ≤55)
回复  : [0]=0x0E [1]=0x20 [2]=? [3]=0 [4]=len(必须等于请求长度) [5..]=数据
```
- `[4] = 帧长 − 5`；`[5] = 方向 (1 读 / 0 写)`；`<more>` = 还有后续块；`<seq>` = 块序号。
- v2（**32 位地址**，Dell 的 `07` 选择子）＝ **BERLINB 族**；**本机芯片把 v2 帧按 v1 解析**（实测三地址返回同一份数据）⇒ 本机是 **v1/GTX8 系**。

### 4.4 明文固件里的**第二套命令族**（0x80/0xA0/0xA1 → 回复 0xA2）

| 类-子命令 | handler | 语义 |
|---|---|---|
| `0xA0-0x0B` | `0x080088C0` | 把 payload 写进**触觉波形缓冲 `0x200040E8`** |
| `0xA1-0x0B` | `0x08008868` | 读回波形缓冲并组 `A2` 回复（`buf[0]=0xA2; buf[1]=n; buf[2..]=波形`；写进固定缓冲 `0x200041B4`；拉低 PA3） |
| `0xA1-0x0F` | `0x0800865C` | 读 27 B @ `0x1800`，回 `A2 + len + 数据 + 校验` |
| `0xA0-0x0D` | `0x080086B4` | 触觉缓冲初始化/清空（`*(0x20004094)=4`；清 `0x2000495E` 起 5780 B 与 `0x2000426C` 起 44 B） |
| 播放入口 | `0x08008628` | 使能 TIM3 → 调回调 `ctx+0x14`；**在本镜像 0 个调用者**（调用者在缺失尾部） |

### 4.5 fwupd 给出的**主芯片命令族**（危险！）
```c
{0x00,0x10,0,0,1,1} 切 Bootloader patch 模式      {0x00,0x11,0,0,1,1} 开始更新
{0x0e,0x12,…}       写 flash（带校验和）          {0x0E,0x13,0,0,1,1} ★软复位
```
已知地址：`CMD_ADDR 0x60CC`（命令信箱）、`BL_STATE_ADDR 0x5095`、`FLASH_RESULT_ADDR 0x5096`、`FLASH_BUFFER_ADDR 0xC000`、`0x452C`（固件版本块 72 B，+9 起 5 字节 patch PID、sum8==0）、`0x60DC`（cfg 版本）。
**实测本机**：`0x452C×72` = 高熵数据（**不是**版本块）、`0x60DC` 首字节 `0x02` ⇒ **本机布局与 NORMANDYL 不完全一致**（未决）。

## §6 ★ 逻辑漏洞审计（自审，必须承认的薄弱点）

| # | 漏洞 | 影响 | 如何补 |
|---|---|---|---|
| **H1** | **"两颗芯片"模型并未被证明。** 同一颗芯片的"payload A=量产固件（加密）+ payload B=测试固件（明文）"同样解释所有证据：16 位窗口是**寄存器空间**（与 CPU 的 `0x08000000`/`0x20000000` 本就不同），所以 `0x40E8` 读不到 `0x200040E8` 在两种模型下都成立 | "主机够不到触觉芯片"的结论**强度被高估** | 若能证明量产固件（A）里**没有** `0x80/0xA0/0xA1` 分发器 ⇒ 两芯；反之同芯。需要解密 A 或拿到完整容器 |
| **H2** | **从未验证过 A 类帧真的送达明文固件里的那些 handler。** 我们只知道"发出去被接受"（`err=0`），不知道主芯片是否**转发** | §5.5/5.6 的阴性**可能无效**（命令可能被主芯片丢弃） | 找一个**副作用可在别处观测**的 A 类命令（如 `0xA0-0x0D` 若真执行会清缓冲）做交叉验证 |
| **H3** | 历史"39 条命令穷举"用的是 `0E <op> 00 00 01 01`（子命令恒 0、且方向=读） | 那份"命令空间无震动命令"的结论**作废**（文档里已标注，但结论仍被引用过） | 只在**安全类**上重做（避开 0x00/0x03/0x0E） |
| **H4** | 我在同一天内**两次改变通道结论**（output/input ↔ feature），并把 A1 帧误判为主因（后已更正） | 早期记录的因果判断不可全信 | 本文 §5 已按时间重排并标注"今天新做" |
| **H5** | **`err=122` 的语义未经验证**（我按 `ERROR_INSUFFICIENT_BUFFER` 解读，但 4096 字节缓冲也是 122） | 以 122 推断"回复形状不对"属于**推测** | 用 `RtlNtStatusToDosError`/驱动日志或换一条已知成功的读来标定 |
| **H6** | 可读空间的"点按 vs 不碰"对照中，**无法确认用户当时是否真的触发了咔哒**（旧日志只有 contacts，没有 button 状态） | §5.2/5.3 的阴性**可能是"没有震动可测"** | 监听 PTP 的 **button usage**（rid=4 里的 button 位），把"真咔哒"时刻对齐到采样 |
| **H7** | `0x452C` 读成高熵数据 ⇒ 本机与 NORMANDYL **地址布局不符**，我尚未解释 | 用 fwupd 的地址做交叉验证时**可能读错东西** | 读 `0x60CC`/`0x5095`/`0x5096`/`0xC000` 看是否吻合；或说明 16 位窗口有**分页** |

## §7 ★ 剩余机会空间（按 价值/代价 排序，全部可执行）

### ~~🔥 O1（已结案，撤销）—— HID 触觉页 `Intensity`（Col02 `rid=9`）~~
- **撤销原因**：项目 2026-09-13 已做**带阳性对照**的实测（`WHY-NOT-VIBRATE.md` §3）：连写 6 个强度值，
  **力度确实改变（写入到达设备）但没有一次产生震动**；且 **写 100 = 反馈关闭**。

### 🔥 O2（唯一真正新的主机侧线索，价值仍有限）—— 厂商 feature 通道 `rid=11` 的"发/收"配对
- 已确认：`SetFeature(rid=11, len=67)` **被接受**（`err=0`）。
- 未知：回复在哪。**可试**（按代价排序）：
  1. **载荷去掉首字节 0x0E**（即 `20 …` 开头）再发一次，然后用 Col04 `GET_INPUT` 读；
  2. 命令行发完后，用 **`ReadFile` 自发报文**（独立句柄、短超时）抓是否推来回复；
  3. **`GetFeature` 扫 rid 组合**：`rid=11/12/6/13` × 长度 `65/66/67/257/737`（这是一次读，安全）；
  4. 若某组合返回 **`0E 20 …` 形状** ⇒ 拿到同步厂商通道 ⇒ **A 类（0xA0/0xA1）回复很可能也能读出来**（那将直接打开触觉命令的门）。
- **风险**：低（都是读帧/已知写帧）。

### 🔥 O3（高，纯离线/联网）—— **补齐缺失的 5,141 B 尾部**
- 途径 A：**Windows Update / Microsoft Update Catalog 找 Goodix 固件 CAB**（我们手上的 `GT7936L_16753412.cab` 就是这类包；**它当初是怎么来的值得复现**）；
- 途径 B：找**同族（7868/7863/Berlin）完整容器**（其它 OEM 的 Goodix 固件包）；
- 收益：拿到 **USART1 ISR（帧装配/校验）** 与 **播放入口的调用者** ⇒ 明确"谁在什么条件下让 LRA 响"。

### O4（中）—— **主芯片命令信箱 `0x60CC` / 状态 `0x5095`/`0x5096` 的"点按时刻"观测**
- 从未做过：**在真咔哒期间**窄窗口监视这三个地址（≤80 次读）。若主芯片用信箱转发触觉命令，这里会露出来。
- 注意：**只读**，不要写 0x00/0x03/0x0E 类命令。

### O5（中）—— **澄清 O7/H7：本机是否是 GTX8**
- 读 fwupd 已知地址 `0x60CC`/`0x5095`/`0x5096`/`0xC000`/`0x452C` 并与 fwupd 语义比对；若全不符，考虑"16 位窗口有分页/银行"的可能。

### O6（兜底，最可靠）—— **D1 硬件**
- 拆机接**主 ASIC ↔ 触觉芯片**的 I2C1/USART1 测试点，ESP32 嗅探一次咔哒 ⇒ 得到**真实播放帧**，照抄注入 ⇒ **原装 LRA 随滑随震**。
- 本轮新增可用资产：**v1 帧格式、55 字节分块、`more/seq` 续块、危险命令清单**。

### O7（旁路）—— **LVFS / 开源生态继续挖**
- fwupd 只有一份 Goodix 触控板固件；但可查其它 OEM（Dell/HP/ASUS）的 Goodix 更新包、以及 `fwupd` 的 `brlb`（BERLIN）实现（**32 位地址 v2 协议**）是否含更多命令语义。

> 实际意义：**第一步处置应是"杀进程 + 等 1–2 分钟"**（今天两次都有效），EC 复位作为后备 —— 这与旧文档的处置顺序有实质增量。

## §8 安全红线（汇总，硬性）


1. **禁止枚举 class `0x00`/`0x03`/`0x0E`**（固件更新/复位；历史挂死真因）。
2. **禁止整段快照**；类 0x20 读 **≤80 次/轮、≤3 次/秒、轮间 ≥3 分钟**，前后各一次 `HEALTH`。
3. A 类（`0xA0/0xA1`）帧：**用户在场且知情**时才发；发前确认已保存工作。
4. 冻结处置：**先杀进程**（关句柄取消挂起 IRP）→ 等 1–2 分钟 → 无效才 EC 复位。
5. 所有探针**必须带单次调用超时护栏**（`VibLink` 已实现）；发/读分离时读侧用 `ONE`（一进程一次调用）。
