# ★★★★★★ 2026-10-10 B12 破局：**官方落盘命令就是 `0E 12`** —— 项目把它列在红线名单里

> **触发**：喆「这些一起做了……再还有什么能做的？」
> **性质**：**纯离线**（只读官方源码；未开设备、未写设备）。
> **来源**：**`goodix/gdix_hid_firmware_update`（Goodix 官方，`master` 分支）** 逐文件逐行阅读；关键源码已落地到 `_gdix_src/`。
> **⚠️ 先声明**：`《全书》§2.6.4` **已有交互路径的握手序列**（`0x80→0x82→写0x96F8→0x83→0x7F/7E0007→0x7D`）。**本文档的新增部分是：`0x12` 这条"RAM→flash 提交"原语的完整格式 + 校验和 + 结果轮询 + 它与本项目红线的关系 + ISP 持久路径。**

---

## 0. 一句话结论

> **Goodix 官方【没有】任何"commit / magic / flush"命令。持久化的唯一机制是命令 `0E 12`** ——
> **"把 RAM `0xC000` 里的一块数据写进 flash 的指定地址"**，并轮询 `0x5096` 直到 `0xAA`。
> **而这正是本项目【红线名单】里的 `0E 12`。**
> ⇒ **B12 从"不知道要发什么"变成"知道要发 `0E 12`，且知道它的完整格式、校验和、结果判据与风险来源"。**

## 1. 官方写 flash 的唯一原语：`GTx2Update::load_sub_firmware`

继承链：`GT7868QUpdate : GTx3Update : GTx2Update`；**`GTx3Update` 没有重写** `load_sub_firmware`，所以落到 `GTx2Update`（`gtx2/gtx2_update.cpp:139-213`）。

```cpp
int GTx2Update::load_sub_firmware(unsigned int flash_addr,
                                  unsigned char *fw_data, unsigned int len)
{
    unsigned char buf_load_flash[15] = {0x0e, 0x12, 0x00, 0x00, 0x06};
    unsigned int unitlen = 0, load_data_len = 0;
    unsigned short check_sum = 0;

    while (retry_load < GDIX_RETRY_TIMES && load_data_len != len) {
        unitlen = (len - load_data_len > RAM_BUFFER_SIZE)
                  ? RAM_BUFFER_SIZE : (len - load_data_len);          /* ★ 4096 */

        /* ① 把这一块写进 RAM 暂存区 */
        ret = dev->Write(FLASH_BUFFER_ADDR, &fw_data[load_data_len], unitlen);  /* 0xC000 */

        /* ② 算 16 位大端字和 */
        for (check_sum = 0, i = 0; i < unitlen; i += 2)
            check_sum += (fw_data[load_data_len + i] << 8) +
                         fw_data[load_data_len + i + 1];

        buf_load_flash[5]  = (unitlen    >> 8) & 0xFF;   /* 长度 高 */
        buf_load_flash[6]  =  unitlen          & 0xFF;   /* 长度 低 */
        buf_load_flash[7]  = (flash_addr >> 16) & 0xFF;  /* 地址 [23:16] */
        buf_load_flash[8]  = (flash_addr >>  8) & 0xFF;  /* 地址 [15:8]  */
        buf_load_flash[9]  = (check_sum  >>  8) & 0xFF;  /* 校验和 高 */
        buf_load_flash[10] =  check_sum        & 0xFF;   /* 校验和 低 */

        /* ★★★ ③ 提交：让 IC 把 RAM 里这块写进 flash */
        ret = dev->Write(buf_load_flash, 11);

        usleep(80000);
        retry = 100;
        do {                                             /* ★④ 轮询结果 */
            dev->Read(FLASH_RESULT_ADDR, temp_buf, 1);    /*   0x5096 */
            if (temp_buf[0] == 0xAA) break;
            usleep(2000);
        } while (--retry);

        if (!retry) { retry_load++; ret = -1; }           /* 失败⇒整块重发，最多 6 次 */
        else {
            load_data_len += unitlen;  flash_addr += unitlen;
            dev->Write(0x5096, &dummy, 1);                /* ★ 清零结果寄存器 */
            ret = 0;
        }
    }
    return ret;
}
```

## 2. ★★★★★ 与项目红线名单的关系 —— **答案就在红线里**

### 2.1 项目现行红线（四条）

```
00 10   00 11   0E 12   0E 13
```

### 2.2 官方源码里这四条**全部**都有对应，且**语义明确**

| 命令 | 上线字节 | **官方语义** | 出处 | 风险评估 |
|---|---|---|---|---|
| **`0E 10`** | `0E 10 00 00 01 01` | **切到 patch / bootloader** | `gt7868q_update.cpp:128,144` | 中等（进升级态） |
| **`0E 11`** | `0E 11 00 00 01 01` | **启动更新（Start update）** | `gt7868q_update.cpp:129,184` | 中等 |
| **`0E 12`** | `0E 12 00 00 06 <len16> <addrHi> <addrMid> <ckHi> <ckLo>` | ★ **把 RAM `0xC000` 的一块写进 flash**（**持久化的唯一机制**） | `gtx2_update.cpp:148-176` | ⚠️ **高**：官方**无独立 erase**，擦除隐含在此命令内 ⇒ **错地址会擦错区** |
| **`0E 13`** | `0E 13 00 00 01 01` | **复位 IC**（= 让新固件**生效**，**不是**落盘） | `gt7868q_update.cpp:130,266` | **低**（只是重启） |

**⇒ ★★★ 关键结论**：
1. **`0E 12` 不是"危险魔法"，它是官方每次刷固件都必发的常规提交命令** —— 项目对它"不知道是什么所以不敢发"的状态**可以结束**。
2. **项目的谨慎【仍然正确】**，但理由变了：危险不在"这条命令本身"，而在**"它没有独立擦除步，擦除是隐含的"** ⇒ **任何地址算错都可能擦掉不该擦的区域**。
3. **`0E 13` 复位是"生效"而非"落盘"** —— 不要把它当持久化手段。

## 3. ★★★★ 完整的官方固件更新序列（`GT7868QUpdate::fw_update`）

出处：`gt7868q/gt7868q_update.cpp:122-311`

| # | 动作 | 发什么（上线字节） | 目标 | 之后等什么 |
|---|---|---|---|---|
| 1 | 切 patch | `0E 10 00 00 01 01` | 直发 | `usleep(250000)` |
| 2 | 关坐标上报 | 写 `0x4160` ← `{33,00,00,00,33}`（**重发 3 次**） | `CMD_ADDR` | — |
| 3 | 等 bootloader | 读 `0x5095` ×1 B | `BL_STATE_ADDR` | **轮询到 `== 0xDD`**（6 次 × 30 ms） |
| 4 | 启动更新 | `0E 11 00 00 01 01` | 直发 | `usleep(100000)` |
| 5 | ★ **逐个子固件** | 每个 4 KB 块：`0xC000` 写 → `0E 12 …` → 轮询 `0x5096==0xAA` | flash 子固件地址 | 见 §1 |
| 6 | （可选）配置 ISP | 同 §1，目标 `0x19000` | `CFG_FLASH_ADDR` | 同 §1 |
| 7 | 开坐标上报 | 写 `0x4160` ← `{34,00,00,00,34}` | `CMD_ADDR` | — |
| 8 | ★ **复位 IC** | `0E 13 00 00 01 01`（重试 3 次） | 直发 | `usleep(300000)` |
| 9 | 切 PTP | 写 `0x4160` ← `{32,00,00,00,32}` | `CMD_ADDR` | — |

> **写 `0x4160` 的 5 字节命令格式**：`{cmd, dataHi, dataLo, ckHi, ckLo}`，其中 **`ck = cmd + dataHi + dataLo`**（`gt7868q_update.cpp:381-391` 的 `cmd_init`）。所以 `{33,00,00,00,33}` 末尾那个 `0x33` 是**校验和**，不是重复命令。

**★ 失败分支同样执行**：开坐标（`0x34`）→ 复位（`0x13`）→ 切 PTP（`0x32`）。

## 4. ★★★★ 两条配置更新路径 —— 这解释了 B12 的症状

`Run()` 里二选一（`gt7868q_update.cpp:97-118`）。

| | **路径 1：ISP 写 flash（持久）** | **路径 2：交互式（写 RAM）** |
|---|---|---|
| 函数 | `flash_cfg_with_isp()` `:313-379` | `cfg_update()` `:393-592` |
| 数据写到哪 | 先 `0xC000`，再 `0x12` → **flash `0x19000`** | **RAM `0x96F8`** |
| 落盘机制 | ★ **`0E 12` 命令本身** | ★ **`0x83` + `0x7D` 握手让 IC 自己决定** |
| 序列 | 无握手；直接 `load_sub_firmware(0x19000, …)` | `轮询 0x4160==0xFF` → 写 `{80,…}` → **轮询 `0x4160==0x82`** → 写 `0x96F8` → 写 `{83,…}` → **轮询 `0x4160` 读 5 B == `0x7F` 或 `7E 00 07`** → 写 `{7D,…}` |
| 结果校验 | 轮询 `0x5096==0xAA` | `7F`=成功 · **`7E 00 07` = "配置与 flash 相同"** · 其它=失败 |
| 收尾 | 由外层统一（开坐标→复位→PTP） | 仅开坐标 `0x34` |

### ★★★ 对 B12 的诊断（三种可能，按可能性排序）

| # | 诊断 | 依据 |
|---|---|---|
| **1（最可能）** | **流程只到"写进 RAM 暂存"就结束，从未发过 `0E 12`** —— 本质上是**从没给 IC 发过"请写 flash"的指令** | 官方**没有**独立 commit；持久化唯一机制就是 `0E 12` |
| **2** | 走交互路径时**缺 `0x83` / `0x7D`**，或**没等 `0x82` 应答** | 官方交互路径必须完成 `0x80→0x82→写→0x83→0x7F/7E0007→0x7D` 全握手 |
| **3（辅助）** | 补上 `0E 12` 后**没有复位 `0E 13`** ⇒ 数据已落盘但**新配置尚未被加载** | `0x13` 是"生效"步 |

> **★ 注意 `7E 00 07` 的官方语义**：`"config data is equal with flash"` —— **`7E 00 07` 不是错误码，它表示"你发的配置与 flash 里已有的完全相同"**。
> ⇒ 本项目过去的判据（`7E 00 07`=与 flash 一致 / `7E 00 02`=有差异）**方向是对的**，但要知道：**做幂等写入时必然得到 `7E 00 07`，那是正常结果。**

## 5. `update flag` 与 `0x12` 的校验和（两个易错点）

### 5.1 `updateFlag` **不是从 IC 读的**

```cpp
// firmware_image.cpp:266-272
updateFlag FirmwareImage::GetUpdateFlag() {
    if (hasConfig) return (updateFlag)(m_firmwareData[m_firmwareSize + 6 + 2]);
    return NO_NEED_UPDATE;
}
```
⇒ **它来自 `.bin` 的 config pack 第 `+2` 字节**，**从未写进 IC 任何寄存器**；只用于 **host 端分支**。
（枚举：`0x00` NO_NEED_UPDATE / `0x01` NEED_UPDATE_FW / `0x02` NEED_UPDATE_CONFIG / `0x10` NEED_UPDATE_CONFIG_WITH_ISP / `0x80` NEED_UPDATE_HID_SUBSYSTEM；`firmware_image.h:31-38`）

### 5.2 ★ `0x12` 的校验和 = **16 位大端字和**（不是字节和！）

```cpp
for (check_sum = 0, i = 0; i < unitlen; i += 2)
    check_sum += (data[i] << 8) + data[i+1];      // unsigned short ⇒ 自然模 65536
```
**⇒ 按【大端 16 位字】累加，不是逐字节累加**（注意：这与**容器级**校验和的"逐字节累加"**不是同一种**，别混）。
**⇒ 地址只发 `[23:16]` 与 `[15:8]` 两个字节**（因为调用方 `sub_fw_flash_addr` 已 `<<8`）⇒ **地址按 256 字节对齐**。

## 6. ★★★★ 最小风险验证设计（**未执行**，需喆批准）

> **红线原则不变**：`0E 12` 仍属高危动作（**无独立 erase，擦除隐含其中**）。
> **但现在的关键差别是：它的格式、地址算术、校验和、结果判据、重试行为【全部已知】** ——
> 所以可以从"盲目试探"升级为"**带完整前后校验的单次受控试验**"。

```
【阶段 0 · 恢复路径（必须先做）】
  0-1 记录基线：cfg 六字段（+0x10F/+0x111/+0x113/+0x115/+0x117/+0x119）+ 0x96F8 前 32 B + 0x19000 前 32 B
  0-2 确认设备健康三连（probe 5/5）
  0-3 写下"阴性判据"与"回滚动作"再动手

【阶段 1 · 只读侦察（零风险）】
  1-1 读 0x4160（CMD_ADDR）—— 官方语义：0xFF = IC 空闲
  1-2 读 0x5095（BL_STATE_ADDR）—— 当前是否 0xDD（是否在 bootloader）
  1-3 读 0x5096（FLASH_RESULT_ADDR）—— 当前值

【阶段 2 · 单次受控提交（★ 唯一有风险的一步）】
  2-1 选一个【已知无害且非关键】的 4 KB 目标地址（候选：flash 0x0A000，官方常量已知；或 cfg 的 0x19000 若走 ISP 路径）
  2-2 先【读回该地址 4 KB 内容并留存】—— 这是"能恢复"的前提
  2-3 把【原样内容】写回 0xC000 → 发 0E 12（长度/地址/字和校验）→ 轮询 0x5096 == 0xAA
      ★ 注意：写【原样内容】⇒ 幂等 ⇒ 即使成功也【不会改变任何东西】⇒ 这是最安全的首次试发
  2-4 立刻读回该地址 4 KB 逐字节比对
  2-5 结果判读：
        · 0x5096 == 0xAA 且读回逐字节一致 ⇒ ★ 持久化原语【打通】（且未改变任何数据）
        · 0x5096 != 0xAA ⇒ 记阴性、停止、不做任何进一步动作
  2-6 之后才考虑 0x13 复位与重启验证

【阶段 3 · 持久性验证】
  3-1 复位（0E 13）→ 重读该地址
  3-2 若仍一致 ⇒ 落盘成立；若回原值 ⇒ 说明 0x12 只到 RAM

【禁止】
  ✗ 不对【自身未知用途】的地址发 0x12
  ✗ 不在未读回原内容前发 0x12
  ✗ 不连发（一次一个块，每块前后校验）
```

**★ 为什么阶段 2-3 用"原样内容"**：官方 `load_sub_firmware` 是"擦+写" ⇒ 用原样内容写回，**结果与现状等价**，却完整走通了 `0E 12` 的全部协议（含校验和与结果轮询）。**这是把"高危动作"变成"幂等探针"的标准做法**，与 elgato 第 7 步"在没人用的擦除块上试写"同源。
