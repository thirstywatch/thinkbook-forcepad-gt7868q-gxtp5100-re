# 我的项目 vs 蓝莓项目 —— 具体区分 + 推进路线

> 日期：2026-10-03 · 触发：喆用蓝莓的方法复现了 Surface 全部四份固件（`surface_fw/SURFACE-ANALYSIS.md`）
> 本文只回答两件事：**① 两个项目到底差在哪；② 这次复现给我的项目带来了什么可执行的东西。**
> 本文所有数字都是本轮实测；脚本在 `surface-vs-mine/`，可复跑。

## 0. 结论速查

| # | 结论 | 对"推进"的意义 |
|---|---|---|
| 1 | **他不是"攻破了原厂"，是"绕开了原厂"** —— 他把模组拆出来配自研 ESP32-S3 主控，自己写 HID 描述符 | 他的"主机能触发触觉"**不可移植**；我们面对的是厂商固件 |
| 2 | **他那边触觉 IC 是"智能 DSP"（CS40L25，带固件容器）；我们这边是"哑驱动 IC"（AW86927，8 KB SRAM + 3 根 TRIG）** | **"去厂商固件包里翻波形"这条方法论在本机结构性无效** |
| 3 | **他那边 EC 固件是明文；我们手上一度以为 EC 固件只有那份 3 MB 加密的** | 本轮证明：**EC 固件在本机 BIOS 包里就是明文** ✅ |
| 4 | ★★★ 本机 BIOS 更新包 `NJCN67WW.exe` 是 **7-Zip SFX**，解出 `isflash.bin`（**19.2 MB 明文 flash 镜像**）+ `platform.ini` | **新的、远比 3 MB 加密包更肥的明文靶场** |
| 5 | ★★★ `isflash.bin` 里有一个 **明文、带标签、未加密的 216 KB 固件**：`UUITE5507-COMPAL01EC-USER0-BS-CODE` | 首次拿到本机**可读的 EC 类固件** |
| 6 | ★★★ 全 19.2 MB 明文 BIOS 里 `AW86927/86927/GXTP5100/GT7868Q/TF100A/Goodix/Haptic/Touchpad/tpcfg` **命中数 = 0** | **EC/BIOS 侧不管触觉**，第三条独立证据到手 |
| 7 | 那份 216 KB 固件的词汇**全是 USB-PD / 扩展坞**（TCPC 寄存器 `0x14/0x1A/0x26…`、`VDM`、`4CC`、`Sink/Source`、`SRDY/SRYR`、`Volt:`、`Curr_L:`） | 它**不是**触控板相关的 EC，是 **PD/扩展坞控制器**（或 EC 的 PD 子模块） |
| 8 | 本轮交付一个**已标定的"固件形态验收器"** `ec_accept.py`：明文 EC **96 分** vs 加密 6–19 分（自检间距 **65**） | 把"解 NJME 加密"从人工挑 XOR 变成**自动打分排序** |

## 1. 三个根本区别（先看这个，再看细节表）

### 1.1 角色不同：**他是设计者，我们是使用者**

| | 蓝莓 | 我们 |
|---|---|---|
| 硬件 | **把 Surface Laptop Studio 1964 的触控板模组拆出来**，接到自研底板上 | 模组留在原机上 |
| 主机 | **他自己的 ESP32-S3**（他写 I²C 主机 + USB HID 描述符） | Windows（inbox `hidi2c` + HID 类驱动） |
| HID 描述符 | **他自己写的**，主动加了 `0x41 Intensity / 0x42 Waveform+Duration / 0x43 Manual Trigger` | 厂商固件里的，`Col02 OutputReportByteLength = 0` |
| 结论 | 他"能做主机触发触觉"，是因为**他就是主机** | 我们改不动设备侧 ⇒ 发出去石沉大海 |

> ★ **这一条决定了"他能做到"不能当"原厂板本来就能"读。** 我在 `SURFACE-ANALYSIS.md` 里逐条复现了他的技术结论（HMWF 几何、DSP 地址布局、初始化表、强度映射都对上了），但**那些结论全部是"他自研主控视角下的描述"**。

### 1.2 器件不同：**智能 DSP vs 哑驱动 IC**（这是最关键的一处）

| | 蓝莓（CS40L25） | 我们（AW86927） |
|---|---|---|
| 是否有固件容器 | ✅ **有**（`SurfaceTouchpadHaptic_2.9.139.bin` 105,591 B → 39,370 B） | ❌ **没有这种概念** |
| 固件形态 | 167 个带 CRC16 的 **DSP 地址-数据写入块** | — |
| 是否有算法 ID | ✅ `0xBD` = VIBEGEN、`0x111` = DYNAMIC_F0 | ❌ 无 |
| 波形存放 | DSP 内存里的 **wavetable 描述符链 + u24 采样**（XM 25 / YM 53） | **8 KB SRAM，掉电即失，每次上电由 I²C 主控下载** |
| 播放选择 | mailbox 索引 + 强度→press/release 索引映射 | **3 根 TRIG × 2 边沿 = 6 条波形** |
| 结果 | ★ 存在"一份触觉固件包"这个东西，所以有"挖出来"这个动作 | ★ **结构性不存在"触觉固件包"** |

> ★★ **这解释了本项目一个长期困惑**：
> 我们一直拿 CS40L25 的模板去找“本机触觉固件”，于是出现"他容器里有 `directory_xm`/`BRIDGE_*` 目录，我们载荷 A 零个有意义 ASCII"。
> **不是我们没认出来，是本机没有被认的对象。**
> ⇒ **"照蓝莓去翻厂商固件包找波形"这条方法论在本机不成立**（见 §5 P5）。

### 1.3 封装不同：**他的 EC 明文，我们的（一度以为）只有密文**

| | 蓝莓那边（SAM = Surface EC） | 我们这边 |
|---|---|---|
| EC 固件 | `SurfaceSAM_9.101.139.bin` · **明文 Thumb + 2,002 条字符串池** | 一度以为只有 `NJME01WW.exe` 里那份 **加密 + LZMA 的 3 MB overlay** |
| 触觉在 EC 里长什么样 | 设备名（`ActuateHaptic`/`HAPTIC_DRIVER`/`BUCK_BOOST`）+ 5 档比较链 + **71 项大端 `reg:val` 初始化表** + BuckBoost 5 项 ROM 虚表 | 未知 |
| 判决 | ✅ 能**直接读**到"EC 侧触觉控制面" | ❌ 读不到（这**不是方法差，是封装差**） |

> ★ **本轮最重要的转向**：本机的 EC 类固件**并不是只能从那份加密包里拿**。见 §3。

## 2. 逐维度对照表（可直接贴墙）

| 维度 | 蓝莓（Surface Laptop Studio 1964） | 喆（ThinkBook 14 G6+ IMH / 21LD） |
|---|---|---|
| 触控主控 | Synaptics **S96U7** | 汇顶 **GT7868Q / GXTP5100** |
| 触控主控固件 | 独立包 `SurfaceTouchpad_4.12.139.bin`（**熵 7.894 = 加密**，真实标识符 0） | 载荷 A（**数值表，无代码**）+ 载荷 B(TF100A) |
| 压力器件 | 独立包 `SurfaceTouchpadForce_10.0.156.bin`（稠密数据表） | 钛方 **TF100A**（载荷 B，**明文 Thumb-2**，20,314 条指令） |
| 触觉 IC | Cirrus **CS40L25**（20 脚，带 DSP） | 艾为 **AW86927FCR**（丝印 `CA4F`，LRA 驱动） |
| 触觉"固件" | ✅ `SurfaceTouchpadHaptic_2.9.139.bin`（167 块） | ❌ 无（波形运行期由主控写入 8 KB SRAM） |
| EC | **SAM**（Surface Aggregator）+ 明文固件 | 联想/ODM EC（`NJME##WW`）+ **BIOS 包里另有明文 ITE 镜像** |
| EC 是否控触觉 | ✅ **是**（SAM → I²C `0x43` → CS40L25） | ❌ **三条独立证据都说否**（见 §4.3） |
| 主机能否触发触觉 | 原机否 / **他自己的板能（因为板是他设计的）** | ❌ 结构性封死（`Out=0`，无第三方 filter，无厂商服务） |
| 触觉参数载体 | Haptic 固件的 30 个追加块（描述符链 + u24 采样） | `tpcfgsid*.cfg` 触觉区 `TAG 0x50–0x7A`（**时长阶梯** `0x5C`，不是波形索引） |
| 波形来源 | 固件容器里挖出来 | GT7868Q 上电下载 / 或走 AW86927 **RTP（芯片内固定波形）** |
| 器件数 | 4（触控 + 压力 + 触觉 + EC） | 4（触控 + 压力 + 触觉 + EC），但**触觉器件不带固件** |

★ **一句话**：**Surface 是"四个都会思考的芯片"，ThinkBook 是"一个会思考（GT7868Q）+ 三个哑器件"。**
蓝莓的做法（逐个芯片挖固件）只对"芯片里有固件"的那一类有效。

## 3. ★ 本轮复现带回来的新东西（这部分是纯增量）

### 3.1 ★★★ 本机 BIOS 更新包 = 7-Zip SFX，可直接解

```
<HOME>\Downloads\NJCN67WW.exe   12,790,536 B
  7-Zip l  → Type = PE ... Name = 7zS.sfx.exe (7-Zip Setup SFX 4.57)
  7-Zip x  → 10 个文件 / 27,330,087 B
    isflash.bin        19,205,640 B   ← Insyde H2O 全 flash 镜像（明文）
    platform.ini           61,204 B   ← flash 分区与流程配置
    H2OFFT-Wx64.exe     3,754,928 B   ← Insyde 官方刷写器
    BiosImageProcx64.dll · FlsHook.exe · InterToolx64.efi · H2OFFT.cat/.inf ...
```

**复跑**：
```bash
"E:/AAA/7-Zip/7z.exe" x "<HOME>/Downloads/NJCN67WW.exe" -o<任意目录> -y
```

### 3.2 ★★★ `platform.ini` 给出的权威事实

```ini
[Region]      BIOS=1  GbE=0  ME=0  EC=0  DESC=0  Platform_Data=0
[UpdateEC]    Flag=0  EC_Path=(空)  EC_BlockSize=64
[SecureUpdate] UpdateEcOnBothRomEcRegionAndEcPart=0
[Platform_Check] PlatformName1=ILVR4  PlatformName2=ILVR6
```

⇒ ① **这个 BIOS 包不刷 EC**（`EC_Path` 为空）⇒ 与"EC 固件独立投递（`NJME*.exe`）"这条旧结论一致；
⇒ ② 但 `[Region]` 里**有 `EC` 这一区**、`[SecureUpdate]` 提到 **`RomEcRegion`** ⇒ **EC 镜像可以（也确实）被放在 BIOS 镜像里** —— §3.3 证实了这一点。

### 3.3 ★★★ `isflash.bin` 里有一个**明文、未加密**的 EC 类固件

```
$_IFLASH_DRV_IMG   @0x00058C0
$_IFLASH_BIOSIMG   @0x01E69B8 / 0x0BB58A0 / 0x0FB58A0
[$_IFLASH_BIOSCER</] @0x011F5AF8
@0x01E6A50  a5a5a5a5a5a5 85958512 5a5aaa aa  "UUITE5507-SB-V0.0520190926"           块长 20,480 B
@0x01EBA50  a5a5a5a5a5a5 a4b58512 9c6eaae7  "UUITE5507-COMPAL01EC-USER0-BS-CODE"  块长 216,064 B
```

- 头部结构（两个块一致）：`6 B 魔数 A5×6` + `4 B` + `4 B` + `NUL 填充的版本标签` + `3C C3 A5 5A` + `01 00 00 00` + 三个 u32。
- 块 A 的第 1 个 u32 = `0x5000` = **块 B 起点的相对偏移**（`0x1EBA5E − 0x1E6A5E = 0x5000`）⇒ **两块是同一容器里连续的两段**。
- **标签里写着 `COMPAL01EC`** ⇒ 这是 Compal（本机 ODM）项目的 **EC** 固件；`ILVR4` 与 `platform.ini` 的 `PlatformName1` 一致 ⇒ **确实属于本平台**。

### 3.4 ★★★ 它（以及整份 19.2 MB BIOS）里**没有任何触觉/触控板词汇**

```
全 19,205,640 B 明文扫描：
  AW86927 / 86927 / GXTP5100 / GT7868Q / TF100A / Goodix / GOODIX
  Haptic / HAPTIC / Vibrat / Actuator / Touchpad / Trackpad / tpcfg / tpcfgsid
  → 命中数 全部 = 0
  LRA → 1 次（0x5B52E4）· VIB → 1 次（0x9C7796）   ← 噪音级，非词汇
```

而那份 216 KB 固件的**全部标签词汇**是 USB-PD / 扩展坞：

```
> PD Port:   > PD CB Port:   > 4CC CMD:   > Wr VDMs   > AttnVDM
> Rd 0x14 / 0x1A / 0x26 / 0x27 / 0x28 / 0x33 / 0x34 / 0x57 / 0x58 / 0x61
Wr Power Path Sink SRDY   > Wr SRYR   > Wr AMEx   > Wr AMEn   > gaid Done
> In Sink / In Source   > Ctrl Sink PWR   > Volt :   Curr_L :
> Dock BTN Mk: / Bk:   DOCK_BTNmk   Dock_reSend   > Dock notify
```

⇒ **它是 PD/扩展坞控制器（或 EC 的 PD 子模块）固件，不是触控板相关的 EC。**

### 3.5 ★★ `NJME*.exe` 的加密区边界首次被**精确**划出

PE 的 `DataDirectory[4]`（Security）**存在且恰好到达文件末尾**：

| | 文件长 | 签名块（明文 PKCS#7） | 真正加密的 payload |
|---|---:|---:|---:|
| `NJME01WW.exe` | 3,312,224 | `@0x326240` · **10,272 B** | **3,121,728 B** |
| `NJME07WW.exe` | 3,347,968 | `@0x32EE88` · **10,104 B** | **3,157,640 B** |

**剥掉签名区后重算**：
- 相同率 **0.3885%** vs 随机基线 `1/256 = 0.3906%` ⇒ **两版明文完全不同（结论不变）**；
- 相同段**只有两处**：`[0x0, 6) = 7a6c621a1ae1`、**`[0x0A, 0x30) = 38 B 全同`**；
- **唯一随版本变化的字段在 payload+`0x06`..`+0x09`**（A `f6 ac e0 04` / B `f5 f3 e0 0f`）；
- payload+`0x0A` 起始的 38 字节以 **`5d 00`** 开头 —— 与 §19.29.5② 记的"LZMA 首字节常为 `5D`"是同一线索。
⇒ ★ **已知明文锚点从 6 B 扩到 ~44 B**，且多了一个"版本字段"的位置。

### 3.6 ★★ 交付一个**已标定**的固件形态验收器

`ec_accept.py`：把 `SURFACE-ANALYSIS.md` 里 SAM 的形态（低熵明文 + 字符串池 + 大端 `reg:val` 表 + Thumb-2）**量化成 0–100 分**。

| 输入（已知） | 分 | 判决 |
|---|---:|---|
| SAM body（**明文 EC**） | **96** | PLAINTEXT-EC ✅ |
| Surface Touchpad body（**加密**） | 14 | CIPHER ✅ |
| Surface Haptic body（块表） | 19 | CIPHER ✅ |
| `ite_ec_blockB.bin`（明文 8051/PD 固件） | 39 | DATA/OPAQUE ⚠️ |
| `NJME01WW` overlay（加密） | **6** | CIPHER ✅ |
| `NJME07WW` overlay（加密） | **7** | CIPHER ✅ |

**自检（打乱对照，`--selftest`）**：同上 SAM 明文 **96** vs ① XOR-1024 打乱 **31** ② 字节乱序 **15** ③ 均匀随机 **3** ⇒ **判别间距 65**。

> ⚠️ **诚实标注两处局限**：
> 1. `ite_ec_blockB`（真正文）只有 39 分 ⇒ **本工具对"8051 类、词汇少"的 EC 家族偏保守**，别拿它单独判"是不是明文"；
> 2. 它的 `KEYWORDS` 面向触觉/触控词汇 —— **这个偏见本身是有用的诊断**（本机 EC 类固件对它 0 命中，正是 §3.4 那条结论）。

## 4. 复现之后，我项目里被改写的判断

### 4.1 ❌ 作废：「要定案 EC 控不控震动，必须先解那份 3 MB 加密 payload」
**改为**：EC 类固件在 `isflash.bin` 里就是明文（§3.3）——**解密这条路可以先不走了**。
（`NJME*.exe` 到底装的是什么，反而成了新问题：**3.12 MB 明文 ≫ 一个 EC 固件的 216–256 KB**。）

### 4.2 ⚠️ 降级：「载荷 A 里没有波形 ⇒ 波形要么在芯片 ROM，要么本机没启用触觉」
**加上第三支**：AW86927 是哑驱动 IC，**它的波形本来就不该以"固件容器"形式出现**。
蓝莓那边能挖出波形，是因为 CS40L25 有 DSP 和 `wmfw`；**本机没有等价物**。

### 4.3 ✅ 加强：「EC 不管触觉」现在有**三条互相独立**的证据

| # | 证据 | 出处 |
|---|---|---|
| 1 | ACPI 的 EC 命名空间 141 处引用，**0 处触觉对象**（全是功耗/热管理） | 全书 §19.25.3 |
| 2 | 全 19.2 MB 明文 BIOS：触觉/触控板词汇 **命中 0**（本机 EC 类固件词汇 100% 是 USB-PD/扩展坞） | **本轮新增** |
| 3 | 结构类比：Surface 的 EC 能控触觉，是因为触觉 IC 是**带 DSP 的智能芯片**；本机 AW86927 是**哑驱动 IC**，没有"EC 转发波形索引"这种设计空间 | **本轮新增** |

⇒ **barryblueice 的「thinkbook 大概率是 ec」对本机不成立**（他是"大概率"推测，不是一手证据）。
⇒ **`poc\ec-haptic-probe.ps1`（EC RAM 差分）的优先级可以降下来** —— 它想回答的问题，离线已经答了。

## 5. 推进路线（按性价比排序）

### P1 ★★★★★ 把"EC 线"从**解密题**改成**比对题**（半天内可闭合）
**要回答的唯一问题**：`isflash.bin` 里那份 `UUITE5507-COMPAL01EC-...` 是不是本机的 EC？

| 判据 | 做法 | 结果含义 |
|---|---|---|
| 版本串比对 | DMI 报 `EC FW Rev 2.67`；`NJME01WW/NJME07WW` 是 EC 包名。看 ITE 镜像里的 `V0.05 / 20190926` 是否能对上其中任何一个 | 对得上 ⇒ **本机 EC 已到手（明文）** |
| 长度/标签比对 | 若哪天解出 `NJME` payload，比它是否含 `UUITE5507` / `COMPAL01EC` / `ILVR4`（本轮在密文里搜这 4 个词 = **0 命中**，符合"全加密"） | 一致 ⇒ 三方闭环 |
| 反汇编验证 | 216 KB、熵 5.79 —— 按 ITE EC（8051 核）反汇编，看是否有 EC 特征外设（KBC/eSPI/ADC） | 有 ⇒ 确认是 EC，而非纯 PD 控制器 |

> ★ **判据要写成可证伪的**：如果三条都对不上，就应当承认"这份 ITE 镜像是 PD/扩展坞控制器，本机 EC 仍只在 `NJME*.exe` 里" —— **不要为了保住结论而模糊化**。

### P2 ★★★★ 用 `isflash.bin` 把既有结论做一次**全盘交叉验证**（1 小时）
19.2 MB 明文 BIOS 是**本项目此前从未有过的资源**。可一次跑完：

- `TB14P_GT7868Q_*` 的载荷 A/B 是否出现在 BIOS 里？（本轮按关键词推：**不在** ⇒ 触控板固件确实独立于 BIOS）
- `tpcfgsid*.cfg` 的 `TAG` 命名空间是否出现在 BIOS？（若出现 ⇒ 找到 cfg 的"出厂来源"）
- `EcCapsuleDxe.bin` 的 `_AUTOPAD/_TBT_IMG/_ISH_IMG` 标签与 `$_IFLASH_*` 标签体系是否同源？
- **这一条最有价值**：BIOS 里有没有 `AW86927` / `GPIO` / `TRIG` 相关的**板级配置（GPIO 表 / ACPI）** ⇒ 可能直接回答 **TRIG1/2/3 接到 GT7868Q 哪根脚**（现在是"淘汰法结论"，中等强度）。

### P3 ★★★★ 用 `ec_accept.py` 把"解 NJME"从**人工挑**改成**自动排序**（2–3 小时）
现状：`.text` 里 147 处真 XOR + 25 处 rol/ror，人工看不出哪处是 payload 解码循环。
改法：
```bash
# 对每一处 XOR 候选（偏移 × 密钥长度）生成解的候选，然后：
python ec_accept.py --body cand_<i>.bin --json cand.json
# 按 EC 分排序取前若干，再人工看
```
- ★ 先在 **SAM** 上验收器必须打 ≥70（已做到 96），否则先修工具（纪律 §19.31.4 坑 32）。
- ★ 额外锚点：payload 已知明文 `7a6c621a1ae1` + `[0x0A,0x30)` 那 38 字节 + 版本字段在 `+0x06`。

### P4 ★★★★ 关掉 EC 分叉，把火力转到**"本机触觉是否启用"**（§19.25.6 第 6.3 条）
这是**方案分叉点**，且现在是**唯一还开放的高价值问题**：
- 若 AW86927 当前**没被启用** ⇒ 它的 I²C/TRIG 都是空闲资源 ⇒ 难度大降，方案换档；
- 判据：示波器夹 `HDP`/`HDN`（点按应见 200 Hz 差分）/ 夹 `TRIG1-3`（应见窄脉冲）/ 读 `GLB_STATE` 应为 `1001`。
- ★ 本轮新增一条**旁证**：`isflash.bin` 全盘 0 触觉词汇 ⇒ **BIOS/EC 侧没有任何初始化 AW86927 的代码路径** ⇒ "本机触觉未启用"的可能性**上升**。

### P5 ★★ 波形线：**明确换靶，别再翻固件包**
| | 蓝莓 | 我们 |
|---|---|---|
| 波形在哪 | CS40L25 的固件容器里（可挖） | AW86927 的 8 KB SRAM（运行期由主控写） |
| 蓝莓的经验 | ROM 模式"能振，但参数有限"；他自己也**没做**触觉信号适配 | — |
| 结论 | — | **"翻厂商固件包找波形"在本机不成立**；要么走 **RTP（芯片内固定波形）**，要么确定"谁在什么时刻写 SRAM / 打 TRIG" |

# 8. 补章（同日追加）：`isflash.bin` 就是本机当前的 BIOS，以及"换 X9-15"这条线的复核

## 8.1 ✅ DMI 实测：`isflash.bin` = 本机现役 BIOS 的逐版本对应

```
BIOS = NJCN67WW      ← 与下载的 NJCN67WW.exe 版本号完全一致
EC   = 2.67
Model= 21LD
SysVer= ThinkBook 14 G6+ IMH
```
⇒ **不是"某个旧版 BIOS"，就是本机现在跑的这一版**。§3 的全部内容因此可直接用于本机结论。

## 8.2 ⚠️ 但 BIOS 模块是 **LZMA 压缩**的 ⇒ "改几个字节刷回去"不成立

用项目自带的 `bios-re/ffs_scan.py` 扫 `isflash.bin`：**FV=26，1554 行**，其中多处出现
`SEC GUID_DEF guid=EE4E5898-3914-4259-9D6E-DC7BD79403CF`（= **LZMA 自定义 GUID**）。

**直接验证**：在 19.2 MB 明文里搜
| 模式 | 命中 |
|---|---:|
| `3D C6 27 00 00`（`cmp eax,0x27c6`） | **0** |
| `3D E8 01 00 00` / `3D E9 01 00 00` | **0** |
| ASCII `Goodix` / `GXTP` / `TPAD` | **0** |

而 `GoodixTpDxe.asm.txt` 里这些指令**确实存在**（见 8.3）。
⇒ **模块在 FV 里是被 LZMA 压过的**，明文镜像里当然搜不到。
⇒ 要改白名单必须 **解压 → 改 → 重压 → 重建 FV → 重算校验 → 过 Insyde secure flash**，
**不是"定位到偏移改两个字节"**。这条路要走，前提是先解决**签名/安全刷写**（H2OFFT.cat 是签名目录）。

## 8.3 ⚠️ 自我修正：我一度以为"白名单还有一条更宽的判据，可能推翻旧结论"——读完上下文后**不成立**

`GoodixTpDxe.asm.txt` 里同一个函数有**两块**判据：

```asm
; —— 块 A（0x5DC9）：宽判据 ——
00005DBF  xor   eax, eax
00005DC1  test  eax, eax
00005DC3  je    0x5ed0          ; ← 恒成立：控制流总是跳到 0x5ED0
00005DC9  movzx eax, word ptr [rsp+0x40]   ; VID
00005DCE  cmp   eax, 0x27c6
00005DD3  jne   0x5ece
00005DD9  movzx eax, word ptr [rsp+0x34]   ; PID
00005DDE  and   eax, 0xfff0
00005DE3  cmp   eax, 0x1e0      ; ★ 覆盖 0x01E0–0x01EF（含 X9-15 的 0x01EA/0x01EB）

; —— 块 B（0x5ED7）：窄判据（实际生效的那条）——
00005ED7  movzx eax, word ptr [rsp+0x40]
00005EDC  cmp   eax, 0x27c6
00005EE1  jne   0x5f0e
00005EE3  movzx eax, word ptr [rsp+0x34]
00005EE8  cmp   eax, 0x1e8
00005EED  je    0x5efb
00005EEF  movzx eax, word ptr [rsp+0x34]
00005EF4  cmp   eax, 0x1e9      ; ★ 只放 0x01E8 / 0x01E9
00005EF9  jne   0x5f0e
00005EFB  lea   rcx, [rip+0x3c56]
00005F02  call  0x97c
00005F07  mov   byte ptr [rsp+0x30], 1    ; 置"已接受"
```

- 块 A 的**入口被 `je 0x5ed0` 恒定跳过**（编译器把条件常量折叠了），看起来是**不可达的 switch 分支**；
- 块 B 从 `0x5ED0` **顺序落入**，且置位 `[rsp+0x30]=1` 后 `xor eax,eax → 返回 EFI_SUCCESS`。

**⇒ 结论：项目记录的「本机白名单 = VID `0x27C6` 且 PID ∈ {`0x01E8`, `0x01E9`}」站得住，我先前的怀疑作废。**
（★ 这正是项目纪律第 31/32 条的样子：**"看到一个更宽的常量"≠"旧结论被推翻"——先把控制流读完。**）

## 8.4 ★ 新的、值得先做的一问：**"代码 10" 到底归因到哪一侧？**

记录里的现象是「**Windows 能看到设备**但代码 10，读不到 HID descriptor」。
但代码 10（`CM_PROB_FAILED_START`）是 **Windows 侧**的启动失败，而 §8.3 那段判据在 **BIOS DXE 里、只在开机时跑**。

| 问题 | 若答案 | 含义 |
|---|---|---|
| **Q1 主机侧**：Windows 为什么 start 不了它？ | ACPI `_DSM`/`_HID` 不匹配、或 PTP 驱动拒绑、或描述符解析失败 | ⇒ 卡点在**主机侧**，比改签名 BIOS **容易得多** |
| **Q2 固件侧**：BIOS DXE 有没有真的拒绝它？ | 若设备**确实出现在设备管理器**，说明 DXE 这一关**可能已经过了** | ⇒ 项目记录把"代码 10"直接归因白名单，**可能混淆了主机侧与设备侧**（纪律第 33 条那两个问题） |

**可离线做的判据**（本机材料已齐）：
1. 读本机 `DSDT`（`acpi/acpi_all/DSDT_LENOVO_CB-01_DSDT.bin`）里 `I2C0.TPAD` 的 `_DSM`/`_CID` 分支，看是否按 PID 分派；
2. 看 `GoodixTpDxe.asm.txt` 中 `call 0x97c` 之后置位的那条链最终影响什么（枚举、供电、还是 firmware 下载）；
3. 核 `platform.ini` 的 `[PermitFlashVersion]` / `[ForceFlash]` 是否与模块型号相关（**与换模块无关，但能确认刷写门禁**）。

## 8.5 三条路的最终裁定

| 路 | 内容 | 卡点 | 裁定 |
|---|---|---|---|
| **A 纯软件（原装模组）** | — | 主机侧结构封死 + EC 三证据 + AW86927 无固件容器 | ❌ **关闭**（不要再投币） |
| **B 自研主控接管** | 从 `AW86927` 的 I²C（`0x5A`/`0x5B`）或 `TRIG` 引脚接一颗 MCU | 焊接 + 拆机 | ✅ 唯一"完全由你控制"的路（蓝莓就是这么赢的），但**要动硬件** |
| **C 换 X9-15 模块（实物已在手）** | 装上去 | 记录归因：BIOS 白名单 PID | ⚠️ **先做 §8.4 的归因复核**——若真是主机侧（代码 10 是 Windows 的码），这条路可能比记录的容易 |

**⇒ 一句话：如果"现在点按本来就有震感"，那你的真实目标不是"让它震"，而是"让主机能控它" ⇒ 只有 B。**
