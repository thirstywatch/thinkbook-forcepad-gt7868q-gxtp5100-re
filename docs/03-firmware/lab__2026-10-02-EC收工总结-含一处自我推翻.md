## 〇 ★★★ 先说最重要的：**本轮推翻了我们自己文档里的一条"定案"**

### 1.1 之前写下的错误

《全书》多处（§19.26.10.5、§19.28 结论表、交接文档）都写了这句话：

> **「描述符来自 GT7868Q 固件，主机改不了」**
> **「伪造/改描述符 → ❌ 封死」**

**★ 这句话是错的。** 本轮在另一个工区 `<LAB>\ca4f-hunt\`
里找到一个**现成的反例**：

```c
// <LAB>\ca4f-hunt\gt7868q-driver\goodix-gt7868q.c
// Goodix GT7868Q Linux Driver  (C) 2024 Terry Wong <terry.wong2@yahoo.com>
static const __u8 *goodix_gt7868q_report_fixup(struct hid_device *hdev,
                                              __u8 *rdesc, unsigned int *rsize)
{
    if (rdesc[607] == 0x15) {      // 0x15 = Logical Minimum (1 byte)
        rdesc[607] = 0x25;        // 0x25 = Logical Maximum (1 byte)
        dev_info(&hdev->dev, "Report descriptor fixup is applied.\n");
    }
    return rdesc;
}
static const struct hid_device_id goodix_gt7868q_devices[] = {
    { HID_I2C_DEVICE(I2C_VENDOR_ID_GOODIX, 0x01E9) },   // ★ 正是本机的 PID
    { HID_I2C_DEVICE(I2C_VENDOR_ID_GOODIX, 0x01E8) },
    { }
};
```

**⇒ 【内核驱动可以在设备枚举时改写 HID 报告描述符】，而且针对的就是本机 PID `0x01E9`。**
**⇒ 而且它改的不是别的，正是 `Logical Min` ⇒ 逻辑量程/灵敏度。**
**⇒ 同仓库的 `local-overrides.quirks` 里还有 `AttrPressureRange=2:0` 与掌压阈值 ⇒ 相互印证。**

### 1.2 为什么我们之前判"封死"是错的

《全书》2019 行与 3379 行其实**已经描述过这个仓库**，但两次都判它"无用"：

| 位置 | 原文 | 问题 |
|---|---|---|
| L2019 |「内容是 report descriptor 修补，**不碰寄存器、不做任何总线透传**」| ✅ 描述对，但**推论错**：它不需要透传就能改描述符 |
| L3379 |「只是 1,663 B 的 report descriptor 修补，**不碰寄存器、不做总线透传**」| ⚠️ 把它当"能力不足"评价，**没问"改描述符能干什么"** |

**★ 错误的性质（与 §19.27.9 那条同类）：**
**"这个工具不做 A" ≠ "这个工具没用"。**
我们用「它不碰寄存器」否定了它，却没意识到**改描述符本身就是一种能力**。

### 1.3 ⚠️⚠️ 但——**这不改变 §19.27 的最终判决**（必须说清，否则会误以为翻盘了）

**关键区分：改描述符 = 改【主机侧看到的声明】；设备侧仍然按固件原样解析。**

```
主机侧：Linux/Windows  HID 栈  ← report_fixup 改的是【这一侧的副本】
                                  ↓
设备侧：GT7868Q 固件里的 rdesc  ← 【完全没变】
```

| 问题 | 答案 |
|---|---|
| 改描述符能让 Windows 以为"这台设备有 Output 报告"吗？ | ✅ **能**（内核驱动说了算）|
| 主机发一个 `Manual Trigger` 报文过去，**设备会处理吗**？ | ❌ **不会** —— GT7868Q 固件里没有那个接收分支 |
| 依据 | §19.28 已证载荷 A 是纯数值表、**零触觉代码**；§19.26.10.5 已证设备只做了"设备发起" |

**⇒ 这条路的真实形态是：「让 Windows 以为能控制，实际发出去的石沉大海」。**
**⇒ 对"让本机在滑动时震动"这个目标【无效】。**

**★ 但它有一个真实且有限的用途（值得记下）：**
- **改 `Logical Min` 放大压力读数** ⇒ 可能影响**按压阈值的判定**（若阈值判定在主机侧）。
  ⚠️ 但本机阈值判定在**设备侧固件**里（点击阈值 140/98 是设备行为）⇒ 主机改量程不改变阈值。
- **改 `Usage` 让 Windows 上报不同的接触面积** ⇒ 影响 Windows 自己的手势判定（如压力相关设置项）。
  ⇒ 这是**改 Windows 行为**，不是改触控板行为。

## 三★★ 附带产出：一条被误判的"封死"，和它的正确形态

### 3.1 `RawRdesc.cs`：纯用户态拿不到原始 rdesc

写了这个工具（`touchpad-lab\poc\RawRdesc.cs`），结论是**能力边界**：

| 方法 | 能否拿到原始 rdesc 字节 |
|---|:--:|
| `HidD_GetPreparsedData` | ❌ 返回**不透明结构体**，无 API 反推 |
| `IOCTL_HID_GET_DEVICE_DESCRIPTOR` | ❌ 需**内核态** filter driver |
| 注册表 `Enum\HID\...` | ❌ 不存 rdesc |
| **KMDF filter，在 `IRP_MJ_READ` 完成时读 buffer+4096** | ✅ **唯一可行** |
| Linux `/sys/kernel/debug/hid/0018:27C6:01E9.000X/rdesc` | ✅ 可行（需另机/另系统） |

★ **顺带纠正一个概念混淆：**
《全书》§19.27 的判定**不需要**原始 rdesc ——
它用的是 `HidP_GetCaps` 读**解析后**的 caps（`out=0`），那是权威结论。
⇒ **"改 rdesc" 与 "改 caps" 是两件事**：内核驱动改的是 rdesc 源码，
解析后如果新声明了 Output，caps 才会变 —— **这才是这条路的技术入口**。

### 3.2 ⚠️ 由此产生一条**新的、值得做的小实验**（不需硬件）

```
用 Linux live USB（本机触控板在 Linux 下是 raw I2C 设备，§19.25.3 已用）读：
  /sys/kernel/debug/hid/0018:27C6:01E9.000X/rdesc
  → 核对第 607 字节是否 0x15
  → 若相符：那个 report_fixup 驱动可以在本机复现
  →★ 顺带：Linux 下的 HID 栈【没有 Windows 那套 PTP 专有逻辑】，
          若能在 Linux 下直接看到/改描述符，那就是最干净的实验台
```
⚠️ **但目的不是"让 Windows 以为能控制"（无效，见 §1.3），
而是【确认我们 §19.27 的 caps 判定在原始描述符层面是否一致】。**

## 四★★★ 收尾：EC 唯一值得做的下一步，还是那个零风险实验

**§19.29.5① 的 `poc\ec-haptic-probe.ps1` 依然是全场性价比最高的动作。**

理由（本轮之后更明确了）：

| 路线 | 需要什么 | 能回答什么 |
|---|---|---|
| **EC RAM 差分** | 20 分钟 + 8 KB RAM 读权限（**已有**）| **EC 到底参不参与震动** ← 这是分叉点本身 |
| 解 EC 固件 | 攻 147 处 XOR + 重放算法（数小时~数天）| EC 固件里有没有触觉代码 —— **但这不回答"EC 控不控制"** |
| 抓 rdesc | Linux live USB | 核对一个字节（顺手做）|

**⇒ 逻辑上：差分实验直接回答分叉问题；解固件只是回答一个更细的子问题。**
**⇒ 若差分显示"按压时 EC RAM 无任何变化"⇒ EC 线基本可关，不必解那 3 MB。**
**⇒ 若差分显示"有变化"⇒ 再解固件才有意义（那时是去找那几个偏移的读写点）。**

## 五★★ 本轮纪律（第 31–33 条）

31. ★★★ **"某工具不做 X" ≠ "该工具没用"。**
    本项目两次用「`ty2/goodix-gt7868q-linux-driver` 不碰寄存器」否定了它，
    **而它做的正是 `report_fixup` —— 改写主机侧的 HID 报告描述符**，
    针对的还是本机 PID `0x01E9`。
    ⇒ **评估一个外部工具前，必须先读完它的全部能力，再问"这些能力对我有什么用"。**
    （与 §19.27.9 的 `ObjectTypeIndex`、§19.29.7 的"边界设定"同源：
    **都是"给评估对象划了太窄的框"。**）

32. ★★ **capstone 的 `disasm()` 遇到非法字节会整体停摆。**
    `.text` 里混着 Delphi 的 RTTI/字符串/跳转表，纯线性反汇编只解出 **88 条**就断。
    ⇒ 必须开 **`md.skipdata = True`**，否则会误判"代码里没有 XOR"。
    ⇒ **本轮就踩了：先得出"没有 XOR 循环"，开 skipdata 后是 147 处。**
    **⇒ 教训：反汇编结果"什么都没找到"时，先怀疑工具配置，再怀疑被测对象。**

33. ★ **"用工具 A 改主机侧的声明" ≠ "设备侧会执行它"。**
    改 rdesc 能骗过 Windows 的 HID 栈，但**设备固件的接收分支不会因此出现**。
    ⇒ 评估"改描述符"这类方案时，必须分两问：
      **Q1 主机侧会怎么反应？**（可改）
      **Q2 设备侧会怎么处理？**（不可改 ⇒ 石沉大海）
    本项目此前只问了 Q1 就判"封死"，或只想到 Q1 就以为"能成"，**两个方向都错**。
