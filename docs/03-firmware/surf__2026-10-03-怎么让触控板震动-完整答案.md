## 一、本轮硬结论（解压 31.57 MB 明文后得到）

### 1.1 修好了一个**卡住整条线的工具 bug**

`bios-re/ffs_scan.py` 里的常量：
```python
LZMA_GUID = bytes.fromhex("9858ee4e14395942d69ede7bd79403cf")   # ← ❌ 字节序写反
```
**正确值**（实测命中 14 次）：
```python
LZMA_GUID = bytes.fromhex("98584eee14395942 9d6edc7bd79403cf".replace(" ", ""))
          # = 98 58 4E EE 14 39 59 42 9D 6E DC 7B D7 94 03 CF
```
**另有第二个坑**：UEFI 这个 GUID 段的压缩数据是 **LZMA_FORMAT_ALONE（13 字节头：props + dictSize + u64 原始长度）**，
**不是 RAW**。用 `lzma.LZMADecompressor(format=lzma.FORMAT_ALONE)` 才对；用 `FORMAT_RAW` 一律报 `Corrupt input data`。

⇒ 修正后：**11 个段全部解压成功，合计 31,570,000 字节明文**（`lzma_out/`）。

### 1.2 ★★★★★ 硬结论：**BIOS 里没有任何 AW86927 的引用**
在**解压后的 31.57 MB 明文**里搜：

| 模式 | 命中 |
|---|---:|
| `AW86927` / `86927` | **0** |
| `GT7868Q` / `TF100A` | 0 |
| `GXTP5100` | 1（在 DSDT 的 `TPID` 表里） |
| `Goodix` | 12（全部在同一个模块里，见下） |

> ★ 这一条把上一轮的"⚠️ BIOS 是 LZMA 压缩的，搜不到 ≠ 不存在"**从"未定"变成了"硬结论"**：
> **主机侧的 BIOS/EC 世界里，完全没有 AW86927 的位置。**

### 1.3 ★★★★ 顺带定性了那个 DXE 模块（明文，不再是压缩包）
```
GoodixTouchpadUpdate
c:\minnowboard\Build\Vlv2TbltDevicePkg\GtpUpdate\GoodixTouchpadFMPImpl.c
<InitGoodixDevice> / <InitGoodixHidDescriptor> / <transWrite> / <transRead>
GtTransmissionWrite / GTPHIDWrite
FmpGetImageInfo() / FmpSetImage / FmpSetPackageInfo
```
⇒ **这个 DXE 的唯一职责就是"触控板固件的 UEFI FMP 更新"**（在 BIOS 阶段刷 GT7868Q/TF100A 的固件）。
★ 而且 **`GtTransmissionWrite` 全镜像只出现 1 次**，位置就在这个 FMP 模块里 ⇒
**它写的是 GT7868Q 自己的内部目标/flash，不是"往 AW86927 转发"。**

## 二、所以"让触控板震动"的三条路，按可行性排序

```
主机 (Windows)
  ├─ ① 标准 HID 触觉 usage  → Col02 Out=0     ❌ 发不出
  └─ ② 厂商命令             → Col04 (RID 0x0E, 64B 双向)   ✅ 能发
        ▼
   GT7868Q（0x2C / _ADR=1）   ← BIOS 阶段由 GoodixTpDxe 用 GtTransmissionWrite 写它自己的 flash
        ▼
   AW86927（0x5A / 0x5B）     ← 寄存器/SRAM/时序全公开，可驱动；但**没有合法的公开入口**
        ▼
      LRA
```

### 路径 1 ★★★★★ **先验证：AW86927 是不是就在【主机 I²C 总线】上**
**依据（硬）**：蓝莓在小米那台上，**用同一条 I²C** 访问了触控 IC（`0x2C`）**和马达（`0x50`）**。
⇒ 这类模组里，**触控 IC 与马达 IC 共享同一条对外 I²C 排线**。
**若本机也是这样** ⇒ 主机可以直接对 `0x5A` 写 ⇒ **照抄公开序列就能震，纯软件，不改任何固件。**

**怎么做（零成本，项目自己标注过却从没真做）**：
1. 用 **Linux live USB** 启动（项目已经用过这个环境做实验）
2. ★ 关键前提：Linux 下**触控板指针不动** ⇒ 说明 `i2c-hid` 很可能**没有成功占用** `0x2C`
3. 先解绑再扫：
   ```bash
   i2cdetect -l                       # 找到触控板那条 bus（Intel I²C0）
   ls /sys/bus/i2c/drivers/i2c_hid/   # 若 0x2c 在，先 unbind
   i2cdetect -y <N>                   # ★ 扫，看有没有 0x5A / 0x5B
   ```
   ⚠️ 项目记过"`i2cdetect` 崩内核" —— 但那是**在 `i2c_hid` 占着 `0x2C` 时**。
   项目自己写下的方法学保留正是：「**须确认扫的是触控板那条 bus、先解绑 `i2c_hid`**」。
   **这条保留到今天还没被执行过。**
4. **判据（二元）**：
   - 扫到 `0x5A`/`0x5B` ⇒ **赢了**：主机直连，照抄 §三 的序列即可
   - 扫不到 ⇒ 马达确实在 GT7868Q 的私有总线上，走路径 2/3

### 路径 2 ★★ 让 GT7868Q 转发
**依据弱**：BIOS 里 0 引用 AW86927；`GtTransmissionWrite` 只有 1 处且属 FMP。
**⇒ 如果 AW86927 的波形是 TF100A（Force IC）发的**（艾为官方架构：「Force IC 算出力后按压力等级把波形发给 AW86927」），
**那 GT7868Q 根本不需要转发** ⇒ **路径 2 很可能不存在**。

### 路径 3 ★ 改 GT7868Q 固件
官方 `tpupdate_7868q` 通道存在（戴尔包实证），但要过 UEFI 胶囊签名。**最后再考虑。**

## 三、一旦路径 1 成立，照抄这段就能震（源码实证）

```
① 软复位      写 0x00 ← 0xAA，延时 3 ms
② SRAM 初始化 0x45 |= bit2 (EN_RAMINIT)
③ 基址        0x2D ← 0x08 ; 0x2E ← 0x00          (SRAM base = 0x0800)
④ 写指针      0x40 ← 0x08 ; 0x41 ← 0x00
⑤ 写波形头    连续写 0x42：01 08 05 <end_hi> <end_lo>
                （ver=1, start=0x0805(BE), end=0x0805+len-1(BE)）
⑥ 写波形      连续写 0x42：N 字节（先用驱动自带的 102 B 正弦波）
⑦ 检测序列    0x4E ← 检测序列0=VBAT ; 0x4D ← GO ; 延时 3 ms ; 0x4D ← NA
⑧ 关 SRAM 初始化 0x45 &= ~bit2
⑨ ★ 播放      0x09 ← STOP
               0x08.PLAY_MODE = 0 (RAM) ; 0x08.AUTO_BST = 1
               0x0A.WAVSEQ1 = 1 ; 0x0B.WAVSEQ2 = 0 ; 0x12.SEQ1LOOP = 0x0F
               0x07 ← 0x7C                      (增益，防失真)
               0x09 ← 0x01                      ★★ GO=1 → 震
```
全部来自 `aw86927/aw86927_clean.c`（Linux 主线版，854 行）；波形数据也在文件里。
**另：艾为官网有 `AW86927S_GUI`（波形设计工具）和 `AW86927S_Driver_MCU`（官方 MCU 示例）—— 需注册/客户权限。**

## 四、下一步（就一件事）

> **插一个 Linux live USB，先 `i2c_hid` unbind，再 `i2cdetect` 扫触控板那条 I²C。**

- **扫到 `0x5A`** ⇒ 路径 1 成立 ⇒ 写一个 SPB 客户端驱动（或 Linux 下直接 `i2cset`）就能让它震，全程纯软件。
- **扫不到** ⇒ 只能走"接管硬件"或"改固件"。

★ 这一步**不需要买设备、不需要拆机、不需要改任何东西**，而且能一次性把"到底有没有纯软件路"这个问题结掉。
