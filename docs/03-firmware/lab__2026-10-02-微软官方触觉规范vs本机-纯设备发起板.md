# 微软官方触觉规范 vs 本机 —— 2026-10-02 晚

> **一句话结论：本机 GXTP5100 是【纯设备发起(device-initiated)】触觉触控板。
> 厂商严格按微软规范做了"设备发起"那一半，连集合层级都对；但"主机发起"那一半整块没做。**
>
> **⇒ 这一条把"主机侧无触觉控制面"从"实测现象"升级为"规范对照后的必然结果"。**

## 一★★ 规范要求 vs 本机实测：逐项对照

本机数据来自 `poc/hid-dump.txt`（`AllCaps.cs` 实测，4 集合全覆盖）。

### 1.1 集合层级 —— ★★ 完全符合规范

| 规范要求 | 本机实测 |
|---|---|
| Haptic Touchpad 的 `SimpleHapticsController`（`0x0E/0x01`）**必须是 PTP 顶层集合的子集合** | ✅ 顶层 = `0x0D/0x05`；SHC = **`lc=6`（`0x0E/0x01`）** 确实挂在下面 |

**⇒ 厂商是照着规范做的，不是随手写的。**

### 1.2 ★★ 主机发起（host-initiated）的 5 个必备项 —— **本机一个都没有**

| Usage | 名称 | 报告类型 | 本机 |
|---|---|---|---|
| `0x0E/0x10` | `Waveform List` | Feature (GET) | ❌ 无 |
| `0x0E/0x11` | `Duration List` | Feature (GET) | ❌ 无 |
| `0x0E/0x21` | **`Manual Trigger`** | **Output** | ❌ 无（**本机 `Col02 Out = 0`**）|
| `0x0E/0x23` | `Intensity`（Output 侧）| **Output** | ❌ 无（同上）|
| `0x0E/0x01` | `SimpleHapticsController` | 集合 | ✅ 集合存在（但里面没内容）|

### 1.3 设备发起（device-initiated）—— ⚠️ 部分符合

| 规范要求 | 本机实测 | 判读 |
|---|---|---|
| `Haptic Intensity` Feature（`0x0E/0x23`） | ✅ **存在**：`FEAT rid=9 up=0x0E u=0x23 lc=6(0x0E/0x01)` | ✅ 有 |
| 规范要求逻辑范围 `min=0`、`max>=4` | ⚠️ **本机是 `log=[100..1]`**（反向刻度） | ❌ **范围不合规** |
| `Button Press Threshold` Feature（`0x0D/0xB0`，物理 `110g..190g`，默认 `150g`）| ❌ **无**（本机 `0x0D` 只有 `0x59/0x55/0x56/0x54/0x30/0x31/0x51`）| ❌ **缺失** |

### 1.4 禁止项 —— ✅ 合规

| 规范禁止 | 本机 |
|---|---|
| `0x0E/0x20Auto Trigger` | ✅ 未声明 |
| `0x0E/0x22 Auto Trigger Associated Control` | ✅ 未声明 |

## 二★★ 三个此前没被点破的推论

### 推论 1：本机震动**不是**"没做触觉"，而是"只做了设备发起那一半"

规范把触觉分成**两套独立机制**：

| | 设备发起（device-initiated） | 主机发起（host-initiated） |
|---|---|---|
| 触发者 | **触控板自己**检测到按压/释放 | Windows 主机发`Manual Trigger` |
| 配置方式 | `SET_FEATURE` 写 `Haptic Intensity` | Output 报告 |
| 本机 | ✅ **做了**（`0x0E/0x23` 存在） | ❌ **完全没做** |

**⇒ 这精确解释了§19.26.10.2 的实测现象**：
「开启 Windows 触觉点击后按压会震动」——因为**震动是触控板自己触发的**，
Windows 只是通过 `SET_FEATURE` 写了一个强度值（`FeedbackEnabled` / `FeedbackIntensity`）。

⚠️ **并且它解释了为什么 §19.26.8 的 ETW 抓不到任何东西**：
主机发的是 `SET_FEATURE`（走 Feature 路径），而 `Microsoft-Windows-SPB-HIDI2C`
的 opcode 表**只有 Read 类事件**（§19.27.1）⇒ **`SET_FEATURE` 在 SPB 层是写事务，本来就抓不到。**
这不是"抓不到"，是**那条路上本来就没有可观测的读事务**。

### 推论 2★ `Intensity` 逻辑范围 `[100..1]` 不合规 —— 这是一个**可动手的把手**

规范：`min=0`、`max>=4`、用户设置线性映射。
本机：`min=100`、`max=1`（**反向**）。

**⇒ Windows 设置界面能显示"触觉点击"并保存偏好，说明它认这个 Feature。**
**⇒ 但刻度反向意味着 Windows 写的值与固件理解的语义可能是反的。**

⚠️ **这不构成"能用"的机会** —— §19.17.3 / `追加十五` 已实测：
写 RID 9 强度**手感无变化**（`intensity-probe.ps1` 记录）。
**⇒ 那次实测的负结论，现在有了规范层的解释：**
**不是"写不进去"，而是"写进去也没用，因为主机发起的整条通路根本不存在"。**

★ **但这引出一个更值钱的问题**：
`Intensity`（设备发起）既然在描述符里、且能被 Windows 写，
**那它到底控制什么？** 如果它控制的是"按压震动强度"，
**那么把它的逻辑范围改成合规的 `0..4`，是否就能让 Windows 的设置真正生效？**
—— ⚠️ ~~**描述符来自 GT7868Q 固件，主机改不了**~~ 🔴 **2026-10-02 夜推翻**（§19.30.1）：`report_fixup` 可改**主机侧**副本。**判决不变**：设备侧无接收分支。
所以这条路仍然封死，但**问题本身值得记下来**。

### 推论 3★★ 官方规范给出了**本项目最需要的"那五条 usage"的权威出处**

§19.26.10 之前，本项目一直用"规范要求 `0x0E/0x21` 作为 OUTPUT"这种**二手转述**。
现在拿到了**一手规范原文**，并发现一个**此前没人提过的关键事实**：

> **`Waveform List`（`0x0E/0x10`）与 `Duration List`（`0x0E/0x11`）是 `Feature` 报告，
> 不是 Output 报告 —— 而 Windows 触控板驱动栈在枚举时会主动 `GET_FEATURE` 读它们。**

**⇒★ 这是一个此前被完全忽略的可能性：**

| 过去我们的假设 | 规范给的真相 |
|---|---|
| "主机要控制触觉，必须设备有 **Output** 报告；本机 `Out=0` ⇒ 死路" | **不完全对** |
| — | 主机**枚举时**会读 Feature 拿"有哪些波形、各多长" |
| — | 这个读取是**必须成功**的（否则 Windows 不会认为设备支持触觉） |
| — | **若本机能补上 `0x0E/0x10` + `0x0E/0x11` 两个 Feature，主机侧就能知道它有哪些波形** |

⚠️ **但这仍然走不通**（理由要写清，避免下次又误判）：
1. ~~描述符在固件里，**主机改不了**~~ → 🔴 **已推翻**（§19.30.1）：主机侧副本**可以改**（`report_fixup`）；改不了的是**设备侧**那一份；
2. `Manual Trigger` 是 **Output**，本机 `Out = 0` ⇒ **发不出触发命令**；
   ⇒ 即使补了 Feature，也只是让主机"看得见"，**仍然"按不动"**。

**⇒ 净结论：规范没有打开任何新路，但把"为什么打不动"的链条补全了。**

## 三★★ 规范里对**本项目方案设计**直接有用的三条

| # | 规范条款 | 对我们的用处 |
|---|---|---|
| **1** | `Waveform Cutoff Time`（`0x0E/0x28`）逻辑最小值须 ≥ `最长波形 × (Repeat Count max + 1)` | ★ 若将来我们能控制波形，**这是唯一能在不改固件前提下"合法地延长震动时长"的字段** |
| **2** | `Retrigger Period`（`0x0E/0x25`）逻辑 max 须 ≥ **1000 ms** | ★ 意味着"一次触发最长可播 1 秒+" —— **对"滑动时持续反馈"这类需求足够** |
| **3** | `Intensity`（`0x0E/0x23`）逻辑 max **不得超过 100** | 本机是 `100..1`，**恰好在合规上限内**，只是方向反了 |

★ **第1、2 条合起来给了一个具体的设计目标**：
若某天真能主机侧触发，**"滑动时震"的最省事实现 = 发一个 `Manual Trigger` + 大 `Retrigger Period` + 大 `Waveform Cutoff Time`**，
不需要多波形、不需要波形选择。**这比"选一个特定波形"简单得多，也是任何合规实现的标准做法。**

## 四★★ 对蓝莓 wiki 的一处更正（他转述得不够准）

蓝莓 `HID-Descriptor.md` 里写他定义了：

```
Report ID 0x41：Intensity Feature
Report ID 0x42：Waveform List + Duration List Feature
Report ID 0x43：Manual Trigger Output
```

**对照微软官方 Haptic Touchpad 示例（§8.1），编号完全一致**：

| Report ID | 微软官方示例 | 蓝莓 | 一致？ |
|---:|---|---|:--:|
| `0x40` | `Button Press Threshold` Feature | 未提 | ❌ 缺 |
| `0x41` | `Haptic Intensity` Feature | `Intensity Feature` | ✅ |
| `0x42` | `Waveform List` + `Duration List` Feature | 同| ✅ |
| `0x43` | `Manual Trigger` + `Intensity` Output | `Manual Trigger Output` | ✅ |

**⇒ 蓝莓是照着这份规范做的（连 Report ID 都一样）。**
**⇒ 但他漏了 `0x40 Button Press Threshold`** —— 而微软明确要求
**"Haptic Touchpad 若支持触觉，这份报告是必需的"**。

⚠️ 这可能是**他自己的项目里Windows 侧行为不完全符合规范的原因之一**，
也是一个值得向他确认的点（见提问清单 Q9）。

## 五★★ 完整"主机侧无触觉控制面"的证据链（现在闭合了）

```
微软规范：主机发起触觉需要 5 个必备项
   Waveform List (0x0E/0x10, Feature)      ❌ 本机无
   Duration List (0x0E/0x11, Feature)      ❌ 本机无
   Manual Trigger (0x0E/0x21, Output)       ❌ 本机无
   Intensity      (0x0E/0x23, Output)       ❌ 本机无
   SHC 集合       (0x0E/0x01)               ✅ 有（但空）
                    ↓
实测：Col02 OutputReportByteLength = 0     （§19.17.2 / §19.27.2）
                    ↓
描述符的 Output 长度 = 固件声明的，不可主机修改
                    ↓
⇒ Windows 在枚举时读到"这台设备没有 Output 报告"
⇒ 不会启用 Manual Trigger 通路
⇒ 主机侧结构性封死（三条独立硬事实 + 规范对照，两条腿都站住了）
```

**⇒ 与 §19.27 完全自洽，且现在多了规范这一独立腿。**
