## 一、蓝莓前代项目（小米机型）实证

### 1.1 他的 README 原文（`ESP32-Precision-TouchPad`）

> **Currently Touchpad Support (already tested):**
> - Lenovo ELAN 33370A TouchPad (Rev.A S8974A, traditional mechanical design)
> - **XiaoMi book 2022 14/16 pro Goodix GT7863 TouchPad (Haptic Engine design)**
>
> **Important**: «小米推广的压感触控板只是用压力感应的马达触发替换了传统机械结构……**Recommand to use XiaoMi Goodix TouchPad.**»

仓库里还带着 `3D Model/XiaoMi Goodix GT7863 with Haptic Engine/`（外壳/底壳/固定板 STEP）。

### 1.2 ★★★★★ 马达控制全文（`main/main/hack/goodix_i2c_motor_hack.c`）

```c
#define MOTOR_ADDR       0x50       // ← 马达芯片自己的 I²C 从地址
#define PIN_SDA          7
#define PIN_SCL          6
#define PIN_RST          3
...
    i2c_device_config_t motor_cfg = {
        .dev_addr_length = I2C_ADDR_BIT_LEN_7,
        .device_address  = MOTOR_ADDR,
        .scl_speed_hz    = 100000,
    };
...
    while (1) {
        uint8_t cmd[] = {0x01, 0x81};        // ← 全部内容：写寄存器 0x01 = 0x81
        i2c_master_transmit(motor_handle, cmd, sizeof(cmd), 50);
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
```

**⇒ 就这么多。** 马达 = 总线上的一个普通 I²C 从设备，**写两个字节就震**。

### 1.3 触控 IC 的完整协议（`main/main/i2c/goodix/goodix_i2c.c`）

```c
#define I2C_ADDR 0x2c          // ← 触控 IC（与本机 DSDT 的 0x2C 一致）
#define RST_IO 3
#define INT_IO 4

/* 上电 */
uint8_t pwr_on[] = {0x05, 0x00, 0x08, 0x00};

/* 切 PTP（精确式触摸板）模式 */
{ 0x05,0x00,  0x33,0x03,  0x06,0x00,  0x05,0x00,  0x03,0x03,0x00 }
/* 切鼠标兼容模式 */
{ 0x05,0x00,  0x33,0x01,  0x06,0x00,  0x05,0x00,  0x01,0x00,0x00 }

/* 读触控数据：I²C 直读 64 字节 */
i2c_master_receive(dev_handle, data, 64, ...);
  data[2] == 0x04  → PTP 报文（scan_time/button_mask/finger 布局都在里面）
  data[2] == 0x01  → 鼠标报文（x/y/buttons）
```

★★★ **这是【I²C 直连】版的汇顶私有命令**：`0x05/0x00` = **Command Register**，
`0x33/0x0N` = **SET_REPORT + Feature ID**，后面跟 feature 内容。
⇒ 与 `goodix_advance_touch_platform/hid.c` 里那条 `((type)<<4)|reportnum` 的 HID 封装**是同一套命令，只是一个走 I²C 直连、一个走 HID 报文**。

### 1.4 那份 GT7863 HID 描述符 = 本机 Col04 的同族

他 wiki 里 `About-Goodix-TouchPad.md` 给出从寄存器 `0x20` 读出的完整描述符，**末尾**：

```
06 00 FF  09 01  A1 01  85 0E
   09 01  19 00 29 FF  15 00 25 FF  95 40 75 08  91 02     ← Output 64 B
   09 01  19 00 29 FF  15 00 25 FF  95 40 75 08  81 02     ← Input  64 B
C0
```
**Usage Page `0xFF00`（厂商）、Usage `0x01`、Report ID `0x0E`、64 B 双向**
⇒ ★ **与本机 `Col04` 完全一致**（项目实测：Report ID 0x0E / Usage Page 0xFF00 / 64 B 双向 / `Out=65`）。

描述符里还有同族的其它厂商/特征报文：`85 06 (256B)`、`85 0B (66B)`、`85 0C (736B)`、`85 0D (4B)`、
以及一批 Digitizer 页的 Feature（`09 52/54/55/56/57/58/59/60`）—— **这份描述符就是"汇顶触控 IC 报文全集"的参照表**。

## 二、★ 小米那台的架构真相（拆官方驱动包实得）

你 Downloads 里我再去找，落到了 `XiaomiBookPro16OLED2022ForcePad.zip`（141 KB），解出来只有驱动：

```
ForcePad_12.7.27.908/
  I2CDriver.inf    I2CDriver.sys (273,888 B)    spbi2cdevice.cat    Install.bat
```

`I2CDriver.inf` 关键行：

```ini
[Version]
Class       = Chipsea
ClassGuid   = {8CF3A932-50FB-4FBB-B7D3-1A33912571A7}
Provider    = %ProviderName%
CatalogFile = SpbI2CDevice.cat
[Standard.NTamd64]
%I2CDriver.DeviceDesc%=I2CDriver_Device, ACPI\CSF70001
...
ConnectInterrupt = 0
[Strings]
ProviderName = "Chipsea"
```

**⇒ 三个硬事实：**
1. 小米那台的**压力（Force）芯片是芯海科技**，在 ACPI 里是**独立设备** `ACPI\CSF70001`（带自己的 SPB I²C 驱动）
2. 这与 2022 年公开报道吻合：「小米笔记本 Pro 14/16 压感触控板采用**芯海科技**压力触控芯片 + 瑞声科技 RichTap 马达」
3. 而蓝莓说它的**触控 IC 是汇顶 GT7863**

★★★★★ **⇒ 合并起来的架构与本机【同构】：**

| | 触控 IC | 压力/力 IC | 马达驱动 |
|---|---|---|---|
| **小米 Book Pro 2022** | 汇顶 **GT7863**（`0x2C`，蓝莓实测） | **芯海 CSF70001**（独立 ACPI 节点） | 某 LRA 驱动 @ **`0x50`**（蓝莓实测） |
| **本机 ThinkBook 14 G6+** | 汇顶 **GT7868Q**（`0x2C`/`_ADR=1`） | 钛方 **TF100A** | 艾为 **AW86927** @ `0x5A/0x5B` |

**⇒ 本机不是"异类"，是同一种三厂拼装架构的另一台而已。**

## 三、★★★★★ 新判据：AW86927 可能在**主机 I²C 总线**上

### 3.1 支持这条判据的证据

**蓝莓把触控板模组排线接到自己的 ESP32 上，用【同一条总线】访问了 `0x2C`（触控 IC）和 `0x50`（马达）。**
⇒ 这说明：**在这类模组上，触控 IC 与马达 IC 共享同一条对外的 I²C 排线。**
⇒ 那么**原机主板上那条 I²C，也同时挂着这两个从设备**（排线就那么几根线）。

**套到本机：如果模组内部同样是"GT7868Q + AW86927 共享对外 I²C"，那么 `0x5A` 就在主机总线上，
Windows 可以直接对它发 I²C 事务 —— "隔着 GT7868Q"这个问题根本不存在。**

### 3.2 ⚠️ 而项目原来那条反证是**无效的**

项目 §19.25.3 记：「Linux 总线扫描见没见到 `0x5A` —— **没见到**」，
但同一行就写明了方法学保留：「**须确认扫的是触控板那条 bus、先解绑 `i2c_hid`**」，
且全书另处记录「触控板那条总线 `i2cdetect` **崩内核**」。

**⇒ 用一条"扫描本身可能失败"的观测，去支持"设备在私有总线上"的结论，是不成立的。**
（这与项目纪律第 32 条同源：**反汇编/扫描"什么都没找到"时，先怀疑工具配置。**）

### 3.3 ⇒ 正确的下一步（不是再扫 Col04）

> **扫主机 I²C 总线上的其它从地址**，看有没有 `0x5A` / `0x5B`。

项目**已经规划过**这条路（`2026-10-01-方案A-关闭安全机制扫I2C-操作手册.md`），当初卡在
「`RwDrv.sys` 被易受攻击驱动黑名单 + HVCI 拦住」。
★ 本轮多了一个**新的对照样本**：小米那个 `I2CDriver.sys`（`spbi2cdevice.cat`，**微软签名**）
就是**一个厂商用来访问 Force 芯片的 SPB I²C 客户端驱动** ——
说明"写一个自己的 SPB 客户端去访问触控板总线上的从设备"是**合规且被厂商自己采用的做法**。

## 六、本轮纪律（第 46–48 条）

46. ★★★ **"别人的旧项目"是最容易被忽略的金矿。**
    我说"查了蓝莓的项目"，其实只查了他**新**项目的 wiki，**没查他前代项目的源码**——
    而**马达控制代码就在前代项目里，两行**。⇒ **跨项目找同一作者的历史产物。**

47. ★★★ **"同构机型"要去找【同类的另一台机器】，而不是找"同一台机器的更多资料"。**
    我一直在本机内部挖，而**小米那台是同构的、已经被别人完整驱动过的机器**。
    它的 `0x50` 直接把"马达是总线上一个普通从设备"这件事证明了。

48. ★★ **"总线扫描没找到"这类证据，必须先确认扫描本身是成功的。**
    项目那条「Linux 扫不到 `0x5A`」带了自己的方法学保留（`i2c_hid` 占用 / `i2cdetect` 崩内核），
    **但它仍被当作支持性旁证用了很久**。⇒ **弱证据要当场标注强度，不能沉淀成"事实"。**
