# 为什么电脑程序不能让我这块触控板震动

> 面向"第一次问这个问题"的人。不需要读过项目其它文档。
> 机器：Lenovo ThinkBook 14 G6+ IMH (21LD) · 触控板 Goodix **GXTP5100**（芯片家族 **GT7868Q**）· VID 27C6 / PID 0x01E9
> 结论核实于 2026-09-13。**本文只讲原理与证据，不要求你做任何硬件操作。**

> **【参考 · 对外版 · 2026-09-14 局部修订】** 本文是**可独立分享的解释性文章**，不是状态文档。
> 项目当前权威状态：**`PREFLIGHT-STATE.md`**；Col04 命令空间的边界与读通道语义：**`COL04-BOUNDARY.md`**。
> **本次修订点（只改 §5，其余未动）：**
> - **路 3「外置马达 + 手势软件」已降级** —— 它只能让掌托/底盖震，**满足不了"触控板本体震"**
> - **路 4「拆机」从"不划算"改为"唯一确定可行"** —— 因为背面照片实证模组内 **`HDP`/`HDN` 焊盘裸露**、拆底盖即可触及
> - 另外：原文"那份固件本文 §3 已经逆完了"指的那份明文本**自称 `Test_FW` 且被截断**；其"是否为在跑固件"**从未验证** ⇒ 相关结论的可信度应下调（见 `PREFLIGHT-STATE.md` §1）

---

## 0. 一句话

**主机对这块触控板的马达，有一个"音量旋钮"，但没有"播放键"。**

而且那个"音量旋钮"只能调点击反馈的力度——**不能让它响**。

---

## 1. 先把方向搞对：触控板是**输入设备**

最常见的误解是："我滑动 → 信号给触控板 → 触控板震动反馈给我"。

方向反了。真实的数据流是**单向的**：

```
你滑动手指 ──→ 触控板（采到坐标）──→ 电脑
                 ↑
            你的手指就是那个"输入信号"
```

**你的手指本身就是输入**。触控板确实"做出反应"了——但它的反应是**把坐标上报给电脑**，不是震动。

震动属于**反方向**：要震，得有一条 `电脑 → 触控板` 的命令通道。而**这条通道在这块板子上不存在**。

### 证据：`Col02` 有零个输出报表

本机触控板暴露 4 个 HID 集合：

| 集合 | 驱动 | 能力 | 说明 |
|---|---|---|---|
| `Col01` | `mouhid` | in=9 | 鼠标兼容模式 |
| **`Col02`** | （仅 hidclass） | **in=40 / out=0** / feat=737 | **PTP 主集合** |
| `Col03` | `MTConfig` | feat=3 | 配置 |
| `Col04` | 无 | in=65 / out=65 | 厂商通道（诊断用） |

**`Col02` 的 `out=0`** —— 零个输出报表。

"输出报表（OUTPUT report）"就是 `电脑 → 设备` 的通道。**PTP 集合上一个都没有**，等于主机连一句"震一下"都无处可写。

---

## 2. 那**按下时**为什么会震？

这是最关键的一问。答案是：**那是触控板的局部反射，电脑全程不参与。**

```
你按下
  ↓
压力传感器读到压力
  ↓
【触控板自己的 MCU】判断「超过阈值」   ← 判定发生在板子内部
  ↓
触控板自己使能 TIM3 → PWM → 驱动 LRA → 震一下
  ↓
（顺便）给电脑发一条"按键按下"的报文
```

**最后那步是副作用，不是原因。** 电脑收到"按键按下"的时候，**震动早就已经发生了**。

这就像**膝跳反射**——信号根本没上到大脑再回来，是**局部闭环**。

### 术语与旁证

学术上这叫 **device-initiated（设备自主触发）**。Linux 上游 RFC（2026-06-16，Rong Zhang 发起，input 维护者 Dmitry Torokhov 与 libinput 维护者 Peter Hutterer 参与）里原话：

> "haptic feedback may be either **device-initiated** or host-initiated...
> **device-initiated ones are currently not configurable at all**"

### 一条你自己就能做的验证

写 `Col02` 的 feature 报表 `rid=9`（Haptic Intensity）到 **100，反馈就消失了**——这是本项目的实测结论（用户体感验证）。

**机械开关是不可能被写寄存器关掉的。** 所以：

- 板面几乎不动、只是震一下 ⇒ **点击完全是 LRA 模拟出来的**（MacBook 那种）
- 有清晰段落感、且写 100 之后段落感**还在** ⇒ 点击是机械开关，震动是额外叠加的

（体感判断，零风险，5 秒。）

### 为什么厂商这么做？**因为延迟。**

局部反射 ~1–5 ms；绕到 Windows 再回来 10–30 ms 以上。**点击反馈的手感全在延迟上**，所以厂商宁可把它写死在固件里，也不走主机。

## 3. 主机对这个马达到底有什么？

**有一个"音量旋钮"，没有"播放键"。**

| 能力 | 有无 | 依据 |
|---|---|---|
| **调**震动强度 | ✓ | `Col02` feature `rid=9`（usage `0x0E/0x23` Intensity）。写 1–10 强、50 变轻、100 关闭 |
| **触发**震动 | ✗ | 见下 |

### 触发要什么，以及我们缺什么

微软《Input Device Haptics Implementation Guide》规定，主机要能触发震动，设备**必须**声明：

| 必需 | usage | 本机 `Col02` |
|---|---|---|
| **Manual Trigger**（**OUTPUT** 报表） | `0x0E/0x21` | ✗ **无** |
| Waveform List | `0x0E/0x10` | ✗ **无** |
| Duration List | `0x0E/0x11` | ✗ **无** |
| Intensity | `0x0E/0x23` | ✓ 有（`rid=9`） |

**五条互相独立的证据**都指向"没有"：

1. 本机描述符：`Col02 out=0`，page 0x0E 下**只有 Intensity**
2. 微软规范：主机触发**必须**有 `Manual Trigger (0x0E/0x21)` OUTPUT 报表 + Waveform/Duration List
3. Linux 上游 RFC：device-initiated 的**无法**由主机发起
4. **一份真在 Windows 上跑起来的实现**（社区项目 `ESP32-Haptic-Precision-TouchPad` 的触觉描述符）恰好声明了这几条 usage ⇒ **别人有、我们没有**
5. 第三方 **GT7863**（同族芯片）的描述符里**同样没有**这几条

### 而且我们直接问过它了

上面五条都是"看出来的"。这一条是**试出来的**（2026-09-13，测试 A）：

连写 6 个不同的强度值（5 / 40 / 75 / 15 / 60 / 90，间隔 4 秒），手指全程轻放在板上。

- **点击反馈的力度确实随之改变** ⇒ 写入真的到了设备（**阳性对照成立**，不是空跑）
- **但没有任何一次产生震动** ⇒ 阴性

### 固件侧也堵死了

本项目还把触控板的固件镜像逆了出来（56 KB 明文 ARM 镜像，STM32F1 级内核）。结论：

- 命令分发表**共 39 条**，**全部取得并逐条分析**
- **无一**读写触觉上下文（`ctx+0x14`）、**无一**碰 TIM2/TIM3

⇒ 就算主机能下发，**固件里也没人接**。

**这是"双层缺失"**：主机侧**没有入口**（描述符不声明），固件侧**没有出口**（命令表不碰马达）。

---

## 4. 这不是"原理上不可能"

**Surface 和 MacBook 的触控板就能被主机命令震动**，因为它们的描述符里声明了 `Manual Trigger`。

所以准确的表述是：

> **是这块板子的固件没有暴露这个接口。** 不是 HID 做不到，不是 Windows 做不到。

### 那"滑动震动"在硬件上做得到吗？**做得到。**

触控板**一直知道你在滑动**——它采到了坐标，信息全在它手里；**马达也在它手里**，驱动链（TIM3 → PWM → LRA）现成可用。

**缺的只是一条判断：**

```
现在的固件：  if (压力 > 141)           → 震
想要的固件：  if (压力 > 141 || 在滑动)  → 震
```

**这不是"加一个功能"，是"加一条 if"。** 这正是为什么不甘心——理论上只差几十个字节的代码。

## 5. 那为什么不做？四条路，现在只剩一条

| 路 | 做什么 | 技术 | 代价 | 结论 |
|---|---|---|---|---|
| **1. 让主机触发内置马达** | 主机发命令 | **墙，无门** | — | ✗ 不可行 |
| **2. 改触控板固件** | 加那条 `if` | **通**（知道改哪、改什么） | **赌上唯一指点设备** | ✗ 不该走 |
| **3. 外置马达 + 手势软件** | 自己加一个振动源 | **通** | ¥40–65，零风险 | ⚠️ **已降级**（见下） |
| **4. 拆机在 `HDP`/`HDN` 外挂震动旁路** | 接原装 LRA 的两根驱动线 | **通** | 一次拆底盖 + 飞两根线 | ✓ **唯一确定可行** |

> **★ 2026-09-14 晚 修订（两处，都很关键）**
>
> **① 第 3 条降级**：它只能把马达装在**掌托/底盖**里，隔着模组外壳 —— 手指感受到的是"笔记本在抖"，不是"触控板在弹"。
> 而用户的真实需求是「**触控板本体震 + 连贯**」⇒ **路 3 满足不了，不再是推荐项。**
>
> **② 第 4 条从"不划算"改为"唯一可行"**：原文判它"以月计的硬件逆向"，理由是"内部总线毫无资料"。
> **现在这个前提被实物和实测推翻了**：
> - **背面照片实证**：模组内 **`HDP` / `HDN` 两个焊盘裸露**，就是原装 LRA 的两根驱动线，**且从金属支架开口朝机内露出 ⇒ 拆底盖即可触及，不必拆开模组本体**（拆底盖是标准无损操作）
> - **不需要懂任何协议**：直接驱动一个线圈就行；而 LRA 参数已逆出（**振幅 119 / 周期 999 / 1999**）
> - 所以它的代价从"逆向一条未知总线"降到"**飞两根线 + 一个防驱动争抢的切换电路**"
> - 风险是**中等且可控**（不是零）：要解决①与原装 TF100A 驱动互斥（否则可能烧驱动）②引线不得妨碍触控板形变
> - **对冲**：所有试错先在**台面样机（¥100）**上做完，真机只做一次已验证的操作

> **关于原来那条"拆机嗅探总线"**（社区里最容易被提出来的）：嗅探改变不了什么 —— 它回答的是"**主机发了什么**"，而这个问题**看描述符就有答案**（`Col02 out=0`）；固件的决策逻辑在**芯片内部**，总线看不到。
> **但"拆机"本身不是错** —— 错的是"拆机去嗅探"，对的是"**拆机去接那两根已经暴露出来的驱动线**"。**目标不同，价值天差地别。**

### 路 2 为什么"技术上通、但绝不能走"

**刷写被三道锁把着：**

1. 官方刷机由 **BIOS 在启动时执行**，Windows 只负责把 `.BIN` 放进 `C:\Windows\Firmware`
2. Windows 只在"有**更新的、已签名的**包"时才安排刷写；已装版本 `0x14030522` **正好等于**设备当前版本 ⇒ **无待刷**
3. 自己造更新包？签名目录会失效 ⇒ **Windows 拒绝安装**

⇒ **刷不进去；就算刷得进去，也没有退路。**

**一次失败 = 永久变砖。而触控板是本机唯一的指点设备**（没有鼠标的话，你会连"点确定"都做不到）。

**而且路 2 和路 3 的收益完全相同**（都能给你滑动震动）——一条要赌上唯一的指点设备，另一条只要几十块钱。

### 路 3 具体要什么

- **一个自己的振动源**：LRA / ERM 马达 / ESP32 + 驱动板
  （社区里那位做触觉触控板的，用的就是 **ESP32 + Cirrus Logic CS40L25 驱动板**，**绕开笔记本主机**）
- **软件识别"滑动"**：触控板照常上报坐标，从 raw 报文里识别滑动即可（本项目已有可用的探针工具）
- 完全不碰触控板 ⇒ **风险为零**

## 6. 常见追问

**Q：那我写程序让它震一下，总可以吧？**
不行。能写的只有 `rid=9`（强度），那是个**参数**，不是**动作**。

> **2026-09-13 实测（测试 A）**：连写 6 个不同值，写入**确实到达设备**（点击反馈力度随之改变 = 阳性对照），**但没有一次产生震动**。⇒ 这条最后的缝，实测阴性。

**Q：为什么我的设置里没有"触觉反馈"？**
**因为这块板子的描述符是坏的。**

`rid=9` 声明出来的逻辑范围是 `[100, 1]`——**上下限颠倒**（实测解析见 `poc/hid-dump.txt:38`）。原厂把该写 `25`（Logical Maximum）的字节写成了 `15`（Logical Minimum）。Linux 社区必须打补丁修**描述符第 607 字节**才能用（ty2 驱动）。Windows 很可能就因为这个不摆这个控件。

> **独立旁证（2026-09-13 检索到）**：Arch Linux 论坛有**同型号**用户（`acpi:GXTP5100` / `27C6:01E9`）报告 `hid-multitouch` 探测失败，内核返回 **`error -22`**（`-EINVAL`）——这正是"**描述符非法 ⇒ HID 解析器直接拒绝**"的典型症状，与上述字节 607 判断高度吻合（非确证，但来自**另一个操作系统、另一个人**）。<https://bbs.archlinux.org/viewtopic.php?id=292878>
>
> 要证实得改描述符才能验证——那正是"路 2"里不该走的那件事。所以这条只能停在"很可能"。

**Q：那别的机器上能调"触觉反馈"的，是不是就能震？**
不是。那是调**强度**（旋钮），不是触发。Windows 的 `TOUCHPAD_PARAMETERS.FeedbackIntensity` 对应的就是 `rid=9`。

**Q：为什么"点击力度 Low/Medium/High"调不了？**
因为那对应 **Button Press Threshold feature 报表（`0x0D/0xB0`）**，**本机描述符里没有这个报表** ⇒ 该功能在本机不存在（所以 Windows 设置里也不会出现）。

**Q：别的牌子的笔记本可以啊？**
对，所以这不是"不可能"，是**这块板子没做**。买之前要确认该机型的触控板声明了 `Manual Trigger`。

**Q：厂商能不能通过更新加回来？**
理论可以。但需要 OEM（联想/汇顶）推一个新固件，**我们无法自助**。

**Q：那我到底还能不能有滑动震动？**
能——**外置马达 + 手势软件**，¥40–65，零风险，今天就能开始。

## 7. 想自己验证的话

| 想验证 | 怎么看 | 风险 |
|---|---|---|
| `Col02` 真的没有输出报表 | 设备管理器 → HID 设备 → 描述符；或任意 HID 描述符查看器，找 `Col02` 的 OUTPUT 项 | 零 |
| page 0x0E 下只有 Intensity | 同上，搜 `05 0E`（Usage Page Haptics） | 零 |
| 点击反馈是不是 LRA 模拟的 | 见 §2 末尾的体感验证 | 零 |
| 强度可调 | 写 `rid=9`（**写前先读回原值备份**） | 低 |

⚠️ **不要**去"枚举/批量试探"厂商命令（`Col04`）。本项目实测：某些 opcode 会**打断应答通道**，而该卡态**会继续恶化成触控板彻底失效**；那一次的恢复手段是**关机 + 拔充电器 + 长按电源键 20–30 秒 + 等 1 分钟 + 开机**。详见 [`HANDOVER.md`](../01-overview/lab__HANDOVER.md) 的操作红线。

> **2026-09-14 重要增补（两种严重度）**：当天又发生**两次**触控板输入冻结（指针不动、**点按仍有震动**），诱因**不是** opcode 枚举，而是**高频读取**（`Col04` 类 0x20 读 683 次、持续 50–75 秒）。这两次**都在 1–2 分钟内自愈**（未断电、未 EC 复位），与上面那种"**只有彻底断电可清**"的永久性 latch **不同源**。
> ⇒ **新的处置顺序**：**① 先杀掉所有后台任务（关句柄/取消挂起 IRP）→ ② 等 1–2 分钟** → ③ 无效再做完整的断电 EC 复位。
> 剂量红线：类 0x20 读 **单轮 ≤80 次、≤3 次/秒、轮间 ≥3 分钟**（实测 90 次 @≤10/s 安全；683 次 @9–13/s 三次中两次触发冻结）。
> 详见 [`INCIDENT-2026-09-14-input-freeze.md`](../09-safety/lab__INCIDENT-2026-09-14-input-freeze.md)。

## 8. 2026-09-14 增补（两条新结论，均不改变本文判断）

| # | 结论 | 证据 |
|---|---|---|
| **N2** | **震动不由 EC 控制** —— 系统里触控板只有 `ACPI\GXTP5100` **一个**设备节点（`PNP0C50` I2C-HID、服务 `hidi2c`），**没有**任何独立的触觉/振动设备，也没有 EC 侧的触觉设备；而模块固件里有**自己的** `TIM3(PWM) → GPIOA → LRA` 驱动链 ⇒ **震动是模组内部闭环**（这也解释了 BIOS 里点按也震、Windows 全程不参与） | `HKLM\SYSTEM\CurrentControlSet\Enum\ACPI` 枚举 + 明文固件反汇编 |
| **N1** | **BIOS 里没有 Goodix 专用代码** ⇒「从 BIOS 里取那个解析固件容器的 DXE 驱动」**是死路** —— `NJCN67WW_FWUpdate.bin`（4.34 MB，Intel FPT 20 分区）全镜像 **0 个** `Goodix/GXTP/TB14P/7868`、**0 个**固件 GUID（4 种编码全试）；Insyde 组件**未压缩**（`pgrm.met` 开头就是明文 `endbr32`），所以"解压"这一步也不存在 | 本次实测（`MASTER-CONSOLIDATION.md` §3.3 / §7.0 N1） |

> 以及 **Goodix 原厂署名的开源实现** `fwupd/plugins/goodix-tp/`（GTX8/NORMANDYL 与 BERLINB 两族协议、命令族常量）。
