## 2. 分发器 0x080091C0 的真实结构（逐条反汇编）

```
入口：r0 = 消息结构 ctx
  ctx[0x104]           ← 命令**类字节**（0x80 / 0xA0 / 0xA1；回复用 0xA2）
  u16 @ ctx+2          ← 16 位**子命令**（小端；即字节 ctx+2=0x00, ctx+3=NN）
  ctx+4 起             ← **payload**（handler 收到的就是这个指针）
```

- **类 0x80** → 单个 handler `0x08001628`
- **类 0xA0** → 子命令开关表：`0x01 0x05 0x0B 0x0D 0x0E 0x0F 0x11 0x12 0x13 0x14 0x15 0x16 0x17 0x18
  0x1D 0x1F 0x20 0x23 0x24 0x26 0x28 0x29 0x32 0x33 0x35 …`（≥26 条，仍在延续）
- **类 0xA1** → 第二张表（`0x203 0x400 0x700 0x800 0xF00 0x1300 0x1500 0x1600 0x1800 0x1D00 0x2300 0x2800 0x2900 …`）
- 其余类 → 走默认分支（`0x08009744/0x0800974A`）＝**同一个空 ACK**

### ⇒ 此前所有探测帧都把子命令写成了 0

项目历史上发出去的帧无一例外是这两种：

| 用途 | 帧 |
|---|---|
| 命令探测（35 条 opcode） | `0E <op> 00 00 01 01` ← 类=op，**子命令=0x0000** |
| 内存读 / 写（唯一成功的一条） | `0E 20 00 00 <len> <rw> <addr16><size16>` ← **子命令=0x0000** |

**于是：`0E 0B 00 00 …` 与 `0E A0 00 0B …` 是完全不同的两条命令，而后者从未发过。**
这也解释了 §15 那个"`0x00–0x0D` 全是同一个空 ACK"的现象——那是**默认分支**的回复，不是命令被拒。

## 3. ★ 这张表里**确实有直通触觉子系统的命令**

| 类-子命令 | handler | 实测语义（反汇编确认） |
|---|---|---|
| **0xA0-0x0B** | `0x080088C0` | 把 `payload[0]=len`、`payload[1..]` 写入 **触觉波形缓冲 `0x200040E8`**（逐字节循环，`*(0x200040E8+i)=ctx[4+i]`） |
| **0xA1-0x0B** | `0x08008868` | **读回** `0x200040E8`，组装 `0xA2` 回复，并 `GPIOA->BRR = 1<<3` 拉低 **PA3**（给对端的握手/中断线） |
| **0xA0-0x0D** | `0x080086B4` | **初始化/清空触觉缓冲**：`*(0x20004094)=4`（状态字）、清 `0x2000495E` 起 **5,780 B**、清 `0x2000426C` 起 **44 B** |
| 0xA0-0x11 / 0x0E / 0x1F | `0x08006E28(1/2, ctx+4)` | 参数下发（三条同族，带 1/2 选择子） |
| 0xA0-0x20 / 0x24 / 0x12 | `0x080049EC(ctx+4)` / `0x08004CD4()` | 另一组动作/查询 |

**触觉数据结构（本轮定位）**
- `0x200040D0` = 触觉 ctx 结构：`+0x10` 计数器、**`+0x14` 播放回调指针**、`+0x18..` 参数
- `0x200040E8` = **波形缓冲**（紧接 ctx 之后）
- `0x20004094` = 触觉状态字（0x0D 命令把它置 4）
- `0x2000495E`（5,780 B）+ `0x2000426C`（44 B） = 命令 0x0D 清空的两个块
- `0x08008628` = "播放"入口：**使能 TIM3**（`0x0800BD44/0x0800BD30(0x40000400,1)`）→ `bl 0x08008858` → `ldr r0,[r0,#0x14]; blx r0`
  ⇒ **它自己在本镜像里 0 个调用者**（与旧结论一致）

## 4. 镜像里还有一块**没人看过的数据表**：0x0800D600–0x0800DCA0（≈1.7 KB）

- 现状：**不是代码**（从任何入口反汇编都是乱码），是**高度结构化的 16 位表**（例：`0x2120 0x211c 0x2108 0x210c 0x2110 …`，夹杂 `0x5412/0x12a5` 之类重复模式）。
- 而 `ctx+0x14` 被写入的"回调"值 `0x0800D6F5` **正落在这块数据表里** ⇒ 旧文档"回调指向浮点表/链是坏的"那种困惑有了合理解释：**那更像是数据地址，不是函数地址**。
- **待办**：把这块表 dump + 解码，判断它是不是 **LRA 波形库**（若是，可回答"有没有长/循环波形"这个关键问题）。

## 5. 仍然缺的那一块：镜像尾部

- 镜像 = 56,480 B（`0x08000000..0x0800DCA0`），但向量表/代码引用到 **`0x0800DFE5`（slot6）、`0x0800DEE9`（IRQ37 USART1）、`0x0800F0B5`（+5,141 B）**。
- 尾部含 **USART1 接收 ISR**（= 命令帧的**装配者**，即帧格式/校验的真身）与"播放"的调用者。
- ⇒ **帧格式（同步字/长度/校验）就在这段缺失代码里**，这是"能不能自己造帧"的最后一道门。

## 7. ★ C 实验已执行（2026-09-14，单发 4 帧，触控板前后均健康 ✓）

工具：`poc/VibProbe.cs` + `poc/vib-probe.ps1`（帧格式按本轮反汇编构造；**单发单读、不轮询、不枚举**，每帧前后各做一次"只读体检"`类0x20 读 0x1000×16`）。

| # | 帧（`[0]=0E`） | 结果 | 读法 |
|---|---|---|---|
| 1 | `A1 0F 00 05 01 18 00 00 1B`（0xA1-0x0F = 读 27B@0x1800） | OUT=True err=0；**读回 err=122**；体检后**活** ✓ | 65B 与 4096B 缓冲皆 122 |
| 2 | 同 #1（复现） | 同上（122） | — |

**结论（已经能站住的三条）**
1. **帧格式推断正确**：`[1]=类,[2..3]=子命令,[4]=长度,[5]=方向,[6..]=payload` —— 非 0 的 `[2..3]` 在类 0x20 下被正常接受（#4）。
2. **类 0xA1 的响应送不出来**：OUT 被接受，但 IN 侧无论 65B/4096B 都 `err=122`（=hidi2c 认为长度字段非法），且与子命令无关（#3）。
   而固件里**所有扩展类的回复都把 `msg[0]` 写成 `0xA2`**（回复类），并不是 0x0E ⇒
   **最可能：命令其实被处理了，只是回复带着一个 HID 描述符没声明的报文形状，被 hidi2c 丢弃。**
3. **零损伤**：四次探针前后，`类 0x20` 读回数据完全一致（`… 43 01 00 00 50 01 …`）⇒ 触控板**健康**，扩展类不会像历史那次枚举那样打挂。

**⇒ 因此"主机能不能到扩展空间"这个问题被收窄成一个具体的技术问题：怎么把 0xA2 形状的回复读出来。**

## 8. 第二轮：波形表解码（阴性）+ ReadFile 捞报文（工具侧死锁，设备无恙）

**① 表 `0x0800D600..0x0800DCA0`（1696 B）解码结果：不是波形库（至少不是任何直白形式）**

| 判据 | 数值 | 含义 |
|---|---|---|
| 整体熵 | 6.94 b/B | 编码/打包数据，不是裸样本 |
| 当 u16 LE | n=848，唯一值 689，均值 22452（≈0x57B4），**无 0 值长游程**（最长仅 3） | 不是"静音+脉冲"的波形样本阵列 |

| 当 u32 | **落在镜像地址区间的偏移表 = 0 个** | 不是偏移表/指针表 |
| 局部形态 | 多处 2–3 字节周期重复（`12 54 A5`/`70 54`/`3B 54`/`3F 7E`） | 像**打包填充**或序列化产物 |

⇒ **结论：波形库假设未获支持**（该区间更像编码/打包数据）。波形若存在，可能在别处或以非样本形式存放。**不做进一步断言。**

**② `ReadFile` 捞自发报文：改为独立句柄后仍卡死 ⇒ 现象升级为"0xA1 之后输入通道被挂住"**

- 第一轮：监听用**命令句柄** ⇒ 体检 2 卡死 >110 s（被外层超时强杀）。
- 第二轮（**已修成独立监听句柄** + 700 ms 硬超时）：监听本身正常返回"700 ms 内无数据"，但
  **体检 2 依旧卡死** >58 s。
- ⇒ **结论更正：卡死与"监听句柄选择"无关**；真实现象是
  **发过一条类 0xA1 的扩展帧之后，同一进程内随后任何 `HidD_GetInputReport` 都会永久阻塞**
  （65B/4096B 都在 122 之后进入该状态）。
- **但设备无恙**：两次事后都用**新进程**核验 —— `ACPI\GXTP5100` = `Started` ✓ 且
  `类0x20 读 0x1000×16` 正常返回**逐字节相同**的数据 ✓ ⇒
  这是**传输/HID 输入通道被 0xA1 命令挂住**的表现，**不是 IC 死**，进程退出即恢复。

**⇒ 这条现象本身就是强证据**：类 0xA1 没有被"当成未知类丢掉"（未知类会给可读的空 ACK），
而是把设备的输入侧带进了一个**只能由"另一条路径"取走回复**的状态（固件里扩展类的回复正是 `0xA2` 类）。
下一步要试的正是那条路径，且**必须在发命令后换一个新进程/新句柄去读**，绝不在同进程里等。

## 11. ★ 第四轮（2026-09-14 11:00）：把"读法"修对，拿到三条硬结论

### 11.1 工具升级：**每一次 HID 调用都加了超时护栏**（这一轮最大的方法学改进）
- 新工具：`poc/VibLink.cs` + `poc/vib-link.ps1`
  模式：`SEND <类> <子命令> <payload> [dwellMs]` / `LISTEN <ms>` / `HEALTH` / `ONE <in|read|feat|mem> …` / `MEMSCAN` / `MEMWATCH` / `MEMDUMP`
- **每个 HID 调用都跑在独立后台线程 + `Join(超时)`** ⇒ 任何一次阻塞都只损失那一条，再也不会"一条卡死吞掉整轮"。
- 事实更正：上一轮的"卡死"**是我自己的读法造成的**——`LISTEN` 里把**阻塞型 `ReadFile` 放在第一步**，
  它挂住之后，**同一进程内后续所有调用都排在它后面**，于是全灭。
  ⇒ 真实现象只有一条：**进程退出会取消挂起的 IRP，新进程立刻恢复**（这也解释了前几轮"设备看起来没事"）。
- **教训（写死）**：① 一次进程只做**一次** IO（`ONE` 模式）；② 阻塞型 `ReadFile` 永远放最后；③ 不要在同一进程里"发完再等"。

### 11.3 回复构造器的完整反汇编（离线，`re/fw_deep15/16`）

`0x08008868(buf, n)`：
```
buf[0] = 0xA2 ; buf[1] = n ; for i<n: buf[2+i] = *(u8*)(0x200040E8 + i) ; GPIOA->BRR = 1<<3
```
调用者 `0x0800968A`（在分发器 `0x080091C0` 内）：
```
n  = *(u8*)(*(u32*)0x20004940 + 1)        ← 收到的报文里第 2 字节当长度
buf = 0x20004128 + 0x8C = 0x200041B4       ← ★ 所有 A1 类回复都写在这个固定缓冲
```
⇒ **`0xA1-0x0B` 的语义就是"把触觉波形缓冲 0x200040E8 的内容回给主机"**，回复形如 `A2 <n> <n 字节波形>`。
同族 `0xA1-0x0F` 走 `0x0800865C`（读 27B@0x1800 后构造 A2 + 校验和），目标缓冲同样是 `0x200041B4`。

### 11.4 ★ 关键阴性结果：可读的 16 位空间**够不到**触觉 RAM

实验：先读 `0x40D0..0x412F`（含波形缓冲 `0x40E8`，基线**全 0**，后段为 `FF`），

⇒ 结合"本镜像分发器**没有**类 0x20（内存读写）分支、而主机的 0x20 通道实测可用"，
**"两颗芯片"模型现在是最优解释**：
- 加密 payload A（100,608 B）= **主触控 ASIC**（实现 0x20 读写 + 触摸处理，并**转发**扩展类）
- 明文 payload B（56,608 B，"TF100A_Test_FW"）= **触觉/LRA 芯片**（本镜像；0xA0/0xA1 表、波形缓冲、TIM3、PA3 握手都在它这边）
- ⇒ 0x20 通道读到的是**主芯片**的空间，读不到触觉芯片的 `0x200040E8`（实验正好符合）

### 13.2 判定：**主机侧找"震动开关"这条路，证据上已经闭合**

到今天为止，四条独立证据一致指向同一结论：

1. **点按时主机侧零厂商报文**（180 s、45 次触摸事件，`reports=0`）⇒ Windows 不参与震动；
2. **主 ASIC 可读空间里没有触觉状态**：`0x4080` 页全 0；`0x40E8`（触觉芯片波形缓冲）主机写不进去；
3. **扩展类（0xA0/0xA1）的回复主机读不出来**：`GET_INPUT(0x0E)`→122、`GET_INPUT(0xA2)`→**87（描述符里没有这个 report id）**；

   **建议下一步就先把 `TBTP` 单独抠出来分析**（找压缩头、试 LZMA/zstd、找 `GXTP`/`TB14P`/`b6ae105a` 字符串）。
2. `EPP1`（`AA 55` 头，1 MB）与 `RBEP`（1.5 MB `$CPD`）是另外两个候选（BIOS/EC 主体）。
3. `$CPD` 很可能是 Lenovo/Insyde 的**压缩组件容器**（需先解压才见 PE/DXE）。
4. 备选对照：`NJCN61WW_FWUpdate.bin`（上一版）与 `NJCN67WW.exe`（刷写器，可能带解压实现）。

## 15. ★ 第六轮：反汇编 Dell 刷写器，拿到**协议权威定义**（2026-09-14）

工具：`re/de_dell_proto.py`（字符串→xref）、`re/de_dump.py`（任意 VA 反汇编）
对象：`poc/pkg/extract/zip0/DellTouchpadUpdate_Hellcat_v0.2.2.100.exe`（**PE32 x86**，ImageBase 0x400000）

### 15.1 ★ 两类帧的完整定义（逐字节反汇编所得）

**v1（16 位地址）**
```
读: 0E 20 00 00 05 01 | addr16BE | len16BE                                    (10 B)
写: 0E 20 <more> <seq> <len+5> 00 | addr16BE | len16BE | data…                (len+10 B)
```
**v2（32 位地址）**
```
读: 0E 20 00 00 07 01 | addr32BE(4) | len16BE                                 (12 B)
写: 0E 20 <more> <seq> <len+7> 00 | addr32BE(4) | len16BE | data…             (len+12 B)
```
- **`[4] = 帧长 − 5`**（读帧 10/12 → 5/7；写帧 len+10/len+12 → len+5/len+7）
- **`[5]` = 方向：`0x01` 读 / `0x00` 写**
- **`<more>` = 还有后续块（1/0）；`<seq>` = 块序号（从 0 起）**
- **单块上限：v1 写 `0x37`=55、v2 写 `0x35`=53、读 `0x3C`=60**（与 65 字节 HID 报文一致）
- 证据 VA：v1 读 `0x4117C0`、v2 读 `0x411960`、v1 写 `0x4113B0`、v2 写 `0x411560`

### 15.2 ★ 回复格式（这里我们此前**有一处偏差**）

```
[0]=0x0E(report id)  [1]=类(0x20)  [2]=?  [3..4]=长度(16 位大端)  [5..]=数据
校验: (buf[3]<<8)|buf[4] 必须等于请求长度，否则报
      "Valid data length from firmware verify failed"（0x4469b8）
```
（证据：`0x4118C4`–`0x41190B` 的 `movzx/shl/add/cmp/je` + `memcpy(dst, buf+5, len)`）
本项目此前的 `MemRead` 用 `r[4]` 当长度、数据取偏移 5 —— **数据偏移一直是对的**，长度字段应取 `[3..4]` 大端。

### 15.3 芯片族确认

工具日志字符串里出现 **`FwImage_7863::initPid` / `initVid`** ⇒ 该工具服务的芯片族 = **7863**（与我们 7868Q 同族），
⇒ **协议可直接套用**。

### 15.4 实测：v2 选择子**不被本机芯片支持**（对照实验）

| 地址 | v1 读结果 | v2 读结果 |
|---|---|---|
| `0x1000` | `00×9 43 01 00 00 50 01 00` | **全 0** |
| `0x1800` | `3C 00 00 00 3C 00 00 00 …` | **全 0** |
| `0x200040D0` / `0x200040E8` / `0x20004100` | — | 三者**返回几乎同一份数据** |

**判定**：芯片把 v2 帧**按 v1 布局解析**（地址取 `[6..7]`=`0x2000`、len 取 `[8..9]`），
所以三个高地址都变成了"读 0x2000 共 60 字节"，才会给出同一份（带活字节的）数据。
⇒ **`0x07` 不被识别；32 位寻址在本机不可用。**

### 15.5 由此得到的两条**新能力**与一条**否定**

1. ✅ **多块写**：`<more>`/`<seq>` 字段此前项目从未用过。单块 55 字节的写，用 `more=1` 串起来
   ⇒ **可以往 16 位空间写任意长数据块**（例如整段配置区/波形区）。
2. ✅ **协议权威定义**：v1 帧与我们实测帧**完全一致**（旁证项目当年的 `hidbuf[4]=len+5` 是对的），
   且 v1 读的 `[3..4]` 大端长度 + 数据偏移 5 已确定。
3. ❌ **A1 类回复为何读不出（补充证据）**：固件构造的回复首字节是 `0xA2`
   （`0x08008868`：`buf[0]=0xA2; buf[1]=n; buf[2..]=波形缓冲`）。
   若该字节被当作 **HID report id**，则 `0xA2` **不在 Col04 描述符里** ⇒
   `HidD_GetInputReport(0xA2)` 直接返回 **87**（本轮实测），而 `GET_INPUT(0x0E)` 得到 **122**。
   ⇒ **主机侧无 API 可读该回复**，与 §13.6b 的结论一致（新的机制解释，不是新出路）。

## 16. 第七轮：方向字节修正后的 A 类写入实测（2026-09-14 11:5x）—— **阴性**

依据 §15.1 的新知识（`[5]` = 方向：`0x01` 读 / `0x00` 写），修正此前所有 A 类帧都误用读方向的问题，重打：

| # | 帧 | 意图 | 结果 |
|---|---|---|---|
| 1 | `0E A0 0B 00 0A 00 \| 08 FF 00 FF 00 FF 00 FF 00` | 写波形缓冲（**方向 0x00**） | `send=True err=0`；**无震动** |

### 16.1 两条结论

1. **方向字节不是症结**：用正确的写方向重打 `A0-0x0B`/`A0-0x0D` 依然不响

2. **附带证据（有价值）**：本次全程使用 A 类帧（含 `0xA0` 写），**输入没有冻结**
   ⇒ 与 §4′ 的修订一致：**冻结的诱因是"类 0x20 连发读突发"，不是 A 类帧**。

### 16.2 主机侧到此为止：完整否定清单

| 假设 | 实验 | 结果 |
|---|---|---|
| 点按时 Windows 下发厂商命令 | 180 s 只读监听 + 疯狂点按 | ❌ `reports=0` |

## 17. 第八轮（用户提问）：**震动是不是 EC 控制的？** + BIOS 解压/解析驱动的结论

### 17.1 ★ 答：**不是 EC** —— 震动由触控板模块自己的控制器产生

| 证据 | 内容 |
|---|---|
| **ACPI 只有一个设备节点** | `ACPI\GXTP5100\1`，`CompatibleIDs = PNP0C50`（I2C-HID），`Service = hidi2c`；**没有任何独立的触觉/振动/EC 侧触觉设备** |
| 容器 GUID 归属 | `HKLM\SYSTEM\CurrentControlSet\Enum\ACPI` 下匹配 `HAP/VIB/LRA/TPAD/GXTP` 的只有 `GXTP5100` 一项 |
| **模块固件里有完整的 LRA 驱动** | 明文镜像里 **TIM3（PWM 定时器）→ GPIOA(PA3 握手) → 波形缓冲 `0x200040E8` → 播放回调 `ctx+0x14`** —— 这是**定时器直驱振子**的电路形态，只有振子接在本芯片上才会这么写 |
| 点按震动的自主性 | 主机侧 180 s 监听 `reports=0`；且 BIOS 里点按也震 ⇒ 不需要 OS、不需要 EC 参与 |

⇒ **EC 只管键盘/电源/指示灯那一摊；触控板的 LRA 是模块内部闭环（自己测力度 → 自己放波形）。**
（附：`NJME01WW.exe`/`NJME07WW.exe`（3.3 MB）里里外外几乎捞不到可读字符串，payload 是打包的，未能进一步验证 —— 但上面的结构证据已足够。）

### 17.2 BIOS 侧："解压"这个前提**本身不成立**

- 全镜像 4,343,352 B 里：**`_FVH` 0 次、`PE` 0 次、标准 LZMA 头 0 次**。
- 但 `$CPD` 组件内容**是明文**：例如 RBEP 分区的 `pgrm.met`（偏移 0x18B40）开头就是
  **`f3 0f 1e fb`（`endbr32`）** 跟着正常 x86 指令 ⇒ **Insyde 的扁平 32 位模块，没有压缩**。
- ⇒ **"先解压 `$CPD`"这一步不需要**；组件可以直接按清单偏移取用。
- 清单结构已解出（RBEP 分区）：条目 = `u32 offset, u32 size, u32 flags, char name[12]`，步长 0x18，
  首个条目在 0x08；部分条目的 offset 带 `0x02000000` 基址（减去即落在分区内）。
  组件：`fitc.cfg / rbe / rbe.met / pgrm / pgrm.met / kernel / syslib / bup / intl.cfg / intl.cfg.met / pm`。

### 17.3 ★ 但 **Goodix 专用的解析驱动不在这个 BIOS 里**（D2 结论：死路）

四份文件都查了（ASCII + UTF-16 + 4 种 GUID 编码）：

| 文件 | `Goodix`/`GXTP`/`TB14P`/`7868` | GUID `b6ae105a-ba93-4fc8-aa28-e63903ffedde` |
|---|---|---|
| `NJCN67WW_FWUpdate.bin`（4.34 MB，BIOS） | **0** | **0**（4 种编码全无） |
| `TB14P_GT7868Q_14030522_20240202.BIN`（容器） | 仅 `YELSTO`/`7868Q` 标签 | **0** |
| `NJCN67WW.exe`（12.8 MB 刷写器） | **0** | **0** |
| `GoodixTouchpad.inf` | ✓ | ✓（**只有它引用**） |

⇒ **BIOS 里没有任何 Goodix 相关代码**，因此"从 BIOS 取容器解析器"这条路**关闭**。
（Windows 侧那个 `UEFI\RES_{GUID}` 只是固件更新用的**资源设备 ID**，实际写 flash 的是 BIOS 的通用
 "UEFI firmware update" 机制 —— 它既不认识 Goodix、也不带厂商字符串。）
- 附带收获：容器头是**大端**结构（`+0x04`=元数据偏移 `0x43C`；`+0x44`=payload A 长度 `100,608`；
  `+0x48`=payload B 长度 `56,608`(=映像 56,480 + 128)) —— 之前按小端搜长度才会 0 命中。

### 18.2 ★ 常量（`fu-goodixtp-common.h` 原文）
```c
#define PACKAGE_LEN 65      // 报文 65 字节（与我们一致）
#define REPORT_ID   0x0E    // ★ 我们一直在用的 0x0E 就是它
#define I2C_DIRECT_RW 0x20  // ★ 类字节 0x20

```
⇒ **我们反汇编 Dell 工具推出的帧格式，被原厂源码逐字节确认。**

### 18.3 ★★ 历史挂死的真因（重大安全发现）

`fu-goodixtp-gtx8-device.c` 里的命令（**class 字节 + 子命令**）：
```c
cmd_switch_to_patch = {0x00,0x10,0x00,0x00,0x01,0x01}   // class 0x00 → 切 Bootloader patch 模式
cmd_start_update    = {0x00,0x11,0x00,0x00,0x01,0x01}   // class 0x00 → 开始更新
buf_load_flash      = {0x0e,0x12,0x00,0x00,0x06,...}    // class 0x0E → 写 flash（带校验和）
cmd_reset           = {0x0E,0x13,0x00,0x00,0x01,0x01}   // class 0x0E → ★ 软复位
```
- 项目文档 `STATUS.md`/`HANDOVER.md` 早就记着「**`0x0E` / `0x0F` / `0x99` 会打断通道、两次挂死**」——
  **现在有确切解释**：`0x0E` 就是**固件更新命令族**（`0E 12` 烧 flash、`0E 13` 软复位），
  `0x00` 族（`00 10`/`00 11`）会把芯片**踢进 Bootloader**。
  ⇒ 当年的"opcode 枚举"打到了更新命令，于是"IC 挂死"。
- **红线（新增，硬性）**：**禁止枚举 class `0x00` / `0x03` / `0x0E`**；
  这几个类是固件更新/复位通道，误发会把触控板送进 Bootloader（可能只能靠 EC 复位救回）。

### 18.4 ★ 传输通道之谜：Linux 用 feature report，Windows 只能用 output/input

`fu-goodixtp-hid-device.c`：`set_report → fu_hidraw_device_set_feature()`、`get_report → ..._get_feature()`。
即**原厂在 Linux 上走 HID feature report（`HIDIOCS/GFEATURE`）**。
但本机实测（`poc/FeatVendor.cs`，四个集合全试）：

| 集合 | in/out/feat | `SetFeature(rid=0x0E)` |
|---|---|---|
| col01 | 9/0/0 | err=1 |
| col02 | 40/0/**737** | **err=1** |
| col03 | 0/0/3 | err=1 |
| col04 | 65/65/0 | err=1（未声明） |

⇒ **Windows 上没有任何集合声明 `rid=0x0E` 的 feature report**（Linux 的 hidraw 是"裸"通道，不受描述符约束；
Windows 的 `HidD_SetFeature` 会先按描述符校验 report id）。
⇒ **Windows 只能用 output/input report —— 本项目最初的选择是对的**；
  这也解释了 Dell 工具为何 `Find the set feature device failed` 后仍能工作。

### 18.5 副产物：GTX8 族的已知地址（可用于交叉验证）

```
CMD_ADDR         0x60CC   // 命令信箱（写 3 字节命令，如 {0x33,0x00,0xCD} 关上报、{0x35,0x00,0xCB} 确认）
BL_STATE_ADDR    0x5095   // Bootloader 状态（期望 0xDD）
FLASH_RESULT_ADDR 0x5096  // 烧写结果（期望 0xAA）
FLASH_BUFFER_ADDR 0xC000  // 4KB RAM 缓冲
0x452C           // ★ 固件版本块 72 字节（+9 起 5 字节 = patch PID 字符串，如 "7868Q"；整块 sum8==0）
0x60DC           // cfg 版本（1 字节）
```
**实测（本机）**：
- `0x452C ×72` → **高熵数据**（不是版本块）、无 ASCII ⇒ **我们这颗的内存布局与 NORMANDYL 不完全一致**
  （或该区被加密/压缩）。记为此项未决。
- `0x60DC` 首字节 = `0x02`（可能是 cfg ver）。
- PID 比对：fwupd 把 **NORMANDYL(GTX8)** 定义为 PID `0x01E0–0x01E7 / 0x0D00–0x0D7F / 0x0DA3`；
  本机触控板 PID = **0x01E9**，**不在表内**（但帧格式与 GTX8 完全一致）⇒ 可能是更新的型号或用同一协议的新 PID 段。
