## 1. 设备 flash 映射图（IC 内部 flash 地址空间）

**格式**：镜像头 256 B + 13 个子固件按表序紧凑平铺（**文件内顺序 ≠ flash 地址顺序**，见 §1.2）。
**地址空间**：`0x000000–0x020000`（128 KB）；**本镜像覆盖到 `0x01FFFF`，但 `0x00E000–0x00FF00` 为空隙**。

### 1.1 映射表（按 flash 地址排序）

| Start | End | Size | Contents |
|---|---|---|---|
| `0x000000` | `0x001000` | 4,096 B | 子固件 idx9 · type `0x02` |
| `0x001000` | `0x004000` | 12,288 B | 子固件 idx8 · type `0x02` |
| `0x004000` | `0x006000` | 8,192 B | 子固件 idx10 · type `0x03` |
| `0x006000` | `0x008000` | 8,192 B | 子固件 idx2 · type `0x03` |
| `0x008000` | `0x00A000` | 8,192 B | 子固件 idx3 · type `0x03` |
| `0x00A000` | `0x00C000` | 8,192 B | 子固件 idx4 · type `0x03` · ⚠️ **此块解扰后 74.16% 全零**（§19.3） |
| `0x00C000` | `0x00E000` | 8,192 B | 子固件 idx5 · type `0x03` |
| `0x00E000` | `0x00FF00` | — | **erased / 未覆盖**（本镜像不含） |
| `0x00FF00` | `0x010700` | 2,048 B | ★ 子固件 idx0 · **type `0x01`**（唯一的 `0x01`；位置形似参数区） |
| `0x010000` | `0x012000` | 8,192 B | 子固件 idx7 · type `0x03`（**与 idx0 在 `0x00FF00–0x010700` 有重叠**，见 §1.3） |
| `0x012000` | `0x013000` | 4,096 B | 子固件 idx12 · type `0x02` |
| `0x013000` | `0x016000` | 12,288 B | 子固件 idx11 · type `0x02` |
| `0x016000` | `0x018000` | 8,192 B | 子固件 idx1 · type `0x03` |
| `0x018000` | `0x01E000` | — | **erased / 未覆盖** |
| `0x01E000` | `0x020000` | 8,192 B | 子固件 idx6 · type `0x03` |
| **`0x19000`** | — | 配置长度 | ★★ **`CFG_FLASH_ADDR` = 配置在 flash 的地址**（**运行期单独写入**，不随固件镜像下发） |
| 其余 | — | — | 未覆盖 |

> **★ 100% 对账（照抄 elgato 的验证法）**：13 个子固件合计 **100,352 B**；镜像头 **256 B** ⇒ `256 + 100352 = 100,608` = **载荷 A 全长**，**零剩余** ✅。
> 但**映射到 flash 地址后并不填满 128 KB**（有 `0x00E000–0x00FF00` 与 `0x018000–0x01E000` 两处空隙）⇒ **"零剩余"是文件级的，不是 flash 级的**。

### 1.2 `type` 的真语义（★ 不是"程序/配置"，是 update-flag 的位号）

官方 `if (!(firmware_flag & (0x01 << sub_fw_type))) continue;`（`gt7868q_update.cpp:213-222`）
—— **`type` 是位索引**，用来与 host 传入的 `firmware_flag` 做位与筛选。
`main.cpp` 注释：`firmware_flag = 0x0C; // update type:0x02,0x03` ⇒ 本机只下 `0x02` 与 `0x03` 两类。
`0x03` = 官方 `FLASH_SUBSYS_TYPE_CONFIG`（**注意：叫 CONFIG，但它是 flash 子系统的分类号，不等于"配置区"**）。
（出处：《全书》§19.3）

### 1.3 ⚠️ 两处需要留意的重叠/空隙

| 现象 | 说明 |
|---|---|
| `0x00FF00`(idx0, 2048 B) 与 `0x010000`(idx7, 8192 B) | 地址区间 **重叠** `0x010000–0x010700`。官方是**顺序平铺**（`fw_image_offset += sub_fw_len`），**不按 flash 地址排布** ⇒ 重叠说明这两块写入 flash 时**同一段被先后覆盖**。**语义未定**（🟡） |
| `0x00E000–0x00FF00`、`0x018000–0x01E000` | 本镜像**未覆盖** ⇒ 对应 flash 区在刷写后仍是**旧内容或擦除态** |

## 2. ★★ 容器族对照：**gtx3/GTX8 vs BRLB**（防再用错族）

> **为什么要有这一节**：本项目曾用 **"小端 32 位字和"** 去验证 gtx3 容器，失败后一度倾向认为"校验算法神秘"。
> **真相是：那个模型属于 BRLB 族，不属于 gtx3 族。** ⇒ 纪律 **124**。

| 维度 | **gtx3 / GTX8**（= 本机 GT7868Q） | **BRLB**（另一族） |
|---|---|---|
| 官方结构名 | `FuStructGoodixGtx8Hdr` / `Gtx8Img`（fwupd）· `gt7868q_firmware_image.h`（官方工具） | `FuStructGoodixBrlbHdr` / `BrlbImg`（fwupd） |
| **头大小** | **256**（`FW_HEADER_SIZE` / `GTX8_FW_DATA_OFFSET`=256） | **512**（`FW_HEADER_SIZE 512`） |
| **长度字段** | `u32` **大端** | `u32` **小端** |
| **校验和字段** | `u16` **大端** | `u32` **小端** |
| **校验和算法** | ★ **逐字节累加** `Σ bytes[6 : len+6] mod 2^16` | ★ **u16 小端字和**（步长 2） |
| 校验位置 | `Σ` 覆盖 `bytes[6 : firmwareSize+6]` | 覆盖数据区 |
| **子固件条目** | 8 B：`kind:u8` · `size:u32`**`be`** · `addr:u16`**`be`**`<<8` · `+1` | 8 B：`kind:u8` · `size:u32`**`le`** · `addr:u32`**`le`** · `+1` |
| **地址语义** | **16 位页地址**（再 `<<8` ⇒ 256 对齐） | **32 位地址** |
| IC 类型枚举 | ★ `FuGoodixtpIcType::**Yellowstone**`（= 本机；`IC_TYPE_YELLOWSTONE = 3`） | （另一分支） |
| 我们的实测 | `size=100,602` · `checksum=0x5F37` **逐字节通过** · `hw_pid=YELSTO` · `subsys_num=13` | — |

**★ 判别速查（拿到一份未知 Goodix 容器时先做这三步）**：
```
① 看头大小：能按 256 解析出合理字段 ⇒ gtx3/GTX8；若 512 才合理 ⇒ 可能是 BRLB
② 看长度字段：按 u32 BE 读出的值 + 6 == 文件长 ⇒ gtx3/GTX8；若 u32 LE 才对 ⇒ BRLB
③ 试校验和：逐字节累加比 u16 BE ⇒ gtx3/GTX8；u16 小端字和比 u32 LE ⇒ BRLB
   ★ 三个都做，别只做一个 —— 单一判据会误导（纪律 124）
```

**⚠️ 已在本项目踩过的坑**：
- ❌ 用"小端 32 位字和"去验 gtx3 ⇒ 失败 ⇒ **误以为"算法神秘"**（实为**选错族**）
- ❌ 从**文件偏移 0** 解析容器 ⇒ 得"PID 全 0 / 子固件数 0 / 校验和失配" ⇒ 宣布"不是这个格式"
  —— **假否定**：本容器是**三层**，容器起点在 `file 0x0113C`（《全书》§19.2.1）
- ⚠️ **`YELSTO` 是 gtx3/GTX8 的家族代号**（`YELLOWSTONE`）；`PNOR_G1` 是**另一族的 magic**（本机 `tpfw_86272_PNOR_G1_7863.bin`）⇒ **两者不可混用同一套解析**

## 5. ★★★ 2026-10-10 追补一：**地址重叠的语义已定**（原 §1.3 的 🟡 待定项）

**实测（离线，纯字节分析）**：

| 项 | 值 |
|---|---|
| 重叠区间 | `0x010000 – 0x010700`（**1,792 B**） |
| idx0（`0x00FF00`, 2048 B）在重叠区的文件偏移 | `0x00200` |
| idx7（`0x010000`, 8192 B）在重叠区的文件偏移 | `0x0C900` |
| **两段逐字节相同** | **11/1792 = 0.61%**（随机期望 0.39%）⇒ **不是同一份数据** |
| 解扰（XOR K 相位 316）后两段相同 | **13/1792 = 0.73%** ⇒ **仍不同** |

**★ 结论（按官方写入顺序推导）**：
官方在 `fw_update()` 里**按【表中顺序】逐块写入**（`for i = 0..sub_fw_num`），**不是按 flash 地址排序**：
```
表序 0  → 写 0x00FF00, 2048 B     覆盖 [0x00FF00, 0x010700)
表序 7  → 写 0x010000, 8192 B     覆盖 [0x010000, 0x012000)  ★ 会盖掉 idx0 的重叠部分
```
⇒ **最终 flash 里 `0x010000–0x010700` 的内容 = 【idx7 的】，不是 idx0 的。**
⇒ **idx0（`type 0x01`）实际只有前 256 B（`0x00FF00–0x010000`）会留在 flash 里** —— **正好一个 flash 页**。

**⇒ 推论（🟡 中置信）**：`type 0x01` 块的**有效载荷可能只有 256 B**；容器表里写的 2048 是"分配长度"，不是全部有效。
（`0x00FF00` 也正对应官方 `gt7868q.h` 里的 `0xFF00` 区，见《全书》§19.3。）

**★ 判别方法（可复用）**：遇"表中地址重叠"时，**不要按地址排序推断最终内容**，而要**按【官方写入顺序】**推断 ——
后写的覆盖先写的。本项目此前按地址排序，**推错了顺序**。

## 7. ★★ 2026-10-10 追补三：**实测通道能否触达 flash 地址**（供 B12 实验用）

**活体只读实测（`lab__r31_persist_probe.py --phase 0`）**：

| 地址 | 读出内容（前 32 B） | 判读 |
|---|---|---|
| `0x096F8`（`CFG_START_ADDR`，RAM 暂存） | `22 01 1B 00 3E 01 04 65 A7 C3 E1 02 B5 02 1F 14 71 48 93 20 22 04 01 20 01 13 88 0A 09 05 00 00` | ✓ 与项目记录的活体 cfg 一致 |
| **`0x19000`（`CFG_FLASH_ADDR`，flash）** | **`FF FB FF FE 00 04 00 00 FF FD FF FC FF FC FF FE 00 01 FF FF 00 06 FF FF 00 03 00 05 00 02 00 01`** | ★★★ **可读，且呈结构化模式** |

**⇒ ★★★ 重要结论：本项目的 Col04 读通道能够触达【flash 地址空间】**（不只是 IC 的 xdata）。
⇒ 这使"幂等落盘探针"（先读回、再原样写回、再比对）**在原理上可行**。

**活体状态实测（`--phase 1`）**：
| 地址 | 值 | 期望 | 判读 |
|---|---|---|---|
| `0x4160` `CMD_ADDR` | **`0xFF`** | `0xFF` = IC 空闲 | ✅ 空闲 |
| `0x5095` `BL_STATE_ADDR` | **`0xBE` / `0xA7`**（两次读到不同值） | `0xDD` = 在 bootloader | ⚠️ **不在升级态**；且**值会变** |
| `0x5096` `FLASH_RESULT_ADDR` | **`0x75`** | `0xAA` = 上次写成功 | 无残留成功标志 |

> ⚠️ **`0x5095` 两次读到不同值（`0xBE` → `0xA7`）** ⇒ 该地址**不是单纯的状态锁存器**，可能随内部活动变化。
> ⇒ **凡用它做"是否已进 bootloader"的判据，必须【多次读 + 连续稳定】再判定**（否则会误判）。

**⇒ 由此发现的关键前置（★ 改变了 B12 实验的风险模型）**：
官方序列是 **`0E 10`(切patch) → 轮询 `0x5095==0xDD` → `0E 11`(启动更新) → 才轮到 `0E 12`**。
实测当前 `0x5095 ≠ 0xDD` ⇒ **`0E 12` 不能直接发**；必须先发 `0E 10` + `0E 11` —— **两条也在红线内，且会使触控板停止工作**。

## 8. 🔴🔴🔴 2026-10-10 重大更正：**§7 的「读通道能触达 flash 地址空间」是【错的】**

> **本文档 §7 曾据"`0x19000` 可读出结构化内容"断言："Col04 读通道能触达 flash 地址空间"。
> 后续只读侦察（同一日、同一通道、未做任何写入）证明该结论【错误】，现予撤回。**

### 8.1 决定性实测（全部只读）

| 测试 | 结果 |
|---|---|
| `0x0A000` 前 **64 B**，连读 **5 次** | ✅ **5/5 逐字节完全相同**（稳定） |
| `0x0A000` 起 **8192 B**，两次 | ⚠️ 仅 **82.7%–85.9%** 相同 |
| **`0x0A3C0` 起 64 B，连读 5 次** | 🔴 **5 次内容完全不同**（且两次分块读都从 `0x3c2` 开始出现差异——**位置固定**） |
| `0x19000` 起 32 B，两次 | 🔴 仅 **18/32** 相同 |
| `0x5095` 多次读 | 🔴 **一直变**：`0xBE → 0xA7 → 0xC2 → 0xB7 → 0xCC` |

**`0x0A3C0` 连读 5 次的形态（关键证据）**：
```
第1次: ff ff fd 2e  ff ff fb a0  ff ff fd 3d  ff ff fb c0  …
第2次: ff ff ff ff  ff ff ff ff  00 00 00 00  ff ff ff ff  …
第3次: 00 00 00 00  00 00 00 00  ff ff ff ff  ff ff fe ……
第5次: ff ff fe aa  ff ff fd d6  ff ff fe 97  ff ff fd b8  …
```
⇒ **4 字节一组的成对结构（`ff ff fd/fb/fe xx`）在不同时刻取到不同数值** ⇒ **实时采样/寄存器窗口**，**不是静态存储**。

### 8.2 ★ 更正后的正确结论

> **本项目 Col04 读通道，在 `0x0A000` / `0x19000` 这类地址上读到的【不是 IC 的 flash 内容】**，
> 而是**部分稳定、部分实时变化的 RAM / 采样 / 寄存器窗口**。
> （稳定的是前部一小段，后部随时刻变化 —— 与《全书》第十四轮"`0x96F8` 分时复用 RAM / 空闲态是采样缓冲"**同一现象族**。）

**⇒ 因此 §7 的推论作废**：
- ❌ "读通道能触达 flash 地址空间"
- ❌ "幂等落盘探针（先读回、再原样写回、再比对）在原理上可行"

### 8.3 ★★★ 由此得到的**正向**结论（很重要）

**官方更新工具【从不读回 flash】** ——`fw_update()` 与 `flash_cfg_with_isp()` **全程只有"写 + 轮询 `0x5096==0xAA`"**，没有任何读回比对。
**⇒ 现在有了原因：通过这条通道根本读不到 flash。**

**⇒ ⇒ 因此 B12 落盘试验的【正确设计】不是"幂等探针"，而是**：
```
① 从官方 .bin 里解出【已知正确】的 4096 B 子固件内容（内容来源可靠，不需要读设备）
② 写进 RAM 暂存 0xC000
③ 发 0E 12（长度 / 地址 / 大端字和校验）
④ 轮询 0x5096 == 0xAA
⑤ 复位 0E 13
⑥ 验证靠【功能】或靠【下次开机后 / 0x96F8 版本字段变化】—— 而不是读回比对
```
⚠️ **残余风险不变且更大**：因为**无法读回**，一旦地址算术错，**没有任何回读层能发现**；
而官方**擦除隐含在 `0x12` 内** ⇒ **错地址 = 静默毁掉一片**。
⇒ **在动 `0E 12` 之前，必须先用"不依赖读回"的方式确认地址算术 —— 目前尚未做到。**

### 8.4 纪律：**第 127 条（新增）**

> **"某地址可读" ≠ "读到的就是该地址的静态内容"。**
> 凡要用"读回"作为写入前的安全前提（幂等/回滚/比对），**必须先证明该地址的读【可重复】**：
> 同一地址**重复读 N 次（N≥5）逐字节一致**，才可当作静态内容。
> **本项目代价**：曾据"能读出结构化内容"推断"读通道触达 flash"，进而设计了幂等探针；
> 实测该处**后段是实时采样** ⇒ 若照原计划写回，写进去的是**采样快照**，会**真的改动 flash**。

## 9. 🔴 2026-10-10 更正 §5：**在官方 `flash_flag=0x0C` 下【无地址重叠】**

> **本文档 §5 曾据"idx0 与 idx7 地址重叠 1792 B + 官方按表序写入"推出"idx7 覆盖 idx0、idx0 实际只有前 256 B 留在 flash"。
> 该推论【不成立】，现予更正。**

**原因**：官方 `main.cpp` 对本机用 **`firmware_flag = 0x0C`**（注释 `update type:0x02,0x03`），
而 `fw_update()` 里是 `if (!(firmware_flag & (0x01 << sub_fw_type))) continue;`
⇒ **`type 0x01` 的块（idx0）被【整块跳过】，根本不下发** ⇒ **重叠不会发生**。

**离线模拟器实测**（`tools/hid/lab__r33_fw_update_sim.py`）：

| 项 | 结果 |
|---|---|
| 本机固件在 `flag=0x0C` 下实际下发的块 | **12 块**（13 块中跳过 idx0） |
| 覆盖地址范围 | `0x000000 – 0x020000`（131,072 B） |
| **被覆盖** | **98,304 B**；未覆盖 32,768 B |
| **重叠** | **无** ✅ |

**⇒ 两种情形必须并列表述（此前只写了后一种且当成了唯一结论）**：
| 情形 | idx0（`0x00FF00`, 2048 B, type 0x01） |
|---|---|
| **`flash_flag = 0x0C`（官方对本机用的）** | ★ **整块不下发** ⇒ 该 flash 区保持原值 ⇒ **无重叠** |
| 若 `flash_flag` 含 `bit0`（即允许 type 0x01） | 会下发，且**后写的 idx7 覆盖其 `0x010000–0x010700`** ⇒ 实际只有前 256 B 生效 |

**⚠️ 方法论教训**：判断"表内地址重叠"时，**必须先确认 `flash_flag`**（哪些类型的块真的会下发）——
**跳过不下发的块，重叠可能根本不存在。** 我此前默认"13 块全下发"，因而多推了一步。
