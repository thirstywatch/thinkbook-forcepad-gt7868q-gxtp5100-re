## 1. 两条链路的物理形态

理解后文的前提：这里有**三个独立处理器**，不是两个。

```
┌─────────────────────────────────────────────────────────────────┐
│  ① 触控板主控 —— Synaptics S96U7                                │
│     固件：SurfaceTouchpad_4.12.139.bin  (364,693 B, 熵 7.89)      │
│     形态：加密/压缩的代码镜像，几乎无字符串                        │
│     职责：触控扫描、手势解析、HID 报告、压力原始值                 │
└───────────────┬─────────────────────────────────────────────────┘
                │ I²C (SDA/SCL) + TS_SPI 四线
                │ 引脚名见 §12：TRACKPAD_SCL/SDA/INT_N/RST_N
                ▼
┌─────────────────────────────────────────────────────────────────┐
│  ② EC 控制器 —— SAM (Surface Aggregator)                         │
│     固件：SurfaceSAM_9.101.139.bin  (1,382,917 B, 2 变体)         │
│     形态：Thumb 代码 + 大量字符串池 + 启动期 LZSS 解压             │
│     职责：触控板生命周期、触觉强度映射、按键/压力状态机、           │
│           BuckBoost 供电轨、固件升级、SSH 内部通道                │
└───────────────┬─────────────────────────────────────────────────┘
                │ I²C 0x43 (HAPTIC_DRIVER) / 0x60 (BUCK_BOOST)
                ▼
┌─────────────────────────────────────────────────────────────────┐
│  ③ 触觉 DSP —— Cirrus Logic CS40L25                             │
│     固件：SurfaceTouchpadHaptic_2.9.139.bin (105,591 B, 熵 5.13) │
│     形态：167 个带 CRC16 的 DSP 地址-数据写入块                    │
│     职责：波形发生（VIBEGEN）、WSEQ 音序、功率控制                 │
└───────────────┬─────────────────────────────────────────────────┘
                │ 电流驱动
                ▼
            LRA 线性谐振执行器（马达）
```

**压感传感器是第四个部件**，独立固件（`SurfaceTouchpadForce_10.0.156.bin`，63,117 B，熵 6.65），
在 EC 侧的设备名叫 `FORCE_SENSOR`（§7）。

**关键认知**：`SurfaceTouchpadHaptic` 里的"Haptic"是**给 DSP 烧的波形数据**，
不是给 EC 烧的代码。EC 自己也有触觉逻辑（强度映射），两者是**不同层面的触觉**：
- **EC 侧**：决定"用哪几个波形"（逻辑层）
- **CS40L25 侧**：存放"这些波形长什么样"（数据层）

## 3. 统一封装格式（四份固件共有）

```
FMP capsule (GUID 6dcbd5ed-e82d-4c44-bda1-7194199ad92a，小端存储)
  └─ HeaderSize(u32) Flags(u32) TotalSize(u32)     ← 长度必须等于文件长度
  └─ FMP item table: version=1, drivers=0, payloads=1
      └─ FMP image header v2 (40 B) + image GUID + image_size + vendor_size=0
  └─ auth: MonotonicCount(8) + WIN_CERTIFICATE_UEFI_GUID (PKCS#7)
      └─ cert_revision=0x200, cert_type=0xEF1
  └─ payload: MSS1(16) + SAML(25) + CFU stream
      └─ CFU: 2 × (16 字节 offer + 记录流)
          └─ Component（去分帧后的连续镜像）
              └─ body（Component 头之后）
```

### 3.1 CFU 记录

```c
struct CfuRecord {
    uint32 component_offset_le;   // 重组镜像内偏移，不是 DSP 地址
    uint8  length;                // 本样本 1..16
    uint8  data[length];
};
```

重组时强制 `component_offset == len(已重组)` —— 空洞、覆盖、倒序、尾部截断**一律报错**。
`component_offset_le` 是 **u32 小端**；而 Component **内部数据是大端** —— 同一文件内字节序会变。

### 3.2 CFU offer（16 字节）

| 样本 | offer | b12 | b13 | b2 |
|---|---|---:|---:|---:|
| SAM 变体 0 | `020000b08b6500090100000004023c00` | `0x04` | `0x02` | `0x00` |
| SAM 变体 1 | `020000b08b6500090100000014023c00` | `0x14` | `0x02` | `0x00` |
| Touchpad | `020011b08b0c00040200000004013c00` | `0x04` | `0x01` | `0x11` |
| Haptic | `000016b08b0900020100000004013c00` | `0x04` | `0x01` | `0x16` |
| Force | `000012b09c00000a0200000004013c00` | `0x04` | `0x01` | `0x12` |

字节 3 = `0xB0`、字节 14:16 = `3C 00` 在四个独立样本中恒定，作为硬不变量。
同胶囊两 offer：字节 0..12 必须相同；两份载荷 **Touchpad/Haptic/Force 字节相同，SAM 不同**。

### 3.3 Component 头与各固件几何

```c
struct ObservedComponentHeader {
    uint32 header_size;       // 20
    uint32 observed_1;        // 1
    uint32 observed_2;        // 1
    uint32 extension_offset;
    uint32 body_offset;
};  // 约束：20 <= extension_offset < body_offset < component_size
```

| 固件 | CFU 记录 | Component | body_offset | body | MSS1 版本 | offer 两份载荷 |
|---|---:|---:|---:|---:|---|---|
| SAM（两变体） | **32,871** | **525,932** | `0x66C` | **524,288** | `0x900658b` | 不同 |
| Touchpad | 8,630 | 138,076 | `0x66C` | 136,432 | `0x4000c8b` | 相同 |
| Force | 1,450 | 23,188 | `0x6C` | 23,080 | `0xA00009C` | 相同 |
| Haptic | **2,461** | **39,370** | `0x6C` | **39,262** | `0x200098B` | 相同 |

四份固件的 FMP flags 均为 `0x50000`。

# 第一部分：震动（触觉）链路

## 4. 触觉固件的形态

**它不是代码，是一张"往 DSP 哪些地址写哪些字节"的清单。**

### 4.1 外层

body 头 8 字节：

```
struct HapticBodyHeader {
    uint32 revision_register_le;  // 0x02800010
    uint32 block_count_le;        // 167
};
```

随后 167 个块，每块 14 字节头 + payload：

```c
struct HapticBlockHeader {
    uint32 sequence_le;       // 从 0 严格连续递增
    uint32 dsp_address_le;    // CS40L25 总线地址
    uint32 payload_size_le;   // 1..240，本样本 4 字节对齐
    uint16 crc16_le;          // CRC16/CCITT-FALSE，仅覆盖 payload
    uint8  payload[payload_size_le];
};
```

**校验状态**：167 块 CRC16 **全部通过**，序列号 0..166 连续，最后一块恰好终止于 body 末尾
（无尾随字节）。地址窗口 `0x02000000` – `0x03804DD0`。

### 4.2 固件身份 —— 在 ID 块里直接读到

序列 0（`addr=0x02000000`, 96 字节）的前 32 字节：

```
00 04 00 00  00 02 03 00  14 00 e1 00  44 0a 06 03
00 52 00 05  00 00 00 00  02 00 00 00  bd 00 00 ...
```

| 字节 | 解读 | 值 |
|---|---|---|
| `14 00 e1 00` | HALO u32 打包 firmware_id | **`0x000E1400`**（即记录的 `0x1400E1`） |
| `44 0a 06 03` | revision | **`0x00060A04`**（即 `0x0A0603`） |
| `bd` | algorithm id | **`0xBD` = VIBEGEN** |
| `03 00` | 紧随的第二个算法高字节 | 对应 `DYNAMIC_F0 = 0x111` |

### 4.3 core / 追加分界

| 区段 | 块序号 | 块数 | payload | 说明 |
|---|---|---:|---:|---|
| **core** | 0–136 | **137** | 30,008 B | 与 Cirrus 参考 `…_ext_boost_0A0603.wmfw` 逐块一致 |
| **Surface 追加** | 137–166 | **30** | 6,908 B | 微软追加的 waveform / WSEQ |
| 合计 | | 167 | 36,916 B | |

> ⚠️ **SAM 内置固件的 revision 是 `0x0A0601`，不是 `0x0A0603`**。
> 两者地址/大小 137/137 一致、内容 132/137 一致，差异在索引 0、11、12、54、90。
> **不要把 SAM 内置的标成 0A0603。**

## 5. DSP 内存空间布局

**这是理解"震动信息在固件里长什么样"的核心一节。**
137 个 core 块不是均匀铺开的，而是分成**稀疏代码/控制区**与**连续数据表区**两种截然不同的形态。

### 5.1 按地址窗口统计

| DSP 地址窗口 | 块数 | payload | 跨度 | 填充密度 | 形态判读 |
|---|---:|---:|---:|---:|---|
| `0x03800000`–`0x03804DE4` | **84** | **19,940 B** | 19,940 B | **100.0%** | **完全连续的查找表** |
| `0x03400000`–`0x03400FD0` | 17 | 4,048 B | 4,048 B | **100.0%** | 连续表（YM wavetable） |
| `0x02800B60`–`0x02801894` | 13 | 2,860 B | 3,380 B | 84.6% | 连续表（XM wavetable + WSEQ） |
| `0x02xxxxxx` | **53** | 10,068 B | **12,588,204 B** | **0.1%** | **稀疏点写，仅 2 个 64 KB 页** |

**两个关键观察**

1. `0x03800000` 段 **84 个块首尾相接、零缝隙**（`written == span`）——
   这不是"一堆独立寄存器写"，而是**一张连续的结构化表**。
2. `0x02xxxxxx` 段横跨 **12.6 MB** 却只写 10 KB，且只落在 `0x02000000` 与 `0x02C00000`
   **两个 64 KB 页**内 —— 典型的**代码段 / 算法段点写**。

### 5.2 追加区与 core 零重叠

| 区域 | 地址范围 | 实际写入 | 块数 | 占广告容量 | 与 core 重叠 |
|---|---|---:|---:|---:|---:|
| XM wavetable | `0x02800B60`–`0x028014C8` | **2,408** | 11 | **97.1%**（容量 2,480） | **0** |
| YM wavetable | `0x03400000`–`0x03400FD0` | **4,048** | 17 | **57.8%**（容量 7,000） | **0** |
| WSEQ | `0x028016D0`–`0x02801894` | **452** | 2 | — | **0** |

**XM 写到控制容量的 97.1%（仅差 72 字节尾部），YM 只写 57.8%（差 2,952 字节）。**
未写尾部**不作补零** —— 没有证据证明它应为零、应继承 ROM，或属于本次有效波形。

### 5.3 顺序规律

块序列**大体按地址升序**（仅在追加区与 core 交界处有回绕）。
这与下载循环的写法一致，也保证固件可重现。

## 6. Wavetable 描述符链（本文新增）

> 项目 wiki 明确记载这一项"尚未可靠解出"。以下结论来自字节分析，
> 并区分**确证**（计数交叉验证）与**推测**（未证部分明确标注）。

### 6.1 结构确证：12 字节大端三元组

XM 与 YM 区域开头都是 **12 字节大端三元组序列**：

```c
struct WaveDescriptor {
    uint32 count_be;    // 本样本全部为 8
    uint32 offset_be;   // 指向区域内偏移
    uint32 type_be;     // 类型/通道标识
};
```

XM 区域前 48 字节原始值：

```
00 00 00 08  00 00 00 4c  00 00 00 16
00 00 00 08  00 00 00 62  00 00 00 16
00 00 00 08  00 00 00 78  00 00 00 16
00 00 00 08  00 00 00 8e  00 00 00 16
```

按三元组读：`count=8`，offset 依次 `0x4C, 0x62, 0x78, 0x8E`（步长 **22**），type 恒 `0x16`。

**终止判据是自洽性，不是猜测**：当 `count > 4096` 或 `offset >= 区域大小` 时停止。
之后同一段字节读作密集 u24 采样。

### 6.2 XM wavetable（`0x02800B60`，2,408 B）

- **25 个描述符**，占据 `0x000`–`0x12C`
- `count` 恒为 **8**
- offset 步长：**22**（13 次）→ **20**（11 次）⇒ 描述符长度分段递减
- type 分两组：

| type | 项数 | offset 范围 |
|---|---:|---|
| `0x0016` | 13 | `0x004C` – `0x0154` |
| `0x0014` | 12 | `0x016A` – `0x0246` |

- 描述符链终止于 `0x012C`，其后 **2,108 B** 为采样负载（702.7 个 u24）

### 6.3 YM wavetable（`0x03400000`，4,048 B）

- **53 个描述符**，占据 `0x000`–`0x27C`
- `count` 恒为 **8**
- type 分 5 组，**四组各 13 项 + 1 个引导项**：

| type | 项数 | offset 范围 |
|---|---:|---|
| `0x0014` | **1** | `0x00A0`（引导项） |
| `0x0012` | 13 | `0x00B4` – `0x018C` |
| `0x0011` | 13 | `0x019E` – `0x026A` |
| `0x000F` | 13 | `0x027B` – `0x032F` |
| `0x000E` | 13 | `0x033E` – `0x03E6` |

- 描述符链终止于 `0x027C`，其后 **3,412 B** 为采样负载（1,137.3 个 u24）

### 6.4 ⭐ 决定性交叉验证

| | 描述符数（本文从字节数出） | metadata 常量（项目从 WMFW 元数据出） |
|---|---:|---|
| XM | **25** | `SURFACE_FW_XM_WAVES = 25` ✓ |
| YM | **53** | `SURFACE_FW_YM_WAVES = 53` ✓ |

**两条完全独立的路径得出同一数字**，可信度远高于单侧推断。
YM 的 `4 × 13 + 1 = 53` 分组结构进一步解释了计数本身。

### 6.5 边界证据（同一段字节的两种读法）

XM `0x012C` 起 24 字节：

```
00 ff ff ff  00 80 00 3c  00 00 00 00  00 00 ff fe
00 fd fc fa  00 f8 f5 f3
```

- 按描述符读：`count = 0x00FFFFFF`（荒谬）⇒ **必须停止**
- 按 u24 BE 采样读：`00FFFF, FF0080, 003C00, 000000, 0000FF, FE00FD, FCFA00, F8F5F3`

YM `0x027C` 起同理：`00FFFF, FF0080, 003600, 000000, 0000FE, FA00F5, EFE700, DFD5CB`。

**数值单调递减的形态符合振动包络形状**，支持 u24 采样解释。

**统计判据**：LE 有符号解释会把均值拉向 `INT24_MIN`
（XM：LE 均值 −44,628，232/702 为负；YM：LE 均值 845,382，122/1,137 为负），
而 BE 解释下 XM 均值 5,464,691 无异常聚集 ⇒ **BE 解释更自洽**。

### 6.6 强度索引落点

强度映射实际选中的索引在区域内的位置（4 字节步进探针）：

| 索引 | XM byte | XM 首 12 字节 | YM byte | YM 首 12 字节 |
|---:|---:|---|---:|---|
| 13 | `0x0034` | `000000a4 00000016 00000008` | `0x0034` | `000000ea 00000012 00000008` |
| 17 | `0x0044` | `00000016 00000008 000000d0` | `0x0044` | `00000012 00000008 00000010e` |
| 24 | `0x0060` | `00000008 000000fc 00000016` | `0x0060` | `00000008 00000013 20000012` |
| 36 | `0x0090` | `00000008 00000154 00000016` | `0x0090` | `00000008 0000017a 00000012` |
| 100 | `0x0190` | `0000fffe 00fdfbf9 00f6f3f0` | `0x0190` | `000002d5 0000000f 00000008` |

低索引（13–36）区呈 **`08` / `12` / `16` 三元循环**，与描述符的 type 值同域；
而 **index 100（强度 0）处是连续递减的 24 位采样**。

> **推测（未证）**：三元循环区是描述符/索引表，index 100 处是实际波形采样。
> 要确证需要 VIBEGEN wavetable ABI，或逐索引实机播放 + 总线 trace。

### 6.7 WSEQ 区域（`0x028016D0`，452 B）

不具描述符链结构。头部按 u32 BE 读为
`0x002C04, 0x000000, 0x001000, 0x4C2800, 0x000000, 0x00204C, …`，
其中 `0x10` / `0x20` / `0x21` 等值与 §8 初始化表中的寄存器编号同域，
**推测**为音序器寄存器组，**未解**。

## 9. 强度→波形索引映射

**形态：一段 Thumb 比较链，5 档，每档两个立即数（按下/释放索引）。**

| | 地址 |
|---|---|
| `set_intensity_setting`（变体 0 / 1） | `0x000D8530` / `0x000D9F30` |
| `setting_to_two_indices`（变体 0 / 1） | `0x000D859A` / `0x000D9F14` |
| 调用点 | `0x000D8544: bl 0x000D859A` |

### 9.1 映射表

| 强度设定 | 按下索引 | 释放索引 | 分支条件 | 覆盖值数 |
|---:|---:|---:|---|---:|
| **0** | **100** | **100** | 零特判 | 1 |
| **1–38** | **17** | **13** | `< 39` | 38 |
| **39–63** | **21** | **15** | `< 64` | 25 |
| **64–88** | **24** | **17** | `< 89` | 25 |
| **89–100** | **36** | **29** | `< 101` | 12 |
| **101–255** | 保持原值 | 保持原值 | `≥ 101` | 155 |

### 9.2 完整反汇编（变体 0，`0x000D8584`–`0x000D85E6`）

```asm
000d8584  push     {r7, lr}
000d8586  mov      r3, r1
000d8588  movs     r2, #1
000d858a  add.w    r1, r0, #8
000d858e  adds     r0, r3, #1
000d8590  bl       0x90dda              ; 边界检查
000d8594  mov.w    r0, #-0x80000000     ; 错误掩码
000d8598  pop      {r1, pc}
000d859a  mov.w    r2, #-0x80000000     ; ← setting_to_two_indices 入口
000d859e  movs     r3, r0               ; r3 = setting
000d85a0  bne      0xd85aa              ; setting != 0 ?
000d85a2  movs     r0, #0x64            ; 0x64 = 100
000d85a4  strb     r0, [r1]             ; press  = 100   ← 只加载一次，存两次
000d85a6  strb     r0, [r1, #1]         ; release= 100
000d85a8  b        0xd85e4
000d85aa  cmp      r3, #0x27            ; 上界 39
000d85ac  bhs      0xd85b8
000d85ae  movs     r0, #0x11            ; 0x11 = 17
000d85b0  strb     r0, [r1]             ; press  = 17
000d85b2  movs     r0, #0x0d            ; 0x0D = 13
000d85b4  strb     r0, [r1, #1]         ; release= 13
000d85b6  b        0xd85e4
000d85b8  cmp      r3, #0x40            ; 上界 64
000d85ba  bhs      0xd85c6
000d85bc  movs     r0, #0x15            ; 21
000d85be  strb     r0, [r1]
000d85c0  movs     r0, #0x0f            ; 15
000d85c2  strb     r0, [r1, #1]
000d85c4  b        0xd85e4
000d85c6  cmp      r3, #0x59            ; 上界 89
000d85c8  bhs      0xd85d4
000d85ca  movs     r0, #0x18            ; 24
000d85cc  strb     r0, [r1]
000d85ce  movs     r0, #0x11            ; 17
000d85d0  strb     r0, [r1, #1]
000d85d2  b        0xd85e4
000d85d4  cmp      r0, #0x65            ; 上界 101
000d85d6  bhs      0xd85e2              ; → 越界：保持原值
000d85d8  movs     r0, #0x24            ; 36
000d85da  strb     r0, [r1]
000d85dc  movs     r0, #0x1d            ; 29
000d85de  strb     r0, [r1, #1]
000d85e0  b        0xd85e4
000d85e2  ldr      r2, [pc, #0x94]      ; ← 越界状态常量
000d85e4  mov      r0, r2
000d85e6  bx       lr
```

`0x000D85E2` 的 `ldr r2,[pc,#0x94]` 解析到常量 **`0x8300001F`** ——
配合错误掩码 `and r0,#0x8300001F`，这是**状态码，不是波形索引**，
语义为"保持已编程值不变"。

### 9.3 两种独立方法交叉验证

1. **符号化**：从 Thumb 指令的 `cmp` / `movs` 立即数还原谓词
2. **穷举**：对还原出的谓词穷举 0..255 全部 256 个输入

两者完全一致。写入按下索引的 store（`strb r0,[r1]`）与释放索引的
（`strb r0,[r1,#1]`）共 **10 处，全部逐条对上**。

> ⚠️ **与 wiki 一致的保留**：index 100 的 waveform 内容未解码，
> 因此**不能断言"强度 0 = 静音"**，只能说它映射到索引 100。

## 13. SAM 启动期 RAM 镜像

**形态：SAM 的 body 里没有 CS40L25 内置描述符、触摸板状态表和 HID 描述符 ——
它们在启动时被 LZSS 解压进 RAM。**

### 13.1 引导分发表（按变体不同）

| 变体 | 分发表地址 | zero 函数 |
|---|---:|---:|
| 0 | `0x000E755C` | `0x00093326` |
| 1 | `0x000E915C` | `0x00096B62` |

清零区间（两变体一致）：`0x00100000`(106,320) / `0x001237F0`(45,632) / `0x0012EA30`(640)

### 13.2 解压算法

```c
token      = byte();
literals   = token & 3;      if (literals == 0) literals = byte() + 3;
matches    = token >> 4;     if (matches == 15)   matches  = byte() + 15;
literals  -= 1;
memcpy(out, src, literals);                 // 原样拷贝
if (matches) {
    low       = byte();
    high      = (token >> 2) & 3;  if (high == 3) high = byte();
    distance  = low + (high << 8);
    for (i = 0; i < matches + 2; i++)     // 逐字节，可重叠
        out[len++] = out[len - distance];
}
```

### 13.3 解压结果

| 变体 | 目标 | 压缩 | 解压 | SHA-256 |
|---|---|---:|---:|---|
| 0 | `0x0011DDB0` | 5,178 | **23,101** | `2022310d8eaa7e0f…` |
| 0 | `0x00001BB8` | 10 | **800** | `67042dfda5683aea…` |
| 1 | `0x0011DDB0` | 5,184 | **23,101** | `2041290bb3a13d8e…` |
| 1 | `0x00001BB8` | 10 | **800** | `67042dfda5683aea…` |

**可信度依据**：两个解压目标必须精确等于 `0x11DDB0` / `0x1BB8`，
且解压段与三个清零区间无重叠 —— 两条都成立才认为解码正确。

### 13.4 装载映射（已验证）

```c
runtime_address = body_file_offset + 0x80000
```

四条独立证据：

1. body 偏移 `0x0` = `0x00001BB8`（初始 SP，ARM 向量表第 0 项）
2. body 偏移 `0x4` = `0x000E4D75`（Reset，低位 1 = Thumb）
3. 字符串 `ActuateHaptic` @ body `0x0DC20` → runtime `0x08DC20`
4. 向量表项 13 = `0x00080000`，恰等于 LOAD_BASE

Reset 入口首条指令 `cpsid i` + 三条 PC 相对 `ldr` —— 典型复位 prologue。
向量表 43/48 项带 Thumb 位。向量 8 = `0x00280000`（bit0=0，ARM 状态）
指向 body 之外 ⇒ **复位代码在跳转前先重映射**，不可直接反汇编该目标。

### 13.5 反汇编覆盖度

| 变体 | 向量入口 | 可达指令 | PC 相对数据引用 |
|---|---:|---:|---:|
| 0 | 42 | 661 | 114 |
| 1 | 43 | 692 | 77 |

body 中 58% 的半字可解码为合法 Thumb —— **代码与数据交织**。
线性扫描在 `0x80174`（变体 0）即遇数据停止，只解出 182 条；
递归下降多解出 **3.6 倍**且不产生误判。

## 16. 复核方法

```bash
cd surface_fw/analyze
python unpack_all.py         # 几何：SAM 32871/525932/524288；Haptic 2461/39370/39262/167
python dsp_layout.py         # DSP 窗口：0x03800000 密度 100%，0x02xxxxxx 仅 2 页
python wavetable.py          # 描述符：XM 25、YM 53
python sam_tables.py         # 初始化表：71 / 70 项，status=ok
python sam_startup.py        # 解压：0x11DDB0(23101) / 0x1BB8(800)
python intensity_map.py      # 强度映射：五档 + 0x8300001F，两变体一致
python ec_inventory.py       # EC 字符串按子系统分组
python touchpad_form.py      # 三份固件形态对比：熵 7.894 / 6.651 / 5.129
python sam_disasm.py         # 常量与字符串证据收集
python sam_flow.py           # 递归下降反汇编
```

**所有脚本在结构不变量被违反时抛异常而非降级输出** ——
因为"尽力而为"的镜像会让下游的波形地址和载荷字节失去可信度。

### 关键复核锚点

| 断言 | 复核方式 |
|---|---|
| MSI 是原封官方包 | `sha256sum` 应为 `522c70e53a44211e5c55a3635109a8c7c6d314f69a4b51fa439d4b4cbfb0184c` |
| 装载映射 `+0x80000` | body 偏移 `0x0` = `0x1BB8`、`0x4` = `0x000E4D75` |
| 两变体同源 | 五个 boost vtable 指针差恒为 `+0x1990` |
| 强度映射 | 10 条 `strb` 立即数：100,17,13,21,15,24,17,36,29 + 越界 `0x8300001F` |
| 描述符数 | XM 25 / YM 53，与 metadata `SURFACE_FW_XM_WAVES` / `YM_WAVES` 一致 |
| 追加区与 core 不重叠 | 三区与 core 重叠块数均为 0 |
| 初始化表差异 | 表 B 比表 A 少且仅少 `0x00002C0C` |
| 三份固件形态差异 | 熵 7.894 / 6.651 / 5.129，代码样窗口 63/0/0 |
