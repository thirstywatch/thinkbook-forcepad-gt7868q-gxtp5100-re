# SPB 客户端驱动（GdixSpbProbe）架构判定 + 蓝莓项目对比核实

> 日期：2026-10-01
> 触发：接手 `goodix-tool` 新线（ROUND70/71 的 SPB 客户端驱动线）
> 方法：本地读源码 + 微软官方 SPB 文档原文 + 仓库全文取回
> 状态标记：✅ 已核实（有一手来源） · ❌ 已否证 · ⚠️ 未验证

---

## 〇、一句话结论

> ❌ **`GdixSpbProbe.sys` 这条路走不通，而且不是"细节要调"，是三层架构性错误。**
> ✅ **微软文档的硬约束：一个 SPB 外设的连接同一时刻只能有一个驱动持有打开。**
> ⇒ 想在这块板子上自己发 I²C 事务，**只能由 `ACPI\GXTP5100` 的函数驱动来做**（也就是必须接管 `hidi2c` 的位置），
> 而该函数驱动同时还得把触控板功能维持住。
> ✅ **顺带否证**：`ty2/goodix-gt7868q-linux-driver` **不是** I²C 驱动，**不能**作为"Linux 可任意读写寄存器"的依据。

---

## 一、❌ SPB 驱动的三层错误（逐层独立、任一层都足以致命）

### 1.1 第一层：不是函数驱动 ⇒ 根本拿不到连接 ID

微软文档原文（[Connection IDs for SPB-Connected Peripheral Devices](https://raw.githubusercontent.com/MicrosoftDocs/windows-driver-docs/d88c9d472f2762a09be62cc673d389ed766b9dd1/windows-driver-docs-pr/spb/connection-ids-for-spb-connected-peripheral-devices.md)）：

> The **driver for an SPB-connected peripheral device receives the connection ID for the device as part of the driver's assigned hardware resources.**
> A KMDF driver receives its hardware resources during an **EvtDevicePrepareHardware** callback.

而 `GdixSpbProbe.c:186-198`：

```c
NTSTATUS EvtPrepareHardware(..., WDFCMRESLIST ResourcesRaw, WDFCMRESLIST ResourcesTranslated)
{
    UNREFERENCED_PARAMETER(ResourcesRaw);
    UNREFERENCED_PARAMETER(ResourcesTranslated);      // ★ 两份资源列表直接丢弃
```

⇒ **连接 ID 就在被丢弃的 `ResourcesTranslated` 里。** 拿不到 ID ⇒ 后面无论怎么写都打不开连接。

另外，连接 ID **不是**那个 GUID：

| 项 | 实际是什么 |
|---|---|
| `{F0E20F09-D97A-49A9-8046-BB6E22E6BB2E}` | 设备的 **SPB 连接参数属性**（`DEVPKEY_Device_SpbConnectionParameters`），里面是 100 B 序列化描述符 |
| **Connection ID** | 一个 **64 位整数**，由 PnP 分配、和参数一起存在 **resource hub** 里，随硬件资源下发 |

`ROUND70_SPB_CONNECTION_ID_FOUND.md` §2.4 把那个 GUID 当成"钥匙"（Connection ID），**这一条是概念错误**。

### 1.2 第二层：设备名是硬编码的，而且这个设备名不是触控板 PDO

```c
RtlInitUnicodeString(&targetName, L"\\Device\\0000008a");   // GdixSpbProbe.c:206
...
WDF_IO_TARGET_OPEN_PARAMS_INIT_OPEN_BY_NAME(&openParams, &targetName, GENERIC_READ|GENERIC_WRITE);
openParams.ShareAccess = FILE_SHARE_READ | FILE_SHARE_WRITE;   // 与官方样例的 ShareAccess = 0 相反
status = WdfIoTargetOpen(ctx->I2CTarget, &openParams);
```

问题有三：

| # | 问题 |
|---|---|
| 1 | `\Device\0000008a` 只是 ACPI dump 里 `GXTP5100` 的 **PDO 名**，ACPI 枚举器分配的名字**每次枚举都可能变** —— 现成反例：`ROUND70` 里 `ACPI\LTCN0001\1` 的父设备就是另一个 PDO 名 |
| 2 | 官方样例加载的**不是 PDO 名**，而是 `RESOURCE_HUB_CREATE_PATH_FROM_ID` 生成的 resource hub 路径。照抄错对象 |
| 3 | `ShareAccess = FILE_SHARE_*` 与官方样例相反（官方 `ShareAccess = 0; CreateDisposition = FILE_OPEN;`）。官方是"独占打开"语义 |

而且代码里自己就留了这句注释，等于承认不知道目标是谁：

```c
KdPrint(("[GdixSpbProbe] -> set IoDeviceObjectName in INF for the target\n"));
```

（INF 里没有任何 `IoDeviceObjectName`。）

### 1.3 第三层：★ 微软文档写明的硬约束 —— 连接已被 `hidi2c` 持有

同一份官方文档结尾：

> ## **"Only one driver can hold an open logical connection to an SPB-connected peripheral device at a time. An attempt by another driver to open a second connection to the same device fails."**

（另见 [SPB Connection Locks](https://raw.githubusercontent.com/MicrosoftDocs/windows-driver-docs/staging/windows-driver-docs-pr/spb/spb-connection-locks.md)：连接锁的典型用途是"客户端驱动与 `Acpi.sys` 共享设备"，**属于平台固件约定的特例**，不是通用旁路入口。）

这条直接判死"再挂一个并列客户端"的思路：

```
Intel Serial IO I2C 7E78  ← 物理上确实可以有多个客户端 ✅
        │
        └── ACPI\GXTP5100\1 ── 但是【这一个外设的连接】只有一个名额
                 └── hidi2c.sys 已经持有 ❌ ← 第二家打开必然失败
```

★ **"I²C 控制器不是 hidi2c 独占的"这句话本身没错，错的是推论**：
控制器可以有并列客户端（不同外设各占一个连接）；**同一个外设的连接**不行。

`ROUND70` 用 Sunia `TcnPeripheral` 做"本机实证"，但那条记录恰好自证了这一点：

| | 触控板（我们） | TCON（Sunia） |
|---|---|---|
| ACPI 节点 | `\_SB.PC00.I2C0.TPAD` | `\_SB.PC00.I2C2.TCON` |
| 服务 | `hidi2c` | `TcnPeripheral`（**独占该节点**） |
| 驱动栈 | `mshidkmdf → hidi2c → ACPI` | `TcnPeripheral → ACPI` |

⇒ Sunia 在 `_SB.PC00.I2C2.TCON` 上是**一家独占**，不是"和 hidi2c 并存"。它证明的是"第三方可以拥有一个 ACPI 节点的函数驱动"，**不是**"可以在别人已占的连接上再开一条"。

### 1.4 附带：INF 的安装路径也走不通

```ini
Class = System                       ; 不是 HIDClass ✅ 意图正确
%...% = GdixSpbProbe_Install, ACPI\GXTP5100      ; ← 这一行等于"抢当 ACPI\GXTP5100 的函数驱动"
```

`README_INSTALL.md` 第 138 行写：

> 触控板是用 `hidi2c.sys` 工作的，**我们的驱动理论上不会取代它**（`Class=System`，非 HIDClass，硬件 ID 不冲突）。

**这条自我保证是错的。** PnP 绑定只按 Hardware ID/Compatible ID 匹配，**与设备类无关**。用 `ACPI\GXTP5100` 匹配 + `pnputil /add-driver ... /install` ⇒ 直接顶掉 `hidi2c` ⇒ 触控板没驱动 ⇒ 立即失灵（连"读到寄存器"都等不到）。

若改成根枚举（`*GXTP…`）避开抢绑定，那它又不是任何 ACPI 节点的函数驱动 ⇒ **又回到 §1.1：拿不到连接 ID**。
⇒ **两个方向互斥，不存在"既不抢绑定又能拿到连接 ID"的中间态。**

### 1.5 附带：代码级 bug（即使架构对了也跑不起来）

| 文件:行 | 问题 |
|---|---|
| `GdixSpbProbe.c:359-360` | `WDF_MEMORY_DESCRIPTOR_INIT_BUFFER(&cmdDesc, &seq, sizeof(seq))` —— `IOCTL_SPB_EXECUTE_SEQUENCE` 的**输入**应是 `SPB_TRANSFER_LIST`；**输出**应是接收数据的缓冲。这里输出描述符给了 `NULL, 0`，`rspDesc` 完全没用上 |
| 同上 | `seq` 是 `SPB_TRANSFER_LIST_AND_ENTRIES(2)` **栈变量**，同步发送虽可行，但语义上仍是错的封装 |
| `GdixSpbProbe.c:280-304` | `GdixBuildReadPkg` 声明返回 `NTSTATUS`，但**函数结尾没有 `return`** ⇒ 返回值未定义（UB） |
| `GdixSpbProbe.c:463-469` | 失败时 `WdfRequestCompleteWithInformation(Request, status, ...)` 传的是失败码 ⇒ 用户态看不出数据 |
| `GdixSpbProbe.c:227-232` | `IoGetAttachedDeviceReference(WdfDeviceWdmGetDeviceObject(Device))` 后用 `ObDereferenceObject` 释放（应 `ObDereferenceObject` 匹配 `IoGetAttachedDeviceReference` 其实正确，但**结果只打印、从不使用**） |
| `GdixSpbProbe.c:49-53` | 自定义 IOCTL 用 `FILE_ANY_ACCESS` ⇒ **任意用户态进程可打开并下指令**。一个"只读安全"的驱动不该是 ANY_ACCESS（应 `FILE_READ_ACCESS` + 严格 `SDDL`） |
| `GdixSpbProbe.inf:21` | `CatalogFile = GdixSpbProbe.cat`，**仓库里没有 .cat**，README 的签名步骤也从未执行过 ⇒ 现在这份 .sys 连加载资格都没有 |

### 1.6 顺带：`ROUND70` §2.2 的 blob 字段解析本身也不可靠

该表把 100 B blob 按 `ConnectionSpeed@0x0C / DataBitLength@0x10 / 连接 ID 长度@0x40` 手工对齐。
而官方结构是**紧凑打包**的（[how-to-get-the-connection-settings](https://raw.githubusercontent.com/MicrosoftDocs/windows-driver-docs/staging/windows-driver-docs-pr/spb/how-to-get-the-connection-settings-for-a-device.md)：`PNP_SERIAL_BUS_DESCRIPTOR` + `ConnectionSpeed` + `SlaveAddress`，**用 `pshpack1.h` 逐字节对齐**）。
★ 该文档自己承认"我最初手工读成 `2`，属字段对齐错误" —— **同一个方法又用了一遍**。

## 二、✅ 官方 KMDF SPB 客户端驱动的正确形状（对照用）

来源：[Hardware Resources for Kernel-Mode SPB Peripheral Drivers](https://raw.githubusercontent.com/MicrosoftDocs/windows-driver-docs/staging/windows-driver-docs-pr/spb/hardware-resources-for-kernel-mode-spb-peripheral-drivers.md)

```c
// ① 在 EvtDevicePrepareHardware 的资源列表里找连接 ID
resourceCount = WdfCmResourceListGetCount(ResourcesTranslated);
for (...) {
    pDescriptor = WdfCmResourceListGetDescriptor(ResourcesTranslated, ix);
    if (pDescriptor->Type == CmResourceTypeConnection) {
        if (pDescriptor->u.Connection.Class == CM_RESOURCE_CONNECTION_CLASS_SERIAL &&
            pDescriptor->u.Connection.Type  == CM_RESOURCE_CONNECTION_TYPE_SERIAL_I2C) {
            connectionId.LowPart  = pDescriptor->u.Connection.IdLowPart;   // ★ 64 位整数
            connectionId.HighPart = pDescriptor->u.Connection.IdHighPart;
        }
    }
}

// ② ID → resource hub 设备路径
DECLARE_UNICODE_STRING_SIZE(szDeviceName, RESOURCE_HUB_PATH_SIZE);
status = RESOURCE_HUB_CREATE_PATH_FROM_ID(&szDeviceName, connectionId.LowPart, connectionId.HighPart);

// ③ 打开连接
WDF_IO_TARGET_OPEN_PARAMS_INIT_OPEN_BY_NAME(&openParams, &szDeviceName, (GENERIC_READ | GENERIC_WRITE));
openParams.ShareAccess       = 0;
openParams.CreateDisposition = FILE_OPEN;
openParams.FileAttributes    = FILE_ATTRIBUTE_NORMAL;
status = WdfIoTargetOpen(SpbIoTarget, &openParams);

// ④ 之后用 WdfIoTargetSendIoctlSynchronously 发 IOCTL_SPB_EXECUTE_SEQUENCE，
//    或直接 WdfIoTargetSendRead/WriteSynchronously 发 IRP_MJ_READ/WRITE
```

`RESOURCE_HUB_PATH_SIZE` / `RESOURCE_HUB_CREATE_PATH_FROM_ID` 在 **`Reshub.h`**。

★ 另一个被误用的 API：`SpbTargetGetConnectionParameters` 是**控制器驱动在 `EvtSpbTargetConnect` 回调里**调用的（[官方文档](https://raw.githubusercontent.com/MicrosoftDocs/windows-driver-docs/staging/windows-driver-docs-pr/spb/how-to-get-the-connection-settings-for-a-device.md)）。

> If your **SPB controller driver** registers an `EvtSpbTargetConnect` callback function, SpbCx calls this function when a client (peripheral driver) sends an `IRP_MJ_CREATE` …
> In response to the `EvtSpbTargetConnect` callback, the **SPB controller driver** should call `SpbTargetGetConnectionParameters` …

⇒ **独立第三方客户端用不了它**。`ROUND70` §2.4 把它列为"入口句柄来源"，是把它当成客户端 API 了。
（`ROUND71` 交接文档 §5.1 已经识别出这个陷阱，但漏了"`RESOURCE_HUB_CREATE_PATH_FROM_ID` 才是客户端的正门"，于是把 `SpbTargetConnect` 的半截理解 + 硬编码设备名拼在了一起。）

## 三、❌ 蓝莓（barryblueice）项目核实：不能作为"Windows 有路"的依据

用户提供的两个项目都核实了。**结论：两个项目都不是 Windows 驱动，都没有主机触发触觉。**

### 3.1 `ESP32-Precision-TouchPad`（前代，汇顶线）

本机已存其 Wiki 全文：`<LAB>\touchpad-lab\vendor\wiki\esp32-ptp\`（39 页）

| 事实 | 一手来源 |
|---|---|
| 用 **ESP32 站在主机位置**，I²C 直连汇顶触摸板（例：`GT7863`），把触摸数据翻译成 **USB HID** 报给 Windows | `I2C-Over-HID-and-USB-HID.md`：*"our ESP32 needs to convert the I2C Over HID of ELAN to USBHID communication"* |
| 汇顶 HID 描述符寄存器地址有 **两种**：`0x01` 或 `0x20`（依据 coreboot 源码） | `About-Goodix-TouchPad.md` 第 1 行 |
| 他拿到的描述符里 **Report ID `0x0E` 是 `0xFF00` vendor 集合、64 字节 Output+64 字节 Input** | `About-Goodix-TouchPad.md` §Report ID 0E |

★ **最后一行对本项目有直接价值**：本机 Col04 的 `0x0E` 通道（`[0E 20 …]` 私有封装）**与这个描述符逐字对应** —— 交叉印证了"`0x0E` = 厂商扩展通道"这个判断是对的（[coreboot](https://github.com/coreboot/coreboot) 那条"0x01/0x20"线索也值得抄一份进本机档案）。

### 3.2 `ESP32-Haptic-Precision-TouchPad`（本代，Surface + CS40L25）

已有解析文档：`<WORKSPACE>`

| 事实 | 结论 |
|---|---|
| 同样是 **ESP32-S3 替换整机主控**（Surface Laptop Studio 1964 / Synaptics S96U7） | 硬件方案，不是 Windows 软件方案 |
| 主机侧**没有任何触觉指令**：869 B 描述符里 `0x0E`(Haptics) 出现 **0 次**（`追加十九`） | 触觉 100% 在设备端固件决定 |
| Windows 只能下发「强度 0–100 / 力度阈值 1–3」**偏好**，且是 vendor feature | 与"主机触发震动"是两件事 |
| 他逆向了 CS40L25 的 DSP 波形固件 + SAM 控制器 | 有价值的方法论，但前提是**他能改设备端** |

⇒ **蓝莓的答案是"绕开"，不是"打开"。** 他把主机侧协议整体替换掉了 —— 而这恰好是我们这台机器上做不到的那一步（OEM 模组不可编程、驱动被 `hidi2c` 占住）。

★ **他为什么说"i2c 明明很简单"**：因为在他的拓扑里，**I²C 两端都是他自己的代码**（ESP32 当 master，触摸板当 slave），**完全没有 OS 驱动参与**。我们的 I²C 里插着一个 `hidi2c.sys`，难点从来不是 I²C 协议本身，而是**谁有权在这条连接上说话**。

## 四、❌ `ty2/goodix-gt7868q-linux-driver` 核实：与交接文档的描述不符

`00-★交接文档-GXTP5100.md` 决策 3 写：

> Linux 的 `i2c-hid` **完整透传** hidraw（任意 `HIDIOCSFEATURE` 可用），不像 Windows 拦截。

**这条依据不成立。** 仓库全文已取回（`goodix-gt7868q.c` 仅 1,663 B）：

```c
static const __u8 *goodix_gt7868q_report_fixup(struct hid_device *hdev, __u8 *rdesc, unsigned int *rsize)
{
    if (rdesc[607] == 0x15) {          // 把描述符里第 607 字节 0x15 改成 0x25
        rdesc[607] = 0x25;
    }
    return rdesc;
}
```

| 项 | 事实 |
|---|---|
| 它是什么 | **`hid-multitouch` 的一个 report descriptor 修补驱动**（1 个字节） |
| 它不是什么 | 不是 I²C 驱动、不碰寄存器、不碰触觉、不做任何总线透传 |
| 设备匹配 | `HID_I2C_DEVICE(I2C_VENDOR_ID_GOODIX, 0x01E9)` / `0x01E8` ⇒ **精确匹配本机** ✅ |
| 上游同款 | [torvalds/linux c8000de](https://github.com/torvalds/linux/commit/c8000deb68365b461b324d68c7ea89d730f0bb85) `HID: multitouch: Add support for GT7868Q` |

`local-overrides.quirks` 全文（431 B，已解码）：

```
[Lenovo Thinkbook G6+ IMH - Goodix GT7868Q]
MatchVendor=0x27C6
MatchProduct=0x01E9
AttrPressureRange=2:0
AttrPalmPressureThreshold=600
AttrThumbPressureThreshold=1000

[Lenovo ThinkBook 16 G7+ IAH ForcePad]
MatchName=*GXTP5100*
ModelPressurePad=1
```

⇒ quirks 干的事是**修正压力上报范围与掌压阈值**，也**不提供任何寄存器访问**。

★ **但这里捞到一个真正有用的新线索**：后面那条 `[Lenovo ThinkBook 16 G7+ IAH ForcePad]` + `MatchName=*GXTP5100*` + `ModelPressurePad=1` 说明 ——
**Linux 社区在 GXTP5100 上是把它当"压感触控板（ForcePad）"处理的**。这暗示 GXTP5100 家族在 Linux 侧可能已有 `PressurePad` 模型，
值得查 `hid-multitouch.c` 里 `ModelPressurePad` 的消费点（**是否与触觉/力反馈路径有关**）。这是本轮唯一新增的可查线索。

## 六、★ 建议的下一步：先做那个"决定生死"的实验（零内核驱动）

`00-触控板结论总表.md` §十 第 ⑭ 项已经写清楚了，而且它是**本项目唯一能判定纯软件路生死的实验**：

> ⑭ ★★★ **在主机 `I2C0` 上探 `0x5A` / `0x5B`**（AW86927 的两种可能地址）
> 依据：`AW86927FCR` 的 I²C 地址由 `AD` 脚配置，手册 Table 3 给了两个候选值
> **有应答 ⇒ AW86927 就在主机总线上 ⇒ 主机可直接写它 ⇒ 纯软件路复活**
> **无应答 ⇒ 它在 GT7868Q 的私有总线上 ⇒ 纯软件够不到它 ⇒ 只剩方案③（HDP/HDN 外挂）**

**为什么现在就该做**：任何 Windows 内核驱动方案（无论新旧）都建立在"能触达 AW86927"这个**未验证前提**上。
先花 1–2 小时用 Linux live USB 把这个前提验掉，再决定要不要投入几天写驱动 —— 这是顺序问题。

顺带（同一次开机可完成）：

| 顺带项 | 手段 |
|---|---|
| 确认 `CA4F` 是否在主机总线 | `i2cdetect -y <总线号>` 看 `0x5A`/`0x5B` |
| 若在，直接读 AW86927 寄存器 | `i2cget`（**只读，零风险**） |
| 交叉验证 0x0E 通道 | 对比 Col04 描述符与蓝莓 Wiki 的 `Report ID 0E` 段 |
| 查 `ModelPressurePad` 消费点 | 读 `hid-multitouch.c`（纯离线） |

⚠️ 红线不变（🔴 是**四条**：`00 10`/`00 11`/**`0E 12`（真写 flash）**/**`0E 13`（重启）**）：**只读、单次 ≤ 32 B、间隔 ≥ 500 ms、绝不碰红线命令**。
