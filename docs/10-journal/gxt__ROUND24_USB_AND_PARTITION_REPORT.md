**日期**：2026-09-30

**任务**：追 `0x248B6` 上游到 USB 端点 ⇒ 确认主机能否直接触发命令
**上游**：`ROUND23_COMMAND_ENTRY_REPORT.md`

## 一、一页话结论

**追 USB 端点的过程中，发现了比端点更重要的东西：固件是分区的，我们此前分析的全部代码只占 28 KB，而真正的"主固件"是加密的。**

| 文件偏移 | 大小 | 熵 | 性质 |
|---|---|---|---|
| `0x00000`–`0x00FFF` | 4 KB | 5.09 | 厂商容器头 |
| `0x01000`–`0x18FFF` | **96 KB** | **7.95–7.99** | ★ **加密区（主固件主体）** |
| `0x19000`–`0x1AFFF` | 8 KB | 6.12–6.48 | 明文代码（含 TF100A 向量表 + 标识） |
| `0x1B000`–`0x25FFF` | 44 KB | 5.38–6.64 | ★ **明文代码（我们分析的全部内容）** |
| `0x26000`–`0x2775B` | 5.9 KB | 6.82–7.15 | 明文代码（继续） |

⇒ **此前所有分析（协议解析、16 条命令、写入封装）都落在 `0x19000` 之后的明文区**
⇒ **而 `0x19ABC` 处的 Cortex-M 向量表（`SP=0x200076C8 / Reset=0x08005164`）指向 `0x08005164`，
   即文件偏移 `0x5164` —— 那里熵 7.81，是密文** ⇒ **主程序从加密区启动**

## 二、追 USB 端点的结果：撞到了墙

### 2.1 `0x248B6` 所在的是一个"主循环"，无 BL 调用者

```
0x24820  bl 0x1AF70      ─┐
0x24824  bl 0x20838       │  依次调用各子系统
0x24828  bl 0x229D0       │  ← ★ 就是 ROUND22 里那个 0xA55A 校准函数
0x2482C  bl 0x22A04       │
0x24830  bl 0x219CC       │
0x24834  bl 0x22508       │
0x24838  bl 0x22AA4       │
0x2483C  bl 0x2320C       │
0x24840  bl 0x23254       │
0x24844  bl 0x232B8       │
0x24848  bl 0x22B30       │
0x2484C  bl 0x1EEEC       │
0x24850  bl 0x23290      ─┘
0x24854  ... 初始化
0x248B0  bl 0x1D720       ; 取报文
0x248B6  bl 0x22C7C       ; ★ 命令分派器
0x248E2  bl 0x1ACEC       ; ★ 协议解析器
0x248F4  b  0x248B0       ; ← 循环
```

### 2.2 四路搜索全部为空

| 搜索方式 | 结果 |
|---|---|
| `find_callers_of(0x24820)` | **0 个** |
| 字面量 `0x08024820` 全镜像 | **0 处** |
| 字面量 `0x08024821`（thumb 位） | **0 处** |
| MOVW/MOVT 构造 `0x08024820` | **0 处** |
| 无条件 `b` / `b.w` → `0x24820` | **0 处** |

⇒ `0x24820` **无任何静态引用**，且它前面是 `0x2481E bx lr`（一个完整函数的结尾）。
⇒ 说明它是**靠 fall-through 进入**的，即 **`0x2481E` 的 `bx lr` 执行后流程继续走到 `0x24820`**
   ⇒ 这只有在**没有返回地址**（栈顶就是入口）时才成立 ⇒ **`0x24820` 是一个"入口"，不是被调用的函数**

### 2.3 为什么静态追不到 USB 端点

**USB 端点处理不走 BL。** 典型 Cortex-M USB 栈：

- USB 中断 → **向量表 IRQ 向量** → ISR
- ISR 把数据放入环形缓冲，**置一个标志**
- 主循环（`0x24820`）轮询该标志，调 `0x1D720` 取报文 → 分发

⇒ **链路是"中断→缓冲→标志→主循环轮询"，不是"BL 链"**。
⇒ **静态 BL 扫描在此处到达方法边界**（这正是 SKILL.md 里"必须声明间接调用局限"的实例）。

### 2.4 但拿到了决定性的间接证据

`0x24820` 主循环里调用的 12 个子系统，**包含 `0x229D0`** ——
就是 ROUND22 里那个"读回 16 位与 `0xA55A` 比对"的 SPI 校准函数。

⇒ 这**独立确认了 ROUND22 的判定**：`0x40003000` 那条 SPI 链是**主循环周期性调用的校准/维护项**，
   与固件更新无关。**判定成立，且现在有了"它在主循环里"这个更强的证据。**

## 三、★★ 重大发现：固件分区（本轮真正价值）

### 3.1 逐 4KB 熵扫描（明文/密文分界）

```
0x00000   熵=5.09   ← 容器头
0x01000   熵=7.77   ┐
0x02000   熵=7.96   │
   ...     ~7.96    │  ★ 96 KB 加密区
0x18000   熵=7.95   │
0x19000   熵=7.48   ┘  ← 过渡
0x1A000   熵=6.47   ┐
0x1B000   熵=6.07   │
   ...     ~6.1     │  ★ 明文代码区
0x25000   熵=6.35   │
0x26000   熵=6.84   ┘  ← 继续，略升
```

### 3.2 明文区的证据（三条独立）

1. **能反汇编成正常 Thumb 代码**：`0x26000` 处 `sxtb.w ip,ip` / `asr.w r1,ip,#0x1f` / `cmp r1,#0` / `bge` —— 标准符号扩展序列
2. **含编译时间戳与子模块名**：`0x19ECC "TF100A_Test_FW"`、`0x19EEC "Nov 28 2023"`、`0x19F0C "19:10:59"`
3. **可见指令字节对**：`b580`(push{r7,lr}) / `4770`(bx lr) / `e7ff`(b.n)

### 3.3 `0x19ABC` 的 Cortex-M 向量表（完整解出）

| 索引 | 名称 | 值 |
|---|---|---|
| [0] | SP | `0x200076C8` |
| [1] | **Reset** | **`0x08005164`** |
| [2] | NMI | `0x0800A678` |
| [3] | HardFault | `0x08008894` |
| [4] | MemManage | `0x0800A448` |
| [5] | BusFault | `0x080053F4` |
| [6] | UsageFault | `0x0800DFE4` |
| [11] | SVC | `0x0800BE24` |
| [12] | DebugMon | `0x080053F8` |
| [14] | PendSV | `0x0800B75C` |
| [15] | SysTick | `0x0800CE7C` |
| [16..] | IRQ0.. | 绝大多数 = `0x0800517E`（默认 stub）|
| | IRQ11 | `0x08006B3C` |
| | IRQ29 | `0x0800D628` |

★ **表内所有地址 ≤ `0x0800DFE4`**
★ 而我们的明文代码在 `0x1A000`..`0x26000`，运行地址（若 `base=0x08000000`）为 `0x0801A000`..`0x08026000`
⇒ **表内地址范围与明文代码范围不重叠**
⇒ 且 `0x08005164` → 文件偏移 `0x5164` → **熵 7.81（密文）**
⇒ **结论：向量表指向的是加密区里的主程序，明文区是"另一套东西"。**

### 3.4 一个关键修正：明文区**不是**由 `0x08019000` 写入的目标

ROUND23 已纠正"28 KB 配置区"的错误。**本轮进一步确认**：

- 写入封装 `0x1B874` 的目标基址 = `0x08019000`，偏移上限 `0x7000`
- 而 `0x1B874` 自己就在 `0x1Bxxx`，**运行地址 = `0x0801B874`**
- `0x0801B874` 落在 `[0x08019000, 0x08020000)` **窗口内** ✔

⇒ **写入封装把自己的代码所在区域当作可写目标** —— 这在"固件自更新"设计里是正常的
   （bootloader 在别处，应用区可自擦写）。
⇒ 但**因为该区是代码**，改写它风险高。ROUND23 的结论**成立并加强**。

### 3.5 双核结构（更新理解）

| 核 | 归属 | 位置 |
|---|---|---|
| Cortex-M4F | 主控 GT7868Q 主程序 | **加密区 `0x1000`–`0x18FFF`（96 KB）** |
| Cortex-M4F | 明文应用/命令处理 | 明文区 `0x19000`–`0x2775B`（含 TF100A 向量表与标识） |
| Turbo51 (8051) | 触控/压力前端固件 | 此前已定位，4.6 KB |

★ **`0x19ABC` 的向量表属明文区**，其 `Reset=0x08005164` 指向密文 —— 
说明**明文区是一个"被主程序加载/校验的子镜像"**，而不是独立上电运行的程序。

## 六、★ CRC-8 的 5 个调用点：**没有一个是校验代码区的**

这是本轮对"改写会不会被检出"的决定性回答。`0x1B6E0(buf,len) = CRC-8(poly 0xA1)` 全固件**只有 5 个调用者**：

| 调用点 | 校验对象 | 长度 | 判定 |
|---|---|---|---|
| `0x1AD50` | 报文缓冲（协议解析器内） | 报文长度 | **入站报文校验** |
| `0x1B098` | 组报文缓冲 | `+1` 起 | **出站报文校验** |
| `0x1EAE6` | 组报文缓冲（`[0]=0xA2`,`[1]=0x3C`） | `0x39`=57 | **出站报文校验** |
| `0x22152` | 组报文缓冲（`[1]=0x1C`） | `0x1C`=28 | **出站报文校验** |
| `0x227B4` | `0x20006174+2` 缓冲 | 动态 | **出站报文校验** |

**逐点核实**（以 `0x1EAE6` 为例）：
```
0x1EA46  movs r0,#0xa2 / strb [r1]      ; 报文第 0 字节 = 0xA2
0x1EA4C  movs r0,#0x3c / strb [r1,#1]   ; 第 1 字节 = 0x3C
0x1EA5C  ... 循环 0x1C 次填充 [2..]      ; 组装负载
0x1EAE0  ldr r0,[sp,#0x18] / adds r0,#1 ; 起始 = 缓冲+1
0x1EAE4  movs r1,#0x39                  ; 长度 = 57
0x1EAE6  bl 0x1B6E0
0x1EAEC  strb.w r0,[r1,#0x3a]           ; 校验值写入报文尾
```
⇒ 典型的**"组包 → 算校验 → 填到包尾"**，与代码区无关。

**⇒ 结论：固件里没有任何一处用 CRC-8 校验那 28 KB（或任何 flash 代码区）。**

这意味着：
- ✅ **改写明文区不会触发本固件自身的完整性检查**
- ⚠️ 但**不能排除**：① 密文区主程序有**别的**校验机制（如哈希、签名）
  ② 主机侧驱动（Windows 上）在加载/初始化时校验固件版本或哈希
  ③ 这是"没找到"，不是"证明不存在"（静态扫描的固有局限）

## 八、方法边界（诚实记录）

**本轮追 USB 端点失败，原因是方法本身的边界，不是执行问题**：

| 尝试 | 结果 |
|---|---|
| BL 反查 | ✗ 中断入口不走 BL |
| 字面量指针 | ✗ 无 |
| MOVW/MOVT | ✗ 无 |
| 无条件跳转 | ✗ 无 |

⇒ **中断驱动 + 缓冲轮询**的架构，静态 BL 扫描必然追不到。
⇒ 必须结合：**向量表定位 ISR → 读 ISR 找工作队列 → 找队列的消费者**。
   而本例的向量表在密文区，所以这条路**在当前信息条件下不可走**。

**这是本轮最有价值的"负结论"** —— 它明确告诉后续：**不要再在静态分析上投入追 USB**。
