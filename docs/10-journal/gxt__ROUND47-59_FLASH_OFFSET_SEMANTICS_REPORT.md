## 一、★★ 重大修正：`0x1800` 写的**不是单字节**

### 1.1 旧结论（错误）

> "命令 `0x3200` → `0x1BA7C` 把**单字节** `0x1B` 写到 flash 偏移 `0x1800`。"

### 1.2 新证据

反汇编 dispatcher 中 `0x3200` 的 case（file `0x22E52`）：

```asm
0x08022E52  movw  r0, #0x4940
0x08022E56  movt  r0, #0x2000
0x08022E5A  ldr   r0, [r0]        ; r0 = 当前 report 指针 (0x20004940)
0x08022E5C  adds  r0, r0, #4      ; r0 = report + 4  ==> 数据起始
0x08022E5E  movs  r1, #0x1b       ; r1 = 0x1B
0x08022E60  bl    #0x0801BA7C
```

而 `0x1BA7C` 内部：

```asm
0x0801BA7C  push  {r7, lr}
0x0801BA7E  sub   sp, #8
0x0801BA80  str   r0, [sp, #4]     ; 存 r0
0x0801BA82  strb.w r1, [sp, #3]    ; 存 r1 (低字节)
0x0801BA86  ldr   r0, [sp, #4]
0x0801BA88  ldrb.w r2, [sp, #3]    ; r2 = r1
0x0801BA8C  mov.w r1, #0x1800      ; r1 = 0x1800  (硬编码 = addr)
0x0801BA90  bl    #0x0801B874      ; 0x1B874(r0, 0x1800, r2)
```

**`0x1B874` 的签名（逐指令确认）**：

| 栈位 | 来源 | 语义 |
|---|---|---|
| `[sp,#0x418]` | `r0` (arg0) | `src` —— 源数据指针 |
| `[sp,#0x414]` | `r1` (arg1) | `off` —— 偏移 |
| `[sp,#0x412]` | `r2` (arg2, **u16**) | `len` —— **长度** |

⇒ `0x1B874(src, off, len)`。
⇒ 而 `0x1BA7C(p_buf, len)` 把 `p_buf` 的 **`len` 字节**写到 flash 偏移 `0x1800`。

### 1.3 结论

| 命令 | 语义（修正后） |
|---|---|
| `0x1B` | **读** 27 字节(`0x1B`)：flash 偏移 `0x1800` → 回 report `0x1C` |
| `0x3200` | **写** 27 字节(`0x1B`)：report+4 的数据 → flash 偏移 `0x1800` |

> ⚠️ 是 **27 字节整块读/写**，不是单字节。原"单字节"判断来自把 `movs r1,#0x1b` 误读为数据值。

## 二、`0x1800` / `0x3800` 的内容 —— 静态镜像里**读不出来**

### 2.1 flash 库的目标地址公式

**`0x1B7B4(dst, off, len)` —— 读**（file `0x1B7B4`）：

```asm
0x0801B7BE  ldr   r0, [sp, #0xc]   ; r0 = off
0x0801B7C0  ldrh.w r1, [sp, #0xa]  ; r1 = len
0x0801B7C4  add   r0, r1
0x0801B7C6  cmp.w r0, #0x7000      ; ★ 边界检查：off+len 必须 < 0x7000
0x0801B7CA  blo   #0x0801B7D6      ; 通过
...
0x0801B7DC  movw  r2, #0x9000
0x0801B7E0  movt  r2, #0x801       ; r2 = 0x08019000
0x0801B7E4  add   r1, r2           ; ★ r1 = 0x08019000 + off
```

**`0x1B874(src, off, len)` —— 写**（file `0x1B874`，含读-改-写）：

```asm
0x0801B886  ldr  r0, [sp, #0x414]  ; r0 = off
0x0801B88A  ldrh r1, [sp, #0x412]  ; r1 = len
0x0801B88E  add  r0, r1
0x0801B890  cmp.w r0, #0x7000      ; ★ 同一道边界
0x0801B894  blo  #0x0801B8A0
...
0x0801B8A4  movw r1, #0x9000
0x0801B8A8  movt r1, #0x801       ; r1 = 0x08019000
0x0801B8AC  add  r0, r1           ; ★ 目标 = 0x08019000 + off
0x0801B8B6  lsrs r0, r0, #0xa     ; page = addr >> 10
0x0801B8C0  bfc  r0, #0xa, #0x16  ; page 内偏移
0x0801B8CC  rsb.w r0, r0, #0x400  ; 0x400 - 页内偏移
0x0801B8F4  bl   0x1B82C          ; 读一整页到栈缓冲
0x0801B8FC  bl   0x1B780          ; ★ 擦除该页
0x0801B944  bl   0x1B9C8          ; ★ 写回该页
```

**底层物理访问**：

```asm
0x1B82C(dst, page):                 ; 纯内存读（memcpy）
    addr = page << 10
    for i in 0..0x400: dst[i] = *(u8*)(addr + i)

0x1B780(page):                      ; 真 FLASH 擦除
    addr = page << 10               ; ★ 注意：没有再 +base
    0x240F0()                       ; FLASH_Unlock: KEYR(0x40022004) = 0x45670123, 0xCDEF89AB
    0x23F80(0x307)                  ; 置位
    0x23FB8(addr)                   ; FLASH_ErasePage: CR(0x40022010) |= 2 (PER); AR(0x40022014)=addr; CR |= 0x40 (STRT)
    0x23FA4()                       ; FLASH_Lock: CR |= 0x80
```

⇒ **标准 STM32 FLASH 控制器**（`0x40022000`，KEY1=`0x45670123`，KEY2=`0xCDEF89AB`）。
⇒ 目标地址 = `0x08019000 + off`，`off < 0x7000` ⇒ 可访问区 `0x08019000 .. 0x0801FFFF`（**28 KB**）。

### 2.2 ⚠️ 致命矛盾

| 事实 | 证据 | 脚本 |
|---|---|---|
| F1 | `0x08019000 + 0x1800 = 0x0801A800` → **file `0x1A800`** | ROUND47 |
| F2 | file `0x1A800` 处是**合法 Thumb-2 代码**：`08 F0 56 FF` = `bl 0x080236B0`，含完整 `push {r7,lr}` … `pop {r7,pc}` 函数 | ROUND53 |
| F3 | `0x19000..0x20000` 区被 **290 处 BL** 调用，含交叉引用自洽闭环（`0x1A8EC → 0x1A99C`） | ROUND54 |
| F4 | 该区有 **80 个** `push{...,lr}` 函数头，平均每 `0x166` 字节一个 | ROUND54 |
| F5 | 该区熵 5.4–6.5（典型明文代码） | ROUND49 |
| F6 | **`tpcfgsid*.cfg` 的标识串（`PCB\0` / `LaiBao` / `Xiaomi` / `7867` / `7986P`）在整个镜像中出现 0 次** | ROUND58 |

**⇒ `0x08019000` 区在静态镜像里 100% 是代码，不可能是可擦写的参数区。**

### 2.3 ★ 自洽解释（终局模型）

向量表位于 file `0x19ABC`（明文区），但**表项全部指向 `0x0800xxxx`**：

| 表项 | 值 | 落点 |
|---|---|---|
| SP | `0x200076C8` | RAM |
| Reset | `0x08005165` | file `0x05165` — **加密区** |
| NMI | `0x0800A679` | file `0x0A679` — 加密区 |
| HardFault | `0x08008895` | file `0x08895` — 加密区 |
| SVC | `0x0800BE25` | file `0x0BE25` — 加密区 |
| PendSV | `0x0800B75D` | file `0x0B75D` — 加密区 |
| SysTick | `0x0800CE7D` | file `0x0CE7D` — 加密区 |

⇒ **主程序运行在加密区（`0x08001000`–`0x08018FFF`，96 KB）**，该区在设备上被解密后**就地执行**。

**⇒ 推论**：`0x1B7B4`/`0x1B874` 里的 `0x08019000` 是**链接期符号化基址**，代表"一个被链接到该位置的存储段"。但：

> ★★★ **该存储段的真实内容不在 `TB14P_...BIN` 程序镜像里。**

理由（F6）：配置文件（cfg）的特征串在镜像中**零出现**，且全镜像只有 `0x00000` 一页熵 < 5.5（那还是容器头）。
⇒ `0x1800` / `0x3800` 等偏移指向的是**设备内的独立参数/校准存储区**（出厂由 cfg 单独烧录，不打包进程序 BIN）。

## 三、参数存储区的完整布局（从 caller 参数还原）

由 `0x1B7B4`（16 个 caller）与 `0x1B874`（9 个 caller）的**实际传参**还原：

| 偏移 | 长度 | 读 | 写 | 备注 |
|---|---|---|---|---|
| `0x00444` | 1 B | — | ✅ `0x1AEF4` (src=`0x200044EC+0x444`) | |
| `0x01800` | **`0x1B` (27 B)** | ✅ `0x1ABAA`（cmd `0x1B`）<br>✅ `0x22128` | ✅ `0x1AC84`（协议 type4）<br>✅ `0x1BA90`（cmd `0x3200`） | **主目标**：读-写镜像对 |
| `0x02000` | `0x444` (1092 B) | ✅ `0x22BFC` → RAM `0x200044EC` | — | 参数块 A |
| `0x02444` | 1 B | ✅ `0x1E68A` `0x1E6CA` `0x1E6F4` `0x22BDE` | ✅ `0x2190E` | 单字节标志位 |
| `0x02C00` | `0x444` (1092 B) | ✅ `0x22B5C` | — | 参数块 B |
| `0x03044` | 1 B | ✅ `0x1E670` `0x1E6B0` `0x1E6E6` `0x22B3E` | — | 单字节标志位 |
| `0x03800` | **8 B** | ✅ `0x232A6` → RAM `0x2000403C+0xA` | ✅ `0x1AC3E`（协议 type4）<br>✅ `0x1AF0A`（cmd `0x1700`） | **次目标**：8 字节块 |

**观察**：
- 三个"块"：`0x1800`(27 B)、`0x2000`(1092 B)、`0x2C00`(1092 B)
- 三个"单字节标志"：`0x444`、`0x2444`、`0x3044`
- 读-写对称：`0x1800` 与 `0x3800` 都是"可读可写"的块，其余多为只读

`0x444`（= 1092）= `0x400 + 0x44`，像是"1 KB 页 + 页内 0x44 偏移"的组合 —— 与 `0x1B874` 的 1 KB 页粒度吻合。

## 四、★★★ "只写 `0x1800`" 的风险评估

### 4.1 先纠正前提

| 原假设 | 修正 |
|---|---|
| "只写 1 个字节" | **写 27 字节整块** |
| "低风险，因为是单字节" | 单字节优势**不存在**，27 字节会覆盖整个块 |

### 4.2 风险分解

| # | 风险 | 严重度 | 说明 |
|---|---|---|---|
| R1 | **写坏固件代码** | 🔴 致命 | `0x1B874` 做的是**擦页 + 写页**（1 KB 粒度）。若 `0x0801A800` 在设备上确实是代码，擦掉那一页 = 固件损坏 = **变砖** |
| R2 | 参数块结构失效 | 🟠 高 | 27 字节若是 TLV/带校验的结构，写错会触发固件回退或初始化失败 |
| R3 | 主机侧驱动校验 | 🟠 中高 | Windows 驱动可能校验固件版本/配置哈希。已于 ROUND24 排除固件自校验（CRC-8 仅用于协议帧），**但主机侧未查** |
| R4 | 不可逆 | 🟠 高 | 擦除后原值丢失（`0x1B874` 是 read-modify-write，**先把整页读出来**——理论上原值还在，但一旦写失败就是残页） |
| R5 | 无法预演 | 🟡 中 | 该存储区**不在镜像里**，无法离线验证写前/写后差异 |

### 4.3 ★ 结论

> **不建议盲写 `0x1800`。**

理由：
1. 物理落点**无法静态确认** —— `0x08019000+0x1800` 在镜像里是代码，但设备上可能是参数区，二者矛盾未解；
2. 操作粒度是**擦页 + 写页（1 KB）**，不是"只动 1 字节"；
3. 一旦落点是代码 ⇒ 该 1 KB 页被擦除 ⇒ **固件损坏**；
4. 变砖后恢复需要官方固件重刷通路，而**该通路尚未打通**（ROUND24 已确认主机无法直接触发写入；`0x40003000` SPI 路径是校准回写，非固件传输）。

### 4.4 若要继续，**最低风险**的前置动作（按优先级）

| 优先级 | 动作 | 目的 | 风险 |
|---|---|---|---|
| ★★★★★ | **先用 cmd `0x1B` 读回 27 字节** | 看内容长什么样：若像 cfg（有 magic / 可读字符串 / 低熵）⇒ 是参数区；若像机器码 ⇒ 是代码区 | 零风险（只读） |
| ★★★★ | USB 抓包，观察 `0x1B` / `0x3200` 的实际流量 | 确认命令真的被固件接受（有 ACK/回 report `0x1C`） | 零风险 |
| ★★★ | 读回后**与 `tpcfgsid*.cfg` 做结构对比** | 判断 27 字节是不是某个 cfg 字段 | 零风险 |
| ★★ | 找官方固件刷新通路（Dell DUP / Goodix 工具） | 建立"变砖可恢复"的安全网 | 需先找到工具 |
| ★ | 仅在①②③全部通过后，考虑写入 | | 高 |

> **红线依旧**：禁批量轮询 Col04；≤2 往返/秒；刷机三连 `00 10 / 00 11 / 0E 12` 绝不碰。

## 六、方法论沉淀（已并入 skill）

1. **"地址被引用" ≠ "该处是数据"** —— 必须反汇编验证。
2. **用 BL 目标密度判定区域性质**：数百处 BL + 自洽交叉引用 + 函数头间距均匀 ⇒ 铁定是代码。
3. **"偏移"必须确认是相对谁的** —— `cmp` 在 `add base` 之前，说明比较的是**偏移**（此教训已于 ROUND23 记录）。
4. **边界检查值 `0x7000` 的作用**：限定可访问窗口 = `base + [0, 0x7000)`，可据此推出参数区大小。
5. **静态镜像 ≠ 设备运行时布局** —— 需要用向量表落点、cfg 特征串出现次数等**交叉证据**判断"某段是否在镜像内"。
6. **单字节写入的"低风险"幻觉**：底层实现是"擦整页 + 写整页"时，单字节写入的粒度优势完全消失。**必须看到最底层的擦写实现才能评估风险。**
