> 触发：喆说「我不信破不了这个 GT7868Q，绝对是你在哪里有漏洞」。
> 结论：**喆是对的。漏洞已定位，且是根因级错误。**
> 但同一轮里也**首次拿到三件套**：官方明文固件 + 官方容器格式 + 官方配置表。
> 日期：2026-09-30（第十五轮）

## 〇、一句话结论

| 项 | 结论 |
|---|---|
| A③「常量填充段泄漏 K」 | ❌ **判据错误**。那段不是「明文全 0 的常量填充」，而是**固件里原样存放的 K 表副本**。`0 ⊕ K = K` 的前提（明文=0）不成立。 |
| `GT7868Q_plain.bin` | ❌ **不是明文固件**。它是「原文 + 被 XOR 打成零的 K 副本段」的混合物。 |
| XOR 算术本身 | ✅ 正确、可复现（`raw[i] ^ K[i%1024]` 在 `[0x1200,0x19800)` 上 0 误差）——**算术对，语义错**。 |

## 一、漏洞的完整证据链

### 1.1 致命观察：K 表以 0x400 步长重复出现在固件自身里

```
raw = GT7868Q_native_fw.bin  (161,628 B)
K   = GT7868Q_scramble_key.bin (1024 B)

raw[0x8800 : 0x8C00] == K   ✔ 完全相等
raw[0x8C00 : 0x9000] == K   ✔
raw[0x9000 : 0x9400] == K   ✔
raw[0x9400 : 0x9800] == K   ✔（0x9800 起为 partial）

且 0x8800 > 0x1200  ⇒  K 副本位于所谓「加扰区」内部，却是明文。
```

**这一步已经自证矛盾**：如果 `[0x1200, …]` 真的整段被加扰，那 `0x8800` 处不可能原样等于 K（除非加扰对这一段恰好是恒等映射）。

### 1.2 那些"零"全部来自自异或

```
plain[i] = raw[i] ^ K[i % 1024]
若 raw[i] == K[i % 1024]  ⇒  plain[i] == 0
```

程序化验证（`raw` 中 K 循环片段出现 2645 处）：

| raw 位置 | 相位 | plain 该处内容 |
|---|---|---|
| 0x3670 | 624 | 全 0 ✔ |
| 0x3674 | 628 | 全 0 ✔ |
| … | … | 全 0 ✔ |
| 0x36a0 | 672 | 前 28 字节 0，第 29 字节起非 0（此处 K 副本只到边界） |

**⇒ 所谓「14816 个零 / 5 KiB 连续零串」= K 副本被打成零，不是「解出了零填充」。**

### 1.3 我此前引以为"铁证"的两条，恰恰是同一个错误的两个面貌

| 曾当作"证据" | 实际含义 |
|---|---|
| 「常量填充段 1024 自相关 = 1.000000」 | 该段是**周期 1024 的重复表**（K 本体），不是"明文全 0" |
| 「`0 ⊕ K = K`，密文直接等于 K」 | 前提错了：那段明文**本来就是 K**，不是 0 |
| 「GT9896 与 GT7868Q 的 K 只差旋转 316」 | 因为 K 是 **Goodix 通用数据表**，不是逐机密钥 |
| 「六条判据 V1–V6 全过」 | 判据里最强的一条（零计数）本身被 K 副本污染 |

### 1.4 修正后的判据（写进 SKILL）

> **禁止用「解出零的多少」作为解扰正确性的主判据**，当密钥候选来自数据自身时尤其危险。
> 必须改用：**「解出的结果是否与已知明文样本同构」**——
> 头部字段、子固件表、段地址/长度、ASCII 标识、表结构。
> 零计数只能作为**辅助**，且必须先扣除「密钥副本位置」。

## 六、给未来的自己

1. **别把「数据自身的重复」当成「密钥泄漏」。**
   判据必须是"解出的东西**长得像什么**"，不是"解出多少个零"。
2. **先找明文样本，再谈破密。**
   本轮真正救场的不是算法，是 `tpfw.bin` —— 一份躺在手里、明晃晃写着 `PNOR_G1` 的官方明文固件。
   如果早点读它的头部，整条 A③ 弯路都可以省掉。
3. **官方源码里的格式定义，比任何自己推的格式都强。**
   `flash_addr(2)<<8` 这条注释，直接让我一次解对了 11 条记录。
4. **喆说"你哪里有漏洞"时，先假设他是对的，然后去找反例。**
   本轮从"怎么可能错"到"找到 2645 处 K 副本"，用了不到 20 分钟。
