## 一、先纠正一个预期：**"装机通电"的信息量其实很低**

| 事实 | 推论 |
|---|---|
| 白名单在 **DXE 引导期**判定，拒绝则 `ADR0` 落占位地址（`0xFF`） | ACPI 交给 OS 的 I2C 从机地址就是错的 |
| 地址错 ⇒ I2C-HID 读不到描述符 | **Windows 与 Linux 都一样** —— 设备根本不在总线上 |
| 因此 | **装机通电只能回答"过 / 不过"这一个二元问题**，读不到描述符、读不到任何地址空间、拿不到任何字节 |

**★ 但这不等于不该装。** 仍建议做一次，理由有三：
1. 它是**决定性的**（我们目前对 PID 只有 ~90% 把握，`0x01EA` 的来源没有逐条回溯 —— 见 `追加二十七` §四）
2. 它能**排除 §3.4 的成因 (b)**（本机未提供 ResetGpio / 上电延时，而 X9-15 模组需要复位才吐描述符）—— 若装上后**能**用，说明成因是 (b) 而非白名单
3. 成本只有一次拆机，且完全可逆

**⇒ 但真正能拿到数据的是下面两条路。**

## 二、三条路线（按性价比排序）

### 🥇 T1 — 零硬件、最高性价比：**向 X9-15 机主要数据**

项目里已经有过 X9-15 用户的 dmesg（`0018:27C6:01EB.0001`），说明**渠道是通的**。需要的是一个很短的清单：

| # | 要什么 | 怎么取（对机主来说很简单） | 为什么关键 |
|---|---|---|---|
| **a** | ★★★ **原始 HID 描述符（十六进制）** | Linux 一条命令：`sudo cat /sys/kernel/debug/hid/0018:27C6:01??.0001/rdesc > rdesc.txt` | **这是"一个有扳机的 GXTP5100 长什么样"的完整答案** —— 直接看到 `0x0E/0x21`(Manual Trigger) 在不在、落在哪个 report ID、以及 **PID 真值** |
| b | 同机 dmesg 全文 | `dmesg \| grep -iE "27c6\|goodix\|haptic\|i2c"` | 确认枚举路径与 PID |
| c | 全量 HID caps | 在 X9-15 上跑项目现成的 `poc/AllCaps.cs` + `dump-all-caps.ps1`（.NET、纯只读） | 与本机那份 caps 逐报表对照 |
| **d** | ★★ **抓包：手指滑动/按压时录一段** | Linux `hid-recorder`，或 Windows USBPcap；**关键是要录到"滑动时震动"那一刻** | ★ 看**主机到底往哪个 report ID 写了什么** ⇒ **主机触发报文的完整格式** |

**★ 为什么 (d) 特别重要 —— 它推翻了一个既有判定的前提：**
`追加二十六` §五 把「伪造描述符骗 Windows」判为 ❌，理由之一是「**发给设备的报文格式未知**（固件加密）」。
**⇒ 一旦拿到 X9-15 的抓包，报文格式就已知了。**
**⇒ 那么这个 ❌ 需要降级为 ⚠️：格式已知，剩下唯一未知是"本机那份固件认不认这套报文"。** 这是一个**新的、可证伪的假设**，比原来的判断更接近可实验。

### 🥈 T2 — 离线 I2C（需要硬件，但一次投入长期可用）

**为什么必须离线**：白名单拒绝 ⇒ 设备不在总线上 ⇒ **本机 Windows 侧永远读不到它**。要读这块板子，只能自己在 I2C 上跟它说话。

**原理**：协议项目已经全解出来了 —— `0x4014`(VER) / `0x4160`(CMD) / `0x96F8`(CFG)，5 字节命令帧 `{cmd,param,0,0,cksum}`，4 字节对齐单块读。

| 步 | 动作 | 期望/判据 |
|---|---|---|
| 1 | 确认排线针脚定义（VCC / GND / SDA / SCL / INT / RST）与**电平**（1.8V 还是 3.3V —— 必须先测） | 针脚错了会烧板 |
| 2 | 上电 → 读 `0x4014` | 期望明文 **`YELSTO`** + 型号串（本机那块自报 `7869`）⇒ 确认同族 |
| 3 | **读描述符寄存器 `0x20`（模块本来的描述符寄存器）** | ★ **不用装机就能拿到 PID 与完整 HID 描述符** —— 与 T1(a) 同源 |
| 4 | 读配置区 `0x96F8` 段 | 与本机那份对照（本机基线/标定表已知） |
| 5 | **尝试读固件区** | ★★ **核心判据：X9-15 这份是【明文】还是【ECB 密文】？** |

**★★ 第 5 步是整个计划的胜负手：**
- 若**明文** ⇒ 项目苦寻不得的"明文镜像"到手，**而且正好是带主机扳机的那一份** ⇒ 可直接差分出扳机代码
- 若**密文** ⇒ 与 `追加二十五` §⑤ 的 ECB 结论一致，项目主线结论进一步加固（也是有效结果）

**参照资料（项目已有）**：`vendor/wiki/esp32-ptp/`（有人用 ESP32 做过 PTP 触控板，I2C-HID 时序可复现）· `re/i2c_isr.py` · `poc/gdix-hid-fw/gtx9_gtx9_i2c_update.cpp`

**⚠️ 离线也一样要守的红线**：
```
① 绝不发刷机三连：{00 10} / {00 11} / {0E 12}
② 先读后写；任何写之前先备份
③ 共地、电平匹配（1.8V/3.3V 先测再接）
④ 不要拿本机【原装】模块当第一只白鼠 —— 这块 X9-15 的板子本来就是研究耗材
⑤ 断电重上电 = 离线环境下的"复位"（比在本机上安全得多，不会牵连整机）
```

### 6.2 ⚠️⚠️ **H-假设（待检验）：X9-15 到底有没有"主机扳机"？**

**本项目从 `追加二十六` 起就沿用一条前提：「X9-15 把扳机开放给主机，本机没有」。**
**本轮新证据显示这条前提很可能被过度采信了 —— 它的原始依据只是社区评论在谈"马达大小"，从未被独立验证。**

**新证据（均为公开、可复核）：**

| 来源 | 原文 |
|---|---|
| libinput 上游 commit `7030dc7c8d5d73ea1f3bd7f79c793f79b3889e6e` | 「a quirk for **ThinkPad X9-15 Gen1** to **detect GXTP5100 as pressure pad**」 |
| Launchpad Bug 2108966（`[SRU] Correct ThinkPad X9-15 Gen1 Touchpad Functionality`） | 「**No mouse movement HID reports are sent from the touchpad for ThinkPad X9-15 Gen1**」 |
| Fedora 论坛用户给出的 quirk 注释 | 「# The ThinkPad X9 15 Gen 1 **Forcepad touchpad is not detected as a pressure pad**」 |
| Deepin 论坛帖（作者实机 ThinkBook 16 G7+ IAH） | 「GXTP5100 的固件在 HID 描述符中**没有正确声明自己是"压力感应板（Force Pad）"**…上游 libinput 已为部分机型（**ThinkBook 14 G7+ IAH、ThinkPad X9-15** 等）添加了 quirk」 |

> ## **⇒ X9-15 的 GXTP5100 描述符**连"压力板"这一层都没有自洽声明** —— 与本机是**同一个毛病**，上游要专门打补丁才能让指针动起来。**
> ## **⇒ 那么「X9-15 有主机扳机」这条前提，**目前没有任何直接证据支持**。**

**⚠️ 但必须把话说到位（不越界）：**
- 「描述符没声明压力板」**不等于**「没有主机扳机」—— 压力板分类（libinput 层）与 **OUTPUT report 里的触发用法**是两件事，前者不蕴含后者。
- 所以正确表述是：**H 假设待检验**，而不是「X9-15 也没有」。

**★ 若 H 被证伪（即 X9-15 其实也没有主机扳机），后果很大：**
```
项目 §五 里「换 X9-15 模块 = 参照系」这个说法要作废 ——
它就不再是"有扳机的那一类"，而只是"马达更好、其余相同的同一类板子"。
⇒ 「换模块」这条路**从一开始就不可能带来主机扳机**，与白名单无关。
```
**★ 最廉价的检验方法**：拿到 X9-15 的原始描述符（`cat /sys/kernel/debug/hid/0018:27C6:01??.0001/rdesc`），看有没有 `0x0E/0x21`。**一条命令即可定论** —— 这也让 T1 的价值重新上升。
**★ 次便宜的方法**：读 libinput 那条 commit 的完整 diff（`gitlab.freedesktop.org` 有 Anubis 反爬，用镜像/GitHub 镜像取）。

### 6.3 ★★ 同 PID 家族：`0x01E9` 到底覆盖哪些机型（**含一处更正**）

**★ 先说清这份"候选清单"是干什么的**：它服务于「**换一块模组**」这条路。一块替换模组必须**同时过两道门**：

| 门 | 要求 | 现状 |
|---|---|---|
| **门 1 · 门禁** | PID 落在本机 BIOS 白名单 `{0x01E8, 0x01E9}` | 只要 PID 对上就自动满足 |
| **门 2 · 能力** | 该模组**真的把扳机交给主机** | ⚠️ **目前没有任何模组被证实过**（见 `§6.2` 的 H-假设） |

> **更正**：本节目初稿写「ThinkBook **14/16 G7+ IAH** 也是 `27c6:01e9`」。逐条回溯来源后：
> **16 G7+ IAH 有直接证据；14 G7+ IAH 只是推断；而那段话里的 ThinkPad X9-15 属于"同问题清单"（同样需要打 quirk），不是同 PID（它是 `01EA`/`01EB`）。原文的并列方式已修正。**

| 证据等级 | 机型 | PID | 来源 |
|---|---|---|---|
| **硬证据** | ThinkBook 14 G6+ IMH（**本机**） | `27C6:01E9` | 项目实测 |
| **硬证据** | **ThinkBook 16 G7+ IAH** | `i2c:27c6:01e9` | Deepin 帖首行（作者实机） |
| **硬证据** | ThinkBook 14+/16+ 2024（Ultra 9 185H） | `27C6:01E9` | Launchpad `2093390`（多用户；comment 25 的 quirk 以该设备名匹配） |
| **推断** | ThinkBook 14 G7+ IAH | 推测同为 `0x01E9` | 与 16 G7+ IAH 同代同系列，**无直接证据** |
| **✗ 不属于这一族** | ThinkPad X9-15 | `0x01EA` / `0x01EB` | §6.1 |

> ## **⇒ 关键：`0x01E9` 覆盖的都是「ThinkBook 同代 GXTP5100 压力板」——所谓"扩容"，实质是把本机同代/同系列的兄弟机型补全，
> ## **而不是发现了新的、能力不同的板子。**

**★★ 而且这条线反过来加强了 H-假设的「证伪倾向」：**

```
已知的所有 GXTP5100 机型（01E9 / 01EA / 01EB）全都落在同一个 bug、同一个症状里 ——
「固件在 HID 描述符中没正确声明自己是压力感应板」，上游要逐机型打 quirk。
⇒ 这是【家族性行为】，不是某个机型的个案。
⇒ 「X9-15 有主机扳机、本机没有」这句话越来越可疑：
   同一家族、同一描述符缺陷 ⇒ 更可能是「都不给主机扳机」，
   而「X9-15 震动更明显」被误读成了「X9-15 主机可触发」。
```

**★★★ 由此得出一条优先级修正：**

> ## **当前第一优先不是「收集更多候选机型」，而是「把 H 定下来」。**
> ## **而 H 最廉价的判定方式，恰恰就在已经排好的第 1–2 步里 ——**
> ## **我们手上就有 X9-15 的实物：只要 I2C 通道跑通，直接读它的描述符寄存器 `0x20`，
> ## 一次就能拿到 X9-15 的完整描述符 ⇒ H 当场定案。**
> ## **⇒ 第 2 步（拆机读板）的价值因此比我先前估计的更高：**
> ## **它不只是"看固件是明文还是密文"，还能**直接定 H** —— 而 H 是当前最大的未知。**

**★ 措辞修正（2026-09-29 再补）**：我把它写成"候选清单扩容了"，**容易读成"问题有戏了"，这是不准确的**。必须说清：

| | 我实际扩容的是 | 我们真正需要的是 |
|---|---|---|
| 内容 | **"能被本机 BIOS 接受并初始化"** 的模块清单 | **"把主机扳机交给主机"** 的模块 |
| 性质 | **必要条件** | **充分条件** |
| 扩容是否有意义 | 只扩大了"物理/兼容上可用"的池子 | **没有增加任何一个"带扳机"的样本** |

**★★ 更关键的是：同 PID 通常意味着同固件家族 ⇒ 这一族很可能一样不给扳机。**
**⇒ 所以 §6.3 这条线索的真正用途是「取证对照」，不是「换板解决问题」：**
1. 它是检验「`0x01E9` 族能力是否恒定」的**对照样本**（若 14+ 2025 也不带扳机 ⇒ 强化 H-假设）
2. 它是**"同 PID、不同固件版本"的入口** —— 若能拿到它的固件更新包，就多一份可差分镜像

**★ 物理可行性补充（本轮新查）**：ThinkBook **14+ 2025**（认证型号 `ThinkBook 14 G7+ IAH`，机型 `21TK…`）
- **机箱 322 × 228 × 15.9 mm**，与本机 `323 × 228 × 15.9 mm` **几乎完全一致**
- 高配版（Ultra 7 255H / Ultra 9 285H / Ryzen AI 9 365）**确实配 Forcepad 全域感知压力玻璃触控板**
⇒ **这一条的物理可行性远强于 13x Gen 4（13 寸板装不进）** —— 但如上表，它只解决了"必要条件"。
**⚠️ 未查**：14+ 2025 的触控板**具体尺寸**（是否也是 80 × 135）—— PSREF 未直接给出，需查其 HMM 或实体测量。

### 6.3b ★ 「伪造 PID 骗过 BIOS」的五条路（2026-09-29 补）

**先分清"骗谁"** —— 三个对象、时机不同，混起来必然得出错误结论：

| 骗谁 | 时机 | 现状 |
|---|---|---|
| **BIOS 的 DXE 白名单** | 引导期 | 见路线 A / B / C |
| **BIOS 的"结论"（那个地址）** | 启动后 | ★ 见路线 D |
| **OS / Windows** | 运行期 | ❌ **无效**，见路线 E |

> ## **★ 最关键的一条澄清：白名单被拒的后果**不是**"BIOS 说了句不准"，而是
> ## **BIOS 不往 ACPI 资源模板里写地址 ⇒ 落占位 `0xFF` ⇒ 设备在 OS 层面**根本不存在**。**
> ## **⇒ 任何"在 Windows 里伪造"都不解决问题（DXE 在 OS 之前，§15.2 已定）。要骗，只能在总线层骗。**

#### 路线 A —— 改 X9-15 模块固件里自报的 PID（`0x01EA` → `0x01E9`）

- **逻辑最自洽**：不改 BIOS、不改主板，只让模块"报一个白名单里的号"。过了门 1，能力仍是模块自己的（门 2 = H）。
- **瓶颈在回刷**：官方刷机工具**主机侧零变换**（原样 `memcpy`）⇒ 必须喂"已加扰"的镜像 ⇒ **若 X9-15 固件是明文，我们改完那两个字节却没法重新加扰回去。**
- ⇒ 它的前提正好是第 2 步要测的那件事（**明文性**）。**先测，再决定 A 值不值得。**

#### 路线 B —— 总线中间人（MITM）：真正的"伪造"

在**模块与主板之间**插一颗 MCU（Pico / RP2040 的 PIO 最合适，ESP32 次之）：

- 面向主板一侧做 **I2C 从机**（**必须支持 clock stretching**），面向模块一侧做 **I2C 主机**
- 透明转发所有读写，**只把描述符应答里的两个字节 `0x01EA` → `0x01E9`**
- ⇒ BIOS 读到白名单内 PID ⇒ **过门 1**；OS 后续读写照旧转发

| | |
|---|---|
| **优点** | 不改固件、不刷 BIOS、**完全可逆** |
| **难点** | 400 kHz 时序余量 · 双向桥 + clock stretching 的工程量 · INT 线要转发 · **桥得塞进机身（空间）** |
| **★ 前置离线工作（必做）** | 反汇编 `bios\out\GoodixTpDxe.asm.txt`（本地已有，6,859 行），**确认 PID 究竟从哪个缓冲区的哪个偏移取** ⇒ 决定"改几个字节、在什么位置"。**不确认就上桥 = 盲改。** |

#### 路线 C —— 改 BIOS 里那一字节

- DXE 不在 Boot Guard 的 IBB 验签范围内 ⇒ **理论可行**（§15.4）
- 但需 SPI 编程器 + 拆机 + 重算 FFS/FV 校验 + 变砖风险，且只对这一台有效 ⇒ **已判不建议**（§15.5）

#### ★★ 路线 D —— 不伪造 PID，而是**让 BIOS 的错误结论失效**（ACPI / DSDT 覆盖）

**本轮新想到的一条，也是我最看好的：**

- BIOS 拒绝的**实际后果只是"地址落占位 `0xFF`"**；而 ACPI 里 `Device(TPAD)` 与 `TPID` 表是**静态存在**的 ⇒ **可以覆盖 DSDT，把占位行的地址强行改成 `0x2C`**
- **Linux 下做起来很干净**：项目已有 DSDT 与 `re/dsdt-*.py` 工具，且有 `iasl` 可重编译 ⇒ 走 initrd 做 ACPI override ⇒ **纯软件、完全可逆（撤掉 initrd 即恢复）、零刷写**
- **它骗的不是 PID，而是"BIOS 没写地址"这件事** ⇒ **不依赖任何固件/白名单改动**
- **未知**：设备是否需要 BIOS 的复位/上电（成因 b）—— **而这个未知正好由第 1–2 步回答**：

> ## **★★★ 逻辑链**：
> ## **若第 2 步的 `i2c-dev` 能读到 `0x4014`=`YELSTO` 与描述符（`0x20`）**
> ## **⇒ 说明模块在 `0x2C` 上活着，BIOS 的"拒绝"只是没写地址**
> ## **⇒ 那么「DSDT 覆盖把地址钉成 `0x2C`」就能让它在 Linux 下真正工作。**
> ## **⇒ 而"能用"的那一刻，同时回答了门 2（H-假设）：跑 `dump-all-caps` 看有没有 `0x0E/0x21`。**

#### 路线 E —— 在 OS 里伪造描述符

❌ **无效**：设备根本不在总线上（地址 `0xFF`），OS 里做什么都影响不到引导期判定（§15.2 已定）。

#### ★ 一条值得顺手确认的疑问

`GoodixTpDxe` 在白名单**通过之后**会置一个"已识别"标志（`mov byte ptr [rsp+0x30], 1`）。**这个标志位到底 gate 了什么？**

- 若只是"继续初始化" ⇒ 白名单只管门 1
- ★ **若它还 gate 了"把设备切到某个模式"（例如打开某个功能），那么白名单就同时管着门 1 和门 2** ⇒ **"伪造 PID" 就有双重价值，值得认真做**
- ⇒ **可离线查**：反汇编 `GoodixTpDxe.asm.txt` 里所有读 `[rsp+0x30]` 的地方

#### 裁定表

| 路 | 骗谁 | 纯软件？ | 可逆？ | 卡点 | 判断 |
|---|---|---|---|---|---|
| A 改模块固件 PID | BIOS | 部分（需刷模块 flash） | 否 | 明文性 + 回刷加扰 | ⏳ 等第 2 步结果 |
| **B 总线中间人** | BIOS | 硬件桥接 | ✅ | 时序/工程/空间 + **PID 来源需先反汇编确认** | 🥈 可做但重 |
| C 改 BIOS | BIOS | ❌ 需 SPI 编程器 | 否 | 变砖风险、只对这一台有效 | ❌ 不建议 |
| **D DSDT 覆盖** | **BIOS 的结论** | ✅ **是** | ✅ **是** | 设备是否需 BIOS 复位（成因 b） | 🥇 **最值得先试** |
| E OS 内伪造 | OS | — | — | 设备不在总线上 | ❌ 无效 |

> ## **⇒ 结论：能"骗"，但最划算的不是伪造 PID，而是**路线 D** ——
> ## **不去改设备的自报值，而是让 BIOS 那句"我不认这块板"失效。**
> ## **⇒ 而 A / B / D 全都建立在同一个前提上：门 2（H-假设）。**
> ## **⇒ 所以顺序不变：先把第 1–2 步做完，别先上硬件。**

### 6.3c ★ 「Linux 下做的事，Windows 会不会生效？」——**分三层看，只有两层能跨系统**

> **一句话：❌ 不会。** Linux 侧的动作里，**只有下沉到「设备层」或「固件层」的改动才对 Windows 生效**；
> **所有 OS 层的改动（包括路线 D 的 DSDT 覆盖）Windows 完全看不到。**

| 层次 | 我们要做的动作 | Windows 侧会不会生效 |
|---|---|---|
| **OS 层（只读）** | `i2c-dev` 直接读寄存器 / 描述符 | ❌ 看不见。**而且读取本来就谈不上"生效"—— 它只是拿数据** |
| **OS 层（内核态）** | `unbind` i2c 驱动 · `libinput` quirk / `local-overrides` | ❌ 一律看不见；unbind 还只在当次启动有效 |
| **OS 层（ACPI）** | ★ **路线 D：initrd 做 DSDT 覆盖** | ❌ **完全看不到** |
| **设备层** | ★ **路线 A：刷模块 flash 改 PID** | ✅ **生效，且与操作系统无关** |
| **固件层** | 路线 C：改 BIOS 的 DXE | ✅ 生效（代价 = 刷写） |

#### 为什么 ACPI 覆盖不跨系统

```
ACPI 表的"所有权"在【操作系统】手里 —— 每个 OS 启动时自己去 UEFI 取表（或用自己的覆盖文件）
Linux 的 initrd ACPI override 只是【替换内核内存里的表】，连固件都没写进去
   ⇒ 这正是它"可逆、零风险"的原因
   ⇒ 也正是它"只对 Linux 生效"的原因
Windows 侧【没有受支持的 ACPI 表覆盖机制】
   （已知做法都要靠内核级补丁 / 测试签名，且随系统更新失效）
```

> ## **⇒ 结论：路线 D 是"研究验证"的好工具（能回答"这块板到底活不活"），**
> ## **但不是"交付手段"。**

#### 那 Windows 上真要能用，只有三条

| # | 做法 | 跨系统 | 代价 |
|---|---|---|---|
| 1 | ★ **把改动下沉到设备层** —— 路线 A：刷模块 flash 把 PID 改成 `0x01E9` | ✅ **唯一"改一次、Win+Linux 都生效"** | 前提：X9-15 固件明文 + 解决"重新加扰回刷" |
| 2 | **把改动下沉到固件层** —— 路线 C：改 BIOS 的 DXE | ✅ 且能同时改掉门 1 与**可能的门 2** | 需 SPI 编程器、变砖风险 |
| 3 | **写一个 Windows 内核驱动**，绕开 ACPI 直接在 I2C 总线上枚举 `0x2C` 并挂 HID | ✅ 纯软件 | 驱动开发 + 测试签名，工程量最大；★ 但**最符合项目原本的诉求（"完全以程序的方式"）** |

**⚠️ 一条未验证的线索**：UEFI 有 `driver####` 变量机制，可让固件在 BDS 阶段加载额外驱动 ⇒
**理论上能"不刷 BIOS 就往固件层注入"**（由该驱动 patch ACPI 表，从而对 Windows 也生效）。
**但联想是否启用该机制未知，未验证，只作备查。**

#### 对所有已做/将做动作的"持久性"盘点

| 动作 | 是否改动持久状态 |
|---|---|
| `i2c-dev` 读取 | ❌ 纯读，零状态改变 |
| `unbind` i2c 驱动 | ❌ 仅当次启动，重启即恢复 |
| `libinput` quirk / `local-overrides` | ❌ 只是 Linux 用户态文件 |
| initrd ACPI 覆盖 | ❌ **不写固件**，撤掉即恢复 |
| Goodix 厂商命令写入（`追加二十六` §12/§13） | ⚠️ 只碰易失寄存器，重启恢复；**但 `0x30/0x31` 曾把固件卡住** |
| 刷模块 flash | ✅ **永久**（跨 OS） |
| 刷 BIOS SPI | ✅ **永久**（跨 OS，风险最高） |

> ## **⇒ 实用推论：第 1–2 步（Linux 下的研究）全程不会改动机器任何持久状态 ——
> ## 做完之后 Windows 侧一切如常，可以放心做。**
> ## **⇒ 但它也不会替你解决问题：验证归验证，交付归交付。**

### 6.3d ★★ 「写一个 Windows 内核驱动」具体意味着什么（2026-09-29 补）

**要解决的问题**：Windows 侧**没有 ACPI 声明的连接，就没法碰这块板**。
Windows 的 I2C 客户端栈（SPB 框架：`SpbCx` + `iaLPSS2_I2C`）里，**"到哪个从机地址、用多快速度"这些连接参数统统来自 ACPI 的 `_CRS`** —— 而 BIOS 拒绝时写的正是 `0xFF` 占位。**⇒ 所以驱动要干的第一件事，就是自己把"地址"造出来。**

#### 三个阶段（成本递增，别一步跨到最贵）

| 阶段 | 做什么 | 要不要写驱动 | 成本 |
|---|---|---|---|
| **3a 探路** | 用 WDK 自带的 **`SpbTestTool`**（或同类 SPB 客户端工具）**从用户态**对控制器发裸传输，看能不能碰到 `0x2C` | ❌ **不用** | 低 —— **先做这个，能省掉 90% 的无用功** |
| **3b 最小驱动** | 写一个 KMDF 驱动：**绕过 SPB 框架、直接操作 LPSS 控制器的 MMIO**，只做 I2C 裸传输（暴露 `DeviceIoControl` 给用户态） | ✅ | 中 —— 几百行 + INF + 签名 |
| **3c 完整交付** | 在 3b 上再加：I2C-HID 协议解析（描述符/输入/输出报告）→ **VHF（Virtual HID Framework）** 造一个虚拟 HID 设备 → **让 Windows 认成 Precision Touchpad** | ✅ | **大 —— 这是个驱动子项目，不是周末活** |

**★ 架构（3c）**：
```
自写内核驱动 → I2C 控制器(LPSS) → 模块 @0x2C → 解析 I2C-HID 报告
                                                     ↓
                                        VHF 提交虚拟 HID 报告
                                                     ↓
                                        Windows 认成 Precision Touchpad
```

#### 真实代价（逐条）

1. **工具链**：WDK + Visual Studio，编 x64 驱动
2. **★ 签名与安全启动**：自用要 `bcdedit /set testsigning on` —— **而 Secure Boot 开启时这条命令会被系统拒绝**（"protected by Secure Boot policy"）⇒ **必须关掉 Secure Boot**。想保留 Secure Boot 就得走 **EV 证书 + 微软签名**（要花钱、要提审）。
3. **内核态风险**：驱动 bug = **蓝屏**。I2C 时序写错可能让系统反复蓝屏。
4. **工程量**：3c 的四个模块（I2C 客户端 / I2C-HID 解析 / VHF 桥接 / 电源管理 + INF 安装）**缺一不可**。
5. **Windows 更新**：大版本升级后测试签名状态可能需要重新确认。

#### ★★★ 但它真正解决了什么 —— 以及真正解决不了什么

| | 内容 |
|---|---|
| **能解决** | ① 让设备**在 Windows 上活起来**（白名单、描述符、Manual Trigger **全部绕过**）<br>② **拿到一个不受 HID 描述符约束的底层通道** —— 因为 I2C-HID 报告是**我们自己解析的**，要发什么输出报文、要读写哪个寄存器，**完全自由** |
| **❌ 不能解决** | **门 2：设备固件里到底有没有"震"的入口。** 驱动只能在 I2C 上说话，**它无法凭空让固件震**。若固件没有触发入口 ⇒ 得到一个"能滑动、能点击、但不会滑动震动"的触控板 ⇒ **和现在的原装板一样** |

> ## **⇒ 关键判断：路线 3 的"研究版本"和"交付版本"要分开看 ——**
> ## **① 如果你要的只是"一个不受 HID 层限制的读写通道"（用来找阈值、扫寄存器、发厂商命令），
> ## 那么 Linux 下 `i2c-dev` 就完全够用 —— 零驱动、零签名、零 Secure Boot 改动、零蓝屏风险。**
> ## **② 只有当你确认"门 2 成立 + 要在 Windows 上日常使用"之后，
> ## 才值得开这个驱动子项目。**
> ##
> ## **⇒ 所以：现在不要写驱动。先做第 3a 步（零成本探路），再按第 1–2 步把门 2 定下来。**

**★ 一句话总结路线 3 的定位**：
> **它是"交付手段"，不是"研究手段"。而研究阶段的一切需求，Linux `i2c-dev` 已经覆盖。**

### 6.3e ★★ 「网上那些删联想 BIOS 白名单的教程」逐类核对（2026-09-29 补）

> 缘起：喆说网上有不少删联想 BIOS 白名单的教程。
> **结论：能借的是「方法论」，不能照搬「步骤」；而且从中挖出一条比刷 BIOS 安全得多的新路。**

#### 一、那些教程到底在做什么（成分分析）

**绝大多数是「WLAN 网卡白名单」**（报错 `1802: Unauthorized wireless network card`），扫的是同一类东西：联想自己的 **`LenovoWmaPolicyDxe`** 这个 DXE 模块。按机型分两代：

| 代 | 代表做法 | 覆盖机型 | 对本机 |
|---|---|---|---|
| **xx30 及更早** | **`1vyrain`（n4ru）** LiveUSB 漏洞链，**免拆机**刷入，顺带解锁 Advanced 菜单 | **仅 X230 / X230t / T430 / T430s / T530 / W530** | ❌ 完全不适用 |
| **Haswell 及以后** | **1vyrain 明确不支持** ⇒ 只能 **CH341A 编程器 + SOIC8 夹子**离线 dump → patch → 刷回 | T440p / W540 / T540 起 | ⚠️ 方法论可借，步骤不可照搬 |
| 各种"博客教程" | 「进 BIOS 找白名单选项关掉」/「关 Secure Boot 就行」 | — | ❌ **纯噪声**：我们的白名单**不在 setup 里**（§11.2 已证） |

> **⇒ 关键认识：联想用「专用 DXE 模块」实现白名单是**惯用手法**——
> 网卡是 `LenovoWmaPolicyDxe`，我们的是 `GoodixTpDxe`。目标模块换了，**方法同源**。**

#### 二、★ 方法论的核心一招（对我们直接可用）

参照 **`github.com/mytbk/firmware_notes` → `tp-uefi-whitelist-removal.md`** 那套通用做法：

```
① UEFITool 打开固件，搜硬件 ID → 定位到那个 DXE 模块
② 在该模块的 PE32 image section 右键 Extract body，导出成独立的 .efi
③ 改指令（原作者的做法：把模块【入口点】改成 ret(0xC3)，让整个模块失效）
④ UEFITool replace body → Rebuild → 另存
⑤ 刷入
```

**⇒ 我们的等价做法（更精准，别整个废掉）：**

| | 改法 | 效果 | 改动量 |
|---|---|---|---|
| ❌ 不推荐 | 把 `GoodixTpDxe` 入口改 `ret` | 整个模块失效 —— **但它可能还负责触控板的上电/复位/初始化，废掉可能设备根本不工作** | 1 字节 |
| ✅ **方案 1（推荐）** | 把那段**恒跳**（`xor eax,eax` / `test eax,eax` / `je 0x5ed0`）改成**不跳** | ★ **恢复厂商原本的宽松检查** `(PID & 0xFFF0) == 0x1E0` ⇒ **整个 `0x01E0–0x01EF` 家族都能过** | 1–2 字节 |
| ✅ 方案 2 | 把 `cmp eax, 0x1e9` 改成 `cmp eax, 0x1ea` | 精确放行 X9-15 那块 | 1 字节 |

> ## **★ 重要视角转换：这不叫"删白名单"，叫"恢复出厂设计"。**
> ## **厂商后来把宽松检查改成了死代码（§15.1），我们只是把它改回去。**

#### 三、刷进去的路径（按风险）

| 路径 | 拆机 | 风险 | 备注 |
|---|---|---|---|
| **CH341A + SOIC8 夹子离线刷** | ✅ | 中 | 社区标准做法。⚠️ **但现代 ThinkBook 的 flash 可能是 WSON8（无引线，夹子夹不住）或 BGA（要拆焊）** ⇒ **先看清封装** |
| **软件刷**（`FPTW64` 等热刷） | ❌ | 高 | 老教程称成功率约 65%；**前提是 BIOS 区未被锁** ⇒ **必须先查 SPI 写保护状态** |
| **不刷**（见下面第四节） | ❌ | **低** | ★ 本轮新发现 |

**★ 软件刷的前置判据（零风险，可直接测）**：
- **`BIOS_CNTL`**（LPC/eSPI 配置空间偏移 `0xDC`）：**bit0 `BIOSWE`** / **bit1 `BLE`** / **bit5 `SMM_BWP`**
- 若 `BLE = 0` 且 `SMM_BWP = 0` ⇒ 主控端可写 ⇒ 软件刷有戏；`BLE = 1` ⇒ 只能离线编程器
- 另需注意 Flash Descriptor 的 `FLMSTR` 是否给了 BIOS 区写权限

#### 四、★★★ 本轮新发现：一条「不刷固件、却**跨系统生效**」的路

**思路来源**：UEFI 生态里 **`EfiGuard`** 这类项目就支持 **「用 UEFI Shell `load EfiGuardDxe.efi`」** 来加载自写驱动 ——
**说明「从 Shell 加载未签名 DXE 驱动」在关掉 Secure Boot 的机器上是可行的。**

**由此得到的路**：
```
关掉 Secure Boot（BIOS setup 里就有，无需刷写）
   ↓
从 U 盘启动进 UEFI Shell
   ↓
load 一个自写的小 EFI 程序
   ↓
由它在内存里把 ACPI 表（DSDT）中 TPID 占位行的地址 0xFF 改成 0x2C，并重算校验和
   ↓
OS（Windows 与 Linux 一视同仁）随后读到的是改过的表
```

| | 说明 |
|---|---|
| **✅ 跨系统** | 因为它改的是 **OS 启动前内存里的 UEFI 配置表** ⇒ Windows 同样读到改后的结果（这正好补上 §6.3c 的缺口） |
| **✅ 零变砖** | **不写 flash** ⇒ 断电/重启即恢复 |
| **✅ 每次开机自动跑** | 用 **`bcfg driver add`** 把驱动写进 **`driver####` NVRAM 变量** —— ★ 这正是 §6.3c 里标为"未验证"的那个机制，**`bcfg` 就是它的标准操作入口** |
| ⚠️ 未知 1 | 关掉 Secure Boot 后固件是否仍强制验签（通常不验，需实测） |
| ⚠️ 未知 2 | DSDT 所在内存（EFI ACPI Reclaim）是否可写 |
| ⚠️ 未知 3 | 以后每次固件/BIOS 更新后需重新确认 |

> ## **★★ 为什么它比"改 `GoodixTpDxe`"更值得先试：**
> ## **`GoodixTpDxe` 的判定在 DXE dispatch 时就跑完了，从 Shell 阶段改根本来不及；**
> ## **而 ACPI 表是 **OS 启动时才被读取**的 ⇒ 来得及。**
> ## **⇒ 所以"内存改 ACPI 表"是时序上唯一站得住的引导期方案 —— 而且它连 flash 都不碰。**

#### 五、不管走哪条路，都该先做的 4 项零风险检查

| # | 检查 | 为什么 |
|---|---|---|
| 1 | **看 flash 封装**（是 8 脚 SOIC 可夹？还是 WSON8 / BGA？） | 决定"离线编程器"这条路的可行性上限 |
| 2 | **查 SPI 写保护状态**（`BIOS_CNTL` 的 `BIOSWE`/`BLE`/`SMM_BWP`） | 决定"软件刷"有没有戏 |
| 3 | ★ **关掉 Secure Boot，进 UEFI Shell，试着 `load` 一个自制小程序** | **一举验证"第四条路"是否可行**，零成本、零风险 |
| 4 | 确认 **Boot Guard 状态** | IBB 若被验签，改 SEC/PEI 必死（DXE 不受影响）；项目此前**没能证实**是否启用（§15.3） |

#### 六、我的建议

> ## **② 若第 3 项可行 ⇒ 优先走"UEFI Shell 内存改 ACPI 表"：跨系统、零变砖，而且够用。**
> ## **③ 只有需要永久固化、且接受变砖风险时，才考虑刷 SPI。**
> ##
> ## **⚠️ 但请注意：这一切仍然**不回答门 2**。**

### 6.3f ★★★ 第四条路的深挖：机制证实 + 找到要改的字节 + **一处必须更正的判断**（2026-09-29 补）

> 喆问「第四条路到底如何」。本轮做了三件事：**验证载体、定位要改的字节、检验项目原有判断**。
> **结论：路成立、载体成熟、字节已定位到——但"改哪一处"还需要一步反编译才能定案。**

#### 一、载体验证：OpenCore 的 ACPI 引擎正好干这件事（源码级）

OpenCore 的 ACPI 流水线（`OcLoadAcpiSupport`）：

```
AcpiInitContext   ← 从 UEFI 系统配置表找 RSDP
AcpiFindRSDP
OcAcpiDeleteTables
Quirks 预处理
OcAcpiPatchTables  ← ★ 二进制 Find/Replace（支持 Mask/ReplaceMask/Count/Skip/Limit/TableSignature/OemTableId/Base）
OcAcpiAddTables
AcpiApplyContext   ← ★ 重建 RSDT/XSDT、重算全部校验和、更新 UEFI 配置表
"UEFI Configuration Table Updated"
```

**⇒ 三个关键点全部对上我们的需求：**
1. **"不修改闪存里的原始固件，而是在内存中把整套表复制一份、改写后再把 RSDP 指向新副本"** ⇒ **不写 flash、重启即恢复、零变砖**
2. **`AcpiApplyContext` 重算全部校验和** ⇒ 解决我们唯一担心的技术细节
3. **更新的是 UEFI 配置表 ⇒ 所有操作系统一视同仁** ⇒ **跨系统生效**（补上 §6.3c 的缺口）

**⚠️ 但载体选择只有一个答案 —— 必须用 OpenCore，不能用 Clover：**
> Clover 的官方迁移文档明确写着 **「Clover does not inject ACPI Tables in Windows」** ⇒
> **Clover 的 ACPI 补丁只对 macOS 生效，对我们完全没用。**
> **而 OpenCore 恰恰相反：它对所有 OS 一视同仁 —— 这正是我们要的，也正是它副作用的来源。**

#### 二、定位要改的字节：**已找到**（本机 DSDT，`bios\out\DSDT-528KB.bin`）

**`TPID` 厂商表在 DSDT 中的位置：`0x70455`–`0x704DA`**（`Name(TPID, Package(5))`，5 行）

#### 三、⚠️⚠️ **必须更正的一处项目判断**

> **原文（`追加二十六` §3.2）**：「`TPDS(列, 值A, 值B, 默认)` = 查表函数（**本 DSDT 内无调用者** ⇒ 逻辑分散在 SSDT）」
>
> **实测（本轮）：`TPDS` 在 DSDT 里出现 4 次 —— 1 处方法定义 + 2 处调用点**，全部 32 张 ACPI 表里**没有任何 SSDT 含 `TPDS`/`TPID`**。

**两处调用点（0x7056F / 0x705D2）：**
```
TPDS 0A 03 0A FE TPDF 0D "MSFT0001" 00    →  TPDS(3, 0xFE, TPDF, "MSFT0001")
TPDS 0A 04 0A FE TPDF 0D "PNP0C50"  00    →  TPDS(4, 0xFE, TPDF, "PNP0C50")
```

**★★★ 这两行改变了一个判断**：
- `TPDS` 调用时传的第 4 个参数是**默认字符串**（`"MSFT0001"` / `"PNP0C50"`）⇒ **`TPDS` 返回的是 HID/CID 字符串，不是地址**
- 同一族还有一串兄弟方法名（`TPLT / TPLM / TPLB / TPLH / TPLS / TPDT / TPDM / TPDB / TPDH / FPTT / FPTM / WTVX / WITX / GPTD / GDBT / UTKX / SPTD`，名单在 `0x83EF` 附近）⇒ **地址与描述符寄存器由其中另一个方法给出**
- ⇒ **若地址也是"带默认参数的调用"给的（像 `TPDS` 一样），那要改的是【调用点上的默认值】，而不是 TPID 表里那一行。** 两者都仍在 DSDT 内、都能 patch，**但偏移完全不同**。

> ## **⇒ 所以"改哪个字节"这一步**还没定案** —— 不能想当然地改占位行。**
> ## **⇒ 但定案成本很低：用 `iasl -d` 反编译 DSDT，把这批 `TPD*/TPL*` 方法族读成可读 ASL，几分钟就能看出地址的真实来源。**
> ## **这一步**纯离线、零风险、不需要拆机、不需要装任何东西到本机**。**

### 6.3g ★ 术语澄清：「能用」有三层，前面几节混用了（2026-09-29 补）

> 喆问：「这个'能用'是指绕过白名单吗？用就是和普通压感触控板一样用是吧？」
> **答：不完全是。必须拆成三层 —— 绕白名单只解决第①层的一半，且第③层完全未被这条路覆盖。**

| 层 | 含义 | 由什么决定 | 第四条路能解决吗 |
|---|---|---|---|
| **① 被系统认出** | 设备出现在设备管理器 / `/dev/input`，Windows 认成 Precision Touchpad | ①a **OS 能不能拿到 I2C 地址**（白名单只影响这个）<br>①b **模块在 `0x2C` 上是否活着并应答描述符**（= 成因 b，取决于 BIOS 有没有做复位/上电） | ✅ 能解决 ①a<br>❓ ①b 未知 |
| **② 基本功能可用** | 指针滑动、点击、双指滚动、手势正常 | ①+ **中断线打通**（本机 `SBFG` 硬编码引脚 182，同一根主板走线，预期没问题）+ 报告链路正常 | ✅ 预期能解决 |
| **③ 触觉行为** | ★ **按下震不震、震感如何、能不能"滑动跟随震"** | ★★ **完全由 X9-15 模块自己的固件决定 —— 与绕白名单无关** | ❌ **完全未定**（= H-假设） |

#### ★ 所以两句话回答

**Q1：「能用」= 绕过白名单吗？**
> **不是。**「绕白名单」只解决 **①a（让 OS 拿到地址）**。
> 真正的"能用"还要 ①b（模块得应答，这是**从没验证过**的成因 b）+ ②（中断与报告链路）。

**Q2：「用」= 和普通压感触控板一样用？**
> **半对，而且这个说法本身正好暴露了问题。**
> - 若指「能滑能点、被认成 PTP」⇒ **大概率可以**（前提 ①② 成立）
> - **但"和普通压感触控板一样用"根本不是目标** —— **本机原装那块本身就是"普通压感触控板"**。
>   如果换过去只是"一样用"，**等于什么都没换到**，还白折腾了绕白名单。

> ## **⇒ 必须把「准入」和「能力」彻底分开：**
> ## **「绕过白名单」解决的是**准入**（这块板能不能被接纳）；**
> ## **「会不会震、震成什么样、能不能滑动跟随震」由**模块固件**决定，与绕白名单毫无关系。**
> ## **⇒ 极端情况下可能发生：白名单完美绕过、板子完美工作、体验让你觉得"和原来差不多"。**

#### 一处需要修正的旧说法（顺带）

`追加二十七` §三 曾写「换 X9-15 模块 ⇒ 执行器不同（TapSense vs 本机小 LRA）⇒ 驱动参数不匹配」。
**这个说法只在"只刷固件不换板"的场景成立。整体换模组时，驱动电路与执行器是同一套、自洽的 ⇒ 不存在参数不匹配问题。**

#### ⇒ 因此路线选择应当按"你要哪一层"来分

| 你要的 | 该走哪条 |
|---|---|
| 让这块 X9-15 板子**在你机上正常工作**（研究/体验/收藏） | 第四条路（OpenCore DSDT 覆盖）或改 BIOS —— 可逆、零变砖，值得做 |
| 让触控板**滑动时跟随震动**（项目原始目标） | ❌ **绕白名单完全不保证** ⇒ 必须先把 **H-假设** 定下来（读它的描述符 `0x20`） |
| 只是"能用" | ⚠️ **根本不用换板** —— 原装那块本来就能用 |

### 6.4 ★★★ **T2' 路线被公开数据证实可行：一台笔记本就够，不需要额外硬件**

**Fedora 论坛那位用户的 dmesg 给出了完整的总线路径：**
```
input: GXTP5100:00 27C6:01EA Touchpad as
  /devices/pci0000:00/0000:00:19.1/i2c_designware.4/i2c-4/i2c-GXTP5100:00/0018:27C6:01EA.0001/input/input5
```
**拆解：**
- 控制器 = **`i2c_designware`（Intel LPSS）→ `/dev/i2c-4`** ⇒ ★ **这些板子在 Linux 下表现为一个常规 I2C 控制器**，而 `i2c-dev` 能把 `/dev/i2c-N` 暴露给用户态
- HID 设备名 `0018:27C6:01EA` 里的 **`0x18` = `BUS_I2C`** ⇒ 确认是 I2C-HID（不是 USB-HID，没有 USB 抓包的可能）

> ## **⇒ 关键洞察：本机 BIOS 的白名单**只影响它往 ACPI 资源里写什么地址**，它**不阻止 Linux 从用户态直接对 I2C 总线上的 `0x2C` 从机地址说话**。**
> ## **⇒ 所以「离线读这块板子」**不需要 ESP32、不需要逻辑分析仪 —— 只需要这台笔记本 + 一个 Linux live。**
> ## **⇒ 而且一次拆机能同时做完两件事：① 看它到底能不能被枚举（验证成因 a/b）② 用 `i2c-dev` 直接读它。**

**T2' 具体步序（下一步真正要做的）：**

| # | 动作 | 命令 / 判据 |
|---|---|---|
| 1 | U 盘做 Linux Live（Ubuntu 24.04+ / Fedora 41+，内核 ≥6.12 对这些机器支持好） | — |
| 2 | 拆机换模块（**只接排线、不上螺钉**） | 见 `追加二十七` §8.2 |
| 3 | 开机进 Live，加载 `i2c-dev` | `sudo modprobe i2c-dev; sudo i2cdetect -l` 找 **DesignWare/LPSS** 那条 → 得到`/dev/i2c-N` |
| 4 | 扫总线看 `0x2C` 在不在 | `sudo i2cdetect -y -r N`；**在 = 模块已上电且在听；不在 = 模块未被释放复位（成因 b）或排线问题** |
| 5 | ★ **读 `0x4014`（官方 VER 地址）** | `sudo i2ctransfer -y N w2@0x2c 0x40 0x14 r4@0x2c` → 期望 **`YELSTO`**；⚠️ **字节序两个方向都试**（`0x40 0x14` / `0x14 0x40` —— 项目在 §14.5 记过这个陷阱） |
| 6 | 成功后读 `0x4160`(CMD) / `0x96F8`(CFG) → 再读 flash | 与 `追加二十三` 的官方地址表一致 |
| 7 | ★★ 核心判据：**固件区读出的是明文还是 ECB 密文？** | 见 §二 T2 第 5 步 |

**⚠️ T2' 红线（离线也一样）：**
```
① **只读**。绝不 i2cset 到任何未知寄存器 —— 尤其 {00 10} / {00 11} / {0E 12} 刷机三连
② 先做第 4 步（探测）再做第 5 步（读数），不要跳步
③ 若第 4 步扫不到 0x2C，先复插排线；仍扫不到 ⇒ 记录为"成因 b 成立"，这是**有效结论**不是失败
④ 整个过程 Windows 侧零改动、BIOS 零改动 ⇒ 无变砖风险
```

- [ ] 尺寸实测（确认 135 × 80）
- [ ] **排线金手指数 / 座子型号**（与拆下来的原装排线并排比）

**★ 为什么这步排第一**：它是唯一"免费"的信息，且 **Flash 型号直接决定后面能走哪条路** ——
**若模块用的是外置 SPI Flash（如 SOP-8），就多出第三条更狠的路：拿 CH341A 夹子直接读 flash（约 ¥20–30），完全绕过 I2C 协议栈**。

### 第 1 步 · ★★ **先在本机原装模块上把 I2C 通道跑通**（关键前置，**不拆机**）

```bash
sudo modprobe i2c-dev
sudo i2cdetect -l                        # 找 i2c_designware(LPSS) 那条 → 得到 /dev/i2c-N
# 从内核手里接管触控板（方法来自 Deepin 帖，现成可用）
echo i2c-GXTP5100:00 | sudo tee /sys/bus/i2c/drivers/i2c_hid_acpi/unbind
sudo i2cdetect -y -r N                   # 期望看到 0x2C
sudo i2ctransfer -y N w2@0x2c 0x40 0x14 r4@0x2c    # 期望 YELSTO；不行就试 0x14 0x40
```

| 结果 | 含义 | 走向 |
|---|---|---|
| 读到 `YELSTO`（或 `00 87 00 00`） | **通道成立** —— 项目**第一次拿到不经过 HID 层的原生 I2C 底层通道** | ⇒ 第 2 步值得做 |
| 读不到 | 先排查：控制器选错 / 字节序 / 忘了 unbind | 仍不通 ⇒ **别拆机**，直接升级到「外置 USB-I2C」或「夹 Flash」路线 |

**★ 为什么必须在原装板上先做**：这是**零成本的前置条件验证**。如果连**被 BIOS 正常支持的**原装模块都读不到，换上去那块更不可能读到 —— 这一步能救下一次白拆机。

**⚠️ Live 环境注意事项**：**别跑 fwupd**（或 `DisabledPlugins=goodixtp`）—— 已知该插件会周期性探测触控板并**造成 I2C 通信超时**（华为 MateBook X Pro 案例：`i2c_hid_acpi … device returned incorrect report (255 vs 14 expected)`）。

### 第 2 步 · 拆机一次，把 X9-15 那块接上，重复第 1 步的命令

- 只接排线、**不上螺钉、不贴 jig**
- 期望 `YELSTO` ⇒ 通道打通 ⇒ 依次读 `0x4160` / `0x96F8` / 配置区 / **固件区（明文 or ECB 密文 = 胜负手）**
- 若扫不到 `0x2C` ⇒ **「成因 b（缺 ResetGpio）成立」= 有效结论**，不是失败
- 顺手把 `追加二十七` §8.3 的 A / B / C 也判了（Windows 侧是否枚举）

### 第 3 步 · 零成本公开线索（可与 0–2 并行）
