# ⑤ Col02 feature 读取通了吗？+ ① I2C 收发函数（换策略后）—— 2026-09-28

## 一、⑤ Col02 的 737 字节 feature：**读通了**（但内容与 RID 无关）

### 1.1 关键突破：**write-only 句柄上 GET_FEATURE 可用**

项目此前记录：「Col02 `rid=11` 能写、**读回恒 `err=122`**」。
本日实测：**用 `GENERIC_WRITE` 打开 Col02（共享模式 3），`HidD_GetFeature` 可以成功返回数据** —— 关键在于**缓冲要给足**：

| 缓冲长度 | RID=2 | RID=6 |
|---|---|---|
| 8 / 64 / 737 | 8/64/738 全 ✓（返回 2 字节） | 64 ✘ `err=87`；**737 ✓** |

⇒ 之前 `err=122` 很可能是**缓冲长度不匹配**（请求的 RID 声明长度与实际不符），不是"设备不支持读"。

### 1.2 全 RID 空间扫描结果（0–255）

| RID | 结果 |
|---|---|
| **2** | ✔ 返回 **2 字节**：`02 15`（载荷 `0x15` = 21） |
| **6 / 7 / 9 / 11 / 12 / 13** | ✔ 全部返回**同一份 257 字节**（报告 ID 字节 = `06` + 256 字节数据） |
| 其余 | ✘（`err=1` 未声明 / `err=87` 参数错） |

### 1.3 ⚠️ 重要保留：**读到的内容与请求的 RID 无关**

用 0xEE 预填缓冲做测试，各 RID 的返回**逐字节完全相同**（`md5 = 7c5e4ea95f57…`，257 字节被写入、其余 481 字节保持 0xEE）：

```
RID=2   → 02 15 EE EE EE …            （只写 2 字节）
RID=6/7/9/11/12/13 → 06 FC 28 FE 84 40 CB 9A …  （同一份，写 257 字节）
```

而项目文档记载这些 RID 的**声明长度各不相同**（`rid=6`=256 / `rid=11`=66 / `rid=12`=736 / `rid=13`=4）。
⇒ **在当前句柄下，读取不是按 RID 定向的** —— 很可能是 HID 类驱动在 write-only 句柄上把请求路由到同一个 feature 页面。**所以"读到了什么"这件事本身还不能与"某个 RID 的语义"绑定。**

### 1.4 那块 256 字节数据的性质

| 指标 | 值 |
|---|---|
| 长度 | 256（= RSA-2048 的字节数，可疑） |
| 熵 | **7.216** / 唯一字节 167（256 字节随机数据的期望唯一数 ≈ 162） |
| 递增/递减序列 | **0 段** |
| ASCII 串 | 无有意义串（4 处碎片全是巧合） |
| 全零区段 | 无 |
| 三次连读 | **内容完全一致**（稳定，非随机挑战） |

⇒ 判读：**高熵、稳定、无结构** ⇒ 更像**密钥/证书/签名**（例如 FMP 更新用的 RSA-2048 材料），**不像参数/配置表**。
（对照：真正的参数表应有可读的数值分布或重复模式。）

### 1.5 ⑤ 的结论与下一步

- ✅ **"Col02 feature 读不出来"这条已被推翻** —— 用 write-only 句柄 + 足够大的缓冲可以读
- ⚠️ 但**要拿到"某 RID 的语义数据"，得先解决"读不按 RID 定向"**：可行办法是**临时禁用触控板设备**（让 PTP 驱动松手），再用**读写句柄**按各 RID 的声明长度精确读取；或走 Linux `hidraw`
- 已有素材：`col02_feature_256B.bin`（256 字节 blob）、`col02_feature_rid2_full.bin`

## 二、① TF100A 的 I2C 收发函数：换策略后**仍未定位**（诚实记录）

### 2.1 换的策略与结果

| 策略 | 结果 |
|---|---|
| 用"4 KB 块解码覆盖率"筛出"可信代码" | ❌ **判据失效**：Thumb-2 按 2 字节步进几乎任何字节都能解出**某种**指令，14 个块覆盖率全是 0.98–1.00 ⇒ 无法区分代码/数据 |
| 搜 I2C 状态轮询惯用法（`ldr rX,[rY,#0x14]` + `lsls … #0x1f/#0x1e/#0x19` + 条件跳转） | ❌ **0 处命中** ⇒ 该固件不是这种写法（可能用 `tst/ands` 或中断/DMA 驱动收发） |
| 列可信代码内的 `str rX,[rY,#0x10]`（DR 写） | 87 处（候选太多，需逐个看上下文） |

### 2.2 ① 的现状（准确版）

- **已定位**：`I2C_Init`@`0x0800FA20`（写 CR2.FREQ / CCR / TRISE）、总线复位@`0x08008A4C`（PE-toggle）、引脚/字段访问层@`0x0800FC20/FC44/FC80`
- **未定位**：真正的收发函数（基址走 r0，所以"常量扫描"无效；两种启发式均失败）
- **可靠的下一步**：把 **BSP 区块 `0x0800F000–0x08011000` 整段按函数读完**（它是连续的可执行块，且已确认包含 I2C_Init 与 EC/GPIO 抽象），从 `I2C_Init` 的调用者与相邻函数入手 —— 这条比继续找"模式"稳，但要花一整轮逐条阅读
- **顺带更正**：昨日称 `0x08012154`"不是代码（rodata）"——**依据不充分**（我的覆盖率判据无效）。事实是**该地址处反汇编不通顺**，但镜像尾部是否含数据段**仍待定**

### 2.3 ② 维持降级结论

TF100A 侧只有载波参数（200/400 Hz、~35% 占空比），回调只是计数器，未找到运行时"开 PWM 段"的站点 ⇒ 包络/pattern 极可能由加密的 TP 侧逐次下发。

# 追加：⑤ 提权读取的结果（2026-09-28 18:0x，设备已禁用/驱动已释放）

> 第一次提权运行**失败**（我的脚本两个 bug：不存在 API `SetupDiGetClassInstallParams`；设备过滤误命中 `intc816&col02`）。已修复后重跑成功。
> 结果目录：`tp-hid/col02-precise/`

## 1. 关键结果：**RID 6 / 7 / 12 返回的数据逐字节相同**

| RID | 请求缓冲 | 结果 | 有效字节 | md5 |
|---|---|---|---|---|
| 2 | 2 | ✔ | 2 | `16104fa33bec` |
| 6 | 257 | ✔ | 257 | `1e11b3f2a0e1` |
| 7 | 257 | ✔ | 257 | `1e11b3f2a0e1`（**与 6 完全相同**） |
| 12 | 737 | ✔ | **只有 257** | `7c5e4ea95f57`（前 257 字节 = 同一份） |
| 9 / 11 / 13 | 声明长度 | ✘ | — | 未成功 |

**三条硬事实**：
1. **RID 6 == RID 7 == RID 12（前 257 字节逐字节相同）**
2. **RID 12 请求 737 字节，设备只回 257 字节**：缓冲 257..736 段**全为我预填的 `0xEE`**（非 0xEE 计数 = 0）⇒ 设备实际只提供 **256 字节数据 + 1 字节报告 ID**
3. RID=2 是另一个独立的 2 字节 feature：`02 15`（数据 `0x15` = 21）

**⇒ 判定：该集合上设备实际只提供「报告 ID=06，256 字节」这一个 feature 页；多个 RID 指向同一份内容（别名）。**
项目文档里"`rid=11`(66 字节) / `rid=12`(736) / `rid=13`(4)"是**描述符里声明的长度**，与设备实际返回不一致。

## 2. 那 256 字节是什么（本轮新增判据）

| 判据 | 结果 |
|---|---|
| 熵 | 7.216；唯一字节 167（256 随机字节期望 ≈162） |
| 结构 | 无递增段、无 ASCII、无全零段、无 ASN.1 DER 头（非证书） |
| **末字节** | `0xC2`（**偶数**）⇒ **不是 RSA 模数**（模数必为奇数） |
| 稳定性 | 同一值反复读一致（非挑战/随机数） |
| **与本地文件的比对** | 在**触控板原生固件 / BIOS 主固件 / isflash 容器 / 电池 capsule / DSDT** 中**全部 0 命中**（前 16 字节、前 32 字节、整块） |

**⇒ 判读：设备独有的高熵、稳定、无结构数据；不是本地任何固件的片段 ⇒ 最可能是「签名 / 密钥材料 / 设备唯一随机数据」**（例如固件签名、或以之为密钥派生材料）。**不是**参数表、不是校准数据（那类通常有结构）。

## 3. 仍未定 + 下一步

- **RID 9 / 11 / 13 与其余 RID（0..24）在"给足 737 缓冲"下能否读**——首轮只按"声明长度"试过它们，结论不完整
- 已把脚本升级为 **全 RID 扫描（RID 0..24 × 缓冲 {2, 257, 737}）**，并记录"有效数据长度"与 md5 ⇒ **再跑一次即可拿到完整 RID 地图**
- 若某个 RID 能返回**不同**内容（尤其短小的值），那才是"可读/可写的配置面"；目前只有 RID 2（1 字节 = 0x15）符合"小参数"特征

# 追加二：全 RID 扫描结果（设备禁用下）—— ⑤ 的最终结论

> 脚本：`tp-hid/col02_precise_read.py`（已升级为 RID 0..24 × 缓冲 {2,257,737}）· 结果：`tp-hid/col02-precise/`

## 1. 完整 RID 地图（设备已禁用、驱动已释放）

| RID | 缓冲 2 | 缓冲 257 | 缓冲 737 | 实际返回 |
|---|---|---|---|---|
| **2** | ✔ `02 15` | ✔ 只写 2 字节 | ✔ 只写 2 字节 | **固定 2 字节：`02 15`** |
| **6 / 7 / 9 / 11 / 12 / 13** | ✘ | ✔ 257 字节 | ✔ 257 字节（其余保持缓冲原值） | **全部返回同一份 256 字节页**（md5 `1e11b3f2a0e1` / 737 缓冲时 `7c5e4ea95f57`） |
| 0–5 / 8 / 10 / 14–24 | ✘ | ✘ | ✘ | 不接受 |

## 2. 三条确定结论

1. **Col02 的 feature 读面已被穷尽**：只有
   - **一个 1 字节页（RID 2 = `0x15`）**
   - **一个 256 字节页（RID 6/7/9/11/12/13 全部指向它）**
2. **读数据不按 RID 区分** —— 在驱动释放（设备禁用）后依然如此 ⇒ **这是设备/固件的行为，不是 Windows 驱动缓存**（首轮用 write-only 句柄时怀疑是驱动，现已排除）
3. **项目文档里 `rid=6`(256) / `rid=11`(66) / `rid=12`(736) / `rid=13`(4) 的"声明长度"与设备实际返回不符** —— 设备只回 256 字节

## 3. 对项目既有结论的影响（需要复核的一条）

- 项目把 **`rid=9` 认定为 Haptics Intensity**（并据此做过 6 次写入实验）。
  **本日实测：读 `rid=9` 返回的是那份 256 字节页，不是 1 字节强度值**。
  ⇒ 两种可能：**① 写入（SetFeature）按 RID 路由、读取不按**（本日未做写测试，无法排除）；**② `rid=9` 的认定需要复核**。
  ⇒ **Col02 里唯一的"小参数"是 RID 2（1 字节 = 0x15 = 21）** —— 若要验证写入语义，应同时对 RID 2 与 RID 9 做"读-改-读"对照（写入后立刻读回看是否变化）。
- 那块 256 字节仍是**设备独有的高熵稳定数据**（熵 7.216、非 RSA 模数、非证书、与本地 5 个固件/容器比对全 0 命中）⇒ 最可能是**签名/密钥材料**，不是参数表。

## 4. ⑤ 的最终状态

| 项 | 状态 |
|---|---|
| 能否读 Col02 feature | ✅ **能**（write-only 句柄；或禁用设备后读写句柄均可） |
| 读到的内容 | **一个 256 字节页 + 一个 1 字节页（RID 2）** |
| 有没有"隐藏配置面" | **没有**（RID 读不区分、其余 RID 不接受） |
| 剩余未知 | 写入语义（SetFeature 是否按 RID 路由）—— 需一次"读-改-读"实验 |

# 追加三：⑤ 的收口（含方法论错误的自认）

> 第二次提权运行输出：`[1/4] 禁用设备 … 失败(err=87)`（`cbSize` 修正后错误码由 1784 → 87，说明参数结构对了一半，但仍被系统拒绝）。

## 1. 我这条方法**根本上错了**

**「禁用设备以释放驱动，然后读 feature」是不可行的**：
- 禁用 HID 子设备的**同时也会停掉 HID 类驱动**，而 **HID 类驱动正是 `HidD_GetFeature` 的传输通道** ⇒ 禁用后**根本读不到**
- 实测佐证：两次运行里禁用都失败，但**句柄始终可打开**（`access=0x40000000`）—— 设备一直没被真正停掉，所以前几轮读到的始终是"经过驱动的正常读"

⇒ **我此前"禁用设备后再读以区分设备/驱动行为"的设计，从根上站不住**。已放弃该路径。

## 2. ⑤ 的最终结论（带明确的不确定性标注）

| 事实 | 置信度 |
|---|---|
| **通过 write-only 句柄可读 Col02 feature**（缓冲需 ≥ 该集合最大 feature 长度） | 高（实测） |
| **RID 2 → 固定 `02 15`（1 字节）** | 高（多次一致） |
| **RID 6/7/9/11/12/13 → 同一份 256 字节页**（内容逐字节相同） | 高（多次一致） |
| **其余 RID（0–5/8/10/14–24）不接受** | 高 |
| 该页是**设备独有、高熵、稳定**数据（非 RSA 模数 / 非证书 / 与本地 5 个固件容器 0 命中） | 高 → 判为**签名/密钥类材料** |
| **"多 RID 同一页"是设备行为还是驱动缓存** | **未定**（区分手段不可行，见 §1；但 HID 类驱动通常**不缓存** feature，倾向"设备侧别名"） |
| **RID 2 改值写入不反映到读回** | **未定**（写返回 True；可能写入生效但无读镜像，也可能被忽略。项目当年是**按行为**验证 rid=9 生效的：写后力度确实变化 ⇒ 说明写入**能**生效） |

## 3. 对项目的净贡献

- **推翻**旧记录「Col02 feature 读回恒 `err=122`（不支持读）」⇒ **能读**，关键是**缓冲给足 737**
- **新增**完整 RID 地图：**一个 1 字节页（RID 2）+ 一个 256 字节页（6 个 RID 别名）**，无其它 feature 面
- **提示复核**：项目认定的 `rid=9 = Haptics Intensity` 在"读"上无法验证（读不区分 RID）；但其**写入确实产生过可见效果**，说明写入通道是有作用的 —— 建议项目文档把"读不到"改为"读不区分 RID，无法用于验证"
