## 一、决定性证据：K 是通用填充表，不是密钥

全部产出在 `fw-touchpad\goodix-tool\`，可用 `FINAL_VERDICT.py` 一键复现。

### E1 · `tpfw.bin` 存在**完美均衡块**

```
@0x01C00 - 0x02000   H=8.000000   每字节恰好 4 次  ★
@0x02000 - 0x02400   H=8.000000   每字节恰好 4 次  ★
@0x02400 - 0x02800   H=8.000000   每字节恰好 4 次  ★
@0x02800 - 0x02C00   H=8.000000   每字节恰好 4 次  ★
@0x02C00 - 0x03000   H=8.000000   每字节恰好 4 次  ★
@0x09C00 - 0x0A000   H=8.000000   每字节恰好 4 次  ★
@0x0A000 - 0x0A400   H=8.000000   每字节恰好 4 次  ★
@0x0A400 - 0x0A800   H=8.000000   每字节恰好 4 次  ★
@0x0C400 - 0x0C800   H=8.000000   每字节恰好 4 次  ★
@0x11400 - 0x11800   H=8.000000   每字节恰好 4 次  ★
共 10 个 / 84 个 1KiB 块 = 11.9%
全文件熵 = 7.997165   卡方 vs 均匀 = 348.1（df=255，p<0.001 临界≈330）
```

「每 1024 B 中 256 个字节值各出现**恰好** 4 次」——真随机数据不会这么齐整。这是**人工构造的数学指纹**。

### E2 · 这 10 个块就是 K 本身

```
tpfw[0x1C00:0x2000] == rot_left(K, 316)    逐字节 0 误差
```

`K` = `GT7868Q_scramble_key.bin`。**GT7868Q 的"加扰表"出现在官方明文的另一个型号里**，而且是最直白的形态：直接旋转着复制。

（顺带，这让记忆里那条 `K9 = rot_left(K, 316)`（GT9896 与 GT7868Q 共享同表）**第一次拿到官方物料级证据**。）

### E3 · K 被循环铺满整个固件体

以 16 B 探针、步长 4 扫描 K 的全部 256 个旋转相位：

```
合计 4619 处命中，覆盖 256/256 个相位
命中数区间: min=14  max=21  中位=16
```

### E4 · 45 对块之间**完全相同**

```
【检验 2】均衡块两两之间命中率
   共 45 对，最高 1.0000，最低 1.0000，中位 1.0000
【检验 3】d[i] = blk[i] - REF[i]
   0x01C00  distinct_d= 1  top5=[('0x0', 1024)]
   ...（10 个块全部 distinct_d = 1）
【检验 4】多重集与 REF 相同? True  差异计数 = 0   （×10）
```

⇒ **不存在"数据被置换进去"这回事。** 固件里就是**把同一张表重复铺了 10 次**。

### E5 · 置换假设被证伪

原本猜测 `存储 = permute(数据 ⊕ 填充)`，于是去解固定置换 π。联合约束结果：

```
各位置候选数分布: {4: 1024}     已唯一确定的位置: 0 / 1024
```

四个候选都不收敛 —— 因为**根本没有置换层**，E4 已经说明这些块完全是同一份数据。

### 于是

> **`raw[i] ^ K[i%1024]` 之所以"看起来成功"（零误差、K2==K），只是因为数据里到处都躺着 K 的副本。**
> 这是 `追加三十一` 那个错误的**根**：不是"钥匙藏在明文里"，而是"**根本不需要钥匙，因为那块数据就是 K 自己**"。

## 二、本轮真正的收获：`tpcfgsid*.cfg` 是**真明文 TLV**

三个文件是**逗号分隔的 `0xNN` 序列**，不是加密 blob。用 `[TAG][LEN][payload]` 走流：

```
sid0  size=1302  TLV 覆盖 1232 字节 (99.5%)
sid2  size=552   TLV 覆盖  480 字节 (98.4%)
sid3  size=1866  TLV 覆盖 1793 字节 (99.5%)
```

99.5% 覆盖 = 结构正确。头部 64 B 是明文标识区：

| 文件 | 头部 ASCII | 说明 |
|---|---|---|
| `sid0` (1302 B) | `PCB` + `7867` + `Xiaomi` + `20240307` | 小米 7867 板 |
| `sid2` (552 B) | （无 ASCII 标识） + `20230407` | 通用 |
| `sid3` (1866 B) | `LaiBao` + `7986P` + `A53` + `20220701` | 莱宝 7986P，**带 I²C 命令模板** |

**这是整条研究线上第一份可读、可改、可对照的触觉相关配置数据。**

## 三、纠正：`0x5A` **不是** AW86927 的 I²C 从地址

上一版（`追加三十四` §三）我写了「`sid3` @0x0146 = I²C 写序列结构」。**过度解读，撤销。**

`verify_5a_struct.py` / `verify_5a_ref.py` 的检验结果：

| 检验 | 结果 | 含义 |
|---|---|---|
| `0x5A` 与 `0x5B` 是否成对相邻 | `sid0` 最近距离 26；`sid2` 无 `0x5B`；`sid3` 最近 963 | ❌ 不成对 |
| `0x5A` 后一字节分布 | `{0x00: 4, 0x14: 1}`，无寄存器号语义 | ❌ 不像 reg |
| 频次对照 | `sid3`: `0x5A`=5，`0x50`=11，`0x1E`=18 | ❌ 与参数字节同量级 |
| 三段式 `5A 00 00 00 50 00 5A` 跨文件共享 | 只在 `sid3` 出现 2 次，`sid0`/`sid2` 0 次 | ⚠️ 是 sid3 私有模板，非通用 I²C |

那两处的真实形态（`sid3` @0x0148 起，父块 `TAG=0x0C, LEN=0x3A`）：

```
@0x0148: 90 01 | 04 00 00 00 | 5A 00 00 00 | 50 00 | 5A 00 00 00 | 00 03 ...
         u16=400  u32=4        u32=0x5A       u16=80   u32=0x5A
@0x0160: 58 02 | 04 00 00 00 | 5A 00 00 00 | 50 00 | 5A 00 00 00 | 00 03 ...
         u16=600  u32=4        u32=0x5A       u16=80   u32=0x5A
```

两处只差**前置的 u16 = 400 / 600**。判读：`[时长 400ms/600ms][类型=4][……]`，是 **Goodix 主机的命令描述符**，其中 `0x5A`（90）是一个**数值参数**，不是从地址。

> ⚠️ 注意：这不否决"某个字节是 AW86927 地址"的可能性，只是**当前证据不支持**。真要确认，得看固件代码怎么消费这个字段。

## 四、从明文 cfg 能提取到的触觉/振动相关素材

`haptic_extract.py` 产出 `cfg_parsed/haptic_report.txt`。

### 4.1 时长常量（400 / 600 ms）

```
sid0/sid2/sid3 中 u16LE 均命中 0x0190(=400ms) 与 0x0258(=600ms)
```

三个不同厂牌（Xiaomi 7867 / 通用 / 莱宝 7986P）都含 —— 是**芯片厂给的参考时长模板**。
Android/Linux FF 框架里：短震 10–50 ms、中 100–200 ms、长 400–1000 ms。**400/600 ms 落在"长振动"档**。

⚠️ 单个 u16 不能证明它就是振动时长，需与固件消费点对照。**这是当前最值得追的一条线索。**

### 4.2 `sid0` @0x00EE 的 18 项 u16 序列

```
[58, 2460, 1, 1, 3370, 111, 97, 93, 97, 95, 97, 101, 101, 97, 99,
 99, 97, 97, 109, 97, 111, 29, 29]
```

去掉前后哨兵（58/2460/1/1/3370）后，主体是 18 项、值域 **93–111**、中心 **97**，末两项 **29/29** 断崖。

- 若说是"振幅包络"→ 幅值太窄（±10%），末两项断崖不合理。
- 更像 **多通道 × 档位的增益/校准系数**，末两项可能是未用通道占位。
- ⚠️ 上一版我把它称为"18 u16 vibration-intensity envelope"，**同样属过度解读，降级为"待定的系数表"**。

### 4.3 通道基线条（确认与触觉无关，但有价值）

```
sid0 @0x0257  n=34  [128,128,128,127,128,128,128,129,...]
sid0 @0x03D2  n=36
sid0 @0x0462  n=20
sid3 @0x03C8  n=76  [128 ×76]
sid3 @0x05A2  n=76
sid3 @0x069E  n=52
```

值全在 127/128/129 —— 以 128 为**零点**的有符号偏移/基线表。长度 20–76 与触控通道数吻合。**这是电容自校准基线**，与触觉无关，但它是"cfg 明文可读"的最佳样本。

### 4.4 固件指纹对照全部落空（这本身是信息）

用 cfg 中的长常量串去 `GT7868Q_plain.bin` 与 `tpfw.bin` 搜索：

| 探针 | 在 GT7868Q_plain | 在 tpfw.bin |
|---|---|---|
| `sid0` 18×u16 | 0 处 | 0 处 |
| `sid0` 校准表 24×u16 | 0 处 | 0 处 |
| `sid3` 校准表 24×u16 | 0 处 | 0 处 |
| `sid0` 时长序列 8×u16 | 0 处 | 0 处 |

⇒ **cfg（主机侧配置）与固件体（芯片侧）不是同一套数据的两个副本**，两边的参数是独立下发的。这解释了很多：cfg 里改参数并不需要动固件。

## 七、给未来的我

1. **"看起来像密钥"和"是密钥"之间隔着一整个对照实验。** 至少做三件事：跨文件频率、跨文件存在性、频次量级。
2. **magic 只承诺 magic 本身。** 任何 `PLAIN`/`PNOR`/`RAW` 标记都不等于"整份文件可读"，必须扫熵剖面 + 找完美均衡块。
3. **"熵 8.0" 不等于随机。** 卡方检验才是判据（本轮 348 vs 阈值 330，p<0.001，显著非随机）。
4. **同一类错误会连续犯三次。** 第三次发生时，说明缺的不是知识是**流程**——所以判据要写进技能，不能只写在文档里。
5. **绕开才是本事。** 花了四轮攻固件，而 `tpcfgsid*.cfg` 一直是明文的。**先扫一遍手头所有素材的"可读性"，再决定攻哪一座。**
