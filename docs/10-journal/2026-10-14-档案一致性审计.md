> 性质：**纯离线、只读**（先审计后修正）。产物：可复现工具 `tools/analysis/lab__archive_audit.py`。
> 动机：本仓库有 **6 份会写"口径数字"的入口文档**（README / README.en / REPO-STRUCTURE / START-HERE / docs/INDEX / 全书 §20.0·§20.10），
> 经历 **16 个本地提交**后，历史轮次留下的数字极易与新事实脱节 —— 入口文档一旦漂移，后来者会被误导。

## §1 审计方法（两类口径）

**① 度量口径**（6 项，全部由文件系统实测）：

```
入库文件数 · 入库 MiB · 工作区文件数 · md 数 · 🔴 总数 · 全书 行数/KB · 脚本数
```

**② 范围口径**（3 项，由登记表/全书自身推导）：

```
登记表最新条目 B<n> · 全书 # §19.<n> 最大编号 · 全书里声明的纪律条数
```

**判定规则**：只在**声明性上下文**里比对（汇总行 `| 登记表 |` / `| 纪律 |` / `| 全书轮次 |`、README 的规模行与"已累计/共 N 条"句），
并**跳过**历史快照行（`2026-10-01` 旧复印本、旧稿行数、整理轮日志）—— 否则会把"历史叙述"误判为漂移。

> ⚠️ 两个实现坑（已修，值得记）：
> 1. `git ls-files` **必须加 `-c core.quotepath=false` 且用 `-z`** —— 否则非 ASCII 路径会被 C 样式转义，体积**少算 10 MiB**（首版实测 34.54 vs 实际 44.15）。
> 2. 范围检查若不加"上下文限定"，会命中「与 §19.41 合计为第 1–137 条的完整体系」这类**子集/历史表述** ⇒ 假阳性。
