## §1 重大修正（三条）

### 1.1 ★「缺失 5,141 字节」是误判

| 项 | 内容 |
|---|---|
| 原说法 | TF100A 固件镜像被截断，缺 5,141 字节（含 USART1 ISR） |
| 出处 | `HANDOVER.md:186` |
| 原算法 | 代码 `0x08008FF6` 处 `movw r1,#0xf0b5` + `movt r1,#0x800` 构造出 `0x0800F0B5`；`0x0800F0B5 − 0x08000000 = 61,621`；`61,621 − 56,480 = 5,141` |
| **漏洞** | 【反汇编】该常量**在镜像中从未作为字面量使用**（字面池 0 命中），且 **r1 的后续用途未证实是代码地址** ⇒ 它可能只是个数据指针，**推不出"镜像应有的长度"** |
| **反证 1** | `STATUS.md:671` 与 `image_bounds.py` **均已承认**「声明长度与在场字节精确相等，**文件无缺字节**」——与"缺失 5,141"自相矛盾，但两处都留在文档里 |
| **反证 2** | 【反汇编】84 项向量表内，**最大越界仅 `vec[6]`(UsageFault) 的 +837 字节**，而 `0x345` 正是它的偏移。**5,141 不来自向量表**，来自一处用途未证的代码字面量，两者量级差 6 倍 |
| **反证 3** | 真实表外还有个 slot 越界 **+8,389**，比 5,141 更大 ⇒ **5,141 属 cherry-pick** |

**⇒ 正确表述**：**不是「文件被截断」，而是「这个更新包不包含完整固件」**。文件本身是完整的。

### 1.2 ★ 镜像确实不完整，但缺的是「≥837 字节」而非 5,141

**独立验证结果**（直接读二进制，2026-09-14 22:0x）：

```
file size = 161628 (0x2775C)
vector table @ file offset 0x19ABC
  initial SP   = 0x200076C8
  reset vector = 0x08005165
  image length = 56480   covers flash 0x08000000 .. 0x0800DCA0

越界向量（共 2 个）:
  UsageFault  idx6  = 0x0800DFE5  →  超出末尾 837 字节
  USART1      idx53 = 0x0800DEE9  →  超出末尾 585 字节

末尾 2KB: 0xFF 仅出现 3 次
末尾 512B: 大量 `?? ?? ?? 3E` 模式 = IEEE754 单精度浮点（值 0.15–0.20）
```

**⇒ 结论**：
- **镜像确实不完整**（2 个向量指向镜像外的地址——**这是硬证据，向量值是直接读的，不受反汇编误读影响**）
- **但缺的是「几个中断处理函数」，不是「末尾几百字节」**
- **缺失下界 = 837 字节**（使 `vec[6]` 合法）；上限无法从二进制唯一确定
- **★ USART1 ISR 确实落在缺失区间内**（超出 585 字节）⇒ 原判断**方向对、量级错**

**顺带纠正一处**：此前（含子代理）称"镜像末尾是 Thumb 代码中途断掉"——**不准确**。末尾其实是**浮点数据表的自然结尾**（`0x3E` 在 Thumb 编码里恰好是 `SUBS r6,#imm`，**极易被误读成代码**）。

**安全探测原则**：
1. **只发"读"（`0xA1` 类），不发"写"（`0xA0` 类）**
2. 从最安全的开始：`0E A1 00 0B <n>`（读回波形缓冲，纯读）

## §6 方法学修正：**免驱 ≠ 有接口**

> 用户提问："联想说触控板是免驱的，那能不能从微软的底层走？"

**答案：不行，且原因比"接口不存在"更根本。**

- **免驱** = 不需要厂商驱动，Windows 内置驱动就能识别和控制它
- **但"能用它做什么"完全由设备的 HID 描述符决定**
- 类比：**免驱打印机 → Windows 能打印，但不能扫描**（不是驱动问题，是没那个功能）

**逐层（Windows 驱动栈）**：
| 层 | 能否触达 |
|---|---|
| 应用层 · WinRT HID API | ✗ 只能发声明过的 report |
| HID 类驱动 `hidclass.sys` | ✗ |
| I2C-HID 传输 `hidi2c.sys` | ✗ |
| Intel I2C 控制器（绕过 HID） | ⚠ 能发任意字节，但设备不认 + 会打乱 HID 状态 |

**根本原因**：**HID 是"设备描述自己"的协议**。描述符里没有的东西，从应用层到传输层哪一层都发不进去——**墙不在微软那一侧，在触控板那一侧**。

**且微软规范自己封死了**：《Input Device Haptics Implementation Guide》要求主机要能触发震动，设备**必须**声明 `Manual Trigger (0x0E/0x21)` 的**输出**报表。本机这三条全无、只有 `Intensity` ⇒ 按规范它就是 device-initiated 设备。

**厂商为什么能做到**：华为/苹果在**固件**里写了"边缘滑动时也触发震动"，**触发源是设备自己**，主机侧不参与。

## §7 需求澄清（重要）

> 用户明确："我要的不是单纯的震动，我要的是我在触控板侧边滑动手指的时候有**连贯的震动**，就像华为笔记本的触控板那样。"

**⇒「连贯」的三要素**：
```
连贯 = 素材（单次震动波形）× 节奏（高频重复触发）× 驱动（连续输出能力）
```
- 素材 ← 监听 HDP/HDN 可得
- 节奏 ← 手势引擎按滑动距离产出触发
- 驱动 ← **唯一缺口**
- 链路：手指滑动 → 手势引擎 → 驱动电路 → 原装 LRA（**四段中三段已具备**）

**诚实的技术差异**：华为 MateBook 用**压电陶瓷（PZT）**，响应 <1 ms；本机 **LRA 起振/停振各约 10–20 ms** ⇒ **"连贯"能做到，但格栅密度不如压电细腻**。

**★ 有利点**：接入点③（直驱 LRA）意味着**驱动信号完全由自己控制** ⇒「连贯」取决于自己的驱动电路，**不受原装固件限制**。
