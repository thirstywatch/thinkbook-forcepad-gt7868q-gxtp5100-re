## 一、为什么这个判据是决定性的（机理）

`追加二十六` §五 / §18.6 把问题定义为：**`CA4F`（20 脚 LRA 驱动 IC）接收的命令由谁下发？**

```
若主机 = TF100A  ⇒ 命令在【明文固件】里 ⇒ 可读、可改 ⇒ 路是活的
若主机 = GT7868Q ⇒ 命令在【ECB 加密固件】里 ⇒ 纯软件路到头
```

**本轮的判定方法，是去证明前一支的前提不成立：**

> **一颗 MCU 要"命令另一颗芯片"，它必须能当主机（或能软件模拟主机）。**
> 因此只需回答：**TF100A 有没有"当主机"的能力被使用？**

**"当 I²C 主机"的必要条件（STM32F1 参考手册 RM0008）：**
```
① 必须由软件置位 CR1 的 START 位（0x0100）—— 这是唯一进入主机模式的入口
② 进入主机后，会读 SR1 的 SB(bit0) 等起始条件，并读 SR2 的 MSL(bit0) 判断主/从
③ 以主机发送时，会向 DR(+0x10) 先写"从机地址 + R/W"
```
**⇒ 只要证明「START 从未被写、SB 从未被查、MSL 从未被测」，就等于证明"它从不发起主机传输"。**

## 二、证据链 ①：中断向量表 —— I²C 的两个中断入口都在

**方法：** 用容器原始字节解出向量表（`addr = 0x08005000 + (fileoff − 0x19ABC)`），
并经交叉验证（字符串 `TF100A_Test_FW` 在地址 `0x08005410` ↔ 文件偏移 `0x19ECC`）。

```
向量表 @0x08005000：initial SP = 0x200076C8
  [ 1] Reset      = 0x08005165
  [27] IRQ11 DMA1_Channel1 = 0x08006B3D   ← 与 §18.2「ADC1+DMA1 连续采样」吻合
  [45] IRQ29 TIM3          = 0x0800D629   ← ★ 即项目旧称「零调用者的播放函数 0x0800D628」
  [47] IRQ31 I2C1_EV       = 0x08008979   ← ★ I²C1 事件中断
  [48] IRQ32 I2C1_ER       = 0x0800894D   ← ★ I²C1 错误中断
  [53] IRQ37 USART1        = 0x0800DEE9
其余 IRQ 全为默认 handler 0x0800517F（= 死循环桩）
```

**★ 附带纠正一条既有说法：** `追加八` / 总表 §2.0 提到「`0x0800D628` 零调用者 ⇒ 疑似测试固件」——

本轮又验证了同一现象：`0x08008978`（I²C1_EV ISR）也是零调用者。
⇒ **「零调用者」在本镜像**不能**作为死代码判据**（这条其实是项目自己已经写下的纪律，此处再落实一次）。

## 三、证据链 ②：ISR 响应的状态位集合 = **纯从机事件集**

**方法：** 反解 `0x0800FC80` / `0x0800FC44` 的打包位域编码：
```
packed_flag 的编码（由 0x0800FC44 反解）：
   寄存器字节偏移 = packed >> 22
   位号          = (packed >> 16) & 0x1F
```
代入 ISR 里的五个常量，**全部落在 SR1（偏移 `0x14`）**：

| ISR | 分支条件常量 | 偏移 | 位号 | **SR1 位** | 从机/主机 |
|---|---|---|---|---|---|
| `0x0800894C`（I2C1_**ER**） | `0x050A0108` | `0x14` | 10 | **AF**（应答失败） | 从机 |
| `0x08008978`（I2C1_**EV**） | `0x05010109` | `0x14` | 1 | **ADDR**（地址匹配） | 从机 |
| 同上 | `0x05060109` | `0x14` | 6 | **RxNE**（收到字节） | 从机 |
| 同上 | `0x05040109` | `0x14` | 4 | **STOPF**（收到停止） | 从机 |
| 同上 | `0x05070109` | `0x14` | 7 | **TxE**（发送就绪） | 从机 |

**关键的反面证据（主机专属线索全部缺席）：**

| 主机专属线索 | 位置 | 本镜像 |
|---|---|---|
| **`SR1.SB`**（起始位已发出，bit0） | SR1 `+0x14` | ❌ **从未被查询**（五个 flag 常量里没有 bit0） |
| **`SR1.BTF`**（字节传输完成，bit2） | SR1 `+0x14` | ❌ 从未被查询 |
| **`SR2.MSL`**（主模式，bit0） | SR2 `+0x18` | ❌ **从未被测试**——SR2 全镜像只有 1 处读（地址匹配后清 ADDR 用），且**返回值被丢弃** |
| `SR2.BUSY` / `SR2.TRA` | SR2 `+0x18` | ❌ 从未被测试 |
| 主机错误（BERR/ARLO/OVR） | SR1 bit8/9/11 | ❌ 错误 ISR 只处理 AF 一项 |

**⇒ I²C 的错误中断只为一个从机事件（AF）准备，事件中断只为一个从机的五个事件准备。**
**这是一段标准的、教科书式的 STM32 标准外设库（SPL）I²C 从机驱动。**

## 四、证据链 ③：对 I²C1 寄存器块的写操作 —— **完全枚举，无 START / 无 STOP**

**这是本轮最硬的一条。** 做法分两步：

### 4.1 先把"全部访问入口"收敛掉

**收敛的底层理由（这是"枚举完全"的关键）：**
> **要碰 `I2C1`，代码必须先把 `0x40005400` 这个常量拼进某个寄存器。**
> 全镜像里 `movw #0x54NN` 只出现 **14 次**，其中 **2 次是假阳性**
> （`0x080064F4` 的 `movt #0x800` ⇒ flash `0x08005400`；`0x08010AB6` 的 `movt #0x4001` ⇒ `0x40015400`），
> **剩下 12 次全部落在 `0x0800894C`–`0x08008B90` 这一段**（并已用 capstone 独立复算确认）。
> 且该基址**从未被写入任何全局变量**（段内只有把回调指针写进上下文，没有把基址存进内存），
> 传递方式一律是 `mov r0, r5` 之类的**按值传参**。
> **⇒ 除这一段之外，镜像里没有任何代码能触碰到 I²C1 的寄存器。**

**★ 而且这条"完备性"还经得起一次对抗性检验：**
> 猜疑是"也许基址被存在某张文里、由别的代码加载"。于是直接在整个容器（161,628 B）里搜**字面量**：
> ```
> 0x40005400 (I2C1 基址)  → LE32 命中 0 处 · BE32 命中 0 处
> 0x40005410 (DR)         → 0 处 / 0 处
> 0x40005414 (SR1)        → 0 处 / 0 处
> 0x40005418 (SR2)        → 0 处 / 0 处
> 0x40005800 (I2C2)       → 0 处 / 0 处
> 0x40013000 (SPI1)       → 0 处 / 0 处
> （对照：0x40010C00 GPIOB / 0x40013800 USART1 同样 0 处）
> ```
> **⇒ I²C1 的基址从未以数据形式存在过，只可能由那 12 个 `movw/movt` 现场拼出。**
> ### ⇒ **"全镜像对 I²C1 的访问 = 那 12 个物化点 + 9 个辅助函数"这一枚举是完备的。**

在这 12 个物化点之外，所有对 `0x40005400` 的寄存器操作，**全部经由 9 个 SPL 风格辅助函数**，
而这 9 个函数的调用点**可以被完全枚举**（用两种独立实现交叉验证：文本解析 + capstone）：

| 辅助函数 | 它写/读什么 | 调用点 | 调用次数 |
|---|---|---|---|
| `0x0800FA20` | `CR2(+4)` FREQ 域 · `CCR(+0x1C)` · `TRISE(+0x20)` · `[+0x90]` | `0x08008B98` | **1** |
| `0x0800FD24` | `CR1 = (CR1 & ~2) \| arg1`；**`OAR1(+0x08) = arg2 \| (arg3 & 0x3FF)`** | `0x08008BA6` | **1** |
| `0x0800FC20` | `[base + (arg>>6)] \|= 1<<(arg&0x1F)` | `0x08008BB0`（arg=`0x109` ⇒ `CR2 \|= 0x200`） | **1** |
| `0x0800FC0C` | `CR1 \|= 0x0001`（PE） | `0x08008BB6` | **1** |
| `0x0800F9CC` | `CR1 \|= 0x0400`（ACK） | `0x08008BBE` | **1** |
| `0x0800F9F8` | `CR1 \|= / &= ~0x0800`（POS） | `0x08008BC6` | **1** |
| `0x0800FBF8` | `DR(+0x10) = arg` | `0x08008B14` `0x08008B1A`（**都在 TxE 处理函数 `0x08008AE4` 内**） | 2 |
| `0x0800FC80` | 读 `CR2(+4)` 与 `[base + (flag_low16>>6)]`（GetFlagStatus） | ISR 的 5 个分支 | 5 |
| `0x0800FC44` | `[base + (flag>>22)] &= ~(1<<((flag>>16)&0x1F))`（ClearFlag） | `0x08008A48`（flag=`0x050A0108` ⇒ **`SR1 &= ~0x400`**） | 1 |

**外加一处内联直写**（不对应任何辅助函数）：
```
0x08008A68  ldr r1,[r0,#0x14]   ; 读 SR1
0x08008A6A  ldr r1,[r0]         ; 读 CR1
0x08008A6C  str r1,[r0]         ; 写回 CR1 —— ★ 写的就是刚读到的值，不可能置位
```
这正是 STM32F1 的 **STOPF 清除序列**（读 SR1 → 写 CR1），且**写入值等于读回值**。

### 4.2 结论：写进 CR1 的位，只有这些

| 写入位 | 掩码 | 语义 | 出处 |
|---|---|---|---|
| PE | `0x0001` | 外设使能 | `0x0800FC0C` |
| ACK | `0x0400` | 应答使能 | `0x0800F9CC` |
| POS | `0x0800` | 应答位置 | `0x0800F9F8` |
| （清）SMBUS | `&~0x0002` | 非 SMBus 模式 | `0x0800FD24`（arg1 = 0） |
| 读回值 | — | STOPF 清除 | `0x08008A6C` |
| **START** | **`0x0100`** | **进入主机模式** | ## **❌ 全镜像 0 次** |
| **STOP** | **`0x0200`** | 产生停止条件 | ## **❌ 全镜像 0 次** |
| OAR2 / SWRST / PEC / ALERT | — | — | ❌ 0 次 |

**其他被写到的寄存器：** `CR2`（FREQ 域 + ITEVTEN）、`OAR1`、`CCR`、`TRISE`、`[+0x90]`、`DR`（仅由 TxE 处理函数写，数据取自 `ctx[0x80+idx]`，`idx ∈ [0,0x7F]`）、`SR1`（仅清 AF 位）。

> ### **⇒ RM0008：I²C 进入主机模式的唯一途径是置位 `CR1.START`。**
> ### **它从未被置位 ⇒ 该外设在物理上不可能成为主机 ⇒ 不可能发起任何 I²C 主机传输。**
> ### **⇒ 「CA4F 的 I²C 主机 = TF100A」被证否。**

## 五、证据链 ④：`OAR1 = 0x58` ⇒ **它把自己配成了从机地址 `0x2C`**

> # 🔴 本节整节作废（2026-09-30 第二十一轮）
> 下述「`0x0800894C` = I2C1_ER ISR」的地址**落在 K 交织表副本 `[0x08800,0x08C00)` 内部**，
> 该区非法指令率 **0.0548**（真代码 `0x1E000` 仅 0.0020）⇒ **是数据不是代码**，
> 因此本节（以及 §二/§三/§四/§六 中依赖该地址的部分）**全部作废**。
> 权威更正：`追加三十七` §23.14。**本节以下内容仅作历史留存，勿再引用。**

链路配置函数 `0x0800DA4C`（= TF↔TP 链路初始化）：

```
0x0800DA6E  r2 = 0x20004128                  ; 链路上下文基址
0x0800DA78  r0 = 0x00061A80  (= 400000)
0x0800DA80  [r2 + 0x11C] = r0                ; ★ 链路时钟 = 400 kHz
0x0800DA84  r0 = r2 + 0x0C                   ; ★ I²C 驱动实例基址 = 0x20004134
0x0800DA88  r1 = 0x58
0x0800DA8A  [r2 + 0x118] = 0x58              ; ★ OAR1 的值 = 0x58
0x0800DA8E  r1 = 0x100
0x0800DA92  [r2 + 0x11A] = 0x0100
0x0800DAA0  [r2 + 0x120] = 0x0800DB39        ; ADDR 回调
0x0800DAA8  [r2 + 0x124] = 0x0800DB5D        ; STOPF 回调
0x0800DAB4  [r2 + 0x128] = 0x0800DADD        ; AF 回调
0x0800DAC4  bl 0x08008B68                    ; → I²C 初始化(0x20004134)
```

驱动实例 `ctx_i2c = 0x20004134 = 链路上下文 + 0x0C`，所以：
- `ctx_i2c[0x10C] = ctx[0x118] = 0x58` ⇒ 传给 `0x0800FD24` 的第 4 个参数 = `0x58`
- `0x0800FD24` 实际执行：**`OAR1(+0x08) = arg2 | (arg3 & 0x3FF) = 0 | 0x58 = 0x58`**
- **`0x58 >> 1 = 0x2C`** ⇒ 7 位从机地址 **`0x2C`**
- `ctx_i2c[0x110] = ctx[0x11C] = 400000` ⇒ 传给 `I2C_Init` 的时钟 = **400 kHz**

**★★ 这与项目既有结论逐字吻合：** `追加十三` 早已从反汇编抠出「**I2C1 @ 400 kHz / 从机 `0x2C` / PB6-PB7**」。
本轮是**从固件字节第一次把它证明出来**（`OAR1` 的实参链路：常量 → 上下文 → 寄存器），
两代独立得出的同一数字互为交叉验证。

**⇒ 一个"把自己配成从机地址"的外设，不是主机。**

## 六、证据链 ⑤：链路的**接线**完整 —— 但 ⚠️ **字节通路未启用**

**方法：** 追"帧就绪标志"的生产者与消费者。

```
【生产者】I²C 地址匹配（ADDR）→ 回调 0x0800DB38：
    link_ctx[0] |= 2                      ; 置"正在被寻址"
    GPIOA->BSRR = 8                       ; ★ PA3 拉高（"门铃"）

【生产者】I²C 停止（STOPF）→ 回调 0x0800DB5C：
    link_ctx[0] = (link_ctx[0] & ~2) | 4  ; ★ 置"一帧收完"（bit2）

【消费者】主循环命令分派器 0x0800E1C0：
    0x0800E1C6  r0 = [0x20004128]; r0 >>= 2; r0 <<= 31
    0x0800E1D4  if (r0 == 0) return       ; ★ 等的就是 bit2
    0x0800E1DC  link_ctx[0] &= ~4         ; 清标志
    0x0800E1EE  class = ctx->[0x104]      ; ★ 取"帧类别"字节
    0x0800E1FA  if (class == 0x80) → 0x08006628
    0x0800E20C  if (class == 0xA0) → 读 ctx->[2]（u16 子命令）
    0x0800E228  switch (sub) { 0x100 / 0x500 / 0xB00 / 0xD00 … }
```

**★★ 这一串把整条线闭合了：**

1. `ctx->[0x104]` 正是 **RxNE 处理函数 `0x08008A70` 单独锁存的"帧第 1 字节"**：
   `0x08008AA4  strh.w r2,[r0,#0x104]`；
2. 分派器 switch 的 `0x80` / `0xA0` 正是项目早已解出的**厂商命令类别**
   （`TF100A命令分派器与I2C链路.md`：`0x80`×1 / `0xA0`×16 / `0xA1`×22）；
3. 分派器读的 `ctx->[2]`（缓冲偏移 2 的 u16）**正好等于 `追加八` 定下的
   `[class][b1][b2][sub_lo][sub_hi][payload]` 里的 `sub`**
   （因为第 1 字节被单独锁存，缓冲从 `wire[1]` 起算 ⇒ `buf[2..3] = wire[3..4] = sub`）。

> ### **⇒ 接线是通的：帧就绪标志确实被主循环分派器消费，分派器读的字段确实是 I²C 驱动里的"帧类别 + 子命令"。**
> ### **⇒ GT7868Q 是这条总线上的主机（已证）。**
> ### **⇒ TF100A 在这条总线上只可能是从机。**

## 六之二、⚠️ **但本轮发现一个必须写下来的矛盾：字节通路没被使能**

**这条是两位独立复核者**同时**指出、并被本方枚举复核确认的：**

```
全镜像对 I²C1 的 CR2(+0x04) 写入只有两处：
  ① 0x0800FA20 (I2C_Init)：CR2 = (CR2 & ~0x3F) | FREQ      ← 只动 FREQ[5:0]
  ② 0x0800FC20 (0x08008BB0 调用，arg = 0x109)：
        [base + (arg>>6)] |= 1 << (arg & 0x1F)
        arg = 0x109  ⇒  偏移 = 4 (CR2)  位号 = 9  ⇒  ★ CR2 |= 0x0200
⇒ CR2 最终只置了 bit9 = ITEVTEN；bit10 = ITBUFEN【从未置位】，bit8 = ITERREN【从未置位】
```

**按 RM0008 的中断使能表：**

| 事件 | 状态位 | 使能位 |
|---|---|---|
| 地址匹配（从机） | SR1.ADDR | **ITEVTEN** ✅ 已开 |
| 收到停止（从机） | SR1.STOPF | **ITEVTEN** ✅ 已开 |
| **接收缓冲非空** | **SR1.RxNE** | **ITBUFEN** ## ❌ **未开** |
| **发送缓冲空** | **SR1.TxE** | **ITBUFEN** ## ❌ **未开** |
| 应答失败 | SR1.AF | ITERREN ## ❌ **未开** |

**⇒ 结论（本轮最重要的副产物）：**
1. **该 I²C 从机的 RxNE / TxE 分支恒不触发 ⇒ 它不会去读 DR，缓冲区不会被填，
   `ctx->[0x104]`（帧类别）**不会被写入**** ⇒ 分派器 `0x0800E1C0` 读到的是**陈旧值**；
2. **整个错误中断（AF）分支也恒不触发**（`ITERREN` = 0）；
3. （叠加 `NOSTRETCH=0`：从机在 RxNE 未读时会拉低 SCL 时钟拉伸 ⇒ 主机**多字节写会卡住**。）
4. 于是这条 I²C 从机实际只做两件事：**地址匹配 → 拉高 PA3 + 置链路标志 bit1**；
   **收到 STOP → 置链路标志 bit2**。

> ### **★★ 这直接动摇项目的一个**前提**：「GT7868Q 把 39 条厂商命令经 I²C1 发给 TF100A」——
> ### **机制上不成立**（收字节的中断没开）。**`追加八` 的"链路 = I²C1"结论需要重新审视。**
> ### **★★ 而 USART1 是唯一"驱动完整、从复位可达、且真实写数据寄存器"的对外链路**
> ### （复核者 B 的核心反证：`0x08010ED2 str r0,[r1,#4]` 是真实 DR 写，调用点 `0x0800DFC0`，PA9/PA10 配 AF、置 `CR1.UE`）。
> ### **⇒ 新的候选假设：TF↔TP 的实际命令链路是 USART1，而 I²C1 从机是
> ### 这份 `TF100A_Test_FW`（测试固件）里的残留/未完成脚手架。**
> ### **⚠️ 这是"候选假设"，不是定论** —— 见 §十①的判定方法。

> - TX 侧：`0x0800DC6C` → `0x0800DD18`（阻塞式逐字节发送 + 轮询 `SR.TC`）→ 只在**一个模块**里有 11 个调用点

## 十、诚实标注：本轮**没有**闭合的六点

**① ★★ 最重要：I²C1 从机的字节通路**为什么不使能**？「39 条命令」到底走哪条线？（未定）**
> 事实（§六之二）已确定：`CR2.ITBUFEN` / `ITERREN` 从未置位 ⇒ RxNE/TxE/AF 三个分支恒不触发。
> 但这留下一个**必须解释的矛盾**：固件在**上电时**就初始化了 I²C 从机（`0x0800DA4C` 由启动链
> `0x0800FD64` 调用）、给了从机地址、还**用 NVIC 使能了 IRQ31/32**
> （`0x0800FE3C(0x1F,…)` / `(0x20,…)`，复核者 A 在 `NVIC_IPR=0xE000E400` / `NVIC_ISER=0xE000E100` 上核实）——
> **却唯独没开"缓冲区中断"**。三种解释：
> ```
> (a) 固件 bug / 这份 Test_FW 未完成（镜像自报 TF100A_Test_FW）
> (b) 设计如此：主机只"ping"（地址+STOP，不含数据），数据走【USART1】
> (c) 该 MCU 的 ITBUFEN 语义与 STM32F1 不同（克隆差异）
> ```
> **怎么判定（都不需要拆机）：**
> ```
> · 夹 I²C1（PB6/PB7）与 USART1（PA9/PA10）各看一次实际流量 ⇒ 一眼定案（零注入）
> · 或：确认这颗 MCU 的型号与参考手册（(c) 就排除）
> · 或：查 ctx+0x106/0x107 状态机在运行期是否真的被改动过
> ```
> **⇒ 这一条比 §五 本身更值得先做**：它决定"39 条命令"这条线的**信源到底是谁**。

**② `CA4F` 是否真的挂在这条 I²C1 上？（未证）**
本轮证明的是「TF100A 不是主机」，**没有**证明「CA4F 在 I²C1 上」。
若 `CA4F` 根本不在 I²C 上（例如被 GT7868Q 用自己的 GPIO/PWM 直接驱动），
结论仍是同一条：**命令不在 TF100A 的明文固件里**。
**⇒ 对 §五 的裁决无影响；但对"GT7868Q 具体怎么做"仍有信息缺口。**

**③ ★ 新线索（未追）：PA0 上可能有一个常驻的 200 Hz / 35% PWM，而
`追加二十六` §18.4 用来否掉它的论据是**无效的**。**

`§18.4` 的理由是「`TIM_MOE_Set` 唯一调用点、参数 enable=1、位于初始化路径 ⇒ MOE 开机即置位 ⇒ 若 PWM 驱动 LRA 就会一直震」。
**但 `TIM2` 上根本没有 `BDTR`/`MOE` 寄存器**（`BDTR` 在偏移 `0x44`，是 TIM1/TIM8 独有）。
`0x0800D78E` 那次调用写的是 `TIM2+0x44` —— 一个**保留地址**，**等于空操作**。
⇒ **§18.4 这条论据不成立**（结论未必错，但它给的理由错了）。

本轮反而查到：`0x0800D704` 的 TIM2 分支**确实**把通道 1 输出打开了：
```
0x0800D75E  [sp,#0x10] = 1
0x0800D760  [sp,#0x28] = 1 (u16)     ← 传给 CCER 配置器的 cfg[0] ⇒ ★ CC1E = 1
0x0800D766  bl 0x080105AC            ← CCER: (CCER & ~1) | cfg[0] ⇒ CC1E 置位
0x0800D76E  r2 = 0x2BC (700) ; bl 0x08010908   ← CCR1 = 700
0x0800D79A  bl 0x08010BC8            ← TIM_Cmd(TIM2, ENABLE)（[base] |= 1）
```
配合 `ARR = 1999`（200 Hz）与 `PA0 = 复用推挽` ⇒ **PA0 上很可能有一个常驻的 200 Hz / 35% 占空比 PWM。**
**这恰好是 LRA 的谐振驱动规格**（`追加二十六` §2.3：Nidec 官方谐振 = 200 Hz）。

> **⚠️ 这与本项目自己的 §3.4 判断需要对齐**：单端 PWM 驱动 LRA 需要外部器件才成交流。
>
> **★ 顺带一个收束性观察（本轮从引脚清单直接得出）：**
> **TF100A 全部"能自主产生信号"的引脚只有三条：**
> ```
> PA0  常驻 200 Hz / 35% PWM（CCR 运行期恒定，编码不了"何时震"）
> PA3  数字输出（上电即高；每次被寻址再置高）—— 唯一"每次都动一下"的输出
> PA9  USART1 TX（帧协议，用途未定）
> ```
> **⇒ 若 TF100A 要对 `CA4F` 说"现在震"，它只能靠 PA3 的那"一次跳变"或 USART1。**
> `PA3` 在 I²C 地址匹配时被拉高（`0x0800DB38` → `BSRR = 8`）——
> **若 PA3 连到 `CA4F` 的触发脚，那将是"每次 GT7868Q 与 TF100A 通信 ⇒ 震一下"，
> 与"滑动跟随震动"的语义不符**（滑动时 GT7868Q 是持续读坐标，不会每次事务都震）。
> **⇒ 仍指向：扳机在 GT7868Q 侧。**

> **⇒ 下一步该做的判定（比 §五 更接近"能不能震"）：**
> **`PA0` 到底连到哪里？** 若连到 `CA4F`，则 `CA4F` 的"波形"就来自 TF100A 这条常驻 PWM；
> 但**因为 CCR 运行期恒定（`追加二十六` §4，两种独立方法）**，它无法编码"何时震" ⇒
> 扳机仍必须在别处。**用万用表通断档查 PA0 更方便，因为它是模组上一个明确引脚。**

**④ USART1 的用途未定（开放项，见 §七 注与 §六之二）**
> **若要彻底排除"TF100A 用 USART1 命令 `CA4F`"，唯一办法是夹 `PA9/PA10` 看有没有该帧协议的实际流量。**
> 这是**观测类**步骤（零注入、零风险），项目已把它列在 `追加二十五` §11。
> **但它不影响 §五 的裁决** —— §五 问的是 I²C 主机归属。

**⑤ 两处措辞/语义保留（复核者提出，已采纳）**
> · **`OAR1 = 0x58` 的严格解释**：F1 要求 `OAR1` 的 `bit14` 由软件保持为 1，而本驱动写入的是
> `0x58 & 0x3FF`（**未置 bit14**）。按 F1 严格语义 ⇒ 7 位地址 `0x2C`（总线字节 `0x58`）；
> 若该克隆容错，也可能被解释成 `0x58`。**⇒ 「从机地址 0x2C」这一数字与 `追加十三` 吻合，但语义上留一分保留。**
> · **"CR1 从未被写入 START/STOP"的准确表述**：CR1 **确实被写过一次**（`0x08008A6C` 的 STOPF 清除序列），
> 但写回的是刚读出的**原值**。准确说法是「**CR1 的 START(0x0100) / STOP(0x0200) 两位从未被置位**」。
> · 另：`TRISE` 与 `CCR` 确实被写（`0x0800FA6C` / `0x0800FAE4`），这是 `I2C_Init` 的一部分，
> **配置主机时序 ≠ 发起主机传输**（复核者 A 把这条列为"最强反向证据"，但结论是它不构成反例）。

**⑥ `[+0x90]` 的写法（未解）**
`I2C_Init`（`0x0800FA20`）在 `clock > 400 kHz` 分支里写了 `I2C1+0x90 = 1`。
`0x90` 超出 STM32F1 的 I²C 寄存器范围（`0x00–0x23`），**疑为该芯片的厂商私有扩展寄存器**
（本链路实际只用 400 kHz，该分支**不执行**）。
⇒ 不影响本判据；仅记录为"这颗 MCU 与标准 STM32F1 存在一处非标准扩展"。

## 十一、独立复核（两个互不通气的复核者）

**方法：** 派出两个独立子代理（都是"盲测"——**不告知本轮任何结论**，只给材料与问题）：
一个做**盲测重分析**，一个做**对抗性证伪**（"尽力推翻"）。两者各自自建脚本、各自写目录
（`fw-touchpad\verify-A\` / `verify-B\`），互不通信。

| 项 | 复核者 A（盲测重分析） | 复核者 B（对抗性证伪） |
|---|---|---|
| 对核心结论「TF100A 不发起 I²C 主机传输」 | ## **未被推翻** | ## **未被推翻** |
| 对核心结论的置信度 | **高** | **中—高** |
| 「唯一 I²C 从机」是否被推翻 | 未推翻 | 未推翻 |
| 「没有别的总线」是否被推翻 | — | ## **后半句被推翻：USART1 成立**（真实 DR 写、可达、配了 PA9/PA10 AF、置 UE） |
| 独立复算量 | 1,295 movw / 1,124 movt；12 个物化点 / 12 个 I²C 调用；全 20,314 地址与 `asm.txt` 一致 | 自建 capstone 解码 + 常量传播 + 有界反向切片 + 可达性（422 个可达基本块）；抽样 210 条助记符一致率 100% |
| 找到的"最强反证" | `CCR/TRISE` 按主机时序编程（但"配置时序 ≠ 发起传输"，不构成反例） | `0x08008A6C str r1,[r0]` 是全镜像唯一 CR1 写 —— 逐指令核对后确认**写回原值**，反证失败 |

**两者独立得出的、本轮采纳的增量（本方已逐条复核）：**
1. ★★ **`CR2.ITBUFEN` / `ITERREN` 从未置位** ⇒ 收发字节分支与整个错误分支恒不触发（→ §六之二）。
2. `0x08010AB6` 的 `0x40015400` 是 **TIM11**；该站点所在的 `base==X` 分派链里**连 I²C 项都没有**
   ⇒ 代码自身就证明它不是 I²C1。
3. `I2C1` 初始化确实**用 NVIC 使能了 IRQ31/32**（写 `NVIC_IPR 0xE000E400` / `NVIC_ISER 0xE000E100`）
   ⇒ 该驱动**上电即起**，不是死代码（但这**不**代表字节通路已使能 —— 两者是两回事）。
4. `OAR1` 未置 `bit14` ⇒ 地址语义留一分保留（→ §十⑤）。
5. 一处**方法学陷阱**（复核者 B 发现）：`DMA1 = 0x40020000` 是用 `movs r0,#0` + `movt r0,#0x4002`
   构造的，**`movw` 被编译器优化掉了** ⇒ **只搜 `movw/movt` 成对模式会漏掉"低半字为 0"的外设基址**。
   （本方复核：`DMA1` 只用于 ADC 采样，`DMA_Init` 的 `CPAR = 0x4001244C` = `ADC1->DR`，
   **没有任何 DMA 通道指向 I²C1**。）
6. 一处**假阳性澄清**（复核者 B）：`0x08010D16/0x08010D2A/0x08010D3E` 看起来像"BRR/ODR/BSRR 三连击"
   （疑似 bit-bang），实为 **GPIO 标准库函数体**（`GPIO_SetBits` / `GPIO_ResetBits` /
   `GPIO_ReadOutputDataBit` 同时读 `ODR` 与 `BSRR`）⇒ **bit-bang 证据不成立**，与本方 §七 结论一致。

**两者共同列出的盲区（本方接受）：**
- 全程是**静态**分析；容器前 105,148 字节是高熵（≈7.98）未解密区，其中含 4 份**相同**的疑似加密向量表
  （SP = `0x20010422`，与 TF100A 明文的 `0x200076C8` 不同 ⇒ 更像 GT7868Q 自己的镜像）。
  **⇒ 本轮结论的准确表述应限定为：「在 TF100A 的明文可执行段 `0x08005000–0x08012C9F` 内」。**
- 无法排除运行期自修改 / 二级 loader 重写 CR1（但那属于 GT7868Q 侧或加密区）。

> ### **⇒ 两个独立复核者都没有推翻 §五 的裁决。**
> ### **⇒ 但两者都独立地把"字节通路未使能"和"USART1 成立"推到了台面上 —— 这是本轮最有价值的副产物。**

## 十二、方法学（本轮新增，写给后来者）

| # | 教训 | 本轮的实例 |
|---|---|---|
| **8** | **"外设被引用"≠"外设被使用"，要看它出现在**什么上下文**里** | `TIM1/TIM8/USART2-5/TIM4-7` 都"出现"了，但只是在 HAL 的 switch 分派表里 ⇒ 是**表项**，不是使用 |

| **10** | **写操作要"枚举到封闭"才能下否定结论** | 说"没有 START"必须同时给出：① 所有访问入口；② 每个入口的调用点；③ 每个入口写入的位。三者齐备才叫"枚举完全" |

| **13** | **独立复算要用第二种实现** | 本轮用「文本解析」与「capstone 反汇编」两套独立实现交叉验证调用点清单；并发现 capstone 朴素线性扫描会因解码失败而**漂移**（必须按已知地址定点复核） |

### 14.3 ★★★ 对项目结论的影响（三条加强 + 一条修正 + 一个高价值新观测）

**① 加强：`追加二十六` §18.5 的「`CA4F` = 波形发生器 + 驱动器」得到证实。**
它有 **8 KB SRAM 波形库**，波形是**运行期由主控经 I²C 下载**进去的（SRAM 掉电即失）。
**⇒ 这正好解释了 §18.3/§18.4 的困惑：波形不在 TF100A 明文段，不是因为"没找到"，
而是因为它根本不在 TF100A 里 —— 它在 CA4F 的 SRAM 里，由别人下载。**

**② 加强：「GT7868Q 是 `CA4F` 的 I²C 主机」从"推断"升级为"必需"。**
```
每次上电后，必须有主控把 ~8 KB 波形库经 I²C 下载进 CA4F 的 SRAM。
TF100A 不可能是它（本轮已证：只做从机、从不产生 START）。
⇒ 只能是 GT7868Q。  ⇒ §五 的裁决（命令在加密固件里）被加强。
```

**③ ⚠️ 修正（诚实）：§五 的问题需要**扩展一句**。**
`AW86927FCR` 的触发**不一定是 I²C 命令** —— 它可以是 **`TRIGx` 上 ≥1 µs 的脉冲**（或 one-wire playback）。
> **⇒ 「谁让 `CA4F` 震」的完整问法 = 「谁在驱动 `TRIG1/2/3`」或「谁在写它的 I²C」。**
> **⇒ TF100A 恰好有一个富余的数字输出 `PA3`（§七.2）—— 所以"TF100A 用 GPIO 脉冲触发 CA4F"
> 这条路在本轮 §五 的 I²C 论证【之外】，本轮【没有】排除。**
> （观测上的保留：`PA3` 表现为"上电即高 + 每次被寻址再置高"，看不到周期性下降沿；
> 若它接 `TRIG1`，需要极性与"每次点击震两下"的节奏吻合才行。**必须实测。**）

**④ ★★ 新的、成本极低、价值极高的观测（直接由本次鉴定导出）：**
```
既然 GT7868Q 每次上电必须向 CA4F 下载 ~8 KB 波形库，
那么在【开机时】夹住 I²C 总线，应当能抓到一段【发往某个非 0x2C 地址的大块写】。

⇒ 项目 `追加十三` 的「路线 A：纯监听，夹 PB6/PB7」现在有了明确靶子。
一次开机监听可同时拿到三样东西：
   ① CA4F 是否就在这条总线上      → 顺带回答 §十②「共不共总线」
   ② CA4F 的 I²C 从机地址         → 由 `AD` 脚决定，实测即知（写它需要这个）
   ③ ★★★ 厂商的原始触觉波形库本身（8 KB）
        → 方案③ 可以直接回放这套原厂波形，不必再自己猜"该震成什么样"
```

**⑤ 对"主机能不能自己触发"：不变。**
仍取决于 `CA4F` 的 `SDA/SCL` 是否与主机可见的那条 I²C（Intel 控制器 / I²C-HID）同网。
但现在多了一个**更好用的判据**：`AW86927FCR` 的 I²C 地址由 `AD` 脚配置、**可配**，
所以"**在主机那条总线上扫一遍地址**"能直接给出答案。
（⚠️ 红线不变：触控板是唯一指点设备，总线扫描有扰动风险 ⇒ 建议在 Linux live-USB 里做，
或先做零风险的万用表通断。）

## 十四之二、离线追加（同日）：`PA3` 是一条被**频繁拉低**的握手线；`PA0` 线索**降级**

> **本节回答用户追问「USART1 / PA3 / PA0 这几个能不能搞清楚」时，先做掉的离线部分。**

### (1) ★★★ `PA3`：我此前的读法**错了**，它不是"上电即高、永不清除"

先把 helper 语义钉死（**手验证实**）：
```
0x0800F7FC(port, val) → [port + 0x14] = val   = GPIO_ResetBits → BRR  （拉低）
0x0800F80C(port, val) → [port + 0x10] = val   = GPIO_SetBits   → BSRR （拉高）
```
再穷举这两个 helper 的**全部**调用点并回溯 `r0`（端口）与 `r1`（位掩码）：

| helper | 调用点数 | 端口 | 位掩码 | 结论 |
|---|---|---|---|---|
| `0x0800F7FC`（**拉低**） | **21** | **全部 = GPIOA** | **全部 = `0x8`（pin3）** | ## **21 处全都在拉低 PA3** |
| `0x0800F80C`（**拉高**） | **2** | GPIOA（1 处经栈传递） | `0x8`（pin3） | **2 处拉高 PA3** |

抽 3 处手工核对（`0x080099E4` / `0x0800A3EE` / `0x0800BE1C`），形态完全一致：
```
movw r0,#0x800 / movt r0,#0x4001   ; GPIOA
movs r1,#8                         ; pin3 = PA3
bl   0x0800F7FC                    ; GPIOA->BRR = 8  ⇒ PA3 拉低
add sp,#N / pop {r7,pc}            ; ★ 都在函数【末尾】
```

**两个拉高点：**
- `0x0800DA6A`：I2C 链路初始化时（拉高一次）
- `0x0800DB54`：**I²C 地址匹配（ADDR）回调**里

**⇒ 真正的语义：**
> **`PA3` = TF100A 的"注意/握手"输出线（doorbell）。**
> **GT7868Q 一来寻址它，就把 PA3 拉高；各种处理函数**干完活**在末尾把它拉低。**
> **⇒ 它是一条**会被反复拉高拉低**的信号线（不是静态电平）。**

### ★ 由此推翻我上一节的推理

§十四 里我写过「`PA3` 表现为上电即高 + 每次被寻址再置高，**看不到周期性下降沿**」——
**那是错的**（当时不知道 `0x0800F7FC` 的语义，漏掉了 21 个拉低点）。

> ## **⇒ 「`PA3` = `CA4F` 的 `TRIG1`（引脚脉冲触发）」这条假设**
> ## **在固件层面【没有被排除】** —— PA3 完全有能力产生反复脉冲。
> ## **它仍然是"唯一可能救回软件路"的两个未验证点之一，必须实测。**

### (2) `PA0`：**降级**（我上一节把它排为"最值得追的新线索"，是过誉了）

**一条纯逻辑的反证（不需要任何仪器）：**
```
AW86927FCR 的 TRIG 语义 = "Send trigger pulse (≥1µs) on TRIG pins to playback waveform"
   ⇒ 一个「常驻的 200 Hz / 35% 方波」每秒给出几百个边沿
   ⇒ 若它接在 TRIG 上，波形会被每秒重触发几百次 ⇒ LRA 会【持续震】
实际：触控板不震
⇒ PA0（若那个 PWM 真在输出）【不可能】是 LRA 的触发器
```
**⇒ `PA0` 只剩两点价值：**
- **文献价值**：订正 `追加二十六` §18.4 那条无效的 MOE 论据（这条订正仍然成立、仍然要留）
- **次要拓扑问题**：PA0 到底连哪（示波器夹一下 10 秒就知道它有没有真输出 200 Hz/35%）

### (3) ★ `USART1`：**升级**，因为它可能是"真正的链路"

本轮已证 **`CR2.ITBUFEN` 从未置位**（§六之二）⇒ **RxNE/TxE 中断不触发 ⇒ GT7868Q 无法经
I²C(0x2C) 读走字节**。那 TF100A 的压力数据怎么出去？只剩两种可能：
```
(a) 走 USART1  → 它驱动完整、从复位可达、真实写 DR，
                 且发送点集中在【压力采集/打包那一小段代码】里（11 个调用点，全在 0x08006098–0x0800620E）
                 帧协议 = 0xA5 同步字 + 长度/校验，460800 baud —— 很像"压力数据流"
(b) I²C 从机 0x2C 只是这份 TF100A_Test_FW 的残留/未完成脚手架
```
**⇒ 假设：TF100A 把打包好的压力数据经 USART1 送给 GT7868Q；I²C 从机是残留。**
**⇒ 判定：开机夹 `PA9`，看有没有周期性【二进制帧】（不是 ASCII 文本）。**

### (4) 三个未知的可判定性与方法（结论：**三个都能搞清楚**）

| 未知 | 最省的办法 | 能否定案 | 定案后能救回软件路吗 |
|---|---|---|---|
| **PA0 有没有真输出 PWM** | 示波器夹 PA0（10 秒） | ✅ 直接 | ❌ 不能（已逻辑排除是触发器） |
| **PA3 = 门铃 还是 = TRIG?** | ★ **点一下触控板，看 PA3 有没有脉冲**（示波器/逻辑分析仪） | ✅ 一次测量即可二分 | ★★ **能**（见下） |
| **PA3 → CA4F `TRIG1`(pin4)?** | 万用表通断 | ✅ 直接 | ★★ **能** |
| **USART1 对端/是否真链路** | 开机夹 PA9 看有无周期帧 | ✅ 基本可判 | ❌ 不能（对端仍是 GT7868Q 加密侧） |
| **CA4F 在不在这条 I²C 上** | ★ 开机夹 I²C 抓 ~8 KB 波形下载 | ✅ 顺带拿到地址 + **原厂波形库** | ★★ **能**（若与主机总线同网） |
| **触发走 I²C 还是 TRIG 引脚** | 夹 I²C + 点击，看有没有写 CA4F 地址 | ✅ 行为二分 | — |

**★ 不用原理图就能定位 `CA4F` 各脚的方法：**
```
① 先用通断找出哪两个脚通向已知的 HDP / HDN 焊盘 ⇒ 那就是 pin7 / pin5
② 按 pin1 圆点方向绕圈数：
     pin4 = TRIG1   pin3 = TRIG2   pin2 = TRIG3
     pin18 = SDA     pin19 = SCL    pin9 = AD（I²C 地址选择）
③ 于是 TRIG1 / SDA / SCL / AD 全部可定位 —— 无需原理图
```

### (5) 只有两种结局能救回"纯软件"

```
(i) CA4F 与主机可见的那条 I²C（Intel 控制器 / I²C-HID）【同网】
      ⇒ 主机可以直接当主机去写 CA4F（它有 RTP 实时播放 + 可配 I²C 地址）
      ⇒ ★ 纯软件路复活

(ii) PA3 = CA4F 的 TRIG1
      ⇒ TF100A 的固件是【明文】的 ⇒ 可以让它自己按压力变化去脉冲 PA3
      ⇒ ★ 模块内自触发（注意：触发源是 TF100A 自己的判断，不是主机手势）
      ⇒ 有限复活

其余任何结局 ⇒ 只剩方案③（HDP/HDN 外挂驱动）
```

### (6) 最小代价回答"还有没有纯软件希望"

**按信息量/成本排序，只做前两步就够：**
```
第 1 步（不拆机，若有 FPC 测试点）：开机夹 I²C 总线
        → 一次拿到：CA4F 在不在总线 · 它的 I²C 地址 · ★原厂 8KB 触觉波形库
第 2 步（同一台设备加一路）：点一下触控板，看 PA3 有没有脉冲
        → 二分"门铃 / 触发"
（第 3 步才需要拆底盖 + 万用表通断，确认 PA3 是否连到 CA4F 的 pin4）
```

**设备：** 一台 ≥4 通道逻辑分析仪（或示波器）· 万用表（通断档）· 细探针
（FCQFN 2×3 mm 约 0.4–0.5 mm pitch，直接点芯片引脚很难，优先找 FPC 测试点/过孔）。

### (7) ★★★ 纯软件方案（**零仪器**，回答用户追问「没有任何设备和工具，能不能软件处理」）

**关键发现（离线、零成本）：** 扫全部 32 张 ACPI 表 ⇒ 触控板挂在 **`\_SB.PC00.I2C0`**
（DSDT `TPAD` 节点，从机地址 `0x2C`，即 **Intel LPSS I²C 控制器**）。
```
⇒ 主机自己就是这条 I²C 总线的主人
⇒ "CA4F 在不在这条总线上" 可以【纯软件】回答
```

**而且刚鉴定出的 `AW86927FCR` 给了一个极其收敛的靶子（手册 Table 3 Address Selection）：**

| `AD` 脚 | I²C 地址（7 位） |
|---|---|
| 0 | ## **`0x5A`** |
| 1 | ## **`0x5B`** |

> ## **⇒ 只需在主机这条 `I2C0` 上探两个地址（`0x5A` / `0x5B`）就能定案：**
> ## **有应答 ⇒ CA4F 就在主机总线上 ⇒ 主机可直接写它 ⇒ 纯软件路复活**
> ## **无应答 ⇒ CA4F 在 GT7868Q 的私有总线上 ⇒ 纯软件够不到它**

⚠️ 注意：`0x2C` 是 ACPI 给**触控板**（GT7868Q）的 I²C-HID 地址；TF100A 的固件也把自己配成 `0x2C`
——**这两个 `0x2C` 不可能是同一条总线上的同一地址**（会冲突），所以要么是两条总线上的巧合同号，
要么其中一处理解需要修正。**这正是扫描时值得顺便验证的点。**

**三条纯软件路子（按推荐度）：**

| # | 方案 | 成本 | 说明 |
|---|---|---|---|
| **1** | **Linux live-USB + `i2c-dev`** | 一个 U 盘 | `i2cdetect -l` 找 `i2c-designware-pci` 那条 → `i2cget -y <bus> 0x5A` / `0x5B`（**只探两个地址，比全扫安全得多**）。命中后 `i2cdump` 读寄存器对照手册，再 `i2cset` 配置 boost/F0 + 走 RTP FIFO 触发播放。**准备一个 USB 鼠标**（触控板可能短暂失效）；live USB 不动硬盘 |
| **2** | Windows + **RWEverything** 戳控制器 MMIO | 免费工具 + 关 VBS/内存完整性 | 原理：designware I²C 的 `IC_TAR`（从机地址）→ `IC_DATA_CMD`（读/写）→ 即可完成一次事务。要手动算寄存器，较繁琐、易错 |
| **3** | **把自己的感官当仪器**（零成本，现在就能做） | 0 | **开机时听/摸触控板有没有震一下**：`PA3` 在 I²C 链路初始化时被拉高一次，若 `PA3→TRIG1`，开机应有一声。**有 ⇒ `PA3=TRIG1` 基本坐实；没有 ⇒ 大概率不是。** 这是**唯一一个不需要任何设备的物理判据** |

**软件问不出来的边界（必须说清）：**
- **「`PA3` 焊到 CA4F 的 pin4」这件事，固件只能告诉我们"TF100A 会驱动 PA3"，
  不能告诉我们"它连到哪"。** 物理连接只能靠通断/示波器。
- **但你不需要知道**：若 CA4F 在主机总线上，直接写它即可；若不在，`PA3` 那条路即便成立，
  也只是"模块内自触发"，而不是主机控制的滑动震动。**⇒ 纯软件路径的成败，几乎完全由方案 1 的扫描结果决定。**

**还有一条纯软件但踩红线的：改 TF100A 明文固件**（让它输出特征脉冲，回刷后看触控板会不会周期性震）。
可行性有（明文 + 容器格式/校验和项目已掌握 + UEFI capsule 回刷路径），但**有变砖风险**
（触控板是本机唯一指点设备）。**⇒ 建议先做方案 1。**

## 十五、一句话总结

> **TF100A 把自己配成了 I²C 从机（地址 `0x2C`），从不产生 START 条件，也从不查询任何主机专属状态位；
> 它收下的那 39 条厂商命令由 GT7868Q 下发。**
> **⇒ `CA4F` 的命令不可能来自 TF100A 的明文固件。**
> **⇒ §五 判据落到"主机 = GT7868Q"一支；纯软件路到头，方案③（HDP/HDN 外挂驱动）仍是唯一可行路线。**
