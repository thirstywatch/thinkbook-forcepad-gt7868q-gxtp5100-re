## 〇、先纠正行动建议里的一个方法学错误

喆建议的验证路径是"打开 Col04 的 HID 设备句柄，记录 OUT/IN 报告，看点击时是否出现新 OUT 报告"。
**如果用 ETW 来做这件事，会得到必然的假阴性。**这不是"抓得不好"，是结构性的：

```
wevtutil gp Microsoft-Windows-SPB-HIDI2C /ge:true
  opcode  0  win:Info
  opcode  1  win:Start
  opcode  2  win:Stop
  opcode 10  IoSpbReadDispatch
  opcode 11  IoSpbReadComplete
  opcode 12  IoForwardToCompletionQueue
```
⇒ **opcode 表里没有任何 Write 类事件。**
HID 的 Output Report 在 SPB/I²C 层就是一次**写事务**。
⇒ 这个 provider **结构上无法记录 Output Report**。
⇒ 所以"ETW 里没看到新 OUT 报告"**不能证明主机没发**，正如"没看到"不能证明"不存在"。
⇒ 若要真正记录 OUT，只能上KMDF filter 抓 `IOCTL_HID_SET_OUTPUT_REPORT`（或 SPB 层的 `IoSpbWriteDispatch`，但 provider 不提供）。

**但根本问题在于：这个问题不需要靠抓包来回答。**下面三条判据都不需要动报文。

---

## ① 描述符层：`Out = 0` ⇒主机【物理上发不出去】

实测（本机 `AllCaps.cs` / `poc\hid-dump.txt`，4 个集合全覆盖）：

| 集合 | UsagePage/Usage | In | **Out** | Feat | 性质 |
|---|---|---|---|---|---|
| Col01 | `0x0001/0x0002` | 9 | **0** | 0 | 鼠标 / 指针 |
| **Col02** | `0x000D/0x0005` | 40 | **0** | 737 | **Precision Touchpad 主体** |
| Col03 | `0x000D/0x000E` | 0 | **0** | 3 | Digitizer Configuration |
| **Col04** | `0xFF00/0x0001` | 65 | **65** | 0 | 厂商通道（rid=14，唯一有 Output） |

**判据（结构性，不是统计性的）：**

1. Windows 的Precision Touchpad 驱动栈工作在 **Col02**。Col02 的 `OutputReportByteLength = 0`。
   ⇒ 主机往这块板子发**任何**方向的报文都无路可走—— `HidD_SetOutputReport` 会直接失败。
   ⇒ **这不是"没抓到"，是"发不出去"。**
2. PTP 规范里主机→设备方向本来只允许极少量报文（软阈值 press 之类），这块板子**一个都没声明**
   （全设备 `page 0x0E` 下只有 `Intensity`（`0x23`，FEATURE，rid=9），且它是 feature 不是 output）。
3. 唯一有 Output 的 Col04 是 `UsagePage 0xFF00`（厂商定义）。
   **⇒ Col04 上能看到的一切 OUT 流量，都只是本项目自己的实验流量，永不代表"主机行为"。**

> ★ 这条同时解释了《全书》§19.17.2 与早期文档的表面矛盾：
> `Col04 Out=65` 与 `Col02 Out=0` 同时成立，两者说的不是同一个集合。

## ② 设备栈层：链路上只有 inbox 驱动，没有任何第三方 filter

注册表实测（`HKLM\SYSTEM\CurrentControlSet\Enum\HID\GXTP5100&ColNN\<实例>`）：

| 集合 | `Service` | `ClassGUID` | `Driver` | `UpperFilters` / `LowerFilters` |
|---|---|---|---|---|
| Col01 | `mouhid` | `4d36e96f…`（鼠标类） | `\0001` | **空/ 空** |
| Col02 | **(无)** | `745a17a0…`（HID 类） | `\0015` | **空 / 空** |
| Col03 | `MTConfig` | `745a17a0…` | `\0016` | **空 / 空** |
| Col04 | **(无)** | `745a17a0…` | `\0017` | **空 / 空** |

**判据：**
- 四个集合的 **UpperFilters 与 LowerFilters 全部为空** ⇒ 链上没有插任何第三方 filter。
- Col02 / Col04 **没有专属 Service** ⇒ 没有厂商服务绑定它们。
- ⇒ 整条消费链只有 Windows inbox：`hidclass.sys` + `spi_hid.sys`（+ `hidi2c.sys`）。
- ⇒ **没有任何第三方代码有机会在 Col02/Col04 上看到或注入报文。**

## ③ 进程层：没有厂商触控板/触觉服务在跑

实测（`Toolhelp32Snapshot` 枚举全系统进程）：

```
系统内进程总数：311
名字匹配 /触控板|HID|Goodix|SPB|Precision|Lenovo/ 的进程：0
```

**判据：**
- 没有任何 Goodix / 联想触控板服务在运行 ⇒ 厂商侧也没有在下发触觉命令。
- 与既有结论一致：已从 MS Update Catalog 确认联想官方只提供 `GdixTouchpadService.exe`
  （右键区 / 双击速度 / 3HB 设置），**不含触觉功能**（§19.23.5(a)，264 条 Goodix 条目枚举结果）。

> ⚠️ 诚实标注这条的**局限**：进程名匹配会漏掉"名字不含关键词但确实在用 HID 的进程"。
> 它是**补强**判据，不是独立闭合。前两条（描述符 + 设备栈）已经独立闭合。

## ④ 附带检验：既有 ETW 样本是**有效**的（可以引用）

既然已有两份 ETW，先验证它们能不能被采信（`etwcheck.py`）：

| 样本 | 事务数 | 时间跨度 | 间隔主簇 | 占比 | 判定 |
|---|---|---|---|---|---|
| `haptic-toggle.etl` | 305 | 39.4 s | **7.80 ms（≈128 Hz）** | **88.5%** | 有效 |
| `haptic-toggle2.etl` | 398 | 36.2 s | **7.80 ms（≈128 Hz）** | **85.1%** | 有效 |

**判据：**
- 88.5% / 85.1% 的读事务间隔落在 `7.80 ms ±0.30 ms` 的单一簇内、簇内实际跨度仅 `7.52–7.95 ms`
  ⇒ **严格等周期轮询**，正是 `spi_hid` 空闲时持续拉取输入报告的形态。
  ⇒ **样本确实抓到了触控板的 HID 读事务，不是空跑**（对照实验设计要求的阳性对照）。
- 两份样本各有一个 ~29–37 秒的超长间隔 ⇒ 抓取中途设备被重枚举/暂停过。
  ⇒ 这意味着**这两份样本不覆盖"点击"事件**（点击期间是否连续轮询未验证），
  所以它们**只能证明"主机在持续读"**，不能证明"点击时主机没写"——后者由 ① 结构性封死。

> ★ 一个方法学教训（值得写进纪律）：
> 第一次做间隔聚类时用了"与前一个间隔之差 ≤ 容差"的串链法，
> 结果 `7.69 / 7.71 / 7.69` 这种抖动会把簇无限延长、吞掉真实的不同间隔，
> 一度得出"间隔不集中、样本无效"的**错误结论**。
> **正确做法**：先取众数附近的值作基准，再把每个间隔**独立**归到最近的簇。
> 以及：同一簇内的浮点抖动可达 ±0.05 ms，**绝不能用精确相等做聚类**。

## ⑤ 合并判决：喆那张表里的第2 行成立，且已被三条独立证据支撑

```
| 观察结果 | 结论 |
|---|---|
| 点击时出现新的 OUT 报告 | 可以继续逆向该报告 |
| 只有 0x96F8 读取，没有任何触觉相关 OUT 报告 | ← ★ 本轮落在这一行 |
| HID 侧完全没有相关输出，但板上 HDP/HDN 有震动波形 | 触觉由 GT7868Q 固件自行处理 |
```

**本轮把第2 行从"观察结论"升级为"结构性结论"：**

| 判据 | 层级 | 独立性 |
|---|---|---|
| Col02 `Out=0`（PTP 集合无输出报告能力） | 描述符 | 不依赖任何运行时观测 |
| 链上无第三方 filter / 无专属 Service | 设备栈 | 不依赖驱动内部行为 |
| 无厂商触控板进程 | 进程 | 依赖命名匹配（补强） |
| 两份 ETW 样本有效性已验证（128 Hz 等周期轮询） | 运行时 | 只证明"主机在读" |

⇒ **不需要做"HID OUT 报告记录器"，也不需要 KMDF filter 驱动。**
⇒ 唯一能改变判决的是**设备固件自己声明了一个新的 Output Report**，
而描述符来自 GT7868Q 固件、主机改不了（~~这条《全书》已定案~~）。<br>🔴 **2026-10-02 夜推翻**：`report_fixup` **可以**改写**主机侧**描述符副本（实证针对本机 PID `0x01E9`，见《全书》§19.30.1）。**但判决不变** —— 设备侧仍无接收分支。

## ⑥ 于是，问题的真正落点变了

原来以为的分叉是"主机 OUT 报告有没有触觉命令"，现在可以替换成：

```
问：GT7868Q 固件里，有没有一条命令能让它转发到 AW86927 / 触发播放？
答：这个问题只能问固件，问不到主机。
    而 GT7868Q 固件主体是 ECB 加密的（§19.23 未破）。
```

| 路线 | 状态（更新后） | 依据 |
|---|---|---|
| 劫持 Windows HID 输出报告 | ❌ **结构性封死** | 本轮 ①② |
| 用 KMDF filter 记录 OUT 报告 | ❌ **不值得做** | 即使做出来也必然是空的（①） |
| 从 Col04 厂商通道下发自定义命令 | ⚠️ 通道通（已实测读写），但**无触觉命令表** | 官方命令表10 条，无马达命令；官方源码搜 `haptic/vibrate/LRA/motor/waveform` = 0 命中 |
| 改 GT7868Q 固件 | ❌ 加密未破 + 官方工具主机侧零变换⇒ 回刷不了 | §19.22.5 |
| **模组内接管私有 I²C / 实体接管 HDP·HDN** | ⬅ **仅剩可行** | 与既有结论一致 |

**⇒ 建议的下一步不再是主机侧记录器，而是：**
1. **拿一次硬件判据**（万用表通断档：AW86927 的 I²C 两根线接到哪颗主控？`HDP/HDN` 又接到哪颗？）
   —— 这是唯一能一次定案"路径 A 还是 B"的动作，且不需要软件。
2. 在等硬件期间，**继续离线挖 GT7868Q 固件外层的明文部分**（4,412 B 外层 + TF100A 明文 20,314 条），
   看能否找到"触觉参数如何被消费"的线索。

## ⑦ 对喆那份复核意见的处置

那8 条复核意见本身质量很高，本轮确认其中**第 8 条（`SetOutputReport` 只是读通道、尚未验证为触觉控制通道）**
被本轮**大幅加强**：不仅是"尚未验证"，而是**在 Windows 主机侧永远不可能验证成功**，因为
PTP 集合 `Out=0`（第 ① 条）。

其余 7 条属于固件/归属层面的证据评级问题（`0x5A` 地址、`0x5C` 归属、`1024 B` 映像冲突等），
本轮未触碰，仍然成立。建议按《全书》既有纪律处理：
- 凡"某功能在运行期发生"的断言必须给出**运行期调用点**；
- 凡"某文件属于某芯片"的判断必须有一条**与文件头自述独立**的证据链。

## 附：本轮工具（可复用）

| 文件 | 作用 | 安全性 |
|---|---|---|
| `hidprobe\hiddiag.py` | 三条判据一次跑完（描述符事实 + 设备栈注册表 + 进程枚举） | 纯读注册表/进程表，**不碰设备** |
| `hidprobe\etwcheck.py` | 校验任意 SPB-HIDI2C ETW 样本的有效性 + 打印 provider opcode 表 | 只解析 ETL |

**踩过的坑（保留在代码注释里）：**
1. `ObjectTypeIndex` **不是稳定 ID** —— Windows 每次构建句柄表时按遇到顺序重编号。
   实测同一个 File 类型在三次连续查询里分别得到 9 / 21 / 50。
   ⇒ "先探一次确定类型索引、再另起一次查询过滤"会**静默漏掉全部结果**。
   （`whoholds.py` / `whoholds2.py` 是踩坑版本，`whoholds3.py` 是修正版，
   但最终发现 `NtQueryObject` 在无 `PROCESS_DUP_HANDLE` 权限时会全线失败，
   而开权限 + `DuplicateHandle` 会挂在某些句柄上——
   ⇒ **整体路线不可靠，已弃用**。本轮改走注册表 + 进程枚举，更稳且足够。）
2. `NtQuerySystemInformation` 的 NTSTATUS 必须按**无符号 32 位**比较，
   用有符号比较会把 `0xC0000004`（INFO_LENGTH_MISMATCH）判成失败。
