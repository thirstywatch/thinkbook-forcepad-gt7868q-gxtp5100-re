## §6 ★ 今晚新解出的三块（本轮增量）

### 6.1 Col04 命令空间边界（【反推固件】，已闭合）

- 分发器 `0x080091C0`，唯一调用者是主循环；参数是固定 RAM 块 `0x20004134`
- 判定式：**类字节**（`ctx+0x104`）+ **一个 u16**（`ctx+2`，取值形如 **`0xNN00`**）
- **类只有 3 个**：`0x80`（1 个入口，带 0x80 字节块 + 校验，**疑数据写入**）、`0xA0`、`0xA1`；**`0xA2` = 回复类**（固件自己发的，禁发）
- **`0xA0` 恰好 16 个**：`01 05 0B 0D 0E 11 12 14 17 1F 20 24 26 32 33 35`
- **`0xA1` 恰好 22 个**：`02 04 07 08 0A 0B 0F 13 15 16 18 1D 23 28 29 2B 2C 2E 32 34 35 36`
- **边界外 = 静默 no-op**（无害）⇒ 探测清单可精确到 38 个值
- 安全分级：**`0xA1` = 查询（结果进响应缓冲 ⇒ 只读）** → `0xA0` = 命令（取 `ctx+4` 载荷 ⇒ 写）→ `0x80` 最后

### 6.2 读通道的取址语义（【实测本机】+【厂商工具】，**已定案**）

> **v1**：帧 `0E 20 00 00 05 01 <addr16BE> <size16BE>`（10 字节），长度上限 60
> **v2**：帧 `0E 20 00 00 07 01 <addr32BE> <len16BE>`（12 字节），**其中 `addr32 = (字节偏移 << 16) | 读取字节数`**
>
> - 长度 **0 → 拒收 `err=122`**；**> 60 → 封顶 60**；帧尾 `len16` 字段**被设备忽略**
> - **v1 与 v2 是同一存储的两种取址形式**，结果逐字节一致（`{offset, len}` 都能对上）
> - **读通道字节精确、跨 12 小时可复现**（今晚读数 vs 12h 前快照逐字节一致）⇒ **可以信任它做测量**

**★ 且修掉了 `poc/VibLink.cs` 里 `Mem2Read` 的一个真 bug**（原来把 addr 当 32 位地址直接填，只在巧合时对）。

### 6.3 读窗口是什么（【实测本机】+【实测：项目快照】）

| 观察 | 结论 |
|---|---|
| 40KB 快照：非零率 51.2%；`0x0000–0x0FFF` 全零；`0x8000–0x9FFF` 5 分钟内变化 20–36% | 是**活着的、结构化的存储**，不是随机 RAM 转储 |
| 按 **16 位大端**解析：`0x8100–0x89FF` ≈ `0x05xx–0x06xx`；`0x4560–0x4B00` ≈ `0x7754–0x77B6`；`0x9200–0x93FF` ≈ `0xFFDx–0xFFEx`；`0x8000` 是 −12…−9 的斜坡 | **是一大片「16 位有符号采样数组」**，各区段各有基线（像各路信号通道） |

### 6.9.3 四条结论

**①【★ 已更正】`A1` 帧被写通道接受（`send=True err=0`），但"被处理 / 不是 no-op"这个说法站不住。**

**更正依据（工区既有实测，不是我今晚新做的）**：`poc/opcode-sweep-log.txt` + `poc/sweep-ops.ps1` ——
历史做过 **class 字节全扫 `0x00–0x2F`**（`pkt[1] = op`，dwell 400 ms，跳过 `0x10/0x11/0x12/0x13/0x20`）：

| class 范围 | 结果 |
|---|---|
| `0x00`–`0x0D` | 正常应答（24 字节块 `00 00 01 01 …`） |
| `0x0E`, `0x0F`, `0x14` … `0x2F` | **连续 28 个 class 全部 `err=122`** |
| `0x30` | liveness 自检失败 → **ABORT**（≈47 帧后通道被拖住） |

⇒ **`err=122` 是"class 未被处理"的默认应答，不是 `A1` 特有的反应。**
⇒ **`A1` 的表现与几十个未处理 class 无法区分** ⇒ 它既没有被应答、也没有证据表明被转发。
⇒ 同一张日志还说明：**当晚看到的"卡顿"更可能是累积帧数（剂量）造成的**，而不是 `A1` 的特有行为。
**（H1 结论不变：否。只是理由比我原先写的更简单。）**

**②【高】拿不到任何 `0xA2` 应答。**
发帧后纯读在 **65 / 67 / 129 / 257 / 737 / 4096** 六种长度下**全部 `err=122`**，持续 **≥3 分钟**，**任何长度都换不回数据**。

**③【高】这个"122 态"是「响应寄存器被留在不可交付状态」，不是"应答通道已乱"。**
决定性对照：发帧**前**纯读 `ok=True` → 发帧**后** `err=122` → **再发一条类 `0x20` 读帧后纯读又回到 `ok=True`**。
⇒ 通道本身完好（读帧照常工作），**122 只是"当前没有可交付的应答"**。

**④【中高】这个反应是「类级」的，不区分 opcode。**
历史已证 `sub=0x0000`（不在合法表里）**同样**产生 122；本次 `sub=0x0B00`（合法 opcode、H1 写法）也是 122。两个不同 opcode、两种字节序，结果相同。
⇒ **没有观察到"合法 opcode 得到应答 / 非法 opcode 被丢弃"这种区分** —— 这正是不支持 H1 的形态。

### 6.9.4 对 H1 的判定

| 假设 | 判定 |
|---|---|
| **H1：GT7868Q 把 `0xA1` 转发给 TF100A、主机能拿到应答** | **实测否**（无应答可取，且反应与 opcode 无关） |

**⇒ 按 §7 的定义，H1 是门。门没开 ⇒ 整条主机侧 Col04 扩展路径作废，转方案 ③（HDP/HDN）。**

**诚实边界**：仍有一种读法未被排除 —— "应答存在但格式非法，故不可交付"。但它与"根本没有应答"在**实际效果上相同：主机拿不到它**。所以结论不变。

### 6.9.5 ★ 方法学副产品（对以后所有实验都有用）

> **纯读（`ONE in 0E <len>`，不发任何帧）就能拿到响应寄存器里"上一条应答"的完整内容，可以重复读、不被消耗。**

以后所有"发一条、看回什么"的实验，**不再需要"发/读分离 + 并发监听"那套易错设计**：

```
① 纯读一次         → 记下当前应答（基线）
② 发一条帧
③ 恢复后再纯读一次  → 内容变了 = 有应答；没变 = 没有
```

**纯读零副作用、可无限次重复。** 这比 LISTEN 方案干净得多。

### 6.11.2 ★ 新发现：128 字节明文段表（解出"解密后装到哪"）

`0x113C` 起的 128 字节里，**24 字节头之后是 12 条 8 字节记录**，编码为

| 类型 | 长度 | 地址 |
|---|---|---|
| 3 | 0x2000 (8 KB) | `0x00016000` |
| 3 | 0x2000 | `0x00006000` |
| 3 | 0x2000 | `0x00008000` |
| 3 | 0x2000 | `0x0000A000` |
| 3 | 0x2000 | `0x0000C000` |
| 3 | 0x2000 | `0x0001E000` |
| 3 | 0x2000 | `0x00010000` |
| 2 | 0x3000 (12 KB) | `0x00001000` |
| 2 | 0x1000 (4 KB) | `0x00000000` |
| 3 | 0x2000 | `0x00004000` |
| 2 | 0x3000 | `0x00013000` |

⇒ **这是 GT7868Q 固件"解密后"的装载布局**（地址最高到 `0x1E000`，约 128 KB 空间）。
⇒ 对逆向者的直接价值：**能区分代码段/数据段、知道每段长度**。
（注：表内还有一条 `[1, 8, 0xFF00]` 形态的条目；各段合计约 86 KB，与声明长度 100,608 不等 ⇒ **还有一张表或另处续接**，列为未定。）

### 6.11.3 ★★ 判决：加密强度（本节最重要的一条）

**① 16 字节分组密码 + 位置无关（ECB 式）——【实测，高置信】**

| 检验 | 结果 |
|---|---|
| 密文按 16 字节切：6,280 块；重复块 129 个、共出现 818 次 | — |
| **这 818 次出现的字节偏移 mod 16** | **分布 = `[(0, 818)]`** —— **其余 15 个余数全为 0** |
| 重复块两两间距（689 个） | **全部是 16 的整数倍** |

⇒ 重复**严格落在 16 字节边界上** ⇒ **分组密码 + 无 IV / 无 salt**。
⇒ **不是**流密码（否则不会有 16 字节同余性），**也不是**带 IV 的 CBC。

**② ★ 四年不换密钥 ——【实测，高置信】**

拿本机密文的 **5,591 个不同块**去撞两份同芯片老固件：

| 对照 | 不同块命中 | 按体积 |
|---|---|---|
| `GOODIXTOUCHPADCAPSULE_22001E0D.Cap`（2020/2021 代） | 844 / 5,591 = **15.1%** | **23.8%** |
| `GOODIXTOUCHPADCAPSULE_26002816.Cap` | 830 / 5,591 = **14.8%** | **23.6%** |
| `GT7936L_16753412.bin`（别的芯片） | 0 / 50（抽样） | — |

⇒ **2024 年的密文块原封不动出现在 2020/2021 年的固件里** ⇒ **同一把密钥、跨版本跨板型、四年未换**。
⇒ 同时说明：**约 24% 的固件体积是跨版本共用的静态内容。**

**③ 明文结构通过密文泄露 ——【实测】**

自相关（字节匹配率，随机基线 0.39%）：

```
lag 16 / 64 / 256 / 512            → 0.38–0.69%      （无信号）
lag 1024 / 1084                    → 7.12% / 0.41%   ← 1024 有峰，1084 没有
lag 2048 / 4096 / 8192 / 16384 / 32768 → 5.5% / 4.9% / 6.9% / 7.0% / 5.0%
```

⇒ 明文的重复结构是**2 的幂次步长**（1K/2K/4K/8K/16K/32K），**不是**容器的 1084。
⇒ ECB 把这些结构**原样保留在密文里**，等于把明文的重复格局送给了任何观察者。

### 6.11.4 这对项目意味着什么（诚实评估）

| 问题 | 答案 |
|---|---|
| **还能解密吗？** | **不能**。无密钥、无已知明文对；"结构泄露"不足以反推。 |

| 分组 K | 各余数类最高频字节的平均占比 |
|---|---|
| 8 | 0.7% |
| 16 | 0.9% |
| 32 | 1.3% |
| **（AES 参考值）** | **≈0.4%** |

**⇒ 完全不偏斜 ⇒ 不是循环 XOR，是真正的 128 位分组密码。**
