## 一、红线（永久生效）

| # | 红线 |
|---|---|
| 1 | **禁止批量轮询 `Col04`** |
| 2 | 单次事务 **≤ 32 B**，间隔 **≥ 500 ms** |
| 3 | ★ **刷机四条（不是三条）`00 10` / `00 11` / **`0E 12`** / `0E 13` 绝不碰** |
| 4 | **未获明确同意，不动 `bcdedit`** |
| 5 | 不删 `.workbuddy`、不删项目目录 |
| 6 | **只读优先**；写入类命令（类 `0x80` / `0xA0`）置于最后 |
| 7 | **`0xA2` 禁发**（它是回复类，不是命令） |

### ★ 红线 3 的精确内容（官方源码原文）

```c
unsigned char buf_switch_to_patch[] = {0x00,0x10, 0x00,0x00, 0x01,0x01};  // 进入刷机模式
unsigned char buf_start_update[]    = {0x00,0x11, 0x00,0x00, 0x01,0x01};  // 进入刷机模式
unsigned char buf_restart[]         = {0x0E,0x13, 0x00,0x00, 0x01,0x01};  // 重启
// load_sub_firmware() 里：
unsigned char buf_load_flash[15] = {0x0e,0x12, 0x00,0x00, 0x06, ...};     // ★ 真正写 flash
```

| 命令 | 官方语义 | 危险等级 |
|---|---|---|
| `00 10` | switch to patch（进入刷机模式） | 危险 |
| `00 11` | start update（进入刷机模式） | 危险 |
| **`0E 12`** | **load flash（★ 真正写 flash）** | ★★★ **最危险** |
| `0E 13` | restart | 危险 |

> ⚠️ **全线旧文档只写"刷机三连 `00 10`/`00 11`/`0E 12`"，漏了 `0E 13`，且未分清 `0E 12`（写）与 `0E 13`（重启）。** 本节已更正为四条。

## 二、事故记录

### 事故一：Col04 高频轮询把 IC 打挂（2026-09-13）

| 项 | 内容 |
|---|---|
| 触发 | 对 `Col04` 厂商通道做高频轮询探测 |
| 后果 | 触控 IC 挂死，需要断电恢复 |
| 教训 | 单次事务 ≤ 32 B、间隔 ≥ 500 ms 是**硬性**的，不是建议 |

### 事故二：触控板输入冻结（2026-09-14，**共两次**）

| 项 | 内容 |
|---|---|
| 触发 | 写入类命令序列 |
| 后果 | 触控板输入完全冻结 |
| 教训 | 写入类命令必须置于最后，且**必须先确认通道真的打开** |

> 🔴 **关联陷阱**：项目曾长期用 `Gx::Write` 的 **16 位帧长度字段误用 `+7`**（官方是 **`+5`**）
> ⇒ **所有写探针的每一帧都被设备静默丢弃**，一度得出错误结论。
> 修后实测：`+7` 时 `0x4160` 毫无变化；`+5` 时变成 `FF 00 00 00`（**写入落地**）。
> **⇒ "写入生效"这既是进展也是风险。**

### 事故三（文档层）：一次正则批量替换把 12,000 行档案截断成 24 行

| 项 | 内容 |
|---|---|
| 后果 | 主档案被截断，靠会话日志才完整恢复 |
| 沉淀的三条硬纪律 | ① **不要用正则批量写文件**（用精确的逐处替换）② **大改前先快照** ③ **所有 ps1 脚本纯 ASCII** |

## 三、★ 恢复阶梯（最终版，严格按序）

设备被打挂时，**按以下顺序**恢复，不要跳步：

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | **等待 ≥ 30 秒** | 部分挂起会自动恢复 |
| 2 | **禁用再启用设备**（设备管理器 / `pnputil`） | 触发 PnP 重新枚举 |
| 3 | **重启 Windows** | 触发完整重新初始化 |
| 4 | **关机断电 ≥ 30 秒（拔电源）** | IC 完全掉电复位 |
| 5 | **EC reset** | 仅在前 4 步无效时 |

> ⚠️ 不要在第 1–3 步之间重复发命令"试探" —— 那会让情况更糟。

## 四、命令寄存器易失性（重要安全事实）

| 项 | 值 |
|---|---|
| 状态判据 | `0xFF` = 空闲是**常态**；写完 5 字节命令后字节0 一律回 `FF`（**不是接受信号**） |
| `0x82` | **仅**为命令 `0x80` 的应答，且需等约 **250 ms** |
| **命令寄存器易失** | 掉电/复位即丢失 ⇒ **不会永久改变设备状态**，但也意味着"看起来恢复了"不等于"没受伤" |

## 六、风险等级矩阵

| 操作 | 风险 | 可逆性 | 建议 |
|---|---|---|---|
| 读 HID 描述符 / feature report | 🟢 极低 | — | 随时可做 |
| 单次 `Col04` 只读（≤32 B / ≥500 ms） | 🟢 低 | — | 需守间隔 |
| ACPI 表导出 | 🟢 极低 | — | 随时可做 |
| EC RAM 只读 | 🟢 低 | — | 需管理员 |
| `Col04` 写入类命令（`0x80` / `0xA0`） | 🟠 中 | 命令寄存器易失 | 最后做，先料板 |
| RWEverything 直打 MMIO（W1） | 🟠 中（需关 HVCI/黑名单） | 可 `step9-restore` 还原 | **实验后必须还原** |
| Linux `i2cdetect` 扫触控板总线 | 🔴 高（**会崩内核**） | 重启可恢复 | 慎用 |
| **`0E 12` load flash** | 🔴🔴🔴 极高 | **不可逆** | **绝不碰** |
| 固件刷写（UEFI capsule） | 🔴🔴 高 | 有回滚（用原件重刷） | **先用料板 + 先零风险预演** |
