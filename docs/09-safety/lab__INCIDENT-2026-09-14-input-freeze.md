## 4′. 因果判定（**11:18 第二次事故后修订**）

**主因（高置信）：类 0x20 的"连发读突发"（整段快照 = 683 次顺序读）**
1. 第二次事故**全程未发任何 A 类帧**，冻结仍发生 ⇒ 与 A 类帧无关，**读突发单独即可致冻**；
2. 两次冻结的时间窗与"683 次读"的两次整段快照**一一对应**（11:14:47–11:15:38 的 snapB、11:18:2x 的 snapC）；
3. 机制吻合：每次 `SetOutputReport`+`GetInputReport` 都是**一次 I2C-HID 往返**；~8 次/秒、连续 80 秒≈683 次往返，
   把 hidi2c 的请求队列/设备的输入通道压住 ⇒ **主机输入上报停摆**，而 MCU 内部的点按→触觉链路不受影响；
4. 与项目史吻合：09-13 两次挂死的共同点是**持续/高频的厂商通道操作**（33 Hz 轮询、opcode 枚举）；
5. **杀掉进程即恢复** 的观察也吻合（句柄关闭 → 挂起 IRP 被取消 → 队列疏通）。

**降级为"未定"：类 0xA1 帧**
- 第一次事故中 122 状态与冻结同时出现，曾被判为主因；
- 现在看更可能：**同一次传输层挂起**的两种表现（或 A1 帧只是"多一次往返"而已）。
- 仍保留的确定事实：A1 帧之后 `GET_INPUT(0x0E)` 会回 **122**，且**会自行恢复**（不是永久态）。
- ⇒ 不否定"0xA0/0xA1 帧也属于高风险"（它至少会改变输入侧状态），但**它不再是冻结的必要条件**。

**可排除**：单次读（`HEALTH` 一次读在两次事故前后都正常）。

**教训**：本项目历史上"最安全的操作"（类 0x20 读）**只在"少量、低频"时安全**；
**"整段快照"这种量级的用法是危险操作**，我此前把它当成安全操作是判断错误。

## 5. 红线更新（强制，写进工作纪律）

1. **🚫 禁止"整段快照"**（683 次连发读）。这就是两次冻结的直接原因。
   - 单次/少量读（`HEALTH`、`MEMSCAN <addr> <≤0x100>`）仍属安全；
   - **Col04 流量上限（硬性）**：≤2 次往返/秒，**单轮 ≤80 次**，轮与轮之间**至少间隔 3 分钟**；
   - 需要更大范围时**分段、跨轮次**取，不要一轮扫完。
2. **类 `0xA0` / `0xA1` 帧仍视为高风险**（会改变输入侧状态）：**不得在用户正在使用电脑时单发**；
   每次前必须确认用户已保存工作、手边有备用输入方式。
3. 冻结后的处置顺序：**先等 1~2 分钟**（两次都自愈）→ 无效再走 EC 复位
   （关机 → 拔充电器 → 长按电源 20~30 s → 等 1 分钟 → 开机）。
   已知无效：热重启 / 禁用-启用设备 / 重启设备 / Novo 孔。
   **先杀进程**（关句柄、取消挂起 IRP）是第一步，往往立刻见效。
4. "发命令后等回复"的实验**必须两进程**（发/读分离），读一侧必须用 `ONE` 模式（**一个进程只做一次调用**）。
5. 每次实验前先做一次 `HEALTH`（类0x20 读 0x1000×16），实验后再做一次，数据逐字节对比作为"设备无恙"的凭据。
6. **任何需要用户在现场的采集，先声明"可能冻结 1~2 分钟"**，让用户有心理准备与备用方案。

### 13.1 ★ 对本文 §3 / §4′ 的更正：`err=122` 的确切语义

- 本文 §3 曾写「冻结与 122 状态同生同灭」「122 状态只由类 0xA1 帧产生」。
  **本次实测给出更准确的机制（证据链完整）：**

| 时刻 | 纯读（不发任何帧） | 说明 |
|---|---|---|
| 发 `A1` **前** | `ok=True  0E 20 00 00 10 …` | 响应寄存器里有上一条应答 |
| 发 `A1` **后**（≥3 分钟，试了 65/67/129/257/737/4096 六种长度） | **`err=122`** | **寄存器里没有可交付的应答** |
| 再发一条**类 `0x20` 读帧**之后 | **`ok=True`，内容正常** | **寄存器被新应答重置** |

**⇒ `err=122` = "响应寄存器当前没有可交付的应答"，不是"应答通道已乱"。**
**⇒ 它不是持久损伤：一条正常的类 `0x20` 读帧即可让读通道恢复正常。**
**⇒ 本文 §3 里"122 状态与冻结绑定"的表述应降级**：122 是**寄存器状态**，冻结是**传输层挂起**，两者可同时出现，但不是同一件事。

### 13.3 新发现：**纯读（零副作用）可以观察应答**

> `ONE in 0E <len>` **不发任何帧**，就能拿到响应寄存器里"上一条应答"的完整内容，且**可重复读、不被消耗**。

⇒ 今后"发一条看回什么"的实验，标准姿势改为：**纯读基线 → 发帧 → 恢复后纯读 → 比对内容**。
**不再需要"发/读分离 + 并发监听"**——那套设计正是本次前两轮失手的原因（读窗口与卡顿期错位）。
