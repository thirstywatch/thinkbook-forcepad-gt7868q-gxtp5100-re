一、★★★ 重大更正：我第 20 轮「撤回 FLASH_KEY1」的撤回，本身是错的
================================================================================

【错误链条】
 · 第 19 轮我提出：固件内含 STM32 FLASH 自编程序列（KEY1 = 0x45670123）。
 · 第 20 轮我用 `D.count(0x45670123.to_bytes(4,'little'))` 得到 0 命中，
   于是**撤回**了该结论，并在报告里写「FLASH_KEY1 不存在」。
 · 第 21 轮（本轮）发现：**撤回是错的，原结论正确。**

【根因 —— 一个典型的判据失效】
 0x45670123 在固件里**从不以连续 4 字节形式出现**，因为它由两条 Thumb 指令拼成：
     movw r0, #0x0123     ; 低 16 位
     movt r0, #0x4567     ; 高 16 位
 ⇒ 字节序列是 `4F F2 23 00  C0 F6 67 40`，原始字节搜索当然 0 命中。
 ⇒ 「用原始字节搜索验证常量存在性」对 ARM Thumb 的 imm32 常量是**无效判据**。
 （同族错误的第 8 次：判据用在其适用边界之外。）

【正确的验证方法与结果】
 用滑动 MOVW/MOVT 配对解码（gap 2–16 B, 同 Rd）后：
     FOUND 0x45670123  at file 0x2410A  (movw@0x2410A, movt@0x2410E, r0)
     FOUND 0xCDEF89AB  at file 0x24114  (movw@0x24114, movt@0x24118, r0)

【★ 反汇编原文（0x240F0-0x24120）—— 教科书级 STM32 FLASH 解锁例程】
   0x240F0  movw r0, #0x2010
   0x240F4  movt r0, #0x4002          ; r0 = 0x40022010 = FLASH_CR
   0x240F8  ldr r0, [r0]
   0x240FA  lsls r0, r0, #0x18        ; 取 bit7 (LOCK)
   0x240FC  cmp r0, #0
   0x240FE  bpl  #0x8024120           ; LOCK=0 则跳过解锁
   0x24102  movw r1, #0x2004
   0x24106  movt r1, #0x4002          ; r1 = 0x40022004 = FLASH_KEYR
   0x2410A  movw r0, #0x123
   0x2410E  movt r0, #0x4567          ; r0 = 0x45670123  = KEY1
   0x24112  str  r0, [r1]             ; 写 KEY1
   0x24114  movw r0, #0x89ab
   0x24118  movt r0, #0xcdef          ; r0 = 0xCDEF89AB  = KEY2
   0x2411C  str  r0, [r1]             ; 写 KEY2  ==> 解锁完成
   0x24120  bx   lr

【★ 配套的 FLASH 全驱动（均为反汇编直读）】
 (a) FLASH_Lock()      0x23FA4: CR(=0x40022010) |= 0x80      ; set LOCK
 (b) FLASH_ErasePage() 0x23FD2-0x2400E:
        CR |= 2            ; PER (page erase enable)
        AR(0x40022014) = addr
        CR |= 0x40         ; STRT (start)
        wait(0xF0000 loops)
        CR &= ~2           ; clear PER
 (c) FLASH_Program()   0x24146-0x24174:
        CR |= 1            ; PG (program enable)
        *(addr) = data     ; 半字写入
        wait(0xF0000 loops)
        CR &= ~1           ; clear PG
 (d) FLASH_WaitBusy()  0x24074-0x240E8: 轮询 SR(0x4002200C) 的 BSY 等位
 ⇒ **芯片具备完整的片上 FLASH 擦/写/锁/等驱动。** 这对「刷入改后的固件」
    一条路线是直接相关的硬证据。

二、★★★ 第二个编程控制器：0x40003000 不是 I2C，是 SPI/EEPROM 命令口
================================================================================

【反汇编原文（0x24288-0x242B6）】
   0x24288  movw r1, #0x3000 ; movt r1, #0x4000   ; 0x40003000
   0x24290  movw r0, #0xaaaa ; str r0, [r1]       ; 写 0xAAAA
   0x24298  movw r1, #0x3000 ; movt r1, #0x4000
   0x242A0  movw r0, #0xcccc ; str r0, [r1]       ; 写 0xCCCC
   0x242A8  movw r1, #0x3000 ; movt r1, #0x4000
   0x242B0  movw r0, #0x5555 ; str r0, [r1]       ; 写 0x5555
   0x24212  ldr r0,[0x4000300C] ; and r0,#2 ; 轮询  ; 状态位等待
   0x24256  bfc r0,#0xc,#0x14 ; str r0,[0x40003008] ; 16 位数据/地址写

【判读】0x55 / 0xAA / 0xCC 三连写同一命令寄存器 + 独立 busy 位轮询，
 是 JEDEC SPI-NOR / EEPROM 的软件复位与命令握手序列。**与片上 FLASH
 (0x40022000) 是两个不同控制器。**
 ⇒ 本固件里有**两条独立的非易失存储写通路**。

三、★★ 更正：0x40005400 的 9 处引用不是 I2C 事务，是 GPIO 引脚助手调用
================================================================================

【第 19/20 轮与审计报告都判为「I2C1 驱动，0x40005400 ×9」】 → 部分错误。

【反汇编原文（0x1D406-0x1D432，重复 5 次同构）】
   0x1D408  push {r7, lr}
   0x1D40A  movw r0, #0x5400
   0x1D40E  movt r0, #0x4000          ; r0 = 0x40005400
   0x1D412  movw r1, #0x108
   0x1D416  movt r1, #0x50a           ; r1 = 0x050A0108
   0x1D41A  bl   #0x802473c           ; helper(r0=base, r1=pindesc)
   0x1D41E  cbz  r0, #0x801d432
   0x1D422  movw r0, #0x4128 ; movt r0, #0x2000 ; adds r0,#0xc
   0x1D42C  bl   #0x801d4d8

【helper 0x2473C 的反汇编 —— 明确是 GPIO 位操作】
   0x2473C  sub sp,#0x18 ; str r0,[sp,#0x10] ; str r1,[sp,#0xc]
   0x24748  ldr r0,[sp,#0x10] ; ldr r0,[r0,#4] ; and r0,r0,#0x400   ; 读 base+4 的 bit10
   0x24754  ldrh.w r1,[sp,#0xc] ; lsrs r1,r1,#6                     ; param>>6 = 寄存器号
   0x2475A  ldr r0,[r0,r1]                                          ; 数组索引取寄存器
   0x2475E  and r2,r1,#0x1f ; movs r1,#1 ; lsl.w r2,r1,r2           ; mask = 1<<(param&0x1F)
   0x24768  ands r0,r2                                              ; 测引脚电平
   0x24776  ubfx r2,r2,#0x10,#5                                     ; (param>>16)&0x1F = 引脚号
   ... 末尾 0x247C6 返回 0/1                                        ; 返回布尔
 ⇒ **这是 `gpio_get_pin(base, pindesc)`，不是 I2C 传输。**

【5 个 pindesc 参数解码（位域 [31:22]=端口 [20:16]=引脚 [7:0]=功能码）】
   0x050A0108 -> 端口 0x14(20) 引脚 10 功能 0x08
   0x05010109 -> 端口 0x14(20) 引脚  1 功能 0x09
   0x05060109 -> 端口 0x14(20) 引脚  6 功能 0x09
   0x05040109 -> 端口 0x14(20) 引脚  4 功能 0x09
   0x05070109 -> 端口 0x14(20) 引脚  7 功能 0x09
 ⇒ 同一「端口 20」的 5 个不同引脚。**不是从地址。**

【对用户核心疑问的意义】
 · 「0x5A/0x5B 是 I2C 从地址」这一线索（审计报告 L5/U1，我第 19 轮也曾引用）
   **不成立** —— `0x5A` / `0xB4` 在整个 0x1D300-0x1DA80 段内**立即数出现 0 次**。
 · 因此「触觉芯片通过 I2C 从地址 0x5A 通信」在本文件里**没有任何代码级锚点**。

五、★★★ 最有信息量的新数字：可压比 0.8797 —— 该区「不是随机，也不是代码」
================================================================================

用真 zlib 压缩器（不是熵估计器）测：
   固件 0x01200-0x19850 (99920 B) → zlib-9 = 87902 B   **比率 0.8797**
   对照 os.urandom (99920 B)      → 99961 B            比率 1.0004
   对照真 Thumb 码 (45056 B)      → 21264 B            比率 0.4719
   对照文本                       →                     比率 0.0088

【把 0.8797 的来源分解（round22）】
 (A) 512 B 块重复：195 块中 183 唯一，重复字节 6144 B = **6.15%**。
     去掉重复副本后比率 **0.9378**（仍显著 < 随机 1.0004）
     ⇒ 块重复只解释一部分，剩余 ~6% 冗余另有来源。
 (B) 熵分解：H0=**7.9978**（几乎满，字节分布**无显著偏斜**）
     条件熵 H1-H0 = **7.1009**（随机对照 7.4576）
     ⇒ *这个数字很关键*：条件熵比随机**低 0.36 bit**，
       说明「给定前一字节后，后一字节的不确定性略低于随机」
       = **存在极弱的字节间相关**。
     ⇒ 但 H0 仍是 7.9978 ⇒ **不是字符集偏斜**，是**序列层面的弱相关**。
 (C) lag 自相关（同位置字节相等率 vs 随机 1/256=0.003906）：
       lag=1  **0.01149  (2.94x)**   <== lag1 明显偏高
       lag=2   0.00595  (1.52x)
       lag=4   0.00539  (1.38x)
       lag=8   0.00485  (1.24x)
       lag=1024 **0.07152 (18.31x)**  <== 1024 周期仍存在（对应已知重复表）
       lag=2048 0.05633 (14.42x)
     ⇒ **lag=1 有 2.94x 相关** —— 这是「相邻字节弱相关」的直接证据，
        与 (B) 的条件熵下降互相印证。
 (D) 反推等效重复率：注入 10% 块复制 → 0.9061；15% → 0.8555。
     实测 0.8797 介于其间 ⇒ 等效「512 B 块级重复率 ≈ 12%」。

【★ 判读（这是本节最重要的推论）】
 · 若该区是**强分组密码**，则 C 的条件熵应为 7.999+（完全无相关）、
   lag1 应为 1.0x、可压比应为 1.000x。**实测三条全部偏离随机。**
 · 若该区是**普通过滤/白化**，也应接近满熵。仍偏离。
 · 偏离非常**弱**（可压比 0.88、lag1 2.94x、条件熵降 0.36 bit），
   **强加密不会留下这种痕迹，弱位置型变换/表格+填充会。**
 ⇒ 与第 19 轮「无强加扰、该区为表/填充/弱结构」的结论**方向一致**，
   而且这次是**用真压缩器 + 条件熵 + 自相关三重独立量**得到的，
   不再依赖那个已被反复证伪的 `|rel|≤8` 判据。

 ⇒ 结论：**该 96 KB 区不是强加密，也不是压缩；它是「弱相关的结构化数据」
   （表 + 填充 + 约 12% 的块级重复）。** 这解释了为什么
   「两个 agent 都说有加密」——高熵（H0≈8.0）**看起来**像加密，
   但条件熵/自相关/可压比三项都显示它并非密码学意义上的密文。

九、结论：对用户「是不是有加密」的最终回答
================================================================================
 问：GT7868Q 固件有没有加密？
 答：**没有在 0x01200-0x19000（96 KB）区留下任何强加密的痕迹。**
     三重独立量（真压缩器可压比 0.8797 / 条件熵低于随机 0.36 bit /
     lag1 自相关 2.94x）一致指向「弱相关的结构化数据」，而非密文；
     而密码学密文应使这三项全部落在随机基线上。
     「两个 agent 说有加密」的原因已定位：**高零阶熵（H0≈8.0）看起来像加密**，
     但零阶熵对**任何**均匀化处理（白化/压缩/加扰/密文）都会给出 8.0，
     它是**非特异判据** —— 这正是本项目反复踩坑的同一类错误。

 问：那 0x01200-0x19000 到底是什么？
 答：最可能是 **配置/参数数据区**（大量重复 512 B 表、约 12% 块级重复、
     弱 lag1 相关），而非代码、非压缩、非密文。

 仍未闭合（诚实边界）：
   · 该区若为表，表的语义未解（需要文档或对照明文固件）
   · 0x40003000 SPI 控制器背后的目标器件未知
   · 本文件是 2 MB flash 的部分镜像，向量表不在其中 ⇒
     **刷入通路（SPI 二次编程 vs 片上 FLASH）已看到两条，但未验证哪条
     用于真正更新触控板固件**

十、★★ 追加（同轮即时发现）：0x40005410 是 UART 数据寄存器，不是 I2C1_DR

【反汇编 0x1D540-0x1D5E8】
   0x1D554  movw r1,#0x5410 ; movt r1,#0x4000   ; 0x40005410
   0x1D55C  ldr r2, [r1]
   0x1D55E  uxtb r2, r2                          ; ★ 掩到 8 位 = 一个字符
   0x1D560  strh.w r2, [r0, #0x104]              ; 存进缓冲结构体
   0x1D570  strb r1, [r0, r2]                    ; 环形缓冲写入
   0x1D578  cmp r1, #0x7f                        ; 128 B 缓冲上限
   0x1D5D4  movs r1, #0x55 ; bl #0x80246b4       ; ★ 写入 0x55（串口字节）
   0x1D5B8  orr r2, r2, #0x40                    ; 置状态位（发送/使能）
【helper 0x246B4】strb r1 → *(struct+0x10)       ; 发送寄存器写
【helper 0x246DC】1 << (val & 0x1F) → struct[val>>6] |= mask  ; 置位（波特率/控制）
【helper 0x246C8】*(base) |= 1                   ; 使能位
【另一个块】0x1D6A2: r5 = 0x40005400 + 0xB800 = 0x40010C00 → 配 (0x1C,3,0x40/0x80)
   ★ 注意：0x40010C00 在 r1 被当成 GPIOB/外设基址使用，而 0x40005400 是参数传入的
⇒ **结论：这是一个「可参数化的串口/SPI 驱动」，base 由调用者传入（一个驱动服务多个串口）。**
   `uxtb` + 128 B 环形缓冲 + 字节发送 = UART 收发路径，**不是 I2C**。
   这**第二次**验证了纪律 19（基址常量 ≠ 外设身份）：`0x40005410「I2C1_DR」`也是我的误标。
   ⇒ 连同第 19 轮的「I2C1 = 0x40005400」，整个「I2C 驱动」判断**全部作废**。
   ⇒ **本文件里没有找到 I²C 主机驱动**；触觉芯片若走 I²C，其通路不在本镜像内。
   新线索（未闭合）：本固件含 **UART 收发路径**（可能对应 `%d\r\n` 调试口）。

十一、★★★ 重大更正：追加二十七 的「I2C 从机驱动 @0x0800894C」建在【数据表】上
================================================================================
【追加二十七 §五 原文主张】
  「I2C1 = 0x40005400 · 12 处真物化点全在 0x0800894C–0x08008B90」
  「IRQ31=0x08008978(I2C1_EV) / IRQ32=0x0800894C(I2C1_ER)」
  「OAR1 = 0x58 ⇒ 从机地址 0x2C」  ⇒  推出「TF100A 是从机、主机只能是 GT7868Q」

【本轮实测反驳（三条独立判据）】

 判据 1 —— 0x40005400 的物化点**根本不在 0x0894C**
   滑动 MOVW/MOVT 配对（同 Rd，gap 2-16）全文件扫描：
     0x40005400 → 仅 9 处：0x1D40A 0x1D436 0x1D45E 0x1D486 0x1D4AE
                            0x1D4F0 0x1D51C 0x1D5A8 0x1D644
     0x40005410 → 2 处：0x1D554 0x1D57C
     0x40005414 → 1 处：0x1D614
     **0x08008xxx 区一处都没有。**
   原始字节搜索复核：'00 54 00 40'（0x40005400 的 LE）= **0 次**；
                     '4C 89 00 08'（0x0800894C 的 LE）= **0 次**。
   ⇒ `0x0800894C` 不是"把 0x40005400 拼出来"，它本身**是一个 Flash 地址值**。

 判据 2 —— 0x0894C 落在 K 表里
   追加三十七 已确证 K 表副本在 0x08800 / 0x08C00 / 0x09000 / 0x09400。
   **0x08900 ∈ [0x08800, 0x08C00)** ⇒ 0x0894C 在 K 表副本内部。
   实测该区字节呈高度规则的重复模式（E2 4E 1E AC / 72 6A 4E CC …），
   是**均衡交织表**的形态，不是代码。

 判据 3 —— 该区**不是代码**（非法指令率）
   分段 udf 率：
     0x8900-0x8C00  = **0.0548**  ← 数据级（真代码应 <0.01）
     0x1E000-0x1E400 = 0.0020    ← 真代码
     0x1D300-0x1D600 = 0.0287    ← 混合（含跳转表/字面量池）
   ⇒ 0x8900 区的 5.5% udf 率说明**把它的字节当指令读是错的**。

【结论】
 ⇒ 追加二十七「TF100A 里有 I2C 从机驱动、OAR1=0x58、从地址 0x2C」这套结论
   **建立在把 K 数据表的字节误读成指令之上，整段作废。**
 ⇒ 由此推出的「TF100A 是从机 ⇒ 主机只能是 GT7868Q ⇒ 扳机在加密固件里」
   **链条断裂**：既不能证明 TF100A 是从机，也不能据此锁定 GT7868Q 为主机。
 ⇒ 这是本项目**同族错误（把数据当代码）的第 9 次**，且这次错了两轮之久
   （追加二十七 2026-09-29 → 今天 2026-09-30 才被推翻）。

【★ 唯一站得住的 I²C 相关事实】
   本固件里 0x40005400/0x40005410/0x40005414 的**全部**引用集中在 0x1D40A-0x1D644，
   而该簇经反汇编（round26/27）确认为 **GPIO 助手 + UART/串口收发驱动**，
   **不是 I²C**。⇒ **本镜像内没有找到 I²C 主机驱动，也没有找到 I²C 从机驱动。**
