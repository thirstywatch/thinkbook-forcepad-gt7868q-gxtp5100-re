## 第 0 章 · 动手前必须有的前置认识

这一章不教你做什么，而是告诉你**哪些直觉是错的**。本项目 20 轮的返工，80% 源于这里的某一条。

### 0.1 笔记本触控板不是"一个设备"，是"一条链"

| 层 | 是什么 | 本项目对应 |
|---|---|---|
| **器件层** | 模组里有几颗芯片 | GT7868Q（触控主控）+ TF100A（压力 MCU）+ AW86927（触觉驱动）+ LRA 马达 |
| **固件层** | 每颗芯片各有自己的固件，可能在同一文件里 | 主机下发的 BIN 里同时含 GT7868Q 容器 + TF100A 的 ARM 镜像 |
| **命令层** | **至少要分清四张表**（见 0.2） | — |
| **地址层** | 同一个数字在不同上下文指不同东西 | `0x2C` 既是主机总线上 GT7868Q 的地址，也是片内 I²C1 上 TF100A 的地址 |
| **总线层** | "主机能碰到"和"芯片之间能碰到"是两回事 | 主机 I²C0（可达但被驱动占）vs 芯片间 I²C1（主机完全够不到） |

> **★ 本项目最大的乱源，就是这五层被混为一谈。**

### 0.2 ★★★ 四张命令表，绝对别混

| # | 名称 | 器件 | 入口 | 条数 |
|---|---|---|---|---|
| **①** | TF100A 内部分派器 | TF100A | `0x0800E1C0` | **39**（`0x80`×1 + `0xA0`×16 + `0xA1`×22） |
| **②** | GT7868Q 内部分派器 | GT7868Q | `0x22C7C` | **16**（`0x0100`–`0x3500`） |
| **③** | GT7868Q 官方命令集 | GT7868Q | `CMD_ADDR 0x4160` | 约 10 |
| **④** | GT7868Q 主机报文 | GT7868Q | `0x1ACEC` | 6 种类型 |

> **① 与 ② 的命令号完全一致** ⇒ **那 16 条属 TF100A，GT7868Q 侧只是中继副本。**
> 所以**不存在"GT7868Q 有 16 条命令"这回事**。曾经据此得出的结论全部作废。

### 0.3 同一个符号可能指不同东西（符号消歧）

| 符号 | 指什么 | 属于哪条总线 / 哪一层 |
|---|---|---|
| `0x5A` / `0x5B` | **AW86927 的 I²C 从地址**（由 `AD` 脚配置） | 器件地址 |
| `0x5B80` / `0x5B94` / `0x5B96` | **GT7868Q 的 16 位 RAM 地址**（阈值表） | 芯片内部 RAM |
| `5A A5` | **GT7868Q 主机报文的魔数** | 主机 → GT7868Q |
| `0x2C`（主机总线） | **GT7868Q 的 I²C 从地址**（ACPI `_CRS` 权威） | 主机 → GT7868Q |
| `0x2C`（片内 I²C1） | **TF100A 的 I²C 从机地址** | GT7868Q → TF100A |
| `1` | ⚠️ **不是 I²C 地址** —— `Name (_ADR, One)` 只是 DSDT 模板遗留 | — |
| `0x1800` / `0x3800` | ⚠️ **两套**：① GT7868Q 参数区偏移 ② 主机报文类型 4 的写入目标 | — |

> **★ 规律**：项目里**大部分"矛盾"不是结论冲突，而是【同一个符号指了不同的东西】却没加限定词。**
> 修矛盾的正确做法常常不是"选一个"，而是**给每个符号加上"哪条总线 / 哪一层 / 哪个器件"的限定**。

### 0.4 三条已被实证关闭的路（别再走）

| 已被证伪的判断 | 真相 |
|---|---|
| 「装 Linux 就能读写参数区（`i2c-hid` 完整透传）」 | 依据的仓库只有 1,663 字节（描述符修补，不碰寄存器）；实测 Linux 下触控板**根本不工作** |
| 「并列 SPB 客户端可绕开 `hidi2c`」 | 微软：**同一外设的连接同时只能一家持有** |
| 「找固件解密密钥」 | **问题不成立**：那 BIN 是 UEFI 胶囊；且高熵区不是密文，是**周期 XOR 加扰** |

### 0.5 通用工作纪律（先背下来）

1. **只读优先。** 写入类命令永远放在最后，且必须先在料板上验证。
2. **任何"读不到 / 搜不到"的结论，中间必须隔一个阳性对照。** 没有阳性对照的"读不到"是无效结论。
3. **先解容器 → 拿到正确块边界 → 再做统计。** 在错误窗口上算出来的熵全是假的。
4. **验证 ARM/Thumb 的 imm32 常量必须反汇编或解码 MOVW/MOVT 配对，绝不能字节搜索。**
5. **大改前先快照。** 本项目一次正则批量替换把 12,000 行档案截断成 24 行。

## 第 1 章 · 侦察工作流总览

### 是什么

一套"从零开始搞清楚一个未知触控板模组"的 fixed 流程。核心思路是**先分清层、再逐层拿证据、每层都标注证据强度**。

### 做什么

```
① 资产采集      固件 / ACPI / HID 描述符 / 驱动文件     （只读，零风险）
        ↓
② 容器解析      BIN 是什么格式？边界在哪？               （纯离线）
        ↓
③ 加扰破解      高熵区能不能还原？                        （纯离线）
        ↓
④ 反汇编追踪    代码在哪？命令分派器在哪？输出到哪？       （纯离线）
        ↓
⑤ 主机侧探测    HID 能发什么？设备栈长什么样？             （真机，只读）
        ↓
⑥ 总线边界      I²C 能不能碰到目标器件？                   （真机，高风险）
        ↓
⑦ 固件侧旁证    EC / ACPI / BIOS DXE 有没有别的通路？      （真机 + 离线）
        ↓
⑧ 收口          逐环节定级，判断"路走不走得通"
```

### 得到什么结果

一张**逐环节证据分级表**（见 `docs/08-findings/`），能明确说出"哪一段已确认、哪一段是推断、哪一段完全没有证据"——而不是一句笼统的"搞清楚了"或"搞不清楚"。

## 第 3 章 · 固件解包与容器解析

> 详细版：`02-firmware-unpack.md`

### 是什么

回答三个问题：**这个 BIN 是什么格式？里面有几段？每段的精确边界在哪？**

本项目最大的教训：**所有统计（熵、零填充、自相关）都必须跑在正确的块边界上，否则结论全是假的。** 早期所有"高熵区"分析都跑在错误边界 `0x1400–0x19800` 上（跨块 + 偏移 452 B），导致后续结论连环出错。

### 做什么

**步骤 1：判断文件是几层**

```
本机 TB14P_GT7868Q_14030522_20240202.BIN 实测三层：

0x00000 .. 0x0113C    4,412 B    外层清单（4 × 1084 B 记录，★ 明文，含配置副本）
0x0113C .. 0x19A3C  100,608 B    ★ 一个完整的官方 Goodix 容器（校验和通过）
0x19A3C .. 0x19ABC      128 B    分隔（仅首 2 字节 04 14）
0x19ABC .. 0x2775C   56,480 B    TF100A ARM 固件（SP=0x200076C8, Reset=0x08005165）
```

> ⚠️ **曾经的错误**：从文件偏移 0 解析 Goodix 容器，得到「PID 全 0 / 子固件数 0 / 校验和失配」，据此宣布"不是这个格式" —— **这是假否定**，因为容器起点在 `0x113C`。
> **⇒ 正确做法：用官方校验和去"扫"容器起点，而不是假设它从 0 开始。**

**步骤 2：按官方结构体解析容器**

汇顶官方结构（`goodix_gtx8_update.c` / `gt7868q_firmware_image.h`，`#pragma pack(1)`）：

```c
#define FW_HEADER_SIZE        256
#define FW_SUBSYS_INFO_SIZE   8
#define FW_SUBSYS_INFO_OFFSET 32        /* 表项自 +0x20 起 */
#define FW_SUBSYS_MAX_NUM     28
#define GT7868Q_SUB_FW_DATA_OFFSET 256  /* 数据区自 +0x100 起 */

struct fw_subsys_info { u8 type; u32 size; u16 flash_addr; };
```

官方读取代码（`gt7868q_update.cpp:213-242`）—— **这就是子固件表的真格式**：

```c
sub_fw_type      = fw_data[pos];
sub_fw_len       = fw_data[pos+1]<<24 | fw_data[pos+2]<<16 | fw_data[pos+3]<<8 | fw_data[pos+4];
sub_fw_flash_addr= (fw_data[pos+5]<<8 | fw_data[pos+6]) << 8;
fw_image_offset += sub_fw_len;   /* ★ 文件里就是【顺序平铺】，与 flash_addr 无关 */
sub_fw_info_pos += 8;
```

**步骤 3：逐字段对账（本机实测）**

| 字段 | 偏移 | 值 |
|---|---|---|
| `size`（u32 BE） | +0 | **100,602**（0x188FA） |
| `checksum`（u16 BE） | +4 | **0x5F37** —— `sum(payload) & 0xFFFF` **逐字节通过** ✅ |
| `hw_pid[6]` | +6 | **`YELSTO`**（= YELLOWSTONE） |
| `hw_vid[3]` | +12 | `00 00 06` |
| `fw_pid[8]` | +15 | **`7868Q`** |
| `cid` + `fw_vid[3]` | +23 | `0x1C` · `02 03 05` |
| `subsys_num` | +27 | **13** |
| `chip_type` | +28 | `0x95` |
| `protocol_ver` | +29 | `0x02` |
| 子固件表 | +0x20 | 13 × 8 B |
| 数据区 | +0x100 | 100,352 B（0x18800） |

**★ 自洽校验**：13 条 `size` 合计 = `0x18800` = 数据区长度 = `size + 6 − 0x100`。分毫不差。
（`+6` 是官方容器前缀：`u32 size` + `u16 checksum`。）

### 得到什么结果

- **13 个子固件的精确边界**（type / size / flash_addr / 绝对文件偏移）。
- 一个**通过官方校验和**的容器起点 —— 这是后续所有分析的地基。
- 明确"外层 4,412 B 是明文"这一事实（加扰**只覆盖容器的子固件数据区**）。

## 第 4 章 · ★ 周期 XOR 加扰破解（本项目最核心的一节）

> 详细版：`03-obfuscation-crack.md`

### 是什么

固件数据区看起来是随机噪声（H0 = 7.9977，接近理论最大 8.0）。问题是：**它是密文、压缩、还是加扰？**

**答案**：**1024 字节周期的 XOR 加扰（scramble），不是密码学加密。** 周期密钥 `K`（1024 B）可完整恢复。

```
plain[x] = raw[x] ^ K[(x + 316) % 1024]        # 316 = 容器相对相位
         = raw[x] ^ rot_left(K, 316)[x % 1024]
```

> 两种基准换算（数据区起点 = 容器 + 0x100）：**316（容器相对）≡ 572（数据区相对）**。

### 做什么

#### 步骤 1：先定性 —— 用三项定量判据排除"分组密码/压缩"

| 判据 | 实测值 | 随机基线 | 结论 |
|---|---|---|---|
| **真压缩器可压比** | **0.8797** | `os.urandom` 1.0004 · 真 Thumb 码 0.4719 · 文本 0.0088 | 偏离随机 |
| **条件熵 H1−H0** | 低于随机 **0.36 bit** | 随机 7.4576 vs 本区 7.1009 | 偏离随机 |
| **lag1 自相关** | **0.01149 = 2.94×** | 随机 0.00381 | 偏离随机 |

⇒ 密码学密文应使三项**全部落在随机基线上**；实测三项全部偏离，且**偏离很弱**
⇒ 排除"分组密码"和"压缩"，但**排除不了周期 XOR 加扰**（加扰恰好是一种能让三项判据都只呈现"弱偏离"的变换）。

> 🔴 **本项目最贵的教训**：当时从"三项偏离随机"外推出"所以没有加扰" —— 错的。
> **三项判据能排除的，和不能排除的，必须分开写。**

#### 步骤 2：恢复周期密钥 K

**K 的来源**：加扰区里如果有**大段零填充**，那么 `0 ⊕ K = K`，raw 里就会直接出现 K 的副本。

**★ 正确的三条判据（缺一不可）**：

| # | 判据 | 为什么可信 |
|---|---|---|
| ① | **字节直方图是否"人工配平"（卡方 ≈ 0）** | 真随机/真数据不会恰好让 256 个值各出现 4 次；keystream 才会 |
| ② | **穷举全部 1024 个相位 + 多份独立样本交叉验证** | 单样本选 1/1024 毫无统计力；**四份独立固件全部指向同一相位**才定案 |
| ③ | **解出后是否出现整块零填充** | 空白 flash 的正常形态；这是"解对了"的最强单点证据 |

**相位剖面（本机，1024 个相位，判据 = 13 块 H0 求和）**：

| 项 | 值 |
|---|---|
| 最优 | **572**（熵 7.0066） |
| 次优 | 60（熵明显更高） |
| 13 块求和 H0 的最小 / 均值 | **88.4678 @572** / 102.4734 |

#### 步骤 3：验证解对了

| 指标 | 加扰区（100,352 B） | 解出后 | 对照 |
|---|---|---|---|
| 熵 H0 | 7.9977 | **7.0066** | 随机 8.0 |
| 二元组熵 H2 | 15.100 | **12.395** | — |
| 零字节 | 0.36% | **14.99%** | 空白 flash 正常水平 |
| **最长连续零串** | **4 B** | **5450 B** | ★ **最硬的一条** |
| 子固件块数 | — | **13** | 官方 `subsys_num = 13` ✅ |

### 🔴 得到什么结果 + 一个必须记住的失败案例

**结果**：13 个子固件的明文全部解出，其中 `type=0x03 / flash_addr=0x0A000` 那块解出后 **74.16% 是零、最长零串 5450 B**（H0 仅 2.7385）—— 这就是"解对了"的铁证。

**必须记住的失败案例（循环论证）**：

项目曾花了两天论证「K 不是密钥」，列了五条"决定性证据"，**全部是循环论证**：

| 曾经的"证据" | 真相 |
|---|---|
| `tpfw.bin` 里 10 个「完美均衡块」 | 其实是 **10 处零填充**（`tpfw` 自己也加扰） |
| `tpfw[0x1C00:0x2000] == rot_left(K, 316)` 逐字节 0 误差 | **这恰恰是正确答案的相位！**（316） |
| K 的 256 个旋转变体在 `tpfw` 中命中 4619 处 | 连续斜坡 = 一整段零填充 |
| 45 对均衡块两两命中率 1.0000 | 同一零填充块的 1024 B 切片 |
| raw 中 2645 处 K 循环片段 | 实测 4438/4441 是**相邻位置**，只分 **3 段连续区** ⇒ 不是 2645 份副本，是 3 段零填充 |

**⇒ 从来不是"同一份数据重复铺 10 遍"，而是"10 段零填充把 K 照了出来"。**

**由此沉淀的错误纪律**：
> ~~一张表在文件里出现 ≥2 份完全相同 ⇒ 它是数据表，不是密钥。~~ ❌
> ✅ **正确纪律：当密钥候选来自数据自身时，"出现次数"完全不能作为判据（循环）。**
> 必须改用：① 直方图是否人工配平 ② 穷举相位 + 多份独立样本交叉 ③ 解出后是否出现整块零填充。

**★ 另一个致命陷阱：解出之后发现"不是代码"**
解出后 13 块的 H0 仍在 6.8–7.4，说明**载荷主体不是代码**（系数 / 基线 / 校准数据 / 空白）——
这曾经被误读为"解密失败"。**"读到的不是代码"是内容问题，不是可读性问题。**

## 第 5 章 · 反汇编与追踪

> 详细版：`04-disassembly.md`

### 是什么

对解出的固件做反汇编，回答：**代码在哪？ARM 还是 Thumb？加载基址是多少？命令分派器在哪？输出到哪个引脚？**

### 做什么

#### 步骤 1：确定镜像身份与基址（★ 三步解法，可直接照抄）

以 TF100A 为例（本项目唯一能完整反汇编的镜像）：

| 步骤 | 做什么 | 得到什么 |
|---|---|---|
| **①** | 读向量表首 8 字节：`SP` / `Reset` | `SP=0x200076C8`、`Reset=0x08005165` |
| **②** | 用 `SP` 值反推 SRAM 基址（`0x20000000`）+ 用 `Reset` 值反推 flash 基址（`0x08000000`） | 确认是 STM32F1 类内存映射 |
| **③** | 用"文件偏移 ↔ 运行地址"的一对锚点求加载偏移 | **加载基址 `0x08005000` ↔ file `0x19ABC`** |

> 🔴 **曾经的错误**：把 TF100A 加载基址当作 `0x08000000`。正确值是 **`0x08005000`**，经**三重交叉验证**定案。
> 另有一段 `0x19A00–0x2775C` 的 ARM 代码曾被归给 GT7868Q，实际是 **TF100A** —— **归属错误**。

**★ 区分两个程序、两套地址空间**：GT7868Q 与 TF100A 是两颗不同的芯片，**它们的地址不得混在一张表里用**。

#### 步骤 2：指令集判定（★ 必须做四类反例标定）

| 判据 | 陷阱 |
|---|---|
| ~~"Thumb 消费字节%"~~ | 🔴 **不专一**：在**全 0x00 上给 100%**、在**英文清单上给 94.7%** ⇒ 它只是"非随机判据"，不是"代码判据" |
| **真代码对照** | 同类真明文固件 GT7936L（BERLIN 族）代码段 Thumb 覆盖 **64.1%**；而本项目载荷 13 块最高 **2.4%** |

> **★ 纪律：凡"覆盖率/消费率"型判据，必须做【真代码 · 随机 · 全零 · 纯文本】四类反例标定。**
> **凡判据在"全零/文本"上也给高分，就不能用来判代码。**

用 capstone 实测：**13 块明文全部不是代码**（含基线标定）。

#### 步骤 3：定位命令分派器 + 建调用图

| 目标 | 方法 | 本项目结果 |
|---|---|---|
| 分派器入口 | 找"取子命令 → 跳表/连续 cmp"的模式 | TF100A `0x0800E1C0`（39 条） |
| 命令全集 | 从分派器穷举所有合法值 | `0x80`×1 + `0xA0`×16 + `0xA1`×22 = 39 |
| 调用图 | 脚本提取 caller/callee | 见 `tools/analysis/` |
| **输出端追溯** | **反向**：从"输出"倒推到引脚 | 输出例程 `0x08005E38`，**全 asm 唯一调用点 `0x08005B8C`** |

#### 步骤 4：输出端反向追溯（★ 本项目最有价值的一次追踪）

> **思路**：不去猜"哪条命令能震"，而是**从"震动"这个可观测现象倒推到引脚**。

| 环节 | 结果 |
|---|---|
| 判据 | `|Δ压力| > 40`（立即数 `0x28`） |
| 检测引擎 | `0x080059E0`（**三任务共用的检测引擎**，不是专属） |
| 点击阈值 | **140 按下 / 98 抬起**（2760 条报文实测） |
| 输出 | `PA3` 门铃（`0x0800D8B2` → GPIOA BRR）+ `A2` 异步回复帧（`0x08008A70` 打包器） |
| **★ TF100A 不驱动 LRA 的四条否定证据** | ① 全 asm 无马达/PWM/定时器写 ② `CR1.START` 全镜像 0 次 ⇒ 只做从机 ③ 无执行器路径 ④ TIM2=200 Hz **不是马达时基** |

### 🔴 得到什么结果 + 三个必须知道的陷阱

**结果**：链路**闭合**了（测压 → 判据 → 检测 → 上报），但**终点不是马达**。 ⇒ **"链路闭合但到不了马达"**。

**陷阱一：32 位常量搜索的假否定**

| 案例 | 错误做法 | 真相 |
|---|---|---|
| `FLASH_KEY1 = 0x45670123` | `D.count(b'\x23\x01\x67\x45')` → "不存在" | 在 `0x2410A`，由 `movw r0,#0x0123` + `movt r0,#0x4567` 拼成，**从不以连续 4 字节出现** |

⇒ **验证 ARM/Thumb 的 imm32 常量必须用 MOVW/MOVT 配对解码或真反汇编，绝不能字节搜索。**

**陷阱二：`0xA2` 是异步产物，不是命令的同步应答**
⇒ **"没收到 `A2`"不能证明设备拒绝。**

**陷阱三：`0x20004090` 是一块 16 字节控制块**，那三个 `cmp #N` **不是子命令编号**（曾误读）。

## 第 6 章 · 主机侧探测（HID 通道）

> 详细版：`05-hid-probing.md`

### 是什么

回答：**Windows 主机到底能对这个设备发什么？** 这是判断"纯软件能不能控制触觉"的直接依据。

### 做什么

#### 步骤 1：枚举四个集合，读描述符

本机四个 HID 集合：

| 集合 | 用途 | `OutputReportByteLength` | `FeatureReportByteLength` |
|---|---|---|---|
| `Col01` | Mouse 应用集合（兼容模式） | — | — |
| **`Col02`** | **Windows Precision Touchpad 顶集合** ★ | **0** ← ★★ | 有 |
| `Col03` | — | — | **1 个报表、3 字节总长**（不是 3 个报表） |
| **`Col04`** | **厂商定义通道** | **65** | — |

> ### ★★ 关键结论：`Col02` 的 `Out = 0`
> 这不是"没抓到"，是**物理上发不出去**。微软 PTP 规范里 Manual Trigger / Waveform / Duration 三个 usage **本机一个都没有**。
> ⇒ **主机侧不存在标准触觉触发面。**

#### 步骤 2：查设备栈（有没有第三方 filter）

```
四集合 UpperFilters / LowerFilters 全空
Col02 / Col04 无专属 Service
⇒ 链上只有 inbox hidclass + hidi2c
```

#### 步骤 3：查进程

全系统 311 进程，0 个 Goodix / 联想触控板相关进程。

#### 步骤 4：真机只读探测（`Col04` 的 rid=14 通道）

⚠️ **必须遵守红线**：单次事务 ≤ 32 B、间隔 ≥ 500 ms、**禁止批量轮询**。

| 探测项 | 结果 |
|---|---|
| `0x96F8` 区 | ✅ **读得出，且与离线配置体逐字节一致** —— 证明通道可用、读值可信 |
| `0x1800` / `0x3800` | 🔴 **读得出但读不稳** ⇒ **不可作数据、更不能据此做写实验** |
| `0x20` 读单报表上限 | **60 B** |
| **32 位地址读** | 🔴 **判否**（带阳性对照） |

### 🔴 得到什么结果 + 两个致命陷阱

**结果**：主机侧触觉控制面**结构性封死**（三条独立硬事实）。 ⇒ 以下两个实验**不要做**：
- 「HID OUT 报告记录器」（含 KMDF filter）—— 由判据 1，做出来**必然是空的**。
- **用 ETW 判"有没有 OUT 报告"** —— `Microsoft-Windows-SPB-HIDI2C` 的 opcode 全表**没有任何 Write 类事件** ⇒ **必然假阴性**。

### ★★★ 但有一个反向证据：高频读 Col04 会【抑制】全部震动反馈

> **这是全项目唯一证明「主机能影响震动路径」的现象 —— 虽然方向是"抑制"而不是"触发"。**

| 项 | 内容 |
|---|---|
| **实测** | 一次 89.7 秒的全量 dump 期间一直按住触控板：**期间没有任何震动反馈，松手（停止读取）后才有反馈**；平时（不读时）按下会震 |
| **★ 结论** | **高频读 Col04 抑制【所有】震动反馈 —— 按下与抬起都被抑制** |
| **推论** | 震动触发**不在内存数据层面**，而在**固件 ↔ 主机 I²C 通信**层面：固件在"按下/抬起"时刻需要与主机完成某种事件交接，被读占住 I²C 从机后该交接失败 ⇒ 震动被跳过 |
| **价值** | ① 解释了"为什么写内存永远无效"—— **固件根本不看那块内存**<br>② 与「震动是两次、与点击状态机的两个跳变沿同源」完全自洽 |

> 🔴 **2026-10-03 更正（重要）**
> 早期文档写作「抑制『**按下**震动』、**不影响**『松开震动』」—— **这个表述是错的。**
> **实际抑制的是【所有】震动反馈（按下 + 抬起）。**
> 误读来源：原观察是"松手的时候有反馈回来"，被理解成"松开这一路不受影响"；
> 真相是**读取停止后**震动恢复，而非"松开这一路免疫"。

**由此闭合的证据链**：

```
主机能读 Col04 内存      ✅ 32 KB 全部可读
主机能写 Col04 内存      ✅ 100% 生效、能保持
固件是否消费这些写入     ❌ 否（全部注入实验 0 命中）
震动触发在哪一层         → 固件↔主机 I²C 通信层（证据：读能抑制它）
⇒ 主机侧"纯软件触发震动"：从"经验判断"升级为"机制解释"
```

**⇒ 由此衍生的一条开放方向**：既然读能**抑制**，那么改变读的**时序 / 地址 / 长度**能否**促进**（触发）震动？
这是缺口 B 唯一有正面证据的方向。 ⚠️ 但注意**观察者效应**：在这个通道上做注入实验会自我污染。

#### ★★★ 2026-10-03 收官：两条最硬的结论

| # | 结论 | 怎么证出来的 |
|---|---|---|
| **① 主机侧碰不到 AW86927 —— 不是工具不行，是它【平时断电】** | §19.33.18 / §19.33.19 | 五条 I²C 总线**全部**排查完毕，`0x5A` **不在任何一条上**；<br>全 DSDT 扫描无任何设备声明 `0x5A`/`0x5B`。<br>⇒ 触觉 IC 只在播放瞬间由 GT7868Q 上电，主机永远赶不上那个窗口 |
| **② 写注入系统性验证：全部无效** | §19.34.4 | 32 KB 可写空间内**逐一**写回验证，无一生效。<br>⇒ 与"高频读能抑制"互证：震动触发**不在内存数据层面** |

> 这两条把"为什么找不到那扇门"从**没扫到**升级为**结构性不可能**。
> 它对方法论的意义：**负结果要穷举到可陈述的边界，才配叫"关闭"** ——
> "我试了几个地址没成"不是结论，"32 KB 全空间逐一写回验证均无效"才是。

**陷阱一：字节序取决于请求地址的低 2 位**
> 读回的字节序**由请求地址的低 2 位决定**。不知道这条，读出来的数全是错的，而且错得很像真的。

**陷阱二：`Gx::Write` 的帧长度字段应该是 `+5`，不是 `+7`**
> 项目曾长期用 `+7`（官方是 `+5`）⇒ **所有写探针的每一帧都被设备静默丢弃**
> ⇒ 「39 条命令全表覆盖、无马达入口」这个结论**一度作废**（通道从未真正打开）。
> 修后实测：`+7` 时 `0x4160` 毫无变化；`+5` 时变成 `FF 00 00 00`（**写入落地**）。
> **这个 bug 的发现方式**：查官方源码的字段偏移，与自己的实现对账。

## 第 7 章 · I²C / SPB 边界

> 详细版：`06-i2c-spb.md`

### 是什么

回答：**主机能不能绕过 `hidi2c`，直接对模组里的触觉驱动 IC（AW86927）说话？**

### 做什么

#### 步骤 1：清点 ACPI 定义的控制器 vs Windows 实际暴露的

| 项 | 数量 |
|---|---|
| ACPI 定义的 I²C 控制器 | **16 个** |
| Windows 实际暴露 | **3 条** |
| 触控板所在 | `\_SB.PC00.I2C0`（`PCI 8086:7E78`，0:15.0），400 kHz，从地址 `0x2C` |

#### 步骤 2：逐条总线实测（本机 5/5 全部闭合）

| 总线 | 结果 |
|---|---|
| I2C0（触控板所在） | 已被 `hidi2c` 独占；用户态明文禁止发 SPB 请求 |
| I2C2 / I2C3 | ❌ **BAR 基址 = 0**（`0x4` 属性位、无地址；`restart-device` 成功但**不分配**）⇒ 主机不可访问 |
| I2C4 / I2C5 | 同形态，已扫清 |
| PCH SMBus | ❌ 已排除（**有阳性对照 `0x44`**） |

#### 步骤 3：Windows 侧三条路线与可行性

| 路线 | 做法 | 代价 / 前提 |
|---|---|---|
| **W1** | 关 HVCI + 驱动黑名单 → 用 RWEverything 直打 MMIO | 最快，**降安全性**；**唯一完全不动 Secure Boot 的路** |
| **W2** | 自写 PawnIO 模块直驱 I²C 控制器 MMIO | 🔴 **PawnIO 校验 RSA-4096 签名**，官方版只加载官方签名模块 ⇒ 要提交上游签名，或装 Unrestricted edition（= 未签名内核驱动 ⇒ 关 Secure Boot） |
| **W3** | 补 ACPI 节点（SSDT 覆盖）+ 自签 KMDF SPB 客户端 | 唯一可长期留驻形态，代价最高 |

**★ 硬约束（微软文档原文）**：SPB 驱动只能用**自己硬件资源里带的 connection ID**，而它由 **ACPI `_CRS`** 决定；**用户态明文禁止**发 SPB 请求。
本轮实证：**全 DSDT 里没有任何设备声明在 `0x5A`。**

#### 步骤 4：Linux 侧交叉验证

```bash
# 前提：先解绑 i2c_hid，让总线安静；单点读，不要用 -y 全扫
# ⚠️ lost arbitration 不要过度解读（三条理由见详细版）
```

> ⚠️ **`0x5A` 没扫到**只有在"扫对总线 + `i2c_hid` 已解绑"时才成立。
> ⚠️ 触控板那条总线上 `i2cdetect` **会崩内核**。

### 得到什么结果

**"主机侧不存在任何可达 AW86927 的 I²C 通道"**（5/5 定案）。

> 🔴 **工具陷阱**：RWEverything 的 `Access → I²C/SMBus` 走的是 **PCH SMBus（i801）**，**不是**触控板所在的 `\_SB.PC00.I2C0`（DesignWare MMIO）⇒ **照它做必然是假阴性**。

## 第 8 章 · EC / ACPI 线

> 详细版：`07-ec-acpi.md`

### 是什么

排查"震动是不是由 EC（嵌入式控制器）参与/触发的"。这是**淘汰法唯一漏掉的候选**，必须实测关闭。

### 做什么

#### 步骤 1：零权限导出完整 ACPI（★ 可复用技巧）

```
HKLM\HARDWARE\ACPI\<表键>\<OEMID>\<OEMTABLEID>\<REV>  →  值名 "00000000" = REG_BINARY
★ SSD1..SSDS 是【平级表键】，不是 SSDT 的子键  ← 曾经漏掉这条导致只导出 3 张表
```

**iasl 反编译正确用法**：
```bash
iasl -e <SSDT...> -d <DSDT.bin>
# ❌ 反编译模式不能用 -o <path>（报 "Option requires a single-character suboption: -o"）
```

产物：32 表 / 761,859 B；DSDT 反编译 100,645 行 / 3.82 MB。

#### 步骤 2：扫描触觉关键词

结果：**全部 0 命中**。

#### 步骤 3：EC RAM 差分实验（★ 决定性）

| 工具 | 用法 |
|---|---|
| PawnIO | `pawnio_open → pawnio_load(blob) → pawnio_execute(handle, "ioctl_xxx", in, out, &retSize)`；模块放同目录；**需要管理员**（`0x80070005` = 权限不足） |
| `LpcACPIEC.bin` | ACPI EC 模块（端口仅 `0x62`/`0x66`），`RD_EC` 握手 |

**实验设计**：6 相位（IDLE / TOUCH / LIGHT / HARD / HOLD / IDLE2）× 6 轮 + 静置噪声对照 + 稳定性过滤。

**★ 只读保证**：`0x81`（写）出现 **0 次**。

#### 得到什么结果

| 阶段 | 结果 |
|---|---|
| 自检 | ✅ `pawnio_open HR=0`、`pawnio_load HR=0`（2612 B）；3×256B 连读非 0xFF、MD5 逐轮不同（RAM 活跃） |
| 采集 | ✅ 6 相位 × 6 轮 |
| 分析 | **⚠ 全零**：所有相位"变化 > 噪声底"的偏移 = **0**；**噪声底 = 98** |

> ⇒ **判定："EC RAM 未见与按压/震动相关的稳定活动" → EC 线关闭**。
> **★ 保留意见（诚实标注）**：① 噪声底 98 偏高 ⇒ 灵敏度有限；② 若 EC "不经 RAM、直接驱动硬件"，本判据**测不出**。
> **⇒ "全零"只能得出"在此灵敏度下未见"，不能升格为"不存在"。**

- `TPID` 五厂商表；`IICBADR0` 的真身 = 从地址（**不是 `_ADR` 的 `1`**）。
- `_DSM` 完整伪 ASL、`_CRS` 资源模板机制见 `docs/06-ec-acpi/`。

## 第 9 章 · cfg 语义分析

### 是什么

`tpcfgsid*.cfg` 是汇顶触控芯片的**配置文件**，由主机在初始化时下发给芯片。搞清它的格式，就知道**触觉参数是否可由主机配置**。

### 做什么

#### 步骤 1：文件头结构（64 B，定案）

| 偏移 | 字段 |
|---|---|
| `0x3B` | `u16LE` = TLV 区长度 |
| `0x3D` | `u8` = 条目数 |
| **`0x40`** | TLV 区起点 |

**★ 自校验闭合**：`0x40 + 1238 = 1302` ✅（= 文件长度）

#### 步骤 2：★ 帧序定案 `[LEN:u8][TAG:u8][payload: LEN-2]`

> 🔴 **旧线的 `[TAG][LEN]` 是反的。** 同起点 `0x40` 头对头对比：
> `[LEN][TAG]` 覆盖 **94.8% / 96.4%**，而 `[TAG][LEN]` 覆盖 **0.0%**；
> 且 **`[LEN][TAG]` 下 55 / 53 条 TAG 严格递增 1.00**。

#### 步骤 3：TAG 命名空间跨厂商共享

- sid0（Xiaomi 7867）vs sid3（LaiBao 7986P）**共有 40 个 TAG**；**`TAG 0x5C` 逐字节相同**。
- **触觉配置区 = `TAG 0x50 – 0x7A`**：
  - `0x5C` = 时长阶梯模板（10, 20, 80, 800, 1000, 2000, 8000, 10000 … ms）
  - `0x5D` = 机型相关档位（32,64,192 vs 64,128,192）
  - `0x50` / `0x60` / `0x68` = 以 **128 为零点**的 ± 微调表（u16）

#### 步骤 4：三方对齐（固件配置体 vs cfg vs 设备活体 `0x96F8`）

| 结论 | 内容 |
|---|---|
| ★ | **固件配置体与 cfg 只共享 `TAG 0x01`（索引表）** |
| ★ | **触觉区在固件配置体里 0 命中** ⇒ 触觉参数**只随 `tpcfgsid<sid>.cfg` 下发** |
| ★★ | **三份 cfg 的机型归属**：`x_108e1f62`→MARSEI(sid0=7867)；`x_driver_e`→BERLIN(sid3=7986P)；`x_ee49202f`→NOR_G1(sid2=7863)。**⇒ 都不是本机** |
| ★★★★ | **但本机的 cfg 映像一直就在我们自己的固件里**（外层 4,412 B 明文，含 4 份配置副本，与活体 `0x96F8` **逐字节相同**） |

### 得到什么结果

- 一套**可复用的 cfg 格式知识**（文件头 + TLV 帧序 + TAG 命名空间）。
- 官方命名佐证：较新 `tpupdate_driver.dll` 有整套 `cfgUpdate*`（`Chip cfg version ↔ cfg file version` 双向比对、`Write cfg data to 0x%04X`）。
- **⇒ 触觉参数确实由 GT7868Q 接收并配置** —— 但**参数不等于触发**，主机仍无法"让它在某一刻震"。

## 第 10 章 · 收口：怎么判断"这条路走不走得通"

### 是什么

做完前面九章，你手上会有一堆"能"和"不能"。这一章是怎么把它们变成**一个可执行的决策**。

### 做什么

**判据：投资优先级 = 证据强度 × 可改性**

> 两条腿，缺一即降级。

| 路线 | 证据强度 | 可改性 | 判定 |
|---|---|---|---|
| HID 标准触发 | 高（`Out=0` 是硬事实） | 0 | ❌ 关闭 |
| Col04 内存写 / 命令 | 高（39 条全表无马达入口） | 0 | ❌ 关闭 |
| GT7868Q 阈值表 | 中 | 低 | ❌ 关闭 |
| 主机 I²C 通道 | 高（5/5 闭合） | 0 | ❌ 关闭 |
| EC | 中（灵敏度有限） | 低 | ❌ 关闭（保留意见） |
| **TF100A 固件补丁** | **高（镜像内逐字节验证）** | **高（明文 + 有刷写通道 + 校验算法已解）** | ✅ **唯一** |

### 得到什么结果 —— 本项目的收口

**TF100A「40 → 8」补丁**：

| 项 | 值 |
|---|---|
| 原理 | 震动判据 = `|基线 − 当前| > 40`，`40` 是两处 Thumb 指令的立即数 `0x28`；**改成 8 ⇒ 判据变灵敏 ⇒ 滑动时手指压力的自然波动反复跨过判据 ⇒ 反复触发点按链路** |
| 载体 | `TB14P_GT7868Q_14030522_20240202.BIN`（161,628 B） |
| 加载基准 | `0x08005000` ↔ file **`0x19ABC`** |
| 改动点 1 | `0x08005A90` ↔ file `0x1A54C`：`28 31` → `08 31`（`adds r1,#0x28` → `#0x08`），后随 `88 42` = `cmp r0,r1` ✅ 互证 |
| 改动点 2 | `0x08005ABC` ↔ file `0x1A578`：`28 39` → `08 39`（`subs r1,#0x28` → `#0x08`），后随 `88 42` ✅ 互证 |
| 差异 | **仅 2 字节**（段内另有 5 处同类字节，一律不碰） |
| sha256 | 原 `0033d075…` → 补丁 `f39f80e0…` |
| 回滚 | 原镜像从未被改动（只读）；回滚 = 用原件重刷 |
| **已知不确定项** | ① 8 未必一次到位（可 16/24 梯度调）② **副作用预警：假点击** ③ 运行期马达门控未定位（不影响本改动逻辑） |

**刷写通道**：**UEFI 胶囊 + BIOS 侧 `GoodixTpDxe`**（**不走 HID** ⇒ 天然绕开"两次打挂均在 I²C-HID 层"的老坑）。
已知流程：`enter pass through → start updating → erase flash → write flash → reload subFW → reset ic`。
已知：更新器对 **TP / TF 两个子系统分别比对版本、分别刷写**（`GTPCheckTFUpdate`）⇒ **要让 TF 被重刷，必须让版本字段发生变化**。

剩余三步：**① 反汇编核实（版本号从哪读 / 有无哈希校验 / 触发条件）→ ② 触发方式核实 → ③ 零风险预演（先只改版本号、不动代码刷一遍）→ ④ 操作单 + 回滚**。

## 附录 · 关键参数速查

```yaml
器件层:
  GT7868Q:  汇顶触控主控 · ACPI\GXTP5100\1 · 主机 I²C 从地址 0x2C · 核为 8051(Turbo51)
  TF100A:   钛方压力 MCU · 片内 I²C1 从机 0x2C · STM32F1 类 = Cortex-M3（非 M4F）
  AW86927:  艾为触觉驱动 IC（丝印 CA4F）· I²C 地址 0x5A/0x5B · 11V H桥 · HDP/HDN = pin7/pin5

固件层（三个不同的东西）:
  TB14P_...BIN:  联想 UEFI FU 胶囊（外层明文清单 + Goodix 容器 + TF100A ARM 镜像）
  tpfw_*.bin:    Goodix 官方 GT7863 HID 固件（唯一通过官方校验）
  tpcfgsid*.cfg: 人可读导出格式（带元信息头），不是二进制 cfg 载荷

容器:
  起点 0x113C · 数据区 +0x100 · size u32BE@+0 · checksum u16BE@+4 = sum(payload)&0xFFFF
  hw_pid "YELSTO" · fw_pid "7868Q" · subsys_num 13 · chip_type 0x95 · protocol_ver 0x02

加扰:
  plain[x] = raw[x] ^ K[(x+316) % 1024]      # K = 1024 B
  相位   316（容器相对） ≡ 572（数据区相对）

地址层:
  TF100A 加载基址  0x08005000 ↔ file 0x19ABC
  写入/访问窗口    0x08019000 .. 0x0801FFFF（28 KB）
  参数区           0x1800(27B) · 0x2000(1092B) · 0x2C00(1092B) · 0x3800(8B)
  单字节标志       0x0444 / 0x2444 / 0x3044
  FLASH 控制器     0x40022000  KEY1=0x45670123  KEY2=0xCDEF89AB

命令层（四张表，必须声明是第几层）:
  ① TF100A 内部分派器  0x0800E1C0   39 条
  ② GT7868Q 内部分派器 0x22C7C      16 条（① 的中继副本）
  ③ GT7868Q 官方命令集 CMD_ADDR 0x4160  约 10 条

  0x82              仅为命令 0x80 的应答，需等约 250 ms
  0xFF              空闲是常态，不是"接受信号"

  不要以为装 Linux 就能读写参数区
  不要把 TF100A 的 39 条当成 GT7868Q 的
  不要把 .cfg.txt 直接当 cfg 载荷下发
```
