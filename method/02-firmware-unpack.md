# 02 · 固件解包与容器解析

> **是什么**：回答"这个 BIN 是什么格式、有几段、每段精确边界在哪"。
> **做什么**：判层数 → 扫容器起点 → 按官方结构体解析 → 自洽校验。
> **得到什么**：13 个子固件的精确边界表（后续所有统计的地基）。

---

## 一、★ 为什么这一步必须先做对

> **所有统计（熵、零填充、自相关）都必须跑在正确的块边界上，否则结论全是假的。**

本项目早期所有"高熵区"分析都跑在**错误边界** `0x1400–0x19800` 上（跨块 + 偏移 452 B），
导致后续"是不是加密""重复率多少"等结论**连环出错**。

---

## 二、步骤 1：判断文件是几层

**不要假设容器从文件偏移 0 开始。**

本机 `TB14P_GT7868Q_14030522_20240202.BIN`（161,628 B）实测**三层**：

```
0x00000 .. 0x0113C    4,412 B    外层清单（4 × 1084 B 记录，★ 明文，含配置副本）
0x0113C .. 0x19A3C  100,608 B    ★ 一个完整的官方 Goodix 容器（校验和通过）
0x19A3C .. 0x19ABC      128 B    分隔（仅首 2 字节 04 14，其余全 0）
0x19ABC .. 0x2775C   56,480 B    TF100A ARM 固件（SP=0x200076C8, Reset=0x08005165）
```

> ### 🔴 曾犯的假否定
> 从文件偏移 0 解析 Goodix 容器 ⇒ 「PID 全 0 / 子固件数 0 / 校验和失配」⇒ 宣布"不是这个格式"。
> **错。** 容器起点在 `0x113C`。
> **⇒ 正确做法：用官方校验和去"扫"容器起点。**

**外层记录结构**：4 条 × **1084 B**（步长 `0x43C`）。
记录 0 头 `73 c0 11 04 / 00 00 04 3c / 00 00 04 3c`，`+0x40` 起有 BE 值 **`0x18900`(100,608) / `0xDD20`(56,608)** —— 正好是两个载荷的尺寸。
记录 1–3 **两两相同**（= 活体 `0x96F8` 配置块 ×3 副本）。

**⇒ 外层是明文，未被加扰；加扰只覆盖容器的子固件数据区。**

---

## 三、步骤 2：按官方结构体解析

汇顶官方（`goodix_gtx8_update.c` / `gt7868q_firmware_image.h`，`#pragma pack(1)`）：

```c
#define FW_HEADER_SIZE        256
#define FW_SUBSYS_INFO_SIZE   8
#define FW_SUBSYS_INFO_OFFSET 32        /* 表项自 +0x20 起 */
#define FW_SUBSYS_MAX_NUM     28
#define GT7868Q_SUB_FW_DATA_OFFSET 256  /* 数据区自 +0x100 起 */

struct fw_subsys_info { u8 type; u32 size; u16 flash_addr; };
```

官方读取代码（`gt7868q_update.cpp:213-242`）—— **这就是子固件表的真格式**：

```c
sub_fw_type       = fw_data[pos];
sub_fw_len        = fw_data[pos+1]<<24 | fw_data[pos+2]<<16 | fw_data[pos+3]<<8 | fw_data[pos+4];
sub_fw_flash_addr = (fw_data[pos+5]<<8 | fw_data[pos+6]) << 8;
fw_image_offset  += sub_fw_len;   /* ★ 文件里就是【顺序平铺】，与 flash_addr 无关 */
sub_fw_info_pos  += 8;
```

> ### ★ `size` 是 **u32 大端**，`flash_addr` 左移 8 位 —— 这两个细节错了全盘皆错。

## 四、步骤 3：逐字段对账（本机实测）

| 字段 | 偏移 | 值 |
|---|---|---|
| `size`（u32 BE） | +0 | **100,602**（0x188FA） |
| `checksum`（u16 BE） | +4 | **0x5F37** —— `sum(payload) & 0xFFFF` **逐字节通过** ✅ |
| `hw_pid[6]` | +6 | **`YELSTO`**（= YELLOWSTONE） |
| `hw_vid[3]` | +12 | `00 00 06` |
| `fw_pid[8]` | +15 | **`7868Q`** |
| `cid` + `fw_vid[3]` | +23 | `0x1C` · `02 03 05` |
| `subsys_num` | +27 | **13** |
| `chip_type` | +28 | `0x95` |
| `protocol_ver` | +29 | `0x02` |
| 子固件表 | +0x20 | 13 × 8 B |
| 数据区 | +0x100 | 100,352 B（0x18800） |

### ★ 自洽校验

```
13 条 size 合计 = 0x18800 = 数据区长度 = size + 6 − 0x100
```

（`+6` 是官方容器前缀：`u32 size` + `u16 checksum`。）**分毫不差。**

## 五、步骤 4：13 个子固件边界（本机）

数据区起点 `0x123C`，块按表序**顺序平铺**：

| # | type | size | flash_addr | 绝对 file_off | 明文 H0 | 零% | 最长 0 串 | ASCII% |
|---|---|---|---|---|---|---|---|---|
| 0 | 0x01 | 0x0800 | 0x0FF00 | 0x00123C | 7.2140 | 4.93 | 4 | 33.8 |
| 1 | 0x03 | 0x2000 | 0x16000 | 0x001A3C | 7.0930 | 13.24 | 858 | 31.2 |
| 2 | 0x03 | 0x2000 | 0x06000 | 0x003A3C | 6.8097 | 18.03 | 1034 | 27.9 |
| 3 | 0x03 | 0x2000 | 0x08000 | 0x005A3C | 7.1892 | 10.05 | 68 | 31.3 |
| **4** | 0x03 | 0x2000 | **0x0A000** | 0x007A3C | **2.7385** | **74.16** | **5450** | 9.0 |
| 5 | 0x03 | 0x2000 | 0x0C000 | 0x009A3C | 7.1458 | 8.41 | 68 | 32.1 |
| 6–12 | … | … | … | … | … | … | … | … |

> **块 4（`flash_addr = 0x0A000`）解出后 74.16% 是零** —— 这是"加扰破解解对了"的最强单点证据。
>
> ⚠️ **跨芯片比对时必须按 flash 地址对齐，不是按序号。** 曾发现 `0x0A000` 跨芯片形态突变（槽位数按型号裁剪）。

## 六、官方刷机流程（供刷写参考）

已知流程（来自 `GoodixTpDxe` 反汇编）：

```
enter pass through → start updating → erase flash → write flash → reload subFW → reset ic
```

| 项 | 内容 |
|---|---|
| 通道 | **UEFI 胶囊**（`UEFI\RES_{B6AE105A-…}`、`oem87.inf`、DriverVersion 0.0.2.8）+ BIOS 侧 `GoodixTpDxe` —— **不走 HID** |
| 触发器 | `C:\Windows\Firmware\*.BIN` 落地 + `Class=Firmware` INF（`FirmwareVersion=0x14030522`）+ UEFI 设备树条目 |
| 版本机制 | **TP / TF 两个子系统分别比对版本、分别刷写**（`GTPCheckTFUpdate`）⇒ **要让 TF 被重刷，必须让版本字段变化** |
| TF 版本串 | `5.21.01.23007`，位于 file `0x264EE` |

**⇒ 走 UEFI 胶囊天然绕开"两次打挂均在 I2C-HID 层"的老坑。**

## 七、检查单

```
□ 容器起点是"扫"出来的，不是假设的？
□ 官方校验和通过？
□ 各 size 合计自洽（= 数据区长度）？
□ 子固件块数 == subsys_num？
□ size 按 u32 大端解了？flash_addr 左移 8 位了？
□ 块按"顺序平铺"取偏移（不是按 flash_addr）？
□ 外层是否明文已确认？
□ 后续统计都跑在正确块边界上？
```
