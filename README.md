## 二、最终结论（先读这个）

### ★ 核心结论

> **主机侧不存在"触发震动"的接口，设备也不监听主机的触觉命令。**

**支撑它的实测（描述符层，非Linux）**：本机 PTP 主体集合 `Col02` 的 `OutputReportByteLength = 0` —— 主机**物理上发不出**触觉输出报表；Haptics 页 `0x0E` 下只有 `Intensity` 一个控件，没有微软规范要求的 `Manual Trigger (0x0E/0x21)`。

> 🔴 **2026-10-03 撤销一条早期依据**：曾把「Linux live USB 下指针不动、点按照样震」列为这条结论的
> 「决定性实测」。**该依据已撤销** —— 当时的 Linux 环境（shell live USB）中触控板**根本未被测试**，
> 驱动未接管，指针是否可动、是否震动**都不说明任何问题**。
> 详见 [矛盾与推翻登记表 §B1](docs/08-findings/00-矛盾与推翻登记表.md)。
> 核心结论本身不受影响（其依据是描述符与设备栈，见下表）。

### 三条独立硬事实（2026-10-02 闭合，互相独立、不需要抓包）

| # | 硬事实 | 依据 |
|---|---|---|
| 1 | **主机物理上发不出触觉命令** —— PTP 主体集合 `Col02` 的 `OutputReportByteLength = 0`。全设备只有厂商集合 `Col04` 有 `Out=65`，且它只有本项目和汇顶官方工具会用 | 描述符层 |
| 2 | **设备栈上没有任何第三方组件** —— 四集合 `UpperFilters`/`LowerFilters` 全空 ⇒ 链上只有 inbox `hidclass` + `hidi2c` | 设备栈层 |
| 3 | **无厂商触控板服务在跑** —— 全系统 311 进程，0 个 Goodix / 联想触控板相关进程 | 进程层 |

### 三层关卡（全部封死）

| 层 | 关卡 | 状态 |
|---|---|---|
| 第 1 层 | HID 描述符未声明触觉能力（无 Manual Trigger / Waveform / Duration） | ❌ 封死 |
| 第 2 层 | `hidi2c.sys` 独占 SPB 连接，微软规定同一外设连接同时只能一家持有 | 🔒 硬阻断 |
| 第 3 层 | 设备固件侧没有主机可调用的"触发"命令 | ❌ 封死 |

### ★★★ 但有一条反向证据：主机确实"碰得到"震动路径 —— 只是方向是抑制

> **高频读 `Col04` 会抑制【所有】震动反馈（按下 + 抬起都被抑制）。**
> 实测：89.7 秒全量 dump 期间一直按住触控板 → **期间无任何震动**，停止读取后恢复。

这是 2026-10-03 之前**唯一**证明「主机能影响震动路径」的现象：

| 项 | 内容 |
|---|---|
| 推论 | 震动触发**不在内存数据层面**，在**固件 ↔ 主机 I²C 通信**层面 ⇒ 解释了"为什么写内存永远无效"（固件根本不看那块内存） |
| 开放方向 | 既然读能**抑制**，改变读的**时序/地址/长度**能否**促进**（触发）？这是缺口 B 唯一有正面证据的方向 |

> 🔴 **2026-10-03 更正**：早期表述"只抑制**按下**震动、**不影响松开**"**是错的**。
> 实际抑制的是**所有**震动反馈；"松手才震"是**读停止后恢复**，不是"松开这一路免疫"。

> 🟢 **2026-10-05 后续**：「唯一证明主机能影响震动路径」这个说法**已过期** ——
> 现在有**第二条**：`0x09`（Col02 RID 9 / `0x0E/0x23` Intensity）**经实测能改震动表现**（写 0 = 静音）。
> ⚠️ 但**性质完全不同**：它只决定"**设备自主触发时用多大劲**"，
> **"任意时刻主动触发"仍然做不到**（缺 `0x0E/0x21 Manual Trigger`）。
> 🔴 **补正（2026-10-08）**：cfg 通道的"**跨重启保持**"**已被推翻** —— 写入**只在会话期内有效**（见下节与登记表 **B12**）。
> 本段结论本身（读抑制全部震动）不受影响。

详见 [`method/METHOD.md`](method/METHOD.md) 第 6 章。

### 纯软件路：主体已终止，但 2026-10-05 打开了一个新分支

| 路线 | 状态 |
|---|---|
| HID 标准触发 | ❌ 无 Manual Trigger（`Col02 Out=0`） |
| Col04 内存直写 / 厂商命令 | ❌ 固件不消费（**但见下方分支**） / 39 条命令全表无马达入口 |
| **★ `cfg_update` 专用命令通道（`0x96F8`）** | 🔴 **2026-10-13 反转**：`7E 00 02` 被官方源码正名为 `TS_CFG_REPLY_CHKSUM_ERR`（**失败**，不是"已应用"），而**按官方算法重算袋校验后**，本机**首次拿到 `0x7F` = `TS_CMD_CFG_OK`** ⇒ **"改 cfg"这条路重新打开**（登记表 **B36/B37/B38**）。<br>🟢 **2026-10-05 打通**：写入被 IC 接受（`7E 00 02`）。<br>🔴 **2026-10-08 更正**：~~跨重启保持~~ **是错的** —— 写入**只在会话期内有效**（会话一结束即回 flash 原值；登记表 **B12**）；`0x96F8` 实为**分时复用 RAM**。<br>⚠️ **未能证明可感知的参数效应**（`+0x115` 五档全不可靠）⇒ 是"通道通了"，不是"能调震动了" |
| **★ HID Feature `0x09`（Col02 RID 9）** | ✅ **2026-10-08 实证**：写 `0` ⇒ 震动反馈消失、写 `100` ⇒ 恢复。**主机侧唯一经实测能改震动表现的接口**。<br>⚠️ 但只决定"设备自主触发时用多大劲"，**不能主动触发**；且**不落盘**（登记表 **B14**） |
| GT7868Q 阈值表（`0x5B80` 区） | ❌ 老线已排除 |
| 主机侧 I²C 通道（5 条总线） | ❌ **5/5 闭合**（要么扫清、要么主机根本不可访问）<br>⚠️ **2026-10-13 补正（B33）**：那 **5 条是 Windows 侧**的 `I2C0/2/3/4/5` + PCH SMBus；Linux 侧 `i2cdetect -l` 有 **20 条**。本次在真实 Linux Live 下解绑 `i2c_hid_acpi` 后抽验 `i2c-0`/`i2c-1` 的 `0x5A/0x5B` ⇒ **全 NACK**，并发现 **`aw86927` 内核驱动在 x86 ACPI 上不可能 probe**（只有 `of:` 别名）⇒ **AW86927 主机可达性结案** |

| **TF100A 固件灵敏度补丁「40 → 8」** | ✅ 唯一有字节级目标的**设备侧**路径 —— 补丁镜像已生成，待刷写 |

> 🔴 BIN 本身**不入库**（厂商固件派生品）⇒ 改用可复现脚本

| **①** | **「cfg 硬墙」推翻** —— 官方 `gtx8` 源码给出**完整校验算法**：YS `sum(data[0..n-3]) == BE16(末 2 B)`；NOR `sum(data) & 0xFF == 0`。本机 1084 B cfg **27/27 袋全部通过**，结构首次完整（`head[2] = bag_num`，**不是「版本号」**） | 打开 7 周来第一个**合法改写流程** |
| **②** | **史上首次 `0x7F`（`TS_CMD_CFG_OK`）** —— 三例对照：**A** 原样 `7E 00 07`（`DATA_EQU`）· **B 合法改写 `7F 00 01 00 80`（成功）** · **C** 改数据不重算袋尾 `7E 00 02`（`CHKSUM_ERR`）。B/C **只差 2 字节** | 单变量铁证；同时给历史上三次 cfg「失败」**正名** |
| **③** | **官方地址表结案** —— 地址表 = 官方 cfg bin 包头 `reg_info`（14 项）；本机只读核验 `command=0x4160` / `cfg_addr=0x96F8` **与行为证据一字不差**；`0x4018` = ASCII `YELSTO` ⇒ **家族结案：Yellowstone** | 「两套地址集」之争终结 |
| **④** | **AW86927 主机可达性结案（B33）** —— 真实 Linux Live 下解绑 `i2c_hid_acpi` 后，`i2c-0`/`i2c-1` 的 `0x5A/0x5B` **全 NACK**；`aw86927` 驱动只有 `of:` 别名 ⇒ **x86 ACPI 上不可能 probe** | 「直接接管触觉 IC」这条路关闭 |
| **⑤** | **微软规范层解释（B40）** —— 规范原文要求 Intensity 集合**不得**含 Manual Trigger ⇒ 本机配置**合规**；主机发起触觉所需三件（`0x0E/0x01` 集合 + Waveform 特征报表 + Manual Trigger 输出报表）**本机全缺** | 「为什么做不到」从推论升级为**规范依据** |
| **⑥** | **`7868Q` vs `7869` 解开** —— 容器与活体 `fw_version` **完全相同**（`1C 02 03 05`）；`7868Q` = 产品/模组标称，`7869` = IC 的 **4 位编号字段** | 消除一条长期「型号矛盾」 |
| **⑦** | **事故 + 新红线（纪律 153 / 154）** —— `0x4160` 命令码盲扫（扫到 `0x10/0x11/0x12`，与刷机语义**可能共享**）致触控板失效；IC 核心状态完好，已按官方退场序列恢复 | 新增两条**不可协商**红线 |
| **⑧** | **唯一没试过的注入面** —— 项目**只发过 `SET_FEATURE`**，**从未发过 Col02 的 OUTPUT 报表**；Windows 因 `out=0` 拦得住，**Linux `hidraw` 拦不住** ⇒ N1 实验面（工具已备） | 暴力线**唯一**未被结构性否决的面 |

> ⚠️ 这一轮的方法论教训也一并入库：纪律 **150**（断言「隐藏校验」前先穷尽厂商源码）、**151**（官方没有时，去找由官方源码派生的第三方工具）、**152**（引用属实 ≠ 优先级排对）、**155**（PE 段 dump 必先比 `VirtualSize` vs `RawSize`）。

## 五、证据分级（本项目最核心的纪律）

**本书所有结论都标了级别。不标级的陈述请按"背景信息"对待。**

| 级别 | 含义 |
|---|---|
| ✅ **【已确认】** | 有本机实测或一手规范原文 |
| ⚠️ **【半确认】** | 有实测但缺一个关键环节，或只有间接证据 |
| ⚠️ **【推断】** | 由排除法或旁证得出，无直接证据 |
| ❌ **【无证据】** | 完全没有材料 |

详见 [`method/08-evidence-grading.md`](method/08-evidence-grading.md)。

**从主机到马达，逐环节定级**（完整表见 `docs/08-findings/`）：

| 环节 | 级别 | 缺什么 |
|---|---|---|
| 主机 → GT7868Q | ✅ 已确认 | — |
| GT7868Q → TF100A | ⚠️ 半确认 | 走 I²C1 还是 USART1 未证；`PA3` 对端未证 |
| TF100A 内部（测压→检测→上报） | ✅ 已确认（限于该镜像） | 无法验证它就是设备实际运行的版本 |
| 谁决定震动 | ⚠️ 推断 | 排除法得出 |
| → AW86927 | ❌ **无证据** | 谁是它的 I²C 主机 / 哪条总线 / 哪个地址，四项全无 |
| AW86927 → 马达 | ⚠️ 半确认 | 本机马达型号未直接确认 |
| 点按震动与主机无关 | ✅ 已确认 | EC 只是"无证据"，不是"已排除" |
