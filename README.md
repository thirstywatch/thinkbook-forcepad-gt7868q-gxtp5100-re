# 汇顶 GT7868Q / GXTP5100 触控板主机控制逆向档案

> 对象：**联想 ThinkBook 14 G6+ IMH（21LD）** 上的压感触控板（ForcePad）—— 汇顶 **GT7868Q** 触控主控（Windows 侧实例名 `GXTP5100`）+ 钛方 TF100A 压力采集 + 艾为 AW86927 触觉驱动。

> 一句话：**在联想 ThinkBook 14 G6+ IMH（21LD）上，用纯软件方式让压感触控板（ForcePad）在滑动时产生震动反馈 —— 以及为什么这条路走不通、唯一剩下的路是什么。**

本仓库是一份**完整的逆向工程过程档案**：不只是结论，还包括每一步"怎么做的、用什么工具、得到什么、踩了什么坑、哪些结论后来被自己推翻了"。目标是让一个没有参与过本项目的人，能按文档独立复现全部分析过程。

## 二、最终结论（先读这个）

### ★ 核心结论

> **主机侧不存在"触发震动"的接口，设备也不监听主机的触觉命令。**

**决定性实测**：Linux live USB 里触控板指针完全不动（主机未建立通信），**点按照样震动** ⇒ 震动是模组内部自治行为。

### 三条独立硬事实（2026-10-02 闭合，互相独立、不需要抓包）

| # | 硬事实 | 依据 |
|---|---|---|
| 1 | **主机物理上发不出触觉命令** —— PTP 主体集合 `Col02` 的 `OutputReportByteLength = 0`。全设备只有厂商集合 `Col04` 有 `Out=65`，且它只有本项目和汇顶官方工具会用 | 描述符层 |
| 2 | **设备栈上没有任何第三方组件** —— 四集合 `UpperFilters`/`LowerFilters` 全空 ⇒ 链上只有 inbox `hidclass` + `hidi2c` | 设备栈层 |
| 3 | **无厂商触控板服务在跑** —— 全系统 311 进程，0 个 Goodix / 联想触控板相关进程 | 进程层 |

### 三层关卡（全部封死）

| 层 | 关卡 | 状态 |
|---|---|---|
| 第 1 层 | HID 描述符未声明触觉能力（无 Manual Trigger / Waveform / Duration） | ❌ 封死 |
| 第 2 层 | `hidi2c.sys` 独占 SPB 连接，微软规定同一外设连接同时只能一家持有 | 🔒 硬阻断 |
| 第 3 层 | 设备固件侧没有主机可调用的"触发"命令 | ❌ 封死 |

### ★★★ 但有一条反向证据：主机确实"碰得到"震动路径 —— 只是方向是抑制

> **高频读 `Col04` 会抑制【所有】震动反馈（按下 + 抬起都被抑制）。**
> 实测：89.7 秒全量 dump 期间一直按住触控板 → **期间无任何震动**，停止读取后恢复。

这是全项目**唯一证明「主机能影响震动路径」的现象**：

| 项 | 内容 |
|---|---|
| 推论 | 震动触发**不在内存数据层面**，在**固件 ↔ 主机 I²C 通信**层面 ⇒ 解释了"为什么写内存永远无效"（固件根本不看那块内存） |
| 开放方向 | 既然读能**抑制**，改变读的**时序/地址/长度**能否**促进**（触发）？这是缺口 B 唯一有正面证据的方向 |

> 🔴 **2026-10-03 更正**：早期表述"只抑制**按下**震动、**不影响松开**"**是错的**。
> 实际抑制的是**所有**震动反馈；"松手才震"是**读停止后恢复**，不是"松开这一路免疫"。

详见 [`method/METHOD.md`](method/METHOD.md) 第 6 章。

### 纯软件路：已终止。唯一剩下的路

| 路线 | 状态 |
|---|---|
| HID 标准触发 | ❌ 无 Manual Trigger（`Col02 Out=0`） |
| Col04 内存写 / 厂商命令 | ❌ 固件不消费 / 39 条命令全表无马达入口 |
| GT7868Q 阈值表（`0x5B80` 区） | ❌ 老线已排除 |
| 主机侧 I²C 通道（5 条总线） | ❌ **5/5 闭合**（要么扫清、要么主机根本不可访问） |
| EC 是否参与震动 | ✅ 已测：否（在本探针灵敏度下）→ 关闭 |
| **TF100A 固件灵敏度补丁「40 → 8」** | ✅ **唯一有字节级目标的路径** —— 补丁镜像已生成，待刷写 |

> **TF100A 破局点**：震动判据 = `|基线 − 当前| > 40`，`40` 是两处 Thumb 指令的立即数 `0x28`。
> **改成 8 ⇒ 判据变灵敏 ⇒ 滑动时手指压力的自然波动反复跨过判据 ⇒ 反复触发点按链路 ⇒ 滑动震动**（设备自发，完全不碰主机协议）。
> 载体 `TB14P_GT7868Q_14030522_20240202.BIN`，加载基准 `0x08005000` ↔ file `0x19ABC`；
> 改动点 `0x1A54C`（`28 31` → `08 31`）与 `0x1A578`（`28 39` → `08 39`），**仅 2 字节**。
> 🔴 BIN 本身**不入库**（厂商固件派生品）⇒ 改用可复现脚本
> **[`tools/firmware/make_tf100a_sens_patch.py`](tools/firmware/make_tf100a_sens_patch.py)**，
> 已用真实镜像验证：**输出与手工补丁件逐字节相同**。

### ★★★ 2026-10-03 收官的两条最硬结论

| # | 结论 | 分量 |
|---|---|---|
| **①** | **主机侧碰不到 AW86927 —— 原因不是工具不行，是它【平时断电】**。<br>五条 I²C 总线全部排查完毕，`0x5A` **不在任何一条上**；<br>全 DSDT 扫描无任何设备声明 `0x5A`/`0x5B`。<br>⇒ 触觉 IC 只在需要播放时由 GT7868Q 上电，主机永远赶不上那个窗口 | 把"为什么找不到"从"没扫到"升级为**结构性不可能** |
| **②** | **写注入系统性验证：全部无效**。<br>32 KB 可写空间内所有候选地址逐一写回验证，**无一生效**。<br>⇒ 与"高频读能抑制震动"互证：**震动触发不在内存数据层面**，<br>固件根本不消费那块内存 | 关闭了"改内存参数"这条路的最后一格 |

> 这两条合起来回答了本项目最初的问题：**不是没找到那扇门，是门在设备内部。**

**本项目有过两次真机事故（触控板输入冻结、IC 被打挂）。以下红线永久生效，优先级高于"推进进度"。**

```yaml
红线层（四条刷机命令，不是三条，全部绝不碰）:
  00 10   switch to patch   ← 进入刷机模式
  00 11   start update      ← 进入刷机模式
  0E 12   load flash        ← ★ 真正写 flash，最危险
  0E 13   restart           ← 重启

其它:
  - 禁止批量轮询 Col04
  - 单次事务 ≤ 32 B，间隔 ≥ 500 ms
  - 0xA2 是回复类，禁发
  - 未获明确同意不动 bcdedit
  - 只读优先；写入类命令置于最后
```

## 五、证据分级（本项目最核心的纪律）

**本书所有结论都标了级别。不标级的陈述请按"背景信息"对待。**

| 级别 | 含义 |
|---|---|
| ✅ **【已确认】** | 有本机实测或一手规范原文 |
| ⚠️ **【半确认】** | 有实测但缺一个关键环节，或只有间接证据 |
| ⚠️ **【推断】** | 由排除法或旁证得出，无直接证据 |
| ❌ **【无证据】** | 完全没有材料 |

详见 [`method/08-evidence-grading.md`](method/08-evidence-grading.md)。

**从主机到马达，逐环节定级**（完整表见 `docs/08-findings/`）：

| 环节 | 级别 | 缺什么 |
|---|---|---|
| 主机 → GT7868Q | ✅ 已确认 | — |
| GT7868Q → TF100A | ⚠️ 半确认 | 走 I²C1 还是 USART1 未证；`PA3` 对端未证 |
| TF100A 内部（测压→检测→上报） | ✅ 已确认（限于该镜像） | 无法验证它就是设备实际运行的版本 |
| 谁决定震动 | ⚠️ 推断 | 排除法得出 |
| → AW86927 | ❌ **无证据** | 谁是它的 I²C 主机 / 哪条总线 / 哪个地址，四项全无 |
| AW86927 → 马达 | ⚠️ 半确认 | 本机马达型号未直接确认 |
| 点按震动与主机无关 | ✅ 已确认 | EC 只是"无证据"，不是"已排除" |
